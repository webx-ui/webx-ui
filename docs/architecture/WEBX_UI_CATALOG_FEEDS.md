# Товарные фиды каталога — `module-catalog-feeds`

Статус: предложена на приёмку человеку (webx-ui#94). Реализация — отдельными этапами по §14.
Архитектура семейства — [`WEBX_UI_CATALOG.md`](WEBX_UI_CATALOG.md), ядро —
[`WEBX_UI_MODULE_CATALOG.md`](WEBX_UI_MODULE_CATALOG.md), обмен —
[`WEBX_UI_MODULE_CATALOG_EXCHANGE.md`](WEBX_UI_MODULE_CATALOG_EXCHANGE.md), шаблоны уведомлений —
[`WEBX_UI_MODULE_NOTIFICATIONS.md`](WEBX_UI_MODULE_NOTIFICATIONS.md) §7.

Сайтам на каталоге нужны выгрузки товаров: Google Merchant, маркетплейсы и агрегаторы, разовые
запросы «клиенту нужен JSON или XML с такими-то полями». Выгрузка настраивается в панели и через
MCP, без кода. Первый заказчик — магазин, которому фид нужен для Google-рекламы (Shopping и
Performance Max).

## 2. Общий Mustache

### 2.1. Что есть сейчас

Сервер: `WebxUi\Notifications\Templates\Template` — проверка, `usages()`, `render()` с замыканием
экранирования; `TemplateError`; `Html` — экранирование, разбор тегов и `plain()`. `Template` не знает
про уведомления, кроме ключей словаря `webx-notifications::errors.*`. Экранирование уже стратегия:
`render()` принимает `Closure`, провайдер отдаёт свою.

Браузер: `packages/core/.../CodeEditor/mustache.ts` — подсветка, `mustacheCompletions()`,
`mustacheProblems()`. В `packages/module-notifications/src/render.ts` — разбор через `mustache.js`,
обход дерева по правилам сервера и то, что привязано к провайдерам.

### 2.2. Что куда переезжает

| Сейчас                                                              | Куда                                     | Заметка                                                    |
| ------------------------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------- |
| `Templates\Template`, `TemplateError`                               | `WebxUi\Templates\`                      | словарь — `webx-templates::errors.*`                       |
| `Templates\Html`                                                    | `WebxUi\Templates\Html`                  | `plain()` нужен фиду для `description_text`                |
| `Events\Variable`, логика `EventDefinition::knows()`                | `WebxUi\Templates\Variable`, `Variables` | один источник подсказок: имя, подпись, пример, поля списка |
| `renderTemplate`, `knows`, `escapeHtml`, `htmlPlain` из `render.ts` | `@webx-ui/core`                          | вместе с зависимостью `mustache`                           |
| `snippetOf` из `variables.ts`                                       | `@webx-ui/core`                          | что вставляет клик по переменной                           |
| новое: `Escapes` (§2.4), `Template::compile()` (§2.5)               | `WebxUi\Templates\`, в браузере — `core` |                                                            |

Остаётся в `module-notifications`: `Renderer`, `Provider::escape`, `TelegramMarkup`, `EmailMarkup`,
`renderMessage`, `escapeFor`, `isHtmlLetter`, `TemplateField.vue`. Поле шаблона не выносим: контекст
канала и контекст фида разные, общая у них логика, и она уже в `core`.

Новый язык редактора не нужен: для `xml` берём `mustache-html`, для остальных форматов — `mustache`.

### 2.3. Куда и почему

**Сервер — новая библиотека `webx-ui/templates`.** Правило имён: что живёт без панели, — библиотека
без префикса. Рендер работает в очереди и не касается панели. В `module-admin` он тянул бы
`mustache/mustache` всем сайтам, а модулю, которому нужен только рендер, — всю панель. Цена — четыре
места в `php/` и новое зеркало для Packagist.

**Браузер — `@webx-ui/core`, новый npm-пакет не заводим.** Язык, автокомплит и проверка уже там, а
рендер предпросмотра — их сосед. Цена — рантайм-зависимость `mustache` у `core` (одна маленькая
библиотека). Отдельный пакет потребовал бы первой публикации руками ради нескольких функций.
Экспорт — из основного входа: подпути у `core` сейчас нет, заводить его ради этого незачем.

### 2.4. Экранирование

`Escapes::for(string $format, array $options): Closure`, та же таблица в браузере. Значение
проходит стратегию один раз; текст шаблона не экранируется.

| Формат | Что делает                                                                                                                                     |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `xml`  | `&`, `<`, `>`, `"`, `'` — сущностями; вычищает управляющие символы 0–31, кроме 9, 10, 13, а также U+FFFE и U+FFFF: парсер XML 1.0 их не примет |
| `json` | экранирование строки JSON без внешних кавычек: кавычки пишет шаблон                                                                            |
| `csv`  | значение с разделителем, кавычкой или переводом строки — в кавычки, внутренняя кавычка удваивается; разделитель — настройка фида               |
| `text` | как есть                                                                                                                                       |

- **JSON одинаков на сервере и в браузере.** PHP — `JSON_UNESCAPED_UNICODE | JSON_UNESCAPED_SLASHES |
JSON_UNESCAPED_LINE_TERMINATORS`: без последнего флага PHP экранирует U+2028, а `JSON.stringify` —
  нет.
- **Сырого вывода нет** (решение 2): `{{{x}}}` и `{{&x}}` по-прежнему читаются как `{{x}}`.
- **HTML в CDATA.** Решение 2 запрещает сырой вывод, а площадки просят HTML в CDATA. Значение
  `Cdata` — маленький класс-обёртка: `xml`-стратегия печатает его целиком как
  `<![CDATA[…]]>`, разбивая `]]>` внутри и вычищая те же символы. Реестр даёт такой вариант для
  переменной типа `html`: `{{description_cdata}}`. Шаблон пишет
  `<description>{{description_cdata}}</description>`, сырого вывода не появляется. Пустая
  `Cdata` — `null`, поэтому `{{#description_cdata}}` работает как обычно. `Template` начинает
  принимать в значениях `Cdata`; в браузер она приходит как `{ "$cdata": "…" }`.
- **Переменная внутри литерала `<![CDATA[ … ]]>` в шаблоне — отказ** с подсказкой про `_cdata`:
  стратегия не видит, где стоит тег, и значение экранировалось бы дважды. Отвергнутый вариант —
  экранировать по положению тега: движку Mustache `escape` известно только значение, а разрезать
  шаблон на границах CDATA нельзя, потому что их пересекают секции.

### 2.5. Что нужно добавить для потока

`Template::render()` на каждый вызов заново разбирает шаблон и создаёт `Engine`. На письмо это
незаметно, на сотню тысяч товаров — нет. Новый `Template::compile($template, $escape): Compiled`
разбирает и проверяет один раз; `Compiled::render($values): string` только подставляет значения.
`render()` остаётся и работает через него. Неизвестные имена при сборке не ищем: их поймала проверка
при сохранении (§8).

Три ограничения движка, которые спека учитывает:

- **`{{.}}` запрещён** (`Template::NAME`), поэтому элемент списка — всегда карта:
  `{{#images}}{{url}}{{/images}}`, а не список строк.
- **Имя — не больше одной точки:** `shop.name`, `property.color`.
- **Секция решает как PHP:** `'0'` — пусто. Проверять цену секцией безопасно только потому, что товар
  без цены отсеян (§5.3), а нулевая скидка переменной `sale_price` не задаётся.

Запятая внутри списка товара разделителем фида не решается: Mustache не знает последнего элемента.
Поэтому каждый элемент любого списка получает поля `first` и `last` (`'1'` или `''`):
`{{#images}}{{^first}},{{/first}}"{{url}}"{{/images}}`.

### 2.6. Как переходят уведомления

Тесты не теряются, потому что переезд идёт одним этапом и без правки поведения:

1. `TemplateTest` переезжает в `php/packages/templates/tests/` как есть, меняется только namespace.
2. `PreviewParityTest`, `render.test.ts` и `tests/fixtures/render.json` остаются в уведомлениях:
   они проверяют сообщение целиком, и теперь — ещё и общий код.
3. Новый общий файл случаев `php/packages/templates/tests/fixtures/render.json` читают тест
   библиотеки и тест в `core`: `first`/`last`, `Cdata`, четыре формата экранирования.
4. Ключи `errors.template-*` переезжают в словарь библиотеки; `webx-templates` добавляется в
   `webx-localization.namespaces`. `PanelTest` и `McpTest` уведомлений держат слова под полем.
5. `module-notifications` получает `require` на `webx-ui/templates` и теряет `mustache/mustache`, npm —
   теряет `mustache`. Классы внутри монорепы никто больше не использует (проверено поиском), алиасы
   не нужны; смена namespace — в changeset.

### 3.2. Связанные таблицы

- `catalog_feed_exclusions` — `feed_id`, `product_id`, `created_at`; ключ по паре, индекс на
  `product_id`, каскад с обеих сторон. Ручные исключения (§5.2): настройка фида, а не карточки
  товара. Таблица, а не JSON, потому что список бывает длинным и проверяется в запросе отбора.
- `catalog_feed_categories` — `feed_id`, `category_id`, `taxonomy_item_id` (null), `value`
  (string(255), null — значение, вписанное вручную); ключ по паре (§6.2).
- `catalog_feed_taxonomies` — `id`, `key`, `locale`, `version`, `source`, `imported_at`; ключ по паре
  `key`, `locale`.
- `catalog_feed_taxonomy_items` — `taxonomy_id`, `external_id` (string(32)), `path` (string(500));
  уникальный ключ `taxonomy_id`, `external_id`; индекс для поиска по `path`.
- `catalog_feed_builds` — журнал (§7.6).
- `catalog_feed_build_rejects` — `build_id`, `product_id`, `reason`; не больше `max_rejects` строк.

### 3.3. Источники `custom_label_0…4`

`custom_labels` — объект с ключами `0`…`4`. Каждой метке назначается один источник:

```json
{
  "0": { "type": "label", "labels": ["sale", "new"] },
  "1": {
    "type": "price_range",
    "ranges": [{ "to": 50, "value": "low" }, { "to": 200, "value": "mid" }, { "value": "high" }]
  },
  "2": { "type": "property", "property": "material" },
  "3": { "type": "constant", "value": "autumn-campaign" },
  "4": { "type": "none" }
}
```

| Тип           | Значение                                                                      |
| ------------- | ----------------------------------------------------------------------------- |
| `label`       | код первой метки товара из списка, в порядке списка; нет такой — пусто        |
| `price_range` | значение первого диапазона, куда попала текущая цена; границы задаются в фиде |
| `property`    | значение свойства по коду, на языке фида; у нескольких значений — первое      |
| `constant`    | постоянное значение                                                           |
| `none`        | пусто, тег не выводится                                                       |

Значение обрезается до 100 символов. Google принимает не больше 1000 разных значений каждой метки на
аккаунт, поэтому сборка считает разные значения и пишет предупреждение в журнал, если их больше
(§7.6). Посчитать можно только в пределах фида, а не аккаунта.

### 3.4. Источники `mpn` и `group_id`

`sources.mpn`: `{ "type": "field" }` по умолчанию — поле товара `mpn` (решение 16), или
`{ "type": "property", "property": "<код>" }` — свойство товара. `sources.group_id` устроен так же,
см. §4.5.

## 4. Переменные

### 4.1. Откуда берутся

Реестр `ProductVariables` живёт в ядре, а не в фидах: спутнику иначе пришлось бы знать про фиды или
фидам — про спутника. Значения считаются пачкой на страницу товаров, как `export()` у колонок обмена.
Колонки обмена попадают в реестр сами (решение 5). Если переменная зарегистрирована явно, она сильнее
колонки с тем же именем: колонка `brand` отдаёт слаг для обратного импорта, а площадке нужно название.

### 4.2. Товар: колонки обмена

Язык — язык фида, `name@de` не нужен: другой язык — другой фид.

| Переменная                         | Значение                                                                   |
| ---------------------------------- | -------------------------------------------------------------------------- |
| `sku`, `external_id`, `slug`       | как в обмене                                                               |
| `barcode`                          | основной штрихкод как есть                                                 |
| `mpn`                              | артикул производителя; источник заменяется настройкой (§3.4)               |
| `barcodes`                         | список, поле `value`: дополнительные штрихкоды                             |
| `name`, `summary`                  | на языке фида                                                              |
| `category`, `categories`           | путь основной категории; пути через `;`                                    |
| `price`, `old_price`               | числа без валюты, точка, два знака                                         |
| `unit`, `priority`, `is_published` | как в обмене                                                               |
| `brand`                            | название бренда (спутник)                                                  |
| `labels`                           | список, поля `code`, `name` (спутник)                                      |
| `stock`, `stock_name`              | код и название статуса (спутник); при пустой строке — статус по умолчанию  |
| `is_purchasable`                   | `'1'` или `''` (спутник)                                                   |
| `property.<код>`                   | значение свойства, несколько — через `;`; семейство `property.*` (спутник) |

Заголовок свойства в обмене — код с `_` вместо `-`; имя переменной пишется так же.

### 4.3. Товар: вычисляемые

| Переменная                               | Значение                                                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------------------------ |

Абсолютные адреса строятся в очереди, где запроса нет: от `app.url`. `ProductImage::url()` на диске
`/storage/…` даёт относительный адрес, переменная достраивает его так же, как `images` в экспорте.

### 4.4. Как модуль или сайт добавляет свою

```php
$this->callAfterResolving(ProductVariables::class, function (ProductVariables $variables): void {
    $variables->register(new WarrantyVariable);
});
```

```php
interface ProductVariable
{
    public function describe(): Variable;   // имя, подпись, пример, поля списка, тип (text, html, list)

    /** @return array<int, string|list<array<string, string>>|Cdata> id товара → значение, пачкой */
    public function values(Collection $products, string $locale): array;
}
```

Семейство имён (`property.*`) приходит провайдером, как `ExchangeColumnProvider`. Занятое имя —
исключение при регистрации, как у колонок. Значения пачкой обязательны: переменная, которая ходит в
базу на товар, превращает сборку в N+1. Автокомплит, проверка неизвестных имён и ресурс MCP берут этот
же реестр.

Колонка обмена с закрытыми данными объявляет маркер `PrivateColumn` и в реестр не попадает (§13).

### 4.5. Варианты и `group_id`

Группировки товаров пока нет: `module-catalog-groups` — волна B, не начат. Каждый вариант сегодня —
самостоятельный товар. Поэтому:

- без настройки `group_id` пустой и `item_group_id` не выводится;
- `sources.group_id` с типом `property` берёт значение свойства, которое объединяет варианты;
- будущий модуль групп регистрирует свою `group_id`, и она становится значением по умолчанию.

Подробнее — §15, вопрос 4.

### 4.6. Шапка и подвал

Товарных переменных здесь нет, контекст свой.

| Переменная                                  | Значение                                                                   |
| ------------------------------------------- | -------------------------------------------------------------------------- |
| `shop.name`, `shop.url`, `shop.description` | название из настроек сайта, иначе `app.name`; адрес; описание фида         |
| `shop.email`, `shop.phone`                  | из контактов `module-settings`, если модуль стоит                          |
| `feed.name`, `feed.locale`, `feed.currency` | настройки фида                                                             |
| `generated_at`                              | дата сборки, ISO 8601                                                      |
| `generated_at_rfc822`                       | дата сборки для RSS                                                        |
| `currencies`                                | список, поля `code`, `rate`; в первой версии одна строка, `rate` = `1`     |
| `categories`                                | список категорий, попавших в фид: `id`, `parent_id`, `name`, `path`, `url` |
| `products_count`                            | сколько товаров записано                                                   |

В `categories` входят категории товаров фида вместе с предками: без предка `parent_id` в YML вёл бы в
никуда. Шапка зависит от того, что станет известно только после товаров, отсюда порядок сборки в §7.1.

## 5. Отбор товаров

Основа всегда одна: `Product::visible()` — опубликован и лежит в видимой категории, удалённые
отсечены (§13). Дальше три слоя решения 15.

### 5.1. Слой 1 — фильтр фида

```json
{
  "categories": { "include": [12, 40], "exclude": [41] },
  "brands": [3],
  "price": { "min": 10, "max": 5000 },
  "labels": ["sale"],
  "properties": { "p.17": ["214", "215"] },
  "only_in_stock": false
}
```

- **Запрос к базе, а не к движку поиска.** Сборка идёт в фоне страницами по курсору `id`, индекс ей
  не нужен, а окно Manticore мешало бы. Нужные условия уже есть у каждого фасета: `Facet::applySql()`.
  Выбор тот же, что в `catalog_products_list`, потому что те же фасеты и `normalise()`.
- **Включить ветку** — фасет `category`: дерево отвечает за потомков. **Исключить ветку** — тот же
  `applySql()` во вложенном запросе под `whereNotExists`. Ядро для этого не меняется; индексы под
  такой запрос проверяются `EXPLAIN` на MariaDB на этапе 5.
- **Ключи фасетов берём из реестра.** Спутник не установлен — его фасета нет, и фильтра в форме тоже.
- **Значения свойств — только через фасеты**, то есть свойства с флагом «в фильтре». См. §15, вопрос 3.
- **«Только в наличии»** — опция, по умолчанию выключена (решение 15). Проверяется по `is_purchasable`
  после загрузки страницы: свой статус «можно купить» знает только спутник наличия, а фид говорит с
  ним через реестр. Без спутника опции нет. В счётчиках сборки — `filtered`, не отсев.

### 5.2. Слой 2 — ручные исключения

`catalog_feed_exclusions` проверяется в том же запросе. Товар не попадает в **этот** фид и остаётся в
других. Причина отсева не пишется: это воля человека. Журнал показывает общее число.

### 5.3. Слой 3 — автоматический отсев

| Причина    | Когда                                       |
| ---------- | ------------------------------------------- |
| `no_price` | цена пуста или не больше нуля               |
| `no_image` | нет ни одной картинки (ролики не считаются) |
| `no_name`  | нет названия на языке фида                  |

- **Название — строго на языке фида.** `displayName()` не годится: он подставляет `#id`, а перевод с
  запасным языком отдал бы текст на другом языке. Нужен `getTranslation('name', $locale, false)`.
- Счётчики причин — в сборке, первые `max_rejects` товаров — в `catalog_feed_build_rejects` (§7.6).
- `availability` не отсеивает: «нет в наличии» выгружается как `out_of_stock` (решение 14).
- Проблемы, которые не убирают товар, — предупреждения журнала (§7.6). Причин отсева больше трёх не
  становится: решение 15 их перечисляет.

## 6. Маппинги

### 6.1. Склад → значение площадки

`stock_map`: код статуса → значение, `{ "in-stock": "in_stock", "on-order": "backorder" }`.

- **По умолчанию:** статус с `is_purchasable` — `in_stock`, без него — `out_of_stock` (решение 14).
  Человек меняет значение любого статуса.
- Статус без строки в `stock_map` берёт значение по умолчанию; новый статус не ломает сборку.
- Значение `preorder` у Google требует `availability_date`, которого в каталоге нет. Такой выбор —
  предупреждение в форме.
- Спутник наличия не установлен: у всех товаров значение `options.default_availability`, по умолчанию
  `in_stock`.

### 6.2. Категория → категория площадки

Значение ищется вверх по дереву: своё, иначе ближайшего предка, иначе пусто. Поэтому маппить можно
ветками, а не каждый лист. Для товара берётся основная категория.

**Справочник Google** лежит в `catalog_feed_taxonomy_items`, по строке на категорию и язык; около 5,6
тысячи строк на язык. Источник — официальный файл
`https://www.google.com/basepages/producttype/taxonomy-with-ids.<язык>.txt`, строки вида
`1 - Animals & Pet Supplies`, первая строка — версия (`# Google_Product_Taxonomy_Version: 2021-09-21`).

Импорт — тремя путями, один разборщик:

1. **По адресу** — очередью; адрес подставлен, язык из настроек фида.
2. **Файлом** — загрузка кусками через `/api/cms/uploads`, назначение `catalog.feed-taxonomy`.
3. **Вручную** — поле значения принимает id или путь без справочника.

Файла есть не на каждом языке: проверено, `uk-UA` отвечает 404, а `en-US`, `ru-RU`, `de-DE` есть.
Нет своего языка — берём `en-US`: id общие для всех языков, и фид отправляет id. Панель предупреждает,
что подписи на английском. В фид идёт `external_id`: Google рекомендует id, а не путь.

**Немаппленая категория:** `google_product_category` пуст, тег не выводится, товар остаётся в фиде,
журнал считает `unmapped_category`. Атрибут у Google необязательный, и Google назначает категорию сам.

`product_type` маппинга не требует — это путь нашей категории (решение 14).

## 7. Сборка и доставка

### 7.1. Запись потоком

Задание `BuildFeed` идёт страницами по `chunk` товаров, курсор — последний `id`:

```
page(chunk):
  products = selection.after(cursor).with(нужные связи).limit(chunk)
  values   = variables.values(products, locale)    # только те, что шаблон использует
  for product:
    reject?          -> счётчик, строка журнала
    only_in_stock?   -> filtered
    append(separator if not first), append(item.render(values))
    запомнить категорию, значения меток
  cursor, body_bytes, счётчики -> строка сборки (lockForUpdate)
  RequestMemo::flush()
```

- **Шапка пишется последней.** `categories` и `products_count` известны только после товаров. Тело
  пишется во временный файл, потом собирается `head + body + foot` потоковым копированием. Диску на
  время сборки нужно два размера файла.
- **Считаем только то, что шаблон использует:** `Template::usages()` даёт имена, реестр отдаёт нужные
  переменные. Плоскому фиду из пяти полей не нужны запросы к свойствам.
- **Память не растёт.** Шаблон скомпилирован один раз (§2.5), страница отпускается. `RequestMemo` в
  долгом задании сам не чистится, а `Stock::of()` кладёт туда по ключу на страницу, поэтому чистим его
  после каждой страницы.
- **Очередь как у импорта:** задание работает `job_seconds`, потом ставит следующее. Повтор безопасен:
  курсор и `body_bytes` пишутся вместе, а задание начинает с обрезки временного файла до `body_bytes`,
  так что упавшая страница не удваивается.
- **Одна сборка на фид.** Новая не ставится, пока есть `queued` или `running`; зависшая дольше
  `stale_minutes` закрывается как `failed`. Сборка на больших каталогах требует живой очереди, как
  массовые действия.

### 7.2. Проверка собранного

До подмены файла, потоком: XML — `XMLReader` по всему файлу; JSON — каждый товар через `json_decode`
по мере записи, шапка и подвал на пробе; CSV — число полей в строке. Провал — сборка `failed`, старый
файл продолжает отдаваться. Площадка лучше получит вчерашний файл, чем битый.

### 7.3. Когда пересобирать

Сторож `webx:catalog:feeds` — раз в минуту, `onOneServer`, только решает и ставит задания.

- **Расписание:** `manual`, `hourly`, `every_6_hours`, `daily` со временем.
- **После изменений** (`rebuild_on_change`). Сигнал — поколение каталога (`StorefrontCache::generation()`,
  §8.4 ядра): его двигает любой путь записи, включая `touch`, и нового шва не нужно. Сравнивается с
  `built_generation`.

Защита от сборки на каждый чих:

| Правило         | Значение по умолчанию | Смысл                                                                      |
| --------------- | --------------------- | -------------------------------------------------------------------------- |
| `quiet_minutes` | 10                    | ждём, пока каталог успокоится: импорт двигает поколение на каждой пачке    |
| `min_interval`  | 60 минут              | не чаще этого, сколько бы ни менялось                                      |
| `max_wait`      | 360 минут             | после первого изменения собираем не позже, даже если каталог не успокоился |
| импорт идёт     |                       | пока прогон обмена `running`, ждём, но не дольше `max_wait`                |

Поколение времени не хранит, поэтому сторож сам записывает `dirty_since` и обновляет его, когда видит
новое поколение. Поколение двигают и посадочные, то есть бывают лишние сборки. Они безвредны: одинаковое
содержимое даёт тот же ETag, и `Last-Modified` не меняется (§7.5).

### 7.4. Подмена файла

Файл каждой сборки — свой: `catalog-feeds/<feed>/<build>.<ext>`. Подмена — одно обновление
`current_build_id`. Это атомарно на любом диске, включая S3, где `rename` нет. Читатель, начавший
скачивание, дочитает старый файл: предыдущие `keep_files` файлов остаются. Диск — `feeds.disk`; временный
файл всегда на локальном диске, иначе дописывать нечем.

### 7.5. Адрес и отдача

`GET /feeds/{key}.{ext}`, обычный маршрут Laravel. Приставка `feeds` настраивается и добавляется в
`webx-routing.reserved`: маршрут с параметром `Reserved` по адресу не узнаёт. Расширение — по формату,
потому что Google требует `.xml` в имени файла. Адрес не меняется при правках фида; смена формата с тем же
ключом отвечает 301 на новое расширение.

- **Ключ** — 40 случайных символов, создаётся один раз, правки его не меняют (решение 8; перевыпуск —
  §15, вопрос 2).
- **Файл отдаётся готовым.** Запрос никогда не собирает: нет готового файла — 404 и `Retry-After`.
- **ETag** — sha256 файла, считается при сборке. **Last-Modified** — время сборки, которая впервые дала
  это содержимое: при том же sha256 новая сборка наследует время старой.
- `If-None-Match` и `If-Modified-Since` — 304 без чтения файла; `HEAD` поддержан.
- Заголовки: тип по формату с `charset=utf-8`, `X-Robots-Tag: noindex`, `Cache-Control: private,
max-age=0, must-revalidate`.
- Сжатие — дело прокси; своего `.gz` в первой версии нет.

### 7.6. Журнал сборок

`catalog_feed_builds`:

| Колонка                                  | Что                                                              |
| ---------------------------------------- | ---------------------------------------------------------------- |
| `feed_id`, `status`                      | `queued`, `running`, `done`, `failed`                            |
| `trigger`                                | `manual`, `schedule`, `change`, `mcp`                            |
| `queued_at`, `started_at`, `finished_at` |                                                                  |
| `selected`, `written`, `filtered`        | сколько прошло запрос, записано, снято опцией «только в наличии» |
| `excluded`                               | сколько снято ручными исключениями                               |
| `rejected`                               | json: `{ "no_price": 12, "no_image": 40, "no_name": 3 }`         |
| `warnings`                               | json, счётчики предупреждений (ниже)                             |
| `error`                                  | текст ошибки сборки                                              |
| `path`, `bytes`, `etag`, `content_at`    | файл                                                             |
| `cursor`, `body_bytes`, `generation`     | служебное                                                        |

Предупреждения не убирают товар: `unmapped_category`, `no_brand`, `no_description`, `invalid_gtin`
(штрихкод есть, но это не GTIN), `small_image` (меньше 500×500 по `width`, `height` галереи),
`label_values` (больше 1000 разных значений метки), `text_cut` (название или описание обрезаны).

Чистка — `webx:catalog:feeds-prune`, ежедневно: журнал старше `keep_builds_days`, файлы сверх
`keep_files`. Текущая сборка не удаляется никогда. В `webx:doctor` — `FeedsCheck`: фид с провалом
последней сборки, файл старше двух периодов расписания, нет живой очереди, размер близок к лимиту,
сайт закрыт (§13).

### 7.7. Лимиты и время

```php
'feeds' => [
    'chunk' => 500,
    'job_seconds' => 60,
    'disk' => env('WEBX_CATALOG_FEEDS_DISK', 'local'),
    'prefix' => env('WEBX_CATALOG_FEEDS_PREFIX', 'feeds'),
    'max_bytes' => 3 * 1024 ** 3,     // Google принимает файл меньше 4 ГБ
    'max_rejects' => 1000,
    'keep_files' => 2,
    'keep_builds_days' => 30,
    'stale_minutes' => 30,
    'quiet_minutes' => 10,
    'min_interval' => 60,
    'max_wait' => 360,
    'sample' => 5,                    // товаров в пробной сборке, 3–5
],
```

**Цель, а не замер:** 100 тысяч товаров за 10 минут в один воркер, память до 128 МБ и без роста,
запросов на страницу — постоянное число, независимое от размера страницы. Замер на этапе 5 ложится в
раздел «Выпуск»; ориентир — экспорт и импорт обмена на 93 тысячах товаров.

## 8. Проверка и предпросмотр

### 8.1. При сохранении

Шаги по порядку, первый провал — отказ 422 под нужной частью шаблона:

1. **Синтаксис Mustache** каждой части: те же `errors.template-*`, что в уведомлениях.
2. **Неизвестные переменные:** имя должно быть в реестре для этой части. Товарная переменная в шапке —
   ошибка; внутри секции списка годятся поля списка.
3. **CDATA:** переменная внутри литерала CDATA — отказ (§2.4).
4. **Пробная сборка** на `sample` настоящих товарах, тем же кодом, что сборка (§7.1), с настройками из
   формы. Если подходящих товаров нет, шаг 5 идёт по шапке и подвалу, и ответ несёт предупреждение.
5. **Разбор:** XML — `libxml` с внутренними ошибками; JSON — парсер с позицией (`seld/jsonlint`): у
   `json_decode` номера строки нет; CSV — одинаковое число полей.

Ошибка разбора содержит номер строки собранной пробы, часть (`head`, `item`, `foot`) и строку этой
части, если её можно определить: сборщик помнит смещение каждой части. Невалидный фид не сохраняется
(решение 9).

Пустой шаблон `item` — отказ. Фид с `driver` проверяет сам класс (§10).

### 8.2. Предпросмотр

`POST catalog/feeds/preview` получает значения формы и отвечает так же, как шаги 1–5: текст пробы,
ошибки, предупреждения, сколько товаров подошло и сколько отсеяно по причинам. Панель и MCP зовут одно
и то же. Можно назвать товары: `product_ids` — посмотреть конкретные (они проходят отбор и отсев; иначе
ответ объяснит, почему товар не попадёт).

### 8.3. Совпадение с сервером

Как в уведомлениях (§7.5 их спеки): панель один раз получает с сервера значения пробы
(`POST catalog/feeds/sample`), дальше рендерит в браузере на каждое нажатие. Переменные считает только
сервер, браузер лишь подставляет и экранирует. Разбор в браузере — `DOMParser` и `JSON.parse`, это
подсказка; решает сервер. Расхождение рендера ловит общий файл случаев (§2.6).

**Источники, сверено 05.11.2026:**

[`gtin`](https://support.google.com/merchants/answer/6324461?hl=en),
[`identifier_exists`](https://support.google.com/merchants/answer/6324478?hl=en),
[`custom_label_0…4`](https://support.google.com/merchants/answer/6324473?hl=en),
[`google_product_category`](https://support.google.com/merchants/answer/6324436?hl=en),
[`image_link`](https://support.google.com/merchants/answer/6324350?hl=en),
[`description`](https://support.google.com/merchants/answer/6324468?hl=en),
[обновление по расписанию](https://support.google.com/merchants/answer/1219255?hl=en) (эта страница
прочитана только в выдаче поиска). Страницы меняются: на этапе пресета сверить заново.

**Структура.** RSS 2.0, корень с `xmlns:g="http://base.google.com/ns/1.0"`, в `channel` — `title`,
`link`, `description`, товары — `item`. Атрибуты с префиксом `g:`, без него значения Google
игнорирует. Пустые атрибуты убираются, поэтому необязательные теги стоят в секциях. Файл содержит все
товары: товар, исчезнувший из файла, исчезает из Merchant Center. Имя файла оканчивается на `.xml`.

**Обязательные атрибуты**

| Атрибут        | Ограничение                                                                                       | Наша переменная                                                      |
| -------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `id`           | до 50 символов, стабилен между обновлениями и языками                                             | `id` (решение 5); Google советует SKU, но допускает любой уникальный |
| `title`        | до 150, простой текст                                                                             | `title`                                                              |
| `description`  | до 5000, простой текст; лишнее Google обрежет                                                     | `long_text`                                                          |
| `link`         | http или https, подтверждённый домен                                                              | `url`                                                                |
| `image_link`   | см. «Картинки» ниже                                                                               | `image_link`                                                         |
| `availability` | `in_stock`, `out_of_stock`, `preorder`, `backorder`                                               | `availability`                                                       |
| `price`        | число и код ISO 4217, `15.00 USD`; нулевая цена запрещена                                         | `list_price_with_currency`                                           |
| `brand`        | до 70; обязателен для новых товаров, кроме фильмов, книг, записей; заглушки вроде «N/A» запрещены | `brand`                                                              |
| `gtin`         | «зависит»: настоятельно рекомендован, если есть                                                   | `gtin`                                                               |
| `mpn`          | до 70; обязателен, если у товара нет GTIN от производителя                                        | `mpn`                                                                |

**Атрибуты для рекламы**

| Атрибут                     | Правило Google                                                                                                                          | У нас                                |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| `custom_label_0…4`          | до 100 символов, одно значение, до 1000 разных значений на аккаунт на метку; покупателю не видны; Performance Max, Shopping, Demand Gen | §3.3                                 |
| `identifier_exists`         | `yes`, `no`; по умолчанию `yes`; `no` только если идентификаторов точно нет; при обратном — предупреждение                              | `no` без `gtin` и `mpn` (решение 14) |
| `sale_price`                | число и валюта; `price` при этом — цена без скидки                                                                                      | `sale_price_with_currency`           |
| `sale_price_effective_date` | ISO 8601, начало и конец через `/`, до 51 символа; без него скидка действует всегда                                                     | пусто, место оставлено               |

| `product_type`              | до 750; в кампаниях используется первое значение                                                                                        | `product_type`                       |

| `item_group_id`             | до 50; один на все варианты; обязателен для вариантов в ряде стран и в бесплатных показах                                               | `group_id`                           |

**GTIN.** Длина 8, 12, 13 или 14 цифр, контрольная цифра верна, пробелы и дефисы убираются. Запрещены
префиксы 02, 04, 2 (внутренние коды) и 05, 98, 99 (купоны). Придумывать нельзя: сомневаешься — не
передавай. Поэтому `gtin` — это `barcode`, прошедший такую проверку, а `barcode` остаётся как есть.
Штрихкод, который не прошёл, — предупреждение `invalid_gtin` и пустой `gtin`.

**Дополнительные штрихкоды (решение 17).** `gtin` у Google повторяется, до 10 значений: это для товара,
у которого настоящих идентификаторов несколько, например глобальный и дистрибьюторский. **Вывод: по
умолчанию пресет передаёт только основной.** В дополнительных штрихкодах бывают внутренние коды, а
контрольная сумма не отличит чужой настоящий GTIN от своего. Человек, уверенный в своих данных, меняет
в копии шаблона одну строку на `{{#gtins}}<g:gtin>{{value}}</g:gtin>{{/gtins}}`.

**Картинки.** JPEG, WebP, PNG, неанимированный GIF, BMP, TIFF; адрес ASCII, RFC 3986, до 2000 символов,
стабильный; до 64 мегапикселей и 16 МБ; с 31.01.2027 — не меньше 500×500, рекомендуется от 1500×1500.
Водяные знаки, текст поверх и заглушки запрещены. Googlebot и AdsBot-Google должны иметь доступ.

**Текст и кодировка.** Описание — простой текст, поэтому `long_text`, а не HTML. Страница `description`
прямо про HTML не говорит, спецификация называет поле простым текстом. Символы — XML-сущностями, файл —
UTF-8. Большая часть данных на языке фида, язык задаётся источником данных в Merchant Center.

**Вне пресета.** `shipping` обязателен в ряде стран, настраивается в аккаунте Merchant Center, в
пресете нет. Для одежды Google требует `color`, `size`, `gender`, `age_group` в ряде стран: это
значения свойств, человек добавляет их в копию шаблона строкой вроде
`{{#property.color}}<g:color>{{property.color}}</g:color>{{/property.color}}`.

**Маппинги пресета:** `stock_map` (§6.1), `taxonomy: google` (§6.2), `custom_labels` — все `none`.

**Набросок шаблона.** Шапка:

### 9.2. Плоские JSON, XML и CSV

Для разовых запросов; человек убирает лишнее и добавляет нужное.

**JSON.** Шапка, разделитель `,`, подвал:

```text
{"generated_at":"{{generated_at}}","currency":"{{feed.currency}}","products":[
```

```text
{"id":{{id}},"sku":"{{sku}}","name":"{{name}}","url":"{{url}}","price":{{price}},
"images":[{{#images}}{{^first}},{{/first}}"{{url}}"{{/images}}],"available":"{{availability}}"}
```

```text
]}
```

**XML.** Шапка `<?xml version="1.0" encoding="UTF-8"?><products>`, подвал `</products>`:

```xml
<product id="{{id}}">
  <sku>{{sku}}</sku>
  <name>{{name}}</name>
  <url>{{url}}</url>
  <price currency="{{feed.currency}}">{{price}}</price>
  <description>{{description_cdata}}</description>
  {{#images}}<image>{{url}}</image>{{/images}}
</product>
```

**CSV.** Шапка — строка заголовков `id,sku,name,url,price,availability`, разделитель — перевод строки:

```text
{{id}},{{sku}},{{name}},{{url}},{{price}},{{availability}}
```

Кавычки ставит экранирование, в шаблоне их нет. Значения не защищаются от формул приставкой `'`: это
исказило бы данные для площадки. Такие файлы читают программы, а не таблицы; см. §13.

## 10. Запасной выход

Для структур, которые Mustache не описывает: вложенность зависит от данных, нужен свой порядок
элементов, бинарный формат. Не основной путь: шаблон видно и можно править без релиза.

```php
interface FeedFormat
{
    public function key(): string;
    public function label(): string;
    public function extension(): string;
    public function contentType(): string;

    /** @return list<string> имена переменных, которые нужно посчитать */
    public function variables(): array;

    public function open(FeedWriter $out, FeedContext $context): void;

    /** @param array<string, mixed> $values значения одного товара */
    public function item(FeedWriter $out, array $values): void;

    public function close(FeedWriter $out, FeedContext $context): void;

    /** Ошибки готового файла, как в §7.2. */
    public function validate(string $path): ?string;
}
```

Регистрация — `FeedFormats::register()` из провайдера пакета сайта; ключ лежит в `feeds.driver`. Отбор,
отсев, переменные, запись потоком, подмена, журнал и доставка — те же. Форма вместо редактора шаблона
показывает название класса. `open()` зовётся после товаров по той же причине, что в §7.1. Класс, которого
больше нет, — `failed` с понятной ошибкой, старый файл продолжает отдаваться.

| `catalog_feeds_builds`          | журнал, страницами                                             | `catalog.view`   |
| `catalog_feeds_build_get`       | сборка: счётчики, причины, предупреждения, первые 50 отсеянных | `catalog.view`   |
| `catalog_feeds_exclusions`      | список исключений                                              | `catalog.view`   |
| `catalog_feeds_exclusions_set`  | `{add?, remove?}`; с `dry_run` — что изменится                 | `catalog.manage` |
| `catalog_feeds_mappings`        | склад и категории фида, что не смаплено                        | `catalog.view`   |
| `catalog_feeds_mappings_set`    | `{stock?, categories?}`                                        | `catalog.manage` |
| `catalog_feeds_taxonomy_search` | поиск по справочнику площадки                                  | `catalog.view`   |
| `catalog_feeds_taxonomy_import` | `{key, locale, url?}`; файла у агента нет, только адрес        | `catalog.manage` |

`catalog_feeds_preview` данных не меняет, поэтому `dry_run` у него нет. Право на него всё же
`catalog.manage`: он собирает пробу по шаблону, присланному извне, а это дорогая операция.

Ресурсы: `catalog://feed-variables` — реестр по частям, `catalog://feed-rules` — как устроен шаблон,
ограничения Mustache (§2.5), экранирование, источники меток. Агенту проще собрать шаблон правильно, чем
разбирать ошибки.

`dry_run` у `create` и `update` делает всю проверку и не пишет. У `rebuild` отвечает, сколько товаров
войдёт и сколько отсеется, по подсчёту запросом.

## 13. Безопасность

**Ключ фида.**

- 40 случайных символов из `Str::random`, 238 бит: перебор не страшен. Хеш не храним: панель должна
  показывать адрес снова.
- Ключ не в журнале изменений (`$hidden` и исключение в истории), не в снимках журнала MCP, не в
  логах приложения.
- Неверный ключ, выключенный фид и фид без файла неотличимы для постороннего: 404. `Retry-After`
  приходит только с верным ключом.
- Ключ — в пути, а значит, в логах прокси. Это цена работы с площадками, большинство из которых заголовка
  не умеет. Фид не содержит ничего сверх витрины, если шаблон этого не добавил (ниже).

**Что фид не отдаёт.**

- Только `Product::visible()`: снятые, удалённые и товары скрытых категорий не выходят ни в файл, ни в
  предпросмотр. Предпросмотр не показывает их и по `product_ids`.
- Переменные — только реестр; шаблон не может обратиться к модели. Лямбды выключены, Blade нет.
- Закрытая колонка обмена объявляет `PrivateColumn` и не становится переменной. `external_id`,
  `priority`, `is_published` переменные есть (решение 5): кто пишет шаблон, тот решает, что показать.
  Шаблон пишет человек с `catalog.manage`, а экспорт этих данных ему и так доступен.
- CSV: приставки против формул нет (§9.2). Значения приходят из каталога, файл читают программы. Если
  фид откроют в таблице, формула из описания сработает; панель об этом предупреждает у формата CSV.

**Тяжёлые запросы.**

- Запрос адреса читает одну строку и отдаёт файл. Сборка на запрос не запускается.
- Именованный лимитер `webx-catalog-feeds`, по ключу и IP: голый `throttle` попал бы в общий счётчик
  гостя вместе с формой входа. Лимит не должен мешать площадке: 60 запросов в минуту.
- `rebuild` и `preview` — только с `catalog.manage`; `rebuild` не ставит вторую сборку (§7.1), предпросмотр
  ограничен `sample` и 20 товарами по `product_ids`.
- Импорт справочника по адресу: только https, запрет частных сетей, лимит размера, как у обмена.

**Закрытый сайт.** Шлюз `CloseSite` перекрывает `/feeds/*`, а площадка пароля не знает. Намеренно не
открываем адрес сам: у закрытого сайта и картинки со страницами товаров Google не увидит. `FeedsCheck` в
`webx:doctor` об этом говорит; открыть можно `webx-admin.gate.except`.

**robots.txt** не должен закрывать `/feeds/` и картинки от Googlebot и AdsBot-Google. Это проверяет тот же
`FeedsCheck`.

## 14. Этапы реализации

Каждый этап — один проверяемый результат и свой changeset. Правка в `php/packages/*` — changeset на
`@webx-ui/php`, в npm-пакете — на него. Разделы «Выпуск», таблицу `WEBX_UI_CATALOG.md` §10 и реестр
пакетов обновляет этап, который выпускает.

1. **Общий Mustache.** Пакеты: новый `webx-ui/templates`, `@webx-ui/core`, `module-notifications` (php и
   npm). `php/` четырежды: `require`, `autoload-dev.psr-4`, `phpunit.xml.dist`, `phpstan.neon.dist`; версия —
   `node scripts/sync-php-version.mjs`; `AGENTS.md`; строка в `WEBX_UI_COMPOSER_PACKAGES.md`.
   **Результат:** все тесты уведомлений зелёные на новом коде, общий файл случаев совпадает в PHP и в
   браузере, в `module-notifications` нет `mustache/mustache`.
2. **`mpn` и дополнительные штрихкоды в ядре** (решения 16 и 17). Пакет и changeset — каталог, не
   спутник. Содержание — §14.1. **Результат:** товар сохраняет оба поля из формы, обмена и MCP, находится
   по любому штрихкоду в SQL и Manticore, тема выводит все штрихкоды.
3. **Реестр `ProductVariables`.** Пакеты: `module-catalog`, `module-catalog-brands`, `-labels`, `-stock`,
   `-properties`. **Результат:** тест получает значения всех переменных §4.2–§4.3 на страницу товаров
   постоянным числом запросов, сайт добавляет свою переменную.
4. **Каркас пакета.** `module-catalog-feeds`: миграции, модели, CRUD API, `CatalogFeedsModule`.
   `php/` четырежды, как в этапе 1. Новый раздел панели, четыре места: `Setup\Catalogue` в `module-admin`;
   `extra.webx.npm` и `extra.webx.panel` в `composer.json` пакета; список модулей в
   `apps/playground/src/panel/main.ts`; `scripts/packages.mjs` в репозитории демо-сайта. Пятое место —
   `SiteBar::entity()` — не нужно: `RouteType` у фида нет. Правки решения 1 обмена, решения 15 и §10
   архитектуры. `AGENTS.md`, `AccessCoverageTest`. **Первую версию npm-пакета публикует человек.**
   **Результат:** фид создаётся и правится через API, права проверяет `AccessCoverageTest`, панель
   показывает пустой раздел.
5. **Сборка.** Отбор, отсев, запись потоком, журнал, проверка файла. **Результат:** `BuildFeed` собирает
   файл на 100 тысячах товаров с замером времени и памяти, повтор упавшей страницы не даёт дублей,
   `assertNoRepeatedQueries` зелёный, `EXPLAIN` на MariaDB записан.
6. **Доставка.** Адрес, ETag, Last-Modified, 304, сторож, защита от частых сборок, подмена, чистка,
   `FeedsCheck`. **Результат:** два запроса подряд дают 200 и 304, импорт в 10 пачек даёт одну сборку,
   упавшая сборка оставляет старый файл доступным.
7. **Проверка и предпросмотр на сервере.** **Результат:** битый шаблон не сохраняется, ошибка XML и JSON
   приходит с номером строки и частью.
8. **Маппинги, справочник и источники меток.** **Результат:** импорт справочника Google по адресу и файлом,
   значение категории наследуется от предка, пять источников меток дают значения в фиде.
9. **Пресеты.** Google Merchant, JSON, XML, CSV; страницы требований сверить заново. **Результат:** каждый
   пресет создаёт фид, который проходит проверку §8 и даёт файл на демо-данных.
10. **Панель.** Пакет `@webx-ui/module-catalog-feeds`, экран `catalog.feed-form`, мок плейграунда, гайд в
    `apps/docs/guide/`. **Результат:** фид создаётся в `/panel/` плейграунда, предпросмотр совпадает с
    сервером, вид проверен в браузере и в тёмной теме.
11. **MCP.** `FeedTools`, ресурсы. **Результат:** агент проходит путь «пресет → маппинг → предпросмотр →
    сборка → журнал» с `dry_run` и без; `AccessCoverageTest` зелёный.
12. **PHP-класс формата.** `FeedFormats`, контракт §10. **Результат:** тестовый класс собирает файл тем же
    конвейером, форма показывает его вместо редактора.
13. **Демо.** Демо-фид на демо-данных сайта, сидер, `PerformanceTest` модуля. **Результат:** `webx:setup`
    ставит модуль, демо-фид собирается.
14. **Проверка на lab.** **Результат:** Google-фид на lab прошёл проверку ниже, итог записан в «Выпуск».

    Lab виден только в домашней сети, поэтому Google забрать файл по адресу не сможет:
    1. `scripts/lab-site.sh refresh`, создать фид из пресета, смаппить две категории, настроить метки,
       собрать; проверить 200, 304, журнал и отсев.
    2. Скачать файл и прогнать скриптом: `xmllint --noout`; все обязательные атрибуты §9.1 есть; длины в
       пределах; ни одного пустого тега; `sale_price` меньше `price`; GTIN с верной контрольной цифрой.
    3. Человек загружает файл в тестовый источник данных Merchant Center вручную («Add products from a
       file») и смотрит раздел диагностики. Ошибки записать в отчёт, правки — в пресет. Адрес для
       настоящей выборки по расписанию проверяется уже на сайте с публичным адресом.

### 14.1. Этап 2: поля ядра

**`mpn` (решение 16).** Колонка `mpn` string(70), null, index в `catalog_products`, рядом с `barcode`, без
уникальности. 70 — предел Google. Конфиг `webx-catalog.fields.mpn` — как у штрихкода, по умолчанию
включён. Форма «Основное», `ProductResource`, `catalog_products_*`, `catalog://fields`, колонка обмена
`mpn`, демо-данные. Решение 2 архитектуры не нарушено: это поле ядра, а не спутника.

**Дополнительные штрихкоды (решение 17). Хранение — таблица** `catalog_product_barcodes`: `id`,
`product_id` (индекс, каскад), `barcode` string(64) (индекс), `position`. Почему таблица, а не JSON:
поиск по коду точным равенством — горячий путь, индекс на колонке закрывает его на любой базе, а JSON на
MariaDB пришлось бы индексировать виртуальной колонкой, и на массиве это не работает. Уникальности нет.

| Где          | Что                                                                                                                                      |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `barcode`    | основной, без изменений: существующие сайты, обмен и MCP работают как раньше                                                             |
| Панель       | поле-список под основным штрихкодом, с `fields.barcode`                                                                                  |
| Обмен        | колонка `barcodes`, значения через `;`, как у `categories`, `labels`, `images`. Пустая ячейка не трогает, с `empty_clears` — стирает     |
| Импорт       | сопоставления товара по этим штрихкодам нет (решение 17); ключ строки `barcode` — только основной                                        |
| MCP          | поле `barcodes` в `catalog_products_get`, `create`, `update`                                                                             |
| Сайт         | `Product::allBarcodes()` — основной первым, для темы; связь грузится запросом на список                                                  |
| `SqlEngine`  | `scopeCoded()`, `scopeMatching()` и сортировка точного совпадения в `search()` — плюс `whereExists` по таблице                           |
| Manticore    | новое поле документа `barcodes`, `code: true`, значения через пробел; схема меняется, нужен `webx:catalog:index --rebuild` — в changeset |
| Поиск панели | тем же движком, отдельной правки нет (решение 14 архитектуры)                                                                            |
| Журнал       | изменение списка — строка истории товара                                                                                                 |
| Индекс       | сохранение списка вызывает `Catalog::touch()`: запись мимо модели товара                                                                 |

Два товара с одним кодом — не ошибка. Точное совпадение в поиске уже считает до двух (`limit(2)`), и
прямой переход только при одном товаре; для дополнительных штрихкодов правило то же.

## 15. Открытые вопросы

К человеку. Рекомендация стоит первой; работа по §14 до этапа, где вопрос нужен, не блокируется.

1. **Валюта фида (решение 7).** В каталоге одна валюта сайта (решение 4 архитектуры), курсов нет
   нигде. Варианты: (а) поле есть, но принимает только валюту сайта — рекомендуется, пересчёт придёт с
   типами цен и валютами; (б) поле `rate` в фиде, вписанное руками, — курс быстро устаревает, а Google
   сверяет цену со страницей. Отдельно: при пустом `webx-catalog.price.currency` фид с ценой с валютой
   не сохраняется, проверка говорит, что задать.
2. **Перевыпуск ключа (решение 8).** «Ключ не меняется» понято как «не меняется сам». После утечки нужен
   выход. Варианты: (а) действие «Перевыпустить ключ» с подтверждением, только `catalog.manage`, только в
   панели — рекомендуется; (б) выхода нет, для нового ключа создают новый фид.
3. **Отбор по свойству (решение 15).** Значения свойств идут через фасеты, а фасет есть только у свойства
   с флагом «в фильтре»; спутник свойств фиды не знает. Варианты: (а) новый метод источника фасетов
   `FacetSource::allFacets()`, который отдаёт фасет и без флага, только для отбора, — рекомендуется,
   это малая правка `module-catalog` и `module-catalog-properties`; (б) в отборе только свойства «в
   фильтре», и это написано в форме.
4. **`group_id` до модуля групп.** Сейчас значение берётся только из свойства (§4.5). Варианты: (а) как
   описано — рекомендуется; (б) ждать `module-catalog-groups`, а пока тег не выводить. Для магазина
   запчастей варианты, скорее всего, не важны; важны для одежды.
5. **Проверка в Merchant Center.** Для этапа 14 нужен тестовый аккаунт и человек, который загрузит файл.
   Это аккаунт первого заказчика или отдельный?
6. **Место для общего Mustache (§2.3).** Рекомендация — `webx-ui/templates` и `@webx-ui/core`. Вариант —
   всё в `module-admin` (php и npm): нет нового пакета и зеркала, но рендер, живущий без панели, окажется
   в её каркасе вопреки правилу имён.
7. **Передача дополнительных штрихкодов в Google (§9.1).** Рекомендация — только основной по умолчанию,
   список доступен переменной `gtins`. Подтвердить или выбрать передачу всех проверенных.
