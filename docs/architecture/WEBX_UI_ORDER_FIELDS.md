# Дополнительные поля заказа — спецификация

Статус: спроектировано, ждёт приёмки человеком (webx-ui#122). Кода нет. Решения человека от
05.11.2026 здесь не пересматриваются; что упирается в код или оставлено спеке — §11.

Часть пакета `webx-ui/module-orders` и его npm-пары, отдельного пакета нет. Основа —
[`WEBX_UI_MODULE_ORDERS.md`](WEBX_UI_MODULE_ORDERS.md); ссылки вида «§20.3 заказов» ведут туда.
Шаблоны писем — общий Mustache: [`WEBX_UI_CATALOG_FEEDS.md`](WEBX_UI_CATALOG_FEEDS.md) §2 и §7
[`WEBX_UI_MODULE_NOTIFICATIONS.md`](WEBX_UI_MODULE_NOTIFICATIONS.md).

**Почему отдельный файл.** Спека заказов — уже 3400 строк, её номера разделов не меняются, а
эта работа идёт сквозь три её части (снимок, оформление, правка). Так живут и другие спутники
спек: `WEBX_UI_PAYMENT_GROUPS.md`, `WEBX_UI_CATALOG_VIDEO.md`. В спеке заказов остаются ссылки:
решение 36 («своих полей в v1 нет») и пункт 4 §18 снимаются, таблицы §3, §31 и §32 получают
строки — это этап 1 (§10).

## 1. Назначение и границы

Магазину нужны свои поля в оформлении: «Нужен монтаж и настройка», «Не перезванивайте, если всё в
наличии», «Покупаю для компании» с названием и кодом компании, «Удобное время доставки». Сейчас
есть только контакты, получатель, комментарий и блоки `delivery` и `payment`.

**В первой версии:**

- определения полей задаёт администратор в панели: список с сортировкой перетаскиванием (решение 1);
- четыре типа: флажок, строка, многострочный текст, список с одним выбором (решение 2);
- простое условие: показать поле при отмеченном флажке-поле (решение 3);
- заказ хранит снимок названия и значения (решение 5);
- вывод на «Спасибо», странице заказа, в письмах и в карточке панели (решение 6);
- правка значений менеджером с записью в журнал (решение 7);
- инструменты MCP (решение 8), вид через тему (решение 9).

**Отложено:**

- типы «дата», «файл», «число» (решение 2);
- условия по способу доставки, оплате и любые другие, кроме флажка (решение 3);
- платные поля: поле не добавляет сумму, в модели нет ни колонки цены, ни задела под неё
  (решение 4); монтаж и подобное считает менеджер правкой состава (§37 заказов);
- фильтр и колонка списка заказов по полю (§5.5);
- поля в «Купить в один клик» и в заказе из панели (§4.5).

**Что поле не делает.** Не трогает цепочку итогов, корзину, `expected_payable`, вехи и статусы.
Значение — данные для людей, а не вход для логики других модулей.

## 2. Модель

### 2.1. Определения — таблица `order_fields`

| Колонка                    | Тип                               | Примечание                                                           |
| -------------------------- | --------------------------------- | -------------------------------------------------------------------- |
| `id`                       | bigint                            |                                                                      |
| `key`                      | string(32), **unique**            | `^[a-z][a-z0-9_]{0,31}$`; после создания не меняется                 |
| `type`                     | string(16)                        | `checkbox`, `text`, `textarea`, `select`; после создания не меняется |
| `place`                    | string(16)                        | `contacts` или `extra` (§4.1)                                        |
| `label`                    | json                              | название, `{locale: text}`, ≤ 190 символов на язык                   |
| `hint`                     | json, null                        | подсказка под полем, `{locale: text}`, ≤ 500; простой текст          |
| `options`                  | json, null                        | только у `select`: `[{"value": "evening", "label": {"en": "…"}}]`    |
| `required`                 | bool, default false               | §3.2                                                                 |
| `active`                   | bool, default true                | выключенное поле покупатель не видит                                 |
| `parent_id`                | FK `order_fields`, null, restrict | поле-флажок условия (§3.3); `null` — показывается всегда             |
| `position`                 | int unsigned, default 0           | порядок в списке                                                     |
| `created_at`, `updated_at` | timestamp                         |                                                                      |

- Название таблицы — как `order_statuses`: определение раздела с приставкой `order_`. Модель —
  `WebxUi\Orders\Models\OrderField`, переводимые `label` и `hint` — как `name` у статусов.
- **Почему таблица, а не настройка `orders.checkout.*` с `wx-repeater`.** Репитер дал бы сортировку
  и `localized` без нового экрана, но у определения есть то, чего у настройки нет:
  - ключ и тип неизменны после создания, а строка репитера всё правит и всё пересылает целиком;
  - условие — ссылка на другую строку: удаление флажка с зависимыми полями — отказ с их списком
    (§7.3), а настройка знает только «значение не прошло проверку»;
  - отдельные инструменты MCP с `dry_run` и понятными отказами (§8.1), как у статусов, а не правка
    всего массива в `orders_checkout_settings_set`;
  - `module-settings` у заказов необязателен (`SettingsScreen`): на сайте без него настройку
    хранить негде, таблица работает всегда.

  Цена таблицы — миграция, узел панели и API. Образец готов: `order_statuses` и `OrderStatuses`.

- **Мягкого удаления нет.** Старым заказам определение не нужно: они держат снимок (§2.2).
- **Предел — 30 определений и 50 вариантов у поля.** Определения читаются целиком на каждый запрос
  оформления, а снимок лежит в строке заказа; предел держит и то, и другое. Отказ — §7.3.
- **Кеш:** все определения одним запросом в `CacheGroups::remember` новой группы `order-fields`,
  как `order-statuses` у `OrderPage`. `OrderField` — в `bumpOn` группы; `arrange` пишет массово,
  без событий модели, поэтому зовёт `bump()` сам. Настроек оформления в этой группе нет.
- **Индексы:** только `unique(key)`. Выборок с `WHERE` нет, список читается целиком.

### 2.2. Снимок — колонка `orders.fields`

`orders.fields` — json, null. Список строк в порядке оформления, на языке заказа:

```json
[
  {
    "key": "installation",
    "type": "checkbox",
    "label": "Installation and setup needed",
    "value": true,
    "text": "Yes"
  },
  {
    "key": "company_name",
    "type": "text",
    "label": "Company name",
    "value": "Company A",
    "text": "Company A"
  },
  {
    "key": "delivery_time",
    "type": "select",
    "label": "Convenient delivery time",
    "value": "evening",
    "text": "18:00–21:00"
  }
]
```

- `label` и `text` — то, что печатается, как есть. `value` — машинное значение: по нему менеджер
  видит выбранный вариант в правке (§6.1), а агент читает ответ без разбора текста.
- **В снимок попадают только заполненные поля (решение 5, выбор спеки).** Пустая строка,
  невыбранный список, снятый флажок и скрытое условием поле не пишутся. Так вывод не проверяет
  пустоту в четырёх местах, а письмо, страница и панель читают один список; строка «Нет» у каждого
  снятого флажка покупателю ничего не говорит. Нет заполненных полей — `null`.
- **Почему колонка, а не таблица значений.** Значения читаются только вместе с заказом и всегда все,
  поиска и индекса по ним в первой версии нет. Таблица стоила бы запроса на каждую страницу заказа,
  письмо и событие, а снимок ложится рядом с `recipient`, `delivery` и `payment` тем же способом.
  Появится фильтр по полю — отдельная таблица значений добавится миграцией из этой колонки (§5.5).
- **Почему не `OrderBlocks`.** Блок — это одно значение с модулем-владельцем: ключ равен колонке,
  проверка и строка `summary` — руками владельца, запись — `patchBlock()`, реестр новых ключей не
  принимает (§6.4 заказов). У полей владельца-соседа нет, это список заранее неизвестных строк
  самого заказа, а правятся они как контакты, через `updateDetails()`. Третий блок был бы подделкой:
  пустой `summary`, `method` без смысла и вкладка, которую некому нести. Оговорка §6.4 про «третий
  блок» к этой колонке не относится.
- **Заказ определений не знает.** `PlaceOrder` получает готовые строки новым параметром `fields`
  (`list<array>`), `Orders::place()` проверяет только их форму и пишет. `Orders::place()` из кода
  работает с выключенным оформлением, как раньше. `OrderData` получает `fields`, поэтому слушатели
  и письма читают снимок события.
- **Определение меняется — снимок нет.** Переименование, новые варианты, выключение и удаление поля
  старые заказы не трогают (решение 5).

## 3. Типы и проверка

### 3.1. Типы

| Тип        | Поле на сайте                  | Значение                    | `text` снимка                    | Проверка                                 |
| ---------- | ------------------------------ | --------------------------- | -------------------------------- | ---------------------------------------- |
| `checkbox` | `<x-webx-field type=checkbox>` | `true`                      | «Да» на языке заказа             | `FILTER_VALIDATE_BOOLEAN`                |
| `text`     | `<x-webx-field>`               | строка без краевых пробелов | то же                            | ≤ 190 символов (`max:190`, как имя)      |
| `textarea` | `<x-webx-field type=textarea>` | то же, переводы строк целы  | то же                            | ≤ 2000 символов (`CommentStep::MAX`)     |
| `select`   | `<x-webx-field type=select>`   | `value` варианта            | подпись варианта на языке заказа | значение — один из вариантов определения |

- Длины — константы, настройки длины у поля нет: в решении 1 её нет, а колонка `orders.fields`
  ограничена этими числами.
- `value` варианта — стабильный ключ по тому же правилу, что `key`. Панель предлагает его из подписи
  и не даёт менять у сохранённого варианта; подпись правится свободно. Варианты уникальны по `value`.
- У списка первая строка всегда пустая («Выберите»): так работает `select` виджетов.
- Значения — простой текст. HTML и разметка не разбираются, вывод экранируется (§9).

### 3.2. Обязательность

- `required` у строки, текста и списка — значение должно быть. У флажка — флажок должен быть
  отмечен: это «подтверждаю…», а не выбор.
- Обязательность — только для покупателя в оформлении. Менеджер в карточке может оставить поле
  пустым (§6.1).
- Обязательное поле, которое показывается всегда, — браузерный `required` и звёздочка, как у
  контактов. Необязательная строка, текст и список — проп `optional`.

### 3.3. Условие «показывать при отмеченном флажке»

- Условие — `parent_id`: ссылка на поле типа `checkbox`. Других условий нет (решение 3).
- **Один уровень.** Родитель сам не зависит от другого поля; у флажка с зависимыми полями условия
  нет. Цепочки ничего не дают примерам из решения 3, а усложняют и проверку, и панель.
- **Родитель и зависимое поле — в одном месте** (§4.1). Каждое место — отдельная форма со своим
  сохранением, поэтому скрытое условием поле из другой формы нельзя честно проверить в момент
  сохранения. Смена места родителя переносит зависимые поля той же записью, и `dry_run` об этом
  говорит.
- **Скрытое условием поле не проверяется и не сохраняется (решение 3):** на сервере его значение
  отбрасывается при сохранении шага, даже если пришло; в черновик и снимок оно не попадает, обязательность
  не действует. Покупатель снял флажок и отметил снова — поля пусты, если шаг сохранялся между этим.
- **Поле показывается, только если родитель активен и отмечен.** Выключенный родитель — зависимые
  поля не показываются, определение остаётся (§7.3).
- **Условие решает сервер**, разметка только прячет (§4.4). Без скриптов и CSS результат тот же.

### 3.4. Ошибки формы

Как у контактов (§20.3 заказов): `save()` шага бросает `ValidationException` по именам полей,
`check()` возвращает `StepError` с тем же полем. Имя поля в форме — `extra.<key>`.

| Код `StepError`      | Когда                           | Слова                                                 |
| -------------------- | ------------------------------- | ----------------------------------------------------- |
| `fields.required`    | обязательное поле пусто         | `checkout.errors.required` с `:field` — название поля |
| `fields.invalid`     | длина или неверный тип значения | правило валидатора с названием поля                   |
| `fields.option_gone` | выбранного варианта больше нет  | новое `checkout.errors.option-gone`                   |

- Коды общие, а не на ключ поля: ключи задаёт магазин, а реестр кодов (`NamesErrors::errorCodes()`)
  статичен. Какое именно поле — говорит `field` ошибки.
- `check()` читает **текущие** определения: поле стало обязательным или вариант исчез, пока покупатель
  думал, — подтверждение отвечает 422 под полем (§24 заказов). Значения выключенных и удалённых полей
  из черновика в заказ не идут и ошибок не дают.

## 4. Оформление

### 4.1. Где поля встают

| `place`    | Где                                                                                    |
| ---------- | -------------------------------------------------------------------------------------- |
| `contacts` | в шаге `contacts`, в его форме, после контактов и получателя, перед кнопкой сохранения |
| `extra`    | новый шаг `extra` «Дополнительно», позиция 850: перед комментарием (900), после оплаты |

- **Шаг `extra` — отдельный, а не форма внутри «Комментария».** Комментарий выключается настройкой
  `orders.checkout.comment`, а поля при этом должны остаться (вопрос 1 §11).
- `applies()` шага — есть активное поле с `place = extra`. Нет таких полей — шага нет, номера шагов и
  страница такие, как сегодня. Шаг — `Checkout\Steps\ExtraStep`, регистрация — рядом с `contacts`
  и `comment`.
- `summary()` шага — названия заполненных полей через запятую, `Str::limit(…, 80)`; пусто — `null`,
  как у комментария. Сводка контактов не меняется.
- Общая логика — один класс `Checkout\CheckoutFields`: определения места, правила, значения из
  черновика, снимок. `ContactsStep` и `ExtraStep` только зовут его для своего места.
- **Проект, заменивший шаг `contacts`** (`CheckoutSteps::register()` с тем же ключом), зовёт
  `CheckoutFields` сам — иначе поля этого места не спрашиваются. Сказать об этом в гайде и `AGENTS.md`.

### 4.2. Черновик

- Новых колонок нет. Значения лежат в `order_checkout_drafts.steps` под ключом `extra` — одной
  картой `{key: value}` для обоих мест: `{"extra": {"installation": true, "delivery_time": "evening"}}`.
  Смена места поля значение не теряет.
- **Шаг пишет только поля своего места.** Сохранение контактов не должно стереть значения шага
  `extra`, и наоборот; чужие ключи `steps` (шаги проекта) тоже остаются.
- `PlacingListener` уже стирает `steps` после заказа (§21.2 заказов). Значит, поля живут один заказ:
  контакты помнятся, а название компании и монтаж — нет. Это верно: поля относятся к заказу.
- Правки слушателя не нужно, черновик переезжает при слиянии корзин как раньше.

### 4.3. Подтверждение

Порядок §24.1 заказов не меняется. На шаге 3 `check(Purpose::Order)` обоих шагов проверяет поля, на
шаге 4 `contribute()` кладёт в `PlaceOrderBuilder::fields()` строки своего места, снимок строится на
языке заказа. Контакты идут раньше, поэтому порядок в снимке — сначала поля контактов, затем
«Дополнительно», внутри — по `position`.

Значения — только из черновика. Кнопка подтверждения сама сохраняет шаг, в котором покупатель печатал
(`checkout.js`), значит, новых полей запроса у `POST /checkout/place` нет.

### 4.4. Разметка и классы

Поля печатает новый вид `webx-orders::checkout.parts.extra-fields` из обоих шагов. Поля — стандартные
`<x-webx-field>` виджетов, своих нет (§27.2 заказов): `name="extra.<key>"`, `:label`, `:hint`,
`:value` или `:checked`, `:options`, `:maxlength`.

```html
<div class="webx-orders-checkout__extra webx-orders-checkout__extra--installation">…</div>

<div class="webx-orders-checkout__extra-group">
  <div class="webx-orders-checkout__extra webx-orders-checkout__extra--for_company">…</div>
  <div class="webx-orders-checkout__extra-when">
    <div class="webx-orders-checkout__extra webx-orders-checkout__extra--company_name">…</div>
    <div class="webx-orders-checkout__extra webx-orders-checkout__extra--company_code">…</div>
  </div>
</div>
```

- **Зависимые поля печатаются сразу за своим флажком**, в своём порядке, внутри `__extra-when`.
- **Условие на сайте — без скрипта,** как блок получателя: `checkout.css` прячет
  `__extra-when`, пока в `__extra-group` не отмечен флажок (`:not(:has(…:checked))`). Правки
  `checkout.js` и виджетов не нужно. Перерисовка шага (`checkout.js`) переносит значения по `name`,
  как у остальных полей.
- **Зависимые поля — без браузерного `required`,** как поля получателя: скрытое обязательное поле не
  дало бы отправить форму. Обязательность говорит сервер, ошибкой под полем. Звёздочки у них нет
  (вопрос 3 §11).
- **Тема** (решение 9): перекрывает `checkout/parts/extra-fields.blade.php` в своём слое, вид одного
  типа — `components/field/<type>.blade.php` виджетов, оформляет классы выше с ключом поля. Новых
  узлов композиции нет: поля живут внутри защищённого `checkout.steps`.
- Вид проверяется в браузере на 360 px и широком контейнере, в тёмной схеме (§27.2 заказов).

### 4.5. Быстрый заказ и заказ из панели

- **`QuickController` полей не спрашивает.** Диалог — телефон и необязательное имя, менеджер всё равно
  перезванивает (§29 заказов). Обязательные поля здесь не действуют, `orders.fields` — `null`.
- **Заказ из панели и `orders_create`** — то же: менеджер заполняет поля в карточке сразу после
  создания (§6.1). Правки `ManagerOrder` нет (вопрос 5 §11).

## 5. Вывод

Вид везде один: строка «название — значение» из снимка. Определения не читаются.

### 5.1. «Спасибо» и страница заказа

`OrderPage::of()` отдаёт `fields` — `[{key, label, text}]`. В `order/body.blade.php` строки встают в
ту же секцию и тот же `<dl class="webx-order__facts">`, что доставка и оплата, после них. Условие
секции становится «есть блоки или поля».

```html
<div class="webx-order__fact webx-order__fact--field webx-order__fact--field-company_name">
  <dt>Company name</dt>
  <dd>Company A</dd>
</div>
```

- Классы: `webx-order__fact--field` — общий, `webx-order__fact--field-<key>` — для иконки темы
  (решение 6).
- `<dd>` многострочного текста держит переводы строк: `white-space: pre-line` по классу `--field`.
- Значения печатаются `{{ }}`, `details` и `{!! !!}` к полям отношения не имеют.
- `thanks.blade.php` включает `order.body`, правка в нём не нужна.
- **Тема с собственной копией `order/body.blade.php`** полей не покажет, пока не добавит цикл. В
  монорепе таких копий нет; строка — в заметках релиза.

### 5.2. «Мои заказы»

`/account/orders/{number}` печатает то же тело — поля есть без правок. В списке заказов их нет: он
про статус и сумму.

### 5.3. Письма

Две переменные общего для всех событий заказа набора (`OrderValues::of()`, `OrderEvents::common()`):

| Переменная    | Что                                                   | Пример                                                                          |
| ------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------- |
| `fields`      | список строк снимка: `key`, `label`, `value` (строки) | `{{#fields}}{{label}}: {{value}}{{/fields}}`                                    |
| `field.<key>` | значение одного поля текстом; поля нет — пусто        | `{{#field.company_name}}Company: {{field.company_name}}{{/field.company_name}}` |

- `value` в письме — это `text` снимка: «Да», подпись варианта. Машинное значение шаблону не нужно.
- **Почему `field.<key>`, а не `fields.<key>`.** Значения отдаются плоско и вкладываются перед рендером
  (`'field.phone'` → `field → phone`, §7 уведомлений). `fields.company_name` положил бы карту в то же
  имя `fields`, где лежит список, и одно из двух потерялось бы. Семейство `field.*` уже есть у
  заявок (`SubmissionEvent`), поэтому `Variable('field.*', …)` работает как есть, и `knows()` на сервере
  и в браузере его понимает. Правок в `webx-ui/templates` и `@webx-ui/core` нет.
- Ключ поля — `[a-z0-9_]`: ровно то, что принимает имя переменной (`Variable`, `Template::NAME`). Дефис
  поэтому не разрешён и в ключе.
- `first` и `last` у строк `fields` есть, как у любого списка (§2.5 фидов).
- Значения покупателя проходят `Provider::escape` один раз и не раскрываются второй раз: `{{…}}` в
  названии компании остаётся текстом (§7.3 уведомлений).
- `'0'` в секции — пусто (§2.5 фидов): `{{#field.code}}` не покажет код `0`. Цикл `{{#fields}}` этой
  ловушки не имеет.
- Шаблоны по умолчанию (`OrderTemplates`): письмо и Telegram, обоим адресатам, — строки `{{#fields}}`
  после доставки и оплаты, перед комментарием. **Уже сохранённые шаблоны каналов не меняются:**
  магазин добавляет цикл сам (вопрос 6 §11).
- Перевод строки многострочного значения в HTML-письме схлопывается в пробел. Принято: чинить это в
  шаблонизаторе значило бы сырой вывод, а его нет (решение 2 фидов).

### 5.4. Панель, карточка

Карточка `orders.show`, вкладка «Покупатель»: новая карточка `buyer-fields` после получателя, узел
`wx-orders-fields` — те же строки «название — значение» и правка (§6.1). Нет строк и нет определений —
карточки нет. Раскрытие строки списка (`GET {id}/glance`) показывает те же строки: заказ там уже
загружен, это бесплатно.

### 5.5. Список — не в первой версии

Колонка и фильтр списка дёшевы только с виду. Набор полей у каждого магазина свой и меняется,
колонка — настройка вида таблицы, а фильтр по json без индекса читает все заказы
(`WEBX_UI_PERFORMANCE.md`). Понадобится — таблица значений с индексом `(key, value)`, отдельной
задачей.

## 6. Правка менеджером

### 6.1. Форма в карточке

- Узел `wx-orders-fields` — свой, а не поля JSON-экрана: экран общий для всех заказов, а у заказа могут
  быть строки поля, которого больше нет. Набор строк считает `OrderCard` для каждого заказа.
- **Что в форме:** строки снимка плюс активные определения, которых в снимке нет (менеджер дописывает
  поле, которое покупатель не заполнил, или заполняет после быстрого заказа).
- **Поле снимка без определения** — название из снимка; строка и текст правятся, флажок и список
  только снимаются: вариантов больше нет.
- **Проверка:** тип, длина, вариант — как в §3.1. Обязательность и условие не действуют: менеджер
  сознательно пишет то, что сказал покупатель.
- **Запись:** `PUT /api/cms/orders/{id}/details` с `fields: {key: value | null}` — только присланные
  ключи. `null`, пустая строка или `false` убирают строку снимка. Новая строка встаёт в конец, название
  и подпись варианта берёт из текущего определения на языке заказа. Значение не изменилось — строка
  нетронута, название остаётся снимком.
- Вводится `OrderDetails::fields()`; `Orders::updateDetails()` берёт рассчитанные строки в той же
  транзакции и под тем же замком заказа. Письмо покупателю правка не шлёт, как правка контактов.

### 6.2. Журнал

- Шкала заказа — строка `StatusChange::DETAILS`, заметка `fields`, как у контактов (§8 заказов). Нужно
  слово `webx-orders::module.fields.fields`, иначе шкала напечатает ключ словаря.
- Общий журнал `webx.history` — изменение «было — стало» строками «название: значение; …».
  **Ловушка:** `Orders::shown()` считает любой массив получателем и из снимка собрал бы пустую строку;
  поле `fields` идёт своей веткой.
- `OrderDetailsChanged` — `fields` в списке изменённого, прежние строки в `before`. Слушателям менять
  нечего.

### 6.3. Права

`orders.manage` — как правка контактов (решение 7). С `orders.view` карточка показывает строки без
правки. Нового права нет.

### 6.4. Определения и старые заказы

Переименование, смена вариантов, выключение и удаление определения снимки не трогают, и обратной
записи в заказы нет. Менеджер, изменивший значение, получает новую подпись только у этой строки.

## 7. Панель настроек

### 7.1. Список полей

- Вкладка «Оформление» экрана `orders.settings`, новая карточка `checkout-extra-card` после
  `checkout-fields-card`, право `orders.checkout.settings` (узел наследует `can` вкладки). Нет
  оформления — вкладки нет. Нет `module-settings` — сейчас `SettingsScreen::patch()` снимает вкладку
  целиком; теперь он снимает её остальные карточки, а эта остаётся: полям настройки не нужны (§2.1).
- Узел `wx-orders-checkout-fields` (Vue, `@webx-ui/module-orders`), запись — своим API, а не общей
  кнопкой сохранения вкладки. Образцы: `StatusesPage.vue` и `StageDialog.vue` (список, диалог, порядок),
  `NumberSampleNode.vue` (свой узел на JSON-экране).
- Строка: название на языке панели, ключ, тип, место, «обязательное», «при флажке: …», переключатель
  «включено», `···` с удалением.
- **Сортировка — `WxSortableList`**, на телефоне те же ручки. Зависимые поля — с отступом под своим
  флажком и двигаются только внутри него: на сайте они печатаются там же (§4.4).

### 7.2. Форма поля

Диалог с полями из решения 1:

| Поле             | Компонент                       | Заметка                                                          |
| ---------------- | ------------------------------- | ---------------------------------------------------------------- |
| Название         | `WxInput`, `localized`          | обязательно на основном языке                                    |
| Ключ             | `WxInput`                       | из названия, транслитом; у сохранённого поля только чтение       |
| Тип              | `WxSelect`                      | у сохранённого поля только чтение                                |
| Варианты         | `WxRepeater`: значение, подпись | только у списка, подпись `localized`                             |
| Подсказка        | `WxInput`, `localized`          | необязательно                                                    |
| Обязательное     | `WxSwitch`                      | у флажка подпись «Нужно отметить»                                |
| Место            | `WxSelect`                      | «Контакты» / «Дополнительно»; у зависимого поля — как у родителя |
| Показывать, если | `WxSelect`                      | «Всегда» или флажок того же места без условия                    |
| Включено         | `WxSwitch`                      |                                                                  |

Слова — английские, группа `checkout.settings.*` словаря `webx-orders`, на всех десяти языках словаря.
Подсказка над списком: не спрашивать здесь данные карт и документов (§9).

### 7.3. API, сервис, отказы

Маршруты — `cms.can:orders.checkout.settings`, только при включённом оформлении:

```
GET    /api/cms/orders/checkout-fields
POST   /api/cms/orders/checkout-fields
PUT    /api/cms/orders/checkout-fields/{field}
DELETE /api/cms/orders/checkout-fields/{field}
PUT    /api/cms/orders/checkout-fields/arrange
```

Сервис `WebxUi\Orders\OrderFields` по образцу `OrderStatuses`: `write`, `remove`, `arrange`, каждый —
с `dry_run` и ответом-планом, отказ — `FieldRefused` с кодом. Панель и MCP зовут одно и то же. Запись
определения идёт в журнал `webx.history`.

| Код              | Когда                                                                      |
| ---------------- | -------------------------------------------------------------------------- |
| `key_invalid`    | ключ не по правилу                                                         |
| `key_taken`      | ключ занят                                                                 |
| `locked`         | попытка сменить `key` или `type`                                           |
| `no_label`       | нет названия на основном языке                                             |
| `no_options`     | у списка нет вариантов, или есть лишние у другого типа                     |
| `option_invalid` | ключ варианта не по правилу, повтор, нет подписи                           |
| `parent_invalid` | родитель — не флажок, сам зависит, другого места или у поля есть зависимые |
| `has_dependents` | удаление флажка с зависимыми полями; отказ называет их                     |
| `too_many`       | больше 30 полей или 50 вариантов                                           |

Выключение флажка с зависимыми полями — не отказ: они перестают показываться, и план об этом говорит.

## 8. MCP

### 8.1. Определения

Инструменты — в `Mcp\CheckoutTools`, при выключенном оформлении их нет (§32 заказов). Изменяющие — с
`dry_run`, ответ — план `OrderFields`; отказ — `ToolFailure` со словами.

| Инструмент                       | Область, право                             | Что делает                                                                                      |
| -------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `orders_checkout_fields_list`    | `orders:read`                              | все определения по порядку: ключ, тип, место, названия и подсказки по языкам, варианты, условие |
| `orders_checkout_fields_save`    | `orders:write`, `orders.checkout.settings` | создать или изменить по `key`; `dry_run` — что увидит покупатель («поле станет обязательным»)   |
| `orders_checkout_fields_delete`  | `orders:write`, `orders.checkout.settings` | удалить по `key`; `dry_run` — что исчезнет; старые заказы не трогает, так и сказано в ответе    |
| `orders_checkout_fields_reorder` | `orders:write`, `orders.checkout.settings` | порядок: `keys` — все ключи; неполный список — отказ                                            |

Примеры `ToolFailure`: «The key of a field never changes: delete „company_code“ and add another»,
«The field „for_company“ has fields shown behind it: company_name, company_code», «Unknown parent
„for_company“: orders_checkout_fields_list lists the fields».

### 8.2. Значения в заказах

- `orders_get` — `fields`: строки снимка целиком (`key`, `type`, `label`, `value`, `text`). Это данные
  покупателя, описание инструмента говорит об этом, как о контактах.
- `orders_update` — новый аргумент `fields`: `{key: value | null}`, правила §6.1, право `orders.manage`.
  `dry_run` — какие строки изменятся. Неизвестный ключ — `ToolFailure`, а не молчание:
  «No field „compny“ on this order and no such definition: orders_checkout_fields_list lists them».
- `orders_history` — строка `details`, как у контактов. `orders_list` полей не отдаёт.

### 8.3. Предпросмотр оформления

- Ресурс `orders://checkout` — определения полей, типы, пределы (§2.1, §3.1), коды `fields.*`.
  Собирается из класса и таблицы, не рукой.
- `orders_checkout_steps` — шаг `extra` с позицией; нет активных полей — причина в `whyNot()`.
- `orders_checkout_preview` — новый блок `fields`: `[{key, place, required, shown, filled}]` для корзины.
  `shown` — видно ли поле при текущем флажке, `filled` — заполнено ли. **Значений нет:** черновик — это
  человек, который ещё не оформил заказ, и MCP такие данные не отдаёт целиком (§32 заказов). Ошибки
  полей — в `steps`, как у всех шагов, под `extra.<key>`.
- `orders_checkout_drafts_list` значений полей не показывает.
- `orders_checkout_preview` — в `PerformanceTest` тёплым, как и был.

## 9. Безопасность, права, персональные данные

| Что                 | Кто                                                                                                            |
| ------------------- | -------------------------------------------------------------------------------------------------------------- |
| Определения: читать | сайт — покупатель видит только активные; панель и MCP — `orders.checkout.settings`, MCP-чтение — `orders.view` |
| Определения: менять | `orders.checkout.settings`                                                                                     |
| Значения: читать    | покупатель своего заказа; `orders.view`                                                                        |
| Значения: править   | `orders.manage`                                                                                                |

- **Значения — данные покупателя, как контакты.** Они видны: на «Спасибо» (сессия оформившего), на
  странице по подписанной ссылке, в кабинете владельца, в письмах и Telegram-каналах, в журнале отправок
  уведомлений, в карточке и журнале панели, в `orders_get`. Больше нигде.
- **Не попадают:** в `data-*` страницы «Спасибо» и счётчики (§26 заказов), в `orders_list`, в
  `orders_checkout_drafts_list`, в поиск.
- **Экспорта заказов нет,** значит, и выгрузки значений нет. Появится — поля подчиняются праву
  `orders.view`.
- **Удаление и обезличивание.** Обезличивания заказа в v1 нет (решение 35 заказов), значения живут со
  снимком, как контакты. При удалении посетителя снимок остаётся (§13.2 заказов). Брошенный черновик уходит
  чисткой вместе с корзиной (§21.3 заказов).
- **Что нельзя спрашивать.** Поле — обычный текст в письмах и журнале: подсказка над списком (§7.2) говорит
  не собирать номера карт, пароли и документы. Запрета в коде нет: поле не знает, что в него пишут.
- **Вход покупателя.** Сервер принимает только ключи активных полей этого места, остальное отбрасывает;
  вариант сверяется с определением; длины ограничены. Шаг идёт тем же маршрутом
  `POST /checkout/steps/{key}` с его защитой; новых точек входа нет.
- **Вывод.** Blade `{{ }}`, Mustache — экранирование провайдера, панель — текстом, без `v-html`. `label` и
  `hint` администратора — тоже простой текст.
- **Новые маршруты** — под `cms.can`, новые инструменты — с `permission:`; `AccessCoverageTest` пакета
  зелёный, открытых маршрутов не добавляется.

1. **«Дополнительно» — отдельный шаг или часть шага «Комментарий»?** Решение 1 говорит «в блоке
   „Дополнительно“ перед комментарием». Предложение: отдельный шаг `extra`, позиция 850. Комментарий
   выключается настройкой, а поля должны остаться; шаг не появляется, если полей нет.
2. **Условие только внутри одного места и в один уровень.** Предложение: да (§3.3). Примеры решения 3
   укладываются, а поле в другой форме нельзя честно проверить при её сохранении.
3. **Звёздочка у обязательного зависимого поля.** Браузерный `required` на скрытом поле мешает отправке,
   поэтому такое поле идёт без него и без звёздочки, как поля получателя. Предложение: оставить; если
   нужна звёздочка — отдельный проп `<x-webx-field>` в `widgets`, правка общего компонента.
4. **Имя переменной — `field.<key>`, а не `fields.<key>` из примера задачи.** Причина — §5.3: одно имя
   не может быть и списком, и картой. Предложение: `fields` и `field.<key>`.
5. **Быстрый заказ и заказ из панели без полей.** Предложение: не спрашивать, обязательность не действует,
   менеджер заполняет в карточке (§4.5). Если заказ менеджера должен спрашивать поля сразу — это ещё один
   экран и аргумент `orders_create`, отдельным этапом.
6. **Сохранённые шаблоны каналов.** Новый цикл попадает только в шаблоны по умолчанию; существующие каналы
   магазин правит сам. Предложение: так и оставить — код не должен переписывать чужой шаблон. На lab и
   демо-каналах проверим с шаблоном по умолчанию.
