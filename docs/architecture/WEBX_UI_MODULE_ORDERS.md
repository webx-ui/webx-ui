# `webx-ui/module-orders` — заказы — спецификация

Статус: спроектировано, ждёт приёмки (webx-ui#56, этап 1); пакет не начат. Карта семейства —
[`WEBX_UI_COMMERCE.md`](WEBX_UI_COMMERCE.md): принципы, цепочка итогов, события заказа. Корзина,
из которой строится снимок, — [`WEBX_UI_MODULE_CART.md`](WEBX_UI_MODULE_CART.md). Соседи, которые
к заказу подключаются: доставка — [`WEBX_UI_MODULE_DELIVERY.md`](WEBX_UI_MODULE_DELIVERY.md) (§11),
посетители — [`WEBX_UI_MODULE_USERS.md`](WEBX_UI_MODULE_USERS.md) (§11, §13.4, §14.1), уведомления
— [`WEBX_UI_MODULE_NOTIFICATIONS.md`](WEBX_UI_MODULE_NOTIFICATIONS.md) (§5, §8). Пакет —
`webx-ui/module-orders` (composer, namespace `WebxUi\Orders`, словарь `webx-orders`), npm-пара —
`@webx-ui/module-orders` (раздел панели). Id модуля — `orders` (области MCP `orders:read` /
`orders:write`, права `orders.*`, §11.1).

Заказ — снимок корзины в момент оформления: строки, цены, скидки, привилегии, зачтённые оплаты,
контакты покупателя и получателя, комментарий, а если установлены доставка и оплата — их блоки.
После создания заказ не зависит ни от одной живой записи: ни от товара, ни от правила скидки, ни от
точки выдачи. Дальше у заказа две оси: **вехи** — системные факты, на которые опираются события и
спутники (оплачен, получен, отменён), и **статусы** — рабочие этапы магазина, которые сайт
настраивает сам и которые покупатель видит сгруппированными в публичные.

## 1. Границы

**Внутри:**

- таблицы заказа, строк, корректировок, оплат, привилегий, вех, возвратов, истории статусов и двух
  наборов статусов (§3); номер заказа (§4);
- создание заказа из корзины: транзакция, блокировки, сверка суммы, идемпотентность (§6) — API
  `Orders::place()`, который зовёт оформление;
- вехи, внутренние и публичные статусы, свободные переходы, история (§5, §8);
- события заказа с полезной нагрузкой (§7); отмена, полный и частичный возврат (§9);
- блоки снимка `delivery` и `payment` — место и API записи, без знания о способах (§6.4);
- автоотмена неоплаченного по настройке (§5.5);
- раздел панели: список, карточка, статусы, настройки (§11); MCP (§12);
- события и переменные для `module-notifications`, привязка каналов к публичным статусам и вехам
  (§10);
- страница заказа для покупателя по подписанной ссылке; «Мои заказы» в кабинете и вкладка в
  карточке посетителя — только если стоит `module-users` (§13);
- словарь `webx-orders` (§14), демо-данные (§15).

**Рядом, но в чужом пакете:**

- **Шаги оформления** — `module-checkout`: форма контактов, выбор доставки и оплаты, показ суммы,
  кнопка «Оформить». Он собирает вход `PlaceOrder` (§6.1) и зовёт `Orders::place()`.
- **Блок доставки** — `module-delivery`: `DeliverySnapshot` (§11.1 его спеки), накладная и
  трекинг; веху «получен» он ставит через API вех (§5.3), вкладку карточки — патчем экрана (§11.3).
- **Блок оплаты** — `module-payments` (спека ещё не написана): способ, переход в шлюз,
  подтверждение; вехи «оплачен» и «оплата не прошла» — через API вех; возврат денег шлюзом — через
  реестр §9.4.
- **Реакции на заказ** — кошелёк, лояльность, сертификаты, склад, учёт слушают события §7 сами;
  контракт `Purchasable` о заказе не знает (решение 4).
- **Цепочка итогов** — один вычислитель `module-cart` (§5.3 его спеки); заказ его не повторяет, а
  зовёт с `Purpose::Order`.

**Снаружи:**

- налоги, счета и закрывающие документы, печатные формы, кроме накладной доставки;
- правка состава заказа после оформления (вопрос 4 §18);
- заказ, созданный менеджером в панели без корзины (вопрос 3 §18);
- склад, резервы, выгрузка в учётную систему — интеграции на событиях;
- автоматический перевод во внутренний статус по вехе (решение 15, вопрос 12 §18).

### 1.1. Без соседей

`module-orders` требует только `module-cart` (снимок строится из его `CartState`). Всё прочее — в
`suggest` и подключается по `class_exists` в `boot()`:

| Нет модуля             | Что меняется                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------- |
| `module-checkout`      | заказы создаёт только код сайта или тест через `Orders::place()`; раздел панели работает            |
| `module-delivery`      | `delivery` в заказе — `null`; вкладки «Доставка» нет; «получен» ставит менеджер                     |
| `module-payments`      | `payment` — `null`; «оплачен» ставит менеджер или статус с вехой; возврат — только «вручную»        |
| `module-users`         | `user_id` всегда `null`; нет «Моих заказов» и вкладки в карточке посетителя; страница по ссылке     |
| `module-notifications` | писем и сообщений нет; блока «Уведомления» в статусах и настройках нет; `webx:doctor` предупреждает |

## 2. Принятые решения (не переоткрывать)

Решения человека от 23.10.2026 и 27.10.2026 (спецификация задачи webx-ui#56); при расхождении
действуют решения 27.10.

1. **Заказ — снимок.** Строки хранят `type`, `ref_id`, `sku`, название, подпись опций, цену,
   скидку, итог строки, количество и `parent_id` (комплект, набор — родитель с детьми). После
   оформления заказ не зависит от живых записей.
2. **Цена и скидки замораживаются в момент оформления;** в корзине они живые.
3. **В заказ переходят привилегии** (benefits: «доставку оплачивает магазин» — отметка для
   менеджера и накладной) **и зачтённые оплаты** (tenders: сертификаты, кешбек — это оплата, не
   скидка).
4. **Реакция на заказ не входит в контракт `Purchasable`:** модули слушают события сами.
5. **Вехи с датами и событиями:** `OrderPlaced`, `OrderPaid`, `OrderReceived`. «Получен» приходит
   из интеграции доставки (трекинг) или ставится менеджером вручную. Отмена и возврат — тоже события
   (кошелёк возвращает списанное, кешбек `pending` отменяется).
6. **Раздел в панели:** список, карточка, смена статусов. **MCP — полный.**
7. **Без соседей.** `module-orders` работает без `module-users`, `module-delivery`,
   `module-payments` и будущих спутников. Заказ сам хранит снимок контактов покупателя (имя,
   телефон, e-mail) и получателя, если он другой. Доставка и оплата — необязательные блоки снимка
   (ключ способа, подпись, цена или «по тарифам перевозчика», детали); их заполняет тот модуль,
   который установлен. Без них заказ — строки, контакты и комментарий.
8. **Покупатель — необязательная ссылка** (`user_id`), только если стоит `module-users`; гостевой
   заказ — норма.
9. **«Мои заказы»** — раздел, который `module-orders` регистрирует в реестре меню кабинета
   `module-users`, только если тот установлен.
10. **Заказ с онлайн-оплатой создаётся до оплаты:** веха «ожидает оплаты», затем переход в шлюз.
    Неоплаченный заказ виден менеджеру (фильтры «ожидает оплаты» / «оплата не прошла»): уточнить,
    сменить способ, отметить оплату вручную, отменить. Автоотмена через N часов — настройка; отмена
    — обычное событие. Модель статусов и вех не знает конкретных способов оплаты.
11. **Статусы — три уровня.** Внутренние — свой набор у сайта (создать, переименовать, порядок,
    цвет, названия на языках сайта, выключить), покупатель их не видит. Публичные — тоже
    настраиваемые (название на языках, порядок), их видит покупатель в кабинете, письмах и на
    странице заказа. Каждый внутренний привязан к одному публичному. Вехи — системные и
    фиксированные: оформлен, ожидает оплаты, оплачен, получен, отменён, возвращён.
12. **Смена внутреннего статуса внутри одной публичной группы** для покупателя ничего не меняет и
    уведомления не шлёт. Уведомления покупателю — по смене **публичного** статуса, настраиваются по
    нему.
13. **Внутренний статус может ставить веху** («Передан в доставку — оплачено» ставит «оплачен»).
    Спутники и интеграции работают с вехами, а не с названиями статусов.
14. **Удаление статуса — мягкое, с восстановлением,** перед удалением — понятный текст о
    последствиях. **Переходы свободные,** история смен пишется (кто, когда, из какого в какой).
15. **Автосмена статуса по трекингу — не сейчас:** интеграции ставят только вехи; точка
    расширения остаётся (вопрос 12 §18).
16. **Статусы обоих уровней — через MCP:** список, создание, правка, удаление и восстановление,
    перевод заказа в статус с `dry_run`.

Решения спеки (предложены здесь; спорное — в §18):

17. **Таблицы — `orders` и `order_*`** (§3), по образцу `carts` / `cart_items`, которые человек
    оставил корзине; карта коммерции писала `orders_*` (вопрос 1 §18).
18. **Номер заказа — строка от `id`,** без отдельного счётчика и без блокировки (§4).
19. **Вехи не снимаются** (журнал только дописывается); ошибочную оплату исправляет возврат или
    отмена (вопрос 5 §18).
20. **Система и интеграции ставят только вехи,** статус не трогают: автоотмена, шлюз и трекинг
    оставляют внутренний статус как был (решение 15). Покупатель видит отмену и оплату отметкой
    рядом с публичным статусом (§13.1).
21. **То, что должно случиться атомарно с заказом** (списание кошелька, резерв склада), —
    синхронный хук `OrderPlacing` внутри транзакции; реакции — `OrderPlaced` после коммита (§6.3,
    вопрос 6 §18).
22. **Заказ не удаляется** ни из панели, ни через MCP: это документ сделки. Обезличивание по
    просьбе человека — вопрос 17 §18.

## 3. Таблицы

Деньги — `bigint` в минимальных единицах валюты заказа (`orders.currency`), `float` нет нигде
(принцип 4 карты). Языковые поля снимка — json `{locale: text}`. Миграции откатываются (`down()` —
в обратном порядке).

## 4. Номер заказа

- **Номер — строка от `id`:** `format(prefix, start + id, pad)`; по умолчанию префикс пустой,
  `start = 1000`, `pad = 0` → `1001`, `1002`… Настройки `orders.number.*` (§11.4). Пишется в той же
  транзакции сразу после вставки (`UPDATE orders SET number = ? WHERE id = ?`).
- **Почему не счётчик:** отдельная таблица с `FOR UPDATE` сериализует все оформления сайта и
  добавляет третью блокировку к корзине и кошельку (§6.3). Пропуски в нумерации (откат транзакции
  съел `id`) для магазина без фискальной нумерации не важны.
- **Смена формата** не трогает выданные номера: номер хранится. Новый префикс не может дать номер,
  который уже есть, — `unique` поймает, настройка проверяет пробным номером при сохранении.
- Поиск в панели и MCP принимает номер и `id`; покупатель и письма видят только номер. Сквозной
  счёт, сброс по годам или случайный номер — вопрос 11 §18.

## 5. Вехи и статусы

### 5.1. Вехи

Закрытый список `WebxUi\Orders\Milestone` (enum), порядок — как на временной шкале карточки:

| Веха               | Кто ставит                                                      | Событие                 | Повтор |
| ------------------ | --------------------------------------------------------------- | ----------------------- | ------ |
| `placed`           | только `Orders::place()`                                        | `OrderPlaced`           | нет    |
| `awaiting_payment` | `Orders::place()` при `awaitPayment: true` (§6.1)               | — (часть `OrderPlaced`) | нет    |
| `paid`             | оплата (`payment:<шлюз>`), менеджер, агент, статус с вехой      | `OrderPaid`             | нет    |
| `received`         | доставка (`delivery:<служба>`), менеджер, агент, статус с вехой | `OrderReceived`         | нет    |
| `cancelled`        | менеджер, агент, статус с вехой, автоотмена (`system`)          | `OrderCancelled`        | нет    |
| `refunded`         | только возврат, когда вернули всё (§9.2)                        | `OrderRefunded` (full)  | нет    |

- **Повторная веха** — не ошибка, а тишина: `mark()` отвечает `AlreadyMarked` с датой и источником
  первой, событие не бросается. Так трекинг, который пришёл после ручной отметки менеджера, ничего
  не двоит (§11.4 спеки доставки).
- **`paid` снимает `awaiting_payment` и `payment_failed_at`** (колонки на `orders`; строка
  `awaiting_payment` в `order_milestones` остаётся — это история).
- **Что нельзя:** `paid` у отменённого — отказ `OrderCancelledAlready` (деньги пришли на отменённый
  заказ — это возврат, а не оплата; менеджер видит строку истории от шлюза, §5.4); `received` у
  отменённого — отказ; `cancelled` у полностью возвращённого — тишина.
- Вехи не снимаются (решение 19, вопрос 5 §18).

### 5.2. Статусы: внутренний и публичный

- У заказа хранится только внутренний (`orders.status_id`); публичный — `status.publicStatus`.
  Покупатель видит публичный, менеджер — оба (внутренний крупно, публичный мелко рядом).
- **Новый заказ** встаёт в статус из настроек: `orders.initial_status` — для обычного,
  `orders.initial_status_awaiting_payment` — для заказа с `awaitPayment` (по умолчанию «Ожидает
  оплаты»). Оба — активные и не удалённые; удалить или выключить такой статус нельзя, пока он
  выбран в настройке (отказ со ссылкой на настройку).
- **Переходы свободные** (решение 14): из любого в любой активный, в том числе назад. Перевод в
  тот же статус — тишина.
- **Перевод в статус с `sets_milestone`** ставит веху тем же вызовом с источником `status#<id>`,
  если её ещё нет; если веха запрещена (§5.1 «что нельзя») — перевод отказывает целиком, чтобы
  статус «Оплачен» не стоял у отменённого заказа. Уход из такого статуса веху не снимает.
- **Статус и веха расходятся законно:** шлюз поставил «оплачен», а заказ стоит в «Ожидает оплаты»
  — пока менеджер его не переставит (решение 20). Список подсвечивает такие заказы фильтром
  «оплачен, а статус ждёт оплаты» — это просто веха + статус в фильтре, а не особая логика.

### 5.3. API

```php
namespace WebxUi\Orders;

final class Orders
{
    /** §6 — the only way an order comes to be. */
    public function place(PlaceOrder $input): Order;

    /**
     * Set a milestone once. Throws a Refusal (§5.1 «what is not allowed»); a repeat returns the
     * first mark and dispatches nothing.
     */
    public function mark(
        Order $order,
        Milestone $milestone,
        string $source,                    // 'payment:gateway-a', 'delivery:carrier-a', 'panel'
        ?CarbonInterface $at = null,       // when it happened; default now
        ?string $reference = null,         // payment id, waybill number
        ?string $note = null,
    ): MilestoneMark;

    /** A failed payment try: a history line and payment_failed_at, not a milestone (§5.4). */
    public function paymentFailed(Order $order, string $source, ?string $reason = null): void;

    /** Free transition (§5.2); dry-run tells what would happen without doing it. */
    public function moveTo(Order $order, OrderStatus $to, string $source, ?string $note = null,
        bool $dryRun = false): StatusMove;

    /** Write a part of a block (§6.4): the waybill number into `delivery`, a new method into `payment`. */
    public function patchBlock(Order $order, string $block, array $patch, string $source): void;

    /** A line in the order's history from a module: «the parcel came back». */
    public function note(Order $order, string $text, string $source): void;

    public function cancel(Order $order, string $source, ?string $reason = null): MilestoneMark;

    public function refund(Order $order, RefundRequest $request, bool $dryRun = false): RefundResult;
}
```

- Автор (`admin_id`) берётся из гарда `cms`, если вызов пришёл из панели или MCP; интеграции и
  команды — `null`, их видно по `source`.
- Каждый метод — одна транзакция с `SELECT … FOR UPDATE` строки заказа: шлюз и менеджер, которые
  отмечают оплату одновременно, не дадут двух событий.
- `StatusMove` (ответ `moveTo`, в том числе на `dry_run`): `from`, `to`, `publicFrom`, `publicTo`,
  `publicChanged`, `milestone` (что поставится), `notifications` (какие каналы получат сообщение —
  §10.2), `refusal` (почему нельзя).

### 5.4. Оплата не прошла

Шлюз отвечает «отказ» или покупатель вернулся без оплаты → `module-payments` зовёт
`paymentFailed()`: строка истории `kind = payment_failed` с причиной, `orders.payment_failed_at =
now()`, событие `OrderPaymentFailed`. Заказ остаётся «ожидает оплаты»; повторная попытка оплаты —
дело оформления и оплаты. Фильтр «оплата не прошла» = `awaiting_payment AND payment_failed_at IS
NOT NULL`. Седьмая ли это веха — вопрос 9 §18.

Деньги, пришедшие на отменённый заказ: `mark(paid)` отказывает, а модуль оплаты пишет `note()` («Платёж
… пришёл после отмены») — менеджер решает возвратом.

### 5.5. Автоотмена неоплаченного

- Настройка `orders.unpaid_cancel_after_hours` (`null` — выключено, по умолчанию `null`).
- Команда `webx:orders:cancel-unpaid [--dry-run]` в расписании каждые 10 минут: `awaiting_payment
= true AND cancelled_at IS NULL AND placed_at < now() − N` по индексу, пачками по 100, каждый —
  `cancel(source: 'system', reason: 'unpaid_timeout')`. Статус не меняется (решение 20).
- Одна неудачная отмена (слушатель `OrderCancelled` упал) не останавливает пачку: лог и следующий
  заказ; отмена уже записана — слушатели после коммита (§7.1).

### 5.6. Удаление и восстановление статусов

**Внутренний статус.** Перед удалением панель и MCP (`dry_run`) показывают:

> В статусе «Кладовщик ищет» 14 заказов. Они останутся в нём — в списке статус будет помечен
> «удалён», новые заказы в него не переводятся. Покупатели по-прежнему видят «В работе». Уведомлений
> не будет. Статус можно восстановить в разделе «Статусы → Удалённые».

- Удалённый статус: не предлагается при смене, виден в фильтре списка с пометкой «удалён» (чтобы
  найти оставшиеся заказы), в истории — с пометкой. Заказ из него уходит обычным переводом; назад
  — нельзя.
- Нельзя удалить статус из настроек «начальный» (§5.2) и последний активный статус публичной
  группы, в которой есть заказы, — иначе им некуда идти внутри группы; отказ объясняет, что сделать.
- **Восстановление** возвращает статус как был (имя, место, веха). Если его публичный удалён —
  отказ «Сначала восстановите „В работе“ или выберите другую группу» (правка привязки разрешена и у
  удалённого).

**Публичный статус.** Удалить можно, только когда в нём нет **активных** внутренних: панель
показывает их списком и предлагает перенести в другую группу одним действием. Заказы в удалённых
внутренних этой группы продолжают показывать покупателю прежнее название (строка не удаляется
физически). Каналы уведомлений удалённого публичного не срабатывают.

**Перепривязка** внутреннего к другому публичному меняет то, что покупатель видит у всех заказов в
этом статусе, — сразу, без уведомлений; перед сохранением панель говорит число таких заказов.

## 6. Снимок из корзины

### 6.1. Вход

```php
namespace WebxUi\Orders;

final readonly class PlaceOrder
{
    public function __construct(
        public Cart $cart,                     // WebxUi\Cart\Models\Cart
        public string $locale,
        public Contact $customer,              // name, phone, email — at least a name and one of the two
        public ?Contact $recipient = null,     // null — the customer receives
        public ?string $comment = null,
        public ?int $expectedPayable = null,   // what the buyer saw; null — no check (code, tests)
        public bool $awaitPayment = false,     // the chosen payment is online (§5.1)
        public array $blocks = [],             // 'delivery' => DeliverySnapshot->toArray(), 'payment' => […]
        public ?string $idempotencyKey = null, // the checkout's form token
        public ?int $userId = null,            // Visitors::current()?->id; the checkout passes it
        public string $source = 'checkout',
    ) {}
}
```

- `awaitPayment` приходит от оформления (оно знает выбранный способ оплаты); заказ про способы не
  знает (решение 10).
- `userId` передаёт вызывающий: заказ не читает `Visitors::current()` сам, чтобы `place()` из
  команды или теста не зависел от запроса.
- Контакты проверяет `Contact` (имя ≤ 190, телефон — `+` и цифры с разделителями, e-mail —
  `email:filter`); что из них обязательно в форме — решает оформление; заказу нужно имя и хотя бы
  телефон или e-mail.

### 6.2. Порядок

```
DB::transaction:
 1. повтор?        idempotencyKey уже есть в orders → вернуть тот заказ, ничего не делать
 2. замок корзины  SELECT … FROM carts WHERE id = ? FOR UPDATE
 3. пересчёт       Calculator::calculate(cart, locale, Purpose::Order) — исключение источника летит
                   дальше (§5.4 спеки корзины): заказ по неполной цепочке не создаётся
 4. проверки       корзина не пуста; нет строк line.unavailable / line.qty_limited; валюта корзины
                   = валюта сайта; payable == expectedPayable → иначе PayableChanged(новое состояние)
 5. блоки          ключи blocks зарегистрированы в OrderBlocks (§6.4), значения проходят схему блока
 6. запись         orders (number = null) → number → order_items (родители, потом дети, карта id)
                   → order_adjustments (line → item_id) → order_tenders → order_benefits
                   → order_milestones (placed [, awaiting_payment]) → order_status_changes (null → начальный)
 7. хук            OrderPlacing (синхронно, в транзакции) — слушатель может отказать (§6.3)
 8. корзина        строки корзины удаляются; корзина остаётся пустой (cookie жив)
commit → OrderPlaced и остальные события после коммита (§7.1)
```

- **Сверка суммы** (§4 карты): `PayableChanged` несёт свежий `CartState`; оформление показывает
  покупателю новую сумму, заказ не создан. Сравнивается `payable`, а не `total`: покупатель платит
  его.
- **Строки, которые нельзя купить,** не выкидываются молча: отказ `CartNotOrderable` со списком
  строк и кодами предупреждений корзины — оформление показывает их покупателю.
- **Генерируемые строки** (подарки правил) попадают в заказ обычными строками с `source` и `label`;
  отказанные (`declined_rules`) — нет, их нет и в `CartState`.
- **Корзина** чистится методом корзины (`Carts::clear()` — нужен в `module-cart`, если его там ещё
  нет; правка — в этапе 3 этой задачи, вопрос 16 §18). `declined_rules` сбрасываются тоже.

### 6.3. Блокировки

Порядок замков всегда один — так оформления не ловят взаимную блокировку:

1. строка `carts` (шаг 2) — один и тот же покупатель не оформит корзину дважды в двух вкладках;
2. замки источников цепочки при `Purpose::Order` (кошелёк блокирует свои партии, §3.2 карты);
3. замки слушателей `OrderPlacing` (склад — свои остатки).

`OrderPlacing` — синхронное событие внутри транзакции с уже записанным заказом (`Order` с id и
номером). Его слушатель делает то, что должно случиться **вместе** с заказом или не случиться
вовсе: кошелёк списывает зачтённое (а не на `OrderPlaced`, как писала карта, — после коммита
списание может не пройти, а заказ уже есть; вопрос 6 §18), склад резервирует. Отказ —
`throw new OrderRefused(code, message)`: транзакция откатывается, оформление показывает `message`.
Медленного (HTTP к шлюзу, письма) в нём быть не должно — это `OrderPlaced`.

### 6.4. Блоки снимка

```php
namespace WebxUi\Orders\Blocks;

final class OrderBlocks
{
    /** A module that fills a block registers it in boot(), under class_exists(OrderBlocks::class). */
    public function register(BlockDefinition $block): void;
}

final readonly class BlockDefinition
{
    public function __construct(
        public string $key,              // 'delivery' | 'payment' — the column it lands in
        public string $module,           // 'delivery'
        public Closure $validate,        // fn (array $value): list<string> — errors; empty — accepted
        public ?Closure $summary = null, // fn (array $value, string $locale): string — one line for the list and mail
    ) {}
}
```

- Колонок две — `delivery` и `payment`; новых ключей реестр не принимает (третий блок — новая
  колонка и решение человека). Реестр нужен, чтобы заказ проверял форму блока руками владельца и
  показывал строку блока в списке и письме, не зная способов.
- **Общая часть блока,** которую заказ читает сам: `method` (ключ способа), `title` (`{locale:
text}`), `price` (`{kind, amount, currency, in_total, …}` — у доставки, §9.3 её спеки; у оплаты —
  комиссия, если есть). Остальное (`point`, `address`, `waybill`, `gateway`) заказ хранит как есть и
  показывает только через вкладку модуля-владельца; без неё — свёрнутым JSON для менеджера.
- `patchBlock()` сливает `patch` в блок (`array_replace_recursive`), проверяет `validate`, пишет
  строку истории `kind = block` и бросает `OrderBlockUpdated`. Так доставка кладёт номер накладной
  (§11.2 её спеки), оплата — смену способа, которую менеджер сделал с покупателем по телефону.

## 7. События и полезная нагрузка

### 7.1. Как бросаются

- Классы — `WebxUi\Orders\Events\*`, все `ShouldDispatchAfterCommit` (кроме `OrderPlacing`):
  слушатель не увидит заказ, которого нет, и не сработает на откаченный.
- **Каждое несёт `OrderData`** — неизменяемый снимок заказа на момент события (принцип: событие
  несёт заказ-снимок, §6 карты), сериализуемый для слушателей в очереди. Слушатель, которому нужна
  модель, берёт её по `$event->order->id`.
- Общие поля каждого события, кроме `OrderData`: `source` (string), `adminId` (?int), `at`
  (`CarbonImmutable`).

```php
final readonly class OrderData
{
    public function __construct(
        public int $id,
        public string $number,
        public ?int $userId,
        public string $locale,
        public string $currency,
        public int $subtotal, public int $adjustmentsTotal, public int $total,
        public int $tendersTotal, public int $payable, public int $refundedTotal,
        public ContactData $customer,
        public ?ContactData $recipient,
        public ?string $comment,
        /** @var list<ItemData> */ public array $items,        // id, parentId, type, refId, sku, name (locale), optionsLabel, price, qty, total, shippable, source, refundedQty
        /** @var list<AdjustmentData> */ public array $adjustments,
        /** @var list<TenderData> */ public array $tenders,    // id, source, amount, refundedAmount, meta
        /** @var list<string> */ public array $benefits,      // keys

        public ?array $payment,

```

### 7.2. Список

| Событие                    | Когда                                               | Полезная нагрузка сверх общей                                                     | Кто слушает (на карте)                                                                                                   |
| -------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |

| `OrderBlockUpdated`        | `patchBlock()`                                      | `string $block`, `array $patch`                                                   | уведомления («номер отправления»), интеграции                                                                            |
| `OrderDetailsChanged`      | менеджер поправил контакты, получателя, комментарий | `list<string> $fields`                                                            | учёт; доставка (получатель в неотправленной накладной)                                                                   |

- **Отмена и возврат — отдельные события, а не общее «веха поставлена»** (вопрос из §6 карты):
  кошельку и лояльности нужны разные данные — отмене достаточно заказа (вернуть всё), возврату нужна
  сумма и строки. Общего `OrderMilestoneReached` нет: слушатель, которому нужны все вехи, слушает
  нужные классы.
- `OrderCancelled` у оплаченного заказа **не возвращает деньги**: `wasPaid = true` — сигнал
  менеджеру и уведомлениям; возврат денег — `refund()` (§9.1).
- Порядок при переводе в статус с вехой: `OrderStatusChanged` → `OrderPublicStatusChanged` (если
  сменился) → событие вехи; все — после одного коммита.

## 8. История

Карточка показывает одну временную шкалу, собранную из трёх таблиц по времени:

- `order_status_changes` — смены статуса (из какого в какой, публичный рядом, если сменился),
  заметки модулей (`note()`), неудачные оплаты, правки блоков;
- `order_milestones` — вехи с источником и `reference`;
- `order_refunds` — возвраты.

Строка: время (`WxDate`), кто (администратор по `admin_id` — имя из `cms_users`, иначе источник
словами: «Шлюз оплаты A», «Служба доставки A», «Система», «Агент: имя администратора» для `mcp`),
что, заметка. С `module-notifications` — блок «Уведомления» под шкалой: строки журнала отправок по
`subject` заказа (`Notifications::deliveriesFor`, §8.1 его спеки).

Правки контактов, комментария и заметки менеджера идут в общий журнал истории панели
(`webx.history`, [`WEBX_UI_HISTORY.md`](WEBX_UI_HISTORY.md)) и в шкалу — строкой «Изменены
контакты». Сами деньги, строки и вехи не правятся вовсе.

## 9. Отмена и возврат

### 9.1. Отмена

- Веха `cancelled` — `cancel()` или перевод в статус с `sets_milestone = cancelled`. Причина —
  обязательна из панели и MCP (строка), у системы — код `unpaid_timeout`.
- Что происходит у соседей — их слушатели `OrderCancelled`: кошелёк возвращает все зачёты заказа,
  лояльность отменяет `pending`, склад снимает резерв.
- Оплаченный заказ отменяется так же, но панель предупреждает: «Заказ оплачен на 120,00. Отмена не
  вернёт деньги — оформите возврат» и предлагает следующим шагом диалог возврата.
- После отмены нельзя: `paid`, `received`, возврат зачётов (их уже вернула отмена). Возврат денег —
  можно (это и есть случай «оплачен, отменён»).

### 9.2. Полный возврат

`refund()` на всю невозвращённую часть: `amount = payable − refunded_total`, все зачёты целиком,
все строки целиком. Когда после записи возврата `refunded_total = payable` и все зачёты вернулись —
ставится веха `refunded` и `OrderRefunded` идёт с `full = true`. Отмены возврат не ставит: товар,
который вернули после получения, — заказ «получен» и «возвращён», это правда.

### 9.3. Частичный возврат

```php
final readonly class RefundRequest
{
    public function __construct(
        public int $amount,                 // money back, minor units; 0 — only tenders
        public array $tenders = [],         // tender id → amount back to the wallet
        public array $items = [],           // item id → qty returned; empty — a money-only refund
        public string $method = 'gateway',  // 'gateway' | 'manual' (§9.4)
        public ?string $reason = null,
        public string $source = 'panel',
    ) {}
}
```

- Проверки: `amount ≤ payable − refunded_total`; каждый зачёт — не больше его остатка; `qty` строки
  — не больше `qty − refunded_qty`; хоть что-то не ноль.
- **Подсказка суммы** в диалоге: выбранные строки по их `total` пропорционально `qty`, дальше
  делится между деньгами и зачётами в той же доле, в какой заказ был оплачен (`payable` :
  `tenders_total`). Менеджер правит обе цифры. Это предложение, правило — вопрос 7 §18.
- Возврат строки не меняет `order_items.total` и итоги заказа: снимок неизменен, возвраты лежат
  рядом. Карточка показывает «Возвращено: 1 из 2» и «К оплате … / возвращено …».

### 9.4. Деньги через шлюз

```php
namespace WebxUi\Orders\Refunds;

/** A payment module that can give money back through its gateway. */
interface RefundsPayments
{
    /** Whether this order's payment can be refunded online, and how much at most. */
    public function refundable(Order $order): ?int;

    /** @throws RefundFailed — with the gateway's reason in words; nothing is recorded then */
    public function refund(Order $order, int $amount, ?string $reason): string;   // gateway reference
}
```

- Реестр `RefundGateways::register(string $method, RefundsPayments $handler)` по ключу способа
  оплаты из блока `payment.method`. `module-payments` регистрирует, заказ о шлюзах не знает.
- `method = 'gateway'` и обработчик есть → сначала `refund()` у шлюза (вне транзакции заказа:
  HTTP), успех → запись возврата с `reference`; отказ шлюза → ничего не записано, менеджер видит
  слова шлюза. Обработчика нет или блок `payment = null` → доступен только `manual` («деньги
  вернули вне сайта»).
- Шлюз вернул деньги, а запись упала — лог `critical` и строка `webx:doctor`; повтор с тем же
  `reference` не вызывает шлюз второй раз. Синхронный вызов против слушателя — вопрос 8 §18.

## 11. Панель

Раздел «Заказы» (`orders`). Экраны — JSON ([`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md)) с
публичными `id` узлов для патчей соседей; npm-пара `@webx-ui/module-orders` регистрирует раздел и
свои типы узлов (`wx-orders-items`, `wx-orders-timeline`, `wx-orders-status`).

### 11.1. Права

| Право             | Что даёт                                                                                             |
| ----------------- | ---------------------------------------------------------------------------------------------------- |
| `orders.view`     | список, карточка, история — чтение; MCP `orders:read`                                                |
| `orders.manage`   | смена статуса, вехи «оплачен» / «получен» вручную, отмена, контакты и заметка, блоки; `orders:write` |
| `orders.refund`   | возвраты — отдельно: деньги                                                                          |

Права — в `OrdersModule::permissions()` и `### Permissions` `AGENTS.md`; маршруты — `cms.can`;

### 11.2. Список — `orders.index`

- Колонки: номер, дата оформления, покупатель (имя, телефон), состав коротко («Item A и ещё 2»),
  итог и «к оплате», внутренний статус (цветной `WxBadge`) с публичным мелко, отметки вех (оплачен,
  получен, отменён, возврат), строка доставки и оплаты (`summary` блоков).
- Поиск — номер, телефон в любом написании (`customer_phone_key`), e-mail, имя.
- Фильтры: внутренний статус (с удалёнными, помечены), публичный, «ожидает оплаты», «оплата не
  прошла», оплачен / не оплачен, получен, отменён, есть возврат, период, гость / посетитель (если
  стоит users), способ доставки и оплаты (по `method` блока). Готовые вкладки над списком: «Новые»
  (начальный статус), «Ожидают оплаты», «Оплата не прошла», «Все».
- Массово: перевести в статус (с предпросмотром — сколько сменят публичный, сколько уведомлений
  уйдёт), отменить (с причиной).
- Один запрос на страницу + статусы одним запросом; превью состава — подзапросом первых строк, а не
  N+1 (`PerformanceTest`, §16).

### 11.3. Карточка — `orders.show`

- **Шапка:** номер, дата, выбор внутреннего статуса (группы — публичные, внутри — внутренние;
  выключенные и удалённые не предлагаются), рядом — что увидит покупатель; отметки вех; действия:
  «Отметить оплату», «Отметить получение», «Отменить», «Оформить возврат» (по правам и §5.1).
- **Смена статуса** — диалог с заметкой и строкой последствий из `dry_run` (`StatusMove`):
  «Покупатель увидит „Отправлен“, уйдёт письмо через канал „Покупателям“» или «Покупатель ничего не
  заметит». Статус с вехой — «Поставит отметку „Оплачен“».
- **Вкладки** (узел `tabs`): «Состав» (`wx-orders-items`: дерево строк, скидки строк, корректировки
  заказа, итоги, зачёты, привилегии отметками — «Доставку оплачивает магазин»), «Покупатель»
  (контакты, получатель, комментарий, заметка менеджера — правка; ссылка на посетителя, если
  `user_id` и стоит users), «История» (`wx-orders-timeline`, §8). Соседи добавляют свои вкладки
  патчем узла `tabs`: «Доставка» — `module-delivery` (§14.2 его спеки), «Оплата» — `module-payments`.
  Без вкладки владельца блок показывается в «Составе» строкой `summary` и свёрнутым JSON.
- Публичные `id` узлов: `header-actions`, `tabs`, `summary` (боковая карточка: итоги, вехи).

### 11.4. Статусы и настройки

- **`orders.statuses`** — две колонки: публичные (порядок перетаскиванием, название по языкам,
  описание, код, каналы уведомлений — если стоит notifications) и внутренние, сгруппированные по
  публичным (перетаскивание внутри и между группами = порядок и перепривязка, цвет из палитры,
  название по языкам, веха, «выключен»). Число заказов у каждого. Внизу — «Удалённые» с
  восстановлением. Удаление и перепривязка — с текстом последствий (§5.6).
- **`orders.settings`** (экран раздела, как `users.settings`): номер (префикс, начало, ширина —
  с пробным номером), начальные статусы (§5.2), автоотмена неоплаченного (часы), каналы
  уведомлений вех (§10.1).

## 12. MCP

Области `orders:read` / `orders:write`; права по правилу §6 спеки доступа (`orders:read` →
`orders.view`, `orders:write` → `orders.manage`; возвраты — `permission: 'orders.refund'`, статусы и
настройки — `permission: 'orders.statuses'`). Каждый изменяющий инструмент принимает `dry_run` и на

## 13. Покупатель

### 13.1. Страница заказа

- `GET /order/{number}` (внутри `{locale?}` сайта, `SiteRoutes::SERVICE`, `no-store`) — подписанная
  ссылка Laravel без срока (`URL::signedRoute`): её получает покупатель в письме и на странице
  «Спасибо» оформления. Подпись неверна → 404 (не 403: не подтверждать, что номер есть).
- Показывает: номер, дату, публичный статус с описанием и шкалой публичных статусов по порядку,
  отметки «Оплачен», «Получен», «Отменён», «Возвращено N» (решение 20: отмена видна, даже если
  статус не меняли), состав, суммы, блок доставки и оплаты строкой `summary`, контакты. Внутренний
  статус и заметка менеджера — никогда.
- Вьюха `webx-orders::order.show` на полях `widgets`, вид — тема. Подпись зависит от `APP_KEY`:
  смена ключа ломает старые ссылки — вопрос 14 §18.

### 13.2. «Мои заказы» и карточка посетителя (если стоит `module-users`)

- Раздел кабинета через `AccountMenu` и `AccountRoutes` ровно как в примере §11.2 спеки users:
  `/account/orders` — список своих заказов (`user_id = visitor.id`), `/account/orders/{number}` — та
  же страница, что §13.1, без подписи (владелец проверяется). `badge` — число незавершённых
  (нет `received`, `cancelled`) одним запросом.
- Вкладка «Заказы» в `users.form` — патч узла `tabs` (§11.3 спеки users) с `wx-orders-list` и
  фильтром `user`; в `summary` — «Заказов: N».
- `DeletionWarnings`: «Активный заказ №1024 будет выполнен, но вы не увидите его в кабинете»;
  слушатель `VisitorDeleting` ставит `user_id = null` у его заказов, снимок контактов остаётся
  (§14.1 спеки users).
- Гостевые заказы на тот же адрес после регистрации — вопрос 2 §18.

## 14. Слова

Словарь `webx-orders` на языки пакетов (паритет держит тест; `en`, `ru`, `uk` — вычитаны):

- `module.php` — название раздела, права, вехи (`milestones.paid` …), палитра цветов;
- `panel.php` — экраны, фильтры, действия, диалоги последствий (§5.6, §9.1), отказы;
- `statuses.php` — набор статусов по умолчанию (§15), из которого заполняются названия на всех
  языках сайта при установке;
- `notifications.php` — подписи событий и переменных, шаблоны по умолчанию;
- `order.php` — страница покупателя и кабинет; счёт — в конце строки («Товаров: :count»).

Даты в панели — `WxDate` / `useDates()`; на сайте и в письмах — формат языка заказа через `Dates`.
Деньги — только `Money::format()` корзины.

## 16. Производительность и кеш

- **Оформление** (`place()`): бюджет запросов фиксирует `PerformanceTest` — вставки строк,
  корректировок и зачётов пачками (`insert` на таблицу), не по одной; пересчёт корзины — один раз.
- **Списки панели** — без кеша (данные живые), с бюджетом и `assertNoRepeatedQueries`;
  `orders_summary` — `COUNT … GROUP BY` по индексам, без загрузки моделей.
- **Страница покупателя и кабинет** — `no-store`, не кешируются; статусы (оба набора) — в
  `CacheGroups::remember` группы `orders.statuses`, сброс — `bumpOn` моделей статусов.
- **Автоотмена и `cancel-unpaid`** — по индексу `(awaiting_payment, placed_at)`, пачками.

## 18. Открытые вопросы (решает человек)

1. **Имена таблиц.** Спека — `orders` и `order_*` (как `carts` / `cart_items`, решение 20 корзины;
   так же человек назвал `order_items` в задаче). Карта коммерции писала `orders_*` по правилу
   «таблицы раздела — под его именем». Оставить `order_*` или `orders_items`, `orders_milestones`…
2. **Гостевые заказы после регистрации** на тот же e-mail (вопрос 5 §20 спеки users). Варианты:
   (а) не показывать — в кабинете только заказы, оформленные со входом; (б) показывать заказы на
   **подтверждённый** адрес аккаунта — запросом по `customer_email`, без записи `user_id`; (в) при
   подтверждении адреса проставлять `user_id` гостевым заказам на этот адрес (раз и навсегда, с
   письмом «к аккаунту привязаны заказы»). Рекомендация — (в): в списке панели и отчётах видно
   владельца, а подтверждение адреса — та же проверка, что вход по ссылке из письма.
3. **Заказ из панели без корзины** («позвонили — оформи»): нужен ли в v1. Если да — экран сборки
   строк из поставщиков и `place()` от временной корзины; MCP `orders_create`.
4. **Правка состава после оформления** (замена товара, «нет в наличии — уберите строку»): сейчас
   снимок неизменен, возможен только возврат строки. Нужна ли правка с пересчётом — тогда версия
   снимка и событие `OrderAmended`.
5. **Снятие ошибочной вехи** («отметили оплату не тому заказу»): сейчас веха вечна, исправление —
   возврат (`manual`, без денег) или отмена. Нужно ли действие «снять веху» с правом и событием.
6. **Списание кошелька — в `OrderPlacing` (в транзакции), а не на `OrderPlaced`,** как писала карта
   (§6 карты). Спека предлагает транзакцию, чтобы заказ и списание были вместе или никак. Если
   оставить `OrderPlaced` — кошельку нужна своя компенсация, когда списание не прошло.
7. **Деление частичного возврата** между деньгами и зачётами: сейчас подсказка в доле оплаты
   (`payable : tenders_total`), решает менеджер. Варианты — сначала деньги, сначала зачёты, всегда
   пропорционально без правки.
8. **Возврат через шлюз** — синхронно из диалога (спека: шлюз отказал — ничего не записано) или
   «запросом» (`OrderRefundRequested`, шлюз отвечает позже, возврат записывается по ответу).
   Второе нужно шлюзам с отложенным возвратом.
9. **«Оплата не прошла»** — флаг и строка истории (спека) или седьмая веха `payment_failed`.
   Веха одна на заказ, а попыток бывает несколько, поэтому предложен флаг.
10. **Письма без `module-notifications`:** сейчас без модуля сообщений нет вовсе. Нужно ли
    встроенное письмо «новый заказ» менеджеру и «заказ принят» покупателю, как базовое письмо Inbox
    (решение 11 уведомлений).
11. **Формат номера:** от `id` с префиксом и началом (спека). Нужны ли сброс по годам
    (`2026-0001`), случайный номер (не выдаёт объём продаж) или фискальная сквозная нумерация.
12. **Автоперевод в статус по вехе** (решение 15 — не сейчас). Точка расширения: настройка
    «веха → внутренний статус» у вехи, применяется только если заказ стоит в статусе «ниже» по
    порядку. Когда делать и нужна ли «ниже».
13. **Покупателю по вехам:** уведомления покупателю идут по смене публичного статуса (решение 12),
    а шлюз ставит «оплачен» без смены статуса (решение 20) — покупатель о приходе оплаты не узнает,
    пока менеджер не переставит. Заводить ли каналы покупателя на `orders.paid` в наборе по
    умолчанию или ждать автоперевода (вопрос 12).
14. **Ссылка на страницу заказа** — подписанная без срока, зависит от `APP_KEY`. Альтернатива —
    свой токен в заказе (хешем, с возможностью отозвать), но тогда письмам после первого нужна
    ссылка без токена в открытом виде.
15. **Готовые роли:** роль «Менеджер заказов» (`orders.view`, `orders.manage`) в сидере, без
    `orders.refund` и `orders.statuses`; заодно — давать ли ей `users.view` (вопрос 10 §20 спеки
    users).
16. **`Carts::clear()`** — в спеке корзины нет метода, который заказ зовёт для очистки; добавить в
    `module-cart` этапом 3 этой задачи или в задаче корзины.
17. **Обезличивание заказа** по просьбе человека: заказ не удаляется (решение 22), контакты в нём —
    персональные данные. Нужна ли команда или действие «обезличить» (имя, телефон, e-mail, адрес в
    блоке доставки → «удалено»), и после какого срока заказ можно обезличивать.
18. **Свои поля заказа** (ИНН компании, время звонка): их добавит оформление. Хранить в колонке
    `extra` заказа по образцу своих полей users (§10 его спеки) — сейчас её нет.
