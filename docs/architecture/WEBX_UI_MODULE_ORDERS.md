# `webx-ui/module-orders` — заказы и оформление — спецификация

Статус: спроектировано. Заказы — webx-ui#56, оформление — webx-ui#58, обе спеки приняты; по
решению человека 29.10.2026 (webx-ui#89) оформление влито в этот пакет, ждёт приёмки (webx-ui#89,
этап 1). Пакет не начат. Карта семейства — [`WEBX_UI_COMMERCE.md`](WEBX_UI_COMMERCE.md): принципы,
цепочка итогов, события заказа. Корзина, из которой строится снимок, —
[`WEBX_UI_MODULE_CART.md`](WEBX_UI_MODULE_CART.md). Соседи, которые к заказу подключаются: доставка —
[`WEBX_UI_MODULE_DELIVERY.md`](WEBX_UI_MODULE_DELIVERY.md) (§11, §12 — шаг доставки), оплата —
[`WEBX_UI_MODULE_PAYMENTS.md`](WEBX_UI_MODULE_PAYMENTS.md) (§10 — реализация слота `PaymentSlot`,
§7.3 — `ShippingChoice`), посетители — [`WEBX_UI_MODULE_USERS.md`](WEBX_UI_MODULE_USERS.md) (§11, §12
— вход в оформлении, §13.4, §14.1), уведомления —
[`WEBX_UI_MODULE_NOTIFICATIONS.md`](WEBX_UI_MODULE_NOTIFICATIONS.md) (§5, §8), формы сайта —
[`WEBX_UI_WIDGETS.md`](WEBX_UI_WIDGETS.md) (§17), layout оформления —
[`WEBX_UI_COMPOSITIONS.md`](WEBX_UI_COMPOSITIONS.md).

Пакет — `webx-ui/module-orders` (composer, namespace `WebxUi\Orders`, оформление —
`WebxUi\Orders\Checkout\…`; словарь `webx-orders`, слова оформления — группой `checkout.*`), npm-пара
— `@webx-ui/module-orders` (раздел панели). Id модуля — `orders` (области MCP `orders:read` /
`orders:write`, права `orders.*`, §11.1 и §31.1). Отдельного пакета оформления нет — ни composer,
ни npm.

Спека из двух частей. **Часть I — заказ** (§1–§16): снимок, вехи и статусы, события, отмена и
возврат, панель, MCP, страница покупателя. **Часть II — оформление** (§19–§34): страница сайта, где
покупатель оставляет контакты, выбирает доставку и оплату и подтверждает заказ. Общие для обеих
частей — границы (§1), решения (§2), план этапов (§17) и отложенное (§18). Номера разделов части I
прежние; раздел N бывшей спеки оформления `WEBX_UI_MODULE_CHECKOUT.md` — здесь §N+16 (её §8.3 —
§24.3), её решение N — решение 43+N (её решение 13 — решение 56).

Заказ — снимок корзины в момент оформления: строки, цены, скидки, привилегии, зачтённые оплаты,
контакты покупателя и получателя, комментарий, а если установлены доставка и оплата — их блоки.
После создания заказ не зависит ни от одной живой записи: ни от товара, ни от правила скидки, ни от
точки выдачи. Дальше у заказа две оси: **вехи** — системные факты, на которые опираются события и
спутники (оплачен, получен, отменён), и **статусы** — рабочие этапы магазина, которые сайт
настраивает сам и которые покупатель видит сгруппированными в публичные.

Оформление — одна страница сайта: покупатель оставляет контакты, при необходимости выбирает
доставку и оплату, видит колонку итогов и подтверждает. Своих денег и своих способов у оформления
нет: суммы считает вычислитель корзины, способы — модули доставки и оплаты через слоты, заказ
создаёт `Orders::place()`. Оформление отвечает за порядок шагов, черновик, сверку показанной суммы
с пересчитанной, защиту от двойной отправки и страницу «Спасибо».

## 1. Границы

**Первая версия — простая** (решение 17): без автоматизации и тонкостей, у каждого бизнеса свой
цикл жизни заказа, и все случаи не покрываются; наворачиваем по первому запросу клиента.
Управлять заказами в основном будет учётная программа клиента через API сайта (отдельная задача),
поэтому **каждая операция с заказом — метод сервиса `Orders`** (§5.3, решение 18); панель, MCP,
оформление и будущие эндпоинты API — тонкие обёртки над ним.

**Один пакет — заказ и оформление** (решение 75). Оформление — способ создать заказ, а не
условие его существования: заказ без страницы оформления (его создаёт учётная программа через API
или код сайта вызовом `Orders::place()`) — законный сценарий. Его закрывает настройка
`webx-orders.checkout.enabled` (решение 76, §19): выключено — нет страницы, слотов, черновиков и
инструментов оформления, а заказы, панель, MCP заказов и страница заказа работают как были.

**Внутри — заказ (часть I):**

- сервис `Orders` — единственная дверь ко всем операциям с заказом (§5.3);
- таблицы заказа, строк, корректировок, оплат, привилегий, вех, возвратов, истории статусов и двух
  наборов статусов (§3); номер заказа (§4);
- создание заказа из корзины: транзакция, блокировки, сверка суммы, идемпотентность (§6) — API
  `Orders::place()`, который зовёт оформление (или код сайта);
- вехи, внутренние и публичные статусы, свободные переходы, история (§5, §8);
- события заказа с полезной нагрузкой (§7); отмена, полный и частичный возврат (§9);
- блоки снимка `delivery` и `payment` — место и API записи, без знания о способах (§6.4);
- привязка гостевого заказа к посетителю и отвязка — если стоит `module-users` (§13.3);
- раздел панели: список, карточка, статусы, настройки (§11); MCP (§12);
- события и переменные для `module-notifications`, привязка каналов к публичным статусам и вехам
  (§10);
- страница заказа для покупателя по подписанной ссылке; «Мои заказы» в кабинете и вкладка в
  карточке посетителя — только если стоит `module-users` (§13);
- словарь `webx-orders` (§14), демо-данные (§15).

**Внутри — оформление (часть II):**

- страница оформления, её шаги и реестр шагов (§20); черновик оформления по корзине (§21);
- контракты слотов доставки и оплаты `Slot`, `ShippingSlot`, `PaymentSlot` и реестр `CheckoutSlots`
  (§22, решение 77) — их реализации живут у владельцев;
- колонка итогов: строки цепочки, «Стоимость доставки», привилегии, место для зачётов и купонов
  (§23);
- подтверждение: сверка суммы, повторное подтверждение, идемпотентность, вызов `Orders::place()`
  (§24);
- гость и вошедший: подстановка контактов, диалог входа на странице (§25); получатель, отличный от
  покупателя (§20.3);
- страница «Спасибо» (§26); layout и вид через композиции (§27); антиспам (§28);
- «Купить в один клик» — в v1, отдельным этапом после основного оформления (§29, решение 62);
- события оформления (§30), право и вкладка настроек (§31), MCP `orders_checkout_*` (§32), слова —
  группа `checkout.*` (§33).

**Рядом, но в чужом пакете:**

- **Цепочка итогов** — один вычислитель `module-cart` (§5.3 его спеки); оформление зовёт его с
  `Purpose::Checkout` для показа, `Orders::place()` — с `Purpose::Order`; заказ его не повторяет.
- **Слот доставки** — `module-delivery`: реализация `ShippingSlot` (`DeliveryCheckoutSlot`, §12 его
  спеки), `DeliverySnapshot` (§11.1), накладная и трекинг; веху «получен» он ставит через API вех
  (§5.3), вкладку карточки — патчем экрана (§11.3).
- **Слот оплаты** — `module-payments`: реализация `PaymentSlot` (`PaymentsCheckoutSlot`, §10 его
  спеки), способы, переход в шлюз, повтор оплаты; вехи «оплачен» и «оплата не прошла» — через API
  вех. Возврата через шлюз в v1 нет (решение 27, §18).
- **Диалог входа и регистрации** — `module-users` (§12 его спеки); оформление ставит кнопку и
  слушает событие входа (§25).
- **Поле зачёта** (сертификаты, кешбек) — `module-wallet`; **поле промокода** — `module-coupons`.
  Здесь — только место для них (§23.3).
- **Капча** — одна на сайт: служба в `widgets`, поставщик — вкладка `module-settings` (§28.1,
  решение 72); оформление только включает её у себя.
- **Реакции на заказ** — кошелёк, лояльность, сертификаты, склад, учёт слушают события §7 сами;
  контракт `Purchasable` о заказе не знает (решение 4).

**Снаружи:**

- налоги, счета и закрывающие документы, печатные формы, кроме накладной доставки;
- правка состава заказа после оформления (решение 23);
- заказ, созданный менеджером в панели без корзины (решение 22);
- склад, резервы, выгрузка в учётную систему — интеграции на событиях;
- API сайта для учётной программы — отдельная задача (шлюз с авторизацией, эндпоинты каждого
  модуля); эта спека требует от него только одного — звать `Orders` (решение 18);
- автоматический перевод во внутренний статус по вехе и автоотмена неоплаченного (решения 30, 37);
- возврат денег через шлюз и холдирование оплаты (решение 27);
- конкретные службы доставки и платёжные шлюзы — их спутники;
- страница корзины — её нет (решение 10 корзины); корзина — виджет, оформление — страница;
- брошенные корзины и письма «вы забыли товар» — не в v1, будущий спутник на черновиках (решение
  70, §18).

### 1.1. Без соседей

`module-orders` требует `module-cart` (снимок строится из его `CartState`), `widgets` (поля и формы
оформления) и `compositions` (layout оформления) — решение 78. Всё прочее — в `suggest` и
подключается по `class_exists` в `boot()` того, кто подключает:

| Нет модуля / выключено     | Заказ (часть I)                                                                                     | Оформление (часть II)                                                          |
| -------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| оформление выключено (§19) | заказы создаёт код сайта, тест или API через `Orders::place()`; раздел панели работает              | нет страницы, черновиков, слотов, вкладки настроек и `orders_checkout_*`       |
| `module-delivery`          | `delivery` в заказе — `null`; вкладки «Доставка» нет; «получен» ставит менеджер                     | шага доставки нет, строки «Стоимость доставки» нет                             |
| `module-payments`          | `payment` — `null`; «оплачен» ставит менеджер или статус с вехой                                    | шага оплаты нет, заказ не ждёт оплаты (`awaitPayment: false`)                  |
| оба слота                  | заказ — строки, контакты и комментарий                                                              | контакты покупателя, получатель, комментарий и подтверждение; заказ без блоков |
| `module-users`             | `user_id` всегда `null`; нет «Моих заказов», вкладки посетителя и привязки; страница по ссылке      | только гость: кнопки «Войти» нет, контакты не подставляются, `userId` — `null` |
| `module-notifications`     | писем и сообщений нет; блока «Уведомления» в статусах и настройках нет; `webx:doctor` предупреждает | «Мы отправили подтверждение» на «Спасибо» не печатается                        |
| `module-wallet`            | зачётов нет                                                                                         | места зачёта в итогах нет (оно пустое без зарегистрированных кусков, §23.3)    |
| `module-coupons`           | —                                                                                                   | места промокода нет                                                            |
| `module-settings`          | экраны настроек раздела — свои (§11.4)                                                              | капча сайта — только из конфига `webx-widgets.captcha` (§28.1)                 |

## 2. Принятые решения (не переоткрывать)

Решения человека от 23.10.2026 и 27.10.2026 (спецификация задачи webx-ui#56); при расхождении
действуют решения 27.10.

1. **Заказ — снимок.** Строки хранят `type`, `ref_id`, `sku`, название, подпись опций, цену,
   скидку, итог строки, количество и `parent_id` (комплект, набор — родитель с детьми). После
   оформления заказ не зависит от живых записей.
2. **Цена и скидки замораживаются в момент оформления;** в корзине они живые.
3. **В заказ переходят привилегии** (benefits: «доставку оплачивает магазин» — отметка для
   менеджера и накладной) **и зачтённые оплаты** (tenders: сертификаты, кешбек — это оплата, не
   скидка).
4. **Реакция на заказ не входит в контракт `Purchasable`:** модули слушают события сами.
5. **Вехи с датами и событиями:** `OrderPlaced`, `OrderPaid`, `OrderReceived`. «Получен» приходит
   из интеграции доставки (трекинг) или ставится менеджером вручную. Отмена и возврат — тоже события
   (кошелёк возвращает списанное, кешбек `pending` отменяется).
6. **Раздел в панели:** список, карточка, смена статусов. **MCP — полный.**
7. **Без соседей.** `module-orders` работает без `module-users`, `module-delivery`,
   `module-payments` и будущих спутников. Заказ сам хранит снимок контактов покупателя (имя и
   фамилия — раздельно, решение 40; телефон, e-mail) и получателя, если он другой. Доставка и оплата — необязательные блоки снимка
   (ключ способа, подпись, цена или «по тарифам перевозчика», детали); их заполняет тот модуль,
   который установлен. Без них заказ — строки, контакты и комментарий.
8. **Покупатель — необязательная ссылка** (`user_id`), только если стоит `module-users`; гостевой
   заказ — норма.
9. **«Мои заказы»** — раздел, который `module-orders` регистрирует в реестре меню кабинета
   `module-users`, только если тот установлен.
10. **Заказ с онлайн-оплатой создаётся до оплаты:** веха «ожидает оплаты», затем переход в шлюз.
    Неоплаченный заказ виден менеджеру (фильтры «ожидает оплаты» / «оплата не прошла»): уточнить,
    сменить способ, отметить оплату вручную, отменить. Отмена — обычное событие. Модель статусов и
    вех не знает конкретных способов оплаты. _Автоотмена через N часов из этого решения убрана из
    v1 решением 37._
11. **Статусы — три уровня.** Внутренние — свой набор у сайта (создать, переименовать, порядок,
    цвет, названия на языках сайта, выключить), покупатель их не видит. Публичные — тоже
    настраиваемые (название на языках, порядок), их видит покупатель в кабинете, письмах и на
    странице заказа. Каждый внутренний привязан к одному публичному. Вехи — системные и
    фиксированные: оформлен, ожидает оплаты, оплачен, получен, отменён, возвращён.
12. **Смена внутреннего статуса внутри одной публичной группы** для покупателя ничего не меняет и
    уведомления не шлёт. Уведомления покупателю — по смене **публичного** статуса, настраиваются по
    нему.
13. **Внутренний статус может ставить веху** («Передан в доставку — оплачено» ставит «оплачен»).
    Спутники и интеграции работают с вехами, а не с названиями статусов.
14. **Удаление статуса — мягкое, с восстановлением,** перед удалением — понятный текст о
    последствиях. **Переходы свободные,** история смен пишется (кто, когда, из какого в какой).
15. **Автосмена статуса по трекингу — не сейчас:** интеграции ставят только вехи; точка
    расширения остаётся (§18).
16. **Статусы обоих уровней — через MCP:** список, создание, правка, удаление и восстановление,
    перевод заказа в статус с `dry_run`.

Решения человека по открытым вопросам первой редакции спеки (27.10.2026):

17. **v1 — упрощённая, без автоматизации и тонкостей.** Наворачиваем по первому запросу клиента:
    у каждого бизнеса свой цикл жизни заказа, покрыть все случаи не пытаемся.
18. **Все операции с заказом — только через сервис `Orders`** (`place`, `mark`, `paymentFailed`,
    `stopAwaitingPayment`, `moveTo`, `cancel`, `refund`, `patchBlock`, `note`, `updateDetails`,
    `linkVisitor` / `unlinkVisitor`, §5.3). Панель, MCP и будущие эндпоинты API сайта — тонкие обёртки: проверить
    право, разобрать вход, позвать метод, отдать ответ. Ни контроллер, ни инструмент, ни слушатель
    не пишут в таблицы заказа сами. Управлять заказами в основном будет учётная программа клиента
    через API сайта — это отдельная задача (шлюз с авторизацией, эндпоинты накидывает каждый
    модуль).
19. **Таблицы — `orders` и `order_*`** (§3), по образцу `carts` / `cart_items`.
20. **Номер заказа — строка от `id`** с префиксом и началом, без отдельного счётчика и без
    блокировки (§4).
21. **Гостевой заказ в кабинете не появляется сам:** в «Моих заказах» — только заказы, оформленные
    со входом; гостевой покупатель открывает заказ по ссылке из письма. В панели, если стоит
    `module-users`, — действия «Привязать к посетителю» (поиск по e-mail и имени) и «Отвязать» в
    карточке заказа, строка в истории (кто, когда, к кому), право `orders.manage`, событие
    `OrderDetailsChanged` с полем `user_id`; в MCP — тот же инструмент с `dry_run` (§13.3).
22. **Заказа из панели без корзины в v1 нет.** _Частично отменено решением 85:_ заказ из панели
    есть, но поверх служебной корзины и обычного `place()`; ручной цены, выбора доставки и оплаты
    менеджером нет.
23. **Правки состава после оформления в v1 нет:** снимок неизменен, возможен только возврат строки.
24. **Снятия ошибочной вехи в v1 нет:** вехи не снимаются, журнал только дописывается; ошибочную
    оплату исправляет возврат или отмена.
25. **Списание кошелька — в `OrderPlacing` внутри транзакции** создания заказа, а не на
    `OrderPlaced`: заказ и списание случаются вместе или никак. Так же — всё, что должно быть
    атомарно с заказом (резерв склада); реакции — `OrderPlaced` после коммита (§6.3). Карта
    коммерции поправлена (§6 `WEBX_UI_COMMERCE.md`).
26. **Частичный возврат делит менеджер сам:** вводит сумму денег и сумму каждого зачёта; ни
    авторасчёта, ни подсказки нет (§9.3).

    `OrderStatusChanged` → `OrderPublicStatusChanged` → `OrderCancelled` после одной фиксации,
    каналы публичного статуса отрабатывают — покупатель видит «Отменён», а не «Принят». Веха —
    своя, с источником отмены, а не `status#<id>`. Такого статуса нет — статус не меняется,
    `webx:doctor` предупреждает (`Orders: cancellation`, замечание по содержимому). Ответ
    `MilestoneMark::$move` (`StatusMove` без вехи, null — перевода нет); `dry_run` панели и
    `orders_cancel` называют статус и что увидит покупатель (`status`), массовая отмена считает
    `moved` и называет статус. Уже отменённые заказы не трогаются: миграции данных нет, повторная
    отмена — тишина и перевода не делает.
89. **Карточка заказа: итоги и статус.** В итогах — «Позиций: N · единиц: M» (часть комплекта —
    не отдельная позиция; возвращённые единицы — «возвращено: K»), источник заказа («Создан в
    панели», «В один клик») — строкой под «Оформлен», причина отмены — плашкой с подписью
    «Причина:» под «Отменён», каждый возврат с причиной и номером операции — под «Возвращено»;
    во вкладке «История» причина отмены и возврата — той же плашкой. Смена статуса — карандаш у
    бейджа в полосе статуса и кнопка «Сменить статус» в шапке рядом с «Отметить оплату» (право
    `orders.manage`); на узкой шапке кнопка уходит в `···`. Карандаш — голая иконка цвета ссылки
    (`--wx-text-link`), без подложки и рамки кнопки; при наведении — оттенок акцента, фокус с
    клавиатуры виден (этап 3).

## 4. Номер заказа

- **Номер — строка от `id`:** `format(prefix, start + id, pad)`; по умолчанию префикс пустой,
  `start = 1000`, `pad = 0` → `1001`, `1002`… Настройки `orders.number.*` (§11.4). Пишется в той же
  транзакции сразу после вставки (`UPDATE orders SET number = ? WHERE id = ?`).
- **Почему не счётчик:** отдельная таблица с `FOR UPDATE` сериализует все оформления сайта и
  добавляет третью блокировку к корзине и кошельку (§6.3). Пропуски в нумерации (откат транзакции
  съел `id`) для магазина без фискальной нумерации не важны.
- **Смена формата** не трогает выданные номера: номер хранится. Новый префикс не может дать номер,
  который уже есть, — `unique` поймает, настройка проверяет пробным номером при сохранении.
- Поиск в панели и MCP принимает номер и `id`; покупатель и письма видят только номер. Сброса по
  годам, случайного и фискального номера в v1 нет (решение 20).

## 5. Вехи и статусы

### 5.1. Вехи

Закрытый список `WebxUi\Orders\Milestone` (enum), порядок — как на временной шкале карточки:

| Веха               | Кто ставит                                                      | Событие                 | Повтор |
| ------------------ | --------------------------------------------------------------- | ----------------------- | ------ |
| `placed`           | только `Orders::place()`                                        | `OrderPlaced`           | нет    |
| `awaiting_payment` | `Orders::place()` при `awaitPayment: true` (§6.1)               | — (часть `OrderPlaced`) | нет    |
| `paid`             | оплата (`payment:<шлюз>`), менеджер, агент, статус с вехой      | `OrderPaid`             | нет    |
| `received`         | доставка (`delivery:<служба>`), менеджер, агент, статус с вехой | `OrderReceived`         | нет    |
| `cancelled`        | менеджер, агент, учётная программа (API), статус с вехой        | `OrderCancelled`        | нет    |
| `refunded`         | только возврат, когда вернули всё (§9.2)                        | `OrderRefunded` (full)  | нет    |

- **Повторная веха** — не ошибка, а тишина: `mark()` отвечает `AlreadyMarked` с датой и источником
  первой, событие не бросается. Так трекинг, который пришёл после ручной отметки менеджера, ничего
  не двоит (§11.4 спеки доставки).
- **`paid` снимает `awaiting_payment` и `payment_failed_at`** (колонки на `orders`; строка
  `awaiting_payment` в `order_milestones` остаётся — это история).
- **Что нельзя:** `paid` у отменённого — отказ `OrderCancelledAlready` (деньги пришли на отменённый
  заказ — это возврат, а не оплата; менеджер видит строку истории от шлюза, §5.4); `received` у
  отменённого — отказ; `cancelled` у полностью возвращённого — тишина.
- Вехи не снимаются (решение 24). Исключение — `refunded`: её снимает отмена ошибочной записи
  возврата, когда заказ после неё больше не возвращён полностью (решение 98, §9.5) — строка вехи и
  колонка `refunded_at`, со строкой истории `milestone_removed`. Новый полный возврат ставит её снова.

### 5.2. Статусы: внутренний и публичный

- У заказа хранится только внутренний (`orders.status_id`); публичный — `status.publicStatus`.
  Покупатель видит публичный, менеджер — оба (внутренний крупно, публичный мелко рядом).
- **Новый заказ** встаёт в статус из настроек: `orders.initial_status` — для обычного,
  `orders.initial_status_awaiting_payment` — для заказа с `awaitPayment` (по умолчанию «Ожидает
  оплаты»). Оба — активные и не удалённые; удалить или выключить такой статус нельзя, пока он
  выбран в настройке (отказ со ссылкой на настройку).
- **Переходы свободные** (решение 14): из любого в любой активный, в том числе назад. Перевод в
  тот же статус — тишина.
- **Перевод в статус с `sets_milestone`** ставит веху тем же вызовом с источником `status#<id>`,
  если её ещё нет; если веха запрещена (§5.1 «что нельзя») — перевод отказывает целиком, чтобы
  статус «Оплачен» не стоял у отменённого заказа. Уход из такого статуса веху не снимает.
- **Статус и веха расходятся законно:** шлюз поставил «оплачен», а заказ стоит в «Ожидает оплаты»
  — пока менеджер его не переставит (решение 38). Список подсвечивает такие заказы фильтром
  «оплачен, а статус ждёт оплаты» — это просто веха + статус в фильтре, а не особая логика.

### 5.3. API

Сервис `Orders` — единственная дверь (решение 18). Контроллеры панели, инструменты MCP и будущие
эндпоинты API сайта проверяют право, разбирают вход, зовут один метод и отдают его ответ; модели
заказа они не сохраняют. Слушатели соседей пишут в заказ тоже только через эти методы.

```php
namespace WebxUi\Orders;

final class Orders
{
    /** §6 — the only way an order comes to be. */
    public function place(PlaceOrder $input): Order;

    /** §29.2 — a manager's lines into a service cart, place(), the cart gone; one transaction. */
    public function placeByManager(ManagerOrder $input, string $source = 'panel'): Order;

    /** §29.2 — the same lines counted for the order and rolled back: nothing stays. */
    public function previewByManager(ManagerOrder $input): ManagerPreview;

    /**
     * Set a milestone once. Throws a Refusal (§5.1 «what is not allowed»); a repeat returns the
     * first mark and dispatches nothing.
     */
    public function mark(
        Order $order,
        Milestone $milestone,
        string $source,                    // 'payment:gateway-a', 'delivery:carrier-a', 'panel'
        ?CarbonInterface $at = null,       // when it happened; default now
        ?string $reference = null,         // payment id, waybill number
        ?string $note = null,
    ): MilestoneMark;

    /** A failed payment try: a history line and payment_failed_at, not a milestone (§5.4). */
    public function paymentFailed(Order $order, string $source, ?string $reason = null): void;

    /**
     * The order stops waiting for payment without the paid milestone: its method was switched to
     * one that does not await payment (§5.5). A history line, no event; a paid or cancelled order
     * is a Refusal.
     */
    public function stopAwaitingPayment(Order $order, string $source): void;

    /**
     * Free transition (§5.2); dry-run tells what would happen without doing it. Into a status
     * that cancels, the panel and an agent give the reason in `note` (decision 83).
     */
    public function moveTo(Order $order, OrderStatus $to, string $source, ?string $note = null,
        bool $dryRun = false): StatusMove;

    /** Write a part of a block (§6.4): the waybill number into `delivery`, a new method into `payment`. */
    public function patchBlock(Order $order, string $block, array $patch, string $source): void;

    /** A line in the order's history from a module: «the parcel came back». */
    public function note(Order $order, string $text, string $source): void;

    /**
     * §9.1 — returns the tenders left on the order to the wallet by marking them refunded, and
     * moves the order into the first active status that cancels (decision 88): `MilestoneMark::$move`.
     */
    public function cancel(Order $order, string $source, ?string $reason = null,
        bool $dryRun = false): MilestoneMark;

    /** §9.3 — records money given back outside the site; moves no money itself in v1. */
    public function refund(Order $order, RefundRequest $request, bool $dryRun = false): RefundResult;

    /** Contacts, recipient, comment, manager note (§8); lines, money and milestones never. */
    public function updateDetails(Order $order, OrderDetails $patch, string $source): void;

    /** §13.3 — only with module-users; a guest order gets its owner, or loses it. */
    public function linkVisitor(Order $order, int $userId, string $source,
        bool $dryRun = false): VisitorLink;

    public function unlinkVisitor(Order $order, string $source, bool $dryRun = false): VisitorLink;

    /** The order a checkout's form token made (§6.2, step 1), or null; the key is hashed the same way. */
    public function findByIdempotencyKey(string $key): ?Order;
}
```

- Автор (`admin_id`) берётся из гарда `cms`, если вызов пришёл из панели или MCP; интеграции и
  команды — `null`, их видно по `source`.
- Каждый метод — одна транзакция с `SELECT … FOR UPDATE` строки заказа: шлюз и менеджер, которые
  отмечают оплату одновременно, не дадут двух событий.
- `StatusMove` (ответ `moveTo`, в том числе на `dry_run`): `from`, `to`, `publicFrom`, `publicTo`,
  `publicChanged`, `milestone` (что поставится), `notifications` (какие каналы получат сообщение —
  §10.2), `refusal` (почему нельзя).
- **Перевод, который ставит `cancelled`,** — это отмена: из панели и MCP без заметки отказ под
  `note`, в том числе на `dry_run` (решение 83). Заметка — причина: строка истории, `note` вехи,
  `OrderCancelled::$reason`.

### 5.4. Оплата не прошла

Шлюз отвечает «отказ» или покупатель вернулся без оплаты → `module-payments` зовёт
`paymentFailed()`: строка истории `kind = payment_failed` с причиной, `orders.payment_failed_at =
now()`, событие `OrderPaymentFailed`. Заказ остаётся «ожидает оплаты»; повторная попытка оплаты —
дело оформления и оплаты. Фильтр «оплата не прошла» = `awaiting_payment AND payment_failed_at IS
NOT NULL`. Это не веха (решение 28): попыток бывает несколько, а веха — одна на заказ.

Деньги, пришедшие на отменённый заказ: `mark(paid)` отказывает, а модуль оплаты пишет `note()` («Платёж
… пришёл после отмены») — менеджер решает возвратом.

### 5.5. Неоплаченный заказ

Автоотмены в v1 нет (решение 37): ни настройки, ни команды, ни расписания. Неоплаченный заказ
менеджер находит вкладкой «Ожидают оплаты» (индекс `(awaiting_payment, placed_at)`) и решает сам:
уточнить у покупателя, сменить способ (`patchBlock`), отметить оплату, отменить (`cancel()`).
**Смена способа на тот, что оплаты не ждёт** (например «при получении»), снимает «ожидает оплаты»:
модуль оплаты после `patchBlock` зовёт `stopAwaitingPayment($order, 'payment:<method>')` (из
панели — источник `panel`; решение 42). Метод пишет строку истории
`kind = payment_awaiting_stopped` с источником, ставит `awaiting_payment = false`, события не
бросает; строка `awaiting_payment` в `order_milestones` остаётся историей. У оплаченного или
отменённого заказа — отказ (Refusal). То же
сделает учётная программа через API сайта, когда он появится. Добавить автоотмену потом — это
команда, которая зовёт тот же `cancel()`; модель для этого не меняется.

### 5.6. Удаление и восстановление статусов

**Внутренний статус.** Перед удалением панель и MCP (`dry_run`) показывают:

> В статусе «Кладовщик ищет» 14 заказов. Они останутся в нём — в списке статус будет помечен
> «удалён», новые заказы в него не переводятся. Покупатели по-прежнему видят «В работе». Уведомлений
> не будет. Статус можно восстановить в разделе «Статусы → Удалённые».

- Удалённый статус: не предлагается при смене, виден в фильтре списка с пометкой «удалён» (чтобы
  найти оставшиеся заказы), в истории — с пометкой. Заказ из него уходит обычным переводом; назад
  — нельзя.
- Нельзя удалить статус из настроек «начальный» (§5.2) и последний активный статус публичной
  группы, в которой есть заказы, — иначе им некуда идти внутри группы; отказ объясняет, что сделать.
- **Восстановление** возвращает статус как был (имя, место, веха). Если его публичный удалён —
  отказ «Сначала восстановите „В работе“ или выберите другую группу» (правка привязки разрешена и у
  удалённого).

**Публичный статус.** Удалить можно, только когда в нём нет **активных** внутренних: панель
показывает их списком и предлагает перенести в другую группу одним действием. Заказы в удалённых
внутренних этой группы продолжают показывать покупателю прежнее название (строка не удаляется
физически). Каналы уведомлений удалённого публичного не срабатывают.

**Перепривязка** внутреннего к другому публичному меняет то, что покупатель видит у всех заказов в
этом статусе, — сразу, без уведомлений; перед сохранением панель говорит число таких заказов.

## 6. Снимок из корзины

### 6.1. Вход

```php
namespace WebxUi\Orders;

final readonly class PlaceOrder
{
    public function __construct(
        public Cart $cart,                     // WebxUi\Cart\Models\Cart
        public string $locale,
        public Contact $customer,              // firstName, lastName, phone, email — a first name and one of the two
        public ?Contact $recipient = null,     // null — the customer receives
        public ?string $comment = null,
        public ?int $expectedPayable = null,   // what the buyer saw; null — no check (code, tests)
        public bool $awaitPayment = false,     // the chosen payment is online (§5.1)
        public array $blocks = [],             // 'delivery' => DeliverySnapshot->toArray(), 'payment' => […]
        public ?string $idempotencyKey = null, // the checkout's form token
        public ?int $userId = null,            // Visitors::current()?->id; the checkout passes it
        public string $source = 'checkout',
    ) {}
}
```

- `awaitPayment` приходит от оформления (оно знает выбранный способ оплаты); заказ про способы не
  знает (решение 10).
- `userId` передаёт вызывающий: заказ не читает `Visitors::current()` сам, чтобы `place()` из
  команды или теста не зависел от запроса.
- `Contact(firstName, ?lastName, ?phone, ?email)`; у получателя e-mail не бывает.
- Контакты проверяет `Contact` (имя и фамилия ≤ 190, телефон — `+` и цифры с разделителями, e-mail —
  `email:filter`); что из них обязательно в форме — решает оформление; заказу нужно имя (фамилия —
  нет) и хотя бы телефон или e-mail.

### 6.2. Порядок

```
DB::transaction:
 1. повтор?        idempotencyKey уже есть в orders → вернуть тот заказ, ничего не делать
 2. замок корзины  SELECT … FROM carts WHERE id = ? FOR UPDATE (Cart::query()->lockForUpdate())
 3. пересчёт       Calculator::calculate(cart, locale, Purpose::Order) — исключение источника летит
                   дальше (§5.4 спеки корзины): заказ по неполной цепочке не создаётся
 4. проверки       корзина не пуста; нет строк line.unavailable / line.qty_limited; валюта корзины
                   = валюта сайта; payable == expectedPayable → иначе PayableChanged(новое состояние)
 5. блоки          ключи blocks зарегистрированы в OrderBlocks (§6.4), значения проходят схему блока
 6. запись         orders (number = null) → number → order_items (родители, потом дети, карта id)
                   → order_adjustments (line → item_id) → order_tenders → order_benefits
                   → order_milestones (placed [, awaiting_payment]) → order_status_changes (null → начальный)
 7. хук            OrderPlacing (синхронно, в транзакции) — слушатель может отказать (§6.3)
 8. корзина        CartService::empty(): строки и declined_rules уходят; запись корзины, cookie и
                   черновик оформления остаются
commit → OrderPlaced и остальные события после коммита (§7.1)
```

- **Сверка суммы** (§4 карты): `PayableChanged` несёт свежий `CartState`; оформление показывает
  покупателю новую сумму, заказ не создан. Сравнивается `payable`, а не `total`: покупатель платит
  его.
- **Строки, которые нельзя купить,** не выкидываются молча: отказ `CartNotOrderable` со списком
  строк и кодами предупреждений корзины — оформление показывает их покупателю.
- **Генерируемые строки** (подарки правил) попадают в заказ обычными строками с `source` и `label`;
  отказанные (`declined_rules`) — нет, их нет и в `CartState`.
- **Корзина** чистится методом корзины (решение 34). В 0.89.0 `CartService::clear()` удаляет запись
  корзины целиком (кнопка «Очистить» виджета) — каскадом ушёл бы и черновик оформления с контактами
  (решение 66), поэтому в этапе 3 в `module-cart` добавляется `CartService::empty(Cart)`: удаляет
  строки и сбрасывает `declined_rules`, запись и её токен остаются.
- **Замок корзины в коде корзины.** В 0.89.0 `CartService` пишет строки без замка строки `carts`:
  строка, добавленная в другой вкладке между пересчётом (шаг 3) и очисткой (шаг 8), ушла бы из
  корзины, не попав в заказ. В этапе 3 записи `CartService` (`add`, `update`, `remove`, `decline`,
  `empty`) берут `lockForUpdate()` той же строки `carts` в начале своей транзакции — тогда они ждут
  `place()`, а не идут параллельно.

### 6.3. Блокировки

Порядок замков всегда один — так оформления не ловят взаимную блокировку:

1. строка `carts` (шаг 2) — один и тот же покупатель не оформит корзину дважды в двух вкладках;
2. замки источников цепочки при `Purpose::Order` (кошелёк блокирует свои партии, §3.2 карты);
3. замки слушателей `OrderPlacing` (склад — свои остатки).

`OrderPlacing` — синхронное событие внутри транзакции с уже записанным заказом (`Order` с id и
номером). Его слушатель делает то, что должно случиться **вместе** с заказом или не случиться
вовсе: кошелёк списывает зачтённое (а не на `OrderPlaced`: после коммита списание может не
пройти, а заказ уже есть; решение 25), склад резервирует. Отказ —
`throw new OrderRefused(code, message)`: транзакция откатывается, оформление показывает `message`.
Медленного (HTTP к шлюзу, письма) в нём быть не должно — это `OrderPlaced`.

### 6.4. Блоки снимка

```php
namespace WebxUi\Orders\Blocks;

final class OrderBlocks
{
    /** A module that fills a block registers it in boot(), under class_exists(OrderBlocks::class). */
    public function register(BlockDefinition $block): void;
}

final readonly class BlockDefinition
{
    public function __construct(
        public string $key,              // 'delivery' | 'payment' — the column it lands in
        public string $module,           // 'delivery'
        public Closure $validate,        // fn (array $value): list<string> — errors; empty — accepted
        public ?Closure $summary = null, // fn (array $value, string $locale): string — one line for the list and mail
    ) {}
}
```

- Колонок две — `delivery` и `payment`; новых ключей реестр не принимает (третий блок — новая
  колонка и решение человека). Реестр нужен, чтобы заказ проверял форму блока руками владельца и
  показывал строку блока в списке и письме, не зная способов.
- **Общая часть блока,** которую заказ читает сам: `method` (ключ способа), `title` (`{locale:
text}`), `price` (`{kind, amount, currency, in_total, …}` — у доставки, §9.3 её спеки; у оплаты —
  комиссия, если есть). Остальное (`point`, `address`, `waybill`, `gateway`) заказ хранит как есть и
  показывает только через вкладку модуля-владельца; без неё — свёрнутым JSON для менеджера.
- `patchBlock()` сливает `patch` в блок (`array_replace_recursive`), проверяет `validate`, пишет
  строку истории `kind = block` и бросает `OrderBlockUpdated`. Так доставка кладёт номер накладной
  (§11.2 её спеки), оплата — смену способа, которую менеджер сделал с покупателем по телефону.

## 7. События и полезная нагрузка

### 7.1. Как бросаются

- Классы — `WebxUi\Orders\Events\*`, все `ShouldDispatchAfterCommit` (кроме `OrderPlacing`):
  слушатель не увидит заказ, которого нет, и не сработает на откаченный.
- **Каждое несёт `OrderData`** — неизменяемый снимок заказа на момент события (принцип: событие
  несёт заказ-снимок, §6 карты), сериализуемый для слушателей в очереди. Слушатель, которому нужна
  модель, берёт её по `$event->order->id`.
- Общие поля каждого события, кроме `OrderData`: `source` (string), `adminId` (?int), `at`
  (`CarbonImmutable`).

## 8. История

Карточка показывает одну временную шкалу, собранную из трёх таблиц по времени:

- `order_status_changes` — смены статуса (из какого в какой, публичный рядом, если сменился),
  заметки менеджеров, агента и модулей (`note()`; они же — лента «Заметки», решение 90), неудачные оплаты, снятие «ожидает оплаты»
  (`kind = payment_awaiting_stopped`, §5.5), правки блоков, привязка и отвязка посетителя
  (`kind = visitor`, §13.3), отмена записи возврата (`kind = refund_reversed`, заметка
  `refund#<id>: <причина>`) и снятие вехи (`kind = milestone_removed`, заметка — веха), §9.5;
- `order_milestones` — вехи с источником и `reference`;
- `order_refunds` — возвраты; отменённая запись остаётся с пометкой «позже отменён».

Строка: время (`WxDate`), кто (администратор по `admin_id` — имя из `cms_users`, иначе источник
словами: «Шлюз оплаты A», «Служба доставки A», «API сайта» для `api`, «Агент: имя администратора» для `mcp`),
что, заметка. С `module-notifications` — блок «Уведомления» под шкалой: строки журнала отправок по
`subject` заказа (`Notifications::deliveriesFor`, §8.1 его спеки).

Правки контактов, комментария и заметки менеджера идут в общий журнал истории панели
(`webx.history`, [`WEBX_UI_HISTORY.md`](WEBX_UI_HISTORY.md)) и в шкалу — строкой «Изменены
контакты». Сами деньги, строки и вехи не правятся вовсе.

## 9. Отмена и возврат

### 9.1. Отмена

- Веха `cancelled` — `cancel()` или перевод в статус с `sets_milestone = cancelled`. **`cancel()`
  переводит заказ в первый активный такой статус** (решение 88): строка истории и события — как у
  перевода, причина — в заметке; без такого статуса заказ остаётся, где стоял, и `webx:doctor`
  предупреждает. Причина —
  обязательна из панели и MCP (строка) в обоих путях: у `cancel()` — `reason`, у перевода —
  заметка `note` (решение 83); отказ — и на `dry_run`. `api` и команды отменяют без причины.
- **Зачёты возвращает отмена.** В той же транзакции `cancel()` проставляет каждому зачёту
  `refunded_amount = amount`; то, что до отмены ещё не было возвращено (`amount − refunded_amount`
  на момент отмены), уходит в событие списком `tendersReturned`. Так зачёт, вернувшийся отменой,
  считается возвращённым: условие полного возврата (§9.2) у отменённого заказа выполнимо, а вернуть
  тот же зачёт второй раз нельзя — его остаток ноль.
- Что происходит у соседей — их слушатели `OrderCancelled`: кошелёк возвращает `tendersReturned`,
  лояльность отменяет `pending`, склад снимает резерв.
- Оплаченный заказ отменяется так же, но панель предупреждает: «Заказ оплачен на 120,00. Отмена не
  вернёт деньги — верните их и отметьте возврат» и предлагает следующим шагом диалог возврата.
- После отмены нельзя: `paid`, `received`, возврат зачётов (их уже вернула отмена). Возврат денег —
  можно (это и есть случай «оплачен, отменён»): когда он вернёт всё, встанет веха `refunded`.

### 9.2. Полный возврат

`refund()` на всю невозвращённую часть: `amount = payable − refunded_total`, остатки всех зачётов,
все строки целиком. Когда после записи возврата `refunded_total = payable` и у каждого зачёта
`refunded_amount = amount` (вернул возврат или отмена, §9.1) — ставится веха `refunded` и
`OrderRefunded` идёт с `full = true`. Веху ставит только возврат: заказ, оплаченный целиком
зачётами, после отмены остаётся «отменён» — деньгами возвращать нечего, зачёты вернула отмена. Отмены возврат не ставит: товар,
который вернули после получения, — заказ «получен» и «возвращён», это правда.

### 9.3. Частичный возврат

```php
final readonly class RefundRequest
{
    public function __construct(
        public int $amount,                 // money back, minor units; 0 — only tenders
        public array $tenders = [],         // tender id → amount back to the wallet
        public array $items = [],           // item id → qty returned; empty — a money-only refund
        public ?string $reference = null,   // the bank's or ledger's operation number, if known
        public ?string $reason = null,
        public string $source = 'panel',
    ) {}
}
```

- Проверки: `amount ≤ payable − refunded_total`; каждый зачёт — не больше его остатка; `qty` строки
  — не больше `qty − refunded_qty`; хоть что-то не ноль.
- **Деление вводит менеджер** (решение 26): сумму денег и сумму каждого зачёта. Авторасчёта и
  подсказки нет; диалог и `dry_run` показывают только остатки — сколько ещё можно вернуть деньгами,
  каждым зачётом и сколько единиц каждой строки.
- Возврат строки не меняет `order_items.total` и итоги заказа: снимок неизменен, возвраты лежат
  рядом. Карточка показывает «Возвращено: 1 из 2» и «К оплате … / возвращено …».

### 9.4. Деньги возвращаются вне сайта

- В v1 возврат — только запись (решение 27): деньги вернули банком, кассой или учётная программа,
  а `refund()` это фиксирует (`method = manual`, необязательный `reference` операции). Сам он денег
  не двигает и ни в какой шлюз не ходит; зачёты возвращает кошелёк по `OrderRefunded`.
- Панель называет действие прямо: «Отметить возврат» с подсказкой «Деньги возвращаются вне сайта —
  здесь отмечается, сколько и что вернули».
- Возврат через шлюз и холдирование — отложены (§18).

### 9.5. Отмена ошибочной записи возврата

Решение 98. Возврат не редактируется: ошибочная запись отменяется, верная вносится новой.

```php
Orders::reverseRefund(Order $order, int $refundId, ?string $reason, string $source, bool $dryRun = false): RefundReversal
```

- Одна транзакция под замком заказа. Строка `order_refunds` не удаляется и сумм не меняет — получает
  `reversed_at`, `reversed_source`, `reversed_by`, `reversal_reason`.
- Откатывается то, что дала запись: `orders.refunded_total −= amount`, `refunded_amount` её зачётов,
  `refunded_qty` её строк. Зачёты, возвращённые **отменой заказа** (§9.1), — не записи, их не трогает:
  у отменённого заказа зачёт, который вернула отменённая запись, снова «к возврату».
- Если веха `refunded` стоит, а после отмены `refunded_total < payable` или у зачёта есть остаток —
  веха снимается (строка `order_milestones` и колонка `refunded_at`) со строкой истории
  `milestone_removed`. Отмена записи только единиц (без денег и зачётов) веху не трогает (§9.2).
- Отказы `RefundReversalRefused`: `foreign` — записи нет у этого заказа, `reversed` — уже отменена.
  Пустая причина из `panel` и `mcp` — `ValidationException` (`reason`); `api` и команды — без причины.
- Строка истории `refund_reversed` и `OrderRefundReversed` после коммита.
- `dry_run` ничего не пишет и отвечает тем же `RefundReversal`: что уходит (деньги, зачёты, единицы),
  `refunded_total` и остаток к возврату после, остатки зачётов и строк, снимется ли веха; отказ — в
  ответе (`refusal`). Ответ панели и `orders_refund_reverse` один — `Panel\Consequences::reversal()`.
- **Панель:** у каждой записи возврата — в «Сводке» и в строке «Истории» — действие «Отменить запись»
  при праве `orders.refund` (`actions.refund_reverse`). Диалог: последствия из `dry_run`, причина
  обязательна; после отмены — тост и предложение сразу открыть диалог возврата. Отменённая запись
  видна серой плашкой, сумма и слова зачёркнуты, «Отменён: причина»; в «Возвращено» её сумма не входит.
  Маршрут `POST {api}/orders/{id}/refunds/{refund}/reverse` (`reason`, `dry_run`), отказ — под `refund`.
- Не делается: правка суммы записи, возврат через шлюз, отмена отмены заказа.

- **Администратору о новом заказе** (решение 81) — второй канал на `orders.placed` в наборе по
  умолчанию: письмо «Новый заказ» — номер, покупатель, состав, сумма, ссылка на карточку в панели
  (`order_url`). Получатель — `{email}` с первым адресом контактов сайта (`Contacts::emails()`
  `module-settings`), взятым, когда набор создаётся; контактов нет — канал создаётся выключенным,
  а `webx:doctor` предупреждает «у канала нового заказа нет получателя».
- Все каналы набора по умолчанию владелец сайта может отключить или перенастроить.
- Один канал можно назначить нескольким статусам: шаблон видит `{{public_status}}` и
  `{{public_status_code}}` и пишет одно письмо на все.
- `send()` зовёт слушатель после коммита с `subject: $order`, `locale: $order->locale`.

### 10.2. Переменные

Общие для всех событий заказа (значения — снимок в момент события, суммы — строкой
`Money::format()`):

| Переменная                                                         | Что                                                                                   | Пример                                     |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------- | ------------------------------------------ |
| `number`                                                           | номер                                                                                 | `1024`                                     |
| `order_url`                                                        | заказ в панели (от `app.url`)                                                         | `https://site.test/cms/orders/1024`        |
| `public_url`                                                       | страница заказа для покупателя, подписанная ссылка (§13.1)                            | `https://site.test/order/1024?signature=…` |
| `placed_at`                                                        | дата и время оформления, формат языка заказа                                          | `27.10.2026 14:05`                         |
| `customer_name`                                                    | имя и фамилия покупателя одной строкой (склейка)                                      | `Buyer A`                                  |
| `customer_first_name`, `customer_last_name`                        | имя и фамилия по отдельности; фамилии нет — пусто                                     | `Buyer`, `A`                               |
| `customer_phone`                                                   | телефон                                                                               | `+800 1234 5678`                           |
| `customer_email`                                                   | **адресат** (`address: 'email'`)                                                      | `buyer-a@example.com`                      |
| `recipient_name`, `recipient_phone`                                | получатель (имя — склейкой), если другой; иначе пусто                                 | `Recipient B`                              |
| `recipient_first_name`, `recipient_last_name`                      | имя и фамилия получателя по отдельности                                               | `Recipient`, `B`                           |
| `items`                                                            | список: `name`, `options`, `qty`, `price`, `total` (строки), `child` («да» у ребёнка) | `[{"name": "Item A", "qty": "2", …}]`      |
| `subtotal`, `discount`, `total`, `tenders`, `payable`              | суммы строкой                                                                         | `120,00 €`                                 |
| `delivery`                                                         | строка блока доставки (`summary` владельца) или пусто                                 | `Branch 12, Town D`                        |
| `payment`                                                          | строка блока оплаты или пусто                                                         | `Online by card`                           |
| `comment`                                                          | комментарий покупателя                                                                |                                            |
| `public_status`, `public_status_code`, `public_status_description` | публичный статус                                                                      | `In progress`, `in_progress`               |
| `status`                                                           | внутренний статус — **только для менеджерских каналов**, см. ниже                     | `Picker is looking`                        |

- Сверх общих: `reason` (отмена, неудачная оплата), `refund_amount` (возврат), `reference`
  (оплата, получение).
- Переменные к событиям заказа может добавлять чужой модуль — через `NotificationEvents::extend()`
  (§11.5 спеки оплаты): `module-payments` добавляет `payment_url`, `payment_instructions`,
  `payment_method`. Их значения считает тот модуль при `send()`, заказ о них не знает.
- `status` объявлен с пометкой «внутренний, покупатель не должен его видеть»: редактор канала
  предупреждает, если шаблон на адресата `customer_email` его использует. Запретить совсем нельзя —
  менеджерский и покупательский канал устроены одинаково.
- Шаблоны по умолчанию (`sample`, §5.1 спеки уведомлений): e-mail и Telegram для каждого события,
  на языках словаря; письмо покупателю — номер, статус, состав таблицей `{{#items}}`, суммы, ссылка
  на страницу заказа; менеджеру — то же плюс телефон и ссылка в панель.

Раздел «Заказы» (`orders`). Экраны — JSON ([`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md)) с
публичными `id` узлов для патчей соседей; npm-пара `@webx-ui/module-orders` регистрирует раздел и
свои типы узлов:

| Тип                       | Вид     | Что                                                                                                                                                                                    |
| ------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `wx-orders-layout`        | layout  | тело карточки `orders.show` (узел `body`): две колонки — вкладки и боковая `summary` — по контейнерному запросу от 900 px ширины карточки; уже — одна колонка, `summary` под вкладками |
| `wx-orders-status`        | layout  | полоса статуса в шапке (узел `header-actions`): внутренний статус, «видит покупатель», вехи; контейнер, в который соседи добавляют свои кнопки                                         |
| `wx-orders-items`         | display | вкладка «Состав»: дерево строк, скидки, корректировки, зачёты, привилегии                                                                                                              |
| `wx-orders-timeline`      | display | вкладка «История» (§8)                                                                                                                                                                 |
| `wx-orders-notes`         | display | блок «Заметки» под вкладками (узел `order-notes`, решение 90): заметки истории заказа на общем `WxNotesList` панели, поле — с `orders.manage`                                          |
| `wx-orders-summary`       | display | боковая карточка (узел `summary`, слот `side` у `wx-orders-layout`): итоги, возвращённое, даты вех                                                                                     |

(`--wx-field-max-width`), и колонки «основное + итоги» на них не встают.

### 11.1. Права

| Право                      | Что даёт                                                                                                                                                     |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `orders.view`              | список, карточка, история — чтение; MCP `orders:read`                                                                                                        |
| `orders.manage`            | смена статуса, вехи «оплачен» / «получен» вручную, отмена, контакты и заметка, блоки, привязка к посетителю (§13.3), заказ из панели (§29.2); `orders:write` |
| `orders.refund`            | возвраты — отдельно: деньги                                                                                                                                  |
| `orders.statuses`          | экраны статусов и настроек раздела (§11.4)                                                                                                                   |
| `orders.checkout.settings` | вкладка «Оформление» экрана настроек и `orders_checkout_settings_set` (§31.1)                                                                                |

Права — в `OrdersModule::permissions()` и `### Permissions` `AGENTS.md`; маршруты — `cms.can`;
`AccessCoverageTest` пакета зелёный; публичные маршруты (§13) — в списке открытых с причиной
«страница покупателя по подписанной ссылке» / «кабинет посетителя». Готовая роль сидера «Менеджер
заказов» (решение 33): `orders.view`, `orders.manage`, `users.view` (право появляется, только если
стоит users); `orders.refund` и `orders.statuses` — у «Администратора».

### 11.2. Список — `orders.index`

- Колонки: номер, дата оформления, покупатель (имя, телефон), состав коротко («Item A и ещё 2»),
  итог и «к оплате», внутренний статус (цветной `WxBadge`) с публичным мелко, отметки вех (оплачен,
  получен, отменён, возврат), строка доставки и оплаты (`summary` блоков).
- Поиск — номер, телефон в любом написании (`customer_phone_key`), e-mail, имя: по имени, по
  фамилии и по «имя фамилия» (`CONCAT_WS` обеих колонок).
- Фильтры: внутренний статус (с удалёнными, помечены), публичный, «ожидает оплаты», «оплата не
  прошла», оплачен / не оплачен, получен, отменён, есть возврат, период, гость / посетитель (если
  стоит users), способ доставки и оплаты (по `method` блока). Готовые вкладки над списком: «Новые»
  (начальный статус), «Ожидают оплаты», «Оплата не прошла», «Все».
- Массово: перевести в статус (с предпросмотром — сколько сменят публичный, сколько уведомлений
  уйдёт), отменить (с причиной).
- Один запрос на страницу + статусы одним запросом; превью состава — подзапросом первых строк, а не
  N+1 (`PerformanceTest`, §16).
- Без вкладки в адресе — «Новые», если в ней есть заказы, иначе «Все» (решение 92). Над списком —
  статистика `GET summary` (решение 93); строка раскрывается, `GET {id}/glance` (решение 94).

### 11.3. Карточка — `orders.show`

- **Шапка:** номер, дата, выбор внутреннего статуса (группы — публичные, внутри — внутренние;
  выключенные и удалённые не предлагаются), рядом — что увидит покупатель; отметки вех; действия:
  «Отметить оплату», «Отметить получение», «Отменить», «Отметить возврат» (по правам и §5.1, §9.4).
- **Статус в полосе** — бейдж с карандашом (диалог смены); та же «Сменить статус» — в шапке
  рядом с «Отметить оплату» (решение 89).
- **Смена статуса** — диалог с заметкой и строкой последствий из `dry_run` (`StatusMove`):
  «Покупатель увидит „Отправлен“, уйдёт письмо через канал „Покупателям“» или «Покупатель ничего не
  заметит». Статус с вехой — «Поставит отметку „Оплачен“».
- **Вкладки** (узел `tabs`): «Состав» (`wx-orders-items`: дерево строк, скидки строк, корректировки
  заказа, итоги, зачёты, привилегии отметками — «Доставку оплачивает магазин»), «Покупатель»
  (контакты, получатель, комментарий — правка; если стоит users — ссылка на
  посетителя и действия «Привязать к посетителю» / «Отвязать», §13.3), «История» (`wx-orders-timeline`, §8).
  Под вкладками — «Заметки» (`order-notes`, решение 90) с закреплённой заметкой над лентой
  (решение 91). Соседи добавляют свои вкладки
  патчем узла `tabs`: «Доставка» — `module-delivery` (§14.2 его спеки), «Оплата» — `module-payments`.
  Без вкладки владельца блок показывается в «Составе» строкой `summary` и свёрнутым JSON.
- Публичные `id` узлов: `header-actions` (`wx-orders-status`), `body` (`wx-orders-layout`),
  `tabs`, `order-notes` (`wx-orders-notes`), `summary` (`wx-orders-summary`: позиции и единицы, итоги, возвраты с причиной, вехи с
  причиной отмены и источником заказа).

### 11.4. Статусы и настройки

- **`orders.statuses`** — две колонки: публичные (порядок перетаскиванием, название по языкам,
  описание, код, каналы уведомлений — если стоит notifications) и внутренние, сгруппированные по
  публичным (перетаскивание внутри и между группами = порядок и перепривязка, цвет из палитры,
  название по языкам, веха, «выключен»). Число заказов у каждого. Внизу — «Удалённые» с
  восстановлением. Удаление и перепривязка — с текстом последствий (§5.6).
- **`orders.settings`** (экран раздела, как `users.settings`): номер (префикс, начало, ширина —
  с пробным номером), начальные статусы (§5.2), каналы уведомлений вех (§10.1); вкладка
  «Оформление» — настройки §31.2 под правом `orders.checkout.settings`, если оформление включено.
- **Как устроено** (этап 7). Оба экрана — маршруты раздела `orders` (`/orders/statuses`,
  `/orders/settings`), ссылки на них — в шапке списка у того, у кого `orders.statuses`; API —
  `/api/cms/orders/statuses…` и `/api/cms/orders/settings` под `cms.can:orders.statuses`.
  - Записи статусов — сервис `OrderStatuses` (`writePublic`, `removePublic`, `restorePublic`,
    `write`, `remove`, `restore`, `arrange`), каждый — с `dry_run` и ответом `StatusPlan`; отказ —
    `StatusRefused` с кодом: `initial` (в статус встают новые заказы — выбран в настройках или
    первый набора), `last_active` (последний активный этап группы, в которой есть заказы, или
    последний активный вообще), `public_deleted`, `has_active` (в публичном ещё живут этапы).
    Выключение этапа держит те же правила, что удаление; перепривязка — правило последнего
    активного. Заказы не трогаются: они едут вместе со статусом, и покупатель видит новое имя.
  - Порядок обоих уровней — одним `PUT …/statuses/arrange` (`publics`, `groups`); этап,
    перетащенный в другую группу, перепривязан, и до сохранения панель показывает, у скольких
    заказов покупатель увидит другое имя. На телефоне то же делает выбор группы в диалоге этапа.
  - Удаление публичного с живыми этапами — один диалог: список этапов и «Перенести их в»
    (`move_to`), этапы переезжают в той же транзакции.
  - Настройки — ключи `orders.number.prefix`, `.start`, `.pad`, `orders.initial_status`,
    `orders.initial_status_awaiting_payment` в `module-settings` (`OrderSettings`); незаписанный
    ключ и сайт без `module-settings` читают конфиг `webx-orders`, экран тогда говорит, что решает
    конфиг. Пробный номер — номер следующего `id`; формат, чей пробный номер уже занят заказом, —
    отказ под `orders.number.prefix`. Начальный статус выбирается из активных в живых группах.
  - Каналы уведомлений публичных статусов и вех на этих экранах — с этапом 9 (уведомления).

## 12. MCP

Области `orders:read` / `orders:write`; права по правилу §6 спеки доступа (`orders:read` →
`orders.view`, `orders:write` → `orders.manage`; возвраты — `permission: 'orders.refund'`, статусы и
настройки — `permission: 'orders.statuses'`). Каждый изменяющий инструмент принимает `dry_run` и на
нём отвечает тем же, что панель показывает в диалоге последствий. Контакты покупателя в ответах —
да: право `orders.view` и есть доступ к персональным данным покупателей, это сказано в описании
инструментов. Деньги — целым и строкой `*_formatted`. Каждый инструмент — тонкая обёртка над
методом `Orders` (решение 18): тот же отказ, тот же ответ `dry_run`, что у панели.

## 13. Покупатель

### 13.1. Страница заказа

- `GET /order/{number}` (внутри `{locale?}` сайта, `SiteRoutes::SERVICE`, `no-store`) — подписанная
  ссылка Laravel без срока (`URL::signedRoute`): её получает покупатель в письме и на странице
  «Спасибо» оформления (§26). Подпись неверна → 404 (не 403: не подтверждать, что номер есть).
- Показывает: номер, дату, публичный статус с описанием и шкалой публичных статусов по порядку,
  отметки «Оплачен», «Получен», «Отменён», «Возвращено N» (решение 38: отмена видна, даже если
  статус не меняли), состав, суммы, блок доставки и оплаты строкой `summary`, контакты. Внутренний
  статус и заметка менеджера — никогда.
- Вьюха `webx-orders::order.show` на полях `widgets`, вид — тема. Подпись зависит от `APP_KEY`:
  смена ключа ломает старые ссылки, это принято (решение 32).

### 13.2. «Мои заказы» и карточка посетителя (если стоит `module-users`)

- Раздел кабинета через `AccountMenu` и `AccountRoutes` ровно как в примере §11.2 спеки users:
  `/account/orders` — список своих заказов (`user_id = visitor.id`), `/account/orders/{number}` — та
  же страница, что §13.1, без подписи (владелец проверяется). `badge` — число незавершённых
  (нет `received`, `cancelled`) одним запросом.
- Вкладка «Заказы» в `users.form` — патч узла `tabs` (§11.3 спеки users) с `wx-orders-list` и
  фильтром `user`; в `summary` — «Заказов: N».
- `DeletionWarnings`: «Активный заказ №1024 будет выполнен, но вы не увидите его в кабинете»;
  слушатель `VisitorDeleting` ставит `user_id = null` у его заказов, снимок контактов остаётся
  (§14.1 спеки users).
- Гостевые заказы сами в кабинете не появляются (решение 21): только оформленные со входом и
  привязанные менеджером (§13.3).

### 13.3. Привязка гостевого заказа (если стоит `module-users`)

- Карточка заказа, вкладка «Покупатель»: «Привязать к посетителю» — поиск по e-mail и имени
  (поиск посетителей `module-users`, первым — совпадение с `customer_email`; шов `Visitors` в
  0.89.0 знает только точный `findByEmail()`, публичный поиск добавляется в users в этапе 10), «Отвязать» — у привязанного. Право —
  `orders.manage`; поиск посетителей требует ещё `users.view`.
- Метод — `Orders::linkVisitor()` / `unlinkVisitor()` (§5.3): `user_id` меняется, снимок контактов
  не трогается (заказ хранит, что ввёл покупатель). Перепривязка к другому — одно действие,
  без отвязки.
- Строка истории `kind = visitor`: кто, когда, к кому (`note` — имя и e-mail посетителя на момент
  привязки) или «отвязан от …». Событие — `OrderDetailsChanged` с `fields = ['user_id']` и
  прежним значением в `before`.
- `dry_run` (панель показывает его в диалоге, MCP — `orders_link_visitor`): кого нашли, был ли
  заказ уже привязан и к кому, «Заказ появится в „Моих заказах“ посетителя».
- Автоматической привязки (по подтверждённому адресу, при регистрации) нет; письмо покупателю
  о привязке не уходит.

## 16. Производительность и кеш

- **Оформление** (`place()`): бюджет запросов фиксирует `PerformanceTest` — вставки строк,
  корректировок и зачётов пачками (`insert` на таблицу), не по одной; пересчёт корзины — один раз.
- **Списки панели** — без кеша (данные живые), с бюджетом и `assertNoRepeatedQueries`;
  `orders_summary` — `COUNT … GROUP BY` по индексам, без загрузки моделей.
- **Страница покупателя и кабинет** — `no-store`, не кешируются; статусы (оба набора) — в
  `CacheGroups::remember` группы `orders.statuses`, сброс — `bumpOn` моделей статусов.
- **Фильтр «ожидает оплаты»** — по индексу `(awaiting_payment, placed_at)`.

## 18. Отложенное

Ответы на вопросы первых редакций — решения 17–37 (заказ) и 62–74 (оформление), §2. Ниже — то,
что сознательно не входит в v1 и делается по первому запросу клиента (решение 17). Вопросы,
которые всплыли при слиянии спек, закрыты решениями 80–82.

**Заказ:**

1. **Возврат через шлюз и холдирование.** У клиентов бывает сразу списание или холдирование до
   завершения заказа (тогда рядом с отменой — кнопки «списать окончательно» / «вернуть»). Модель
   вех этому не мешает: холдирование — новая веха между `awaiting_payment` и `paid`, возврат шлюзом
   — тот же `refund()` с `method = gateway`.
2. **Автоотмена неоплаченного** через N часов (решение 37) — команда поверх `cancel()` (§5.5).
3. **Автоперевод во внутренний статус по вехе** (решения 15, 30). Точка расширения: настройка
   «веха → внутренний статус» у вехи, которую применяет `mark()` через тот же `moveTo()`.
4. **В заказе из панели** (решения 22, 85, §29.2) — ручная цена или скидка строки и выбор доставки
   и оплаты менеджером; **правка состава** оформленного заказа (решение 23), **снятие вехи**
   (решение 24), **обезличивание** (решение 35), **свои поля `extra`** (решение 36).
5. **Автоматическая привязка гостевых заказов** к посетителю по подтверждённому адресу (решение 21:
   в v1 — только вручную в панели).
6. **Номер заказа** со сбросом по годам, случайный или фискальный (решение 20).

**Оформление:**

7. **Брошенные оформления** (решение 70) — письмо «вы не закончили заказ» по черновикам с e-mail:
   отдельный спутник поверх `order_checkout_drafts` и `CheckoutStepSaved`, с согласием на рассылку.
8. **Минимальная сумма заказа** («от N», решение 73): настройка оформления (отказ с подсказкой
   «добавьте ещё на N») или условие `module-cart-rules`.
9. **Свои поля оформления** (решение 65): реестр полей шага контактов по образцу своих полей users
   (§10 его спеки) вместе с `extra` у заказа (решение 36).
10. **Подсветка изменившихся строк при сверке** (решение 69): скрытое поле `expected_lines` (пары
    `id:line_total` строк и `source:amount` корректировок, какими их видел покупатель) и класс
    `is-changed` у строк, которые разошлись с новым `CartState`.

**Часть II. Оформление** (§19–§34). Бывшая спека `WEBX_UI_MODULE_CHECKOUT.md`, её §N — здесь §N+16.

## 19. Адреса

Маршруты — внутри `{locale?}` сайта, `SiteRoutes::SERVICE` (как страница заказа), стек `web`,
`Cache-Control: no-store`, `Vary: Cookie`. Префикс — `webx-orders.checkout.path` (по умолчанию
`checkout`); адрес занят маршрутом, `routing` не отдаст его странице. Именованный маршрут
`checkout` — тот, который ищет кнопка виджета корзины (§9.1 её спеки).

```
GET  /checkout                     страница оформления (§20); пустая корзина — §20.4
POST /checkout/steps/{step}        сохранить шаг: контакты, получатель, комментарий, свой шаг проекта
GET  /checkout/summary             колонка итогов фрагментом HTML (§23) — для перерисовки скриптом
POST /checkout/place               подтверждение (§24)
GET  /checkout/thanks/{number}     «Спасибо» (§26)
POST /checkout/quick               «Купить в один клик» (§29), если включено
```

- **Только своя корзина.** Корзина — `CartHandle::cart()` `module-cart` (гость — по cookie, вошедший —
  по `user_id`); оформление не принимает id корзины ни в адресе, ни в теле.
- **Оформление выключено** (`webx-orders.checkout.enabled = false`, решение 80) — маршрутов выше нет:
  именованного `checkout` нет, и кнопка корзины пропадает или ведёт на `webx-cart.checkout_url` —
  страницу оформления сайта, которая сама зовёт `Orders::place()`. Слоты, черновики, MCP оформления
  и команда чистки не регистрируются; заказы, панель и страница заказа работают как были.
- **JSON и HTML одним маршрутом** — по соглашению форм (`FormResponse`, §17.4 спеки виджетов): с
  `Accept: application/json` ответ — `{ ok, html, redirect, … }`, без — redirect с flash.
- Слоты ходят в свои API (`/api/delivery/*`, `/api/payments/*`) сами; оформление их не
  проксирует.

## 20. Шаги

### 20.1. Страница и порядок

```
┌───────────────────────────────────────────────┬──────────────────────────┐
│ 1. Контакты         Buyer A, +800 1234 5678 ✎ │ Ваш заказ                │
│ 2. Доставка   (слот, если стоит и нужен)      │ 3 товара на сумму  …     │
│    населённый пункт → способы → точка/адрес   │ Скидка             …     │
│ 3. Оплата     (слот, если стоит)              │ Стоимость доставки …     │
│    способы оплаты                             │ ─────────────────────    │
│ 4. Комментарий к заказу                       │ К оплате           …     │
│                                               │ [ Подтвердить заказ ]    │
│                                               │ ☐ Согласен с условиями   │
└───────────────────────────────────────────────┴──────────────────────────┘
```

- **Подтверждение — не секция, а колонка итогов** (§23): решение 45 называет его шагом, образец
  (решение 53) держит кнопку справа. Реестр (§20.2) знает его как последний шаг `confirm`, который
  нельзя убрать.
- **Узкий контейнер** (`@container`, не медиа-запрос): колонка итогов уходит под шаги, кнопка
  подтверждения — в конец страницы и липкой строкой «К оплате · Подтвердить» внизу.
- **Состояние шага отдаёт модуль, сворачивание выбирает тема** (решение 63). Секция каждого шага
  печатает и форму, и строку-сводку (`summary()` шага) с «Изменить»; класс секции — `is-done`
  (шаг пройден: `summary()` не `null` и `check(Checkout)` пуст) или `is-open` (первый
  незаполненный — тот, куда идёт покупатель). Вид секций задаёт корень композиции атрибутом
  `data-steps`: `open` (по умолчанию в пакете) — все формы раскрыты, сводки нет; `collapse` — у
  `is-done` видна сводка, форма скрыта до «Изменить». `theme-default` ставит `collapse` патчем
  узла `checkout` (§27.1); тема, которой это не нужно, ничего не делает. Модуль не меняется ни в
  каком из двух видов: CSS пакета и `checkout.js` читают атрибут.
- **Вернувшийся покупатель** видит `is-open` на первом незаполненном шаге; при `collapse` —
  пройденные свёрнуты над ним.
- **Кнопка подтверждения активна** всегда, а не только после всех шагов: нажатие проверяет всё
  (§24.1) и ведёт фокус к первому незаполненному шагу с ошибкой. Так покупатель с подставленными
  контактами и запомненной доставкой подтверждает одним нажатием.

### 20.2. Реестр шагов

```php
namespace WebxUi\Orders\Checkout\Steps;

interface Step
{
    /** 'contacts', 'delivery', 'payment', 'comment' — stable, used in addresses and MCP. */
    public function key(): string;

    /** Whether the step is shown for this checkout at all (delivery: shippable lines exist). */
    public function applies(CheckoutContext $context): bool;

    /** The open step: a Blade view the page prints inside the step's section. */
    public function render(CheckoutContext $context): Htmlable;

    /** One line for the collapsed step; null — the step is not filled yet. */
    public function summary(CheckoutContext $context): ?string;

    /**
     * Whether the step is ready to place an order with. Cheap for Purpose::Checkout,
     * strict for Purpose::Order (a slot re-validates its point, re-quotes, §22).
     *
     * @return list<StepError>  empty — ready
     */
    public function check(CheckoutContext $context, Purpose $purpose): array;

    /** Puts what the step owns into the order input; called once, inside place (§24.1). */
    public function contribute(CheckoutContext $context, PlaceOrderBuilder $order): void;
}

final class CheckoutSteps
{
    /** A step with a key that exists replaces it: a project overrides 'contacts' this way. */
    public function register(Step $step, int $position): void;

    public function remove(string $key): void;

    /** @return list<Step> in position order, filtered by applies() */
    public function for(CheckoutContext $context): array;
}
```

| Ключ       | Позиция | Чей                                     | Что                                                       |
| ---------- | ------- | --------------------------------------- | --------------------------------------------------------- |
| `contacts` | 100     | оформление                              | покупатель, кнопка входа, получатель (§20.3)              |
| `delivery` | 200     | слот `ShippingSlot` (`module-delivery`) | шаг доставки — обёртка слота (§22.1)                      |
| `payment`  | 300     | слот `PaymentSlot` (`module-payments`)  | шаг оплаты — обёртка слота                                |
| `comment`  | 900     | оформление                              | комментарий покупателя; выключается настройкой            |
| `confirm`  | —       | оформление                              | колонка итогов, согласие, кнопка (§23, §24); не удаляется |

- **Свой шаг проекта** — класс `Step` с позицией между (`250` — «Время звонка»). Своих полей
  оформления и заказа в v1 нет (решение 65, решение 36): шаг пишет в заказ свой блок
  (зарегистрированный в `OrderBlocks`) или строку истории через `Orders::note()` в слушателе
  `OrderPlacing`; реестра полей шага контактов нет.
- **`CheckoutContext`** — неизменяемый снимок на запрос: `cart` (`Cart`), `state` (`CartState` с
  `Purpose::Checkout`, считается один раз на запрос), `draft` (§21), `visitor` (`?Visitor` из шва
  `module-admin`), `locale`, `currency`; метод `shippingChoice(): ?ShippingChoice` — выбор доставки
  нейтральным описанием для шага оплаты (§22.2), лениво и один раз на запрос. Шаги не читают cookie
  и сессию сами.
- **`StepError`** — `step`, `field` (имя поля формы или `null`), `message` на языке запроса,
  `code` для MCP (`contacts.phone_required`, `delivery.point_gone`).
- **`PlaceOrderBuilder`** — изменяемая сборка входа `PlaceOrder` (§6.1): шаг ставит
  свои поля (`customer`, `recipient`, `comment`, `block('delivery', …)`, `awaitPayment()`), чужие
  поля не видит. Ключ блока, который уже занят, — исключение.

### 20.3. Контакты и получатель

Поля шага `contacts` — поля и оболочка `widgets` (§17.2–§17.3 спеки виджетов):

| Поле                          | По умолчанию              | Настройка (`orders.checkout.fields.*`)    |
| ----------------------------- | ------------------------- | ----------------------------------------- |
| Имя                           | обязательное              | всегда обязательное                       |
| Фамилия                       | необязательное            | `required` / `optional` / `hidden`        |
| Телефон                       | обязательное              | `required` / `optional` / `hidden`        |
| E-mail                        | обязательное              | `required` / `optional` / `hidden`        |
| «Получатель — другой человек» | флажок, снят              | `orders.checkout.recipient`: `on` / `off` |
| Имя получателя                | обязательное, если флажок | —                                         |
| Фамилия получателя            | как фамилия покупателя    | по `orders.checkout.fields.last_name`     |
| Телефон получателя            | обязательный, если флажок | —                                         |

- **Заказу нужно имя и хотя бы телефон или e-mail** (§6.1). Экран настроек не даёт
  сделать оба `hidden` или оба `optional`; сочетание `optional` + `optional` проверяется на
  отправке: «Укажите телефон или e-mail».
- **В заказ** — `Contact(firstName, lastName, phone, email)`: имя и фамилия идут раздельно в
  `customer_first_name` и `customer_last_name` (решение 64; накладной службы доставки нужны
  раздельно). Склейку «Имя Фамилия» для писем и списка даёт заказ (`ContactData::name()`, §7.1).
- **Телефон** — поле `tel` с проверкой `Contact` заказа (`+` и цифры с разделителями). Маски
  страны нет: страна не задана (принцип обезличивания); пример в подсказке — `+800 1234 5678`.
- **Получатель** — `Contact(firstName, lastName, phone)` без e-mail; флажок снят —
  `recipient = null` («тот же»).
  Флажок не зависит от доставки: забрать самовывоз или услугу может другой человек.
- **E-mail вошедшего** подставляется, но правится (решение 49): в заказ идёт введённый; профиль не
  меняется (вопрос 6 §20 спеки users).

### 20.4. Пустая и неоформляемая корзина

- **Пустая корзина** (`CartState::isEmpty()`) — страница печатает «Корзина пуста» со ссылкой на
  главную или `webx-orders.checkout.empty_url`; шагов нет. Черновик не удаляется.
- **Строки, которые нельзя купить** (`line.gone`, `line.unavailable`, `line.qty_limited`,
  `line.currency`) — над шагами блок предупреждений корзины (тексты `warnings` из `CartState`) со
  ссылкой «Открыть корзину» (виджет корзины в режиме сайта). Кнопка подтверждения при этом не
  выключается: нажатие отвечает тем же списком (`CartNotOrderable`, §24.2), фокус — на блок.
- **`price.down` / `price.up`** — показываются строкой у товара в колонке итогов («подешевел»,
  «подорожал»), заказ не блокируют: сверка сравнивает с тем, что на экране, а не с
  `price_at_add`.

  не создаёт (как чтение корзины, решение 19 корзины). Вошедшему контакты подставляются при показе
  из `Visitor`, в черновик они попадают первым сохранением шага.
- **Почему не сессия:** выбор доставки уже живёт по корзине (`delivery_selections`), корзина живёт
  по своей cookie дольше сессии; черновик в сессии потерялся бы при её истечении, а доставка — нет.
  Почему не колонки в `carts`: корзина не знает оформления (§1 её спеки).
- **Персональные данные** гостя, который не оформил заказ, лежат здесь до чистки (§21.3); MCP
  показывает их маской (§32).

### 21.2. После заказа

`Orders::place()` очищает строки корзины `CartService::empty()` (шаг 8 §6.2); запись корзины, её
cookie и черновик живут.
Оформление в той же транзакции (слушатель `OrderPlacing`, только для своего `source = 'checkout'`)
**оставляет** в черновике контакты и получателя — следующий заказ того же гостя подставит их — и
стирает `comment`, `steps`, `terms_accepted_at`, `terms_version`, `place_key`, `shown_payable`.
Контакты гостя помнятся до чистки — 30 дней без активности (решение 66, §21.3).

### 21.3. Чистка

- Черновик удаляется каскадом вместе с корзиной (`webx:cart:prune`, §4.3 спеки корзины).
- Своя команда `webx:orders:checkout-prune [--dry-run]` в расписании раз в сутки: черновики с
  `updated_at` старше `webx-orders.checkout.draft_days` (по умолчанию 30) удаляются, даже если корзина
  жива, — контакты незавершённых оформлений не должны жить столько же, сколько товары в корзине.
- `VisitorSignedOut` (шов `module-admin`): корзина гостя снимается с cookie (§13.3 спеки users),
  черновик корзины аккаунта остаётся с ней.
- **Вход (`VisitorSignedIn`).** Нет корзины аккаунта — гостевая становится ею, черновик остаётся
  при ней сам. Есть — `AccountCarts::signedIn()` `module-cart` сливает строки и **удаляет**
  гостевую корзину, а с ней каскадом и черновик. Поэтому корзина перед удалением гостевой бросает
  синхронное событие `CartsMerging(guestCartId, accountCartId)` (внутри своей транзакции;
  добавляется в `module-cart` в этапе 12), и слушатель оформления переносит черновик гостевой
  корзины к корзине аккаунта, если у той своего нет; есть — гостевой уходит с корзиной.

## 22. Слоты доставки и оплаты

### 22.1. Общий контракт

Слот — шаг, который принадлежит другому модулю и который оформление знает только по ключу и
контракту. Оформление оборачивает слот в `Step` само (`SlotStep`): секция, сводка, проверка и
вклад в заказ идут через методы ниже.

```php
namespace WebxUi\Orders\Checkout\Slots;

interface Slot
{
    /** 'delivery' | 'payment' — the step key and the order block key at once. */
    public function key(): string;

    /** Whether the step is shown: delivery — Delivery::needed($state), payment — payable > 0 and a method available. */
    public function needed(CheckoutContext $context): bool;

    /** The step's body; the slot prints its own components and talks to its own API. */
    public function render(CheckoutContext $context): Htmlable;

    /** One line for the collapsed step: "Branch 12, Town D · Free". Null — nothing chosen yet. */
    public function summary(CheckoutContext $context): ?string;

    /**
     * Whether what the buyer chose is still valid.
     * Purpose::Checkout — from stored records only; Purpose::Order — strict: re-validate,
     * re-quote without cache, no fallbacks (§9.2 of the delivery spec).
     *
     * @return list<StepError>
     */
    public function check(CheckoutContext $context, Purpose $purpose): array;

    /** The order block (§6.4) — called after check(Order) passed. */
    public function snapshot(CheckoutContext $context): array;
}
```

- **Регистрация** — владелец в `boot()`, только если стоит `module-orders` (`CheckoutSlots` есть в
  пакете всегда; при выключенном оформлении реестр никто не опрашивает):
  `if (class_exists(CheckoutSlots::class)) $this->callAfterResolving(CheckoutSlots::class, fn ($s) => $s->register(new DeliveryCheckoutSlot(...)))`.
  Ключей два — `delivery` и `payment`; третий слот — новый блок заказа и решение человека (§6.4). Повторная регистрация ключа — исключение.
- **Событие на странице.** После каждой правки выбора слот бросает на `document` событие
  `webx:checkout:slot-changed` (`detail`: `slot`, `summary`). Скрипт оформления по нему
  перерисовывает колонку итогов (`GET /checkout/summary`, §23). Доставка уже бросает
  `webx:delivery:changed` (§12.3 её спеки) — её слот переводит его в общее событие, чтобы
  оформление не знало имён событий соседей.
- **Состояние выбора хранит владелец** (решение 56) по `cart_id`; оформление его не читает.
  Единственное, что один слот узнаёт о другом, — `ShippingChoice` через `CheckoutContext` (§22.2).
- **Падение слота** при `Purpose::Checkout` — секция со строкой «Не удалось загрузить», лог,
  страница живёт; при `Purpose::Order` — заказ не создаётся (как источник цепочки, §5.4
  корзины).

### 22.2. `ShippingSlot` — доставка

```php
interface ShippingSlot extends Slot
{
    /**
     * The totals line "Delivery cost" (§23.1): an amount, "Free" with the old price crossed out,
     * "at carrier rates" with an optional estimate, or null — nothing chosen.
     */
    public function totalsLine(CheckoutContext $context): ?ShippingLine;

    /** What the payment step may know about the chosen delivery (§7.3 of the payments spec); null — nothing chosen. */
    public function choice(CheckoutContext $context): ?ShippingChoice;
}

/** Built by ShippingSlot, read by PaymentSlot through CheckoutContext::shippingChoice(). */
final readonly class ShippingChoice
{
    public function __construct(
        public string $method,           // delivery method key: 'store-pickup', 'carrier-a-branch'
        public string $carrier,          // 'store' or a carrier key
        public bool $cashOnDelivery,     // the carrier collects money on handover for this method and point
        public bool $storePickup,        // the buyer collects it at the shop's own point
    ) {}
}

final readonly class ShippingLine
{
    public function __construct(
        public string $kind,           // 'fixed' | 'free' | 'carrier_rates'
        public ?int $amount = null,    // fixed: in the total already, as the delivery adjustment
        public ?int $was = null,       // free: crossed out
        public ?int $estimate = null,  // carrier_rates: "≈ …", not in the total
    ) {}
}
```

- **`needed()`** — `Delivery::needed($context->state)`: нет доступной строки с `shippable = true` —
  нет шага (решение 46), нет строки в итогах, блок `delivery` заказа — `null`.
- **Сумма доставки в цепочке уже есть:** доставка — `AdjustmentSource` с приоритетом `1000` и
  `meta.kind = delivery` (§9.3 её спеки). Колонка итогов не прибавляет `amount` ещё раз: она
  убирает корректировку `meta.kind = delivery` из списка скидок и показывает её строкой
  «Стоимость доставки» по `totalsLine()`.
- **`check(Order)`** — повторный `validate()` выбора и `quote()` без кеша (§11.1 и §9.2 её спеки):
  снятая точка — «Пункт выдачи больше не работает, выберите другой»; расчёт не прошёл —
  «Не удалось рассчитать доставку, выберите другой способ».
- **`snapshot()`** — `Delivery::snapshot($selection, $quote)->toArray()` (§11.1 её спеки).
- **`choice()`** — способ, перевозчик, «наложенный платёж» способа и точки, «самовывоз из
  магазина»; поля — ровно те, что ждёт оплата (§7.3 спеки оплаты). Нет слота доставки, шаг не
  нужен или способ не выбран — `CheckoutContext::shippingChoice()` отдаёт `null`.
- **Реализация** — `WebxUi\Delivery\Checkout\DeliveryCheckoutSlot` в `module-delivery`; `render()`
  печатает `<x-webx-delivery::step>` (§12.3 её спеки).

### 22.3. `PaymentSlot` — оплата

```php
interface PaymentSlot extends Slot
{
    /** Whether the chosen method is paid online after the order exists (§5.1). */
    public function awaitsPayment(CheckoutContext $context): bool;

    /**
     * Where the buyer goes right after the order is placed: a gateway page, or null — the thanks page.
     * Called after commit; must not throw for a placed order — on failure it returns null and logs.
     */
    public function next(OrderData $order): ?string;

    /** "Pay now" on the thanks page and the order page for an order that still awaits payment. */
    public function payAgainUrl(OrderData $order): ?string;
}
```

- **Порядок шагов** — оплата после доставки (позиции 200 и 300): способ оплаты может зависеть от
  способа доставки (наложенный платёж не для любого почтомата). Слот оплаты получает выбор
  доставки только как `CheckoutContext::shippingChoice()` (§22.2): ни доставка, ни оплата друг друга
  в `require` не держат и в API друг друга не ходят. После `webx:checkout:slot-changed` от доставки
  скрипт оформления перерисовывает и шаг оплаты (§7.3 спеки оплаты).
- **`needed()`** — `payable > 0` и есть доступный способ (§10.1 спеки оплаты); один способ — шаг
  показывается свёрнутой строкой с его названием (покупатель видит, как платит), выбирать нечего.
- **Комиссия способа** («+2 % за оплату картой») — если `module-payments` её введёт, она
  `AdjustmentSource` цепочки корзины, как доставка, а не строка оформления. В v1 комиссий нет.
- **`snapshot()`** — блок `payment` заказа: общая часть `method`, `title`, `price` (§6.4 спеки
  заказов), детали — владельца.
- **`next()`** — после коммита (§24.1, шаг 6): адрес шлюза → ответ `FormResponse::redirect()`;
  `null` — «Спасибо». Шлюз недоступен — заказ уже создан и «ожидает оплаты»; покупатель попадает на
  «Спасибо» с кнопкой «Оплатить» (`payAgainUrl()`), менеджер видит заказ в фильтре «ожидает
  оплаты» (решение 10).
- **Выбор оплаты** хранит `module-payments` по корзине (`payment_selections`, по образцу
  `delivery_selections`); реализация слота — `PaymentsCheckoutSlot` (§5 и §10 спеки оплаты,
  решение 74). `next()` там — `Payments::begin()` и адрес `/pay/go/{uuid}` без запроса к шлюзу
  (§8.2 спеки оплаты), что и требует «не бросает» выше.

## 23. Колонка итогов

### 23.1. Строки

Из `CartState` с `Purpose::Checkout` (один расчёт на запрос) и слотов; суммы — строками
`*_formatted` от `Money::format()` (решение 32 корзины), оформление не форматирует само:

| Строка                              | Откуда                                                                                   | Когда видна                                                        |
| ----------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| «N товаров на сумму»                | `units`, `subtotal`                                                                      | всегда                                                             |
| строка товаров (свёрнуто)           | `lines`: картинка, название, `qty`, `line_total`; «подешевел» / «подорожал»              | раскрывается по «Состав заказа»                                    |
| «Скидка»                            | Σ `adjustments` без `meta.kind = delivery`; раскрывается списком подписей                | есть скидки                                                        |
| «Стоимость доставки»                | `ShippingSlot::totalsLine()`: сумма, «Бесплатно» + зачёркнутая, «по тарифам перевозчика» | слот доставки нужен и способ выбран; не выбран — «выберите способ» |
| привилегии                          | `benefits`: подписи строками с отметкой — «Доставку оплачивает магазин»                  | есть привилегии (решение 50)                                       |
| подсказки                           | `hints`: «До бесплатной доставки осталось N»                                             | есть подсказки                                                     |
| «Оплачено сертификатом» …           | `tenders`: подпись и сумма                                                               | есть зачёты                                                        |
| **«К оплате»**                      | `payable`                                                                                | всегда                                                             |
| «+ доставка по тарифам перевозчика» | `ShippingLine::kind = carrier_rates`, мелко под «К оплате»                               | доставка не в сумме                                                |

- **Количество в «N товаров»** — `units` корзины (её счётчик); слово — `pluralForm()` по CLDR
  (CLAUDE.md §5, строка на каждую форму).
- **Пустые списки — без строк**, а не «Скидка: 0».

### 23.2. Фрагмент и скрытые поля

`GET /checkout/summary` и сама страница печатают колонку одним видом
`webx-orders::checkout.summary` со скрытыми полями формы подтверждения:

- `expected_payable` — `payable` этого расчёта (целым);
- `place_key` — ключ повтора (§24.3);
- `webx_ts` и honeypot (§28).

Сервер пишет `shown_payable` в черновик, только если черновик уже есть (чтение черновик не
создаёт, §21.1). Скрипт перерисовывает колонку целиком по `webx:checkout:slot-changed`,
`webx:form:success` шага и событию входа (§25): так `expected_payable` всегда тот, что на экране.

### 23.3. Место для зачёта и промокода

Реестр `CheckoutSummaryParts` (`register(string $key, SummaryPart $part, int $position)`):
необязательные куски колонки итогов между строками и «К оплате». В пакете он пустой (решение 51):

- `module-coupons` — поле «Промокод» и кнопка «Применить» (свой API, применённый код — строкой
  скидки через цепочку);
- `module-wallet` — поле суммы «Оплатить сертификатом / кешбеком» с подписью лимита «не больше N %»
  (свой API, сумма — `Tender` цепочки).

```php
interface SummaryPart
{
    public function applies(CheckoutContext $context): bool;

    public function render(CheckoutContext $context): Htmlable;
}
```

Кусок меняет состояние только через свой API и бросает `webx:checkout:slot-changed` (`slot` — его
ключ); оформление перерисовывает итоги. В композиции колонки (§27) у реестра — узел
`checkout.summary.parts`, тема может перенести его выше или ниже.

### 23.4. Согласие с условиями

Настройка `orders.checkout.terms`:

| Значение   | Что видит покупатель                                                       | Проверка            |
| ---------- | -------------------------------------------------------------------------- | ------------------- |
| `none`     | ничего                                                                     | —                   |
| `notice`   | под кнопкой: «Нажимая кнопку, вы соглашаетесь с условиями» (ссылка)        | —                   |
| `checkbox` | флажок «Я согласен с условиями» (ссылка), без него кнопка отвечает ошибкой | обязательный флажок |

- Ссылка — страница сайта `orders.checkout.terms_page` (выбор страницы из `module-pages` или адрес);
  второй документ (обработка персональных данных) — `orders.checkout.privacy_page`, если задан.
- **Запись о согласии — строка истории заказа** (решение 67), колонки нет. Слушатель
  `OrderPlacing` оформления (в транзакции заказа, §21.2: заказ без записи не появится) зовёт
  `Orders::note($order, $text, 'checkout')` при `notice` и `checkbox`:
  «Согласие с условиями: <название страницы> (<адрес>), версия <версия>, <время>»; второй документ
  — тем же текстом второй строкой.
- **Версия условий:** у страницы `module-pages` — номер её опубликованной версии (текст той
  версии хранит история страниц, своей копии текста у оформления нет); у внешнего адреса версии
  нет — в строке «версия неизвестна», в `terms_version` — сам адрес. Сменилась версия —
  `terms_accepted_at` в черновике сбрасывается, флажок нужно отметить снова.
- Значение по умолчанию — `notice`.

## 24. Подтверждение

### 24.1. Порядок

`POST /checkout/place` (`expected_payable`, `place_key`, `terms`, антиспам):

```
1. антиспам      honeypot, метка времени, лимит (§28); пойман — §28
2. ключ          place_key совпадает с черновиком? нет — 409 «страница устарела», свежая колонка
3. шаги          check(ctx, Purpose::Order) каждого шага по порядку → первая ошибка каждого шага;
                 ошибки есть — 422 с ошибками по полям, ничего не создано
4. сборка        contribute() каждого шага → PlaceOrder (customer, recipient, comment, blocks,
                 awaitPayment от PaymentSlot, userId = visitor?.id, locale, idempotencyKey = place_key,
                 expectedPayable = expected_payable, source = 'checkout')
5. заказ         Orders::place($input) → Order | PayableChanged | CartNotOrderable | OrderRefused;
                 в транзакции — слушатель OrderPlacing: черновик (§21.2), запись согласия (§23.4)
   сумма меньше  PayableChanged и новый payable < expected_payable → ещё один place() с
                 expectedPayable = новый payable и тем же ключом (§24.4); снова разошлось — 409
6. после коммита PaymentSlot::next() → redirect шлюза или «Спасибо»; номер — в сессию (§26)
```

- **Шаги проверяются до транзакции заказа,** а сумма — внутри неё: снятую точку и пустой телефон
  покупатель видит списком без замков корзины, а сравнение `payable` идёт по той же цепочке, по
  которой пишется снимок (§6.2), — между проверкой и записью сумма измениться не
  может.
- **`Purpose::Order` у слота доставки** считает цену без кеша (§9.2 её спеки), и
  `Orders::place()` пересчитает цепочку ещё раз; два расчёта службы на подтверждение — цена
  честности, медленный слот остаётся медленным только на нажатии кнопки.

### 24.2. Ответы

| Исход                               | Код | Что видит покупатель                                                                           |
| ----------------------------------- | --- | ---------------------------------------------------------------------------------------------- |
| заказ создан                        | 200 | `FormResponse::redirect()` — шлюз или «Спасибо»                                                |
| ошибки шагов                        | 422 | ошибки по полям; фокус — на первое поле первого шага с ошибкой, шаг раскрывается               |
| `PayableChanged`, сумма выросла     | 409 | §24.4: новая колонка итогов и «было — стало»; заказ не создан                                  |
| `PayableChanged`, сумма уменьшилась | 200 | заказ создан по новой сумме, на «Спасибо» — «Сумма уменьшилась на N» (§24.4)                   |
| `CartNotOrderable`                  | 409 | блок предупреждений корзины над шагами (§20.4) и ссылка «Открыть корзину»                      |
| `OrderRefused` (слушатель)          | 409 | `message` слушателя в общей области формы («Сертификат уже использован»); колонка перерисована |
| ключ устарел                        | 409 | «Страница устарела, проверьте заказ» и свежая колонка                                          |
| пустая корзина и ключ уже дал заказ | 200 | redirect на «Спасибо» того заказа (§24.3)                                                      |

Ответ 409 — тело `{ code, message, html }`: `code` — `checkout.payable_changed`,
`checkout.cart_not_orderable`, `checkout.refused`, `checkout.stale`; `html` — свежая колонка итогов.
Оболочка формы показывает `message` в общей области (§17.3 спеки виджетов), скрипт оформления по
`webx:form:error` с `code` подменяет колонку. Без JavaScript — redirect на `/checkout` с flash
сообщения; страница печатает свежую колонку сама.

### 24.3. Двойная отправка

Три рубежа, каждый закрывает своё:

1. **Оболочка формы** гасит повторный submit, пока идёт отправка (`is-sending`, §17.3 спеки
   виджетов) — двойной клик.
2. **Ключ повтора.** `place_key` — 32 случайных байта (hex), выдаётся с колонкой итогов; в черновике
   — sha256. В `PlaceOrder::$idempotencyKey` уходит сам ключ, заказы хранят свой хеш (§3 и §6.2): повтор того же ключа возвращает тот же заказ, ничего не делая, — второй запрос из
   другой вкладки, повтор после обрыва сети, «Назад» и повторное нажатие. Ответ на повтор — тот же
   redirect на «Спасибо» или на шлюз.
3. **Замок строки корзины** в `Orders::place()` (шаг 2 §6.2) — две вкладки с разными
   ключами не оформят одну корзину дважды: вторая увидит пустую корзину.

- **Ключ меняется**, только когда заказ создан (`OrderPlacing`, §21.2); после `PayableChanged` и
  ошибок шагов ключ тот же — заказа нет, повтор безопасен.
- **Повтор после созданного заказа**, когда ключ в черновике уже сменился: шаг 2 §24.1 видит
  несовпадение; прежде чем ответить 409, оформление спрашивает заказы по ключу
  (`Orders::findByIdempotencyKey()`, решения 41 и 68, §5.3)
  и, если заказ есть и он из этой корзины (`cart_id`), отвечает redirect на его «Спасибо».

### 24.4. Сверка суммы и повторное подтверждение

Решение 26: рост — новое подтверждение, уменьшение — заказ по новой сумме.

```
выросла:
покупатель видел 120,00 (expected_payable = 12000)
  → place: цепочка с Purpose::Order даёт 125,00
  → PayableChanged(state) → 409 checkout.payable_changed
  → колонка: «Сумма изменилась: было 120,00, стало 125,00. Проверьте заказ и подтвердите ещё раз»
            expected_payable = 12500, place_key — тот же
  → покупатель нажимает «Подтвердить» второй раз → place со 12500 → заказ

уменьшилась:
покупатель видел 120,00 (expected_payable = 12000)
  → place: цепочка даёт 115,00 → PayableChanged(state), транзакция откатилась, заказа нет
  → оформление сразу зовёт place ещё раз с expectedPayable = 11500 и тем же ключом → заказ
  → «Спасибо»: «Сумма заказа уменьшилась на 5,00» (разница — в сессии рядом с номером, §26)
```

- **Повтор при уменьшении — у оформления, `Orders::place()` не меняется:** сверка в заказах
  остаётся строгим равенством (§6.2), меньшая сумма — это второй вызов с ней. Если и
  второй расчёт разошёлся (цена сменилась ещё раз между вызовами), покупатель получает 409 с
  «было — стало» как при росте; третьего вызова нет.
- **Какие строки изменились, не показывается** (решение 69): одна фраза «было — стало», колонка
  итогов — свежая. Подсветка строк (`expected_lines`, `is-changed`) — по первому запросу
  заказчика (§18).
- `CheckoutPayableChanged` (§30) бросается в обоих случаях — воронка видит и уменьшения.
- **Валюта** не меняется посреди оформления (одна валюта сайта, решение 4 каталога); расхождение
  валюты — `CartNotOrderable` с `line.currency`.

## 25. Гость и вошедший

- **Гость** оформляет без аккаунта (решение 49): контакты, `userId = null`. Кнопка «Войти» в шаге
  контактов — `<x-webx-users::sign-in-button />`, если стоит `module-users` (`class_exists`), —
  открывает диалог входа (§12.1 спеки users). Сам диалог не открывается.
- **Вошедший** — `Visitors::current()`: имя, фамилия, телефон, e-mail подставляются в поля шага,
  пока черновик их не хранит; хранит — показывается черновик (покупатель уже правил). Над полями —
  «Вы вошли как Buyer A · Выйти».
- **Вход на странице.** Скрипт оформления слушает `webx:users:signed-in`, **отменяет** событие
  (диалог не перезагружает страницу) и перерисовывает шаг контактов и колонку итогов: при входе
  корзина слилась с корзиной аккаунта (§13.3 спеки users), цены групп могли измениться. Ключ
  повтора выдаётся новый — корзина могла смениться. Без JavaScript диалог — страница входа с
  возвратом на `/checkout`.
- **Неподтверждённый e-mail** не мешает (решение 9 спеки users): оформление не ставит
  `webx.visitor:verified` и баннер не дублирует.
- **Соцсеть** уводит к провайдеру и возвращает на `/checkout`; черновик и корзина — на сервере.
- **«Зарегистрироваться после заказа»** — на «Спасибо» гостю с `module-users` (§26). Привязка
  прежних гостевых заказов к аккаунту — вручную в панели (§13.3), автоматическая — §18.

## 28. Антиспам

Оформление — форма сайта, которая создаёт запись в базе и шлёт письма; боту интересна. Защита —
как приём inbox (§7 его спеки), с поправками на то, что страница не кешируется:

- **CSRF** — да (стек `web`): страница `no-store`, токен свежий; оболочка форм обновит его на 419.
- **Honeypot** — скрытое поле в форме подтверждения и в шаге контактов; заполнено — ответ как
  при успехе (redirect на `/checkout`, без заказа и без ошибки), строка в лог.
- **Метка времени** — `webx_ts` (`Crypt`) в форме подтверждения; страница не кешируется, поэтому
  метка честная: моложе `webx-orders.checkout.min_seconds` (по умолчанию 3) — отказ «Попробуйте ещё раз»;
  без метки или нечитаемая — отказ.
- **Лимит частоты** — `throttle:webx-orders-checkout` на `POST /checkout/place`: 10 в минуту на IP и 5
  созданных заказов в час на корзину (`webx-orders.checkout.throttle`). Шаги — 60 в минуту на IP.
- **Origin/Referer** — чужой origin отвергается (как inbox).
- **Капча** — настройка `orders.checkout.captcha` (`off` / `on`, по умолчанию `off`): `on` — капча сайта
  (§28.1) в форме подтверждения, поставщика и ключей у оформления нет. `on` при сайте без
  поставщика — экран настроек и `orders_checkout_settings_set` отказывают («Сначала выберите капчу сайта»).
- **Один клик** (§29) — без корзины и без шагов, поэтому строже: метка, honeypot, лимит 3 в час на
  IP и телефон, капча по той же настройке.

### 28.1. Капча сайта (правка `widgets`, `module-settings`, `module-inbox`)

Решение 29: один поставщик и одни ключи на весь сайт; пользуются формы inbox, оформление и вход
посетителей (`module-users`). Сейчас капча целиком в `module-inbox`: служба
`WebxUi\Inbox\Antispam\Captcha`, ключи — конфиг `webx-inbox.captcha.*` из окружения
(`WEBX_INBOX_RECAPTCHA_KEY`, `…_SECRET`, `…_TYPE`, `WEBX_INBOX_TURNSTILE_*`), поставщик — у каждой
формы (`antispam.captcha`: `off | recaptcha | turnstile`).

**Куда — в `widgets`, а не в `module-settings`.** Капча — часть оболочки форм сайта (`<x-webx-form>`
уже держит отправку, пока её скрипт не готов, `detail.wait`, §17.3 спеки виджетов), и `widgets`
требуют все три пользователя: inbox, оформление, users. `module-settings` — хранилище настроек
и экран панели; служба в нём сделала бы проверку формы сайта зависимой от раздела панели. Поэтому
— по образцу согласия на cookie (`webx-widgets.consent`): служба и конфиг — в `widgets`, вкладка
`module-settings` пишет те же ключи и сильнее конфига.

| Что                                 | Где                                                                                                                                                                                                                               |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| служба `WebxUi\Widgets\Captcha`     | `provider()`, `configured()`, `check(Request)`, печать виджета и скрипта; перенос `Inbox\Antispam\Captcha` без смены поведения (отказ при поставщике без секрета, типы ключей reCAPTCHA, `min_score`)                             |
| конфиг `webx-widgets.captcha`       | `provider` (`null` / `recaptcha` / `turnstile`); `recaptcha.key/secret/type/min_score`, `turnstile.key/secret/mode` из `WEBX_CAPTCHA_*`                                                                                           |
| вкладка «Капча» в `module-settings` | группа «Интеграции»: поставщик, тип ключа reCAPTCHA, режим Turnstile, публичный ключ; **секрет — только окружение** (как сейчас: секрет не ложится в базу и не уходит в MCP); `settings_get` показывает «секрет задан / не задан» |
| формы inbox, оформление, вход users | своё «капча вкл/выкл»; поставщик — сайта                                                                                                                                                                                          |

**Бесшовное обновление** (на продакшене есть сайт с настроенной капчей форм — после обновления
ничего не перенастраивается и капча не пропадает):

1. **Ключи — запасным путём, без переноса.** Конфиг `webx-widgets.captcha` читает
   `env('WEBX_CAPTCHA_RECAPTCHA_KEY', env('WEBX_INBOX_RECAPTCHA_KEY'))` и так каждый ключ; сайт,
   опубликовавший `config/webx-inbox.php`, тоже не теряет ключей: служба при пустом
   `webx-widgets.captcha.<поставщик>.*` берёт `webx-inbox.captcha.<поставщик>.*`. Старые имена
   работают бессрочно; `webx:doctor` советует переименовать.
2. **Поставщик — миграцией данных `module-inbox`.** Если поставщик сайта не задан, а у включённых
   форм есть `antispam.captcha` ≠ `off`, миграция пишет в настройки сайта поставщика этих форм
   (два разных у разных форм — того, у кого больше форм, и строку в лог). Форма сохраняет своё
   значение: до и после миграции `antispam.captcha` с поставщиком значит «капча вкл»; форма, чей
   поставщик не совпал с сайтом, продолжает работать со своим (запасной путь в inbox), находка
   аудита `inbox.captcha_provider_mismatch` предлагает сменить. `down()` настройку снимает.
3. **До переноса inbox читает старое.** Пока поставщик сайта не задан (миграция ещё не прошла,
   сайт без `module-settings`), inbox берёт поставщика формы и ключи `webx-inbox.captcha.*` — ровно
   как сейчас.
4. **Проверки аудита inbox** (`CaptchaKeys`, `CaptchaUnused`, `SpamWithoutCaptcha`) зовут службу
   `widgets`; тексты и имена переменных окружения в находках — новые, со старыми в скобках.

Проверка пункта плана (этап 10): фикстура сайта «до обновления» — окружение `WEBX_INBOX_TURNSTILE_*`,
форма с `antispam.captcha = turnstile`, без настроек сайта; после `migrate` форма печатает тот же
виджет, отказывает без токена и принимает с верным (подставной ответ проверки), настройки сайта
показывают Turnstile, в `.env` ничего не менялось; `migrate:rollback` возвращает как было.

## 29. «Купить в один клик»

Частый запрос магазинов (решение 54), в v1 — отдельным этапом после основного оформления (решение
62, этап 19 §17): кнопка на карточке товара, диалог «Оставьте телефон — мы перезвоним», заказ без
корзины и без шагов.

- **Это заказ, а не заявка Inbox.** Менеджер работает с ним в разделе заказов, по статусам, со
  снимком цены; заявка в Inbox потеряла бы цену и товар как строку. `source = 'quick'` —
  фильтр в списке заказов и отметка в карточке.
- **Поток:** `<x-webx-orders::checkout.quick-button type="catalog.product" :ref="$product->id" />` у
  кнопки «Купить» → диалог (`<x-webx-dialog>` с `<x-webx-form>`): телефон обязательный, имя
  необязательное, согласие по `orders.checkout.terms` → `POST /checkout/quick` `{type, ref, qty, options?,
phone, name?}`.
- **Корзина покупателя не трогается:** ни её строки, ни cookie, ни черновик оформления (§29.1).
- **Контакт без имени:** `PlaceOrder` требует имя (§6.1), заказы это не меняют. Без
  имени в `customer_first_name` идёт слово «Покупатель» на языке заказа (`webx-orders::checkout.quick.anonymous`),
  фамилия — `null`; телефон обязателен, e-mail не спрашивается.
- **Доставка и оплата** — не выбираются: менеджер уточняет по телефону и дописывает блоки через
  `patchBlock()` (§6.4).
- **Ответ** — сообщение на месте («Спасибо! Перезвоним в течение 15 минут» — текст настройки
  `orders.checkout.quick.message`), без «Спасибо»-страницы.
- **Включение** — `orders.checkout.quick.enabled` (выключено по умолчанию); кнопка не печатается, пока
  выключено. Для какого поставщика кнопка — любой `Purchasable`; первым — `catalog.product` в виде
  каталога (правка вида — в задаче каталога).
- **Ключ повтора — из запроса, а не со страницы:** карточка товара может кешироваться целиком, и
  ключ в ней сделал бы заказ каждого покупателя заказом первого. Ключ — хеш IP, телефона, строки и
  окна в 10 минут: тот же диалог дважды за 10 минут — один заказ.
- **Без CSRF**, как приём inbox: маршрут вне `PreventRequestForgery` (токен с закешированной
  страницы чужой), защищают метка, honeypot, origin и лимиты §28. В диалоге нет ничего личного.
- **Откуда заказ** — источник вехи `placed` (`order_milestones.source`, уникальный ключ
  `(order_id, milestone)`): колонки в `orders` нет, фильтр списка и `orders_list` — `source`.

### 29.1. Временная корзина — служебная запись `carts`

Выбор спеки (ответ 1 человека оставил его спеке): **служебная запись `carts` без cookie**, а не
корзина в памяти.

```
POST /checkout/quick → DB::transaction:
  1. корзина      запись carts с токеном, который не уходит в cookie (случайный, его хеш никому
                  не выдан), locale и currency сайта
  2. строка       добавление через тот же путь, что «В корзину»: Purchasables, проверка опций и
                  количества, лимиты строки (§5 спеки корзины)
  3. заказ        Orders::place(cart, customer, source: 'quick', expectedPayable: null,
                  blocks: [], idempotencyKey: ключ повтора из запроса)
  4. уборка       служебная корзина удаляется (orders.cart_id — без FK, §3)
отказ на любом шаге — откат всего: ни корзины, ни заказа
```

- **Почему не в памяти:** `Orders::place()` запирает строку корзины (`FOR UPDATE`), пересчитывает
  цепочку по её строкам с `Purpose::Order` и привязывает корректировки к `cart_items.id` (§6.2). Корзина в памяти потребовала бы второй вход в `place()` и второй путь снимка —
  два места, где расходятся скидки и подарки. Запись даёт один путь без правки `Orders::place()`:
  правила корзины, подарки и привилегии работают в один клик так же, как в оформлении.
- **Почему не корзина покупателя:** решение 62 — её не трогаем; у покупателя в корзине могут быть
  другие товары, а один клик — заказ ровно одной строки.
- **`expectedPayable = null`:** цену покупатель видел на карточке, сверять не с чем; сумма заказа —
  та, что посчитала цепочка, и она же в ответе диалога («Заказ 1024 на 120,00»).
- **Что меняется рядом:** `Orders::place()` — ничего (`PlaceOrder::$source` уже строка, `quick` —
  новое значение); в разделе заказов — отметка «В один клик» в списке и карточке и фильтр по
  `source` (этап 19). `module-cart` — ничего: `CartService::add(null, $items, $locale)` в 0.89.0
  уже создаёт корзину и отдаёт её токен в `AddResult`, а cookie ставит только контроллер корзины —
  служебная корзина его просто не получает; уборка — `CartService::clear()`. Утечка служебных
  корзин невозможна (транзакция), а если появится — их уберёт `webx:cart:prune`.

### 29.2. Заказ из панели

Решение 85: менеджер принимает заказ по телефону и оформляет его сам. Второй логики заказа нет —
это тот же путь, что у «одного клика» (§29.1), только строк несколько и контакты вводит менеджер.

```
Orders::placeByManager(ManagerOrder, source = panel) → DB::transaction:
  0. проверка   контакты и комментарий — как в place() (§6.1), до корзины: неверный телефон
                не создаёт даже откатываемой записи
  1. корзина    CartService::add(null, lines, locale) — служебная запись carts без cookie;
                строки — как «В корзину»: Purchasables, опции, количество, лимиты
  2. заказ      Orders::place(cart, customer, recipient, comment, source, idempotencyKey)
  3. уборка     CartService::clear()
отказ на любом шаге — откат всего: ни корзины, ни заказа
```

- **`ManagerOrder`:** `lines` (`{type, ref, qty?, options?}` — как `CartService::add()`), `locale`
  (язык заказа: названия и письма), `customer`, `recipient?`, `comment?`, `idempotencyKey?`
  (токен формы: второе нажатие — тот же заказ). Цены нет: заказ считает цепочка корзины.
- **Источник и автор.** Панель зовёт с `source = panel`, MCP — с `source = mcp` (как все
  инструменты, §12). Для обоих `place()` пишет `admin_id` вошедшего администратора в веху `placed`
  и первую строку истории. Отметка «Создан в панели» в списке и карточке, `panel` в фильтре списка.
- **Отказы** — те же, что у `place()`: `ValidationException` по полям (`items` — пустой состав,
  `items.N.ref` — нет товара или он не продаётся, `customer.*` — контакты), `CartNotOrderable`,
  `OrderRefused` слушателя `OrderPlacing`.
- **Предпросмотр** `previewByManager()` → `ManagerPreview` (`state` — `CartState` с
  `Purpose::Order`, `refusal` — `CartNotOrderable` или `null`): те же проверки, корзина создаётся,
  считается для заказа и откатывается. Это `dry_run` у `orders_create`; ответ — `orderable`,
  `refusal`, `message` и `totals` (строки, суммы, предупреждения корзины).
- **Право** `orders.manage` проверяет вызывающий (маршрут — `cms.can`, инструмент —
  `permission:`), как у всех методов `Orders`.
- **Доставка и оплата** не выбираются, ручной цены и скидки нет (§18): блоки дописывают модули
  через `patchBlock()` (§6.4), как у «одного клика».
- **Экран «Новый заказ»** (`/orders/new`, кнопка в списке при `orders.manage`;
  `Http\Controllers\Panel\NewOrderController` только оборачивает `Orders`):
  - **поиск** — `GET new/products?search=`: `Purchasables::find()` модуля корзины спрашивает
    поставщиков с `FindsPurchasables` (§5.1 спеки корзины), заказ не знает каталога; у товара с
    вариантом — `options` с выбором, строка без выбора не считается и не оформляется;
  - **живые итоги** — `POST new/preview`: `previewByManager(input, contacts: false)` — только
    строки, контакты ещё вводятся; ответ — `orderable`, `message`, `totals` (`CartState`, с
    предупреждениями); отказ строки — 422 `items.N.*` под этой строкой;
  - **заказ** — `POST new`: `placeByManager(source: panel)`, ключ повтора — токен формы; ответ —
    `id` и номер, экран открывает карточку; язык заказа — язык сайта, выбор при нескольких.

## 30. События

Оформление своих событий заказа не бросает — это часть I (§7). Свои:

| Событие (PHP)                              | Когда                              | Кому                                        |
| ------------------------------------------ | ---------------------------------- | ------------------------------------------- |
| `CheckoutStepSaved(cartId, step)`          | шаг сохранён                       | воронка, будущий спутник брошенных          |
| `CheckoutPayableChanged(cartId, from, to)` | сверка разошлась                   | лог, MCP-воронка                            |
| `CheckoutPlaced(orderId, cartId)`          | после коммита заказа из оформления | аналитика; заказное — слушать `OrderPlaced` |

На странице — `webx:checkout:slot-changed` (§22.1), `webx:checkout:placed` (`detail`: номер, сумма,
валюта — для счётчиков с согласием).

Классы — `WebxUi\Orders\Checkout\Events\…`. `CheckoutPayableChanged` бросается на каждое
расхождение: нажатие, которое разошлось дважды (§24.4), — два события; черновик считает их в
`order_checkout_drafts.payable_changes` для воронки (§32). Заказ из подтверждения ставит
черновику `last_step = confirm` — так воронка видит, кто дошёл до заказа.

## 32. MCP

Инструменты оформления — в модуле `orders` с префиксом `orders_checkout_`, области — те же
`orders:read` (→ `orders.view`) и `orders:write`; изменение настроек — `permission:
'orders.checkout.settings'`. Изменяющий инструмент — с `dry_run`. Деньги — целым и `*_formatted`.
При выключенном оформлении (§19) инструментов и ресурса нет.

| Инструмент                     | Что делает                                                                                                                                                            |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `orders_checkout_steps`        | какие шаги и слоты зарегистрированы, их позиции, кто владелец; какие покажутся для корзины `cart_id` (если передан) и почему нет («нет shippable-строк»)              |
| `orders_checkout_preview`      | пробное подтверждение корзины `cart_id`: итоги с `Purpose::Checkout`, `check(Checkout)` каждого шага, что помешает заказу (ошибки шагов, строки корзины) — без записи |
| `orders_checkout_funnel`       | черновики за 1/7/30 дней по `last_step`, сколько дошли до заказа, сколько расхождений суммы (`CheckoutPayableChanged`) — «где бросают»                                |
| `orders_checkout_drafts_list`  | черновики страницами: корзина, шаг, сумма, когда; контакты — маской (`B*** A`, `+800 *** **78`, `b***@example.com`)                                                   |
| `orders_checkout_settings_get` | настройки §31.2                                                                                                                                                       |
| `orders_checkout_settings_set` | изменить настройки; `dry_run` — что изменится на странице («шаг комментария исчезнет», «оба контакта необязательные — отказ»)                                         |

- **Ресурс `orders://checkout`:** шаги и слоты, куски колонки итогов (`CheckoutSummaryParts`),
  настройки и их значения, коды ошибок (`StepError::code`) и ответов 409 — из реестров, не рукой.
- Полных контактов черновика MCP не отдаёт: это не покупатели, а люди, которые не оформили заказ;
  контакты оформленного — `orders_get`.
- `orders_checkout_preview` и `orders_checkout_funnel` — в `PerformanceTest` тёплыми.
- **Пробное подтверждение задаёт вопросы `place` в его порядке** (`CheckoutPreview`): шаги с
  `check(Purpose::Order)` — как проверяет само подтверждение, ошибки по полям, как в его 422;
  затем расчёт `Purpose::Order` и `Orders::orderable()` — 409 `cart_not_orderable`; затем сумма
  против той, что страница последней показала покупателю (`shown_payable` черновика; без черновика —
  сумма страницы сейчас): больше — 409 `payable_changed`, меньше — заказ с ней и `decrease`.
  Антиспам, ключ повтора и флажок согласия — свойства запроса покупателя, их пробный вызов не
  проверяет (флажок — `terms_checkbox: true` в ответе). Коды ответов — `CheckoutAnswers`, коды
  ошибок шагов — `NamesErrors::errorCodes()` шага или слота (необязательный интерфейс).

## 34. Производительность, регистрации, тесты оформления

- **Один расчёт цепочки на запрос** (`CheckoutContext::$state`); шаги и колонка берут его, а не
  считают снова. `GET /checkout` — бюджет запросов в `PerformanceTest` с подставными слотами и
  корзиной из 10 строк (комплект с детьми, подарок); `assertNoRepeatedQueries`.
- **Кеша страниц нет** (`no-store`): страница личная. Настройки оформления — в
  `CacheGroups::remember` группы `orders.checkout`, сброс — `bumpOn` модели настроек.
- **Подтверждение** — бюджет на `place` (проверки шагов + `Orders::place()`), расчёт службы на
  `Purpose::Order` — один на нажатие.
- **Индексы:** `order_checkout_drafts (updated_at)` — чистка и воронка; `last_step` в воронке —
  `GROUP BY` по выборке за период (`EXPLAIN` на MariaDB в этапе 12).
- **Регистрации:** отдельного пакета нет — четыре места в `php/` и четыре места раздела у
  `module-orders` уже есть (этап 2); `SiteBar` — у оформления нет `RouteType`; раздел «Оформление» в
  `AGENTS.md` пакета (лимит 150 строк — на весь `module-orders`, подробности — в гайде); демо — заказы
  из демо `module-orders` (§15), своих данных у оформления нет.
- **Тесты, которые держат контракты:** `SlotContractTest` (абстрактный, его наследуют доставка и
  оплата), `StepOrderTest` (без слотов — контакты, комментарий, подтверждение; с подставными — по
  позициям; без shippable — без доставки), `PlaceIdempotencyTest` (двойной `POST`, две вкладки,
  повтор после смены ключа), `PayableChangedTest` (рост — 409 и повторное подтверждение;
  падение — заказ по новой сумме и строка на «Спасибо»; два расхождения подряд — 409),
  `CheckoutWithoutNeighboursTest` (только cart, widgets и compositions), `CheckoutDisabledTest`
  (выключено — нет маршрутов, слотов и инструментов; `Orders::place()` из кода работает).
