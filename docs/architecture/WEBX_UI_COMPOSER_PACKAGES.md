# WebX UI — реестр composer-пакетов

Живой список: что нужно сделать на стороне Laravel. Дополняется по мере появления идей. Для каждого пакета — назначение, состав, npm-пара, статус.

Статусы: `идея` → `спроектирован` → `в работе` → `опубликован`.

Namespace: `webx-ui/*`, размещение: `php/packages/*` в монорепо, публикация через split-репозитории — как это устроено и что нажимать на packagist.org, см. [`WEBX_UI_PHP_RELEASE.md`](WEBX_UI_PHP_RELEASE.md).

Версия у всех php-пакетов общая, как у `illuminate/*`: один тег — один релиз.

## Правило: MCP-инструменты у каждого модуля

Каждый модуль обязан реализовать `ProvidesMcpTools`. Минимум — CRUD-инструменты по его сущностям (list, get, create, update, delete, publish/unpublish где применимо). Но CRUD — не цель: при проектировании модуля отдельно анализировать, какие задачи ИИ реально будет решать с этим модулем, и предлагать набор специализированных tools, resources и prompts. Список инструментов — часть спецификации модуля, ревьюится вместе с API.

Ориентиры для поиска полезных инструментов:

- массовые операции («у всех товаров категории X …»)
- аудит и поиск проблем (незаполненное, дубли, битые ссылки)
- генерация черновиков (описания, ответы, alt-тексты) с последующим подтверждением
- аналитика и сводки (что изменилось за неделю, что ждёт модерации)
- сквозные сценарии между модулями (создать страницу + SEO + медиа за один вызов)

Все изменяющие инструменты поддерживают `dry_run` и попадают в лог с возможностью отката.

## Правило: локализация у каждого модуля

Ни одной строки интерфейса в коде. Всё, что видит человек, живёт в `lang/` пакета и приходит
через `__('webx-<модуль>::<группа>.<ключ>')`.

- Пакет грузит переводы сам: `loadTranslationsFrom(__DIR__.'/../lang', 'webx-<модуль>')` и
  публикует их через `publishes`. **Namespace обязан начинаться с `webx-`** — `DictionaryBuilder`
  собирает словарь панели ровно по префиксам из `config('webx-localization.namespaces')`, и
  пакет с другим именем в словарь не попадёт, молча и без ошибки.
- **В поставке десять языков:** `en` (он же fallback), `ru`, `uk`, `de`, `pl`, `fr`, `es`, `it`,
  `pt`, `tr`. Fallback подкладывается **под** локаль построчно, поэтому наполовину переведённая
  группа показывает переведённое и английское, а не пустой экран. Какие из них предлагать
  администратору, решает сайт в `config('webx-localization.panel')` — пакет только везёт.
- Коды без региона. `LocaleCatalogue::normalise` приводит `pt-br` к `pt-BR`, а `ru_RU` к `ru`;
  пока регион не нужен, каталоги называются одной буквенной парой. `pt` — европейский
  португальский; `pt-BR` заводится отдельно, когда появится проект, которому он нужен.
- RTL (`ar`, `he`) в набор не входит намеренно: это не строки, а `dir="rtl"` и пересмотр всей
  вёрстки — своя задача, не часть перевода.
- Носителем вычитаны `en`, `ru` и `uk`. Остальные семь — машинный перевод, и README пакета
  говорит об этом прямо: репозиторий открытый, правка от носителя ценнее умолчания.
- Группы по смыслу: `module.php` (название раздела и пункты меню), `errors.php` (сообщения
  ошибок API), `validation.php` (атрибуты и переопределения), дальше — сколько нужно.
- npm-пара держит те же ключи по-английски в `messages.ts` и объявляет их
  `admin.i18n.defaults('webx-<модуль>', messages)`. Это пол: панель, собранная без сервера, всё
  равно со словами, и ключ никогда не попадает на экран вместо фразы.
- Ошибки сервера (422 в том числе) переводятся **на сервере**, по `X-Webx-Locale` из запроса.
  Фронт их только показывает.
- Тест в каждом модуле: наборы ключей `en`, `ru` и `uk` совпадают — ни пропусков, ни лишнего.
- После правки `lang/` — `php artisan webx:locales:clear`: словарь кешируется, и без этого
  правка не видна.

Переводимые поля самих сущностей — другая история, это `HasTranslations` из
`webx-ui/localization`.

## Правило: имя пакета

Всё, из чего состоит панель, — пакет с префиксом `module-`: каркас `webx-ui/module-admin` и
разделы `webx-ui/module-auth`, `webx-ui/module-media`; npm-пара называется так же
(`@webx-ui/module-admin`, `@webx-ui/module-auth`). Библиотека, которая живёт и без панели, — без
префикса: `nested-set`, `localization`, `mcp`. Это и есть разделение: по имени видно, панель это
или библиотека. До 0.12.0 каркас назывался `webx-ui/admin` (`@webx-ui/admin`); старые имена
помечены как замещённые новым и больше не публикуются.

Идентификатор модуля (`Module::id()`, он же префикс прав `<id>.<action>`, областей MCP
`<id>:<scope>` и имён инструментов `<id>_<tool>`) называет то, что модуль показывает, а не
таблицу под ним: администраторы — `admins`. `users` зарезервировано за пользователями сайта —
отдельным модулем, когда сайту понадобятся регистрация и вход.

## Ядро

### `webx-ui/module-admin` — каркас

Статус: в работе — контракты и точки входа готовы

- `ModuleInterface`, сборка манифеста `GET /api/cms/manifest`
- catch-all `/cms/{any}` → Blade-заглушка SPA
- единый формат ответов: пагинация (LengthAwarePaginator как есть), ошибки 422, ресурсы
- middleware `cms.auth`, базовые политики
- artisan-команды: `webx:install`, `webx:make-module`

Сделано: `Contracts\Module` + `AbstractModule`, `ModuleRegistry` (дубли id запрещены), `GET /api/cms/manifest`, catch-all `/cms/{any}` на Blade-заглушку, `ApiResponse` для простых полезных нагрузок, обе artisan-команды. Не сделано: `cms.auth` и политики — это `module-auth`; пока панель открыта, и `webx:install` об этом предупреждает.

npm-пара: `@webx-ui/module-admin`

#### Пароль на сайт на время тестирования

Сделано 24.09.2026 (план — 18.09.2026). Сайт, выложенный на публичный домен до открытия,
закрывается HTTP Basic — **весь, кроме панели, её JSON, MCP и предпросмотра**. Любой сайт на этих
пакетах рано или поздно живёт месяц на реальном домене, пока его смотрят заказчик и разработчик, и
никто больше.

- **Место — `module-admin`, а не `module-auth`.** Авторизация отвечает на вопрос «кто этот
  администратор» и живёт в сессии; здесь надо ответить раньше маршрутизации, без сессии и без
  единого запроса в базу.
- **Глобальный middleware `Gate\CloseSite`, `Kernel::pushMiddleware` в `$this->app->booted()`** —
  как `RedirectRequests` у `module-seo`, и по той же причине: адрес без маршрута до группы `web`
  не доходит, а калитка, которая пропускает все 404, — не калитка. Добавляется всегда и сам читает
  выключатель на каждом запросе, поэтому включить её — строка в `.env` и `config:cache`, а не
  деплой. `module-admin` загружается раньше `module-seo`, так что калитка стоит перед редиректами
  и не выдаёт чужому, какие адреса переехали.
- **Кого пускают без пароля — реестр `Gate\Openings`,** а не список в одном месте: каждый пакет
  знает, где он отвечает и что делает запрос к нему законным.
  - `module-admin`: `webx-admin.path` и `webx-admin.api_path` (MCP при `webx-mcp.path = null`
    лежит под вторым), `/.well-known/*` (ACME и discovery OAuth) и маски сайта в
    `webx-admin.gate.except` (`Str::is` по пути без ведущего слэша).
  - `mcp`: `webx-mcp.path`, когда сервер вынесен отдельно, и префикс OAuth
    (`webx-mcp.oauth.prefix`, по умолчанию `oauth`) — `/oauth/authorize`, `/oauth/token`,
    `/oauth/register`, `/oauth/device`. Агент не умеет отвечать на Basic, и закрытый танец
    выглядел бы в клиенте ошибкой, в которой нет ни сайта, ни калитки.
  - `module-blocks`: `/_preview/{type}/{id}` **только с валидным токеном** (подпись и есть
    пропуск; чужая догадка остаётся за паролем), `/_preview/block-stage` (его стережёт сессия
    панели) и бандлы `/blocks/*` — `runtime.js` грузит сам фрейм предпросмотра, и без него блоки
    там мёртвые.
- **Приём заявок `module-inbox` исключением не становится.** Форма стоит на закрытой странице, и
  посетителей у неё в это время нет.
- **Пары логин-пароль — только из окружения**, без экрана настроек (решение 18.09.2026):
  `WEBX_SITE_GATE=true`, `WEBX_SITE_GATE_USERS="client:secret,tester:other"`. Имя кончается на
  первом двоеточии, пары разделены запятой. Сравнение `hash_equals` по всем парам сразу.
  Включено, но пар нет — закрыто для всех (fail closed). Выключатель, который закрывает сайт,
  живёт рядом с `APP_DEBUG`, а не в базе, которую правит тот же человек, что может себя запереть.
- **Пароль хранится как написан, без хеша** (решение 24.09.2026). Хеш спасает только при утечке
  `.env`, а там уже `APP_KEY` и пароль базы; пароль общий, тестовый, его диктуют заказчику; а
  браузер шлёт пару на каждый запрос — bcrypt на каждый запрос стоит десятки миллисекунд.
- **Ответ:** 401 с `WWW-Authenticate: Basic realm="<APP_NAME>", charset="UTF-8"`,
  `X-Robots-Tag: noindex, nofollow`, `Cache-Control: no-store` и `Vary: Authorization`. Страница за
  паролем получает `Vary: Authorization` и `noindex` тоже — иначе общий кеш отдаст её следующему
  посетителю. Тело — вьюха `webx-admin::gate`, слова `webx-admin::gate.*` на десяти языках.
- **Ссылки-пропуска не будет** (решение 18.09.2026). `?webx-gate=<секрет>` с подписанной кукой
  избавил бы от диктовки пары, но пропуск в адресной строке попадает в историю, в мессенджер и в
  реферер, и закрытый сайт перестаёт быть закрытым тише, чем кто-либо это заметит.
- **Статика мимо PHP остаётся открытой.** `/storage/**` и `/build/**` отдаёт веб-сервер, и
  middleware их не видит: прямая ссылка на загруженный файл работает и при закрытом сайте. Кому
  этого мало — правило на прокси, но тогда проходы для панели, API и предпросмотра придётся
  повторить там же.
- **`webx:doctor`** (`Doctor\Checks\SiteGate`): включено без пар — ошибка; включено с парами —
  строка `ok` с числом пар и напоминанием выключить (не предупреждение: `--strict` роняет деплой
  на предупреждениях, а тестовый сайт деплоят закрытым нарочно). Опубликованный конфиг без блока
  `gate` при `WEBX_SITE_GATE=true` в окружении — ошибка: сайт считают закрытым, а он открыт
  (`mergeConfigFrom` сливает один уровень). Без переменной — молчание, иначе каждый старый сайт
  получил бы предупреждение на каждом деплое.
- **Проверка:** `GateTest` в `module-admin`, проход MCP и OAuth в `OAuthDoorTest`, предпросмотр в
  `PreviewTest` у `module-blocks`, и фаза `closed` в `scripts/php-smoke.sh` — `.env` плюс
  `config:cache` на настоящем приложении, ровно то, чего Testbench не видит.

MCP-инструмента у калитки нет: это настройка окружения, а не данные сайта.

### `webx-ui/mcp` — MCP-сервер

Статус: в работе — контракт и реестр готовы, транспорт отложен

Позволяет ИИ-агентам (Claude и др.) подключаться к сайту и читать/корректировать данные через Model Context Protocol. Аналог манифеста для админки, но для ИИ.

- MCP-сервер как часть Laravel-приложения: endpoint `/mcp` (Streamable HTTP), базируется на официальном `laravel/mcp` — проверить текущее состояние пакета перед реализацией
- контракт `ProvidesMcpTools` для модуля: модуль объявляет tools, resources и prompts; ядро собирает их в один сервер
- авторизация: токены с областями (`seo:write`, `pages:read`), привязка к администратору, лог всех вызовов с возможностью отката
- режим подтверждения: изменяющие операции могут требовать одобрения в админке (очередь предложенных изменений)
- rate limiting, sandbox для dry-run

Примеры инструментов по модулям:

- `seo`: получить/обновить SEO сущности, создать правило для URL, добавить редирект, прогнать аудит
- `pages`/`news`: список, чтение, правка текста и блоков, публикация
- `products`: цены, остатки, описания, характеристики
- `media`: список файлов, alt-тексты
- `inbox`: чтение обращений, смена статуса, черновик ответа

Сделано: контракт `ProvidesMcpTools` (tools, resources, prompts) + трейт с пустыми ответами, `Tool::read()` / `Tool::mutating()` — у изменяющего инструмента `dry_run` добавляется принудительно, а область по умолчанию `<модуль>:write`, — `ToolRegistry` поверх реестра модулей, команда `webx:mcp-tools`.

Не сделано намеренно: транспорт. `laravel/mcp` на 0.9.5 (есть `v1.0.0-beta.1`), и завязываться на его API до 1.0 рано — контракты модулей от этого не зависят и менять их не придётся. Туда же авторизация по областям, журнал вызовов и очередь подтверждений.

npm-пара: раздел в `@webx-ui/module-admin`: токены и области, журнал вызовов, очередь подтверждений.

## Модули

### `webx-ui/module-auth` — авторизация

Статус: в работе — вход, роли и защита панели готовы

- Sanctum, login/logout/me, refresh
- сущность администратора отдельно от пользователей сайта (своя таблица `cms_users` или guard)
- роли и права (свои или `spatie/laravel-permission` как зависимость — решить)
- восстановление пароля, 2FA (TOTP) — второй очередью
- события `AdminLoggedIn`, `AdminLoggedOut`, лог входов

Решено и сделано: своя таблица `cms_users` и guard `cms` (администратор — не пользователь сайта); роли свои, без `spatie/laravel-permission` — права объявляют модули в манифесте, и таблица permissions была бы второй, расходящейся копией этого списка; Sanctum в cookie-режиме, панель ходит через группу `web`. Установка пакета сама закрывает API панели, а не ждёт, пока про это вспомнят. Лог попыток входа с поиском всплесков неудач.

Не сделано: восстановление пароля, 2FA, приглашения. Токены с областями для MCP — когда дойдёт очередь до транспорта MCP; `HasApiTokens` на модели уже есть.

npm-пара: `@webx-ui/module-auth` — страница логина, стор, guard, interceptor токена

MCP: список администраторов и ролей, выдача/отзыв прав, история входов, поиск подозрительной активности, создание приглашения. Без инструментов смены пароля и выдачи токенов через ИИ.

### `webx-ui/nested-set` — дерево

Статус: в работе — первый пакет, на нём обкатан конвейер публикации

Не модуль, а библиотека-зависимость для других модулей (категории, страницы, папки файлового менеджера, меню).

- trait `HasNestedSet` для Eloquent: `lft`, `rgt`, `parent_id`, `depth`
- операции: `appendTo`, `prependTo`, `insertBefore/After`, `moveTo`, `up/down`
- запросы: `ancestors`, `descendants`, `siblings`, `root`, `isChildOf`
- сборка дерева из плоского списка, `toTree()`, `toFlatTree()`
- перестройка индексов `fixTree()`, проверка целостности
- scope для нескольких деревьев в одной таблице (`scope_id`)
- JSON-ресурс для фронта: узел + `children`

Решено: собственная реализация. `kalnoy/nestedset` — только как ориентир по API и набору операций, код не используем и не оборачиваем.

Сделано: trait `HasNestedSet` (чтение, размещение, перемещение поддерева, `up`/`down`), `toTree`, `fixTree`, `checkTreeIntegrity`, несколько деревьев в одной таблице через `getNestedSetScopeAttributes()`, Blueprint-макрос `nestedSet()`. Не сделано: soft deletes (осознанно бросает исключение), права на узлы; отдельный JSON-ресурс не нужен — форму даёт `toTree()`.

npm-пара: нет напрямую; компоненты дерева в `@webx-ui/core` (wx-tree) и drag-and-drop сортировка принимают его JSON-формат.

MCP: не свои инструменты, а хелперы для модулей-потребителей: `move_node`, `get_tree`, `get_path`, `check_integrity` — чтобы pages/media/categories не реализовывали работу с деревом каждый по-своему.

### `webx-ui/localization` — языки

Статус: сделано (ядро); реализуется **до** `webx-ui/module-seo` — `seo_meta` тоже переводимая

Не модуль, а библиотека. Разводит две задачи, которые в прошлом проекте слиплись в одну кучу:
фразы интерфейса (пишет разработчик, конечный список ключей, живут в пакете) и контент (пишет
редактор, живёт в БД). Смешивать их — и есть тот бардак, из-за которого переводы оказались
отдельно у сайта и отдельно у админки.

- таблица `locales` (code BCP-47, name, native_name, direction, is_default, is_active, sort);
  конфиг — только сид для свежей установки и ответ, пока таблицы ещё нет (первый `migrate`)
- `Locales` — сервис: `codes()`, `default()`, `current()`, `use()`, `chain()`, `panel()`,
  `resolvePanel()`; кеш с инвалидацией через `webx:locales:clear`
- `LocaleCatalogue` — справочник ~38 языков (имя, самоназвание, направление). Справочник, а не
  ограничение: языка вне списка он не запрещает
- `HasTranslations` — переводимые атрибуты в JSON-колонке, формат как у
  `spatie/laravel-translatable`; `forLocale()`, `getTranslations()`, `whereTranslation()`,
  `orderByTranslation()`; Blueprint-макрос `translatable()`
- middleware `webx.locale` (публичная часть: префикс пути или Accept-Language) и
  `webx.panel-locale` (панель: язык подписанного администратора → `X-Webx-Locale` → браузер)
- `DictionaryBuilder` — словарь интерфейса для SPA: собирает `lang/` всех установленных
  пакетов с префиксом `webx-`, мержит построчно поверх fallback, учитывает
  `lang/vendor/<namespace>/` приложения

Решения, которые уже приняты и их стоит помнить:

- **Язык панели — свойство человека, а не сайта** (колонка `locale` в `cms_users`,
  контракт `HasPanelLocale`). Сайт на украинском может вести администратор с английским
  интерфейсом. `webx-localization.panel` перечисляет языки, на которые интерфейс реально
  переведён, — это другой список, чем языки публикации.
- **Один файл фраз на модуль, обе половины читают его же.** Vue-пакет держит английские
  дефолты в коде (чтобы работать без сервера), словарь с сервера их перекрывает. Второй
  словарь внутри npm-пакета — та самая ошибка прошлого проекта.
- **Мерж построчно, а не по группам:** один новый ключ в релизе не должен обнулять экран,
  переведённый год назад.
- **JSON-колонка не даёт уникальности slug внутри языка** (выбор осознанный). Уникальность
  адреса уходит в таблицу `routes` в `webx-ui/routing` — там она держится сразу по всем
  сущностям, а не по одной таблице. До этого валидация опирается на `whereTranslation()`.
- Множественное число пока не решено: у славянских языков три формы, и сервер с браузером
  должны считать одинаково. Кандидат — явные ключи `one/few/many/other` и таблица правил на
  локаль вместо пайпов Laravel.

API панели (в `webx-ui/module-admin`, потому что API панели — его зона): `GET {api}/locales` и
`GET {api}/translations/{code}` — публичные, экран входа рисуется до сессии;
`PUT {api}/auth/locale` — выбор администратора (в `module-auth`). Манифест несёт `locale`,
`locales` и `panelLocales`.

npm-пара: отдельного пакета нет — i18n живёт в `@webx-ui/module-admin` (`createAdmin({ locale })`,
`useI18n()`, скоупнутый `t()`), словарь тянется с сервера.

MCP: пока нет. Кандидаты на потом — `list_locales`, `find_missing_translations`,
`translate_entity` (черновик перевода сущности, с подтверждением).

### `webx-ui/routing` — реестр адресов сайта

Статус: **v0.1 сделана** (15.09.2026). Спецификация и решения —
[`WEBX_UI_ROUTING.md`](WEBX_UI_ROUTING.md), гайд — `apps/docs/guide/routing.md`.

Библиотека, не раздел: своего экрана у реестра нет, а публичная часть сайта пользуется им сама по
себе — тот же случай, что `nested-set` и `localization`. npm-пары нет.

Пишется до `module-pages`, потому что адресное пространство **плоское**: страница, рубрика,
категория и товар лежат в одном корне и конфликтуют между собой. Внутри модуля страниц это не
решается — модуль не видит чужих адресов.

- `routes` — одна строка на адрес: `locale`, `path` (без языковой приставки, нижний регистр),
  `kind` (`canonical` | `alias`), `entity_type`/`entity_id`; уникальность `(locale, path)`.
- `HasUrl` + `RouteTypes::register(new RouteType(...))` — вся интеграция модуля. Сохранение,
  переименование, перенос ветки, удаление и восстановление реестр держит сам.
- Форматтеры (`Slug`, `TreePath`, `SlugId`, `SlugSku`, `Prefixed`) — чистые функции от сущности;
  проект подменяет чужой форматтер конфигом, `webx:routes:rebuild --type=` переселяет адреса.
- Столкновения: `OnConflict::Fail` (валидация под полем) или `Suffix` (`base-2`, с возвратом
  суффикса в slug сущности).
- Разбор: `Route::fallback()`, одно написание адреса (301), точное бьёт префиксное, хвост
  принимает тип, публикацию решает обработчик; найденное едет дальше в `Resolution::of($request)`.
- Забронированные адреса проверяются **при сохранении**: сначала роутер проекта, потом список в
  конфиге и префикс панели.
- Команды `webx:routes:rebuild` и `webx:routes:check`; MCP — `resolve_url`, `where_is`,
  `find_conflicts`.

Стык с SEO: `UrlNormaliser` переехал сюда из `module-seo` (одно написание адреса на обе
половины), алиасы отдаются панели узким контрактом `RouteAliases` и показываются вкладкой
«Автоматические» рядом с ручными правилами, а `Resolution` даёт `<head>` сущность без `:for`.

### `webx-ui/module-seo` — SEO: раздел панели и рендер `<head>`

Статус: **v0.1 сделана** (php и npm, 14.09.2026). Спецификация и решения —
[`WEBX_UI_MODULE_SEO.md`](WEBX_UI_MODULE_SEO.md), гайд — `apps/docs/guide/seo.md`.

**Это один пакет, а не два.** В прежней редакции реестра SEO был записан библиотекой
`webx-ui/seo` и разделом `webx-ui/module-seo`. Решено слить. По нашему правилу именования
(CLAUDE.md §1) голое имя носит библиотека, которая живёт **без** панели: `nested-set` — чистый
алгоритм, `localization` публичная часть использует сама по себе. А SEO-рендеру без SEO-раздела
рисовать нечего — ни правил, ни дефолтов, ни Organization: всё это авторится в панели. По
собственному критерию библиотекой он не является.

Шов при этом намечен внутри и его надо держать: рендер и резолвер — в `WebxUi\Seo\Rendering\`,
раздел — в `WebxUi\Seo\Panel\`, источники регистрируются через контракт `SeoSource`, а не
зашиваются. Если контентным модулям когда-нибудь понадобится рендер без раздела, разрез по
готовому шву механический.

Что в v0.1:

- `seo_urls` — правила для произвольных адресов: точное совпадение, маска (`/catalog/*`,
  `/catalog/**`), regex; приоритет внутри группы. Текстовые поля переводимые, по колонке на поле.
- `seo_redirects` — 301/302 тем же матчером, со счётчиком срабатываний. Глобальная middleware,
  **не** группа `web`: до адреса без маршрута группа не доходит.
- Резолвер и источники: `UrlRuleSource` (100), `DefaultsSource` (10), приоритет 50 держится
  свободным под `HasSeo`. Мерж **по полям**, не по источникам.
- Рендер `<head>`: `@webxSeo` / `<x-webx-seo::head :for="$page" />`, шаблон title, мягкие лимиты.
- `/robots.txt` из настройки `seo.robots-txt`; вкладка SEO в настройках приезжает патчем от
  модуля, а не от сайта.
- `wx-seo` — тип поля на обеих половинах: всё, что страница говорит о себе, одним объектом.

MCP: `seo_urls_list`, `seo_urls_get`, `seo_urls_set`, `seo_test_url`, `seo_redirects_list`,
`seo_redirects_set`, `seo_import_redirects`. Скоупы `seo:read` / `seo:write`.

Сделано 16.09.2026 (сессия D `module-pages`): трейт `HasSeo`, `seo_meta`, `EntitySource` и тип
поля `wx-seo` на сервере. Осталось отложенным (§16 спецификации): лог 404 и `find_404s`;
аудит (сущности без SEO, дубли title, длинные description); `sitemap.xml`; плагины
`SeoExtension` (breadcrumbs, schema.org для сущностей, hreflang, twitter-cards); схлопывание
цепочек редиректов.

### `webx-ui/module-blocks` — конструктор блоков

Статус: спроектирован 15.09.2026; рендер, наборы стилей, предпросмотр и панель (сессии A–D
плана) написаны 15.09.2026, дальше — MCP, релиз и демо. Спецификация — [`WEBX_UI_MODULE_BLOCKS.md`](WEBX_UI_MODULE_BLOCKS.md).

Раздел панели, где тип блока создаётся целиком — схема полей, шаблон Blade, стили и скрипт, — плюс
механизм, который собирает из блоков содержимое любой сущности и печатает его на сайте. Пишется до
`module-pages`: содержимое страницы — массив блоков, и формат хранения нельзя сочинить позже.

Раньше значился как `module-components`; переименован, потому что раздел в панели называется
«Блоки», а идентификатор модуля — это то, чем он называется в панели.

- `blocks` / `block_versions` / `block_bundles` — тип, неизменяемые слепки версий и собранные
  наборы CSS и JS по хешу «тип + версия».
- Правда в базе, а не в сгенерированных файлах: деплой из репозитория снёс бы всё, что сделали в
  панели. Переносимость — `webx:blocks:export` / `import`.
- Вложенность — не отдельная сущность, а поле: узел `wx-blocks` в схеме блока-контейнера.
- Blade редактируется через панель осознанно; раздел приравнен по правам к доступу на деплой.
- У скрипта блока контракт входа (функция на экземпляр) и мост `webx.provide` / `webx.use` к тому,
  что уже собрано на сайте.
- Предпросмотр — служебный адрес `/_preview/{type}/{id}` с подписанным токеном, один и тот же для
  фрейма в панели, кнопки «Открыть на сайте» и телефона.

Черновики и версии сущностей — общий механизм каркаса (`HasDraft`, `HasVersions`,
`entity_versions`), он появляется здесь же, потому что без него не работает предпросмотр. Туда же
правка в `nested-set`: узел, ещё не вставленный в дерево.

npm-пара: `@webx-ui/module-blocks` — узел `wx-blocks` для описанных экранов, конструктор на экране
сущности и раздел «Блоки».

MCP: `blocks_list`, `blocks_get`, `blocks_create`, `blocks_update`, `blocks_publish`,
`blocks_render`, `blocks_get_content`, `blocks_set_content`, `blocks_edit_content`,
`blocks_preview_url` — и ресурсы с домашними правилами вёрстки, каталогом блоков и списком того,
что сайт отдаёт через `webx.provide()`. Точечная правка содержимого (операции по ключам,
`revision` против затирания) — §18.1 спецификации.

### `webx-ui/module-pages` — страницы

Статус: спроектирован 16.09.2026, кода нет — [спецификация](WEBX_UI_MODULE_PAGES.md).

Первый модуль, который собирает соседей на живой сущности: дерево (`nested-set`), адрес из реестра
(`routing`, тип `page`, форматтер `TreePath`, политика `Fail`), содержимое блоками
(`module-blocks`), черновик и версии (`module-admin`), SEO (`module-seo`). Своего кода мало, и
это правда: он же — первая настоящая проверка всех четырёх.

- **Главная — корневой узел** с пустым слагом: `UrlNormaliser::join` выбрасывает пустые сегменты,
  поэтому её путь `''`, а у ребёнка `about`, а не `home/about`. Правок в `routing` не требует.
- У главной правится содержимое, но не структура; отдаётся возможностями узла (`can.address`,
  `can.move`, `can.delete`), а не признаком «корень».
- `title` и `slug` переводимые, адрес свой на каждый язык. Уникальности слага в таблице нет — она
  в реестре, по `(locale, path)`.
- Удаление мягкое, ветка гаснет целиком (`trashed_with`), адреса освобождаются событиями.
- Экран списка — табличное дерево с ленивыми детьми, поиск отменяет дерево; редактор — вкладками
  Контент · Настройки · SEO · История.
- Здесь же открыто отложенное в `module-seo`: `HasSeo`, `seo_meta`, `EntitySource` (сессия D).

npm-пара: `@webx-ui/module-pages` — раздел «Страницы» и редактор.

MCP: `pages_tree`, `pages_get`, `pages_create`, `pages_update`, `pages_move`, `pages_publish`,
`pages_unpublish`, `pages_delete`, `pages_restore`. Содержимое блоками агент правит
`blocks_edit_content` — второго способа делать то же самое не заводим.

Права — отдельной задачей: пока `pages.view` и `pages.manage`.

### `webx-ui/module-inbox` — формы и заявки

Статус: спроектирован 17.09.2026, кода нет — [спецификация](WEBX_UI_MODULE_INBOX.md).

Формы сайта и мини-CRM вокруг того, что с них приходит: администратор собирает форму в панели
(поля мышкой, а не кодом), вставляет её компонентом или блоком, посетитель отправляет, получателям
уходит письмо, а в панели у заявки есть статус, ответственный и заметки. Списано с работающего
модуля на `shop.alfatech.local`; расхождения названы в §2 спецификации.

- **Поле формы — строка в таблице, а не узел схемы экрана.** У поля есть id, на который ссылается
  ответ, порядок для перетаскивания и флаг `in_table` — «колонка в списке заявок».
- **Значение хранит снимок поля** (подпись и тип на момент отправки), поэтому старая заявка
  читается своими словами, а поле удаляется мягко и историю не уносит.
- Приём — своя дверь вне CSRF (кэшируемая страница отдаёт протухший токен), антиспам без капчи по
  умолчанию, заявка сохраняется **до** писем.
- Модуль первым в экосистеме отправляет почту: ни очередей, ни mailable до него не было.
- Вложения — на своём приватном диске, не в медиабиблиотеке; отдача через панель с проверкой прав.
- Вёрстка публичной формы — дефолтная и подменяемая публикацией вьюх; скрипт без зависимостей,
  форма работает и без JS.
- Статусы настраиваемые; канбан отложен (данные под него готовы).

npm-пара: `@webx-ui/module-inbox` — раздел «Inbox»: формы, редактор формы, заявки, статусы.

MCP: `inbox_forms_list`, `inbox_form_get`, `inbox_form_save`, `inbox_list`, `inbox_get`,
`inbox_set_status`. Приём заявок агенту не отдаётся — дверь и так публичная.

Права: `inbox.view`, `inbox.update`, `inbox.manage`.

### `webx-ui/module-faq` — вопросы и ответы

Статус: выпущен 24.09.2026 в v0.37.0 — [спецификация](WEBX_UI_MODULE_FAQ.md), гайд —
`apps/docs/guide/faq.md`.

Вопросы с переводимыми вопросом и ответом, плоские категории без адреса, порядок руками — общий и
внутри категории. Своей страницы у модуля нет: общая страница FAQ — это страница с блоком.

- Разметка `FAQPage` — одна на страницу (`Seo::put()`), по умолчанию только там, где категории
  не выбраны; вся выключается `WEBX_FAQ_MARKUP`. `module-seo` и `module-pages` — `suggest`.
- Якорь вопроса — из текста вопроса, ссылка `#якорь` открывает его на странице.
