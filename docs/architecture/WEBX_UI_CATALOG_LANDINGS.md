# Посадочные каталога — `module-catalog-landings`

Спутник ядра каталога: посадочные страницы фильтров для SEO. Архитектура семейства —
[`WEBX_UI_CATALOG.md`](WEBX_UI_CATALOG.md) (§8.1, решения 17–19 и 26), ядро и его реестры —
[`WEBX_UI_MODULE_CATALOG.md`](WEBX_UI_MODULE_CATALOG.md) (§7.7 `FilterUrls`, §10.3 SEO), свойства —
[`WEBX_UI_CATALOG_PROPERTIES.md`](WEBX_UI_CATALOG_PROPERTIES.md); здесь они не повторяются.
Выпущено в v0.56.0; спека — справочник того, что есть.

Ручная перелинковка между любыми адресами и FAQ на странице — не здесь, а в `module-seo`
([`WEBX_UI_MODULE_SEO.md`](WEBX_UI_MODULE_SEO.md) §18): посадочная там просто один из адресов.

## 1. Что это

**Посадочная — та же страница листинга, что у категории**: тот же шаблон, фильтр, сортировка и
пагинация, но набор фильтров зашит, а у страницы свой адрес, своё SEO и свой текст. Сверх листинга
— только полоса рекомендуемых товаров. Страница из блоков (баннеры, произвольная вёрстка) — это
`module-pages`, не посадочная.

## 2. Решения (не переоткрывать)

1. **Основа — категория или весь каталог.** Бренд — обычный фасет в наборе, отдельной основы
   «страница бренда» нет. Фасет категории в набор не входит: категория — основа.
2. **Набор — любые фасеты, включая несколько значений одного фасета и диапазоны** («ноутбуки до
   50 000»). Хранится по id значений, а не по слагам: переименование свойства, значения или бренда
   посадочную не трогает.
3. **Адрес плоский от корня сайта**, как у категорий (решение 23 архитектуры): `/noutbuki-apple/`.
   Слаг на каждом языке, уникальность на весь сайт проверяет `routing`; смена слага — алиас и 301.
4. **Два одинаковых набора на одной основе запрещены.** Ключ — хеш нормализованного набора.
5. **SEO — карточка `wx-seo` (`HasSeo`)**, шаблон по умолчанию — из H1. Правило адреса
   `module-seo` (приоритет 100) бьёт всё, как везде.
6. **Два текста: над списком и под ним.** У категории один (над списком), и она его оставляет:
   расхождение в данных, а не в вёрстке — у листинга два места под текст (§6.2).
7. **Своя сортировка по умолчанию — необязательная.** Выбор читателя (`?sort=`) её бьёт.
8. **Рекомендуемые товары — отдельная полоса над листингом**, подобранная руками. Выдачу она не
   меняет и в сортировку не вмешивается. Закрепление товаров в самой выдаче не делаем.
9. **Пустая выдача:** страница живёт, но `noindex`, в карте сайта её нет, в панели — «0 товаров».
10. **Значение набора слили с другим** — посадочная молча переходит на новое. **Значение удалили** —
    оно выпадает из набора, посадочная получает пометку «требует внимания»; если набор опустел или
    совпал с другим — снимается с публикации (§9).
11. **Перелинковка внутри каталога — здесь** (§7): подборки на категории, соседние посадочные,
    такие же в других категориях, «товар в подборках».
12. **Массовое создание** — действием в панели и инструментом MCP: категория × значения фасета по
    шаблонам слага, H1 и SEO (§8.3).
13. **Права — каталога** (`catalog.view` / `catalog.manage`), MCP — скоупы `catalog:read` /
    `catalog:write` под `catalog` через `SatelliteTools`, как у свойств.

## 3. Как работает страница

Посадочная — это **страница категории с заранее выбранным состоянием фильтра**; всё остальное
даёт механика ядра, второй реализации листинга нет (правки ядра — §10):

- `LandingHandler` зовёт `Storefront::listing()` с основой (`scope` — категория или ничего),
  **затравкой состояния** — набором посадочной — и `subject: $landing`. Хвост адреса
  **складывается** с затравкой (`FilterState::merge()`): значения списка объединяются, диапазон
  хвоста заменяет диапазон набора;
- фильтр видит набор выбранным: значения отмечены, их можно снять;
- ссылки фильтра строит ядро и пропускает через переписчик (§5): состояние, равное набору, — адрес
  посадочной; набор плюс что-то ещё — `/noutbuki-apple/color_black/`; снятое значение — меньшая
  посадочная или категория;
- правило «одно написание» ядра сравнивает запрошенный адрес с построенным: `/noutbuki/brand_apple/`
  отвечает 301 на `/noutbuki-apple/`, а `/noutbuki-apple/brand_dell/` («Apple и Dell» по сложению)
  — 301 на `/noutbuki/brand_apple_dell/`. У адреса один смысл. Построенный адрес страницы с
  затравкой — путь затравки, каким его назовут переписчики, плюс хвост; отдельного параметра «где я»
  у `listing()` нет, цена — второй `prepare()` переписчиков на странице посадочной.

Выбор подкатегории на посадочной — переход, как на странице категории (§8.3 архитектуры), но
вместе с набором: посадочная игровых ноутбуков Apple, если она есть, иначе
`/igrovye-noutbuki/brand_apple/`. Посадочная без основы работает в контексте `root`, даже если сама
страница корня каталога выключена (решение 25 архитектуры): фасеты по охвату, как в корне.

## 4. Схема

### `catalog_landings`

| Колонка                    | Тип                       | Примечание                                                     |
| -------------------------- | ------------------------- | -------------------------------------------------------------- |
| `id`                       | `bigIncrements`           |                                                                |
| `category_id`              | `foreignId` null          | основа; null — весь каталог                                    |
| `filters`                  | `json`                    | нормализованный набор: `{ key: { values: [...], min, max } }`  |
| `filters_hash`             | `string(64)` null         | sha256 от основы и набора; уникальный; null — у сломанной (§9) |
| `name`                     | `json`                    | переводимое; подпись в панели и в ссылках подборок             |
| `slug`                     | `json`                    | переводимое; пишется в реестр `routing`                        |
| `h1`                       | `json` null               | переводимое; пусто — `name`                                    |
| `text_above`, `text_below` | `json` null               | переводимые, rich-text                                         |
| `sort`                     | `string(32)` null         | ключ из `webx-catalog.sorts`                                   |
| `on_category`              | `boolean` default `false` | показывать в «Подборках» категории                             |
| `position`                 | `integer` default `0`     | порядок в подборках и среди соседей                            |
| `is_published`             | `boolean` default `false` |                                                                |
| `attention`                | `string(32)` null         | `value_removed` \| `duplicate` \| `empty_set`                  |
| `products_count`           | `integer` null            | сколько видно на витрине; null — ещё не посчитано              |
| `counted_at`               | `timestamp` null          |                                                                |
| `deleted_at`, timestamps   |                           | soft delete, как у категорий                                   |

`catalog_landing_products` — `landing_id`, `product_id`, `position`: рекомендуемые. Невидимый на
витрине товар полоса пропускает, а не удаляет: вернули — снова в полосе.

`catalog_landing_runs` — прогоны генерации пачкой (§8.3).

**Набор.** Нормализация перед хешем: ключи по алфавиту, значения по возрастанию id, диапазон —
`min`/`max` числами, пустые фасеты выброшены. Фасет категории в наборе и фасет, которого нет в
реестре `Facets` на момент сохранения, — ошибка валидации; фасет, исчезнувший потом, — §9. В API
набор — как в таблице: `{ key: { values: [...] } | { min, max } }`; коды и слаги — в MCP (§11).

## 5. Переписчик

`LandingRewriter implements FilterUrlRewriter`:

- **`prepare()`** — один запрос на рендер: опубликованные посадочные основ текущего контекста
  (категория страницы и категории, на которые ведут ссылки фильтра) плюс посадочные без основы;
  держит их в памяти запроса (`scoped`), как `ProductProperties`.
- **`rewrite()`** — среди посадочных той же основы ищет **наибольшую покрывающую**: каждый фасет
  посадочной есть в состоянии и **равен** ему (те же значения, тот же диапазон). Наибольшая — с
  большим числом фасетов, при равенстве — меньший `position`, потом меньший `id`. Остаток — `rest`
  в `RewrittenUrl`, ядро допишет его сегментами.
- Равенство по фасету, а не «значения посадочной входят в выбранные»: при выбранных Apple и Dell
  посадочная на Apple не основа — иначе у `/noutbuki-apple/brand_dell/` было бы два смысла.
- **Индексируемость:** `RewrittenUrl::$indexable` только открывает — состояние, переписанное
  целиком (пустой `rest`), при товарах в выдаче. Без флага или с остатком решают правила фильтра.
  Закрывает пустую посадочную её `seoData()` (§6.3).

## 6. Витрина

### 6.1. Адрес и обработчик

`RouteType('catalog.landing', Landing::class, formatter: Slug::class, handler: LandingHandler,
acceptsTail: true, onConflict: OnConflict::Fail)` — в одном пространстве с категориями, поэтому
занять слаг категории нельзя, и наоборот. Модель — `Visible` (опубликована, не удалена, основа
видна), `HasBreadcrumbs` (крошки основы, потом посадочная), `ListingSubject`, `HasSeo`,
`HasListingTexts`, `HasDefaultSort`. Шаблон — `webx-catalog::category`, тот же, что у категории.

### 6.2. Тексты, сортировка, полоса

- **Тексты** шаблон берёт у владельца страницы (`$page->owner()`, §10): над списком и блок
  `webx-catalog-category__text` между пагинацией и нижней точкой. Категория отдаёт описание в
  верхнее, посадочная — оба. Печатаются только на `isPlain()`: вторая страница и выбор поверх
  набора — без текстов, как у категории.
- **Сортировка по умолчанию** — `HasDefaultSort`; ключ, которого витрина не предлагает, — как
  `null`. Canonical такую страницу сортированной не считает; ссылка на сортировку каталога по
  умолчанию несёт `?sort=default`, иначе читатель не смог бы её выбрать.
- **Рекомендуемые** — точка `catalog.listing.top`: полоса карточек той же разметки
  (`webx-catalog::card`) только на чистой первой странице. Карточки готовятся вместе с карточками
  страницы (`StorefrontParts::prepare()`), иначе у них не было бы меток и бренда. Заголовок —
  слово словаря, переопределяется вьюхой.
- Части витрины (полоса, ссылки §7) берут данные у композеров вьюх (`LandingViews`), а не из
  `prepare()`: им нужна страница или товар. Сайт, опубликовавший вьюху, данные сохраняет.

### 6.3. SEO

- Чистая посадочная — карточка `wx-seo` посадочной; пустой title — шаблон
  `webx-catalog-landings::seo.title` («{h1}»), пустой H1 — `name`. Canonical — на себя.
  `ListingSource` берёт `owner()->seoData()`, пока поверх набора ничего не выбрано
  (`isFiltered()`).
- Выбор поверх набора — закрыт (`noindex, follow`), как любая комбинация; `filterTitle` пуст на
  любой странице с затравкой — заголовок остаётся именем посадочной.
- Пустая выдача — `noindex` (решение 9): `robots` в `seoData()` по `products_count = 0`, поэтому
  `<head>`, карта и `test-url` отвечают одинаково (решение 2 §17.1 спеки SEO).
- Разметка: `BreadcrumbList` и `ItemList`, как у категории.

### 6.4. Карта сайта

Тип реестра `catalog.landing` с `Visible` — файл `sitemap-catalog.landing.xml` получается сам.
Пустые выпадают через `noindex`. Первый уровень фильтра, забранный посадочной, `FilterSitemap`
уже пропускает.

### 6.5. Счётчик товаров

`products_count` считает задача `CountLandings` движком (тот же запрос, что у витрины, только
счёт; посадочные одной основы без товаров в индексе — одним запросом на основу).

- **Триггер — событие ядра** `WebxUi\Catalog\Events\ProductsIndexed(products, categories)` из
  `Indexer`: категории пачки с предками (поле `categories` документов), без второго чтения
  товаров. Слушатель одним `UPDATE` снимает `counted_at` у посадочных этих основ и без основы и
  ставит одну `CountLandings` (`ShouldBeUnique`: перестройка индекса — сотни пачек, пересчёт один).
- На `SqlEngine` индекса и события нет: `webx:catalog-landings:count` каждые 15 минут считает все;
  ночью `--all` — на любом движке, страховкой.
- Счёт пишется мимо модели (не правка — ни журнала, ни слушателя карты); переход `0 ↔ не 0` сам
  двигает поколение карты сайта.
- Тот же проход чинит наборы (`LandingRepairs::sweep()`, §9).

## 7. Перелинковка внутри каталога

Четыре выборки (`LandingLinks`), у каждой Blade-партиал, который сайт переопределяет, и лимит в
конфиге `webx-catalog-landings.links.*`:

| Где        | Что                                                         | Порядок                          |
| ---------- | ----------------------------------------------------------- | -------------------------------- |
| категория  | «Подборки»: `on_category` этой основы                       | `position`                       |
| посадочная | соседние: другие посадочные той же основы                   | `position`                       |
| посадочная | такие же в других категориях: тот же набор, другая основа   | по дереву категорий              |
| товар      | «Товар в подборках»: набор целиком входит в значения товара | `position`, потом глубина основы |

- **Точки:** «Подборки» — `catalog.listing.top` на странице без выбора (`isFiltered()` ложно, в
  том числе на второй странице); соседи и другие категории — `catalog.listing.bottom` на посадочной
  без выбора поверх набора; товар — `catalog.product.aside`. Точки печатает только шаблон
  `category` (в нём и посадочная без основы); `root` и страница бренда — нет.
- **Только опубликованные с товарами.** Пустая посадочная не получает ссылок.
- **«Товар в подборках»** — кандидаты: посадочные основы товара и её предков плюс без основы.
  Значения товара — из его документа индекса (`Documents::build()`, тот же, что у индексации),
  сверка в памяти: один запрос к посадочным, ни одного на товар. По смыслу листинга значения
  одного фасета в наборе — «или»: товар Dell есть в подборке «Apple или Dell».
- Ссылка с анкором `name` посадочной; заголовки блоков — слова словаря.

## 8. Панель

npm-пакет `@webx-ui/module-catalog-landings` (`catalogLandings()`); на php — `LandingsModule`
(группа «Каталог», order 303, после брендов, идентификатор `landings`). Журнал изменений —
`HistoryTypes`, модуль `catalog-landings`. Мок плейграунда —
`apps/playground/server/panel/catalog-landings.ts`.

### 8.1. Раздел

`LandingsPage`: название, адрес, основа, набор чипами («Бренд: Apple, Dell», «Цена: до 50 000»),
товаров, состояние, пометка внимания. Фильтры: основа (дерево), «требует внимания»,
опубликованные, «пустые». Поиск по названию и адресу.

### 8.2. Форма

`LandingEditorPage` с экраном `catalog.landing-form` (`landing-form.json`); новая — по
`…/landings/new`, первое сохранение переводит адрес на id.

- **Основа** — категория деревом, пусто — весь каталог.
- **Набор** — узел `wx-catalog-landing-set`: «добавить фасет» из уместных в основе (набор свойств
  категории плюс фасеты ядра и спутников); значения — тем же полем, что в фильтре списка товаров
  (справочник — множественный выбор с поиском, число — от/до). Рядом — живое число товаров
  (`POST /landings/count`, движком) и предупреждение, если набор уже занят.
- **Адрес** — `wx-catalog-landing-slug`, слаг на каждом языке; подсказку (`suggested`, по языку)
  приносит тот же `POST count`, считает её `LandingWords`, как и шаблоны генерации, — подсказка
  и пачка не расходятся.
- **Тексты** — `name`, `h1`, над списком и под ним (`wx-rich-text`, переводимые).
- **Сортировка** — `wx-catalog-landing-sort` из реестра каталога; пустая — значение `default`
  («Как у категории»), потому что пустую строку селект ядра показывает плейсхолдером; в данные
  пишется `null`. Плюс «показывать в подборках категории» и порядок.
- **Рекомендуемые** — `wx-catalog-landing-products`: комбобокс с поиском, порядок
  перетаскиванием; ресурс отдаёт `recommended_items` (id, название, артикул, в корзине ли) рядом
  с `recommended`, чтобы не спрашивать товары второй раз.
- **SEO** — карточка `wx-seo`; ссылка «открыть на сайте».

### 8.3. Создать пачкой

Диалог в списке, сервис `LandingGenerator` (его же зовёт MCP):

1. основы — одна категория, несколько или поддерево;
2. фасет и значения. **Только фасет значений:** диапазону нечего подставить в `{value}`,
   категория — основа; и то и другое — 422 под `facet`. «Все значения» — значения с товарами в
   основе не меньше `min_products` (по умолчанию 1); явно перечисленные порогом не режутся;
3. шаблоны: слаг (`{category}-{value}`, слаги из адреса категории и значения; без `{value}` — 422
   под `slug`, иначе у всех строк один адрес), `name` и H1 (`{category} {value}`), title и
   description для карточки SEO; публиковать сразу или нет;
4. **предпросмотр** таблицей: адрес, H1, товаров, конфликт — слаг занят, набор уже есть, `empty`
   (0 товаров), `no-slug` (у основы или значения нет слага на каком-то языке). Конфликтные строки
   пропускаются, не ломая остальные.

Прогон — своя таблица `catalog_landing_runs`, а не `BulkRun` ядра: тот знает только товары. Строки
предпросмотра фиксируются при старте; до `generate.sync_limit` (50) — в самом запросе, больше —
задачей `GenerateLandings` пачками `generate.chunk` (100), за раз не больше `generate.max` (5000).
Ответ — `id`, `status`, `total`, `done`, `skipped` (отказано в предпросмотре), `failed` (отказал
`LandingForm` по дороге), `errors`.

### 8.4. API

`/api/cms/catalog/landings` — список, CRUD, `publish`/`unpublish`, `restore`, `count` (с
`suggested`), `generate` (`dry_run`), `facets?category=` (уместные фасеты основы со значениями для
конструктора; считает `BaseFacets`, его же зовёт MCP). Валидация 422: слаг занят (кем — как у
артикула), набор занят (какой посадочной), фасет категории в наборе.

## 9. Значения, которые исчезают

Посадочная хранит id значений, поэтому слушает `FacetValueRetargeted(facetKey, from, to)` — ядро
поднимает его из `FilterAliases::retarget()` только для значений (`FilterAliases::VALUE`;
переименование кода фасета — не исчезновение), даже если ни один алиас на значение не вёл.

- **`to` — id** (слияние): значение в наборе заменяется; набор совпал с другой посадочной —
  `attention = duplicate`, снята с публикации.
- **`to` — null** (удаление значения, мягкое удаление бренда): значение выпадает,
  `value_removed`; опустел фасет — выпадает фасет; опустел набор — `empty_set`, снята с
  публикации. Восстановленный бренд в наборы не возвращается, как любое удалённое значение.
- **Удалённое свойство** события не поднимает: значения в корзине живы и вернутся с ним, а у
  числового значений нет вовсе. Поэтому витрина читает набор без исчезнувших фасетов сразу
  (`LandingSet::state()`), а запись — фасет выпал, пометка, снятие с публикации — делает пересчёт
  (`LandingRepairs::sweep()` в `LandingCounter`, §6.5). Пересчёт приходит сам: удаление свойства
  помечает его товары к индексации, а ночной — страховка.
- **Основа в корзине** — посадочная невидима (`Visible` смотрит на основу), восстановили — снова на
  месте. Пометки нет: это не поломка набора.
- **Ключ набора у сломанной — пустой.** `duplicate` и `empty_set` не держат `filters_hash`, и
  посадочная, с которой набор совпал, остаётся владельцем. Сохранение в форме спрашивает ключ
  заново (422, если занят) и снимает пометку. Ключ посадочной в корзине держится: восстановить её
  не значит завести вторую.

Журнал пишет изменение набора с причиной.

## 10. Правки ядра

Что посадочные добавили в `module-catalog` (и одной правкой в `module-catalog-brands`):

1. **Затравка состояния.** `Storefront::listing()` принимает `FilterState $base`; состояние
   страницы — `base`, сложенный с хвостом (`FilterState::merge()`, §3).
2. **`CatalogPage`:** `owner()` — сначала субъект, потом категория (посадочная стоит на категории,
   но говорит за себя); `isFiltered()` — выбрано ли что-то поверх `base`; `isPlain()` — не
   `isFiltered()`, без сортировки и первая страница.
3. **`RewrittenUrl::$indexable`** (§5).
4. **`HasListingTexts { textAbove(locale), textBelow(locale) }`** — у `Category` (описание —
   верхний) и у посадочной.
5. **`HasDefaultSort`** — отдельный контракт, а не метод `ListingSubject`: иначе бренд обязан
   отвечать «у меня нет». `Listing::sortOf()` берёт его, когда `?sort=` нет.
6. **Точки `catalog.listing.top` и `catalog.listing.bottom`** в `StorefrontParts`, получают
   `CatalogPage`.
7. **`FacetValueRetargeted`** (§9); мягкое удаление бренда зовёт `retarget(brand, id, null)`.
8. **`ListingSource`** — карточка SEO владельца без выбора поверх затравки, `filterTitle` пуст на
   странице с затравкой (§6.3).
9. **`ProductsIndexed`** из `Indexer` (§6.5).

Тестовый переписчик ядра (`tests/Fixtures/LandingRewriter.php`) умеет наборы по §5; `LandingSeamsTest`
держит эти швы без спутника.

## 11. MCP

`LandingTools` и ресурс `LandingsResource` (`catalog://landings` — правила дома: когда делать
посадочную, шаблоны, «не плодить пустые») в `WebxUi\CatalogLandings\Mcp`, отданы каталогу через
`SatelliteTools`. Инструменты `catalog_landings_*`: `list` (фильтры как в панели, включая
`attention`), `get`, `create`, `update`, `delete`, `restore`, `publish`, `unpublish`, `count`
(набор → число товаров без сохранения), `facets` (то же, что `GET facets?category=`, но со слагами
значений — иначе агенту неоткуда взять слова набора), `generate` (§8.3, `dry_run` — предпросмотр;
фасет кодом, значения слагами, строки несут ещё `value_slug`), `generation` (прогресс генерации,
ушедшей в очередь).

- Набор — кодами фасетов и слагами значений на языке `locale` (по умолчанию — язык сайта по
  умолчанию); ищутся сначала на нём, потом на остальных, код — ещё и как ключ реестра (`price`).
  Неизвестный слаг — отказ с отсылкой к `catalog_landings_facets`. Хранится по id, ответ отдаёт оба.
- Название и адрес при создании необязательны: без них — из основы и набора тем же `LandingWords`.
  Слова одного языка строкой ложатся поверх остальных языков, а не вместо них.

## 12. Отложено

Обмен посадочными CSV/XLSX (MCP покрывает массовую работу); закрепление товаров в выдаче; второй

`module-seo`, не посадочных.
