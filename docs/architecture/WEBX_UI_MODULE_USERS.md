# `webx-ui/module-users` — посетители сайта — спецификация

Статус: спроектировано, ждёт приёмки (webx-ui#57, этап 1); пакет не начат. Решения человека — §2,
отложенное — §20. Пакет — `webx-ui/module-users` (composer, namespace `WebxUi\Users`, словарь
`webx-users`), npm-пара — `@webx-ui/module-users` (раздел панели). Id модуля — `users` (области MCP
`users:read` / `users:write`, права `users.*`, §16). Таблицы — `users` и `users_*` (§3).

Посетитель сайта — тот, кто регистрируется и входит **на сайте**: покупатель магазина, читатель
закрытого раздела, участник клуба. Это не администратор: у него своя модель, своя таблица, свой гард
и ни одного пути в `/cms` ([`WEBX_UI_PERMISSIONS.md`](WEBX_UI_PERMISSIONS.md) §2). Модуль общий, а не
магазинный: кабинет без магазина — профиль, способы входа и пароль; магазинные модули
подключаются к нему сами, через реестры и шов в `module-admin` (§4), и `module-users` не знает ни
одного из них. Карта коммерции — [`WEBX_UI_COMMERCE.md`](WEBX_UI_COMMERCE.md), корзина —
[`WEBX_UI_MODULE_CART.md`](WEBX_UI_MODULE_CART.md), формы сайта — §17
[`WEBX_UI_WIDGETS.md`](WEBX_UI_WIDGETS.md), layout кабинета — `layout.account` §3.7
[`WEBX_UI_COMPOSITIONS.md`](WEBX_UI_COMPOSITIONS.md).

## 1. Границы

**Внутри:** таблица `users` и соседние (§3); гард `site` (§5); регистрация и вход по e-mail и паролю,
выход, «запомнить меня» (§6); восстановление пароля с отдельной страницей (§7); подтверждение e-mail,
баннер и повторная отправка (§8); вход и регистрация через соцсети, реестр провайдеров, Google и
Facebook из коробки, ключи в панели (§9); привязка и отвязка соцсетей (§9.6); свои поля сайта и их
реестр (§10); обязательность полей формы настройкой (§10.5); кабинет, реестр его разделов и маршруты
под ним (§11); диалог входа для оформления заказа (§12); группы посетителей (§13); удаление аккаунта и
приватность (§14); защита от перебора (§15); раздел панели (§16); MCP (§17); словарь, демо, письма.

**Рядом, в `module-admin`** (§4): контракт `Visitors` — «кто сейчас вошёл, его контакты, подтверждён
ли e-mail» — с пустой реализацией по умолчанию, события входа и выхода, middleware `webx.visitor`.
Это шов для модулей, которые должны работать и без `module-users` (магазин — гостем).

**Граница с администраторами (`module-auth`)** — правила §2 спеки прав без исключений:

| Что               | Администратор                                   | Посетитель                                                                        |
| ----------------- | ----------------------------------------------- | --------------------------------------------------------------------------------- |
| Модель и таблица  | `WebxUi\Auth\Models\CmsUser`, `cms_users`       | `WebxUi\Users\Models\User`, `users`                                               |
| Гард              | `cms` (сессия), `api` (Passport)                | `site` (сессия)                                                                   |
| Права             | `cms_roles`, `<module>.<act>`, `HasPermissions` | нет; `HasPermissions` не реализует никогда                                        |
| Доступ в `/cms`   | по правам                                       | никогда: `cms.auth` пускает только `CmsUser`                                      |
| MCP, ключи, OAuth | да                                              | нет                                                                               |
| Одна почта        | отдельная учётка администратора                 | отдельная учётка посетителя; связи по e-mail нет, вход в одну не открывает другую |

- Сессия у сайта одна на оба гарда (одна cookie). **Выход посетителя не трогает вход
  администратора:** `Auth::guard('site')->logout()` и новый CSRF-токен, но не
  `session()->invalidate()` — тот выбросил бы и гард `cms` (тест держит: администратор, вошедший на
  том же браузере, после выхода посетителя остаётся в панели). Вход посетителя —
  `session()->regenerate()` (без потери данных сессии).
- Маршруты сайта и кабинета на гарде `site`; ни один маршрут модуля не стоит под `cms.auth`, кроме
  панели (§16), а там действует администратор над записями посетителей.

**Граница с магазином** (решение 6):

- В `composer.json` у `module-users` нет ни одного магазинного пакета — ни в `require`, ни в
  `suggest`. Ни одной строки `class_exists(…Orders…)` в коде модуля.
- Направление зависимостей одно: магазинный модуль знает посетителя через контракт `Visitors`
  (`module-admin`, §4) — всегда, — и через реестры `module-users` (меню кабинета, вкладки карточки) —
  если он стоит (`class_exists`, `suggest`), как каталог регистрирует поставщика в корзине.
- Магазин без `module-users` работает: `Visitors::current()` — `null`, все заказы гостевые.

**Снаружи:**

- **Заказы, история заказов** — `module-orders`: свой `user_id` в заказе, свой раздел кабинета «Мои
  заказы», своя вкладка в карточке посетителя (§11.3, §16.2).
- **Корзина и слияние гостевой** — `module-cart` слушает событие входа (§13.3); колонка привязки — в
  его таблице.
- **Кошелёк, сертификаты, подарок другому покупателю** — `module-wallet`, `module-certificates`:
  владелец баланса — посетитель по id из `Visitors`; поиск получателя подарка — `Visitors::findByEmail()`.
- **Шаг оформления** — `module-checkout`; здесь — компонент диалога входа и контакты вошедшего (§12).
- **Конструктор условий** — `module-admin`; здесь — поле условия «группа посетителя», когда
  конструктор появится (§13.2).
- **Рассылки, подписки, согласия на маркетинг** — не здесь.
- **Вход по телефону и коду из SMS, двухфакторный вход посетителя** — не в первой версии (§20).

## 2. Принятые решения (не переоткрывать)

Решения человека от 23.10.2026 и 27.10.2026 (спецификация задачи webx-ui#57); при расхождении
действуют решения 27.10.

1. **Посетители — отдельно от администраторов.** Регистрация, вход, соцвход; доступа к панели нет
   никогда; администраторы — `module-auth`.
2. **Вход** — по e-mail и паролю; через соцсети — Google и Facebook в первой версии; Apple — позже,
   новый провайдер подключается реестром и не правит модуль (§9.1). Ключи OAuth-приложений —
   настройки сайта в панели, не только `.env`; провайдер без ключей не показывается (§9.3).
3. **Восстановление пароля** — ссылка на почту → отдельная страница: новый пароль и повтор. Ссылка
   одноразовая и с ограниченным сроком. Ответ на запрос не раскрывает, есть ли такой e-mail (§7).
4. **Регистрация** — имя и фамилия необязательные, телефон, e-mail (логин); или через соцсеть с
   данными провайдера, а если провайдер не отдал e-mail — спросить его (§9.5). Обязательность полей
   формы, в том числе телефона, — настройка сайта, а не код (§10.5).
5. **Кабинет** — редактирование профиля (имя, фамилия, телефон, e-mail, пароль), привязка и
   отвязка соцсетей; нельзя отвязать последний способ входа (§11, §9.6).
6. **Свои поля сайта** — точка расширения: сайт или модуль объявляет поле (тип, обязательность, где
   показывать — регистрация / профиль / панель, проверка); поле появляется в регистрации, профиле,
   экране панели и MCP без правки модуля. Типы — те же, что у экранов панели (`FieldTypes`). Где
   хранить — решает спека (§10.3).
7. **Кабинет — не обязательно магазин.** Без магазина — профиль, способы входа, пароль. Разделы
   кабинета регистрируют модули через реестр меню (§11.2). `module-users` не знает ни одного
   магазинного модуля; группы, слияние корзины, поля условий — точки подключения (§13). Магазин
   работает и без `module-users`.
8. **Вход в оформлении заказа** — гостем или со входом, регистрацию не навязываем. Вход — диалог на
   странице оформления (e-mail и пароль, соцсети, «Забыли пароль?», «Регистрация») без ухода со
   страницы. Вошедшему контакты подставляются сами и правятся. Шаг оформления — `module-checkout`;
   здесь — диалог и контакты (§12).
9. **Подтверждение e-mail обязательно, но не блокирует.** Письмо со ссылкой после регистрации,
   повторная отправка с ограничением частоты; неподтверждённый входит и оформляет заказ, видит
   баннер «Подтвердите e-mail». Возможности «только для подтверждённых» объявляет модуль-владелец
   общим признаком, а не правкой `module-users` (§8.4). E-mail, который провайдер отдал как
   проверенный, — подтверждён. Смена e-mail — новый адрес неподтверждён до перехода по ссылке (§8.5).
10. **Магазину** — группы покупателей (поле условий правил корзины), история заказов, привязка
    гостевой корзины при входе (слияние с корзиной аккаунта), баланс кошелька принадлежит
    покупателю, сертификат можно подарить другому покупателю — всё точками подключения (§13).
11. **Layout кабинета — композиция** `layout.account` (webx-ui#49), меню и разделы — свои (§11.4).
12. **Вид — тема.** Образец — крупный маркетплейс, упрощённо; разметка — поля и формы `widgets`,
    вид — CSS темы (§11.5).

Ответы человека на открытые вопросы спеки (27.10.2026):

13. **Таблица `users` скелета уходит из скелета.** `users`, `password_reset_tokens` и
    `App\Models\User` убираются из скелета `webx-ui/site`. Миграция модуля: таблицы нет — создать;
    есть пустая таблица Laravel по умолчанию — удалить и создать свою; есть с данными — отказаться с
    понятным сообщением и строкой `webx:doctor` (§3). Правка скелета — этап 3 (§19).
14. **Соцсеть по проверенному адресу связывается сама.** Провайдер сообщает, что адрес проверен
    (Google с `email_verified`), и аккаунт с этим адресом есть — соцсеть привязывается, вход без
    пароля, на адрес аккаунта — письмо «Привязан вход через Google». Без отметки «проверен» (и у
    Facebook) — «войдите паролем — и привяжется». Доверяет ли модуль отметке провайдера — свойство
    провайдера в реестре (`trustsVerifiedEmail()`), не код модуля (§9.1, §9.7).
15. **Регистрация на занятый адрес** отвечает честно: «Адрес уже зарегистрирован — войдите или
    восстановите пароль»; защита — лимит регистраций (§15).
16. **Смена e-mail** — только после перехода по ссылке на новый адрес, с текущим паролем; письмо на
    прежний адрес (§8.5).
17. **Гостевые заказы в кабинете не появляются:** в «Моих заказах» — только заказы, оформленные со
    входом; гостевой заказ менеджер привязывает вручную в панели (решение 21 и §13.3
    [`WEBX_UI_MODULE_ORDERS.md`](WEBX_UI_MODULE_ORDERS.md)).
18. **Галочки «обновить профиль» в оформлении нет.** Контакты вошедшего подставляются в заказ из
    профиля; покупатель меняет их для этого заказа, профиль от этого не меняется. Профиль правится
    только в кабинете (§12.2).
19. **Выгрузки своих данных в первой версии нет** — по первому запросу клиента (§14.2, §20).
20. **Раздел в панели — «Клиенты»**: слово по умолчанию в словаре на всех языках (en «Customers» и
    т. д.), сайт меняет его словом словаря. Id модуля, права, таблицы, MCP — по-прежнему `users`
    (§16).
21. **Общий `Field` — в `module-admin`.** Поле настроек провайдера (§9.1) — общий класс
    `module-admin`; на нём и `module-users`, и `module-notifications`, копии нет. Перенос — этап 7
    (§19).
22. **Готовые роли:** `users.view` и `users.manage` по умолчанию — только у «Администратора»;
    исключение — «Менеджер заказов» получает `users.view` для привязки заказа к клиенту (решение 33
    [`WEBX_UI_MODULE_ORDERS.md`](WEBX_UI_MODULE_ORDERS.md), §16.1).

Упрощения первой версии (решение человека 27.10.2026, комментарий к webx-ui#57) и решения
28.10.2026 (задача реализации webx-ui#88):

23. **Из первой версии убрано** (всё — в §20):
    - захват неподтверждённого аккаунта владельцем почты: строка §9.7 «адрес не подтверждён /
      проверен» идёт по «войдите паролем — и привяжется»; у владельца почты остаётся сброс пароля,
      который у неподтверждённого аккаунта отвязывает соцсети (§7, п. 5);
    - `prune_unverified_days` и чистка неподтверждённых аккаунтов (§14.3);
    - массовые действия в списке панели и `users_groups_assign` по фильтру (§16.2, §17) — группы
      посетителю назначают карточка и `users_update`;
    - `users_summary` и сводки модулей в `users_get` (§17).
24. **Группы клиентов — упрощены:** код и название на одном языке; без переводов, `is_default`,
    сортировки и отказа слушателей при удалении (§3, §13.1, §16.2).
25. **`.env` остаётся** запасным источником ключей провайдеров (§3, §9.3).
26. **Сквозная проверка — на lab-сайте** (`scripts/lab-site.sh`, постоянный сайт devbox на чекауте
    монорепы), а не на одноразовом сайте `site up` (§19, этап 11).
27. **Слияние гостевой корзины (§13.3) — последний этап задачи реализации**, после этапа 11, в
    `module-cart`: корзина уже выпущена (webx-ui#54) (§19, этап 13).

## 3. Таблицы

Все миграции откатываются (`down()` удаляет в обратном порядке). Индексы под каждый `WHERE` и
`ORDER BY` проверяются `EXPLAIN` на MariaDB в этапе, который их вводит.

### `users`

| Колонка                    | Тип                              | Примечание                                                                         |
| -------------------------- | -------------------------------- | ---------------------------------------------------------------------------------- |
| `id`                       | bigint                           |                                                                                    |
| `email`                    | string(191), **unique**          | логин; хранится нормализованным: обрезан, нижний регистр                           |
| `email_verified_at`        | timestamp, null                  | `null` — не подтверждён (§8)                                                       |
| `password`                 | string, null                     | хеш; `null` — аккаунт без пароля (вошёл соцсетью, создан из панели до приглашения) |
| `first_name`               | string(100), null                |                                                                                    |
| `last_name`                | string(100), null                |                                                                                    |
| `phone`                    | string(32), null, index          | как ввёл посетитель, без пробелов по краям; не логин, не уникален                  |
| `locale`                   | string(12), null                 | язык писем и кабинета: язык страницы при регистрации, дальше — последний вход      |
| `extra`                    | json, null                       | свои поля сайта (§10.3)                                                            |
| `blocked_at`               | timestamp, null                  | заблокирован администратором (§6.3)                                                |
| `remember_token`           | string(100), null                | «запомнить меня»                                                                   |
| `last_sign_in_at`          | timestamp, null, index           | для списка панели и MCP; без IP и устройства (§14)                                 |

- Колонки `name` нет: имя и фамилия раздельно (решение 4); полное имя — аксессор `name` (имя и
  фамилия через пробел, без них — часть e-mail до `@`).
- **Таблица `users` скелета** (решение 13). Скелет `webx-ui/site` до сих пор создаёт Laravel-таблицы
  `users` (`name NOT NULL`, `password NOT NULL`) и `password_reset_tokens`, модель `App\Models\User`
  и гард `web` на ней; этап 3 убирает их из скелета. На уже созданных сайтах таблица есть и обычно
  пуста, поэтому миграция модуля смотрит, что нашла:
  - таблицы `users` нет — создаёт свою;
  - есть таблица Laravel по умолчанию (колонка `name`, нет `first_name`) и она пуста — удаляет её
    вместе с пустой `password_reset_tokens` и создаёт свою;
  - есть таблица с данными — отказывается: исключение со словами «Table `users` already holds N
    rows; move them out or drop the table, then migrate again», а `webx:doctor` пишет ту же строку.
    Переносить ли свои данные, решает сайт.
  - `down()` удаляет только свою таблицу; таблицу Laravel не возвращает.

### `users_identities` — привязанные соцсети

| Колонка            | Тип                           | Примечание                                               |
| ------------------ | ----------------------------- | -------------------------------------------------------- |
| `id`               | bigint                        |                                                          |
| `user_id`          | FK `users`, `cascadeOnDelete` |                                                          |
| `provider`         | string(32)                    | ключ провайдера: `google`, `facebook`                    |
| `provider_user_id` | string(191)                   | id у провайдера (`sub` у Google)                         |
| `email`            | string(191), null             | адрес, который отдал провайдер, — для подписи в кабинете |
| `created_at`       | timestamp                     | когда привязан                                           |
| `last_used_at`     | timestamp, null               | последний вход этим способом                             |

- **unique (`provider`, `provider_user_id`)** — один аккаунт Google — один посетитель;
  **unique (`user_id`, `provider`)** — у посетителя не больше одной привязки каждого провайдера.
- Токены доступа провайдера **не хранятся**: модулю нужен только факт «это тот же человек», API
  провайдера после входа не зовётся.

### `users_password_resets` — ссылки сброса и приглашения

| Колонка      | Тип                                        | Примечание                                                    |
| ------------ | ------------------------------------------ | ------------------------------------------------------------- |
| `user_id`    | FK `users`, `cascadeOnDelete`, **primary** | одна живая ссылка на посетителя: новая заменяет прежнюю       |
| `token_hash` | char(64)                                   | `sha256` токена из ссылки; сам токен не хранится              |
| `purpose`    | string(16)                                 | `reset` — «забыли пароль»; `invite` — аккаунт из панели (§16) |
| `expires_at` | timestamp                                  | `reset` — `webx-users.reset_minutes` (60); `invite` — 7 дней  |
| `created_at` | timestamp                                  |                                                               |

- Своя таблица, а не брокер Laravel с `password_reset_tokens`: брокер ключуется адресом почты, а
  адрес меняется; здесь ключ — посетитель. Строка удаляется при использовании (одноразовость), при
  смене пароля любым путём и при смене e-mail.
- Протухшие строки чистит `webx:users:prune` (§14.3).

### `users_groups` и `users_group_user`

| `users_groups`             | Тип                    | Примечание                                                                 |
| -------------------------- | ---------------------- | -------------------------------------------------------------------------- |
| `id`                       | bigint                 |                                                                            |
| `code`                     | string(64), **unique** | `[a-z0-9-]`; по нему группу называют условия, MCP, код сайта (`wholesale`) |
| `name`                     | string(255)            | на одном языке, без переводов (решение 24); в панели список — по названию  |
| `created_at`, `updated_at` | timestamp              |                                                                            |

`users_group_user`: `group_id` FK `cascadeOnDelete`, `user_id` FK `cascadeOnDelete`, primary
(`group_id`, `user_id`), index (`user_id`), `created_at`. Связь «многие ко многим» (§13.1).

### `users_providers` — ключи провайдеров

| Колонка       | Тип                     | Примечание                                                                 |
| ------------- | ----------------------- | -------------------------------------------------------------------------- |
| `key`         | string(32), **primary** | ключ провайдера из реестра                                                 |
| `enabled`     | bool, default false     | включён администратором                                                    |
| `options`     | json, null              | открытые настройки (`client_id`, домен Apple-сервиса …)                    |
| `credentials` | text, null              | `encrypted:array` ключом приложения: `client_secret`, приватный ключ Apple |
| `updated_at`  | timestamp               |                                                                            |

- Образец — каналы `module-notifications` (`credentials` зашифрованы, наружу — только «задано»):
  секрет не уходит ни в ответ панели, ни в MCP, ни в журнал истории, ни в `toArray()`.
- `.env` остаётся запасным путём: `WEBX_USERS_GOOGLE_CLIENT_ID` и т. п. читаются, если в панели
  поле пустое (§9.3). Панель сильнее `.env`.

### Где что не лежит

- **Сессии** — общая таблица `sessions` сайта (или драйвер сессий сайта), без своих колонок.
- **Настройки** (обязательность полей, включена ли регистрация, лимиты писем) — в настройках сайта
  под ключами `users.*`, экран `users.settings` (§16.3), как `audit.settings` у аудита. Секреты
  провайдеров — только в `users_providers`.
- **Заказы, корзина, кошелёк** — в своих таблицах со своим `user_id` (§13).

## 4. Шов в `module-admin`: кто сейчас вошёл

Магазинные и любые другие модули должны спрашивать «кто посетитель» и работать без `module-users`.
Поэтому контракт и события живут в `module-admin`, от которого зависят все, а `module-users` — одна
из реализаций.

```php
namespace WebxUi\Admin\Visitors;

/** Who is signed in on the site. Bound to NullVisitors until a visitors module binds its own. */
interface Visitors
{
    /** The signed-in visitor of this request, or null for a guest. */
    public function current(): ?Visitor;

    public function find(int $id): ?Visitor;

    /** For a gift to another customer: an exact, normalised address; never a search. */
    public function findByEmail(string $email): ?Visitor;

    /** Where to send a guest who must sign in first; null — nowhere (no visitors module). */
    public function signInUrl(?string $back = null): ?string;
}

final readonly class Visitor
{
    public function __construct(
        public int $id,
        public string $email,
        public bool $verified,          // the e-mail is confirmed (§8)
        public ?string $firstName,
        public ?string $lastName,
        public ?string $phone,
        public ?string $locale,
        /** @var list<string> */
        public array $groups = [],      // group codes (§13.1)
    ) {}

    public function name(): string;    // first and last name, or the part of the e-mail before "@"
}
```

- **`NullVisitors`** — привязка по умолчанию (`singletonIf`, чужая побеждает): `current()` —
  `null`, `find*` — `null`, `signInUrl()` — `null`. `module-users` привязывает `UserVisitors`.
- **События** (`WebxUi\Admin\Visitors\Events`): `VisitorSignedIn(int $visitorId, string $method)`
  (`password`, `google`, …, `registration`, `reset`), `VisitorSignedOut(int $visitorId)`,
  `VisitorRegistered(int $visitorId, string $method)`, `VisitorDeleting(int $visitorId)` (§14.1).
  Событие бросается в том же запросе, где произошёл вход: слушатель (корзина) видит cookie гостя.
- **Middleware `webx.visitor`** (алиас регистрирует `module-admin`):
  - `webx.visitor` — нужен вошедший посетитель; гость — redirect на `signInUrl(текущий адрес)`,
    JSON — 401 `{code: "visitor.guest"}`; `signInUrl() === null` (нет модуля) — 404: возможности
    без посетителей на этом сайте нет;
  - `webx.visitor:verified` — то же плюс подтверждённый e-mail; неподтверждённый — страница
    «Подтвердите e-mail» со ссылкой «отправить ещё раз» (вьюха модуля посетителей, у `NullVisitors`
    не наступает), JSON — 403 `{code: "visitor.unverified"}`.
- **Blade:** `@visitor … @endvisitor`, `@visitorVerified … @endvisitorVerified` — для частей
  страницы, которые не кешируются целиком (§11.6).

Что модуль-владелец пишет, чтобы закрыть возможность для неподтверждённых (решение 9), — §8.4.

## 5. Гард и модель

- Гард **`site`** (`webx-users.guard`), драйвер `session`, провайдер `webx-users` (Eloquent,
  `WebxUi\Users\Models\User`). Провайдер дописывает гард и провайдер в `auth.guards` /
  `auth.providers` в `register()`, если сайт их не объявил сам. Гард по умолчанию (`web`) не
  трогается: код сайта, который зовёт `auth()->user()`, не получает посетителя молча. Ловушка из
  `laravel-and-php.md` («только `cms.auth` переключает гард») здесь та же: модуль везде называет гард
  по имени.
- `User` — `Authenticatable`, `MustVerifyEmail` (свой текст письма, §8), `HasExtra`,
  `HasTranslations` нет (переводить в посетителе нечего). Не реализует `HasPermissions`
  (правило 1 §2 спеки прав; тест держит).
- Пароль — `Hash::make`, правило — `Password::min(8)` с настройкой `webx-users.password_rules`
  (сайт ужесточает конфигом); `uncompromised()` — выключено по умолчанию (зовёт внешний сервис).
- E-mail нормализуется в мутаторе (обрезан, нижний регистр); уникальность — индексом и правилом.

## 6. Регистрация, вход, выход

### 6.1. Адреса

Все страницы — под приставкой `webx-users.prefix` (по умолчанию `account`), внутри `{locale?}` как
остальные маршруты сайта, с атрибутом `SiteRoutes::SERVICE` (не редактируются SEO-правилом, не
попадают в ссылки, `noindex`), ответ `Cache-Control: no-store`:

| Метод и адрес                                | Что                                                    |
| -------------------------------------------- | ------------------------------------------------------ |
| `GET/POST /account/sign-in`                  | вход                                                   |
| `GET/POST /account/register`                 | регистрация                                            |
| `POST /account/sign-out`                     | выход                                                  |
| `GET/POST /account/forgot`                   | запрос ссылки сброса                                   |
| `GET/POST /account/reset/{token}`            | страница нового пароля (§7)                            |
| `GET /account/verify/{id}/{hash}`            | подтверждение e-mail, подписанная ссылка (§8)          |
| `POST /account/verify/resend`                | отправить письмо ещё раз                               |
| `GET /account/email/{id}`                    | подтверждение нового адреса, подписанная ссылка (§8.5) |
| `GET /account/auth/{provider}`               | уход к провайдеру (§9)                                 |
| `GET/POST /account/auth/{provider}/callback` | возврат от провайдера; без языковой приставки (§9.4)   |
| `GET/POST /account/auth/complete`            | дозаполнить e-mail и обязательные поля после соцсети   |
| `GET /account`, `/account/profile`, …        | кабинет (§11)                                          |
| `GET /account/state`                         | JSON о вошедшем для кешируемых страниц (§11.6)         |

Вошедший на `sign-in` / `register` уходит в кабинет; гость в кабинете — на `sign-in` с возвратом.
Возврат (`intended`) принимается только относительным адресом своего сайта.

### 6.2. Формы

Формы — Blade из полей и оболочки `widgets` (`<x-webx-field>`, `<x-webx-form>`, §17
[`WEBX_UI_WIDGETS.md`](WEBX_UI_WIDGETS.md)): без JavaScript — обычный POST, с ним — отправка на
месте, ошибки 422 по полям, проверка в браузере по серверным правилам (`FormRules`), ответ —
`FormResponse::redirect()`. `autocomplete` — `email`, `current-password` / `new-password`,
`given-name`, `family-name`, `tel`: менеджер паролей и автозаполнение работают.

**Регистрация** — поля по порядку: имя, фамилия, телефон, e-mail, пароль, свои поля сайта с местом
`registration` (§10), согласие на обработку данных (`consent`, текст — настройка
`users.consent-text`; пустая — поля нет). Повтора пароля на регистрации нет (кнопка «показать» у
поля пароля); повтор — на странице сброса (решение 3). Обязательность имени, фамилии, телефона и
своих полей — по настройке (§10.5); e-mail и пароль — всегда. Под формой — кнопки провайдеров
(§9) и «Уже есть аккаунт? Войти».

После регистрации посетитель **сразу вошёл** (решение 9 — подтверждение не блокирует), получает
письмо подтверждения и уходит на `intended` или в кабинет. Бросаются
`VisitorRegistered` и `VisitorSignedIn` (`registration`).

**Вход** — e-mail, пароль, «Запомнить меня», «Забыли пароль?», кнопки провайдеров,
«Регистрация». Неверная пара — одна фраза на любой случай (нет адреса, нет пароля у аккаунта,
неверный пароль), §15.

**Выключатель регистрации** — настройка `users.registration` (`open` / `closed`): закрыто —
страница регистрации 404, кнопок «Регистрация» нет, соцсеть не создаёт новых аккаунтов (только
входит в существующие). Вход работает. Нужно сайту «только по приглашениям».

### 6.3. Заблокированный

`blocked_at` не пускает ни паролем, ни соцсетью, ни ссылкой сброса: вход отвечает своей фразой «Аккаунт
заблокирован, свяжитесь с магазином» — блок ставит администратор, и человек должен знать, куда
идти. Фраза отдаётся только на **верный** пароль или живую соцсеть: перебором блок не узнать.
Действующие сессии гаснут на следующем запросе (проверка в провайдере гарда).

## 7. Восстановление пароля

1. **Запрос** — `/account/forgot`, одно поле e-mail. Ответ всегда один: «Если аккаунт с этим адресом
   есть, мы отправили ссылку» — и на существующий адрес, и на несуществующий, и на заблокированный;
   время ответа выравнивается: письмо уходит очередью, а не в запросе (§15).
2. **Ссылка** — `/account/reset/{token}`, токен — 32 случайных байта base64url; в базе `sha256`
   (§3). Срок — `webx-users.reset_minutes` (60). Новая просьба заменяет прежнюю ссылку.
3. **Страница** — новый пароль и повтор (`confirmed`), правила пароля §5. Протухшая или
   использованная ссылка — та же страница с фразой «Ссылка устарела» и формой запроса новой.
4. **После смены:** строка ссылки удалена (одноразовость); `remember_token` и все прочие сессии
   посетителя гаснут (`Auth::logoutOtherDevices` по смыслу; сессии в базе — удаляются по
   `user_id`); посетитель вошёл; письмо «Пароль изменён» на адрес аккаунта.
5. **Сброс доказывает почту.** Аккаунт с неподтверждённым e-mail после сброса — подтверждён. И если
   до этого e-mail был неподтверждён, сброс **отвязывает все соцсети** аккаунта: иначе чужой, который
   зарегистрировал аккаунт на чужую почту и привязал свою соцсеть, сохранил бы вход после того, как
   владелец почты вернул себе аккаунт (защита от «предварительного захвата», §9.7).
6. Аккаунт без пароля (вошёл соцсетью) получает пароль тем же путём — так у него появляется второй
   способ входа.

## 8. Подтверждение e-mail

### 8.1. Письмо

- После регистрации по e-mail и после регистрации соцсетью, если провайдер не подтвердил адрес
  (§9.5), уходит письмо со ссылкой `/account/verify/{id}/{hash}` — подписанная (`temporarySignedRoute`),
  срок `webx-users.verify_hours` (72), `hash` — `sha1` текущего адреса: смена адреса гасит старые
  ссылки.
- Переход по ссылке подтверждает адрес **без входа**: ссылку открывают и на другом устройстве.
  Вошедший уходит в кабинет с фразой «E-mail подтверждён», гость — на страницу с той же фразой и
  кнопкой «Войти».
- Протухшая ссылка — страница «Ссылка устарела» с кнопкой «Отправить ещё раз» (для вошедшего) или
  входом (для гостя).

### 8.2. Повторная отправка

`POST /account/verify/resend` — только вошедшему неподтверждённому. Лимит —
`webx-users.verify_throttle`: не чаще раза в минуту и не больше 5 в час на посетителя; сверх —
429 с фразой «Письмо уже отправлено, попробуйте через N минут». Кнопка в баннере и в кабинете
после отправки показывает «Отправлено» и неактивна до конца минуты.

### 8.3. Баннер

Вошедшему неподтверждённому на каждой странице сайта — полоса «Подтвердите ваш e-mail: письмо
отправлено на a…@example.com» и ссылка «Отправить ещё раз». Узел `users.verify-banner` модуль
добавляет в композицию `layout` (первым ребёнком `main`, патч модуля); тема двигает или убирает его
патчем по `id`. Страница кешируется целиком, поэтому баннер печатается скрытым и показывается
скриптом по состоянию (§11.6); на страницах `no-store` (кабинет) — сразу сервером. Закрыть баннер
можно на сессию (крестик), навсегда — нельзя.

### 8.4. «Только для подтверждённых» — признак, а не правка `module-users`

Модуль-владелец возможности решает сам и пишет это у себя, через шов §4:

- **маршрут** — `->middleware('webx.visitor:verified')`; неподтверждённый видит «Подтвердите e-mail»
  со ссылкой повторной отправки, JSON — 403 `visitor.unverified`;
- **часть страницы** — `@visitorVerified … @else …кнопка «Подтвердите e-mail» @endvisitorVerified`;
- **в коде** — `app(Visitors::class)->current()?->verified`;
- **раздел кабинета** — `AccountSection(verified: true)` (§11.2): пункт меню виден, раздел
  открывает «Подтвердите e-mail» вместо содержимого.

Пример из решения — избранное: `module-favorites` ставит `webx.visitor:verified` на свои маршруты
записи; `module-users` о нём не знает. Оформление заказа такого признака не ставит (решение 9).

### 8.5. Смена e-mail

Новый адрес не подтверждён до перехода по ссылке. Как именно — по образцу смены адреса
администратора (`WebxUi\Auth\Profile\EmailChange`):

- в профиле посетитель вводит новый адрес и **текущий пароль** (у аккаунта без пароля — без него;
  тогда смену подтверждает только почта); адрес не должен быть занят другим аккаунтом;
- письмо уходит **на новый адрес** со ссылкой `/account/email/{id}` — подписанной, на 60 минут, с
  новым адресом и отпечатком прежнего; в базе до перехода ничего не меняется, вход — по прежнему
  адресу;
- переход по ссылке меняет `email`, ставит `email_verified_at = now()` (ссылку открыл владелец нового
  ящика — это и есть подтверждение), гасит ссылку сброса и остальные ссылки смены (отпечаток больше
  не совпадает); на **прежний** адрес уходит письмо «Адрес входа изменён»;
- в профиле до перехода — строка «Ждёт подтверждения: b…@example.com» с повторной отправкой.

Почему не «адрес меняется сразу, но неподтверждён»: опечатка в новом адресе запирала бы человека
вне аккаунта (вход — по адресу, на который не дойдёт ни одно письмо), а открытая чужая сессия
уводила бы аккаунт на чужой ящик. Так и решено (решение 16).

### 8.6. Где письма

Письма модуля — Mailable `WebxUi\Users\Mail\*` (подтверждение, сброс, приглашение, «пароль
изменён», «адрес входа изменён», «привязана соцсеть»), очередью, на языке посетителя (`locale`), с
вьюхами, которые перекрывает тема. Они работают без `module-notifications`: восстановление пароля
не может зависеть от необязательного модуля. Если `module-notifications` стоит, модуль объявляет
событие `users.registered` (адресат — администратор: «новый покупатель»), и только его; служебные
письма посетителю через каналы не идут. Пока транспорт почты пишет в лог (`log`, `array`) не на
локальной машине — `webx:doctor` предупреждает: регистрация обещает письмо, которое не уйдёт.

## 9. Соцсети

### 9.1. Реестр провайдеров

```php
namespace WebxUi\Users\Social;

interface Provider
{
    /** The key a visitor's identity and the settings store: `google`. [a-z0-9-] */
    public function key(): string;

    /** A dictionary key or plain words: "Google". */
    public function label(): string;

    /** An icon for the button: a view name the theme may override. */
    public function icon(): string;

    /**
     * The settings an administrator fills in the panel: secret ones go to `credentials`,
     * encrypted and never given back; the others to `options`.
     *
     * @return list<Field>
     */
    public function fields(): array;

    /**
     * Whether the module may trust the provider's "this e-mail is verified" and link the provider
     * to an existing account with that address without a password (§9.7). False for a provider
     * that does not say it, or says it carelessly.
     */
    public function trustsVerifiedEmail(): bool;

    /** Where the provider sends the visitor back; shown in the panel to copy into its console. */
    public function callbackUrl(): string;

    /** Send the visitor to the provider. `state` is the module's own, checked on the way back. */
    public function redirect(ProviderConfig $config, string $state): RedirectResponse;

    /**
     * Who came back. Throws ProviderFailed with a dictionary key when the provider refused, the
     * visitor cancelled, or the answer is broken.
     */
    public function profile(ProviderConfig $config, Request $request): SocialProfile;
}

final readonly class SocialProfile
{
    public function __construct(
        public string $id,                 // the provider's stable id of the person
        public ?string $email,             // null when the provider did not give one
        public bool $emailVerified,        // true only when the provider says so explicitly
        public ?string $firstName = null,
        public ?string $lastName = null,
        public ?string $phone = null,
    ) {}
}

final readonly class ProviderConfig
{
    /** @param array<string, mixed> $options  @param array<string, mixed> $credentials */
    public function __construct(public array $options, public array $credentials) {}

    public function get(string $name): mixed;   // options, then credentials, then the .env fallback
}
```

- `Field` — общий класс `module-admin` `WebxUi\Admin\Support\Field` (решение 21, этап 7): форма
  прежнего `WebxUi\Notifications\Sending\Field` (`name`, `label`, `secret`, `kind`, `choices`,
  `default`) и `required` — без него провайдер не показывается (§9.3); `module-notifications` на
  нём, копии нет. Поле секрета в панели — «задано / заменить», никогда не значение.
- **Регистрация:** `SocialProviders::register(Provider $provider)` в `boot()` пакета или сайта.
  Ключ повторно — исключение. Модуль не правится, чтобы подключить провайдера (решение 2).
- **Реализация** — поверх `laravel/socialite` (зависимость `module-users`): базовый класс
  `SocialiteProvider` берёт драйвер Socialite, подставляет ключи из `ProviderConfig` и адрес
  возврата, выключает его собственный `state` (у модуля свой, §9.4) и переводит ответ в
  `SocialProfile`. Провайдер, которого нет в Socialite, реализует контракт сам.
- **Из коробки:** `GoogleProvider` (поля `client_id`, `client_secret`; `emailVerified` — из
  `email_verified` ответа; `trustsVerifiedEmail()` — `true`) и `FacebookProvider` (`app_id`,
  `app_secret`; Facebook не сообщает, проверен ли адрес, — `emailVerified = false`, письмо
  подтверждения уходит как обычно, решение 9; `trustsVerifiedEmail()` — `false`).

**Пример нового провайдера — Apple** (в гайде, не в модуле): пакет сайта ставит драйвер Apple для
Socialite из сообщества и регистрирует класс с полями `client_id` (Services ID), `team_id`, `key_id`
и секретом `private_key`; особенности, которые контракт уже выдерживает: Apple возвращает POST на
адрес возврата (маршрут возврата принимает `POST` и стоит вне CSRF — его защищает `state`), отдаёт
имя только при первом входе (берётся в `SocialProfile` тогда же), может отдать адрес-пересыльщик
(`…@privaterelay.appleid.com`) — это обычный e-mail аккаунта, подтверждённый (`email_verified`).

### 9.2. Кнопки

Под формами входа, регистрации и в диалоге оформления (§12) — по кнопке на каждый **показываемый**
провайдер, в порядке реестра (сайт меняет конфигом `webx-users.social.order`). Компонент
`<x-webx-users::social-buttons />`, вьюха кнопки перекрывается темой; иконка — вьюха провайдера.

### 9.3. Ключи и «показывается ли»

- Ключи — экран `users.settings`, вкладка «Вход через соцсети» (§16.3): переключатель, поля
  провайдера, адрес возврата с кнопкой «Скопировать», ссылка на консоль провайдера (из словаря
  провайдера).
- Значение поля: панель → `.env` (`WEBX_USERS_<KEY>_<FIELD>`) → нет. Провайдер **показывается**,
  только если включён в панели (или включён в `.env` флагом `WEBX_USERS_<KEY>_ENABLED`, пока в
  панели строки нет) и **все** его обязательные поля заданы. Иначе нет ни кнопки, ни маршрута
  (`/account/auth/{provider}` — 404), а экран настроек говорит, чего не хватает.
- Секреты не показываются нигде: ни в ответе экрана, ни в MCP (§17), ни в журнале истории (запись —
  «секрет изменён»), ни в `webx:doctor`.

### 9.4. Поток входа

1. `GET /account/auth/{provider}` — модуль кладёт в сессию `state` (32 случайных байта), язык
   страницы, `intended` и **намерение**: `sign-in` (вход или регистрация) или `link` (привязка из
   кабинета, только вошедшему). Уходит к провайдеру.
2. `GET|POST /account/auth/{provider}/callback` — один адрес на все языки (его прописывают в консоли
   провайдера). `state` не совпал или истёк — «Не удалось войти, попробуйте ещё раз», никаких
   действий. Провайдер отказал или посетитель отменил — та же фраза и возврат на форму входа.
3. Найти посетителя по (`provider`, `id`):
   - **нашёлся** — вход (если не заблокирован), `last_used_at`; `VisitorSignedIn($id, $provider)`;
   - **не нашёлся** — §9.5 (новый аккаунт) или §9.7 (адрес уже занят).
4. Возврат — на `intended` с языком из сессии.

### 9.5. Регистрация через соцсеть

- Регистрация открыта (§6.2) и адрес свободен — аккаунт создаётся с данными провайдера: e-mail, имя,
  фамилия (телефон — если отдал). Пароля нет. `email_verified_at` — `now()`, если
  `emailVerified`, иначе `null` и письмо подтверждения (§8.1).
- **Провайдер не отдал e-mail** или не хватает обязательных по настройке полей (телефон, свои поля
  с местом `registration`) — страница `/account/auth/complete`: «Почти готово» с недостающими
  полями. Аккаунт не создаётся, пока она не отправлена: профиль провайдера лежит в сессии 15 минут.
  Введённый вручную адрес — неподтверждённый, письмо уходит. Введённый адрес занят — §9.7.
- Согласие на обработку данных (если настроено) — на той же странице «Почти готово»: соцсеть его не
  даёт.

### 9.6. Привязка и отвязка в кабинете

- Раздел «Вход и безопасность» (§11.1): список показываемых провайдеров — «Привязан (адрес, дата)
  · Отвязать» или «Привязать». Привязать — тот же поток с намерением `link`; `id` у провайдера уже
  привязан к **другому** аккаунту — отказ «Этот аккаунт Google уже связан с другим профилем»,
  ничего не переносится.
- После привязки — письмо «Привязан вход через Google» на адрес аккаунта: если это сделал не
  владелец, он узнает.
- **Последний способ входа не отвязывается** (решение 5): отвязка разрешена, только если после неё
  остаётся пароль или другая привязка. Иначе кнопка «Отвязать» неактивна с подсказкой «Задайте
  пароль, чтобы отвязать последний способ входа» и ссылкой на установку пароля; сервер отвечает 422
  тем же словом (проверка на сервере, а не только кнопкой).
- Провайдер выключили в панели — привязка остаётся в базе, но не считается способом входа: войти
  ею нельзя. Поэтому правило «последний способ» считает только **показываемых** провайдеров плюс
  пароль, а экран провайдера в панели предупреждает: «N посетителей входят только через Google;
  после выключения войдут сбросом пароля» (адрес у каждого есть).
- **Установка пароля** аккаунту без пароля — в том же разделе: «Задать пароль» отправляет письмо со
  ссылкой сброса (§7) на адрес аккаунта. Не форма «новый пароль» на месте: у соцаккаунта с
  неподтверждённым адресом это был бы способ закрепиться в чужом аккаунте.

### 9.7. Совпадение адреса: как не захватить чужой аккаунт

Провайдер вернул адрес, на который уже есть аккаунт, а связи (`provider`, `id`) нет. «Проверен» ниже —
провайдер сказал, что адрес проверен (`SocialProfile::$emailVerified`), **и** провайдер в реестре
этому доверяет (`trustsVerifiedEmail()`, §9.1; решение 14). Правила:

| Наш аккаунт          | Адрес провайдера «проверен» | Что делаем                                                                                                 |
| -------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------- |
| адрес подтверждён    | да                          | **связываем сами:** привязка, вход без пароля, письмо «Привязан вход через Google» на адрес аккаунта       |
| адрес подтверждён    | нет                         | **не связываем сами.** «Аккаунт с этим адресом уже есть. Войдите паролем — и вход через Google привяжется» |
| адрес не подтверждён | нет                         | то же                                                                                                      |
| адрес не подтверждён | да                          | то же (решение 23)                                                                                         |

- **Связываем сами** (решение 14). Провайдер, которому модуль доверяет, ручается, что вошедший
  владеет ящиком, а наш аккаунт на этот ящик подтверждён — это один человек. Привязка создаётся,
  вход — как обычной привязкой (`VisitorSignedIn($id, $provider)`), письмо «Привязан вход через
  Google» уходит на адрес аккаунта: если это был не владелец, он узнает. Пароль, прежние привязки и
  сессии не трогаются. Заблокированный аккаунт — не связывается и не входит (§6.3).
- **«Войдите — и привяжется».** Провайдер без отметки «проверен» или без доверия (Facebook): профиль
  провайдера остаётся в сессии 15 минут; успешный вход паролем в **этот же** аккаунт в той же сессии
  привязывает его и пишет письмо «Привязан вход через Google». Вход в другой аккаунт или истечение —
  привязки нет.
- **Почему без доверия не связываем по совпадению адреса.** Тот, кто завёл аккаунт у провайдера на
  чужой адрес (у Facebook адрес не обязательно проверен), иначе вошёл бы в чужой магазинный аккаунт.
- **Наш адрес не подтверждён — не связываем сами, даже с доверенным провайдером** (решение 23).
  Такой аккаунт мог завести кто угодно на чужую почту (предварительный захват), поэтому соцсеть к
  нему привязывается только входом паролем. Владелец почты возвращает аккаунт сбросом пароля: сброс
  подтверждает адрес и отвязывает все соцсети неподтверждённого аккаунта (§7, п. 5). Захват
  аккаунта владельцем почты прямо из потока соцсети — в §20.
- Тот же принцип в другом месте: регистрация по e-mail, когда адрес занят, отвечает «Адрес уже зарегистрирован — войдите
  или восстановите пароль» (решение 15: ответ честный, защита — лимит §15).

## 10. Свои поля сайта

### 10.1. Контракт поля

```php
namespace WebxUi\Users\Fields;

enum Placement: string
{
    case Registration = 'registration';   // the sign-up form and the "almost done" page (§9.5)
    case Profile = 'profile';             // the account's profile page
    case Panel = 'panel';                 // the visitor's card in the panel and MCP
}

final readonly class UserField
{
    /**
     * @param  string  $type  a FieldTypes key: 'wx-input', 'wx-select', 'wx-date-picker', …
     * @param  array<string, mixed>  $props  the screen node's props: options, `type: email`, …
     * @param  list<Placement>  $placements
     * @param  list<string>  $rules  extra Laravel rules on top of the type's: 'max:40', 'regex:…'
     */
    public function __construct(
        public string $name,                       // the key in `extra`: [a-z0-9-], not a column name
        public string $type,
        public string $label,                      // a dictionary key or plain words
        public array $props = [],
        public bool $required = false,             // the default; the panel setting overrides (§10.5)
        public array $placements = [Placement::Registration, Placement::Profile, Placement::Panel],
        public array $rules = [],
        public bool $unique = false,               // no two visitors with the same value
        public bool $visitorEditable = true,       // false: shown in the profile, changed in the panel only
        public ?string $hint = null,
        public int $position = 100,
        public ?string $source = null,             // who declared it: a module id or 'site'
    ) {}
}

final class UserFields
{
    public function register(UserField ...$fields): void;   // a module, in boot()

    /** @return list<UserField>  in `position` order, then the order of registration */
    public function all(): array;

    /** @return list<UserField> */
    public function for(Placement $placement): array;

    public function get(string $name): ?UserField;
}
```

- **Кто объявляет.** Модуль — `UserFields::register()` в `boot()`, если `module-users` стоит
  (`class_exists`, `suggest`). Сайт — без PHP-класса, в конфиге `webx-users.fields` (массив тех же
  ключей; `rules` — только строками, чтобы конфиг кешировался) или тем же вызовом из провайдера сайта.
- **Проверки при регистрации поля** (исключение, а не молчание): имя занято встроенной колонкой
  (`email`, `phone`, `first_name`, …) или другим полем; тип не знаком `FieldTypes`; `select` /
  `radio-group` без `options`.
- Пример — клубная карта, которую заводит администратор, а посетитель только видит, и дата рождения
  в регистрации:

```php
app(UserFields::class)->register(
    new UserField('club-card', 'wx-input', 'Club card', unique: true, visitorEditable: false,
        placements: [Placement::Profile, Placement::Panel], rules: ['regex:/^[0-9]{6,12}$/']),
    new UserField('birthday', 'wx-date-picker', 'Date of birth',
        placements: [Placement::Registration, Placement::Profile, Placement::Panel], rules: ['before:today']),
);
```

### 10.2. Типы

Тип поля — ключ `FieldTypes` экранов панели ([`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md) §6.2): его
`rules()` и `store()` проверяют и приводят значение везде одинаково — с сайта, из панели, из MCP;
`resolve()` отдаёт его сайту. Для формы сайта у типа должна быть пара в полях `widgets`:

| `FieldTypes`                                  | `<x-webx-field type>`            |
| --------------------------------------------- | -------------------------------- |
| `wx-input` (`props.type`: text/email/tel/url) | `text` / `email` / `tel` / `url` |
| `wx-textarea`                                 | `textarea`                       |
| `wx-input-number`                             | `number`                         |
| `wx-switch`, `wx-checkbox`                    | `checkbox` (одна галочка)        |
| `wx-select`, `wx-segmented`, `wx-radio-group` | `select` / `select` / `radio`    |
| `wx-checkbox-group`                           | `checkbox` с `:choices`          |
| `wx-date-picker`                              | `date`                           |

Остальные типы (медиа, цвет, повторитель, дерево …) — **только с местом `panel`**: посетитель их на
сайте не заполняет. Поле с таким типом и местом `registration` / `profile` — исключение при
регистрации и строка `webx:doctor`. Тип, который добавит проект (`FieldTypes::register('map', …)`),
на сайт попадает, когда проект зарегистрирует ему пару: `UserFields::siteType('map', 'text')`.

### 10.3. Где хранятся: колонка `extra`

Значения своих полей — в `users.extra` (json), механизмом «полей проекта» `module-admin`
(`HasExtra`, `ScreenRecord`, [`WEBX_UI_MODULE_SERVICES.md`](WEBX_UI_MODULE_SERVICES.md) §3.4).
Почему не своя таблица «поле — значение»:

- **один механизм на весь проект:** у услуг, команды, статей поля проекта уже лежат в `extra`; тот же
  `ScreenRecord` раскладывает экран посетителя, тот же `extra('club-card')` читает Blade, MCP пишет
  под тем же именем — новой подсистемы нет;
- **запись посетителя читается одним запросом:** кабинет, карточка панели и MCP не делают JOIN на
  каждое поле и не собирают значения строками;
- **поле убрали — данные не мешают:** значение остаётся в `extra` и ничего не ломает (как у полей
  проекта), чистить — дело сайта;
- **цена:** фильтр и сортировка списка панели по своему полю и проверка `unique` идут по
  `JSON_EXTRACT` без индекса. Для тысяч и десятков тысяч посетителей это приемлемо; сайту, которому
  нужен быстрый поиск по клубной карте, модуль даёт команду `webx:users:index-field club-card` —
  виртуальная колонка `extra_club_card` и индекс на неё отдельной миграцией сайта (этап 4, §19;
  до тех пор `unique` проверяется запросом под блокировкой записи).

`unique` — проверка при сохранении (`ScreenRecord` и форма сайта) с понятной ошибкой «Это значение
уже занято»; гонка двух одновременных записей — допустимый риск без индекса.

### 10.4. Куда попадает поле

| Место                            | Как                                                                                                                                                                           |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **регистрация**                  | вьюха формы печатает `UserFields::for(Registration)` через `<x-webx-field>` после встроенных полей; правила — из `FieldType::rules()` + `rules` поля + обязательность (§10.5) |
| **«почти готово»** после соцсети | те же поля, если обязательны и пусты (§9.5)                                                                                                                                   |
| **профиль**                      | `for(Profile)`; `visitorEditable: false` — значение текстом, без поля; сервер такие ключи из запроса посетителя отбрасывает                                                   |
| **панель**                       | `for(Panel)` — узлами в карточке `project-fields` экрана `users.form` (сервер добавляет их в дерево при отдаче экрана, патч сайта не нужен); `required` — то же правило       |
| **MCP**                          | `users_get` отдаёт `fields: {name: value}`, `users_update` принимает их под теми же именами и проверяет теми же правилами; ресурс `users://catalog` перечисляет поля с типами |
| **Blade сайта**                  | `$user->extra('club-card')` — разрешённое типом значение                                                                                                                      |

Поле, добавленное сайтом патчем экрана `users.form` напрямую (как у услуг), тоже сохранится в
`extra` — но на сайт и в MCP-описание не попадёт: для этого его объявляют контрактом. Гайд говорит
это прямо.

### 10.5. Обязательность — настройка

Экран `users.settings`, вкладка «Регистрация и профиль» (§16.3): по строке на каждое поле, которое
посетитель заполняет сам, — встроенные `first_name`, `last_name`, `phone` и свои поля с местом
`registration` или `profile`:

| Значение   | Регистрация           | Профиль                             |
| ---------- | --------------------- | ----------------------------------- |
| `hidden`   | поля нет              | поля нет                            |
| `optional` | есть, «необязательно» | есть                                |
| `required` | есть, обязательно     | есть, обязательно (очистить нельзя) |

- Хранится в настройках сайта `users.fields.<name>` (`hidden` / `optional` / `required`).
  Умолчание: встроенные — `optional`; своё поле — по его `required` (`required` или `optional`).
  `email` и пароль в списке не стоят — они обязательны всегда.
- Поле, ставшее обязательным позже, не запирает старых посетителей: профиль просит заполнить его
  при следующем сохранении, а вход и заказ работают. Оформление заказа решает своё обязательное само.
- Подписи и порядок полей — не настройка (порядок — `position`, вид — тема).

## 11. Кабинет

### 11.1. Страницы

| Адрес               | Раздел              | Что                                                                                                                                             |
| ------------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `/account`          | —                   | redirect на первый раздел меню (по умолчанию — профиль)                                                                                         |
| `/account/profile`  | Профиль             | имя, фамилия, телефон, свои поля с местом `profile`; e-mail со сменой (§8.5); баннер подтверждения                                              |
| `/account/security` | Вход и безопасность | пароль (смена с текущим или «Задать пароль» письмом, §9.6); соцсети: привязка и отвязка; «Выйти на всех устройствах»; удаление аккаунта (§14.1) |

Это весь кабинет без магазина (решение 7). Смена пароля на месте — текущий пароль, новый и повтор;
после — остальные сессии гаснут, письмо «Пароль изменён».

### 11.2. Реестр разделов кабинета

```php
namespace WebxUi\Users\Account;

final readonly class AccountSection
{
    public function __construct(
        public string $id,                 // 'orders' — also the composition node id: account.menu.orders
        public string $label,              // a dictionary key: 'webx-orders::account.menu'
        public string $route,              // a route name: 'webx.orders.account.index'
        public string $icon = 'circle',    // an icon of the theme's set
        public int $position = 100,        // profile — 10, security — 90: shop sections fall between
        public bool $verified = false,     // needs a confirmed e-mail (§8.4)
        public ?string $active = null,     // a route name pattern that lights the item: 'webx.orders.account.*'
        public ?Closure $badge = null,     // fn (Visitor $v): ?string — a counter: "2" active orders
    ) {}
}

final class AccountMenu
{
    public function register(AccountSection $section): void;   // a module, in boot()

    /** @return list<AccountSection>  in position order; `active` resolved against the request */
    public function for(Visitor $visitor): array;
}
```

- **Как модуль добавляет раздел** — `module-orders` (пример):

```php
if (class_exists(AccountMenu::class)) {
    app(AccountMenu::class)->register(new AccountSection(
        id: 'orders', label: 'webx-orders::account.menu', route: 'webx.orders.account.index',
        icon: 'package', position: 30, active: 'webx.orders.account.*',
    ));
    AccountRoutes::group(function () {
        Route::get('orders', [AccountOrdersController::class, 'index'])->name('webx.orders.account.index');
        Route::get('orders/{order}', [AccountOrdersController::class, 'show'])->name('webx.orders.account.show');
    });
}
```

- **`AccountRoutes::group(Closure)`** объявляет маршруты под приставкой кабинета, внутри
  `{locale?}`, с middleware `web`, `webx.visitor`, `SiteRoutes::SERVICE` и `no-store` — модуль не
  повторяет их и не ошибается в одном из пяти.
- «Мои заказы» появляется, только если стоит `module-orders`; кошелёк — только с `module-wallet`:
  они сами регистрируют раздел (решение 7). Ни `module-users`, ни тема их не перечисляют.
- `badge` зовётся только для показа меню и одним запросом модуля-владельца (бюджет кабинета держит
  `PerformanceTest`, §18).
- Сайт убирает раздел конфигом `webx-users.account.hidden` (`['wallet']`) или патчем композиции по
  `id` узла.

### 11.3. Вкладки карточки посетителя в панели

Тот же принцип в панели: модуль заказов добавляет вкладку «Заказы» в экран `users.form` патчем
экрана (`ScreenRegistry` патчи модулей, [`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md) §5) с узлом,
который сам и рисует (`wx-orders-list` с `filter: {user: …}`). У экрана — публичные `id` для
этого: `tabs` (вкладки), `summary` (карточка сбоку: «Заказов: 12», баланс кошелька). Модуль users
не знает, какие вкладки есть.

### 11.4. Layout — композиция `layout.account`

- Страницы кабинета зовут layout с хендлом **`users.account`**: `<x-dynamic-component
:component="config('webx-users.layout') ?: 'layout.account'" handle="users.account">`. Модуль
  объявляет хендлы `Compositions::handles('users', ['users.account', 'users.auth'])`.
- `layout.account` (формат — §3.7 спеки композиций) строит `account` с `account.menu` и
  `account.body`. **Меню** — патч модуля `layout.account/default.json`: в `account.menu` встаёт
  компонент `webx-users::account-menu` (пункты из `AccountMenu::for()`, активный, бейджи, «Выйти»).
  Если `layout.account` в теме ещё нет — модуль кладёт его базу сам (своим слоем), тема перекрывает.
- **Страницы входа, регистрации, сброса** — хендл `users.auth`, по умолчанию `layout` (узкая
  карточка формы по центру — вьюха модуля); сайт ставит `layout.minimal` конфигом
  `webx-compositions.layouts`.
- Раздел модуля внутри кабинета — обычный вид модуля с тем же вызовом layout (`handle="users.account"`):
  меню и сетка у всех разделов одни.

### 11.5. Вид

Разметка — поля и формы `widgets`, карточки и меню — классы `webx-account*`
(`webx-account__menu`, `__item`, `is-active`, `__badge`, `__section`, `__title`), стили — на
`--site-*` в `account.css` модуля, грузится только на страницах модуля. Вид «как у крупного
маркетплейса, упрощённо» — меню слева на широком контейнере, сверху списком на узком
(`@container`, а не медиа-запрос), карточки разделов; остальное — тема. Проверка — в браузере, 360 px
и тёмная схема (CLAUDE.md §3, §5).

### 11.6. Кешируемые страницы и вошедший

Страницы сайта кешируются целиком (решение 8 спеки inbox), поэтому **ничего личного в общий HTML не
печатается**:

- модуль ставит cookie `webx_visitor` (не httpOnly, без данных: `1` — вошёл, `u` — вошёл, адрес не
  подтверждён) при входе и снимает при выходе; скрипт `users.js` (≈1 КБ, с любой страницы, где
  есть узлы модуля) по ней показывает скрытые заранее части: «Войти» ↔ «Кабинет», баннер §8.3;
- имя в шапке и счётчики — `GET /account/state` (`no-store`, JSON: `signedIn`, `name`, `verified`,
  `email` — маской), только если cookie есть: гость не делает ни одного запроса;
- кабинет, вход, оформление — `no-store`, там сервер печатает всё сам;
- компонент шапки `<x-webx-users::header-link />` — «Войти» / «Кабинет»; `theme-default` ставит его в
  `actions` шапки, если модуль стоит (как триггер корзины).

## 12. Вход в оформлении заказа

### 12.1. Диалог входа

`<x-webx-users::sign-in-dialog />` — `<x-webx-dialog>` (§6 и §17.3 спеки виджетов) с тремя видами
внутри одного окна, переключаемыми без перезагрузки:

1. **Вход** — e-mail, пароль, «Запомнить меня», кнопки провайдеров, «Забыли пароль?»,
   «Регистрация»;
2. **Забыли пароль** — поле e-mail, ответ «Если аккаунт есть, мы отправили ссылку» на месте; ссылка
   из письма открывает обычную страницу сброса (§7), после неё — возврат на оформление
   (`intended`);
3. **Регистрация** — та же форма, что на странице (§6.2), со своими полями сайта.

- Открывающий — `data-webx-sign-in` или ссылка `#webx-sign-in`; окно печатается одно на страницу,
  если на ней есть открывающий (как формы в окне, §6.4 спеки виджетов). Без JavaScript ссылка ведёт
  на `/account/sign-in?back=<текущий адрес>` — страница входа с возвратом.
- **Без ухода со страницы:** вход и регистрация отвечают `FormResponse` — диалог закрывается,
  бросается событие `webx:users:signed-in` (`detail`: имя, `verified`) на `document`, а следом —
  перезагрузка текущей страницы, **если** никто не отменил событие. Оформление, которому нужно
  обновиться на месте, отменяет его и перерисовывает шаг сам (`html` в ответе формы). Слушать
  событие — дело `module-checkout`.
- **Соцсеть** уводит к провайдеру — без этого OAuth не работает — и возвращает на ту же страницу
  оформления (`intended` = текущий адрес). Корзина при этом не теряется: она на сервере.
- Регистрацию гостю не навязываем (решение 8): диалог открывается кнопкой «Войти» оформления, а
  не сам.

### 12.2. Что `module-users` отдаёт оформлению

Только через шов `module-admin` (§4) — `module-checkout` не зависит от `module-users`:

- `Visitors::current()` → `Visitor` с `firstName`, `lastName`, `phone`, `email`, `verified`,
  `groups` — оформление подставляет контакты профиля в свои поля, покупатель может поменять их для
  этого заказа (например, телефон). Правка в заказе **не** меняет профиль, галочки «обновить
  профиль» нет (решение 18): профиль правится только в кабинете.
- `Visitors::signInUrl($back)` — адрес входа для гостя без JavaScript.
- `VisitorSignedIn` — корзина сливает гостевую (§13.3), оформление может пересчитать цены групп.
- Компонент диалога и кнопка `<x-webx-users::sign-in-button />` — оформление ставит их в свой шаг,
  если `module-users` стоит (`class_exists`), иначе шаг без входа.

## 13. Точки подключения для магазина

### 13.1. Группы

- Группы — в `module-users` (таблицы §3): это свойство посетителя, а не корзины. Связь многие ко
  многим: «оптовый» и «клуб» — разные оси, и правило «скидка клубу» не должно знать про опт.
- Группа — код и название на одном языке (решение 24): переводов, групп «по умолчанию» для новой
  регистрации и ручного порядка нет.
- Назначает администратор (карточка посетителя), MCP (`users_update`) и код модулей
  (`$user->groups()->attach()`).
- Наружу — коды групп в `Visitor::$groups` (§4): правилам корзины не нужна модель `module-users`.
- Удаление группы никто не останавливает: связи с посетителями уходят каскадом, правило, которое
  называет удалённый код, просто перестаёт с ним совпадать. Отказ слушателей при удалении — §20.

### 13.2. Поле условий

Когда конструктор условий появится в `module-admin` (`WEBX_UI_CONDITIONS.md`, карта коммерции §5),
`module-users` регистрирует в его реестре поле «Группа посетителя» (`users.group`, оператор «в
любой из», варианты — группы) и «Посетитель вошёл» (`users.signed_in`). Значение поле берёт из
`Visitors::current()`, а не из корзины: `CartContext` о посетителе не знает. Пока конструктора нет —
ничего не регистрируется (проверка `class_exists`), этап реализации — после конструктора (§19).

### 13.3. Слияние гостевой корзины

Код — в `module-cart` (его таблица и его правила слияния, решение 18 спеки корзины); здесь — что
`module-users` даёт и как договорились:

- **Привязка** — колонка `carts.user_id` (bigint, null, unique, без FK: `module-users` может не
  стоять) — миграция `module-cart`. Своей таблицы связи у users нет: связь «корзина — владелец»
  принадлежит корзине.
- **Вход** — `module-cart` слушает `VisitorSignedIn` (класс из `module-admin`, без зависимости от
  users): есть гостевая корзина по cookie и есть корзина аккаунта — строки гостевой **добавляются**
  в корзину аккаунта (одинаковые строки складываются, как решение 18; дети не сливаются), гостевая
  удаляется, cookie переключается на корзину аккаунта. Корзины аккаунта нет — гостевая получает
  `user_id`. Это «слияние с корзиной аккаунта» из решения 10.
- **Выход** — `VisitorSignedOut`: cookie корзины снимается, гость начинает с пустой; корзина
  аккаунта ждёт следующего входа.
- **Удаление аккаунта** — `VisitorDeleting`: корзина аккаунта удаляется.
- Этап — 13 в задаче реализации webx-ui#88, после этапа 11 (§19, решение 27); отложенный вопрос 2
  §15 спеки корзины закрывается этим разделом.

### 13.4. История заказов, кошелёк, сертификаты

- **Заказы** хранят `user_id` (null — гость) из `Visitors::current()` при создании; раздел кабинета
  и вкладку карточки регистрируют сами (§11.2, §11.3). Прежние гостевые заказы на тот же адрес к
  аккаунту сами не привязываются — менеджер привязывает их в панели (решение 17).
- **Кошелёк** — владелец партий — `user_id` посетителя; раздел кабинета «Кошелёк» — сам.
- **Подарок сертификата другому покупателю** — `Visitors::findByEmail()`: нашёлся — партия в его
  кошелёк, нет — код письмом. Это единственный поиск посетителя по адресу наружу; он точный, не
  поиск по подстроке, и `module-certificates` не показывает дарителю, нашёлся ли получатель.

## 14. Приватность и удаление

### 14.1. Удаление аккаунта

- **Сам посетитель** — «Удалить аккаунт» в «Вход и безопасность»: подтверждение текущим паролем
  (у аккаунта без пароля — вводом своего адреса), предупреждения модулей, кнопка «Удалить навсегда».
- **Предупреждения** — реестр `DeletionWarnings::register(Closure(Visitor): ?string)`: кошелёк говорит
  «Баланс 1 250,00 будет потерян», заказы — «Активный заказ №… будет выполнен, но вы не увидите его
  в кабинете». users не знает, кто предупреждает.
- **Что происходит** (одна транзакция): `VisitorDeleting($id)` — слушатели отвязывают или обезличивают
  своё (заказы — `user_id = null`, снимок контактов в заказе остаётся: это документ сделки; корзина
  — удаляется; кошелёк — по своей спеке); затем строка `users` удаляется **физически**, привязки,
  ссылки сброса и группы — каскадом; сессии посетителя удаляются; письмо «Аккаунт удалён» на адрес,
  который был.
- **Администратор** — то же действием в карточке и `users_delete` в MCP (с `dry_run`): «что
  случится» — список предупреждений.
- Мягкого удаления нет: аккаунт, удалённый по просьбе человека, не должен восстанавливаться. Тот же
  адрес может зарегистрироваться заново — это новый аккаунт.

### 14.2. Что храним и не храним

- Не храним: IP и устройство входов, токены провайдеров, пароли в открытом виде (только хеш),
  токены сброса (только хеш).
- `last_sign_in_at` — для администратора («давно не заходил»), без журнала входов. Журнал входов
  посетителей (как `cms_login_records` у администраторов) — не в первой версии.
- Посетитель видит и правит всё, что о нём хранит модуль: профиль, свои поля (кроме
  `visitorEditable: false` — их видит), привязки. Выгрузки своих данных одним файлом в первой версии
  нет (решение 19, §20).

### 14.3. Чистка

`php artisan webx:users:prune [--dry-run]` — в расписании `daily()` (как `webx:cart:prune`):
протухшие ссылки сброса и приглашений. Неподтверждённые аккаунты не удаляются: решение 9 разрешает
им заказы, а чистка таких аккаунтов в первую версию не входит (решение 23, §20).

## 15. Защита от перебора

| Действие                         | Ключ лимита              | Лимит (умолчание, `webx-users.throttle.*`) | Ответ сверх                                                       |
| -------------------------------- | ------------------------ | ------------------------------------------ | ----------------------------------------------------------------- |
| вход паролем                     | e-mail + IP; отдельно IP | 5 в минуту на пару; 30 в минуту на IP      | 429 «Слишком много попыток, подождите N с»                        |
| регистрация                      | IP                       | 5 в час                                    | 429                                                               |
| запрос сброса                    | e-mail + IP; отдельно IP | 3 в час на пару; 20 в час на IP            | тот же ответ «если аккаунт есть…» (сверх лимита письмо не уходит) |
| страница сброса (POST)           | IP                       | 10 в минуту                                | 429                                                               |
| повторная отправка подтверждения | посетитель               | 1 в минуту, 5 в час                        | 429 с минутами                                                    |
| смена e-mail                     | посетитель               | 3 в час                                    | 429                                                               |
| уход к провайдеру                | IP                       | 20 в минуту                                | 429                                                               |
| диалог входа                     | те же ключи, что вход    |                                            |                                                                   |

- **Единые ответы:** вход — «Неверный e-mail или пароль» на любой отказ; на несуществующий адрес
  `Hash::check` всё равно выполняется с подставным хешем — время ответа не выдаёт адрес. Сброс — один
  ответ всегда (§7). Повторная отправка подтверждения — только вошедшему, адрес не принимается.
- Регистрация раскрывает занятость адреса — так решено (решение 15); от перебора адресов её держит
  лимит регистраций выше.
- Неудачные входы — событие `VisitorSignInFailed` (без пароля и без адреса в открытом виде — хеш
  адреса) для будущих сигналов; журнала нет.
- CSRF — на всех формах (оболочка `widgets` обновляет протухший токен сама); возврат провайдера
  защищён `state`, а не CSRF (§9.4).
- `AccessCoverageTest`: публичные маршруты модуля — в списке открытых с причиной «вход посетителя»
  и лимитом.

## 16. Панель

Раздел «Клиенты» (решение 20): слово по умолчанию — ключ `module.title` словаря `webx-users` на всех
языках (en «Customers», ru «Клиенты» …), сайт меняет его словом своего словаря. Id модуля, права,
таблицы, MCP — `users`. Экраны —
JSON ([`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md)); npm-пара `@webx-ui/module-users` регистрирует
раздел. Каждое изменение — в журнал истории (`webx.history`), секреты — словом «изменён».

### 16.1. Права

| Право            | Что даёт                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `users.view`     | список, карточка, группы — чтение; MCP `users:read`                                                                                        |
| `users.manage`   | правка профиля и своих полей, группы посетителя, блок, письма (сброс, подтверждение, приглашение), создание, удаление; группы — справочник |
| `users.settings` | экран `users.settings`: регистрация, обязательность полей, ключи провайдеров                                                               |

Права — в `UsersModule::permissions()` и `### Permissions` `AGENTS.md`; маршруты — `cms.can`;
`AccessCoverageTest` пакета зелёный.

**Готовые роли** (решение 22): данные посетителей — персональные, поэтому `users.view` и
`users.manage` по умолчанию есть только у «Администратора». Исключение — роль «Менеджер заказов»
сидера `module-orders` получает `users.view`, чтобы привязать заказ к клиенту (решение 33
[`WEBX_UI_MODULE_ORDERS.md`](WEBX_UI_MODULE_ORDERS.md)); роль заводит и наполняет `module-orders`,
`module-users` её не знает. `users.settings` — только «Администратор».

### 16.2. Экраны

- **`users.index`** — список: имя, e-mail, телефон, группы, «подтверждён», способы входа (иконки
  провайдеров и «пароль»), дата регистрации, последний вход. Поиск — по имени, e-mail, телефону;
  фильтры — группа, подтверждён ли, провайдер, заблокирован, период регистрации. Массовых действий
  нет (решение 23): группы и блок — в карточке. Связи (группы, привязки) — одним запросом на
  страницу (N+1 нет).
- **`users.form`** — карточка: профиль (имя, фамилия, телефон, e-mail — с пометкой «подтверждён» и
  действием «Подтвердить вручную»), карточка `project-fields` (свои поля с местом `panel`), группы,
  способы входа (список; «Отвязать» — с тем же правилом последнего способа), состояние (дата
  регистрации, последний вход, `blocked_at`), действия: «Отправить ссылку сброса пароля»,
  «Отправить письмо подтверждения», «Заблокировать / Разблокировать», «Удалить» (с предупреждениями
  §14.1). Публичные `id` узлов для модулей: `tabs`, `summary`, `project-fields` (§11.3).
- **Пароля в панели нет:** администратор не видит и не задаёт пароль посетителя — только
  отправляет ссылку. **Новый посетитель из панели** — e-mail и профиль, без пароля, письмо-приглашение
  со ссылкой `invite` на 7 дней (страница та же, что сброс: «Задайте пароль»).
- **`users.groups`** — справочник групп: код, название (одним языком), число посетителей; список —
  по названию, без перетаскивания; удаление — с подтверждением «Посетителей в группе: :count», без
  отказа слушателей (§13.1, решение 24).
- **Смена e-mail администратором** — сразу, с `email_verified_at = null` и письмом подтверждения на
  новый адрес, письмом «адрес изменён» на прежний: администратор действует по просьбе человека, а
  посетитель подтвердит адрес сам.

### 16.3. Настройки — `users.settings`

Экран раздела (как `audit.settings`), право `users.settings`:

- **Регистрация и профиль** — регистрация открыта / закрыта (§6.2), текст согласия на обработку
  данных (`localized`), обязательность полей (§10.5).
- **Вход через соцсети** — по карточке на провайдера реестра: включён, поля провайдера (секрет —
  «задано / заменить»), адрес возврата с кнопкой «Скопировать», что не хватает до показа (§9.3),
  предупреждение о посетителях, которые входят только им (§9.6).
- **Письма** — адрес отправителя берётся из настроек почты сайта; здесь — только ссылка туда и
  строка «транспорт пишет в лог» (§8.6).

## 17. MCP

Области `users:read` / `users:write`; права по правилу §6 спеки доступа (`users:read` →
`users.view`, `users:write` → `users.manage`, настройки — `permission: 'users.settings'`). Каждый
изменяющий инструмент принимает `dry_run`. **Пароли, хеши, токены сброса и приглашений, `remember_token`,
секреты провайдеров и id у провайдеров не показываются никогда** — ни в ответах, ни в ресурсе, ни в
журнале вызовов; e-mail и телефон — да, право `users.view` и есть доступ к персональным данным (это
сказано в описании инструментов, чтобы человек знал, что даёт агенту).

| Инструмент                  | Что делает                                                                                                                                                              |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users_list`                | страницами: id, имя, e-mail, телефон, группы (коды), подтверждён, способы входа (`password`, `google`…), заблокирован, даты; фильтры как в панели, `search`; сортировка |
| `users_get`                 | по id или точному e-mail: профиль, свои поля (`fields`), группы, способы входа с датами, даты                                                                           |
| `users_create`              | создать посетителя без пароля; `invite: true` — письмо-приглашение                                                                                                      |
| `users_update`              | профиль, свои поля (проверка как с экрана), группы (`groups`: коды, замена списка), `blocked`; смена e-mail — как администратором (§16.2)                               |
| `users_delete`              | удалить; `dry_run` отвечает предупреждениями модулей (§14.1)                                                                                                            |
| `users_send_password_reset` | отправить ссылку сброса; ответ — «отправлено», без ссылки                                                                                                               |
| `users_resend_verification` | отправить письмо подтверждения; неподтверждённым только                                                                                                                 |
| `users_unlink_provider`     | отвязать соцсеть с правилом последнего способа (§9.6)                                                                                                                   |
| `users_groups_list`         | группы с числом посетителей                                                                                                                                             |
| `users_groups_save`         | создать или изменить группу по `code`                                                                                                                                   |
| `users_groups_delete`       | удалить; связи с посетителями — каскадом, отказа слушателей нет (§13.1); `dry_run` — сколько посетителей в группе                                                       |
| `users_settings_get`        | настройки §16.3 без секретов: провайдеры — включён, показывается, чего не хватает, `credentials: ["client_secret: set"]`                                                |
| `users_settings_set`        | регистрация открыта/закрыта, обязательность полей, включение провайдера; **секреты через MCP не задаются** — только в панели                                            |

- **Ресурс `users://catalog`:** встроенные поля и свои поля сайта (имя, тип, места, обязательность
  по настройке, `unique`, `visitorEditable`, источник), провайдеры реестра (ключ, подпись,
  показывается ли), группы, разделы кабинета из реестра, правила пароля и лимиты — собирается из
  реестров и констант, а не пишется рукой.
- Отказ — `ToolFailure` со словами («Visitor 15 does not exist»; «Cannot unlink the last way to
  sign in»; неизвестная группа — со списком известных).
- `users_list`, `users_groups_list` — в `PerformanceTest` тёплыми.

**Словарь `webx-users`** на десять языков (`en`, `ru`, `uk` вычитаны носителем, остальные — машинный
перевод; паритет держит тест): `module.php` (название, права), `auth.php` (вход, регистрация, сброс,

полей), `mail.php` (письма), `screen.php` (панель), `errors.php` (MCP и 422). Счёт — числом в конце
(«Клиентов: :count»). Слова форм сайта перекрываются пропсами компонентов и темой, как у
виджетов. Подписи своих полей — ключ словаря сайта или слова поля.

**Производительность** ([`WEBX_UI_PERFORMANCE.md`](WEBX_UI_PERFORMANCE.md)):

- страница кабинета — бюджет запросов: посетитель (1), меню с `badge` (по запросу на модуль с
  бейджем), содержимое раздела; `assertNoRepeatedQueries`;

  `bumpOn` — `users_providers`, сохранение `users.settings`;

  `last_sign_in_at`.

**Регистрации** (CLAUDE.md §5): `php/composer.json` (`require`, `autoload-dev.psr-4`),
`phpunit.xml.dist`, `phpstan.neon.dist`, `node scripts/sync-php-version.mjs`; `scripts/php-smoke.sh`;
