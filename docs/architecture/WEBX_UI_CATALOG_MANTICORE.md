# Движок Manticore — `module-catalog-manticore`

Спутник ядра каталога: реализация `CatalogEngine` на Manticore Search для каталогов, которые
`SqlEngine` уже не тянет (больше пары тысяч товаров). Архитектура семейства —
[`WEBX_UI_CATALOG.md`](WEBX_UI_CATALOG.md) (§4.2, §4.3, §5), ядро, контракт движка и очередь
индексации — [`WEBX_UI_MODULE_CATALOG.md`](WEBX_UI_MODULE_CATALOG.md); здесь они не повторяются.
Выпущено в v0.56.0; спека — справочник того, что есть. Как легло в код — §5, замеры — §4.

## 1. Решения (не переоткрывать)

1. **Пакет — `module-catalog-manticore`, а не библиотека.** Без ядра каталога ему нечего
   индексировать — тот же довод, что собрал SEO одним `module-seo`. Своего пункта меню нет, место
   в панели (состояние индекса, очередь) — на правах раздела без меню.
2. **Manticore ставим не мы.** Пакет подключается к готовому серверу по HTTP JSON API:
   `MANTICORE_HOST`, `MANTICORE_PORT` (9308). Сервер общий для нескольких проектов — нормальный
   случай, а не исключение (так живёт хомлаб).
3. **`MANTICORE_TABLE_PREFIX` обязателен и без умолчания.** Из `APP_NAME` его не вывести: два
   демо — один сайт с одним `APP_NAME` и одной Manticore, и они молча перетёрли бы индексы друг
   друга. Без префикса движок не стартует, `webx:doctor` говорит почему. Префикс — `[a-z0-9_]`,
   таблицы — `{prefix}_catalog_products_{locale}`, суффикса `_idx` нет. Пакет трогает только
   таблицы своего префикса; doctor предупреждает, если префикс — начало чужих имён.
4. **Обычная жизнь — по товару, через очередь ядра** (§5.3 архитектуры): сохранение помечает,
   воркер пишет пачкой, упавший Manticore не роняет сохранение. Полная перестройка нужна, только
   когда Manticore подключили к каталогу с товарами, поменялась схема индекса (язык, морфология,
   новая версия пакета) или сервер потерял данные.
5. **Таблица на язык, и в каждой — все языки сайта.** Свой язык — в основных полях с бо́льшим
   весом, остальные — в поле «на других языках» с меньшим; артикул, штрихкод и бренд — в каждой.
   Нет перевода — в основные поля идёт текст основного языка, как на витрине. Так товар находится
   словом на любом языке сайта со страницы любого языка, и это гарантия, а не «обычно в названии
   есть латиница».
6. **Морфология таблицы — процессоры всех языков сайта, свой первым.** У языков на одном
   алфавите выигрывает первый процессор, поэтому немецкая таблица разбирает слова по-немецки,
   английская — по-английски; ради этого таблицы и разделены. Соответствие «язык → процессоры» —
   конфиг пакета с умолчаниями; язык без настройки — без морфологии.
7. **Поиск по началу слова включён всегда** (`min_prefix_len`) — подстраховка для языков, где
   морфология слабая или её нет.
8. **Перестройка — подменой, без окна с неполным каталогом.** `--rebuild` собирает
   `{table}_next` рядом, витрина работает на старой, затем подмена. Добавление языка на живом
   магазине — реальный сценарий (§1.1).
9. **Устаревшую схему видит doctor, перестройку запускает человек.** `prepare()` сравнивает
   требуемую схему с живой; на 93 тысячах товаров перестройка — нагрузка, и время для неё
   выбирает человек.
10. **Карточка товара от Manticore не зависит** — она из базы по адресу. Без движка ломаются
    только списки: категория, фильтры, поиск.
11. **Каталог до `sql_engine_limit` откатывается на `SqlEngine` сам**: покупатель не замечает,
    в логе предупреждение, doctor показывает.
12. **Каталог больше лимита отвечает 503 с `Retry-After`** — «каталог временно недоступен», шапка,
    меню и подвал на месте. Не 500 и не пустой список: 503 поисковик переждёт, пустую категорию с
    200 — запомнит. `SqlEngine` с фасетами на 93 тысячах положил бы базу.
13. **Панель откатывается на `SqlEngine` всегда**, с плашкой над списком: человек один, нагрузка
    небольшая, работа не встаёт.
14. **Недоступность запоминается на полминуты** после первой ошибки — дальше запасной путь сразу,
    без ожидания; таймаут соединения 1–2 секунды, а не 30 по умолчанию.
15. **Встроенного нечёткого поиска нет.** `fuzzy=1` с морфологией не находит ничего, без неё —
    часть опечаток (§2).
16. **Пустой результат — второй заход:** другая раскладка среди языков сайта, затем `CALL QSUGGEST`
    на каждое слово и поиск исправленным запросом. Сверху — «Показаны результаты для …, искать
    …» (две строки, переводимые, шаблон переопределяемый).
17. **В панели — те же два захода**, подсказок при вводе нет.
18. **Без Manticore — только `LIKE`** `SqlEngine`, без исправлений: для запасного режима
    достаточно.
19. **Коды товара — в двух видах:** артикул, штрихкод и внешний ID как есть (разбиты по
    разделителям) и нормализованные — нижний регистр, только буквы и цифры, поиск по подстроке.
    Запрос нормализуется так же; спецсимволы ввода экранируются всегда — `/`, `-` и кавычки
    ошибкой не становятся.
20. **Точное совпадение кода — первым**, выше любых совпадений по названию.
21. **Витрина: запрос ровно равен артикулу или штрихкоду одного опубликованного товара — сразу
    его карточка** (302). В панели — одна строка в списке.
22. **Подстрока ищется только в кодах.** Для названий хватает морфологии и начала слова. (Infix
    при этом включён у всей таблицы — §5.4; решение держит запрос.)
23. **Смысл фасетов — ядра** (§8.1 спеки ядра): выбранный сужает всё, кроме себя; дерево — с
    потомками; число — min/max. Manticore отвечает ровно как `SqlEngine`, только быстрее.
24. **Поля индекса — из `Facet::field()`**; множественные значения (категории с предками,
    значения свойств) — MVA. Значения всех справочных свойств — один атрибут `pv`, один `FACET`
    на все, `BatchCountedFacet` раскладывает; числа свойств — JSON-картой `pn` (§5.2).
25. **Счётчики — пакетом:** запрос с `FACET` по невыбранным плюс по запросу на каждый выбранный
    без его фильтра, одним заходом (§5.3).
26. **Общий набор тестов на оба движка** — одни сценарии на `SqlEngine` и Manticore с одинаковым
    ответом; в CI — сервис-контейнер Manticore отдельной джобой (§5.8).
27. **В панели — «Система → Поисковый индекс»**, только при движке `manticore`: подключение (хост,
    версия, префикс, доступность), по каждой языковой таблице — товаров в индексе против товаров в
    базе, очередь (сколько ждут и с какого времени самый старый), «схема устарела» с кнопкой
    «Перестроить» — задачей в очереди с прогрессом, а не долгим HTTP-запросом.
28. **MCP — `catalog_index_status`**, только чтение: чтобы агент ответил, почему товара нет в
    поиске.

### 1.1. Добавить язык на сайт с товарами

Добавили язык в настройки сайта → doctor: «индекс устарел, запустите
`webx:catalog:index --rebuild`» → перестройка создаёт таблицу нового языка (в ней пока текст
основного языка) и подменой обновляет остальные (их морфология и поле «на других языках»
меняются) → дальше каждый переведённый товар уходит в очередь при сохранении. Витрина всё это
время работает.

## 2. Проверено на Manticore 29.0.2

Временные таблицы на хомлабе, созданы и удалены. Это то, на чём стоят решения 5–7, 15–16 и 19–22.

- Товар с русским названием без латиницы и английским «Protective case for phone»: в `_ru`
  (`lemmatize_ru_all, stem_en`) находится по case, cases, чехлы, чехлов. В `_en` с одним
  `stem_en` «чехлы» не находит, с `stem_en, lemmatize_ru_all` — находит: морфология нужна всех
  языков, а не только своего.
- `libstemmer_de, stem_en`: находятся Schutzhüllen, cases, phones.
- Веса полей: «кабель» в `_ru` — 10643 (своё поле), «cable» — 3643 (поле других языков).
- Украинский: `lemmatize_uk_all` есть, но неполный — «чохли» находит «чохол», «чохлів» нет;
  `libstemmer_uk` отсутствует. Это словарь Manticore, а не схема; лечится синонимами или
  словоформами — волна B.
- `ALTER TABLE … morphology=` и `ALTER TABLE … RENAME` работают.
- Опечатки: `fuzzy=1, distance=2` с `lemmatize_ru_all, stem_en` — ни одной из шести; с `none` —
  «наушнеки» и «headphnes» да, «кабль» и «чехлол» нет. `CALL QSUGGEST` с морфологией исправил все
  пять (чехлол, кабль, наушнеки, headphnes, телефрн). Раскладка «xt[jk» → «чехол» и
  `CALL AUTOCOMPLETE` («чех» → чехол) работают.
- Артикулы `AT-1234/56`, `NGK.BKR6E-11`: стандартная разбивка находит «AT-1234», «1234», «BKR6E»,
  но не «at1234» и «bkr6e11», а «AT-1234/56» целиком — синтаксическая ошибка (`/` — оператор).
  `blend_chars` хуже: «AT-1234» перестаёт находиться. Нормализованное поле с подстрокой находит
  at123456, at1234, bkr6e11, 123456 и «34/5».
- `CALL QSUGGEST` без infix отвечает «suggests work only for keywords dictionary with infix
  enabled», а `infix_fields` на одно поле real-time-таблица молча игнорирует (в
  `SHOW TABLE … SETTINGS` его нет, и `@name ехол` находит «чехол»).
- `expand_keywords=1` в запросе нужен для начала слова без infix (`protec` → «protective»); с
  infix он искал бы `*слово*` и в названиях.
- `/bulk` в несуществующую таблицу — ошибка, а не автосоздание (`INSERT` через SQL таблицу бы
  создал). Несколько операторов через `;` в одном запросе HTTP API — синтаксическая ошибка.
- Пустых значений нет; MVA бывают только целые; float 32-битный (99.99 читается как 99.989998);
  сортировка — не больше чем по пяти ключам.
- Infix при `dict=keywords` почти ничего не стоит: подстроки в словарь не пишутся, а
  разворачиваются при запросе. На 93 тысячах товаров — 40,5 МБ на диске без infix, 44,4 МБ с
  `min_infix_len` 3 и столько же с 4.
- **Подмена не атомарна.** На таблице в 93 тысячи под восемью читателями окно между `DROP` и
  `RENAME` — 18–34 мс, в нём 13–33 упавших чтения из ~1 600 («unknown local table»). Два `RENAME`
  (живую в сторону, новую на место, старую удалить потом) дают то же окно.
- У образа `manticoresearch/manticore` нет тега `29` — только полные версии.

## 3. Отложено

- **Подсказки при вводе** — выпадашка в строке поиска: слова из `CALL AUTOCOMPLETE` и товары с
  картинкой и ценой, JSON-эндпоинт и Blade-компонент. Manticore их умеет (§2), решено отложить.

## 4. Приёмка

Принят на выгрузке эталонного магазина: `webx-cms.local` (OSPanel, SQLite, PHP 8.4) с Manticore
29.0.2 хомлаба по сети, префикс `webx_cms_local`, три языка (ru, uk, en) — три таблицы по 93 677
документов (93 525 товаров выгрузки плюс демо; импорт — 993 с, ошибок ноль). Время движка —
тёплое, медиана и p90 из 20 вопросов, с сетью до хомлаба.

## 5. Как легло в код

### 5.1. Пакет и сервер

- `php/packages/module-catalog-manticore`, namespace `WebxUi\Catalog\Manticore`, зависит от
  `module-catalog`, `illuminate/http` и Guzzle. Движок — `ManticoreEngine` в `CatalogEngines` под
  ключом `manticore`.
- Конфиг `webx-catalog-manticore.php`: `host`, `port`, `table_prefix` (env `MANTICORE_*`),
  `connect_timeout` 1,5 с, `timeout` 5 с, `down_for` 30 с, карта морфологии, `min_prefix_len` 3,
  `min_infix_len` 3, веса (10/3), `facet_values`, `relevance_sample` (1000), `layouts`,
  `schema_for` (60), `swap_wait` (150 мс), `rebuild.timeout` (3600), `rebuild.queue`.
- **Сервер — класс `Manticore`.** SQL в raw-режиме через `/sql?mode=raw`, документы — `/bulk`
  (`replace`/`delete`); `INSERT` через SQL не пишем — он создал бы таблицу. Отказ сервера
  (соединение, ответ без JSON) запоминается в кеше на `down_for` секунд и пишется в лог; ответ с
  ошибкой — не отказ, а `ManticoreError`.

### 5.2. Таблица и схема

- `{prefix}_catalog_products_{locale}`; локализованный текст — колонка своего языка (без
  перевода — основной), остальные языки — `other_languages`; `name` — ещё и строковый атрибут для
  сортировки. Морфология — процессоры всех языков сайта, свой первым.
- **Числа свойств — JSON-картой, а не атрибутом на свойство.** В ядре `IndexField::JSON`; `pn` —
  JSON, `RangeFacet` читает `pn.12` как `DOUBLE(pn['12'])`. Новое числовое свойство не меняет схему
  таблицы — иначе каждое требовало бы перестройки, вопреки §6 спеки свойств.
- **Пустых значений нет.** Число, которого может не быть (цена), несёт флаг (`price__set`):
  диапазон и его концы берут только товары с флагом, сортировка ставит товары без цены в конец в
  обе стороны. Несколько строк, дробей или флагов — JSON-массив. Концы диапазона отдаются как
  `%.7g`.
- **Коды** — флаг `code` у `IndexField`; `CoreDocument` помечает им `sku`, `barcode` и
  `external_id`. В таблице три колонки на все коды: `codes` — как написаны (стандартная разбивка:
  «AT-1234/56» — at, 1234, 56), `codes_flat` — нижний регистр, только буквы и цифры
  (`TableSchema::flat()`), `code_keys` — те же целиком, JSON-список.
- **Infix у всей таблицы** (`min_infix_len`), потому что без него нет `QSUGGEST`, а на одно поле
  его не включить (§2). `expand_keywords` из запроса убран.
- **Сравнение схемы (решение 9)** — `DESCRIBE` и `SHOW TABLE … SETTINGS` против `TableSchema`:
  колонки, типы и свойства, `morphology`, `min_prefix_len`, `min_infix_len` (`index_exact_words`
  Manticore ставит сам — не сравнивается). `prepare()` создаёт недостающие таблицы и не трогает
  устаревшие; `status()` — состояние каждой таблицы для doctor и страницы панели.
- **Живая схема.** `ManticoreEngine::reading()` берёт колонки и настройки живой таблицы (кеш на
  `schema_for` секунд, сбрасывается после `prepare()` и подмены) и у устаревшей спрашивает и пишет
  по `TableSchema::within()` — требуемой схеме, суженной до колонок того же типа: коды — только при
  всех трёх колонках, число — только с флагом, `min_*_len` — таблицы. Фасет без атрибута отвечает
  пусто, без infix нет `QSUGGEST`. Без этого вставал и воркер: `/bulk` отвечал «unknown column»,
  очередь стояла. Таблица `_next` пишется по полной схеме.

### 5.3. Запрос и фасеты

- **Не «один вызов», а один заход** (решение 25): в HTTP API нет нескольких операторов, поэтому
  страница, итог (`FACET 1`) и счётчики всех невыбранных фасетов — один оператор, а рядом,
  параллельно (`Http::pool`), — по оператору на выбранный фасет без его выбора, один на концы всех
  диапазонов и, если источник выбирает уместные фасеты, выборка id для него. Время — одного
  запроса, а не суммы.
- **Раскладка — у `BatchCountedFacet`:** `indexValues()` (выбор в значениях поля: «да» свойства —
  это id свойства в `pb`) и `splitIndexCounts()` (один `FACET pv` раскладывается по свойствам —
  `owners()` у справочников и интервалов).
- **Уместные фасеты** (`RelevantFacets`) решает общий `FacetPlacement` для обоих движков; Manticore
  даёт источнику выборку до `relevance_sample` id найденного — доли по выборке, а не по всем.
- **Фасеты спутников пишут в документ только видимое.** Бренды и метки так и делали (скрытие
  помечает их товары); `StockDocument` пишет статус наличия, только если он в фильтре, а товар без
  строки — под статусом по умолчанию, как в базе.

### 5.4. Поиск

- **Слова** — `MATCH` по текстовым колонкам с весами; каждое слово от `min_prefix_len` букв —
  `(слово | слово*)` (решение 7). **Коды** — `| (@codes_flat *плоский запрос*)`, если плоский
  запрос не короче `min_infix_len`: подстрока только у кодов (решение 22). Ввод экранируется
  всегда; запрос без единой буквы и цифры — пустой ответ, а не ошибка.
- **Точное совпадение (20)** — `IN(code_keys, '<плоский запрос>') AS is_exact` первым ключом
  сортировки (у сортировки остаётся три плюс `id`), и в том же заходе `… AND is_exact = 1 LIMIT 2`
  → `CatalogResult::$exact` — до двух id, чтобы отличить «один» от «нескольких». Manticore
  сравнивает плоско: «at123456» — это «AT-1234/56». `SqlEngine` сравнивает как есть
  (`Product::scopeCoded`, коллация базы), совпавшие первыми через `ORDER BY CASE`; `LIKE` смотрит
  и `external_id`.
- **Переход на карточку (21)** — `Storefront::listing()` для поиска: ровно один `exact`, ничего не
  выбрано, без `?page=` → 302 на `url()` товара, на обоих движках. В панели `ProductController`
  отдаёт одну строку (`total` 1); счётчики фасетов остаются от всего найденного.
- **Два захода (16–17)** — `ManticoreEngine::answer()`: пусто, запрос есть, не `asTyped` →
  раскладки (`KeyboardLayouts`: en, ru, uk, be, de; только языки сайта, сначала язык страницы;
  символ, которого нет в исходной раскладке, снимает её) — все варианты параллельно, `LIMIT 1`,
  первый непустой; затем `CALL QSUGGEST(слово, таблица, 1 AS limit)` на каждое буквенное слово
  параллельно (коды и числа не исправляются) и поиск исправленным. Не нашлось — пустой ответ без
  исправления. Худший случай — четыре захода на запрос страницы.
- **«Показаны результаты для …»** — `CatalogResult::$corrected`; `CatalogQuery::$asTyped`
  (`?typed=1`, его несут ссылки сортировки и редиректы), `withSearch()` для повторного вопроса.
  Витрина — вид `webx-catalog::search-corrected` и строки `storefront.search-corrected` /
  `-instead`; панель — `corrected` в ответе списка, строка над таблицей с кнопкой
  (`panel.search-corrected` / `-instead`).

### 5.5. Перестройка

- **Подмена (решение 8)** — интерфейс ядра `RebuildsAside`: `prepare(rebuild: true)` создаёт
  `{table}_next`, `index()` пишет туда, `Indexer::rebuild()` в конце зовёт `completeRebuild()`
  (`DROP` старой, `ALTER TABLE … RENAME`) и заново ставит в очередь товары, изменённые с начала
  перестройки. Воркер во время перестройки пишет в обе таблицы.
- **Окно подмены** (§2) движок переживает сам: получив «unknown local table» на вопросе, ждёт
  `swap_wait` и спрашивает ещё раз (`throughSwap()`) — 1 413 вопросов витрины сквозь перестройку,
  ни одного отказа. Запись воркера в этот миг падает; пачка остаётся в очереди и уходит следующим
  проходом.
- **Задача `RebuildIndex`** (`tries` 1, `timeout` и очередь из `rebuild.*`) — одна на всю
  перестройку: подмена в конце, обрыв оставляет старые таблицы. Прогресс — `RebuildProgress` в
  кеше (общий у веба и воркера): `queued → running (done/total) → done | failed`, колбэк
  `progress(done, total)` у `Indexer::rebuild()`. Вторая перестройка, пока первая ждёт или идёт, —
  409; без вестей 15 минут — `stalled`, кнопка снова доступна.
- **Перестройка из консоли видна со счётом:** `status()` таблицы с `_next` рядом отдаёт
  `rebuilding` и `filled`; страница пишет «Перестройка заполняет таблицу рядом: N из M» и
  опрашивает сервер раз в 2 с. Кнопку это не прячет (§6).
- Смена схемы новой версией пакета — «устарела» у doctor и `--rebuild`, пока таблица живёт по
  живой схеме (§5.2).

### 5.6. Откат и недоступность

- Панель (`context: panel`, `withUnpublished`, `onlyTrashed`) и каталог до `sql_engine_limit` — на
  `SqlEngine`; больше лимита — `CatalogUnavailable`.
- **Плашка (13) — по ответу, а не по движку:** откат ставит `CatalogResult::$fellBack`, список
  товаров отдаёт `fell_back`, `ProductsPage` рисует предупреждение (`panel.fell-back` ядра).
- **503 (12)** — `CatalogUnavailable::render()`: HTML — вид `webx-catalog-manticore::unavailable` в
  макете каталога (`webx-catalog.layout` — макет сайта с шапкой, меню и подвалом), `noindex`, 503 и
  `Retry-After`; JSON — `{message}` с теми же заголовками. Строки —
  `webx-catalog-manticore::storefront.unavailable-*`, вид публикуется тегом
  `webx-catalog-manticore-views`.

### 5.7. Doctor, панель, MCP

- **Doctor** — `ManticoreCheck`, только при `engine = manticore`: нет префикса или сервер не
  отвечает — fail; префикс — начало чужих таблиц — warn; таблица языка отсутствует или устарела —
  warn с командой перестройки.
- **Раздел — `SearchIndexModule`, id `search-index`,** группа `system`, порядок 720, права
  `search-index.view` / `search-index.manage`; регистрируется только при движке `manticore`
  (`available()`), маршруты `GET /api/cms/search-index` и `POST …/rebuild` без движка отвечают 404. Отчёт — `IndexStatus::report()`: подключение (адрес, префикс, `SHOW VERSION`, доступность и
  ошибка), товары в базе вместе с корзиной (она тоже индексируется), `status()` каждой таблицы,
  очередь — `Catalog::queue()`. Каждая часть спрашивается отдельно: без сервера страница всё равно
  показывает очередь и базу.
- **npm — `@webx-ui/module-catalog-manticore`:** `catalogManticore()`, страница `SearchIndexPage`
  (сервер, очередь, таблицы — карточками на узкой ширине, полоса перестройки с опросом раз в 2 с),
  словарь `webx-catalog-manticore::panel`. Мок плейграунда —
  `apps/playground/server/panel/catalog-manticore.ts`: русская таблица устарела, перестройка идёт
  по часам, `POST /api/cms/search-index/_outage` выключает сервер — видна плашка над товарами.
- **MCP — `catalog_index_status`** через `SatelliteTools`, только на движке `manticore`: отчёт
  страницы и, с `product`, почему товара нет в поиске — удалён, снят или скрыт в базе, ждёт в
  очереди с какого времени, что о нём в каждой таблице (`ManticoreEngine::document()`).
- Регистрации — `Setup\Catalogue` (`catalog-manticore`), `extra.webx.npm`/`panel`, плейграунд,
  `scripts/packages.mjs` сайта. Гайд — «The search index on Manticore» в
  `apps/docs/guide/catalog.md`.

## 6. Открыто

- **Колонка сменила тип — до перестройки её как будто нет.** Живая схема (§5.2) оставляет только
  колонки того же типа: атрибут, ставший из строки JSON, не спрашивается и не пишется, фасет по
  нему пуст до `--rebuild`. Сейчас таких смен нет; появится — решать вместе с ней.
- **Сохранённый товар доходит до витрины за минуту** (§4). Если понадобится быстрее — ядро после
  сохранения ставит в очередь Laravel одну задачу «разобрать очередь индекса» с замком,
  планировщик остаётся страховкой (при работающем воркере ~1 с).
- **Страница категории целиком — ~320 мс на рабочей машине**, из них движок ~45. Остальное —
  карточки и подписи фасетов из базы (SQLite, OSPanel); это ядро витрины, а не движок.
  Профилировать на хомлабе, где база и PHP боевые.
- **Консольная перестройка и кнопка панели друг о друге не знают.** 409 отвечает только на задачу
  панели; кнопка, нажатая во время `--rebuild` из консоли, пересоздаст `_next`, и консольный
  прогон упадёт на записи. Страница эту перестройку видит (§5.5), но кнопку не прячет: таблица
  `_next`, оставленная убитой перестройкой, держала бы её вечно.
- **Перестройку обрывает флаг недоступности.** Один отказ соединения помечает сервер упавшим на
  `down_for` секунд — для всех процессов, и следующая запись перестройки падает «failed less than
  30 seconds ago». Старые таблицы на месте, перестройку запускают снова. Видно было только под
  стендом, исчерпавшим порты (ловушка в `docs/pitfalls/laravel-and-php.md`, «Manticore»).
