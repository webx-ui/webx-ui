# Группы способов оплаты и значки платёжных систем — спецификация

Статус: предложена на приёмку человеку (webx-ui#114). Реализация — отдельной задачей по плану §10.
Спека дополняет [`WEBX_UI_MODULE_PAYMENTS.md`](WEBX_UI_MODULE_PAYMENTS.md): контракт способа §6,
список для покупателя §7, страница оплаты §8.4–§8.5, шаг оформления §10, панель §13, MCP §16, кеш
§18. Спутник LiqPay — [`WEBX_UI_PAYMENT_LIQPAY.md`](WEBX_UI_PAYMENT_LIQPAY.md) (решение 3, §6),
что умеют шлюзы — [`WEBX_UI_PAYMENT_GATEWAYS.md`](WEBX_UI_PAYMENT_GATEWAYS.md).

Сейчас шаг «Оплата» — плоский список одинаковых плашек. С несколькими шлюзами и несколькими способами
у каждого он становится длинным и непонятным. Покупатель должен видеть 3–4 понятные группы, а внутри
выбранной — конкретные способы.

```
○ Оплата при отриманні        [иконка]   пояснение / комиссия перевозчика
● Онлайн оплата               VISA ●● GPay  Pay
    ● Картою онлайн           VISA ●●
    ○ Google Pay              GPay
    ○ Apple Pay               Pay
    ○ monobank                mono
    ○ Миттєва розстрочка      ПриватБанк
○ Рахунок для підприємств     [иконка]
```

## 1. Решения

Решения человека (04.11.2026, спецификация задачи). Не пересматриваются.

1. **Группы по смыслу — из коробки.** База даёт готовые группы, каждый тип объявляет свою группу по
   умолчанию, способ попадает туда сам. В панели группу можно переименовать, переставить, сменить
   пиктограмму и описание; способ можно перенести. Сайт с одним-двумя способами про группы не думает.
2. **Значки ставит спутник** по включённым настройкам способа. Выключил — значок пропал. У способа —
   его значки, у группы справа — все значки её способов. Менеджер картинок не грузит. У группы —
   простая пиктограмма, меняется в панели.
3. **Только два уровня: группа → способ.** «Через Google Pay» и «через Apple Pay» — отдельные способы
   того же типа с одной галочкой, рядом с остальными в группе. Группа с одним способом — одна строка.
4. **Apple Pay и Google Pay — только там, где они возможны.** Проверка в браузере. Не сработала —
   способ показывается: оплату терять нельзя.
5. **Несколько шлюзов не запрещаем.** Панель предупреждает о похожих пунктах и не мешает сохранить.
   Название шлюза покупателю не показываем, если магазин сам так не назвал способ.
6. **«Выбрать другой способ» на странице оплаты** — тот же сгруппированный вид, тот же компонент.

Решения этой спеки (приняты вместе с ней):

7. **Группа способа — вычисляемая.** В строке способа хранится только перенос менеджера; `null` —
   группа типа. Существующим способам миграция ничего не пишет (§2.4).
8. **Значки — единственный источник для всего остального.** «Только Apple Pay» (§4) и похожесть (§5)
   выводятся из `marks()`: второго объявления у спутника нет.
9. **Строка одного способа показывает способ, а не группу.** Название, подпись и значки — способа;
   от группы только пиктограмма. Поэтому сайт с двумя способами в разных группах читается как сегодня,
   а «Оплата на кассе» при самовывозе (§12.1 базы) не теряется.
10. **Группа одна — шапки нет.** Все способы сайта в одной группе — плоский список, как сейчас.
11. **Выбор группы сразу выбирает её первый способ** — предложение, вопрос 1 §11, доводы в §6.3.
12. **Своих групп в v1 нет** — предложение, вопрос 4 §11: только три встроенные.

## 2. Модель групп

### 2.1. Таблица `payment_groups`

Группы — строки, а не настройки: нужны порядок, языковые поля и кеш той же группы `payments`.

| Колонка                    | Тип                    | Примечание                                               |
| -------------------------- | ---------------------- | -------------------------------------------------------- |
| `id`                       | bigint                 |                                                          |
| `key`                      | string(64), **unique** | `on_receipt`, `online`, `transfer`; навсегда             |
| `title`                    | json                   | название по языкам; `{}` — слово словаря на каждом языке |
| `description`              | json, null             | подпись под названием                                    |
| `pictogram`                | string(32)             | имя из набора §2.5                                       |
| `position`                 | smallint unsigned      | ручной порядок групп                                     |
| `created_at`, `updated_at` | timestamp              |                                                          |

К `payment_methods` добавляется `group_key` — string(64), null, без внешнего ключа: `null` значит
«группа типа» (решение 7). Индекс не нужен: включённые способы читаются целиком и лежат в кеше (§18
базы).

### 2.2. Группы из коробки

| Ключ         | en             | ru            | uk             | Пиктограмма | `position` |
| ------------ | -------------- | ------------- | -------------- | ----------- | ---------- |
| `on_receipt` | Pay on receipt | При получении | При отриманні  | `cash`      | 10         |
| `online`     | Pay online     | Оплата онлайн | Оплата онлайн  | `card`      | 20         |
| `transfer`   | Bank transfer  | По реквизитам | За реквізитами | `document`  | 30         |

Названия — в новом файле словаря `webx-payments::groups`, на всех языках пакета (`de en es fr it pl
pt ru tr uk`). Описаний по умолчанию нет: база не знает, что именно включил магазин, а неверная
подпись хуже пустой. Описание пишет менеджер.

### 2.3. Как тип объявляет группу

Новая возможность — необязательный интерфейс (§6.4 базы), старые спутники не ломаются:

```php
namespace WebxUi\Payments\Contracts;

/** A type whose methods belong elsewhere than its kind suggests (groups spec §2.3). */
interface DeclaresGroup
{
    /** A key of `MethodGroups`: `on_receipt`, `online` or `transfer`. */
    public function defaultGroup(): string;
}
```

Без интерфейса группу даёт вид типа, и этого хватает почти всем:

| Тип                                   | `kind()`  | `awaitsPayment()` | Группа       |
| ------------------------------------- | --------- | ----------------- | ------------ |
| спутник шлюза, `liqpay.checkout`      | `Online`  | —                 | `online`     |
| `store.on_receipt`, наложенный платёж | `Offline` | `false`           | `on_receipt` |
| `store.bank_transfer`                 | `Offline` | `true`            | `transfer`   |

Встроенным типам и спутнику LiqPay править ничего не надо. Интерфейс — для исключений: например,
счёт для юрлиц, который выставляет онлайн-шлюз, объявит `transfer`. Неизвестный ключ из
`defaultGroup()` — группа по виду и предупреждение `webx:doctor`.

### 2.4. Миграция

- Миграция создаёт таблицу, три строки и колонку `group_key`. **Способы не трогает:** у всех
  `group_key = null`, и каждый сразу в группе своего типа (решение 7). Новый спутник так же попадает
  на место сам.
- **Порядок групп на уже настроенном сайте.** Сегодня порядок один на все способы; чтобы первый пункт
  покупателя остался первым, миграция ставит группам `position` по наименьшей `position` включённых
  способов, группа ищется через реестр типов. Включённых нет, тип неизвестен — порядок таблицы §2.2.
- Откат убирает колонку и таблицу. Переносы менеджера при этом теряются — способы всё равно плоские.
- **Что заметит покупатель.** Способы одной группы теперь идут подряд: порядок вида «карта, при
  получении, рассрочка» станет «карта, рассрочка, при получении». Это смысл группировки, но об этом
  стоит написать в changeset.

### 2.5. Пиктограммы

Свой набор в пакете: `card`, `cash`, `document`, `bank`, `wallet`, `truck`, `store`, `qr`. Файлы —
`resources/views/icons/*.blade.php`, вывод — `<x-webx-payments::pictogram>`, `currentColor`, размер
24 px. Так устроены иконки виджетов: у `webx-ui/module-payments` нет зависимости от тем, а в спрайте
`theme-default` карты, купюры и документа нет. Тема переопределяет вид по обычному пути
`<layer>/views/vendor/webx-payments/`. Вне набора имя не сохраняется.

`icon` способа (картинка из медиатеки, §5 базы) остаётся: если задана, она стоит на месте пиктограммы
в строке одного способа и перед названием в подсписке.

### 2.6. Чтение и порядок

- **`WebxUi\Payments\MethodGroups`** — группы из кеша: `remember('payments.groups', ['payments'], …)`,
  `localized: false`; модель `PaymentGroup` — в `bumpOn` группы `payments`.
- **`Method`** получает `groupKey` — то, что в строке. Реестра типов у него нет, поэтому действующую
  группу считает `Methods::option()`: `groupKey` или группа типа. Перенос на неизвестный ключ идёт по
  группе типа.
- **`MethodOption`** получает `group`, `marks` и `wallets` (§4.1); `toArray()` их отдаёт, поэтому
  `GET /api/payments/methods` дополнительно получает `groups`.
- **`Methods::grouped(list<MethodOption>): list<MethodGroupView>`** — чистая функция, без запросов.
  Принимает уже отфильтрованный список, поэтому шаг и страница оплаты зовут её с разными наборами.
  Группы идут по `position` группы, способы внутри — по `position` способа. Значки группы —
  объединение значков её способов без повторов, в порядке реестра §3.2.
- **Запросов на тёплом кеше не прибавляется:** бюджет шага остаётся 1 (§18 базы).

### 2.7. Пустая группа

| Что с группой                                 | Покупатель                  | Панель                                |
| --------------------------------------------- | --------------------------- | ------------------------------------- |
| нет способов                                  | не видит                    | видит, можно перетащить в неё         |
| все способы выключены                         | не видит                    | видит, способы приглушены             |
| все способы недоступны для заказа (§7.1 базы) | не видит                    | `payments_available` называет причину |
| остался один способ                           | одна строка (решение 3)     | без изменений                         |
| осталась одна группа                          | плоский список (решение 10) | без изменений                         |

Отдельного выключателя у группы нет: группу выключают её способы.

## 3. Значки

### 3.1. Контракт спутника

```php
namespace WebxUi\Payments\Contracts;

/** A type that can say which payment systems a method takes (groups spec §3). */
interface ProvidesPaymentMarks
{
    /**
     * Keys of `PaymentMarks` the method offers the buyer right now, read from its settings.
     * Cheap and pure: no gateway call, no database.
     *
     * @return list<string>
     */
    public function marks(Method $method): array;
}
```

Аргумент — `Method`, а не массив настроек: тип и так работает с неизменяемым `Method` (§6.1 базы).
Тип без интерфейса значков не показывает. Неизвестный ключ пропускается, `webx:doctor` предупреждает.

### 3.2. Реестр значков

`WebxUi\Payments\PaymentMarks` — ключ, название для `alt`, файл, признак кошелька. Порядок реестра —
порядок показа. Спутник может добавить свой значок: `PaymentMarks::register()` с файлом своего пакета,
как типы и шлюзы в `callAfterResolving` (§14.1 базы).

| Ключ         | `alt`      | Кошелёк | Кто даёт                                            |
| ------------ | ---------- | ------- | --------------------------------------------------- |
| `visa`       | Visa       | нет     | LiqPay и все шлюзы обзора                           |
| `mastercard` | Mastercard | нет     | LiqPay и все шлюзы обзора                           |
| `apple-pay`  | Apple Pay  | **да**  | LiqPay, mono, WayForPay, Portmone, NovaPay, iPay.ua |
| `google-pay` | Google Pay | **да**  | LiqPay, mono, WayForPay, Portmone, NovaPay, iPay.ua |
| `privat24`   | Приват24   | нет     | LiqPay                                              |
| `privatbank` | ПриватБанк | нет     | рассрочка: LiqPay, прямой спутник                   |
| `mono`       | monobank   | нет     | спутник mono                                        |

Файлы — `resources/marks/*.svg` пакета `module-payments`, отдаются маршрутом
`webx/payments/marks/{key}.svg` с адресом по хешу и вечным кешем, как `step.js` (`ScriptController`).
В строке — `<img width="38" height="24" alt="Visa">`: значки повторяются у группы и способа, и инлайн
раздул бы каждую перерисовку шага.

### 3.3. Правила знаков

Значки — чужие товарные знаки, поэтому рисовать их самим нельзя. Коротко, что важно для кода:

| Система    | Правило                                                                                             | Источник                                                                                                                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Apple Pay  | только файл Apple, менять можно лишь высоту; поле вокруг — четверть высоты; знак не кнопка          | [HIG](https://developer.apple.com/design/human-interface-guidelines/apple-pay), [Marketing](https://developer.apple.com/apple-pay/marketing/)                                                                       |
| Google Pay | только файл Google, не перекрашивать контур; не меньше значков других систем; «Pay» не переводить   | [Brand guidelines](https://developers.google.com/pay-wallet/products/api/web/guides/best-practices/brand-guidelines)                                                                                                |
| Visa       | только актуальные файлы Brand Center, синий на сайтах; использовать могут принимающие Visa продавцы | [Brand Center](https://corporate.visa.com/en/about-visa/brand.html), [E-commerce standards](https://corporate.visa.com/content/dam/VCOM/corporate/about-visa/documents/visa-ecommerce-brand-standards-sept2025.pdf) |
| Mastercard | символ только в полном цвете; размер и частота наравне с другими системами                          | [Brand Center](https://www.mastercard.com/brandcenter/us/en/brand-requirements/mastercard.html)                                                                                                                     |

Из этого следует:

- **Один размер для всех:** 38 × 24 px. Требование равенства есть и у Google, и у Mastercard.
- **Подложка — часть файла, а не темы.** Значок — готовая карточка со своим белым полем: в тёмной теме
  он остаётся белым, полноцветный символ не страдает, а CSS не хранит цветов. Тема значки не красит.
- **Поле вокруг.** Apple просит четверть высоты знака: при 24 px это 6 px. Зазор между значками —
  `--site-space-2` (8 px); если в файле знак меньше карточки, сверить на настоящих файлах (этап 2 §10).
- **Значок не кнопка:** он внутри `label` строки и сам по себе не нажимается.
- **Минимальные размеры Mastercard и Visa** на этом этапе не сверены. Сверить вместе с файлами.
- **mono и ПриватБанк:** правила знаков не искались. Сверить вместе с файлами или спросить банк.

Откуда взять файлы и можно ли положить их в MIT-репозиторий — вопрос 2 §11. Макет нарочно показывает
серые плашки со словом, а не нарисованные логотипы.

### 3.4. Что показывается

- **Строка способа** — значки `marks()` этого способа.
- **Строка группы** — объединение значков её способов (§2.6). Шире нет смысла ограничивать: ключей
  всего семь, а на узкой ширине значки переносятся.
- **Узкий шаг (контейнер < 480 px).** У закрытой группы значки уходят строкой под текст. У открытой
  группы их нет вовсе: те же значки стоят ниже у способов, а на шести значках шапка выходила в 153 px.
  Это единственное отступление от решения 2 — вопрос 3 §11.
- **Значок кошелька виден там же, где кошелёк возможен** (§4.3).

### 3.5. LiqPay: `paytypes` → значки

`LiqPayCheckoutType` реализует `ProvidesPaymentMarks` по семи полям §6 спеки LiqPay:

| Поле              | `paytypes`    | Значки               |
| ----------------- | ------------- | -------------------- |
| `pay_card`        | `card`        | `visa`, `mastercard` |
| `pay_apay`        | `apay`        | `apple-pay`          |
| `pay_gpay`        | `gpay`        | `google-pay`         |
| `pay_privat24`    | `privat24`    | `privat24`           |
| `pay_qr`          | `qr`          | —                    |
| `pay_moment_part` | `moment_part` | `privatbank`         |
| `pay_paypart`     | `paypart`     | `privatbank`         |

- У `qr` общего знака нет, поэтому значка нет.
- **Ни одной галочки:** `paytypes` не уходит, страница покажет настройки кабинета (§6 спеки LiqPay).
  Что там включено, база не знает, поэтому `marks()` пуст.
- Что принадлежность рассрочек ПриватБанку верна для обоих полей, сверяется с документацией LiqPay на
  этапе 2 §10.

## 4. Видимость Apple Pay и Google Pay

### 4.1. Как способ это объявляет

Отдельного объявления нет (решение 8). **Способ кошелька — тот, у которого все значки — кошельки.**
База считает `MethodOption::$wallets` сама:

| `marks()`                         | `wallets`                 | Где виден                   |
| --------------------------------- | ------------------------- | --------------------------- |
| `apple-pay`                       | `apple-pay`               | где есть Apple Pay          |
| `google-pay`                      | `google-pay`              | где есть Google Pay         |
| `apple-pay`, `google-pay`         | `apple-pay`, `google-pay` | где есть хотя бы один       |
| `visa`, `mastercard`, `apple-pay` | —                         | везде: карта работает везде |
| пусто                             | —                         | везде                       |

Строка несёт `data-wallets="apple-pay google-pay"`. Запросов к шлюзам нет: всё решается в браузере
покупателя, и только для способов с `wallets`.

### 4.2. Проверка в браузере

Общий скрипт `methods.js` (§6.5). Ответ — один из трёх: да, нет, не знаю. **«Не знаю» значит показать**
(решение 4).

**Apple Pay** — синхронно, внешних скриптов нет:

```js
function applePay() {
  if (!('ApplePaySession' in window)) return false // Chrome on Android: the API is not there at all
  try {
    return window.ApplePaySession.canMakePayments()
  } catch {
    return null // an insecure page, a frame: the check did not work
  }
}
```

`canMakePayments()` без аргументов отвечает, умеет ли устройство Apple Pay. Наличие карты в Wallet она
не проверяет, и это нам подходит: покупатель сможет добавить карту. Что идентификатор продавца ей не
нужен, известно из описания метода; страница документации Apple на этапе не открылась, проверить на
этапе 4 §10.
Отсутствие `ApplePaySession` — это ответ «нет», а не сбой: иначе на Android скрывать было бы нечего.

**Google Pay** — по документации Google это `isReadyToPay` библиотеки `pay.js`:

```js
const request = {
  apiVersion: 2,
  apiVersionMinor: 0,
  allowedPaymentMethods: [
    {
      type: 'CARD',
      parameters: {
        allowedAuthMethods: ['PAN_ONLY', 'CRYPTOGRAM_3DS'],
        allowedCardNetworks: ['VISA', 'MASTERCARD'],
      },
    },
  ],
}
```

- Библиотека `https://pay.google.com/gp/p/js/pay.js` грузится **только если на странице есть способ с
  `google-pay` в `wallets`**. Магазин без такого способа чужих скриптов не получает.
- Нет ответа за 1500 мс, скрипт не загрузился, запрет CSP, отказ промиса — «не знаю», способ показан.
- `existingPaymentMethodRequired` не используем: Google предупреждает, что он зависит от cookie и не
  годится для решения показывать ли кнопку.
- `merchantId` в запросе нет. Документация `isReadyToPay` его не упоминает, но и прямо не говорит, что
  он не нужен: проверить на этапе 4 §10.
- Google заявляет поддержку Chrome, Firefox, Safari, Edge и Opera, поэтому скрывается Google Pay редко.
  Вопрос 5 §11 — стоит ли это чужого скрипта на оформлении.

**Результат запоминается** в `sessionStorage` на вкладку (`try/catch`): шаг перерисовывается после смены
доставки, и без памяти строки мигали бы, а `pay.js` грузился бы снова.

### 4.3. Что скрывается

Ответ «нет» убирает:

1. строки способов, у которых ни один кошелёк из `wallets` не возможен;
2. значки этого кошелька — и у способов, и у групп: значок Apple Pay на Android обещал бы то, чего нет;
3. группу без оставшихся способов.

Оставшийся один способ собирает группу в одну строку: скрипт переносит в шапку название, подпись и
значки этого способа (решение 3).

**Пока ответа нет, строки видны:** скрывать сначала значило бы потерять способ при сбое. Apple Pay
отвечает синхронно, поэтому скачка почти нет; Google Pay скрывается редко.

**Если скрыть пришлось бы всё** — ничего не скрывается. Магазин, где единственный способ — Apple Pay,
покажет его и на Android: пустой шаг не даст оформить заказ вовсе (решение 4).

**Выбранный способ оказался скрыт** (выбрал на iPhone, продолжил на компьютере; корзина та же):

- скрипт отмечает первый видимый способ той же группы и записывает его;
- в группе никого не осталось — снимает выбор новым `DELETE /api/payments/selection`, и покупатель
  выбирает заново. Шаг при этом просто не готов, как при первом открытии.

Макет этот случай показал наглядно: группа открыта, а способ не отмечен.

**Сервер кошелёк не проверяет.** Он не знает устройства покупателя. `check()` пропускает такой способ,
и если скрипт не сработал, покупатель попадёт на страницу шлюза — это и есть «не терять оплату».

## 5. Предупреждение о похожих способах

**Похожи** два включённых способа одной группы с **одинаковым непустым набором значков** (порядок не
важен). Это покрывает пример решения 5: Google Pay через LiqPay и через mono — оба `{google-pay}`, и
две карты разных шлюзов — оба `{visa, mastercard}`.

Не считается похожим: «карта с Apple Pay» рядом с «только Apple Pay». Наборы разные, и покупатель
видит разные пункты: именно так выглядит набросок задачи.

- **Код:** `SimilarMethods::of(list<Method>): array<string, list<string>>` — чистая функция, ключ способа
  → ключи похожих. Способы без `ProvidesPaymentMarks` в сравнении не участвуют.
- **Список способов:** значок-предупреждение в строке и подсказка с именем похожего способа.
- **Форма способа:** `WxAlert` уровня `warning` над полями — слова «This group already has a method with
  Google Pay: the buyer will see two similar items. Tell them apart by title, for example “Google Pay via
  monobank”.» Для набора из нескольких значков — «…a method with the same payment systems…».
- **Ответ сохранения** несёт `warnings`; панель показывает его и в тосте. **Сохранение не блокируется.**
- Выключенный способ не предупреждает, пока его не включат.

```html
      </label>
    </fieldset>
  </div>

```

- **Группа с одним способом** — та же шапка с данными способа и `data-method`, подсписка нет. Группа
  одна — только строки `__option`, без шапок (решение 10).
- **Классы — `webx-payments__*`, как в коде.** §10.3 базы говорит `.wx-payments-*`, но `payments.css` и
  шаблоны давно на `webx-payments`; новые классы — как в коде, все в `AGENTS.md`.

### 6.2. Раскрытие — на CSS

Подсписок открыт правилом `.webx-payments__group:has(> .webx-payments__group-head input:checked)`.
Скрипт для этого не нужен, поэтому при загрузке ничего не прыгает. Браузер без `:has()` показывает все
подсписки открытыми (`@supports not selector(:has(*))`): длиннее, но работает.

### 6.3. Выбор группы с несколькими способами — предложение

**Предложение: сразу выбран первый видимый способ группы, по порядку менеджера.** Шаг выбора один.

Доводы за:

- **Нет лишнего клика**, про который было сомнение: самый частый случай (первый способ — карта) — один
  клик вместо двух.
- **Нет состояния «группа выбрана, способ нет».** Иначе нужна новая ошибка в `check()`, обработка в
  `summary()` и в «Place the order» (решение 68 базы). С предложением шаг всегда готов.
- **Порядок становится инструментом магазина:** менеджер ставит первым то, что выгоднее.
- **Выбор виден:** подсписок открывается с отмеченным пунктом прямо под нажатием, а итог заказа называет
  способ. Шлюз показывает покупателю свою страницу, поэтому случайный выбор не приводит к оплате.

Довод против: покупатель может не заметить подсписок и заплатить не тем способом. Ошибка дешёвая: на
странице шлюза можно уйти назад, а «Выбрать другой способ» остаётся.

Что при этом верно:

- При первом открытии ничего не выбрано, кроме случая одного способа (как сейчас). Первая запись —
  после действия покупателя.
- Снова открыл группу — снова первый способ: памяти о прошлом выборе нет, она усложнила бы правило.
- «Первый» — первый видимый: скрытые кошельки (§4.3) пропускаются.

### 6.4. Запись выбора

Форма шлёт `group` и `method`. Правило на сервере одно: **`method` из группы `group` — он; иначе первый
доступный способ группы.** Оно нужно только без скрипта: радиокнопка `method` прошлой группы уходит
вместе с формой, а у строки одного способа её нет совсем. `PUT /api/payments/selection` принимает то
и другое, скрипт шлёт только `method`.

Без JavaScript работает всё то же: раскрытие на CSS, «Save» отправляет форму, кошельки не скрываются.
Отдельного вида нет.

### 6.5. Скрипт

`step.js` делится: общая часть — `methods.js` (группа → первый способ, кошельки §4, сборка группы в одну
строку); запись и событие `webx:checkout:slot-changed` остаются в `step.js`. `MutationObserver` уже
оживляет шаг после перерисовки. **`data-autosave` единственного способа ждёт ответа кошельков.**

### 6.6. Подпись и комиссия

Подпись строки — `Presentation::$note` способа: описание или слово типа, например комиссия службы у
`store.on_receipt` (§12.1 базы). Отдельного поля комиссии нет: `price` в блоке заказа — `null` (§10.4
базы). Подпись шапки группы с подсписком — `description` группы, пустая — без строки.

### 6.7. Ширина, тема, доступность

- **Ширину решает контейнер** `webx-payments` (он уже есть), а не окно: порог 480 px. Значки у строки
  способа остаются справа на любой ширине, текст переносится.
- **Цвета только токенами `--site-*`.** Значки свои цвета держат в файле (§3.3).
- **Тёмная тема:** подложка значка белая. Радиокнопку красит тема через `color-scheme`, в
  `theme-default` тёмной схемы нет — вопрос 7 §11.
- **Высота строки ≥ 44 px** (замер §9), вся строка — `label`.
- **Клавиатура — родные радиокнопки, `role` не нужен.** Две группы радио: `name="group"` и `name="method"`.
  Стрелки ходят по группам и сразу выбирают; Tab из группы переходит на отмеченный способ подсписка,
  стрелки — по способам. Скрытый подсписок не в порядке обхода (`display: none`).
- **Читалка:** `fieldset` + `legend` на обоих уровнях, у значка `alt`. Смена выбора объявляется родным
  поведением радио; подсписок идёт в DOM сразу за шапкой.

### 6.8. Страница оплаты

- `PayPage::others()` отдаёт `MethodOption`, а не `{ key, title }`; `pay/others.blade.php` рисует
  `<x-webx-payments::methods>` внутри того же `details`. Текущий способ заказа в списке не участвует, и
  группа, где он был один, пропадает.
- **Выбор здесь не пишется сразу:** смена способа сразу уводит в шлюз (§8.5 базы), поэтому под списком —
  кнопка **«Continue»**. Форма идёт на `POST /pay/{number}/method`, контроллер принимает то же
  `group` + `method` по правилу §6.4.
- `methods.js` подключается и на странице оплаты: иначе Apple Pay останется на Android.
- **«Оплатить онлайн сейчас»** у заказа «при получении» по §8.4 базы — отдельные кнопки, на lab их шесть.
  Предложение: тот же компонент только с онлайн-способами — вопрос 6 §11.

## 7. Панель

Читать перед этапом: [`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md). Отдельного экрана нет: группы — блок
экрана `payments.methods`, где менеджер и так расставляет способы.

- **`MethodsPage.vue`:** левая колонка — группы по порядку. У группы — ручка, пиктограмма, название,
  «Изменить»; под ней `WxSortableList` с её способами. Все списки с одним `group="payment-methods"`:
  проп уже есть, способ перетаскивается между группами. Группы — внешний `WxSortableList`.
- **Пустая группа** принимает способ: подпись пустого списка вместо `WxEmpty`.
- **Диалог группы:** название и описание (`localized`), пиктограмма — `WxRadioGroup` с превью набора §2.5
  (`WxIconPicker` здесь не подходит: у него набор ядра, а не сайта).
- **Форма способа:** поле «Группа» (`wx-select`) в карточке `rules`: «По умолчанию (Оплата онлайн)» и три

  сверить с `delivery_mode` на этапе 6 §10.
- **`group_key` нормализуется:** перенос в группу типа пишет `null`, и способ снова следует за типом.
- **Значки** показываются в строке способа только для чтения: менеджер их не настраивает (решение 2).
- **Маршруты:** `GET groups`, `PUT groups/{key}`; `PUT methods/order` принимает
  `{ groups: [{ key, methods: [id…] }] }` и порядок групп вместе со способами, одной транзакцией.
- **Права:** чтение — `payments.view`, запись — `payments.manage`, нового права нет. Маршруты — `cms.can`,
  `AccessCoverageTest` зелёный.
- **Кеш:** `PaymentGroup` — в `bumpOn`. Массовая запись порядка событий модели не шлёт, поэтому `bump()`
  руками; тест свежести — на порядок групп и на перенос способа.

## 11. Открытые вопросы

Решает человек.

1. **Выбор группы.** Предложение — сразу первый способ (§6.3). Нужно подтвердить.
2. **Файлы значков.** Рисовать нельзя, а скачать их из Brand Center Visa и Mastercard может только
   человек. И главное: можно ли класть чужие знаки в публичный MIT-репозиторий? Правила разрешают показ
   принимающему продавцу, а раздачу в пакете — не обязательно. Варианты:
   - файлы в пакете `module-payments` с отдельной заметкой, что знаки не под MIT;
   - файлов в репозитории нет, сайт кладёт их сам — но это спорит с решением 2 («менеджер не грузит»).

   Предложение — первый вариант, если нет возражений юридического характера. Это не юридическое
   заключение: при сомнении лучше спросить у эквайера или юриста.

3. **Значки у открытой группы на узком экране.** Предложение — не показывать, они стоят ниже (§3.4).
   Решение 2 говорит «у группы справа — все значки»; если это строго — шапка на 360 px выше на две строки.
4. **Свои группы.** Предложение — не в v1 (решение 12): просьбы не было, а удаление группы со способами
   добавляет правила. Если понадобятся, таблица уже готова: нужны создание, удаление и возврат способов к
   группе типа.
5. **`pay.js` на оформлении.** Чужой скрипт ради способа, который скрывается редко. Предложение —
   оставить, он грузится только при способе «только Google Pay». Другой вариант — не проверять Google Pay
   вовсе и показывать всегда; решение 4 тогда выполняется только для Apple Pay.
6. **«Оплатить онлайн сейчас»** тем же компонентом вместо отдельных кнопок (§6.8). Решение 6 говорит только
