# Группы способов оплаты и значки платёжных систем — спецификация

Статус: принята человеком (webx-ui#114), реализация — webx-ui#116: этапы 1–7 плана §10 сделаны, этап 8 —\nприёмка на настоящих устройствах.
Спека дополняет [`WEBX_UI_MODULE_PAYMENTS.md`](WEBX_UI_MODULE_PAYMENTS.md): контракт способа §6,
список для покупателя §7, страница оплаты §8.4–§8.5, шаг оформления §10, панель §13, MCP §16, кеш
§18. Спутник LiqPay — [`WEBX_UI_PAYMENT_LIQPAY.md`](WEBX_UI_PAYMENT_LIQPAY.md) (решение 3, §6),
что умеют шлюзы — [`WEBX_UI_PAYMENT_GATEWAYS.md`](WEBX_UI_PAYMENT_GATEWAYS.md).

Сейчас шаг «Оплата» — плоский список одинаковых плашек. С несколькими шлюзами и несколькими способами
у каждого он становится длинным и непонятным. Покупатель должен видеть 3–4 понятные группы, а внутри
выбранной — конкретные способы.

```
○ Оплата при отриманні        [иконка]   пояснение / комиссия перевозчика
● Онлайн оплата               VISA ●● GPay  Pay
    ● Картою онлайн           VISA ●●
    ○ Google Pay              GPay
    ○ Apple Pay               Pay
    ○ monobank                mono
    ○ Миттєва розстрочка      ПриватБанк
○ Рахунок для підприємств     [иконка]
```

## 1. Решения

Решения человека (04.11.2026, спецификация задачи и разбор §11). Не пересматриваются.

1. **Группы по смыслу — из коробки.** База даёт готовые группы, каждый тип объявляет свою группу по
   умолчанию, способ попадает туда сам. В панели группу можно переименовать, переставить, сменить
   пиктограмму и описание; способ можно перенести. Создавать и удалять группы в панели нельзя (решение
   12). Сайт с одним-двумя способами про группы не думает.
2. **Значки ставит спутник** по включённым настройкам способа. Выключил — значок пропал. У способа —
   его значки, у группы справа — все значки её способов; у раскрытой группы на узком экране в шапке
   их нет, они ниже у способов. Менеджер картинок не грузит. У группы — простая пиктограмма, меняется
   в панели.
3. **Только два уровня: группа → способ.** «Через Google Pay» и «через Apple Pay» — отдельные способы
   того же типа с одной галочкой, рядом с остальными в группе. Группа с одним способом — одна строка.
4. **Способ «только Apple Pay» — только там, где Apple Pay возможен.** Проверка встроенная в браузер
   (`ApplePaySession`), без чужого кода. Не сработала — способ показывается: оплату терять нельзя.
   **Способ «только Google Pay» показывается всегда:** чужой скрипт `pay.js` на оформление не грузим.
5. **Несколько шлюзов не запрещаем.** Панель предупреждает о похожих пунктах и не мешает сохранить.
   Название шлюза покупателю не показываем, если магазин сам так не назвал способ.
6. **«Выбрать другой способ» на странице оплаты** — тот же сгруппированный вид, тот же компонент.

Решения этой спеки (приняты вместе с ней):

7. **Группа способа — вычисляемая.** В строке способа хранится только перенос менеджера; `null` —
   группа типа. Существующим способам миграция ничего не пишет (§2.4).
8. **Значки — единственный источник для всего остального.** «Только Apple Pay» (§4) и похожесть (§5)
   выводятся из `marks()`: второго объявления у спутника нет.
9. **Строка одного способа показывает способ, а не группу.** Название, подпись и значки — способа;
   от группы только пиктограмма. Поэтому сайт с двумя способами в разных группах читается как сегодня,
   а «Оплата на кассе» при самовывозе (§12.1 базы) не теряется.
10. **Группа одна — шапки нет.** Все способы сайта в одной группе — плоский список, как сейчас.

Решения человека по вопросам спеки (04.11.2026):

11. **Выбор группы сразу выбирает её первый видимый способ** (§6.3).
12. **Свои группы — через конфиг сайта.** `config/webx-payments.php` задаёт список групп; три из коробки
    описаны там же, их можно переопределить или убрать. Панель правит группы поверх конфига, но не
    создаёт и не удаляет их. Группа пропала из конфига — её способы возвращаются в группу своего типа
    (§2.1, §2.7).
13. **Файлы значков — из Simple Icons,** в пакете `module-payments` с отдельной заметкой о товарных
    знаках. Человек ничего не скачивает. Чего в коллекции нет — текстовая плашка (§3.2, §3.3).
14. **«Оплатить онлайн сейчас»** у заказа «при получении» — тем же компонентом вместо отдельных кнопок
    (§6.8).
15. **Тёмная схема `theme-default`** — отдельная задача позже. Здесь тёмный вид проверяется на временной
    схеме, как в макете.
16. **Страница LiqPay с `apay` вне Safari и `gpay` без Google Pay** проверяется на этапе 8 §10.

## 2. Модель групп

### 2.1. Конфиг и таблица `payment_groups`

**Какие группы есть, решает конфиг сайта; как они называются и стоят — панель** (решение 12). Конфиг —
решение разработчика сайта, поэтому он в коде и едет с деплоем. Правки менеджера — данные: им нужны
языковые поля, порядок и кеш той же группы `payments`, поэтому они в таблице, а не в конфиге.

```php
// config/webx-payments.php
'groups' => [
    'on_receipt' => ['title' => 'webx-payments::groups.on_receipt', 'pictogram' => 'cash'],
    'online' => ['title' => 'webx-payments::groups.online', 'pictogram' => 'card'],
    'transfer' => ['title' => 'webx-payments::groups.transfer', 'pictogram' => 'document'],
],
```

- **Ключ массива** — ключ группы, навсегда. Порядок массива — порядок групп по умолчанию.
- **`title`** — ключ словаря или готовая строка: `__()` вернёт её как есть. Своя группа сайта
  переводится словарём сайта.
- **`pictogram`** — имя из набора §2.5. Неизвестное имя — группа без пиктограммы и предупреждение
  `webx:doctor`.
- **`mergeConfigFrom` сливает только верхний уровень**, поэтому `groups` в конфиге сайта заменяет список
  целиком. Это и нужно: чего там нет, того на сайте нет. Сайт без своего `groups` получает три группы.

Таблица хранит только правки. Строка появляется при первой правке группы в панели, а её пустое поле
значит «как в конфиге»:

| Колонка                    | Тип                     | Примечание                                                  |
| -------------------------- | ----------------------- | ----------------------------------------------------------- |
| `id`                       | bigint                  |                                                             |
| `key`                      | string(64), **unique**  | ключ из конфига                                             |
| `title`                    | json, null              | название по языкам; нет языка — `title` конфига             |
| `description`              | json, null              | подпись под названием; в конфиге подписи нет                |
| `pictogram`                | string(32), null        | имя из набора §2.5; `null` — `pictogram` конфига            |
| `position`                 | smallint unsigned, null | ручной порядок; `null` — после упорядоченных, как в конфиге |
| `created_at`, `updated_at` | timestamp               |                                                             |

**Группа пропала из конфига.** Её строка остаётся и игнорируется: `MethodGroups` идёт по конфигу, а не
по таблице. Вернётся ключ — вернутся и правки менеджера. Чистить строки незачем: их единицы.

К `payment_methods` добавляется `group_key` — string(64), null, без внешнего ключа: `null` значит
«группа типа» (решение 7). Индекс не нужен: включённые способы читаются целиком и лежат в кеше (§18
базы).

### 2.2. Группы из коробки

| Ключ         | en             | ru            | uk             | Пиктограмма |
| ------------ | -------------- | ------------- | -------------- | ----------- |
| `on_receipt` | Pay on receipt | При получении | При отриманні  | `cash`      |
| `online`     | Pay online     | Оплата онлайн | Оплата онлайн  | `card`      |
| `transfer`   | Bank transfer  | По реквизитам | За реквізитами | `document`  |

Названия — в новом файле словаря `webx-payments::groups`, на всех языках пакета (`de en es fr it pl
pt ru tr uk`). Описаний по умолчанию нет: база не знает, что именно включил магазин, а неверная
подпись хуже пустой. Описание пишет менеджер.

### 2.3. Как тип объявляет группу

Новая возможность — необязательный интерфейс (§6.4 базы), старые спутники не ломаются:

```php
namespace WebxUi\Payments\Contracts;

/** A type whose methods belong elsewhere than its kind suggests (groups spec §2.3). */
interface DeclaresGroup
{
    /** A key of `MethodGroups`: one of the site's groups, `config('webx-payments.groups')`. */
    public function defaultGroup(): string;
}
```

Без интерфейса группу даёт вид типа, и этого хватает почти всем:

| Тип                                   | `kind()`  | `awaitsPayment()` | Группа       |
| ------------------------------------- | --------- | ----------------- | ------------ |
| спутник шлюза, `liqpay.checkout`      | `Online`  | —                 | `online`     |
| `store.on_receipt`, наложенный платёж | `Offline` | `false`           | `on_receipt` |
| `store.bank_transfer`                 | `Offline` | `true`            | `transfer`   |

Встроенным типам и спутнику LiqPay править ничего не надо. Интерфейс — для исключений: например,
счёт для юрлиц, который выставляет онлайн-шлюз, объявит `transfer`. Неизвестный ключ из
`defaultGroup()` — группа по виду и предупреждение `webx:doctor`.

**Группы типа на сайте нет** (сайт убрал `transfer` из конфига, а способ такого типа включён) — способ
встаёт в первую группу конфига, `webx:doctor` предупреждает. Способ не пропадает ни при какой правке
конфига. Пустой `groups` — групп нет, плоский список (решение 10).

### 2.4. Миграция

- Миграция создаёт таблицу и колонку `group_key`. **Способы не трогает:** у всех
  `group_key = null`, и каждый сразу в группе своего типа (решение 7). Новый спутник так же попадает
  на место сам.
- **Порядок групп на уже настроенном сайте.** Сегодня порядок один на все способы; чтобы первый пункт
  покупателя остался первым, миграция создаёт строки групп с `position` по наименьшей `position`
  включённых способов, группа ищется через реестр типов. Включённых нет, тип неизвестен — строк нет,
  порядок конфига.
- Откат убирает колонку и таблицу. Правки и переносы менеджера при этом теряются — способы всё равно
  плоские.
- **Что заметит покупатель.** Способы одной группы теперь идут подряд: порядок вида «карта, при
  получении, рассрочка» станет «карта, рассрочка, при получении». Это смысл группировки, но об этом
  стоит написать в changeset.

### 2.5. Пиктограммы

Свой набор в пакете: `card`, `cash`, `document`, `bank`, `wallet`, `truck`, `store`, `qr`. Файлы —
`resources/views/icons/*.blade.php`, вывод — `<x-webx-payments::pictogram>`, `currentColor`, размер
24 px. Так устроены иконки виджетов: у `webx-ui/module-payments` нет зависимости от тем, а в спрайте
`theme-default` карты, купюры и документа нет. Тема переопределяет вид по обычному пути
`<layer>/views/vendor/webx-payments/`. Вне набора имя панель не сохраняет; конфиг — §2.1.

`icon` способа (картинка из медиатеки, §5 базы) остаётся: если задана, она стоит на месте пиктограммы
в строке одного способа и перед названием в подсписке.

### 2.6. Чтение и порядок

- **`WebxUi\Payments\MethodGroups`** — группы конфига с правками таблицы. В кеше только строки таблицы:
  `remember('payments.groups', ['payments'], …)`, `localized: false`; модель `PaymentGroup` — в `bumpOn`
  группы `payments`. Слияние с конфигом — при чтении: иначе правка конфига ждала бы сброса кеша.
- **`Method`** получает `groupKey` — то, что в строке. Реестра типов у него нет, поэтому действующую
  группу считает `Methods::option()`: `groupKey`, если группа есть в конфиге; иначе группа типа; нет и
  её — первая группа конфига (§2.3). Перенос на неизвестный ключ идёт по группе типа, строка способа
  при этом не меняется: вернётся ключ — вернётся и перенос.
- **`MethodOption`** получает `group`, `marks` и `applePayOnly` (§4.1); `toArray()` их отдаёт, поэтому
  `GET /api/payments/methods` дополнительно получает `groups`.
- **`Methods::grouped(list<MethodOption>): list<MethodGroupView>`** — чистая функция, без запросов.
  Принимает уже отфильтрованный список, поэтому шаг и страница оплаты зовут её с разными наборами.
  Группы идут по `position`, затем по порядку конфига; способы внутри — по `position` способа. Значки группы —
  объединение значков её способов без повторов, в порядке реестра §3.2.
- **Запросов на тёплом кеше не прибавляется:** бюджет шага остаётся 1 (§18 базы).

### 2.7. Пустая группа

| Что с группой                                 | Покупатель                  | Панель                                |
| --------------------------------------------- | --------------------------- | ------------------------------------- |
| нет способов                                  | не видит                    | видит, можно перетащить в неё         |
| все способы выключены                         | не видит                    | видит, способы приглушены             |
| все способы недоступны для заказа (§7.1 базы) | не видит                    | `payments_available` называет причину |
| остался один способ                           | одна строка (решение 3)     | без изменений                         |
| осталась одна группа                          | плоский список (решение 10) | без изменений                         |
| группа убрана из конфига                      | способы в группе типа       | не видит; `webx:doctor` называет ключ |

Отдельного выключателя у группы нет: группу выключают её способы, а убирает с сайта конфиг.

## 3. Значки

### 3.1. Контракт спутника

```php
namespace WebxUi\Payments\Contracts;

/** A type that can say which payment systems a method takes (groups spec §3). */
interface ProvidesPaymentMarks
{
    /**
     * Keys of `PaymentMarks` the method offers the buyer right now, read from its settings.
     * Cheap and pure: no gateway call, no database.
     *
     * @return list<string>
     */
    public function marks(Method $method): array;
}
```

Аргумент — `Method`, а не массив настроек: тип и так работает с неизменяемым `Method` (§6.1 базы).
Тип без интерфейса значков не показывает. Неизвестный ключ пропускается, `webx:doctor` предупреждает.

### 3.2. Реестр значков

`WebxUi\Payments\PaymentMarks` — ключ, название для `alt`, файл или ничего. Порядок реестра — порядок
показа. Спутник может добавить свой значок: `PaymentMarks::register()` с файлом своего пакета, как типы
и шлюзы в `callAfterResolving` (§14.1 базы).

| Ключ         | `alt`      | Файл             | Кто даёт                                            |
| ------------ | ---------- | ---------------- | --------------------------------------------------- |
| `visa`       | Visa       | `visa.svg`       | LiqPay и все шлюзы обзора                           |
| `mastercard` | Mastercard | `mastercard.svg` | LiqPay и все шлюзы обзора                           |
| `apple-pay`  | Apple Pay  | `applepay.svg`   | LiqPay, mono, WayForPay, Portmone, NovaPay, iPay.ua |
| `google-pay` | Google Pay | `googlepay.svg`  | LiqPay, mono, WayForPay, Portmone, NovaPay, iPay.ua |
| `privat24`   | Приват24   | нет: плашка      | LiqPay                                              |
| `privatbank` | ПриватБанк | нет: плашка      | рассрочка: LiqPay, прямой спутник                   |
| `mono`       | monobank   | нет: плашка      | спутник mono                                        |

**Файлы** берутся из [Simple Icons](https://simpleicons.org/) один раз и лежат в репозитории:
`resources/marks/*.svg` пакета `module-payments`, зависимости от `simple-icons` нет. Значок — путь из
коллекции на белой карточке 38 × 24, цвет — `hex` этого знака из данных коллекции. Отдаются маршрутом
`webx/payments/marks/{key}.svg` с адресом по хешу и вечным кешем, как `step.js` (`ScriptController`).
В строке — `<img width="38" height="24" alt="Visa">`: значки повторяются у группы и способа, и инлайн
раздул бы каждую перерисовку шага.

**Чего в коллекции нет.** Проверено на версии 16.36.0: Приват24, ПриватБанка, monobank нет; из шлюзов нет
и LiqPay, NovaPay, WayForPay, Portmone, iPay.ua, но им значок и не нужен (решение 5). Такой ключ
рисуется **текстовой плашкой**: `<span class="webx-payments__mark is-text">Приват24</span>` той же
высоты 24 px, цвета — токены темы. Появится файл — ключу в реестре дописывается файл, остальное не
меняется.

**Заметка о знаках** — `resources/marks/NOTICE.md`, ссылка на неё в `README.md` пакета:

> The trademarks shown by these files belong to their owners and are not covered by the MIT licence of
> this package. The SVG files come from Simple Icons (CC0), version 16.36.0.

| Google Pay | только файл Google, не перекрашивать контур; не меньше значков других систем; «Pay» не переводить   | [Brand guidelines](https://developers.google.com/pay-wallet/products/api/web/guides/best-practices/brand-guidelines)                                                                                                |

| Google Pay | «Use only the mark provided by Google», «Don't create your own mark or alter it in any way». Про одноцветный вариант ни слова | страница прочитана                               |
| Apple Pay  | только файл Apple, меняется лишь высота; нельзя делать свою версию знака                                                      | выдержки поиска; страницы Apple не открылись     |
| Mastercard | символ приёма карт — только в полном цвете; сплошной и серый — при технических ограничениях                                   | выдержки поиска; Brand Center ответил 403        |
| Visa       | только файлы Brand Center, синий на сайтах                                                                                    | с первой попытки этапа; PDF сейчас не прочитался |

Смягчает только одно: старые правила Mastercard для Masterpass разрешали одноцветный знак там, где все
способы оплаты тоже одноцветные, и цвет каждого значка взят из его бренда (§3.2): Visa остаётся синей.
Полного соответствия это не даёт. Что с этим делать — вопрос 1 §11, этап 2 он не задерживает: значок — один
файл, замена не трогает код.

**Лицензия.** Коллекция Simple Icons — CC0, но её [отказ от ответственности](https://github.com/simple-icons/simple-icons/blob/develop/DISCLAIMER.md)
оговаривает, что CC0 коллекции не значит CC0 каждого значка, и просит смотреть поле `license` в данных. У
четырёх наших значков его нет, а отсутствие, по той же оговорке, ни о чём не говорит. Права на сами знаки
CC0 в любом случае не передаёт, об этом и заметка §3.2.

Из правил следует:

- **Один размер для всех:** 38 × 24 px, плашка — той же высоты. Требование равенства есть и у Google, и у
  Mastercard.
- **Подложка — часть файла, а не темы.** Значок — готовая карточка со своим белым полем: в тёмной теме
  он остаётся белым, а CSS не хранит цветов. Тема значки не красит.
- **Поле вокруг.** Apple просит четверть высоты знака: при 24 px это 6 px. Зазор между значками —
  `--site-space-2` (8 px); если в файле знак меньше карточки, сверить на настоящих файлах (этап 2 §10).
- **Значок не кнопка:** он внутри `label` строки и сам по себе не нажимается.
- **Без искажений:** путь коллекции не правится, знак только масштабируется с сохранением пропорций.
- **Минимальные размеры Mastercard и Visa** на этом этапе не сверены. Сверить вместе с файлами.

Макет нарочно показывает серые плашки со словом, а не логотипы.

### 3.4. Что показывается

- **Строка способа** — значки `marks()` этого способа.
- **Строка группы** — объединение значков её способов (§2.6). Шире нет смысла ограничивать: ключей
  всего семь, а на узкой ширине значки переносятся.
- **Узкий шаг (контейнер < 480 px).** У закрытой группы значки уходят строкой под текст. У открытой
  группы их в шапке нет (решение 2): те же значки стоят ниже у способов, а на шести значках шапка
  выходила в 153 px.
- **Значок Apple Pay виден там же, где возможен Apple Pay** (§4.3). Значок Google Pay виден всегда.

### 3.5. LiqPay: `paytypes` → значки

`LiqPayCheckoutType` реализует `ProvidesPaymentMarks` по семи полям §6 спеки LiqPay:

| Поле              | `paytypes`    | Значки               |
| ----------------- | ------------- | -------------------- |
| `pay_card`        | `card`        | `visa`, `mastercard` |
| `pay_apay`        | `apay`        | `apple-pay`          |
| `pay_gpay`        | `gpay`        | `google-pay`         |
| `pay_privat24`    | `privat24`    | `privat24`           |
| `pay_qr`          | `qr`          | —                    |
| `pay_moment_part` | `moment_part` | `privatbank`         |
| `pay_paypart`     | `paypart`     | `privatbank`         |

- У `qr` общего знака нет, поэтому значка нет.
- **Ни одной галочки:** `paytypes` не уходит, страница покажет настройки кабинета (§6 спеки LiqPay).
  Что там включено, база не знает, поэтому `marks()` пуст.
- Что принадлежность рассрочек ПриватБанку верна для обоих полей, сверяется с документацией LiqPay на
  этапе 2 §10.

## 4. Видимость Apple Pay и Google Pay

**Скрывается только Apple Pay** (решение 4). Google Pay показывается всегда: проверить его можно только
библиотекой Google `pay.js`, а чужой скрипт на оформлении не стоит способа, который скрывался бы редко.

### 4.1. Как способ это объявляет

Отдельного объявления нет (решение 8). **Способ «только Apple Pay» — тот, чей единственный значок —
`apple-pay`.** База считает `MethodOption::$applePayOnly` сама:

| `marks()`                         | `applePayOnly` | Где виден                             |
| --------------------------------- | -------------- | ------------------------------------- |
| `apple-pay`                       | да             | где есть Apple Pay                    |
| `google-pay`                      | нет            | везде                                 |
| `apple-pay`, `google-pay`         | нет            | везде: Google Pay показывается всегда |
| `visa`, `mastercard`, `apple-pay` | нет            | везде: карта работает везде           |
| пусто                             | нет            | везде                                 |

Строка несёт `data-apple-pay-only`. Запросов к шлюзам нет: всё решается в браузере покупателя.

### 4.2. Проверка в браузере

Общий скрипт `methods.js` (§6.5). Ответ — один из трёх: да, нет, не знаю. **«Не знаю» значит показать**
(решение 4).

```js
function applePay() {
  if (!('ApplePaySession' in window)) return false // Chrome on Android: the API is not there at all
  try {
    return window.ApplePaySession.canMakePayments()
  } catch {
    return null // an insecure page, a frame: the check did not work
  }
}
```

`canMakePayments()` без аргументов отвечает, умеет ли устройство Apple Pay. Наличие карты в Wallet она
не проверяет, и это нам подходит: покупатель сможет добавить карту. Что идентификатор продавца ей не
нужен, известно из описания метода; страница документации Apple на этапе не открылась, проверить на
этапе 4 §10.
Отсутствие `ApplePaySession` — это ответ «нет», а не сбой: иначе на Android скрывать было бы нечего.

Проверка синхронная, внешних скриптов и таймаутов нет, поэтому запоминать ответ незачем: после
перерисовки шага она просто выполняется снова.

### 4.3. Что скрывается

Ответ «нет» убирает:

1. строки способов с `data-apple-pay-only`;
2. значок `apple-pay` — и у способов, и у групп: на Android он обещал бы то, чего нет;
3. группу без оставшихся способов.

Оставшийся один способ собирает группу в одну строку: скрипт переносит в шапку название, подпись и
значки этого способа (решение 3).

**Без скрипта или при сбое строки видны:** скрывать сначала значило бы потерять способ. Ответ синхронный,
поэтому скачка почти нет.

**Если скрыть пришлось бы всё** — ничего не скрывается. Магазин, где единственный способ — Apple Pay,
покажет его и на Android: пустой шаг не даст оформить заказ вовсе (решение 4).

**Выбранный способ оказался скрыт** (выбрал на iPhone, продолжил на компьютере; корзина та же):

- скрипт отмечает первый видимый способ той же группы и записывает его;
- в группе никого не осталось — снимает выбор новым `DELETE /api/payments/selection`, и покупатель
  выбирает заново. Шаг при этом просто не готов, как при первом открытии.

Макет этот случай показал наглядно: группа открыта, а способ не отмечен.

**Сервер Apple Pay не проверяет.** Он не знает устройства покупателя. `check()` пропускает такой способ,
и если скрипт не сработал, покупатель попадёт на страницу шлюза — это и есть «не терять оплату».

**Что покажет страница LiqPay** с `apay` вне Safari и с `gpay` без Google Pay, на этом этапе не
проверялось (решение 16). Способ «только Google Pay» попадёт туда на любом устройстве, поэтому ответ
важен именно для него. Apple Pay может предлагать вход через QR-код вне Safari: тогда скрытие убирает
возможный путь, но карта остаётся.

## 5. Предупреждение о похожих способах

**Похожи** два включённых способа одной группы с **одинаковым непустым набором значков** (порядок не
важен). Это покрывает пример решения 5: Google Pay через LiqPay и через mono — оба `{google-pay}`, и
две карты разных шлюзов — оба `{visa, mastercard}`.

Не считается похожим: «карта с Apple Pay» рядом с «только Apple Pay». Наборы разные, и покупатель
видит разные пункты: именно так выглядит набросок задачи.

- **Код:** `SimilarMethods::of(list<Method>): array<string, list<string>>` — чистая функция, ключ способа
  → ключи похожих. Способы без `ProvidesPaymentMarks` в сравнении не участвуют.
- **Список способов:** значок-предупреждение в строке и подсказка с именем похожего способа.
- **Форма способа:** `WxAlert` уровня `warning` над полями — слова «This group already has a method with
  Google Pay: the buyer will see two similar items. Tell them apart by title, for example “Google Pay via
  monobank”.» Для набора из нескольких значков — «…a method with the same payment systems…».
- **Ответ сохранения** несёт `warnings`; панель показывает его и в тосте. **Сохранение не блокируется.**
- Выключенный способ не предупреждает, пока его не включат.

## 6. Вид для покупателя

Проверено на макете — §9. Один компонент `<x-webx-payments::methods>` на все места (решение 6).

### 6.1. Разметка

```html
<fieldset class="webx-payments__groups">
  <legend class="webx-payments__methods-title">Payment method</legend>

  <div class="webx-payments__group" data-group="online">
    <label class="webx-payments__group-head">
      <input class="webx-payments__radio" type="radio" name="group" value="online" />
      <svg class="webx-payments__pictogram" aria-hidden="true">…</svg>
      <span class="webx-payments__row-text">
        <span class="webx-payments__row-title">Pay online</span>
        <span class="webx-payments__row-note">Card, wallet or instalments</span>
      </span>
      <ul class="webx-payments__marks">
        <li data-mark="visa"><img class="webx-payments__mark" src="…" alt="Visa" /></li>
      </ul>
    </label>

    <fieldset class="webx-payments__group-methods">
      <legend class="visually-hidden">Pay online</legend>
      <label class="webx-payments__option">
        <input class="webx-payments__radio" type="radio" name="method" value="gpay" />
        …
      </label>
    </fieldset>
  </div>
</fieldset>
```

- **Группа с одним способом** — та же шапка с данными способа и `data-method`, подсписка нет. Группа
  одна — только строки `__option`, без шапок (решение 10).
- **Классы — `webx-payments__*`, как в коде.** §10.3 базы говорит `.wx-payments-*`, но `payments.css` и
  шаблоны давно на `webx-payments`; новые классы — как в коде, все в `AGENTS.md`.

### 6.2. Раскрытие — на CSS

Подсписок открыт правилом `.webx-payments__group:has(> .webx-payments__group-head input:checked)`.
Скрипт для этого не нужен, поэтому при загрузке ничего не прыгает. Браузер без `:has()` показывает все
подсписки открытыми (`@supports not selector(:has(*))`): длиннее, но работает.

### 6.3. Выбор группы с несколькими способами

**Сразу выбран первый видимый способ группы, по порядку менеджера** (решение 11). Шаг выбора один.

Доводы:

- **Нет лишнего клика**, про который было сомнение: самый частый случай (первый способ — карта) — один
  клик вместо двух.
- **Нет состояния «группа выбрана, способ нет».** Иначе нужна новая ошибка в `check()`, обработка в
  `summary()` и в «Place the order» (решение 68 базы). С предложением шаг всегда готов.
- **Порядок становится инструментом магазина:** менеджер ставит первым то, что выгоднее.
- **Выбор виден:** подсписок открывается с отмеченным пунктом прямо под нажатием, а итог заказа называет
  способ. Шлюз показывает покупателю свою страницу, поэтому случайный выбор не приводит к оплате.

Что принято в расчёт: покупатель может не заметить подсписок и заплатить не тем способом. Ошибка дешёвая: на
странице шлюза можно уйти назад, а «Выбрать другой способ» остаётся.

Что при этом верно:

- При первом открытии ничего не выбрано, кроме случая одного способа (как сейчас). Первая запись —
  после действия покупателя.
- Снова открыл группу — снова первый способ: памяти о прошлом выборе нет, она усложнила бы правило.
- «Первый» — первый видимый: скрытый Apple Pay (§4.3) пропускается.

### 6.4. Запись выбора

Форма шлёт `group` и `method`. Правило на сервере одно: **`method` из группы `group` — он; иначе первый
доступный способ группы.** Оно нужно только без скрипта: радиокнопка `method` прошлой группы уходит
вместе с формой, а у строки одного способа её нет совсем. `PUT /api/payments/selection` принимает то
и другое, скрипт шлёт только `method`.

Без JavaScript работает всё то же: раскрытие на CSS, «Save» отправляет форму, Apple Pay не скрывается.
Отдельного вида нет.

### 6.5. Скрипт

`step.js` делится: общая часть — `methods.js` (группа → первый способ, Apple Pay §4, сборка группы в одну
строку); запись и событие `webx:checkout:slot-changed` остаются в `step.js`. `MutationObserver` уже
оживляет шаг после перерисовки. **`data-autosave` единственного способа идёт после проверки Apple Pay.**

### 6.6. Подпись и комиссия

Подпись строки — `Presentation::$note` способа: описание или слово типа, например комиссия службы у
`store.on_receipt` (§12.1 базы). Отдельного поля комиссии нет: `price` в блоке заказа — `null` (§10.4
базы). Подпись шапки группы с подсписком — `description` группы, пустая — без строки.

### 6.7. Ширина, тема, доступность

- **Ширину решает контейнер** `webx-payments` (он уже есть), а не окно: порог 480 px. Значки у строки
  способа остаются справа на любой ширине, текст переносится.
- **Цвета только токенами `--site-*`.** Значки свои цвета держат в файле (§3.3).
- **Тёмная тема:** подложка значка белая. Радиокнопку красит тема через `color-scheme`. В `theme-default`
  тёмной схемы нет, этап 3 проверяет тёмный вид на временной схеме (решение 15).
- **Высота строки ≥ 44 px** (замер §9), вся строка — `label`.
- **Клавиатура — родные радиокнопки, `role` не нужен.** Две группы радио: `name="group"` и `name="method"`.
  Стрелки ходят по группам и сразу выбирают; Tab из группы переходит на отмеченный способ подсписка,
  стрелки — по способам. Скрытый подсписок не в порядке обхода (`display: none`).
- **Читалка:** `fieldset` + `legend` на обоих уровнях, у значка `alt`. Смена выбора объявляется родным
  поведением радио; подсписок идёт в DOM сразу за шапкой.

### 6.8. Страница оплаты

- `PayPage::others()` отдаёт `MethodOption`, а не `{ key, title }`; `pay/others.blade.php` рисует
  `<x-webx-payments::methods>` внутри того же `details`. Текущий способ заказа в списке не участвует, и
  группа, где он был один, пропадает.
- **Выбор здесь не пишется сразу:** смена способа сразу уводит в шлюз (§8.5 базы), поэтому под списком —
  кнопка **«Continue»**. Форма идёт на `POST /pay/{number}/method`, контроллер принимает то же
  `group` + `method` по правилу §6.4.
- `methods.js` подключается и на странице оплаты: иначе Apple Pay останется на Android.
- **«Оплатить онлайн сейчас»** у заказа «при получении» — тот же компонент и та же кнопка «Continue»
  вместо отдельных кнопок, на lab их было шесть (решение 14). В списке все способы заказа, кроме его
  собственного: есть онлайн — `details` раскрыт и называется «Оплатить онлайн сейчас», нет — закрыт и
  называется «Выбрать другой способ».

## 7. Панель

Читать перед этапом: [`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md). Отдельного экрана нет: группы — блок
экрана `payments.methods`, где менеджер и так расставляет способы. Панель показывает группы конфига и
правит их; кнопок «Добавить» и «Удалить» у групп нет (решение 12).

- **`MethodsPage.vue`:** левая колонка — группы по порядку. У группы — ручка, пиктограмма, название,
  «Изменить»; под ней `WxSortableList` с её способами. Все списки с одним `group="payment-methods"`:
  проп уже есть, способ перетаскивается между группами. Группы — внешний `WxSortableList`.
- **Пустая группа** принимает способ: подпись пустого списка вместо `WxEmpty`.
- **Диалог группы:** название и описание (`localized`; пустое название — слово из конфига), пиктограмма — `WxRadioGroup` с превью набора §2.5
  (`WxIconPicker` здесь не подходит: у него набор ядра, а не сайта).
- **Форма способа:** поле «Группа» (`wx-select`) в карточке `rules`: «По умолчанию (Оплата онлайн)» и
  группы сайта. Это путь с клавиатуры: перетащить между списками ею нельзя. Как поле получит варианты —
  сверить с `delivery_mode` на этапе 6 §10.
- **`group_key` нормализуется:** перенос в группу типа пишет `null`, и способ снова следует за типом.
- **Правка группы** создаёт строку `payment_groups` с этим ключом или обновляет её (§2.1).
- **Значки** показываются в строке способа только для чтения: менеджер их не настраивает (решение 2).
- **Маршруты:** `GET groups`, `PUT groups/{key}`; `PUT methods/order` принимает
  `{ groups: [{ key, methods: [id…] }] }` и порядок групп вместе со способами, одной транзакцией.
- **Права:** чтение — `payments.view`, запись — `payments.manage`, нового права нет. Маршруты — `cms.can`,
  `AccessCoverageTest` зелёный.
- **Кеш:** `PaymentGroup` — в `bumpOn`. Массовая запись порядка событий модели не шлёт, поэтому `bump()`
  руками; тест свежести — на порядок групп и на перенос способа.

| `payments_groups_reorder`  | **новый:** порядок групп; `dry_run`                                                                                      |
| `payments_methods_list`    | плюс `group`, `group_key`, `marks`, `similar_to`                                                                         |
| `payments_methods_save`    | плюс `group` (ключ или `null` — группа типа); в ответе `warnings` (§5), `dry_run` их тоже показывает                     |
| `payments_methods_reorder` | порядок внутри групп (`methods`); при переносе — как в панели (`groups: [{ key, methods }]`, не названное остаётся)      |
| `payments_available`       | плюс `group` и `apple_pay_only` способа; ответ говорит, что Apple Pay решает браузер покупателя                          |

- **Правка языков.** `payments_groups_save` меняет только названные языки: панель шлёт все сразу, агент
  обычно один. Пустой язык возвращает слово конфига, `null` — все сразу.
- **`payments://catalog`** дополняется: ключи групп, пиктограммы, значки реестра.
- **Отказ словами:** «Unknown group: …», «Unknown pictogram: …».
- `payments_groups_list` — в `PerformanceTest` тёплым.
- Новые инструменты — в `### Permissions` и `AGENTS.md` пакета.

## 9. Макет

Статичный HTML на настоящих токенах темы lab и настоящем `payments.css`, с прототипом поведения.
Вне репозитория, Chromium через Playwright. Значки — серые плашки со словом (§3.3). Тёмная схема —
временная, в `theme-default` её нет.

| Замер                                     | 360 px    | 1280 px     |
| ----------------------------------------- | --------- | ----------- |
| `scrollWidth` / `clientWidth`             | 360 / 360 | 1280 / 1280 |
| элементов за правым краем                 | 0         | 0           |
| наименьшая высота строки                  | 60 px     | 60 px       |
| высота шага, открыта «Онлайн», 5 способов | 672 px    | 589 px      |

Светлая и тёмная дали одинаковые размеры. Проверено поведением, а не только видом:

- группа закрыта → стрелка на неё открывает подсписок и выбирает первый способ;
- Tab переходит на отмеченный способ, стрелка переключает способ;
- без Apple Pay пропадают и строка, и значок у группы; Google Pay остаётся;
- без обоих кошельков список и значки верны, но выбранный скрытый способ оставлял группу без отметки —
  отсюда правило §4.3.

Макет собран до решения 4 в нынешнем виде и скрывал оба кошелька. Для Apple Pay всё сказанное верно,
Google Pay теперь не скрывается; переделывать макет не нужно.

Не проверено на макете: плоский список единственной группы (решение 10), сборка группы в одну строку
скриптом (§4.3), настоящие файлы значков, настоящие телефоны, читалка.

## 11. Открытые вопросы

Решает человек. Этапы плана не ждут.

1. **Монохромные значки при явном запрете (§3.3).** Решение 13 допускало монохром, если явного запрета
   нет; он есть у всех четырёх систем. Предложение — выпускать файлы Simple Icons, как решено: значок
   заменяется одним файлом, а знаки показывает принимающий их продавец. Другой путь — официальные файлы
   из Brand Center, но скачать их может только человек, и вопрос раздачи в MIT-пакете тогда встаёт
   заново. Это не юридическое заключение: при сомнении лучше спросить у эквайера или юриста.
