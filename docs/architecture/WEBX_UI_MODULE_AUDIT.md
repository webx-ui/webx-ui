# `webx-ui/module-audit` — аудит сайта

Раздел панели «Аудит»: обход собственного сайта и набор проверок, который сеошник, верстальщик и
админ делают руками на каждом новом проекте. Зеркала, индексные файлы, слэши, 404, robots, карта
сайта, title и H1, битые ссылки, заголовки безопасности, конфиг продакшена. Пара к нему —
`@webx-ui/module-audit`. Реестр пакетов — [`WEBX_UI_COMPOSER_PACKAGES.md`](WEBX_UI_COMPOSER_PACKAGES.md).

Статус: спецификация написана 01.10.2026, код не начат. Порядок — CLAUDE.md §6.

## 1. Границы

- **Свои проверки, без внешних сервисов.** Всё, что можно узнать запросом к своему сайту, из его
  базы или конфига. Внешние сервисы — потом и спутниками (§13), первый — DataForSEO.
- **Максимум информации, а не только ошибки.** Обход сохраняет снимок каждой страницы (§4) — по
  нему в панели строится любая выборка, как в Screaming Frog. Находки — вид поверх снимка.
- **Отдельный модуль, а не часть `module-seo`.** По правилу имён (CLAUDE.md §1) это раздел панели,
  а большинству проверок SEO-модуль не нужен: зеркала, слэши, битые ссылки, H1 — это факты
  HTTP-ответа и HTML. SEO, каталог и другие модули приносят свои проверки и исправления через
  контракт (§6, §7) — так же, как спутники каталога.
- **Не делаем:** Core Web Vitals и Lighthouse (нужен headless Chrome на сервере), рендер JS,
  позиции в выдаче, внешние ссылки на сайт. Это работа внешних сервисов.

## 2. Решения (не переоткрывать)

1. **Свой краулер** на HTTP-клиенте Laravel (пул Guzzle) и `DOMDocument` + `DOMXPath`. Без
   `spatie/crawler`: у нас уже есть карта и реестр адресов, а лишняя зависимость в каждом сайте
   не нужна.
2. **Префикс таблиц — `audit_*`**, идентификатор модуля — `audit`, права — `audit.view`,
   `audit.run`, `audit.manage`, MCP-скоупы `audit:read` / `audit:write`.
3. **Проверка — класс за контрактом `AuditCheck`**, реестр `AuditChecks` — синглтон; модули
   регистрируют свои проверки из провайдеров. Исправление — отдельный контракт `AuditFix` (§6).
4. **Находка не чинит сама.** Исправление — только явной кнопкой (или MCP с `dry_run`), и делает
   его модуль, которому принадлежит то, что меняется: нормализацию адресов — `module-seo`,
   алиасы — `routing`.
5. **Прогон — задача в очереди, порциями.** Одна задача обходит пачку адресов и ставит в очередь
   следующую — ни один хостинг не любит задачу на 20 минут. Прогресс — в `audit_runs`, панель его
   опрашивает. С драйвером `sync` прогон из панели не запускается — предупреждение и команда
   `php artisan webx:audit:run` для крона.
6. **Сайт стучится сам к себе, но по публичному имени.** Запрос идёт на `APP_URL` с настоящим
   `Host` и SNI, а соединение — на адрес из настройки «подключаться к» (`CURLOPT_RESOLVE`, по
   умолчанию — как резолвит DNS). Так аудит работает в Docker и за NAT без hairpin, а проверяет
   ровно то, что видит посетитель.
7. **Вежливость по умолчанию:** 2 параллельных запроса, лимит 1000 страниц, свой `User-Agent`
   (`WebxAudit/1.0`). robots.txt по умолчанию **не** соблюдается — это свой сайт, — но всё, что
   им закрыто, помечается на странице.
8. **История — через отпечаток.** У находки `fingerprint` = проверка + адрес + ключ деталей;
   сравнение с прошлым прогоном даёт «новая / висит / исправлена» без хранения состояний.
   Снимки страниц держим за последние N прогонов (настройка, по умолчанию 5), находки — дольше.
9. **Скрыть можно, удалить — нет.** Осознанное (`noindex` на странице поиска, длинный title у
   лендинга) скрывается правилом `audit_ignores`: проверка + маска адреса + причина + кто скрыл.
10. **Пороги — настройками**, с дефолтами из §5. Длина title и description — в символах, с
    подсказкой про пиксели в объяснении проверки.
11. **Все слова — ключами словаря** модуля, как у остальных разделов; у каждой проверки — три
    текста: что найдено, почему это важно, как исправить.
12. **Каждый абсолютный адрес классифицируется по хосту** — не только ссылки, а всё, что ведёт
    наружу: `href`, `src`, `srcset`, `url()` в инлайн-стилях, `action` форм, `og:image`,
    canonical, hreflang, JSON-LD, `<loc>` карты. Классы: свой, свой через другое зеркало,
    **стенд разработки**, внешний (§5.6). Повод — живой случай 01.10.2026: клиент наполнил сайт
    на dev-стенде абсолютными адресами, после выкладки ссылки и картинки вели на dev, заметили
    случайно.
13. **Контент проверяется и в базе, а не только обходом.** Обход видит опубликованное, а ссылки на
    стенд лежат и в черновиках, скрытых записях, полях, которые шаблон не выводит. Модули отдают
    свои текстовые поля контрактом `AuditContentSource` (§6), поиск адресов в них — общий.

## 3. Прогон

Охват выбирается при запуске: **полный**, **только быстрые** (пробы + конфиг + база, секунды),
**по списку адресов** (после правки — перепроверить пять страниц).

Этапы полного прогона:

1. **Конфиг** — читает `config()` и окружение, без запросов.
2. **Пробы** — несколько десятков запросов к хосту: зеркала, схема, индексные файлы, слэши,
   регистр, случайный адрес, robots.txt, sitemap.xml, TLS.
3. **Затравка** — главная, все адреса из `sitemap.xml` (с индексом), канонические строки реестра
   `routing`. Источник у страницы запоминается: так находятся сироты и адреса мимо карты.
4. **Обход** — в ширину от затравки, только свой хост, глубина считается от главной. Редиректы
   не следуют автоматически: каждый шаг цепочки — своя запись.
5. **Внешние ресурсы** — внешние ссылки и картинки проверяются `HEAD` (откат на `GET`), с кешем на
   прогон и отдельным лимитом.
6. **База** — проверки модулей, которым не нужен обход, и поиск адресов в контенте всех записей,
   включая черновики (§2 п. 13). Этот этап входит и в «только быстрые».
7. **Разбор** — проверки по снимку: дубли, сироты, глубина, взаимность hreflang. Отпечатки,
   сравнение с прошлым прогоном, счётчики.

## 4. Схема

### `audit_runs`

`status` (`queued | running | done | failed | cancelled`), `scope`, `base_url`, `resolve_to`,
`pages_limit`, `pages_crawled`, `progress` (этап и счётчики), `counts` json (по важности и
группам), `started_by` (администратор, `schedule`, `mcp`), `started_at`, `finished_at`, `error`.

### `audit_pages` — снимок страницы

| Группа   | Поля                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |
| Адрес    | `url`, `url_hash`, `final_status`, `redirect_to`, `depth`, `source` (`home`, `sitemap`, `registry`, `link`, `probe`)   |
| Ответ    | `status`, `content_type`, `bytes`, `ttfb_ms`, `total_ms`, `compression`, `headers` json (выборка), `blocked_by_robots` |
| Разметка | `title`, `description`, `h1` json, `headings` json (счёт по уровням), `canonical`, `robots_meta`, `x_robots_tag`       |
| Языки    | `lang`, `hreflang` json                                                                                                |
| Соцсети  | `og` json, `twitter` json                                                                                              |
| Данные   | `json_ld` json (типы и ошибки разбора)                                                                                 |
| Текст    | `word_count`, `text_hash`                                                                                              |
| Связи    | `links_in`, `links_out_internal`, `links_out_external`, `images`, `images_without_alt`, `in_sitemap`, `in_registry`    |

### `audit_links`

`run_id`, `from_page_id`, `to_url`, `to_page_id` (null для внешних), `kind` (`a`, `img`,
`srcset`, `script`, `link`, `iframe`, `form`, `style`, `meta`, `json_ld`), `anchor`, `rel`,
`target`, `host`, `host_class` (`own | own_mirror | dev | external`), `status` (для внешних —
после проверки).

### `audit_content_urls` — адреса, найденные в базе

`run_id`, `source` (модуль и тип записи), `record_id`, `record_label`, `field`, `locale`,
`url`, `host`, `host_class`, `published` (видна ли запись на сайте), `edit_url` (куда вести из
панели).

### `audit_issues`

`run_id`, `check`, `severity` (`error | warning | notice`), `page_id` (null для проверок хоста
и базы), `url`, `details` json, `fingerprint`, `state` (`new | persisting`), `ignored_by` (id
правила скрытия). Исправленные — вычисляются из прошлого прогона, отдельно не хранятся.

**`details` — данные для раскрытия, а не текст.** Строка-сводка (`summary`: «ещё 1 страница с
таким title», «5% текста при пороге 10% · 662 слова») и, если нужно, таблица (`table`:
`columns` + `rows`, у ячейки — тип `url | status | bool | text | missing`). Панель рисует
раскрытие по этой форме одним компонентом, своя вёрстка у проверки не нужна. Примеры:

- `hreflang.*` — матрица: язык, адрес, ответ, «ссылается назад», индексируется; недостающая
  строка (`x-default`) — ячейками `missing`, красным;
- `*.duplicate` — список «ещё N страниц» со ссылками на их карточки;
- `redirects.chain` — шаги цепочки с кодами;
- `hosts.dev_content` — запись, поле, язык, «Открыть в редакторе».

### `audit_ignores`

`check`, `pattern` (точный адрес или маска как в правилах SEO), `reason`, `created_by`.

## 5. Проверки

Важность: **E** — ошибка, **W** — предупреждение, **N** — к сведению. Пороги в скобках — дефолты
настроек.

### 5.1. Конфиг (`config.*`)

| Проверка              | Что                                                                       | Важность |
| --------------------- | ------------------------------------------------------------------------- | -------- |
| `config.debug`        | `APP_DEBUG=true` на рабочем домене                                        | E        |
| `config.env`          | `APP_ENV` не `production`                                                 | W        |
| `config.app_url`      | `APP_URL` не совпадает с хостом и схемой, с которых сайт реально отвечает | E        |

| `config.site_gate`    | калитка с паролем включена — сайт закрыт для поисковиков                  | N        |

### 5.6. Исходящие адреса и чужие хосты (`hosts.*`)

**Стенд разработки** — хост из настройки «Другие адреса этого сайта» (dev, stage, старый домен)
плюс то, что стендом быть обязано: `localhost`, `127.0.0.0/8`, `::1`, частные сети
(`10/8`, `172.16/12`, `192.168/16`), зоны `.local`, `.localhost`, `.test`, `.example`,
`.invalid`, `.internal`, хосты с первым словом `dev`, `stage`, `staging`, `test`, `preview`,
`demo`. Хост из `APP_URL` стендом не считается никогда — иначе локальный прогон на
`shop.local` объявит ошибкой весь сайт.

| Проверка                  | Что                                                                                                | Важность |
| ------------------------- | -------------------------------------------------------------------------------------------------- | -------- |
| `hosts.dev_page`          | на странице ссылка или ресурс (картинка, скрипт, стиль, `og:image`, canonical…) на стенд           | E        |
| `hosts.dev_content`       | адрес стенда в базе — в том числе в черновике или скрытой записи (покажет, где и в каком поле)     | E        |
| `hosts.similar`           | хост похож на свой: то же первое слово в другой зоне (`shop.local` при `shop.com`) — глазами       | W        |
| `hosts.wrong_mirror`      | ссылка на свой сайт через `http` или другое зеркало — каждый клик через 301                        | W        |
| `hosts.absolute_own`      | абсолютная ссылка на свой хост — работает, но сломается при следующем переезде                     | N        |
| `hosts.new_domain`        | внешний домен, которого не было в прошлом прогоне — так видно и опечатки, и взлом со спам-ссылками | N        |
| `hosts.external_many`     | больше 100 внешних ссылок на странице                                                              | N        |
| `hosts.external_redirect` | внешняя ссылка отвечает редиректом — лучше сразу на конечный адрес                                 | N        |
| `hosts.blank_opener`      | `target=_blank` без `rel=noopener` на внешнюю ссылку                                               | N        |

Исправление `audit.replace-host`: заменить хост стенда на рабочий (или сделать ссылку
относительной) во всех найденных полях. Сначала предпросмотр — список записей, полей и число
замен, — потом замена **через модели модулей**, не SQL: журнал изменений `module-admin` пишет
каждую правку, и её можно откатить.

## 6. Контракты

```php
interface AuditCheck
{
    public function id(): string;            // 'title.duplicate'
    public function group(): string;         // 'page'
    public function needs(): array;          // ['config'] | ['probes'] | ['database'] | ['crawl']
    public function run(AuditContext $context): iterable; // of Finding
}

interface AuditFix
{
    public function id(): string;            // 'seo.normalise-host'
    public function fixes(): array;          // ids of checks it closes
    public function available(Finding $finding): bool;
    public function preview(Finding $finding): FixPreview; // what will change, for dry_run
    public function apply(Finding $finding): void;
}

interface AuditContentSource
{
    public function id(): string;            // 'pages', 'blog.posts', 'blocks'
    /** Every record, drafts and hidden ones included, chunked. */
    public function records(): iterable;     // of ContentRecord: id, label, published, edit_url
    /** Text-bearing fields: plain text, HTML, block JSON, URL fields; per locale. */
    public function fields(ContentRecord $record): iterable; // of ContentField
    /** Writes a field back through the model, so the history journal sees it. */
    public function replace(ContentRecord $record, ContentField $field, string $value): void;
}
```

`AuditContext` отдаёт снимок прогона (страницы, ссылки, пробы), HTTP-клиент с теми же
настройками и пороги. Проверки по `crawl` выполняются на этапе разбора по уже собранному
снимку — ни одна из них сама сайт не обходит.

Где исправить кнопкой нельзя (зеркало и схема на уровне веб-сервера — запрос на «чужой» хост до
Laravel не доходит), находка несёт готовый сниппет для nginx и Apache.

## 7. Что приносят другие модули

Регистрируют проверки и исправления, только если `module-audit` установлен (`suggest` в
composer.json, регистрация под `class_exists`).

- **`module-seo`:**
  - проверки по базе: сущности без `seo_meta` или с пустыми полями, дубли title между
    сущностями, правила SEO на адреса, которые отвечают 404, редиректы на отсутствующие адреса,
    цепочки в `seo_redirects` — до обхода, по таблице;
  - **middleware нормализации адреса** с настройками: главное зеркало, https, схлопывание
    слэшей, срез индексных файлов, политика конечного слэша, нижний регистр — всё одним 301 без
    цепочки. Исправления `seo.normalise-*` закрывают `host.*` из §5.2;
  - исправление `seo.collapse-chain` для `redirects.chain` (пункт «Схлопывание цепочек»
    `WEBX_UI_MODULE_SEO.md` §16);
  - исправление `seo.robots-sitemap` — дописать `Sitemap:` в `seo.robots-txt`.
- **`routing`:** алиасы, ведущие в никуда; канонические строки без живой сущности.
- **`module-media`:** картинки библиотеки без `alt`, файлы в базе без файла на диске, тяжёлые
  оригиналы, которые отдаются без превью.
- **`module-catalog`:** категории без описания, товары без картинки, опубликованные товары без
  цены.
- **`module-menu`:** пункты меню на 404 и на редиректы.
- **Каждый контентный модуль** (`module-pages`, `module-blocks`, `module-blog`,
  `module-services`, `module-catalog`, `module-menu`, `module-banners`, `module-settings`,
  `module-seo` — `canonical` и `og_image` правил, …) — `AuditContentSource` для своих полей. Без
  него поля модуля в базе не проверяются, и раздел «Источники» в обзоре это показывает: какие
  модули стоят, а источника не отдали.
- **`module-admin`, следом:** предупреждение прямо при сохранении — поле со ссылкой на стенд или
  абсолютной ссылкой на свой хост подсвечивается до того, как попадёт на сайт. Тот же
  классификатор хостов, вынесенный в общий код. Не часть аудита, но та же беда, пойманная раньше.

**Команда для выкладки:** `php artisan webx:audit:run --quick --fail-on=error` — быстрый прогон
(конфиг, пробы, база) с ненулевым кодом выхода при ошибках. Шаг деплоя после миграций: сайт со
ссылками на dev-стенд или с `APP_DEBUG=true` не выедет молча.

## 8. Панель

Раздел «Аудит» в группе «Система».

- **Обзор** — последний прогон: здоровье в процентах, счётчики по важности и группам, «новые /
  исправлены» относительно прошлого, прогресс текущего прогона, кнопка запуска с выбором охвата.
- **Находки** — таблица проверок, раскрытие — адреса. Фильтры: важность, группа, состояние
  (новая, висит, скрыта). У проверки — три текста из §2 п. 11, кнопка исправления с
  предпросмотром, «Скрыть» с причиной.
- **Страницы** — все обойдённые адреса со всеми полями снимка, выбор колонок, фильтры по любому
  полю, экспорт CSV.
- **Карточка страницы** — выезжает справа. Шапка: код ответа, адрес, title, «Перепроверить»
  (охват «по списку адресов» на одну страницу), «Экспорт» (снимок и находки страницы).
  Вкладки со счётчиками:
  - **Обзор** — ответ, заголовки, время, вес, разметка `<head>`, источник и глубина;
  - **Проблемы** — находки страницы, раскрытие по `details` (§4), метка NEW, «?» с тремя
    текстами;
  - **Входящие** и **Исходящие** — ссылки с анкором, `rel`, ответом и классом хоста;
  - **Картинки**, **CSS**, **JS** — ресурсы страницы из `audit_links`: размер, ответ, кэш,
    сжатие, `alt` у картинок;
  - **Микроразметка** — найденные блоки JSON-LD с ошибками и предупреждениями.

  Скриншота и замера скорости тут нет — нужен браузер, это спутники (§13).

- **Исходящие** — все хосты, на которые ссылается сайт, по классам (§5.6): число ссылок и
  страниц, ответы, `rel`, когда впервые замечен. Раскрытие хоста — страницы с анкорами и записи
  в базе с полями и ссылкой «Открыть в редакторе». Стенды разработки — наверху, красным.
- **Прогоны** — история, сравнение двух прогонов.
- **Настройки** — базовый адрес, «подключаться к», **другие адреса этого сайта** (стенды и
  старые домены), лимиты, параллельность, пороги, исключённые пути, ночной прогон по расписанию
  (выключен по умолчанию), сколько прогонов хранить.

## 9. MCP

`audit_run` (охват, список адресов), `audit_status`, `audit_issues` (фильтры как в панели),
`audit_pages` (фильтры по полям снимка), `audit_page_get`, `audit_hosts` (исходящие по
хостам, с местами в базе), `audit_ignore`, `audit_fix` (с
`dry_run` — предпросмотр). Ресурс модуля — каталог проверок с объяснениями, чтобы агент чинил
причину, а не симптом.

## 10. npm-половина

`@webx-ui/module-audit`: экраны §8 на компонентах ядра (`WxTable` с колонками на выбор,
`WxProgress`, `WxTabs`, `WxDrawer` для карточки страницы). Опрос прогресса — пока прогон идёт.

## 12. Открытые вопросы

- Здоровье в процентах — как считать, чтобы одна сотня `images.alt` не топила сайт с рабочим
  `noindex` на главной. Предложение: вес по важности, проверка считается один раз, а не на адрес.
- Обходить каждую языковую версию целиком или главную и дальше по hreflang.
- Хранить ли HTML страницы (для «показать, где именно») — место против удобства. Предложение: не
  хранить, держать в деталях находки выдержку вокруг проблемного места.

## 13. Потом: `module-audit-dataforseo`

- **Отдельный спутник**, как спутники каталога: платная интеграция не попадает в базовую
  установку, а рядом так же встанут другие поставщики: PageSpeed Insights API — Core Web Vitals и
  кнопка замера скорости в карточке страницы; скриншот страницы — тоже спутником (headless Chrome
  или внешний сервис).
- Поставщик за тем же контрактом: OnPage API DataForSEO пишет находки в те же `audit_issues` с
  `source = dataforseo` — одна таблица, один экран, одни кнопки.
- Логин и пароль API — в настройках спутника; без них раздел работает на своих проверках, и это
  нормальное состояние, а не ошибка.
- Перед прогоном — оценка стоимости (страниц × цена) и подтверждение; потолок расходов в месяц —
  настройкой.
- Не раньше, чем выпущен свой аудит (A1–A5).
