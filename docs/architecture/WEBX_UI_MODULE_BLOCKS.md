# `webx-ui/module-blocks` — спецификация и план реализации

Конструктор блоков: раздел панели, в котором тип блока создаётся целиком — схема полей, шаблон
Blade, стили и скрипт, — и механизм, который собирает из таких блоков содержимое любой сущности и
печатает его на сайте. Реестр пакетов — [`WEBX_UI_COMPOSER_PACKAGES.md`](WEBX_UI_COMPOSER_PACKAGES.md),
экраны — [`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md), адреса — [`WEBX_UI_ROUTING.md`](WEBX_UI_ROUTING.md).

Статус: спроектирован 15.09.2026; сессии A (пакет и рендер), B (стили, скрипты и наборы), C
(версии и предпросмотр) и D (панель) написаны 15.09.2026, остальное — по плану §20. Спецификация описывает **v0.1**; отложенное — в §21, нерешённое — в §22.

Пишется **до** `module-pages`, потому что содержимое страницы — это массив блоков, и формат
хранения нельзя сочинить позже: первый же сайт получит миграцию контента. `module-pages` подключает
трейт `HasBlocks` и узел `wx-blocks` в своём экране, и больше ничего про блоки не знает.

Прототипы, по которым согласована панель: [экран страницы с
конструктором](https://claude.ai/artifact/STXF7X34T32NSSggsEFNqJ) и [раздел
«Блоки»](https://claude.ai/artifact/UFhq5V7ew8ENH9zFZW1eg4).

## 1. Границы

Пакет владеет четырьмя вопросами:

1. **Что такое тип блока** — из чего он состоит, где хранится, как версионируется (§4, §5).
2. **Как блок превращается в HTML** — рендер, вложенность, изоляция падений (§7, §8).
3. **Как его стили и скрипты попадают на страницу** — наборы по хешу, рантайм, мост к сборке
   сайта (§9, §10).
4. **Как всем этим управляют** — раздел панели, MCP, экспорт (§14, §18, §17).

Пакет **не** владеет: сущностями (страницами, статьями, товарами), их адресами, их SEO и их
версиями. Версии и черновики — общий механизм каркаса `module-admin` (§11), блоки лишь занимают
место в слепке.

### Почему один пакет, а не библиотека плюс раздел

Рассматривали разделение на `webx-ui/blocks` (рендер) и `webx-ui/module-blocks` (панель) — по
образцу `routing` → `module-seo`. Отвергнуто: у блоков нет жизни без панели. Библиотека, которая
умеет рисовать блоки, но не умеет их заводить, бесполезна — типы негде взять, они не в коде, а в
базе. Шов между половинами держится внутри пакета, как в `module-seo`: `WebxUi\Blocks\Rendering\`
и `WebxUi\Blocks\Panel\`.

## 2. Принятые решения (не переоткрывать)

- **Источник правды — база, не файлы.** Блок целиком (схема, шаблон, CSS, JS) — строки в БД.
  Генерация файлов в `resources/` отвергнута: на хомлабе образ собирается из репозитория, и
  следующий деплой снёс бы всё, что сделали в панели. Переносимость решается экспортом (§17), а не
  местом хранения.
- **Blade редактируется через панель, и это осознанный риск.** `@php`, вызовы хелперов, `{!! !!}`
  доступны. Песочницы не будет: в любом подмножестве, которое мы придумаем, найдётся дыра. Раздел
  доступен одной роли и выключается конфигом; доступ к нему приравнен к доступу к деплою (§16).
- **Вложенность — это поле, а не отдельная сущность.** Блок-контейнер («Секция») объявляет в своей
  схеме узел `wx-blocks`, значение которого — массив блоков (§6). Никакого второго механизма
  «слотов» нет.
- **Версия типа блока пишется на каждое сохранение.** Это код, история правок работает журналом
  аудита — прямое следствие решения про `@php`. У сущностей политика другая (§11).
- **Публикация блока — своё действие.** Опубликованная версия действует на все страницы, где блок
  стоит. Кнопка публикации страницы не публикует блок молча, а предупреждает и называет число
  затронутых страниц.
- **Стили и скрипты едут набором по хешу** (§9), а не всем файлом и не инлайном по умолчанию.
- **У скрипта есть контракт входа** — функция на экземпляр, а не код, выполняемый один раз (§10).
  Без него ломаются: два одинаковых блока на странице, вложенный блок и — в первую очередь —
  подмена узла в предпросмотре.
- **Предпросмотр — служебный адрес с идентификатором** (`/_preview/{type}/{id}`), не канонический
  адрес с параметром: у новой записи адреса ещё нет (§12).
- **Один рендер на всё.** Предпросмотр в панели, ссылка «Открыть на сайте» и живая страница — один
  и тот же код. Отдельного «рендера для панели» не существует.

## 3. Схема

### `blocks` — тип блока

| Колонка                | Тип               | Смысл                                                         |
| ---------------------- | ----------------- | ------------------------------------------------------------- |
| `id`                   | id                |                                                               |
| `slug`                 | string(64) unique | он же `type` в значениях; переименование — ломающее изменение |
| `title`                | string(120)       | как называется в списке при добавлении блока                  |
| `description`          | string(255) null  | подсказка редактору и инструкция агенту                       |
| `icon`                 | string(64) null   | имя из набора ядра                                            |
| `group`                | string(64)        | раздел в списке при добавлении блока; из `webx-blocks.groups` |
| `sort`                 | smallint          | порядок в каскаде CSS (§9) и в списке блоков                  |
| `allow`                | json null         | какие типы можно класть внутрь; `null` — блок не контейнер    |
| `allowed_in`           | json null         | где разрешён сам; `null` — где угодно                         |
| `max_per_entity`       | smallint null     | сколько экземпляров на сущность                               |
| `is_enabled`           | bool              | скрыт от редакторов, но продолжает рисоваться                 |
| `draft_version_id`     | fk null           | черновая версия; `null` — черновика нет                       |
| `published_version_id` | fk null           | что действует на сайте; `null` — не публиковался              |
| timestamps             |                   |                                                               |

**`title` и `description` не переводимые колонки, и это решение, а не упущение.** Подписи полей
внутри блока живут в `schema`, то есть в узлах экрана, где переводимая строка выражается маркером
`trans::<namespace>::<key>` (§10 спеки экранов). Сделай заголовок блока json-колонкой с
`HasTranslations` — и заголовок переводился бы одним механизмом, а подписи его собственных полей
другим; это разъезжается в форме, в экспорте и в MCP. Поэтому здесь обычная строка на языке той
команды, которая завела блок, а кому нужен многоязычный экипаж в панели — пишет в это поле тот же
`trans::`-маркер. Цена переводимости платилась бы на каждом блоке, польза нужна редко, а переход
`string` → переводимая колонка дешёв (миграция кладёт значение в язык по умолчанию), обратный —
нет.

### `block_versions` — неизменяемый слепок

| Колонка      | Тип              | Смысл                                             |
| ------------ | ---------------- | ------------------------------------------------- |
| `id`         | id               |                                                   |
| `block_id`   | fk               |                                                   |
| `number`     | int              | 1, 2, 3… в пределах блока; уникально с `block_id` |
| `schema`     | json             | дерево узлов экрана (§5)                          |
| `template`   | longtext         | Blade                                             |
| `styles`     | longtext         | CSS                                               |
| `script`     | longtext null    | тело инициализатора (§10)                         |
| `sample`     | json             | образцовые значения                               |
| `author_id`  | fk null          |                                                   |
| `source`     | string(16)       | `panel` \| `mcp` \| `import`                      |
| `comment`    | string(255) null |                                                   |
| `created_at` |                  |                                                   |

Слепок целиком, а не диффом: откат тривиален, а экономить тут нечего — версия блока это несколько
килобайт текста.

### `block_bundles` — собранный набор стилей и скриптов

| Колонка      | Тип           | Смысл                                             |
| ------------ | ------------- | ------------------------------------------------- |
| `hash`       | string(16) pk | хеш от отсортированного списка пар «тип + версия» |
| `types`      | json          | из чего собран — для отладки и чистки             |
| `css`        | longtext      | склейка, в порядке `sort`                         |
| `js`         | longtext null | склейка инициализаторов                           |
| `created_at` |               |                                                   |

Пишется при первом рендере такого набора, читается маршрутом отдачи (§9). Не кеш, а таблица:
сброшенный кеш на проде не должен превращаться в страницу без стилей.

### Что добавляется сущности

Трейт `HasBlocks` не требует своей таблицы: содержимое лежит json-колонкой на самой сущности
(`blocks`), и ещё одной — черновик (`draft`, §11). Blueprint-макрос `blocks()` добавляет только
`blocks`; черновик и `published_at` добавляет макрос `draft()` каркаса `module-admin` — черновики
его механизм, и сущности без блоков (товару) они нужны точно так же.

## 4. Из чего состоит тип блока

Опознание и показ — `slug`, `title`, `description`, `icon`, `group`, `sort`, `is_enabled`.
Ограничения — `allow`, `allowed_in`, `max_per_entity`. Содержательная часть живёт в версии:
`schema`, `template`, `styles`, `script`, `sample`.

`sample` — не украшение. Он решает три задачи сразу: превью при выборе блока (§14), значения для проверки
рендером перед публикацией (§15) и самая понятная агенту документация формы данных (§18).

## 5. Схема полей — это узлы экрана

Схема блока — массив узлов формата `@webx-ui/schema` (`{ id, type, label, props, visible }`), тот
же, что у описанных экранов. Следствия: форму строит существующий `WxScreenRenderer`; правила
валидации выводятся тем же кодом, что в `module-settings` (`ScreenValues`, включая ловушку с
точкой в ключе); переводимые подписи работают маркером `trans::`.

Отдельного языка описания полей не заводим — это и есть содержание §12 спеки экранов.

## 6. Вложенность

Узел `wx-blocks` в схеме блока объявляет вложенный конструктор:

```json
{
  "type": "wx-blocks",
  "id": "content",
  "label": "Содержимое",
  "props": { "allow": ["text", "gallery", "columns"], "max": 8 }
}
```

Значение такого поля — массив узлов той же формы, что и корневое содержимое сущности:

```json
[ { "key": "01H…", "type": "section", "values": { "background": "muted",
    "content": [ { "key": "01H…", "type": "text", "values": { … } } ] } } ]
```

`key` — идентификатор экземпляра, генерируется при добавлении и переживает перетаскивание: по нему
панель подменяет узел в предпросмотре, а `WxRepeater` держит форму под кареткой.

Шаблон печатает вложенное директивой `@blocks('content')`. Глубина ограничена пятью уровнями —
дальше это уже не конструктор, а вёрстка мышкой.

## 7. Рендер

```php
Blocks::render($entity->blocks)   // → HtmlString
```

- Шаблон компилируется `Blade::compileString()` и кладётся в
  `storage/framework/views/blocks/{slug}-{version}.php`. Ключ содержит номер версии, поэтому
  инвалидации не требуется вовсе: новая версия — другой файл. `view:cache` эти шаблоны не трогает,
  первый запрос после деплоя компилирует заново.
- **Каждый блок рисуется в `try`/`catch`.** На проде исключение уходит в лог, на месте блока
  остаётся пусто; в предпросмотре — плашка с сообщением и номером строки. Без этого опечатка в
  одном шаблоне уносит весь документ, и узнаём мы об этом от посетителя.
- В шаблон приходят значения блока (`$title`, `$tone`, …), `$block` (тип, версия, `key`) и
  `$entity`.
- **Значение приходит таким, каким его отдаёт тип поля,** а не таким, как лежит в базе:
  `Rendering\Values` прогоняет каждое значение через `FieldType::resolve()` — ровно то же, что
  `ScreenValues` делает для настроек. `wx-media` хранит `{ path, alt, title }`, а шаблон читает
  ещё и `url`. Значение типа, которого нет в реестре (`wx-blocks`, поле проекта), и значение
  ключа, которого нет в схеме, проходят как есть. Резолв — один на блок, до создания
  `BlockContext`, поэтому `$block->values` (и `data-wx-values` для скрипта) говорит то же,
  что переменные.
- **В режиме предпросмотра** рендер оборачивает каждый блок парой HTML-комментариев
  `<!--wx:{key}-->…<!--/wx:{key}-->`. По ним панель находит диапазон и подменяет его после правки
  поля. Комментарии не влияют на вёрстку и на живом сайте не печатаются.
- `data-wx-block="{slug}"` на корне пишет автор шаблона — это нужно рантайму скриптов (§10) и на
  живом сайте тоже. Отсутствие — предупреждение при сохранении, не ошибка.

### Обвязка: чей шаблон

Блоки — это середина документа. Всё вокруг них принадлежит другим, и границы такие:

- **Layout — сайта.** `<html>`, `<head>` с `@webxSeo` и `@webxBlocks`, шапка, подвал. Лежит в
  репозитории сайта; мы его не поставляем.
- **Вью на тип сущности — модуля-потребителя.** `module-pages` везёт `show.blade.php`, где внутри
  сайтового layout стоит `@blocks('content')` и больше ничего. `module-news` везёт свой, где перед
  блоками напечатан первый экран статьи.
- **Какой вью — решает сущность.** Поле «Шаблон» на её экране выбирает из списка, объявленного
  проектом в конфиге (ключ → имя вью). Сайт добавляет свои варианты, не трогая модуль; сам вью
  публикуемый и переопределяется целиком.

Отсюда требование к модулю-потребителю: **имя layout берётся из конфига**
(`webx-<модуль>.layout`, по умолчанию `layouts.app`), а если такого вью нет — модуль подставляет
свой запасной, голый документ с `@webxSeo`, `@webxBlocks` и содержимым. Иначе на свежей установке,
пока у сайта ещё нет вёрстки, предпросмотр показывает пустоту, и выглядит это как сломанный
модуль, а не как пустой сайт.

Предпросмотр при этом **ничего не выбирает**: он зовёт тот же обработчик типа из `routing`, что
отвечает на настоящий адрес, и тот сам берёт вью по полю сущности. Панель знает только тип и
идентификатор (§12).

### Что проект подменяет под себя

Публичных контроллеров у сущностей нет: `routing` держит один `Route::fallback()` и отдаёт
найденную запись обработчику типа (`RouteHandler`, §6 спеки роутинга). Он и есть контроллер,
живёт в модуле-потребителе — `WebxUi\Pages\Rendering\PageHandler`. У самого `module-blocks`
публичных маршрутов два: отдача набора (§9) и предпросмотр (§12).

**Страница, которой не нужен редактор,** остаётся обычной страницей Laravel: маршрут в
`routes/web.php` сайта, свой контроллер, свой вью на том же layout. Резолвер ей не мешает — он на
`Route::fallback()`, то есть включается, только когда обычного маршрута нет. И редактор не заведёт
дубль: реестр при сохранении адреса опрашивает роутер (§10 спеки роутинга) и отклоняет занятый
путь ошибкой под полем. Такой контроллер при этом волен печатать `Blocks::render()` где угодно
посреди своего вью — «нередактируемая» обычно значит «структура зафиксирована кодом», а не
«редактор не трогает ничего».

Подменяется это лестницей, от дешёвого к дорогому:

1. **Свой блок** — большинство «нужно персонально под проект» это кусок вёрстки, а он теперь
   заводится в панели без кода вообще.
2. **Вью** — публикуется в `resources/views/vendor/<модуль>/`, дальше вёрстка целиком проектная.
3. **Конфиг** — layout, список шаблонов, группы блоков, класс модели.
4. **View composer** — если вью нужны свои данные (меню, крошки, похожие статьи). Своего механизма
   не заводим: в Laravel он есть и его знают.
5. **Свой обработчик типа** — `AppServiceProvider::boot()` выполняется после провайдеров пакетов,
   а `RouteTypes::register()` пишет по ключу типа, поэтому повторная регистрация перекрывает
   модульную. Это **поддерживаемое поведение**, а не побочный эффект реализации, и должно быть
   записано в спеке роутинга и покрыто тестом.
6. **Своя модель** — через конфиг модуля; колонки добавляет миграция проекта.

Первые четыре ступени расхождения с обновлениями модуля не создают, две последние — создают,
поэтому они последнее средство.

### Первый экран сущности

У статьи перед блоками обычно стоит шапка с заголовком, датой, автором и обложкой. Она печатается
**вью, а не блоком**: это поля записи, они уже спрошены на её экране, и заводить для них блок
значит спрашивать дважды и разрешать редактору удалить заголовок статьи.

Ловушка, которую это создаёт, закрывается в конструкторе (§14): редактор видит в предпросмотре
крупный заголовок, не находит его в дереве блоков и не понимает, где это править.

## 8. Реестр типов

```php
BlockTypes::all();            // включённые типы с опубликованной версией
BlockTypes::find('hero');
BlockTypes::draft('hero');    // черновая версия — только под токеном предпросмотра
```

Реестр читает базу и кеширует список; инвалидация — при публикации версии и командой
`webx:blocks:clear`. Типы из кода в v0.1 не поддерживаются: всё, что есть, заведено в панели (§22).

## 9. Стили и скрипты

Какие типы стоят на странице, известно из дерева значений. Дальше:

1. Множество пар «тип + версия» → отсортировать по `sort`, затем по `slug` → хеш.
2. `@webxBlocks` в `<head>` печатает `<link rel="stylesheet" href="/blocks/{hash}.css">`, а перед
   `</body>` — `<script type="module" src="/blocks/{hash}.js">`, если у набора есть скрипты.
3. Маршрут отдаёт строку из `block_bundles` с `Cache-Control: public, max-age=31536000, immutable`.

**`@webxBlocks` раскрывается в `@stack`, а не вычисляется заранее.** Рендер блоков пушит свой набор
в стек в тот момент, когда действительно рисует; секции и стеки Laravel разрешаются после того, как
весь вью отрисован, поэтому в уже «пройденный» `<head>` попадает то, что зарегистрировали ниже по
документу. Это важно не для сущностей — там обработчик знает содержимое заранее, — а для страниц,
которые сайт рисует своим маршрутом и контроллером и зовёт `Blocks::render()` где-то посреди вью
(§7): вычисление «до рендера» там невозможно в принципе. Заодно на странице без блоков не
печатается ничего.

Почему набором, а не одним файлом на сайт: страница тянет только то, что на ней стоит. Почему
файлом, а не инлайном: хеш содержит версии, поэтому файл кешируется навсегда, а страницы с
одинаковым набором его делят — на сайте из двухсот страниц наборов оказывается пара десятков.
Публикация новой версии меняет хеш только у тех страниц, где блок стоит. Инлайн остаётся режимом в
конфиге для маленьких наборов.

Порядок склейки — по `sort` типа: два блока рано или поздно заспорят за одно правило, и решать
спор должен автор, а не алфавит.

Чистка и прогрев — `webx:blocks:bundles --prune` и `--warm`.

## 10. Контракт входа скрипта и мост к сборке сайта

Поле `script` — **тело инициализатора**, а не код, выполняемый один раз. В набор оно едет обёрнутым:

```js
webx.block('hero', async (el, values) => {
  /* тело */
})
```

Рантайм (~30 строк, едет тем же файлом) находит `[data-wx-block="hero"]` и зовёт функцию на каждый
найденный корень; повторный вызов на поддереве — `webx.mount(root)`, им же пользуется панель после
подмены узла.

Мост к тому, что уже собрано на сайте:

```js
webx.provide('swiper', Swiper) // точка входа сайта
const Swiper = await webx.use('swiper') // скрипт блока
```

`use` возвращает промис: бандл сайта может приехать позже. Список того, что сайт объявил, — данные:
он показывается в редакторе блока рядом с полем скрипта и отдаётся ресурсом в MCP, чтобы агент знал,
что доступно **на этом** сайте. Путь роста, если понадобится настоящий `import`, — import map из
манифеста Vite; написанное он не ломает.

## 11. Черновики и версии сущностей

Механизм общий и живёт в каркасе `module-admin` — он понадобится новостям и товарам, а не только
страницам. Здесь описан потому, что без него не работает предпросмотр.

**Три места и правило, которое их разводит:**

- колонки сущности — **то, что сейчас на сайте**;
- `draft` (json на той же строке) — **то, что готовится**; черновик ровно один;
- `entity_versions` — **прошлое сайта**.

Публикация копирует `draft` в колонки и пишет строку в историю. Живой сайт читает колонки,
предпросмотр — `draft`. Для ни разу не опубликованной записи это работает само: колонки пустые,
`draft` полон, версий ноль.

```
entity_versions
  id
  versionable_type, versionable_id     -- индекс (type, id, number)
  number        -- 1, 2, 3… у публикаций; у автосейва null — это не точка истории
  kind          -- published | autosave
  payload json  -- слепок: переводимые поля, blocks, вклад HasSeo
  is_pinned
  author_id, source, comment
  created_at
```

Рядом с `draft` у сущности лежит `published_at`: обработчик адреса отвечает по нему 404 без
единого запроса, а «ни разу не публиковалась» и «снята с сайта» — одно и то же состояние.

- **История — это публикации.** Промежуточные сохранения в неё не пишутся: слепок страницы с
  блоками весит килобайты, автосохранение раз в полминуты за месяц даст тысячи строк, и прочитать
  такую историю невозможно — в ней нет событий.
- **`kind = autosave`** — кольцо из пяти последних снимков черновика. Не история, а страховка на
  случай «снёс блок, автосохранилось, вкладку закрыл». В отдельной вкладке не показывается.
- **Лимит — тридцать публикаций на сущность**, подрезка происходит в момент записи новой, поэтому
  превысить его невозможно. Команда `webx:versions:prune` нужна на случай, когда лимит уменьшили.
  Флаг «закрепить версию» выводит её из-под подрезки.
- **`payload` не выбирается в списке.** Экран истории тянет метаданные, тело — отдельным запросом.
- **Структура не версионируется.** Родитель в дереве, порядок среди соседей и slug применяются
  сразу, а не при публикации. Иначе получаем черновик, который переедет в момент публикации, и
  дерево в двух состояниях сразу — это невозможно ни показать, ни проверить на уникальность адреса.
- **Откат** — не «восстановить», а взять старую версию в черновик и опубликовать обычным путём.

### Новая запись

«Новая страница» — это `POST`, который сразу заводит черновик и возвращает `id`: иначе не работают
ни предпросмотр, ни автосохранение, ни агент — ровно тогда, когда собираешь страницу с нуля.

Чтобы это не било по дереву, новая запись создаётся **вне дерева**, без позиции в nested-set.
Вставка двигает границы половине таблицы, а «создать черновик одним кликом» превращает редкую
операцию в частую — это гонка и дыры от брошенных черновиков. Узел встаёт в дерево один раз: при
первой публикации или когда редактор сам выбрал родителя. В панели такие записи видны отдельной
строкой «Черновики · N» над деревом.

Для этого в `webx-ui/nested-set` есть detached-состояние: `saveDetached()` сохраняет узел с
границами 0/0 — позицией, которой у размещённого узла не бывает, так что колонки остаются как
есть и старые таблицы не трогаются. Его пропускают `ordered`, `roots`, `fixTree` и
`checkTreeIntegrity`; `appendTo()` / `saveAsRoot()` вставляют его в дерево как новый.

Нетронутый черновик — без заголовка и блоков — живёт неделю и удаляется командой; в списке он не
показывается, пока пуст.

## 12. Предпросмотр

`/_preview/{type}/{id}?token=…` — служебный адрес. Резолвер делает то же, что сделал бы на
настоящем адресе, и отдаёт ту же страницу; обработчик подсовывает `Resolution` настоящей сущности,
поэтому крошки, активный пункт меню и канонический URL не врут, хотя путь другой.

- Токен подписанный, короткоживущий, привязанный к администратору: один параметр `token`, внутри —
  тип, идентификатор, кто попросил и срок, подпись HMAC ключом приложения. Токен на одну запись
  не открывает другую; плохой или просроченный — 403, а не 404 (адрес верный, права нет).
- Ответ — `no-store` и `X-Robots-Tag: noindex`. В реестре адресов служебный путь не заводится.
- Под токеном берутся `draft` сущности **и** черновые версии типов блоков. Стили подтягиваются
  сами: у черновой версии другой хеш, значит другой набор.
- Панель показывает этот адрес в `<iframe>`; кнопка «Открыть на сайте» ведёт по нему же в новую
  вкладку, с неё и смотрят на телефоне.
- Панель и сайт — одно приложение на одном домене, поэтому мостик внутрь фрейма не нужен:
  выделение блока — это класс на элементе, подмена после правки — замена диапазона между
  комментариями (§7). В разметку сайта панель ничего не подмешивает, кроме своего `<style>`,
  живущего только в режиме предпросмотра.
- Отдельная история — показать черновик наружу (клиенту, копирайтеру): тот же механизм, другой срок
  и «только смотреть». В v0.1 не делаем, добавляется одним полем.

## 13. Экран «Блоки»

Список — карточки с живой миниатюрой на образце, группой, `slug`, числом страниц и чипами версий
(«Черновик v4», «На сайте v3»).

Редактор — две колонки. Слева вкладки «Шаблон», «Стили», «Скрипт», «Поля», «Настройки», «История»;
под редактором — строка проверок (§15) и пилюли «вставить поле», собранные из схемы. Справа —
превью на образце с переключателем ширины и обвязки, под ним форма образца, построенная из
редактируемой схемы, и «Где используется».

Цикл замкнут: правишь схему — перестраивается форма; правишь значения — перерисовывается превью;
правишь шаблон или стили — перерисовывается оно же.

## 14. Экран сущности: конструктор

Живёт в модуле-потребителе, здесь описан узел `wx-blocks`, который тот ставит в свой экран.
Вкладка «Содержимое» имеет два состояния:

- **ничего не выбрано** — две колонки: дерево блоков и превью во всю оставшуюся ширину,
  десктопное. Режим сборки: видно макет целиком, порядок блоков и стыки между ними;
- **блок выбран** — три колонки: дерево, широкая форма полей, превью ужимается до **телефона в
  натуральную величину**. Не ужатый десктоп: 1280 в колонке 420 px — это масштаб 0.32, где ничего
  не прочитать, а телефон 1:1 читается и ломается чаще.

Десктоп и планшет открываются во весь экран по кнопке, возврат по `Esc`. Выход из правки блока —
`Esc`, кнопка «Готово» или повторный клик по узлу. Меню панели схлопывается в иконки, пока открыт
конструктор. Ниже 1320 px колонка превью убирается в кнопку.

Тяжёлые поля решаются не шириной: у `WxRichText` есть «развернуть» на всю рабочую область, у
галереи в колонке сетка миниатюр, а выбор файлов открывает медиатеку модалкой.

**То, что печатает вью, тоже видно в дереве.** Если у типа есть первый экран из полей записи
(§7), над блоками стоит неперетаскиваемая строка — «Шапка статьи · из полей записи». Клик уводит
на вкладку с этими полями. Удалить её нельзя, она не блок; но без неё редактор видит в
предпросмотре заголовок, которого нет в дереве, и не понимает, где он правится.

### Выбор блока

Диалог по «+ Добавить блок» (`openModal`). В нём — карточки типов: миниатюра, отрисованная на
`sample`, название и описание. Миниатюра здесь не украшение: по названию «Секция» невозможно
отличить полосу во всю ширину от контейнера с колонками, а по картинке — можно.

- **Что показано.** Только `is_enabled` типы с опубликованной версией, разрешённые в этом месте:
  пересечение `allow` родительского узла и `allowed_in` самого типа. Исчерпавший `max_per_entity`
  показан неактивным с причиной, а не спрятан — иначе редактор ищет пропавший блок.
- **Группы** — заголовки разделов в этом списке. Нужны, когда типов становится больше десятка; при
  пяти диалог показывает плоский список без заголовков.
- **Поиск** отменяет группировку и ищет по названию, описанию и `slug` — плоским списком, как
  поиск по дереву страниц.
- **Пусто** — не пустая коробка, а объяснение: «внутрь секции можно класть только текст, галерею и
  колонки» либо «блоков ещё нет» со ссылкой в раздел, если есть право.

Список групп — в конфиге (`webx-blocks.groups`), а не enum в коде: набор зависит от сайта («Промо»,
«Каталог»), порядок задаётся там же, подписи переводятся обычным словарём интерфейса. Свободная
строка в колонке дала бы «Контент», «контент» и «Контенты» — три группы вместо одной.

Слово «пикер» — наш жаргон и до редактора не доезжает: поле типа называется «Группа», подсказка
объясняет, что это раздел в списке при добавлении блока.

## 15. Проверки

**При сохранении** (предупреждения, не запреты):

- селекторы CSS, не начинающиеся с префикса блока (`.b-{slug}`);
- голые элементные селекторы (`h2`, `a`, `img`) — они задевают весь сайт;
- `@media` вместо `@container` — у блока ширину решает контейнер, а не окно;
- отсутствие `data-wx-block` на корне.

**Перед публикацией версии** (запрет):

- шаблон компилируется;
- блок рисуется на `sample` и на значениях со всех страниц, где он уже стоит;
- переменные шаблона существуют в схеме.

Не прошло — публикации нет, ошибка показана под редактором с номером строки. Иначе одна опечатка
агента кладёт все страницы, где стоит блок.

## 16. Безопасность

- Раздел требует отдельного права (`blocks.manage`), которое по умолчанию есть только у
  супер-администратора. Правка блока — это выполнение произвольного PHP.
- `webx-blocks.editing` в конфиге выключает редактирование целиком: на проде типы приезжают
  импортом, а раздел работает на чтение.
- В README — первой строкой: доступ к разделу равен доступу к деплою.
- История версий с автором и источником (§3) — журнал аудита, и это вторая причина, по которой
  версия пишется на каждое сохранение.

## 17. Экспорт и импорт

`webx:blocks:export [slug…] --path=` пишет по файлу на тип: `{slug}.json` с манифестом, шаблоном,
стилями, скриптом и образцом. `webx:blocks:import` читает их обратно, создавая новую версию, если
содержимое отличается.

Это ответ на единственную настоящую цену хранения в базе: блок не едет через git. Проект при
желании держит выгрузку в `resources/blocks/*.json` как сид для свежей установки и как предмет
ревью, а перенос с локального сайта на боевой становится двумя командами.

## 18. MCP

Инструменты (`webx-ui/mcp`, изменяющие — с принудительным `dry_run`, область `blocks:write`).
Реестр сам добавляет к имени префикс модуля, поэтому имена короткие — `list`, а не `list_blocks`:
агент видит `blocks_list`, и `blocks_list_blocks` было бы масло масляное.

| Инструмент                                 | Что делает                                    |
| ------------------------------------------ | --------------------------------------------- |
| `blocks_list`, `blocks_get`                | каталог типов и содержимое одного             |
| `blocks_create`, `blocks_update`           | завести и править тип                         |
| `blocks_publish`                           | опубликовать версию (прогоняет проверки §15)  |
| `blocks_render`                            | отрисовать тип на присланных значениях → HTML |
| `blocks_get_content`, `blocks_set_content` | содержимое сущности                           |
| `blocks_edit_content`                      | точечная правка по ключам (§18.1)             |
| `blocks_preview_url`                       | подписанная ссылка на черновик                |

`render` и `preview_url` — не украшение, а замыкание петли: без них агент пишет шаблон, не
видя результата, и мы получаем ровно ту вёрстку, которую он вообразил.

Ресурсы и подсказки: домашние правила вёрстки (токены `--wx-*`, БЭМ с префиксом блока, контейнерные
запросы, картинки через `module-media`, что доступно в шаблоне и что запрещено), словарь узлов
экрана для схемы, каталог существующих блоков с образцами — чтобы агент переиспользовал, а не плодил
пятый герой-блок, — и список того, что сайт объявил через `webx.provide()`.

**Транспорт** — `laravel/mcp` 1.0 (вышел 14.09.2026, `php ^8.2`, `illuminate ^13.0` — в нашей
вилке), поднят в сессии E. `WebxServer` в `webx-ui/mcp` ничего не объявляет сам: на старте
читает реестр и заворачивает каждый инструмент, ресурс и подсказку в класс, которого ждёт
транспорт; JSON-схема модуля уезжает как написана, read-инструмент помечен `readOnlyHint`.
Маршрут — `{api_path}/mcp`, закрыт middleware `webx.mcp-auth`: пользователя спрашивает у guard
`sanctum`, без него 401 JSON-ом, выключенному администратору 403. **Область — это ability
Sanctum-токена**, проверяется один раз до обработчика; `php artisan webx:mcp:token email`
выпускает токен администратору со всеми областями реестра (или `--scopes=`). Тот же сервер по
stdio — `mcp:start webx`, без токена: кто может запустить artisan, может всё и так. Обработчик
получает вторым аргументом администратора, от чьего имени вызов, а отказ, который агент должен
прочитать, бросает `ToolFailure`.

### 18.1. Точечная правка содержимого — сделано 16.09.2026

Пара «прочитать дерево — записать дерево» меняет один заголовок ценой всей страницы в обе стороны,
а правку, которую за это время сделал редактор, теряет молча. Поэтому рядом стоит
`blocks_edit_content` — операции по ключам, тем же словарём, что у патчей экранов (§5 спецификации
экранов): `set`, `add`, `move`, `remove`. Второго словаря для того же понятия в системе нет.

- **`set` мержит по полям, заменяет по значению.** Поле, которого нет в операции, остаётся как
  было; поле, которое есть, берёт новое значение целиком. Глубже поля лезть нельзя — что значит
  значение, знает только тип поля.
- **`locale` пишет один язык** переводимого поля. Без него строка в переводимое поле — не правка,
  а потеря всех остальных языков, и `BlockType::localizedFields()` позволяет сказать об этом
  прямо, а не после. Обратное тоже отказ: `locale` для обычного поля.
- **Операции списком** — связная правка (добавил, переставил, убрал старый) применяется одним
  вызовом и с одной проверкой.
- **`revision`** — короткий хеш дерева, который отдаёт `blocks_get_content`. Прислал — правка
  отбивается, если содержимое с тех пор изменилось; не прислал — пишется поверх. У черновика
  своего номера нет (автосейвы — кольцо, номера у них нет), поэтому «страница, какой я её прочитал»
  — это само содержимое. `blocks_set_content` принимает `revision` тем же образом.
- **Читать тоже дёшево:** `blocks_get_content` с `outline: true` отдаёт карту (`key`, `type`,
  вложенность, строка текста), с `key` — один узел целиком.

Дерево правит `WebxUi\Blocks\ContentEdit` — чистые функции над деревом, ничего не сохраняющие;
инструменты только переводят в них аргументы и потом прогоняют результат через ту же нормализацию
ключей, что и `set_content`. Панель, когда ей понадобится то же самое, ходит туда же.

## 19. API панели

```
GET    /blocks                    список типов
POST   /blocks                    новый тип (сразу черновая версия 1)
GET    /blocks/{id}               тип с черновой и опубликованной версией
PUT    /blocks/{id}               сохранить черновик (пишет версию)
POST   /blocks/{id}/publish       опубликовать версию
POST   /blocks/{id}/render        отрисовать на присланных значениях
GET    /blocks/{id}/usage         где стоит
GET    /blocks/{id}/versions      история
POST   /blocks/{id}/versions/{n}/restore
```

Ошибки проверок — 422 в форме, которую панель уже понимает, с указанием файла и строки.

## 20. Пошаговый план

Одна ветка `feat/module-blocks` на все сессии, changeset на каждый затронутый пакет.

### Сессия A — пакет и рендер — сделано 15.09.2026

Скелет `php/packages/module-blocks`, три миграции (§3), модели, `BlockTypes` с кешем, компиляция
Blade из базы с кешем по версии, `@blocks`, `HasBlocks` + макрос `blocks()`, изоляция падений,
маркеры предпросмотра. Тесты: рендер, вложенность, лимит глубины, падение одного блока не роняет
страницу.

Что выяснилось по ходу и стало правилом:

- **Переменные шаблона — это поля схемы, а не ключи значений.** Рендер заводит переменную на
  каждый `id` из `schema` и кладёт туда значение или `null`; ключи значений, которых нет в схеме,
  переменными не становятся. Иначе поле, добавленное в блок после того, как страницы уже
  написаны, роняло бы их все «Undefined variable» — а так старые страницы печатают `null`, и это
  же правило бесплатно даёт проверку §15 «переменные шаблона существуют в схеме»: незаявленная
  переменная падает на образце при публикации.
- **`$entity` в шаблоне бывает `null`** — на проверке образца и когда блоки печатает контроллер
  сайта без сущности. Писать `$entity?->title`; проверка перед публикацией этому и учит.
- **Номер строки в исключении — это строка скомпилированного файла, не шаблона.** Blade
  удваивает перенос после каждого `{{ }}` (PHP один съедает), и файл длиннее шаблона.
  Обратно строка считается по копии шаблона с маркером в начале каждой строки — тем же
  приёмом, что у Ignition; копия не исполняется, поэтому маркер внутри выражения ничему не
  мешает.
- **`publish()` уже прогоняет проверку на образце** (компиляция и рендер, §15). Прогон по значениям
  со всех страниц, где блок стоит, — вместе с учётом использования в сессии D.
- **Указатели `draft_version_id` / `published_version_id` без FK в базе.** Таблицы ссылаются друг
  на друга, и круговое ограничение стоило бы alter в обе стороны под каждый драйвер ради того,
  что модель и так гарантирует; версии удаляются вместе с блоком в `deleting`, а не только каскадом.

### Сессия B — стили, скрипты и наборы — сделано 15.09.2026

Сборка набора, `block_bundles`, маршруты `/blocks/{hash}.css` и `.js`, директива `@webxBlocks`,
рантайм с `webx.block` / `webx.mount` / `webx.provide` / `webx.use`, команды `bundles --prune|--warm`
и `blocks:clear`. Тесты: один и тот же набор даёт один хеш; публикация версии меняет хеш только у
затронутых страниц; отдача кешируется.

Что выяснилось по ходу и стало правилом:

- **`@webxBlocks` — не `@stack`, а ленивый `echo`.** Набор вычисляется в момент печати тега, и
  этого достаточно: при `@extends` и в компонентах содержимое рисуется раньше layout'а, так что
  `<head>` уже знает всё, что ниже. Стек дал бы то же самое, но заставил бы рендер пушить набор
  на каждый `render()` и плодить дубли на странице с двумя зонами. Аргумент делит теги
  (`'styles'` в `<head>`, `'scripts'` перед `</body>`), `'runtime'` печатает один рантайм.
- **Рантайм идемпотентен и отдаётся отдельно** — `/blocks/runtime.js?v=<хеш содержимого>`.
  `webx.provide` на стороне сайта требует, чтобы `webx` уже существовал, а на странице без
  блоков набора нет вовсе; сайт, которому это нужно, печатает `@webxBlocks('runtime')` в
  `<head>` до своего входа, и копия внутри набора отходит в сторону.
- **Значения для скрипта блок несёт сам** — `data-wx-values` (JSON) на корне, рядом с
  `data-wx-block`. Рендер чужой шаблон не трогает, а второго механизма передачи не нужно.
- **Строка набора пишется, только когда есть что отдавать.** Набор без стилей и скриптов — не
  пустой файл, а молчащая директива; JS набора без скриптов — `null` и 404 без кеша.
- **`--warm` знает сущности из конфига** (`webx-blocks.entities`, классы моделей с `HasBlocks`):
  пакет сущностей не знает, а трейт регистрирует себя только при первом использовании класса.
  `--prune` сносит наборы, где хоть одна версия уже не опубликованная.
- **Список «что напечатал ответ» сбрасывается на `RequestHandled`** — иначе в долгоживущем
  процессе он рос бы между запросами, и второй ответ тянул бы стили первого.

### Сессия C — версии и предпросмотр — сделано 15.09.2026

В `module-admin`: `HasVersions`, `HasDraft`, `entity_versions`, лимиты и кольцо автосейвов,
`webx:versions:prune`. В `nested-set`: detached-состояние узла. Здесь: маршрут `/_preview/{type}/{id}`,
подписанный токен, `no-store`, `noindex`, подстановка `Resolution`. Тесты и smoke: предпросмотр
после `config:cache`, черновая версия блока видна только под токеном.

Что выяснилось по ходу и стало правилом:

- **`draft()` — макрос каркаса, `blocks()` добавляет только `blocks`.** Черновик нужен и сущности
  без блоков, а два макроса, каждый из которых добавляет `draft`, столкнулись бы в первой же
  миграции, где стоят оба. Рядом с `draft` макрос кладёт `published_at` (§11).
- **Detached-узел — это границы 0/0 плюс `parent_id = null`, а не nullable-колонки.** Границы
  размещённого узла начинаются с 1, так что 0/0 свободно, схема не меняется и старые таблицы не
  требуют alter. Строка с родителем и границами 0/0 — не черновик, а поломка (импорт записал
  `parent_id` и ничего больше), и `fixTree` её чинит. Удаление detached-узла не закрывает
  «дыру» — закрыть её на позиции 0 значило бы сдвинуть всё дерево на единицу.
- **Трейты каркаса не спрашивают друг друга через `method_exists`.** `HasVersions` исключает из
  слепка структурные колонки по именам (`draft`, `published_at`, `lft`, `rgt`, `depth`,
  `parent_id`, `slug`; переопределяется `unversionedAttributes()`), а переводимое поле берёт
  сырой JSON колонки, а не значение атрибута — иначе в версию уезжал бы один язык. `HasDraft`
  спрашивает про историю у класса (`class_uses_recursive`), не у метода: PHPStan разбирает
  трейт в контексте каждого класса, и `method_exists($this, …)` там либо «всегда истина», либо
  вызов несуществующего метода.
- **Публикация сносит автосейвы.** Они страховали черновик, которого больше нет; оставить их —
  значит предложить «восстановить» содержимое, которое старше того, что на сайте.
- **`withDraft()` — копия, а не сама модель.** Обработчик получает клон с черновиком поверх
  колонок; `save()` на нём опубликовал бы черновик мимо истории, поэтому копия и никогда не
  сохраняется. Рендерер после ответа забывает режим предпросмотра (`flush()` на
  `RequestHandled`), иначе в долгоживущем процессе следующий посетитель увидел бы черновики.
- **`Resolution` для записи без адреса — несохранённая строка `Route`** с путём от форматтера,
  если тот в состоянии его назвать, и пустым — если нет. Конструктор `Resolution` требует
  строку, а делать её nullable ради предпросмотра значило бы трогать контракт роутинга.
- **Префикс `_preview` закрыт в реестре адресов** через `Reserved::prefixes()` рядом с префиксами
  панели: маршрут с параметрами роутер про один адрес не спросишь.

### Сессия D — панель — написано 15.09.2026

npm-пакет `@webx-ui/module-blocks`: узел `wx-blocks` для описанных экранов, конструктор (§14),
раздел «Блоки» (§13), проверки в редакторе. Composer-половина: контроллеры (§19), права, экраны,
локализация в десяти языках.

Что выяснилось по ходу и стало правилом:

- **Настройки типа — форма компонента, а не описанный экран.** Экранная машинерия здесь всё же
  работает, но в другом месте: схема блока рисуется `WxScreenRenderer` — и как форма образца в
  редакторе типа, и как форма полей выбранного блока в конструкторе. Вкладка «Настройки»
  экраном быть не может: варианты `group` приходят из конфига сайта, `allow` и `allowed_in` —
  из списка соседних типов, и патчить это на каждом запросе значило бы описывать не экран, а
  его вычисление.
- **Поле схемы называется `id`, форма ждёт `name`.** Схема блока по §5 — узлы с `id`; рендерер
  привязывает поле к модели по `name`. Перед отрисовкой `formSchema()` кладёт `id` в `name`
  каждому узлу, у которого его нет, — и только на клиенте: в базе и в экспорте схема остаётся
  такой, какой её написал автор.
- **Render-эндпоинт с несохранённым шаблоном — это сохранение.** `POST /blocks/{id}/render`
  с `values` рисует то, что лежит в базе, и открыт по `blocks.view`; с `content` он компилирует
  присланный Blade, то есть исполняет PHP, и требует `blocks.manage` плюс включённое
  `editing` — ровно то, что требует `PUT`. Компилируется ad hoc в файл по хешу текста.
- **Каталог для конструктора отдаёт и выключенные типы.** `GET /blocks/catalog` — это все типы с
  опубликованной версией: пикер прячет `is_enabled = false`, а дерево страницы, где такой блок
  уже стоит, всё ещё должно уметь показать его форму. Схема в каталоге — черновая, если черновик
  есть: предпросмотр под токеном рисует черновики (§12), и форма должна знать те же поля.
- **Одинаковое содержимое версию не пишет.** `PUT` сравнивает присланные поля с текущей версией
  и пишет новую, только если что-то отличается; сохранение одних настроек версию не плодит.
  Первую версию `POST` пишет всегда, пустую, — иначе редактору нечего открыть.
- **Проверка перед публикацией — на образце и на всех страницах.** `Publisher` прогоняет черновик
  на значениях каждого экземпляра из `webx-blocks.entities` (живые и черновые деревья) и только
  потом зовёт `Block::publish()`. Отказ — 422 с сообщением под `template`, строкой шаблона и, если
  упало на странице, её названием. Из этого же следует, что учёт использования (`Usage`) читает
  оба дерева: то, что на сайте, и `draft`.
- **Линты дублируются в двух языках нарочно.** `Panel\Lints` отдаёт предупреждения с
  сохранённой версией (их же услышит агент через MCP), `lint.ts` считает те же четыре плюс
  «переменная не в схеме» вживую под редактором. Сообщения — из одного словаря `checks.*`.
- **`allowed_in` знает слово `root`.** `null` — где угодно, список — только внутри названных
  типов, и `root` в этом списке значит «и на самой странице». Иначе тип, разрешённый в секции,
  нельзя было бы разрешить ещё и в корне.
- **Перетаскивание — только среди соседей.** Перенос блока между контейнерами — не drag, а
  «дублировать» плюс «убрать»: перетаскивание через правила `allow` требовало бы судьи на каждом
  сбросе, и `WxSortableList` с общей группой такого судьи не имеет. Открытый хвост, не решение.
- **Предпросмотр сущности приезжает от хозяина экрана.** Узел не знает, какую сущность редактируют;
  экран потребителя (`module-pages`) отдаёт адрес `Preview::url()` через `provideBlocksPreview()`
  и бампает `reload` после автосейва. Без него конструктор — дерево плюс форма. Живая подмена
  после правки поля: `POST /render` с `values` и `key` → замена диапазона между маркерами
  (`frame.ts`), `webx.mount` на вставленном; если маркеров нет (блок новый, страница не
  сохранялась) — перезагрузка фрейма.
- **Отложено до `module-pages`:** строка «из полей записи» над деревом (§14) — её содержание
  знает только потребитель; схлопывание меню панели в иконки, пока открыт конструктор, — нужен
  крючок в `AdminShell`; проверка в браузере и на телефоне — на живом сайте в сессии F, у
  доков и плейграунда нет Laravel, а без него нет ни каталога, ни превью.

### Сессия E — MCP и документация — написано 15.09.2026

Транспорт в `webx-ui/mcp` на `laravel/mcp` 1.0, инструменты, ресурсы и подсказка (§18),
экспорт/импорт (§17), гайд `apps/docs/guide/blocks.md`, узел `wx-blocks` в гайде экранов.

Что выяснилось по ходу и стало правилом:

- **Sanctum только публикует миграцию.** `HasApiTokens` на `CmsUser` был с самого начала, а
  таблицы `personal_access_tokens` ни у одного сайта нет: Sanctum 4 не грузит миграции сам.
  Поэтому первый шаг README у `webx-ui/mcp` — `vendor:publish --tag=sanctum-migrations`, а
  `webx:mcp:token` проверяет таблицу и говорит, что сделать, вместо ошибки базы. В тестах
  миграцию грузим из vendor по пути класса `Sanctum`.
- **Guard кеширует пользователя между запросами одного теста.** Второй `postJson` с другим
  bearer-токеном получает пользователя первого: `RequestGuard` держит `$user`, и в тесте его
  никто не сбрасывает. Лечится `auth()->forgetGuards()` перед каждым запросом с новым токеном;
  на живом сервере это не воспроизводится — там на каждый запрос новый процесс или новый
  контейнер.
- **Один вход для трёх дверей.** Правила и нормализация формы вынесены в `Panel\BlockInput`:
  `BlockRequest`, инструменты и импорт проверяют одно и то же, поэтому файл, который
  импортируется, — это тип, который приняла бы панель. Сравнение содержимого переехало в
  `Block::contentDiffers()`, проверки без публикации — в `Publisher::check()`: это и есть
  `dry_run` у `blocks_publish`.
- **Сущность для агента называется словом, а не классом.** `Mcp\Entities` даёт имя из
  `RouteTypes` (`page`), а незарегистрированной модели — kebab-case класса; список имён уезжает
  в описание аргумента `entity`, так что агенту не нужно спрашивать.
- **`set_content` пишет черновик, публикацию сущности не предлагает.** Дерево нормализуется
  (`key` дописывается, неизвестные типы — отказ, глубина — по конфигу), кладётся в `draft` через
  `saveDraft()` с источником `mcp`; сайт показывает прежнее, пока человек не опубликует. Модель
  без `HasDraft` получает колонку напрямую — и это единственный случай, когда агент меняет живой
  сайт.
- **Экспорт — опубликованная версия, `--draft` — редактируемая.** Тип без публикации в экспорт
  по умолчанию не попадает и об этом сказано; импорт всегда кладёт черновик, `--publish` гоняет
  проверки и оставляет упавший тип черновиком с ненулевым кодом выхода.
- **Рендер не резолвит типы полей.** Значение `wx-media` в шаблон приходит как хранится —
  `{ path, alt, title }`, без адреса; в guidelines это сказано прямо, а сам резолв — открытый
  хвост §22, закрывать вместе с первыми настоящими блоками в F.

### Сессия F — релиз и демо — демо собрано 16.09.2026

Релиз обеих половин, затем `webx-cms.local`: три-четыре настоящих блока, собранная из них главная,
проверка на живом телефоне. Только после этого `module-pages` (§21).

Порядок поменяли: сначала сайт на пакетах из чекаута, потом релиз. Панель до этого никто не
видел в браузере, и цена ошибки после релиза — целый релизный круг. Демо — раздел «Страницы»
сайта: модель `Page` с четырьмя трейтами, тип адреса `page`, экран `pages.form` с узлом
`wx-blocks`, редактор с автосохранением в черновик и публикацией. Четыре типа: `hero`
написан агентом через MCP (`blocks_update` → `blocks_render` → `blocks_publish`), `text`,
`columns` (контейнер) и `gallery` (`wx-repeater` + `wx-media` + скрипт) — импортом с
`--publish`; содержимое главной положено `blocks_set_content`, опубликовано из панели.

Что выяснилось по ходу и стало правилом:

- **Контейнерный запрос на собственном классе элемента меряет предка.** `.wx-blocks` был
  и контейнером, и субъектом `@container` — а браузер разрешает запрос по ближайшему
  контейнеру-предку, то есть по чему-то чужому. Плюс порог трёх колонок применялся к
  двухколоночному состоянию, и на ноутбуке превью страницы не появлялось вовсе. Контейнер
  теперь на обёртке `.wx-blocks-host`, превью прячется в кнопку только в режиме правки
  ниже 1080px и в одну колонку ниже 720px.
- **Несуществующий токен молчит.** Четыре имени (`--wx-color-border`, `--wx-color-surface`,
  `--wx-color-surface-sunken`, `--wx-color-text-muted`) не существуют, `var()` от них — пустота:
  панели дерева и формы стояли без рамок и фона, тесты этого не видят. Проверять
  `grep -o "var(--wx-[a-z0-9-]*)"` против `tokens.css`.
- **`wx-media` в шаблоне печатался через диск.** Обход в одну строку —
  `Storage::disk(config('webx-media.disk'))->url($image['path'])`, — так была собрана галерея
  демо; хвост §22 закрыт в сессии G, и обход из демо убран.
- **Петля агента сошлась с первого раза:** `blocks_update` записал версию с источником `mcp`,
  `blocks_render` показал HTML на образце, `blocks_publish` опубликовал; `blocks_set_content`
  положил шесть узлов с вложенностью и вернул ссылку на предпросмотр. Транспорт — POST
  JSON-RPC на `/api/cms/mcp` с `Accept: application/json, text/event-stream`, без
  `initialize`.
- **Скомпилированный шаблон называется по содержимому, а не только по номеру** (PR #136).
  Тесты сайта на sqlite в памяти и сам сайт компилируют в один каталог, и у каждого свой
  `hero` версии 1 — у панели это пустой черновик, у импорта настоящий шаблон. Кто первый
  скомпилировал, того и печатали: тест получал страницу без hero и ни одной ошибки. Имя
  файла теперь `{slug}-{version}-{sha1[:12]}.php`; свойство «новая версия — новый файл,
  ничего не инвалидируется» сохранено.

### Сессия G — значения полей резолвятся — сделано 16.09.2026

Хвост §22: `Rendering\Values` в рендере, `wx-media` в шаблоне отдаёт `url`. Тесты: поле,
поле внутри `wx-repeater`, поле внутри layout-узла, значение вне схемы и вложенное дерево —
как есть.

Что выяснилось по ходу и стало правилом:

- **Схема блока называет поля `id`, а всё, что ходит по экрану, ищет `name`.** `Tree::fields()`
  останавливается на узле с `name` — этим и живёт `wx-repeater`, которому надо найти поля одного
  элемента. У блока имён нет, поэтому `wx-repeater` с `wx-media` внутри не резолвился бы вовсе:
  список полей элемента пустой, значит резолвить нечего, и ошибки при этом никакой. Перед
  резолвом схема нормализуется (`id` → `name`) — так же, как `formSchema()` делает на клиенте и
  ровно по той же причине; в базе, в экспорте и у агента схема остаётся авторской.
- **Что под полем — принадлежит полю, а не блоку.** Обход собирает узлы в карту `id → узел` и
  спускается в `children` только у того, чей тип в реестре не зарегистрирован: layout (`wx-card`,
  `wx-tabs`) держит поля самого блока, а `wx-repeater` — поля своего элемента, и `city` из
  элемента не должен становиться ключом верхнего уровня.
- **Резолв — до `BlockContext`, а не в `$data`.** Иначе переменная шаблона знает адрес картинки,
  а `$block->values`, которым шаблон кормит скрипт через `data-wx-values`, — нет; галерея на
  скрипте получила бы пути вместо адресов.
- **`MediaFieldType` спрашивает базу на каждое значение.** Страница с галереей из десяти картинок
  — десять запросов там, где сайт раньше звал `Storage::url()`. Поле теперь помнит найденные
  строки на время ответа (сброс на `RequestHandled`, как у рендера); помнится строка, а не адрес:
  подписанная ссылка приватного бакета живёт час, и отдавать её из памяти нельзя.

## 21. Что потом

`module-pages` пишется поверх готового конструктора: тип `page` с форматтером `TreePath`, дерево на
`nested-set`, `HasBlocks`, `HasVersions`, `HasSeo` и экран из §14. Он же закрывает отложенную
проверку `module-seo` на живом телефоне (§16 её спеки) и даёт реестру адресов первого потребителя.

## 22. Открыто и отложено

- **Переводимость содержимого.** Скорее всего `blocks` и `draft` переводимы целиком, то есть
  структура блоков у каждого языка своя: на разных языках вёрстка расходится, а «синхронизировать
  структуру» — источник вечных багов. Решить вместе с `module-pages`, когда появится вторая локаль
  на живой сущности.
- **Типы блоков из кода.** Блок, написанный руками в репозитории сайта, — законный случай, но в
  v0.1 реестр читает только базу. Добавляется вторым источником, контракт не меняется.
- **Правка простого текста прямо в превью** (`contenteditable` на узле с `data-field`). Заметно
  улучшает работу, но тянет каретку, undo и вставку из Word.
- **Глобальные элементы** (шапка, подвал, форма подписки, настраиваемые один раз) и **шаблоны
  блоков** — готовые связки из нескольких блоков. Механизм тот же, спроектировать позже.
- **Сравнение двух версий** типа блока построчно. В v0.1 — только откат.
- **Ссылка на черновик наружу** с длинным сроком и без права правки (§12).
- **Импорт вёрстки**: отдать агенту готовый HTML и получить предложенное разбиение на поля. Это
  сценарий, а не механизм, — ресурсы MCP есть с сессии E, осталось попробовать на живом сайте.
