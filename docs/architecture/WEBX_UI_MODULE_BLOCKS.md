# `webx-ui/module-blocks` — спецификация

Конструктор блоков: раздел панели, в котором тип блока создаётся целиком — схема полей, шаблон
Blade, стили и скрипт, — и механизм, который собирает из таких блоков содержимое любой сущности и
печатает его на сайте. Реестр пакетов — [`WEBX_UI_COMPOSER_PACKAGES.md`](WEBX_UI_COMPOSER_PACKAGES.md),
экраны — [`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md), адреса — [`WEBX_UI_ROUTING.md`](WEBX_UI_ROUTING.md).

Статус: выпущено (§20), вместе с видимостью блока (§23), компонентами (§24) и зонами лейаута
([`WEBX_UI_LAYOUT_REGIONS.md`](WEBX_UI_LAYOUT_REGIONS.md)); нерешённое — в §22.

Содержимое любой сущности — массив блоков, и формат хранения общий: `module-pages` и другие
потребители подключают трейт `HasBlocks` и узел `wx-blocks` в своём экране и больше ничего про
блоки не знают.

## 1. Границы

Пакет владеет четырьмя вопросами:

1. **Что такое тип блока** — из чего он состоит, где хранится, как версионируется (§4, §5).
2. **Как блок превращается в HTML** — рендер, вложенность, изоляция падений (§7, §8).
3. **Как его стили и скрипты попадают на страницу** — наборы по хешу, рантайм, мост к сборке
   сайта (§9, §10).
4. **Как всем этим управляют** — раздел панели, MCP, экспорт (§14, §18, §17).

Пакет **не** владеет: сущностями (страницами, статьями, товарами), их адресами, их SEO и их
версиями. Версии и черновики — общий механизм каркаса `module-admin` (§11), блоки лишь занимают
место в слепке.

### Почему один пакет, а не библиотека плюс раздел

У блоков нет жизни без панели: библиотека, которая рисует блоки, но не заводит их, бесполезна —
типы не в коде, а в базе. Шов между половинами держится внутри пакета, как в `module-seo`:
`WebxUi\Blocks\Rendering\` и `WebxUi\Blocks\Panel\`.

## 2. Принятые решения (не переоткрывать)

- **Источник правды — база, не файлы.** Блок целиком (схема, шаблон, CSS, JS) — строки в БД.
  Генерация файлов в `resources/` отвергнута: на хомлабе образ собирается из репозитория, и
  следующий деплой снёс бы всё, что сделали в панели. Переносимость решается экспортом (§17), а не
  местом хранения.
- **Blade редактируется через панель, и это осознанный риск.** `@php`, вызовы хелперов, `{!! !!}`
  доступны. Песочницы не будет: в любом подмножестве, которое мы придумаем, найдётся дыра. Раздел
  доступен одной роли и выключается конфигом; доступ к нему приравнен к доступу к деплою (§16).
- **Вложенность — это поле, а не отдельная сущность.** Блок-контейнер («Секция») объявляет в своей
  схеме узел `wx-blocks`, значение которого — массив блоков (§6). Никакого второго механизма
  «слотов» нет.
- **Второй механизм — компоненты, и он для шаблонов, а не для содержимого.** Тип блока можно
  вызвать тегом `<x-webx-block type="…">` из любого шаблона — другого блока, вьюхи модуля,
  лейаута сайта; тип вида `component` в выборе блоков не стоит вовсе. Слоты у тега есть, но это
  слоты вызова, а не вложенность содержимого: дерево страницы по-прежнему держит только
  `wx-blocks`. Подробно — §24.
- **Версия типа блока пишется на каждое сохранение.** Это код, история правок работает журналом
  аудита — прямое следствие решения про `@php`. У сущностей политика другая (§11).
- **Публикация блока — своё действие.** Опубликованная версия действует на все страницы, где блок
  стоит. Кнопка публикации страницы не публикует блок молча, а предупреждает и называет число
  затронутых страниц.
- **Стили и скрипты едут набором по хешу** (§9), а не всем файлом и не инлайном по умолчанию.
- **У скрипта есть контракт входа** — функция на экземпляр, а не код, выполняемый один раз (§10).
  Без него ломаются: два одинаковых блока на странице, вложенный блок и — в первую очередь —
  подмена узла в предпросмотре.
- **Предпросмотр — служебный адрес с идентификатором** (`/_preview/{type}/{id}`), не канонический
  адрес с параметром: у новой записи адреса ещё нет (§12).
- **Один рендер на всё.** Предпросмотр в панели, ссылка «Открыть на сайте» и живая страница — один
  и тот же код. Отдельного «рендера для панели» не существует.
- **Видимость — ключ в структуре узла, а не поле схемы** (§23). `hidden: true` рядом с `key`,
  `type` и `values`; нет ключа — блок виден. Пропуск один, в `Renderer::list()`, поэтому
  выключенный контейнер выключает и всё внутри, ничего там не стирая.

## 3. Схема

### `blocks` — тип блока

| Колонка                | Тип               | Смысл                                                         |
| ---------------------- | ----------------- | ------------------------------------------------------------- |
| `id`                   | id                |                                                               |
| `slug`                 | string(64) unique | он же `type` в значениях; переименование — ломающее изменение |
| `title`                | string(120)       | как называется в списке при добавлении блока                  |
| `description`          | string(255) null  | подсказка редактору и инструкция агенту                       |
| `icon`                 | string(64) null   | имя из набора ядра                                            |
| `group`                | string(64)        | раздел в списке при добавлении блока; из `webx-blocks.groups` |
| `sort`                 | smallint          | порядок в каскаде CSS (§9) и в списке блоков                  |
| `allow`                | json null         | какие типы можно класть внутрь; `null` — блок не контейнер    |
| `allowed_in`           | json null         | где разрешён сам; `null` — где угодно                         |
| `max_per_entity`       | smallint null     | сколько экземпляров на сущность                               |
| `is_enabled`           | bool              | скрыт от редакторов, но продолжает рисоваться                 |
| `draft_version_id`     | fk null           | черновая версия; `null` — черновика нет                       |
| `published_version_id` | fk null           | что действует на сайте; `null` — не публиковался              |
| timestamps             |                   |                                                               |

**`title` и `description` не переводимые колонки, и это решение.** Подписи полей блока живут в
`schema` и переводятся маркером `trans::<namespace>::<key>` (§10 спеки экранов); json-колонка с
`HasTranslations` у заголовка дала бы второй механизм, который разъезжается с первым в форме,
экспорте и MCP. Многоязычной панели в это поле пишут тот же `trans::`-маркер. Переход `string` →
переводимая колонка дешёв, обратный — нет.

### `block_versions` — неизменяемый слепок

| Колонка      | Тип              | Смысл                                             |
| ------------ | ---------------- | ------------------------------------------------- |
| `id`         | id               |                                                   |
| `block_id`   | fk               |                                                   |
| `number`     | int              | 1, 2, 3… в пределах блока; уникально с `block_id` |
| `schema`     | json             | дерево узлов экрана (§5)                          |
| `template`   | longtext         | Blade                                             |
| `styles`     | longtext         | CSS                                               |
| `script`     | longtext null    | тело инициализатора (§10)                         |
| `sample`     | json             | образцовые значения                               |
| `author_id`  | fk null          |                                                   |
| `source`     | string(16)       | `panel` \| `mcp` \| `import`                      |
| `comment`    | string(255) null |                                                   |
| `created_at` |                  |                                                   |

Слепок целиком, а не диффом: откат тривиален, а экономить тут нечего — версия блока это несколько
килобайт текста.

### `block_bundles` — собранный набор стилей и скриптов

| Колонка      | Тип           | Смысл                                             |
| ------------ | ------------- | ------------------------------------------------- |
| `hash`       | string(16) pk | хеш от отсортированного списка пар «тип + версия» |
| `types`      | json          | из чего собран — для отладки и чистки             |
| `css`        | longtext      | склейка, в порядке `sort`                         |
| `js`         | longtext null | склейка инициализаторов                           |
| `created_at` |               |                                                   |

Пишется при первом рендере такого набора, читается маршрутом отдачи (§9). Не кеш, а таблица:
сброшенный кеш на проде не должен превращаться в страницу без стилей.

### Что добавляется сущности

Трейт `HasBlocks` не требует своей таблицы: содержимое лежит json-колонкой на самой сущности
(`blocks`), и ещё одной — черновик (`draft`, §11). Blueprint-макрос `blocks()` добавляет только
`blocks`; черновик и `published_at` добавляет макрос `draft()` каркаса `module-admin` — черновики
его механизм, и сущности без блоков (товару) они нужны точно так же.

## 4. Из чего состоит тип блока

Опознание и показ — `slug`, `title`, `description`, `icon`, `group`, `sort`, `is_enabled`.
Ограничения — `allow`, `allowed_in`, `max_per_entity`. Содержательная часть живёт в версии:
`schema`, `template`, `styles`, `script`, `sample`.

`sample` — не украшение. Он решает три задачи сразу: превью при выборе блока (§14), значения для проверки
рендером перед публикацией (§15) и самая понятная агенту документация формы данных (§18).

## 5. Схема полей — это узлы экрана

Схема блока — массив узлов формата `@webx-ui/schema` (`{ id, type, label, props, visible }`), тот
же, что у описанных экранов. Следствия: форму строит существующий `WxScreenRenderer`; правила
валидации выводятся тем же кодом, что в `module-settings` (`ScreenValues`, включая ловушку с
точкой в ключе); переводимые подписи работают маркером `trans::`.

Отдельного языка описания полей не заводим — это и есть содержание §12 спеки экранов.

## 6. Вложенность

Узел `wx-blocks` в схеме блока объявляет вложенный конструктор:

```json
{
  "type": "wx-blocks",
  "id": "content",
  "label": "Содержимое",
  "props": { "allow": ["text", "gallery", "columns"], "max": 8 }
}
```

Значение такого поля — массив узлов той же формы, что и корневое содержимое сущности:

```json
[ { "key": "01H…", "type": "section", "values": { "background": "muted",
    "content": [ { "key": "01H…", "type": "text", "values": { … } } ] } } ]
```

`key` — идентификатор экземпляра, генерируется при добавлении и переживает перетаскивание: по нему
панель подменяет узел в предпросмотре, а `WxRepeater` держит форму под кареткой.

Шаблон печатает вложенное директивой `@blocks('content')`. Глубина ограничена пятью уровнями —
дальше это уже не конструктор, а вёрстка мышкой.

## 7. Рендер

```php
Blocks::render($entity->blocks)   // → HtmlString
```

- Шаблон компилируется `Blade::compileString()` в файл, имя которого содержит номер версии
  (§20), поэтому инвалидации не требуется: новая версия — другой файл. `view:cache` эти шаблоны не
  трогает, первый запрос после деплоя компилирует заново.
- **Каждый блок рисуется в `try`/`catch`.** На проде исключение уходит в лог, на месте блока
  остаётся пусто; в предпросмотре — плашка с сообщением и номером строки. Без этого опечатка в
  одном шаблоне уносит весь документ, и узнаём мы об этом от посетителя.
- В шаблон приходят значения блока (`$title`, `$tone`, …), `$block` (тип, версия, `key`) и
  `$entity`.
- **Значение приходит таким, каким его отдаёт тип поля,** а не таким, как лежит в базе:
  `Rendering\Values` прогоняет каждое значение через `FieldType::resolve()` — ровно то же, что
  `ScreenValues` делает для настроек. `wx-media` хранит `{ path, alt, title }`, а шаблон читает
  ещё и `url`. Значение типа, которого нет в реестре (`wx-blocks`, поле проекта), и значение
  ключа, которого нет в схеме, проходят как есть. Резолв — один на блок, до создания
  `BlockContext`, поэтому `$block->values` (и `data-wx-values` для скрипта) говорит то же,
  что переменные.
- **В режиме предпросмотра** рендер оборачивает каждый блок парой HTML-комментариев
  `<!--wx:{key}-->…<!--/wx:{key}-->`. По ним панель находит диапазон и подменяет его после правки
  поля. Комментарии не влияют на вёрстку и на живом сайте не печатаются.
- `data-wx-block="{slug}"` на корне пишет автор шаблона — это нужно рантайму скриптов (§10) и на
  живом сайте тоже. Отсутствие — предупреждение при сохранении, не ошибка.

### Обвязка: чей шаблон

Блоки — это середина документа. Всё вокруг них принадлежит другим, и границы такие:

- **Layout — сайта.** `<html>`, `<head>` с `@webxSeo` и `@webxBlocks`, шапка, подвал. Лежит в
  репозитории сайта; мы его не поставляем.
- **Вью на тип сущности — модуля-потребителя.** `module-pages` везёт `show.blade.php`, где внутри
  сайтового layout стоит `@blocks('content')` и больше ничего. `module-news` везёт свой, где перед
  блоками напечатан первый экран статьи.
- **Какой вью — решает сущность.** Поле «Шаблон» на её экране выбирает из списка, объявленного
  проектом в конфиге (ключ → имя вью). Сайт добавляет свои варианты, не трогая модуль; сам вью
  публикуемый и переопределяется целиком.

Отсюда требование к модулю-потребителю: **имя layout берётся из конфига**
(`webx-<модуль>.layout`, по умолчанию `layouts.app`), а если такого вью нет — модуль подставляет
свой запасной, голый документ с `@webxSeo`, `@webxBlocks` и содержимым. Иначе на свежей установке,
пока у сайта ещё нет вёрстки, предпросмотр показывает пустоту, и выглядит это как сломанный
модуль, а не как пустой сайт.

Предпросмотр при этом **ничего не выбирает**: он зовёт тот же обработчик типа из `routing`, что
отвечает на настоящий адрес, и тот сам берёт вью по полю сущности. Панель знает только тип и
идентификатор (§12).

### Что проект подменяет под себя

Публичных контроллеров у сущностей нет: `routing` держит один `Route::fallback()` и отдаёт
найденную запись обработчику типа (`RouteHandler`, §6 спеки роутинга). Он и есть контроллер,
живёт в модуле-потребителе — `WebxUi\Pages\Rendering\PageHandler`. У самого `module-blocks`
публичных маршрутов два: отдача набора (§9) и предпросмотр (§12).

**Страница, которой не нужен редактор,** остаётся обычной страницей Laravel: маршрут в
`routes/web.php` сайта, свой контроллер, свой вью на том же layout. Резолвер ей не мешает — он на
`Route::fallback()`, то есть включается, только когда обычного маршрута нет. И редактор не заведёт
дубль: реестр при сохранении адреса опрашивает роутер (§10 спеки роутинга) и отклоняет занятый
путь ошибкой под полем. Такой контроллер при этом волен печатать `Blocks::render()` где угодно
посреди своего вью — «нередактируемая» обычно значит «структура зафиксирована кодом», а не
«редактор не трогает ничего».

Подменяется это лестницей, от дешёвого к дорогому:

1. **Свой блок** — большинство «нужно персонально под проект» это кусок вёрстки, а он теперь
   заводится в панели без кода вообще.
2. **Вью** — публикуется в `resources/views/vendor/<модуль>/`, дальше вёрстка целиком проектная.
3. **Конфиг** — layout, список шаблонов, группы блоков, класс модели.
4. **View composer** — если вью нужны свои данные (меню, крошки, похожие статьи). Своего механизма
   не заводим: в Laravel он есть и его знают.
5. **Свой обработчик типа** — `AppServiceProvider::boot()` выполняется после провайдеров пакетов,
   а `RouteTypes::register()` пишет по ключу типа, поэтому повторная регистрация перекрывает
   модульную. Это **поддерживаемое поведение**, а не побочный эффект реализации, и должно быть
   записано в спеке роутинга и покрыто тестом.
6. **Своя модель** — через конфиг модуля; колонки добавляет миграция проекта.

Первые четыре ступени расхождения с обновлениями модуля не создают, две последние — создают,
поэтому они последнее средство.

### Первый экран сущности

У статьи перед блоками обычно стоит шапка с заголовком, датой, автором и обложкой. Она печатается
**вью, а не блоком**: это поля записи, они уже спрошены на её экране, и заводить для них блок
значит спрашивать дважды и разрешать редактору удалить заголовок статьи.

Ловушка, которую это создаёт, закрывается в конструкторе (§14): редактор видит в предпросмотре
крупный заголовок, не находит его в дереве блоков и не понимает, где это править.

## 8. Реестр типов

```php
BlockTypes::all();            // включённые типы с опубликованной версией
BlockTypes::find('hero');
BlockTypes::draft('hero');    // черновая версия — только под токеном предпросмотра
```

Реестр читает базу и кеширует список; инвалидация — при публикации версии и командой
`webx:blocks:clear`. Типы из кода не поддерживаются: всё, что есть, заведено в панели (§22).

## 9. Стили и скрипты

Какие типы стоят на странице, известно из дерева значений. Дальше:

1. Множество пар «тип + версия» → отсортировать по `sort`, затем по `slug` → хеш.
2. `@webxBlocks` в `<head>` печатает `<link rel="stylesheet" href="/blocks/{hash}.css">`, а перед
   `</body>` — `<script type="module" src="/blocks/{hash}.js">`, если у набора есть скрипты.
3. Маршрут отдаёт строку из `block_bundles` с `Cache-Control: public, max-age=31536000, immutable`.

**`@webxBlocks` не вычисляется заранее, а печатается лениво** (§20): в уже «пройденный» `<head>`
попадает то, что отрисовали ниже по документу. Это нужно страницам, которые сайт рисует своим
контроллером и зовёт `Blocks::render()` посреди вью (§7), — вычислить набор «до рендера» там
невозможно. На странице без блоков не печатается ничего.

Почему набором, а не одним файлом на сайт: страница тянет только то, что на ней стоит. Почему
файлом, а не инлайном: хеш содержит версии, поэтому файл кешируется навсегда, а страницы с
одинаковым набором его делят — на сайте из двухсот страниц наборов оказывается пара десятков.
Публикация новой версии меняет хеш только у тех страниц, где блок стоит. Инлайн остаётся режимом в
конфиге для маленьких наборов.

Порядок склейки — по `sort` типа: два блока рано или поздно заспорят за одно правило, и решать
спор должен автор, а не алфавит.

Чистка и прогрев — `webx:blocks:bundles --prune` и `--warm`.

## 10. Контракт входа скрипта и мост к сборке сайта

Поле `script` — **тело инициализатора**, а не код, выполняемый один раз. В набор оно едет обёрнутым:

```js
webx.block('hero', async (el, values) => {
  /* тело */
})
```

Рантайм (~30 строк, едет тем же файлом) находит `[data-wx-block="hero"]` и зовёт функцию на каждый
найденный корень; повторный вызов на поддереве — `webx.mount(root)`, им же пользуется панель после
подмены узла.

Мост к тому, что уже собрано на сайте:

```js
webx.provide('swiper', Swiper) // точка входа сайта
const Swiper = await webx.use('swiper') // скрипт блока
```

`use` возвращает промис: бандл сайта может приехать позже. Список того, что сайт объявил, — данные:
он показывается в редакторе блока рядом с полем скрипта и отдаётся ресурсом в MCP, чтобы агент знал,
что доступно **на этом** сайте. Путь роста, если понадобится настоящий `import`, — import map из
манифеста Vite; написанное он не ломает.

## 11. Черновики и версии сущностей

Механизм общий и живёт в каркасе `module-admin` — он понадобится новостям и товарам, а не только
страницам. Здесь описан потому, что без него не работает предпросмотр.

**Три места и правило, которое их разводит:**

- колонки сущности — **то, что сейчас на сайте**;
- `draft` (json на той же строке) — **то, что готовится**; черновик ровно один;
- `cms_versions` — **прошлое сайта**.

Публикация копирует `draft` в колонки и пишет строку в историю. Живой сайт читает колонки,
предпросмотр — `draft`. Для ни разу не опубликованной записи это работает само: колонки пустые,
`draft` полон, версий ноль.

```
cms_versions
  id
  versionable_type, versionable_id     -- индекс (type, id, number)
  number        -- 1, 2, 3… у публикаций; у автосейва null — это не точка истории
  kind          -- published | autosave
  payload json  -- слепок: переводимые поля, blocks, вклад HasSeo
  is_pinned
  author_id, source, comment
  created_at
```

Рядом с `draft` у сущности лежит `published_at`: обработчик адреса отвечает по нему 404 без
единого запроса, а «ни разу не публиковалась» и «снята с сайта» — одно и то же состояние.

- **История — это публикации.** Промежуточные сохранения в неё не пишутся: слепок страницы с
  блоками весит килобайты, автосохранение раз в полминуты за месяц даст тысячи строк, и прочитать
  такую историю невозможно — в ней нет событий.
- **`kind = autosave`** — кольцо из пяти последних снимков черновика. Не история, а страховка на
  случай «снёс блок, автосохранилось, вкладку закрыл». В отдельной вкладке не показывается.
- **Лимит — тридцать публикаций на сущность**, подрезка происходит в момент записи новой, поэтому
  превысить его невозможно. Команда `webx:versions:prune` нужна на случай, когда лимит уменьшили.
  Флаг «закрепить версию» выводит её из-под подрезки.
- **`payload` не выбирается в списке.** Экран истории тянет метаданные, тело — отдельным запросом.
- **Структура не версионируется.** Родитель в дереве, порядок среди соседей и slug применяются
  сразу, а не при публикации. Иначе получаем черновик, который переедет в момент публикации, и
  дерево в двух состояниях сразу — это невозможно ни показать, ни проверить на уникальность адреса.
- **Откат** — не «восстановить», а взять старую версию в черновик и опубликовать обычным путём.

### Новая запись

«Новая страница» — это `POST`, который сразу заводит черновик и возвращает `id`: иначе не работают
ни предпросмотр, ни автосохранение, ни агент — ровно тогда, когда собираешь страницу с нуля.

Чтобы это не било по дереву, новая запись создаётся **вне дерева**, без позиции в nested-set.
Вставка двигает границы половине таблицы, а «создать черновик одним кликом» превращает редкую
операцию в частую — это гонка и дыры от брошенных черновиков. Узел встаёт в дерево один раз: при
первой публикации или когда редактор сам выбрал родителя. В панели такие записи видны отдельной
строкой «Черновики · N» над деревом.

Для этого в `webx-ui/nested-set` есть detached-состояние: `saveDetached()` сохраняет узел с
границами 0/0 — позицией, которой у размещённого узла не бывает, так что колонки остаются как
есть и старые таблицы не трогаются. Его пропускают `ordered`, `roots`, `fixTree` и
`checkTreeIntegrity`; `appendTo()` / `saveAsRoot()` вставляют его в дерево как новый.

Нетронутый черновик — без заголовка и блоков — живёт неделю и удаляется командой; в списке он не
показывается, пока пуст.

## 12. Предпросмотр

`/_preview/{type}/{id}?token=…` — служебный адрес. Резолвер делает то же, что сделал бы на
настоящем адресе, и отдаёт ту же страницу; обработчик подсовывает `Resolution` настоящей сущности,
поэтому крошки, активный пункт меню и канонический URL не врут, хотя путь другой.

- Токен подписанный, короткоживущий, привязанный к администратору: один параметр `token`, внутри —
  тип, идентификатор, кто попросил и срок, подпись HMAC ключом приложения. Токен на одну запись
  не открывает другую; плохой или просроченный — 403, а не 404 (адрес верный, права нет).
- Ответ — `no-store` и `X-Robots-Tag: noindex`. В реестре адресов служебный путь не заводится.
- Под токеном берутся `draft` сущности **и** черновые версии типов блоков. Стили подтягиваются
  сами: у черновой версии другой хеш, значит другой набор.
- Панель показывает этот адрес в `<iframe>`; кнопка «Открыть на сайте» ведёт по нему же в новую
  вкладку, с неё и смотрят на телефоне.
- Панель и сайт — одно приложение на одном домене, поэтому мостик внутрь фрейма не нужен:
  выделение блока — это класс на элементе, подмена после правки — замена диапазона между
  комментариями (§7). В разметку сайта панель ничего не подмешивает, кроме своего `<style>`,
  живущего только в режиме предпросмотра.
- Отдельная история — показать черновик наружу (клиенту, копирайтеру): тот же механизм, другой срок
  и «только смотреть». Не сделано (§22), добавляется одним полем.

## 13. Экран «Блоки»

Список — карточки с живой миниатюрой на образце, группой, `slug`, числом страниц и чипами версий
(«Черновик v4», «На сайте v3»).

Редактор — вкладки «Шаблон», «Стили», «Скрипт», «Поля», «Настройки», «История» во всю ширину
экрана, и у каждой рядом то, что нужно ей. Под редактором кода — строка проверок (§15), у шаблона
ещё и пилюли «вставить поле», собранные из схемы.

**Справа стоит то, что нужно открытой вкладке:** превью на образце с переключателем
ширины — у «Шаблона» и «Стилей» (оба рисуют блок), форма образца, построенная из редактируемой
схемы, — у «Полей». У «Скрипта», «Настроек» и «Истории» справа нет ничего, и они занимают всю
ширину. Ниже 1080 px поля колонка одна.

Превью одно на обе вкладки и переключается `v-show`, а не `v-if`: фрейм, вынутый из документа и
вставленный обратно, перезагружается. Зато скрытая вкладка — это `display: none`, где у документа
во фрейме высота ноль, поэтому `BlockStage` меряет себя заново, когда к нему возвращается ширина.

**Превью стоит на странице сайта.** Блок на браузерных стилях выглядит черновиком,
поэтому `BlockStage` грузит `/_preview/block-stage` (`StageController`): макет из
`webx-blocks.layout` — тот же `<x-layout>`, что у страниц, с шапкой, подвалом и стилями сайта, —
а в слоте пустая пара маркеров `sample` и пустой `<style id="wx-stage-styles">` в голове.
Страница грузится один раз; каждая правка шаблона, стилей или образца подменяет блок между
маркерами и текст стиля (`fillStage`), а не перезагружает документ — иначе шапка перерисовывалась
бы на каждый символ. Перезагрузка только на новый скрипт: `webx.block()` назад не отзывается.
Ссылки и формы сайта во фрейме заморожены (`freezeFrame`). Фрейм высотой со страницу, своего
скролла у сцены нет — прокручивается панель, как у превью страниц (`is-grown`): окно с
`max-height` обрезало подвал сайта. Пустой ключ — `webx-blocks::standalone`; `webx:panel --sync` и
`webx:doctor` работают с ним так же, как с `webx-pages.layout`. Ответ `render` называет адрес
сцены (`stage`); без него клиент рисует блок на голом документе.

Под редактором скрипта — три примера: обработчик, значение из `values` и библиотека через
`webx.use()`. Код английский и не переводится, подпись к каждому — строка словаря. Читать, а не
вставлять: четыре строки, упавшие в середину чужой функции, — не услуга.

Значок типа выбирается из набора (`WxIconPicker`), а не вписывается руками: имени, которого в
наборе нет, `WxIcon` не рисует вовсе и ничего об этом не говорит (§4 `CLAUDE.md`).

**«Где используется» — поповер за словами «на 3 страницах»** в подзаголовке, оформленными ссылкой,
а не карточка в колонке.

Цикл замкнут: правишь схему — перестраивается форма; правишь значения или шаблон со стилями —
перерисовывается превью.

Ширину превью выбирает переключатель, но **первую выбирает само превью**: самое широкое
устройство, которое влезает в колонку хотя бы вполовину (десктоп 1280 в колонке телефона —
картинка страницы с буквами в два пикселя). С первого клика ширина принадлежит редактору.

Кнопки «Сохранить» и «Опубликовать» дублируются в панели действий, **состояние — нет**: чипы
версий стоят рядом с именем, и второй раз внизу они не говорят ничего нового.

## 14. Экран сущности: конструктор

Живёт в модуле-потребителе, здесь описан узел `wx-blocks`, который тот ставит в свой экран.
Вкладка «Содержимое» имеет два состояния:

Колонки две в обоих состояниях: узкая — дерево или форма открытого блока на его месте, широкая —
превью всей страницы. Меняется только узкая:

- **ничего не выбрано** — дерево блоков. Режим сборки: видно макет целиком, порядок блоков и стыки
  между ними;
- **блок выбран** — форма его полей вместо дерева. Превью не двигается и не ужимается: страница
  под формой — это та же страница, про которую форма.

Ширина узкой колонки одна на оба состояния — `clamp(360px, 34%, 520px)`, — и именно потому, что
они в ней сменяются: колонка, меняющая размер, двигала бы превью и пересчитывала его масштаб на
каждом открытии блока. Третьей колонки (форма отдельно от дерева) нет нарочно: превью в ней
ужималось бы до телефона, а телефон — выбор в панели превью, а не следствие раскладки.

**На узкой панели колонка одна, и это превью.** Ниже 900 px поля дерево и форма переезжают в
ящик снизу (`WxDrawer`, 88% высоты — полоска страницы сверху говорит, что ящик _над_ страницей).
Открывают его карандашом в панели превью (только в этом режиме) и кликом по блоку в превью —
сразу на форме этого блока. Превью здесь начинается с телефона, на планшете — с 834; серого поля
по бокам нет — с ним страница уже шапки и панели действий. Решает замер (`useElementWidth`), а не
контейнерный запрос: меняется место, где дерево и форма отрисованы, а такое CSS не умеет.
Компактный режим требует превью — дверь в ящик на его панели.

В ящике название блока — заголовок ящика с путём по вложенности; идентификатор типа (`cta`) туда
не едет: телефон — место, где блок заполняют, а не пишут. «Esc» дописывается к «Готово» только
там, где эта клавиша есть. `···` в строке дерева рисуется в 32 px, а нажимается в 44 (палец-мишень
`WxActions`), разницу добирает невидимая юбка `::after`.

Ширину превью выбирают переключателем в его панели — десктоп, планшет, телефон; по умолчанию
десктоп. Во весь экран — кнопкой, возврат по `Esc`. Выход из правки блока — `Esc`, кнопка «Готово»
или повторный клик по узлу. Меню панели схлопывается в иконки, пока открыт конструктор. Ниже
720 px колонка превью убирается в кнопку — порог один, потому что состояние раскладки одно.

Строка дерева — ручка перетаскивания, название, флаги и `···`. Плитки со значком типа нет: у
большинства типов своего значка не заведено, и одна и та же плитка на всех строках ничего не
различала бы.

**Выбор блока доводит его до окна — минимальным сдвигом и только если он не помещается
целиком**, не по центру. Считается полоса между плавающими панелями (превью сверху, действия
снизу), а не весь экран; не влезающий в полосу блок ставится к её верху. Правило одно для клика в
дереве и в превью.

**Двигается при этом панель, и только она.** `scrollIntoView` не годится: он прокручивает _все_
прокручиваемые предки, включая документ во фрейме, и превью оставалось без начала с пустым фреймом
внизу. Поэтому сдвиг считается сам и применяется к ближайшему прокручиваемому предку превью (или к
окну), а страница внутри фрейма перед каждым замером возвращается на ноль.

Чего дерево лишает, пока оно убрано, то живёт в шапке формы: шаги «предыдущий/следующий блок» по
плоскому порядку страницы (вложенные считаются) и путь по вложенности слева от названия. Кнопка
превью там же — она нужна ровно там, где дерева с его кнопкой на экране нет.

Тяжёлые поля решаются не шириной: у `WxRichText` есть «развернуть» на всю рабочую область, у
галереи в колонке сетка миниатюр, а выбор файлов открывает медиатеку модалкой.

**То, что печатает вью, тоже видно в дереве.** Если у типа есть первый экран из полей записи
(§7), над блоками стоит неперетаскиваемая строка — «Шапка статьи · из полей записи». Клик уводит
на вкладку с этими полями. Удалить её нельзя, она не блок; но без неё редактор видит в
предпросмотре заголовок, которого нет в дереве, и не понимает, где он правится.

### Выбор блока

Диалог по «+ Добавить блок» (`openModal`). В нём — карточки типов: миниатюра, отрисованная на
`sample`, название и описание. Миниатюра здесь не украшение: по названию «Секция» невозможно
отличить полосу во всю ширину от контейнера с колонками, а по картинке — можно.

- **Что показано.** Только `is_enabled` типы с опубликованной версией, разрешённые в этом месте:
  пересечение `allow` родительского узла и `allowed_in` самого типа. Исчерпавший `max_per_entity`
  показан неактивным с причиной, а не спрятан — иначе редактор ищет пропавший блок.
- **Группы** — заголовки разделов в этом списке. Нужны, когда типов становится больше десятка; при
  пяти диалог показывает плоский список без заголовков.
- **Поиск** отменяет группировку и ищет по названию, описанию и `slug` — плоским списком, как
  поиск по дереву страниц.
- **Пусто** — не пустая коробка, а объяснение: «внутрь секции можно класть только текст, галерею и
  колонки» либо «блоков ещё нет» со ссылкой в раздел, если есть право.

Список групп — в конфиге (`webx-blocks.groups`), а не enum и не свободная строка: набор зависит от
сайта, порядок задаётся там же, подписи переводятся словарём, а свободная строка дала бы
«Контент», «контент» и «Контенты». Поле типа называется «Группа» — слово «пикер» до редактора не
доезжает.

### Копировать и вставить

Блок со всем, что внутри, или весь список страницы переносится на другую страницу — и в другой
модуль: страницы, статьи, услуги и зоны макета хранят одно и то же дерево `{ key, type, values }`.

- **Буфер** — `localStorage`, ключ `wx-blocks-clipboard`, конверт
  `{ format: 'webx-blocks-clip', format_version: 1, copied_at, nodes }` (`clipboard.ts`). Один на
  домен; другие вкладки видят копию по событию `storage`. После вставки не очищается — один блок
  кладут на несколько страниц. Конверт другой версии или битый — то же, что пустой буфер.
- **Копировать** — строка в `···` блока; **«Копировать все блоки»** — `···` в шапке списка.
- **Вставить** — только пока в буфере что-то есть, и строка называет что: «Вставить после:
  Обложка» в `···` блока, «Вставить внутрь» на контейнере (по строке на каждое его поле — иначе в
  пустой контейнер не попасть), «Вставить» в шапке — в конец страницы.
- **Ключи** — новые на всю глубину, как у «Дублировать».
- **Что не встаёт** — по тем же правилам, что выбор блока: тип не предлагается на этом сайте
  (или такой тип внутри блока — блок не вставляется целиком), `allowed_in` / `allow` поля,
  `max` списка, `max_per_entity`. Встаёт то, что можно; остальное перечислено в тосте с причиной.
- **Сервер не участвует**: вставка — правка дерева в памяти, сохраняется формой владельца и
  проверяется `ContentValues`, как любая другая.
- **Другие сайты — нет**: `localStorage` живёт в своём домене, а пути медиа и id ссылок у другого
  сайта свои. Перенос между сайтами — отдельная задача, `format_version` оставлен под неё.

## 15. Проверки

**При сохранении** (предупреждения, не запреты):

- селекторы CSS, не начинающиеся с префикса блока (`.b-{slug}`);
- голые элементные селекторы (`h2`, `a`, `img`) — они задевают весь сайт;
- `@media` вместо `@container` — у блока ширину решает контейнер, а не окно;
- отсутствие `data-wx-block` на корне;
- на сайте с темой — CSS знает только токены (§8 спеки тем): буквальный цвет и шрифт,
  `var(--site-…)` вне словаря цепочки, запасное значение в нём (`Lints::tokens()`, в редакторе —
  `tokenLints()` по `tokens` из ответа типа). Тип из слоя темы при sync — запрет (TH2.2).

**Перед публикацией версии** (запрет):

- `data-wx-block` на корне, если есть, — ровно slug (`Lints::marker()`): рантайм и панель
  сравнивают точно, и «Quote» у типа `quote` — блок, чей скрипт не запускается;
- шаблон компилируется;
- блок рисуется на `sample` и на значениях со всех страниц, где он уже стоит;
- переменные шаблона существуют в схеме.

Не прошло — публикации нет, ошибка показана под редактором с номером строки. Иначе одна опечатка
агента кладёт все страницы, где стоит блок.

**Значения в содержимом** (запрет). Каждое значение блока проверяется `rules()` своего
типа поля — теми же правилами, что экран настроек, — на каждой двери: `blocks_set_content`,
`blocks_edit_content`, сохранение и автосохранение панели, сохранение зоны и публикация (на случай
черновика, записанного до проверок; событие модели `publishing` из `HasDraft`). Плюс место блока:
`props.allow`/`props.max` поля-контейнера (без своего `allow` — `allow` типа, без обоих — любой тип),
`allowed_in` и `max_per_entity` типа. При публикации сущности или зоны ещё и блок типа, которого
нет ни под каким slug (`ContentValues::publishProblems()`): сайт молча выбросил бы его. Ошибка адресуется `blocks.<key>.<field>`; панель открывает
блок и пишет под полем, агент получает «тип [key], field [поле]: …». Ссылка вне `http(s)`, `mailto`,
`tel`, относительного пути и якоря не печатается и на чтении. Ключ библиотеки, которого в ней нет,
отбивается только у нового значения (`ChecksNewValues`): удалённая картинка на старой странице
сохранению не мешает. Одно место — `ContentValues`.

**Смена `localized`** у поля, которое уже стоит на страницах. Чтение не верит флагу, а смотрит на
форму значения (`Locales::isMap()`: список — никогда не карта языков). При публикации версии,
которая меняет флаг, значения на страницах, в черновиках и зонах переводятся в новую форму
(`LanguageShapes`): простое значение — в основной язык, карта — в основной язык; если в других
языках есть текст, публикация спрашивает (`DropsTranslations`, 409 в панели, `drop_translations`
у агента). Сохранение черновика заранее говорит, сколько страниц затронет.

**Переименование типа** (`Renamer`) переписывает `type` во всём содержимом (живое, черновики,
зоны), `allow`/`allowed_in` других типов и свои `data-wx-block` и `.b-{slug}` — новой версией,
опубликованной сразу, если старая была на сайте. Отказ, пока другой шаблон вызывает тип тегом или
модуль объявил этот slug. История сущностей не переписывается — вместо этого тип помнит прежние
slug'и (`blocks.former_slugs`), и восстановление старой версии страницы, услуги или зоны
(`restoreVersion()` → `HasBlocks::restoredPayload()`) ведёт их к нынешнему. Контент, присланный
вместе с новым slug (форма редактора, `content` рядом с `rename_to`), переносится на новый slug
(`Renamer::carry()`), а не пишется черновиком со старым маркером.

## 16. Безопасность

- Раздел требует отдельного права (`blocks.manage`), которое по умолчанию есть только у
  супер-администратора. Правка блока — это выполнение произвольного PHP.
- `webx-blocks.editing` в конфиге выключает редактирование целиком: на проде типы приезжают
  импортом, а раздел работает на чтение.
- В README — первой строкой: доступ к разделу равен доступу к деплою.
- История версий с автором и источником (§3) — журнал аудита, и это вторая причина, по которой
  версия пишется на каждое сохранение.

## 17. Экспорт и импорт

`webx:blocks:export [slug…] --path=` пишет по файлу на тип: `{slug}.json` с манифестом, шаблоном,
стилями, скриптом и образцом. `webx:blocks:import [slug…] [--path=|--theme] [--replace=<slug>…]
[--publish] [--dry-run]` читает их обратно — из каталога или из слоёв темы.

Это ответ на единственную настоящую цену хранения в базе: блок не едет через git. Проект держит
выгрузку в `theme/blocks/` или `resources/blocks/*.json` как предмет ревью, а перенос с dev на
боевой — две команды, вторую запускает человек. Деплой (`webx:boot`) файлов не импортирует.

**Тип, который на сайте уже есть, — сайта** (`WEBX_UI_BLOCK_SCHEMAS.md` §1, §4). Импорт создаёт
новые типы; совпадающий с файлом — `unchanged`; отличающийся — `differs`: не пишется, а
печатается расхождение (`Panel\TypeDiff`: поля `+ − ~` по ключу, строки шаблона, стилей, скрипта и
образца, поля строки). Сравнение — с версией, которую правят: открытый черновик, иначе
опубликованная. Перезапись — только `--replace=<slug>`, по одному названному типу: новая версия
(`source = import`, «Replaced from …»), прежняя остаётся в истории. `--replace=*`, `all` и slug не
из источника — отказ без записи (`Panel\ReplaceRefused`). `--publish` публикует созданное и
заменённое.

### 17.1. Из панели

Те же документы, но руками и без shell: основа будущего каталога готовых блоков, которые
импортируют на сайт и стилизуют под него.

- **Пакет.** Один файл на выгрузку: `{ "format": "webx-blocks", "format_version": 1,
"exported_at", "blocks": [документ, …] }`, документ — ровно файл команды. Порядок — граф вызовов,
  вызываемое первым (`Graph::order`). Читается пакет, голый список документов и одиночный файл
  команды (`Exchange::read`); команда читает пакеты тоже.
- **Компоненты едут с блоком.** `Exchange::pack()` добирает по `Calls::of` всё, что вызывают
  выбранные типы, транзитивно: блок без своих компонентов на другом сайте ничего не нарисует. Не
  опубликованное без флага черновиков — в `skipped`, вызванное, но отсутствующее — в `missing`;
  файл всё равно пишется, панель говорит, чего в нём нет.
- **Импорт — дважды.** `POST /blocks/import` с `dry_run` показывает план по строке на тип
  (`created`/`unchanged`/`differs`/`replaced`/`failed` и причина; у `differs` — `diff`, `from`,
  `draft`), потом тот же файл без него. `Panel\Importer` общий с командой: правила `BlockInput`,
  правило §17 выше, порядок графа; круг между типами — 422 до записи. У строки `differs` в диалоге —
  свёрнутое расхождение и свой переключатель «Replace» (выключен, «выбрать все» нет); запрос несёт
  `replace: [slug, …]`, slug не из файла или `*` — 422 (`errors.replace`). Заменённый тип получает
  новую черновую версию (`source = import`); «Опубликовать» гоняет проверки, не прошедший остаётся
  черновиком, а в плане это репетиция в откатываемой транзакции. Файл панель шлёт текстом и сервер декодирует сам, а
  маршрут выведен из `TrimStrings` и `ConvertEmptyStringsToNull`: иначе шаблон без конечного
  перевода строки читался бы изменённым, и неизменный пакет писал бы версию каждого типа.
- **Права.** Экспорт — `blocks.view`, импорт — как создание типа (`blocks.manage` + `editing`).
  Кнопки — в шапке раздела и (экспорт) в редакторе типа.

Не сделано: медиа из образцов (`sample`) едут ссылками, файлы не переносятся; импорт под другим
идентификатором при совпадении — тоже нет, пока не понадобится каталогу.

### 17.2. Схема изменилась: лишние значения

Значения блока хранятся в дереве узлов `{key, type, values, hidden}` записи (и её черновика) по id
поля и со схемой не мигрируют. Поле, которого схема больше не знает (удалили в панели, по MCP или
заменой через `--replace`), оставляет **лишнее значение** (stray value):

- **Сайт** отдаёт его шаблону как есть, без resolve (`Rendering\Values`). Посетитель его не видит:
  шаблон, читающий переменную не из схемы, не публикуется.
- **Панель** сохраняет его намеренно, без проверок (`ContentValues`): поле, вернувшееся в схему,
  найдёт своё значение. Правка с панели на сайте (site bar) лишнее отклоняет.
- **MCP** (`blocks_set_content`, `blocks_edit_content`) новый ключ или новое значение лишнего поля
  отклоняет («<type> has no field [x]», `StrayValues::unknown()`); хранящееся можно оставить тем же
  или убрать (`unset`).
- **Чистка** — `webx:blocks:prune [--dry-run]` и исправление аудита `blocks.prune-stray`: удаляют
  лишнее из записи и черновика прямым UPDATE, **без версии**, черновик, отличавшийся только лишним,
  сбрасывается. Проверка аудита `blocks.stray_values` только сообщает. После prune вернуть поле со
  значениями уже нельзя — поэтому чистка всегда явная.
- **Смена типа поля** не мигрирует: старое значение читается правилами нового типа, и сохранение
  записи может отказать — тип поля меняют вместе с правкой содержимого. **Переименования поля** нет:
  старое значение становится лишним, новое поле пустое.

Мигрирует только смена `localized` (`Panel\LanguageShapes`).

## 18. MCP

Инструменты (`webx-ui/mcp`, изменяющие — с принудительным `dry_run`, область `blocks:write`).
Реестр сам добавляет к имени префикс модуля, поэтому имена короткие — `list`, а не `list_blocks`:
агент видит `blocks_list`, и `blocks_list_blocks` было бы масло масляное.

| Инструмент                                  | Что делает                                                  |
| ------------------------------------------- | ----------------------------------------------------------- |
| `blocks_list`, `blocks_get`                 | каталог типов и содержимое одного                           |
| `blocks_create`, `blocks_update`            | завести и править тип                                       |
| `blocks_publish`                            | опубликовать версию (прогоняет проверки §15)                |
| `blocks_render`                             | отрисовать тип на присланных значениях → HTML               |
| `blocks_get_content`, `blocks_set_content`  | содержимое сущности                                         |
| `blocks_edit_content`                       | точечная правка по ключам (§18.1)                           |
| `blocks_preview_url`                        | подписанная ссылка на черновик                              |
| `blocks_delete`                             | удалить тип (те же отказы, что у панели)                    |
| `blocks_versions`, `blocks_version_restore` | история типа и откат в черновик                             |
| `blocks_usage`                              | где стоит тип и кто его вызывает                            |
| `blocks_region_*`                           | зоны: publish, unpublish, discard, versions, restore, adopt |

Всё, что панель делает с блоками, есть и у агента —
удаление, история, место, переименование (`blocks_update` с `rename_to`), черновик и история
зон, «Дублировать» (`duplicate` в `blocks_edit_content`); история страниц и услуг —
`pages_versions`/`pages_version_restore`, `services_versions`/`services_version_restore`.

`render` и `preview_url` — не украшение, а замыкание петли: без них агент пишет шаблон, не
видя результата, и мы получаем ровно ту вёрстку, которую он вообразил.

Ресурсы и подсказки: домашние правила вёрстки (токены `--wx-*`, БЭМ с префиксом блока, контейнерные
запросы, картинки через `module-media`, что доступно в шаблоне и что запрещено), словарь узлов
экрана для схемы, каталог существующих блоков с образцами — чтобы агент переиспользовал, а не плодил
пятый герой-блок, — и список того, что сайт объявил через `webx.provide()`.

Транспорт, маршрут, токены и области — общие для всех модулей, живут в `webx-ui/mcp`
(`WebxServer` поверх `laravel/mcp`); отказ, который агент должен прочитать, бросает `ToolFailure`.

### 18.1. Точечная правка содержимого

Пара «прочитать дерево — записать дерево» меняет один заголовок ценой всей страницы в обе стороны,
а правку, которую за это время сделал редактор, теряет молча. Поэтому рядом стоит
`blocks_edit_content` — операции по ключам, тем же словарём, что у патчей экранов (§5 спецификации
экранов): `set`, `add`, `move`, `remove`. Второго словаря для того же понятия в системе нет.

- **`set` мержит по полям, заменяет по значению.** Поле, которого нет в операции, остаётся как
  было; поле, которое есть, берёт новое значение целиком. Глубже поля лезть нельзя — что значит
  значение, знает только тип поля.
- **`locale` пишет один язык** переводимого поля. Без него строка в переводимое поле — не правка,
  а потеря всех остальных языков, и `BlockType::localizedFields()` позволяет сказать об этом
  прямо, а не после. Обратное тоже отказ: `locale` для обычного поля.
- **Операции списком** — связная правка (добавил, переставил, убрал старый) применяется одним
  вызовом и с одной проверкой.
- **`revision`** — короткий хеш дерева, который отдаёт `blocks_get_content`. Прислал — правка
  отбивается, если содержимое с тех пор изменилось; не прислал — пишется поверх. У черновика
  своего номера нет (автосейвы — кольцо, номера у них нет), поэтому «страница, какой я её прочитал»
  — это само содержимое. `blocks_set_content` принимает `revision` тем же образом.
- **Читать тоже дёшево:** `blocks_get_content` с `outline: true` отдаёт карту (`key`, `type`,
  вложенность, строка текста), с `key` — один узел целиком.

Дерево правит `WebxUi\Blocks\ContentEdit` — чистые функции над деревом, ничего не сохраняющие;
инструменты только переводят в них аргументы и потом прогоняют результат через ту же нормализацию
ключей, что и `set_content`. Панель, когда ей понадобится то же самое, ходит туда же.

## 19. API панели

```
GET    /blocks                    список типов
POST   /blocks                    новый тип (сразу черновая версия 1)
GET    /blocks/{id}               тип с черновой и опубликованной версией
PUT    /blocks/{id}               сохранить черновик (пишет версию)
POST   /blocks/{id}/publish       опубликовать версию
POST   /blocks/{id}/render        отрисовать на присланных значениях
GET    /blocks/{id}/usage         где стоит
GET    /blocks/{id}/versions      история
POST   /blocks/{id}/versions/{n}/restore
```

Ошибки проверок — 422 в форме, которую панель уже понимает, с указанием файла и строки.

## 20. Выпуск

Выпущено и стоит на обоих демо; потом приехали видимость блока (§23), компоненты (§24) и зоны
шапки и подвала ([`WEBX_UI_LAYOUT_REGIONS.md`](WEBX_UI_LAYOUT_REGIONS.md)). Решения реализации, на
которых модуль держится:

- **Переменные шаблона — поля схемы, а не ключи значений:** на каждый `id` — переменная (значение
  или `null`). Поле, добавленное позже, старые страницы не роняет; незаявленная переменная падает
  на образце при публикации. `$entity` бывает `null` — писать `$entity?->title`.
- **Скомпилированный шаблон — `{slug}-{version}-{sha1[:12]}.php`:** новая версия — новый файл,
  инвалидации нет. Строка ошибки пересчитывается с компилированного файла на шаблон.
- **`@webxBlocks` — ленивый `echo`, не `@stack`** (`'styles'`, `'scripts'`, `'runtime'`); рантайм
  идемпотентен и отдаётся отдельно (`/blocks/runtime.js?v=…`); набор без стилей и скриптов не
  пишется. Напечатанное и режим предпросмотра сбрасываются на `RequestHandled`.
- **Значения резолвятся до `BlockContext`** (§7). Схема перед резолвом нормализуется `id` → `name`;
  в `children` обход спускается только у незарегистрированных (layout) типов. `MediaFieldType`
  помнит на ответ строку файла, а не адрес — подписанная ссылка живёт час.
- **Каркас:** `draft()` — макрос `module-admin`; detached-узел — границы 0/0 и `parent_id = null`;
  указатели версий без FK; публикация сносит автосейвы; `withDraft()` — копия, которая никогда не
  сохраняется.
- **Одна дверь на три входа:** `Panel\BlockInput` (панель, MCP, импорт); `Publisher::check()` (он
  же `dry_run`) гоняет черновик на образце и на значениях всех экземпляров из
  `webx-blocks.entities`, живых и черновых. Одинаковое содержимое версию не пишет.
- **`POST /render` с `content` компилирует присланный Blade** — поэтому `blocks.manage` плюс
  `editing`. Каталог конструктора отдаёт и выключенные типы, схему — черновую.
- **Настройки типа — форма компонента, а не описанный экран;** `allowed_in` понимает `root`.
  Предпросмотр сущности отдаёт хозяин экрана (`provideBlocksPreview()`).
- **`set_content` агента пишет черновик;** модель без `HasDraft` — единственный случай, когда агент
  меняет живой сайт. Экспорт — опубликованная версия (`--draft` — редактируемая), импорт кладёт
  черновик.

## 21. Что потом

На блоках стоят `module-pages` ([`WEBX_UI_MODULE_PAGES.md`](WEBX_UI_MODULE_PAGES.md)), `module-blog`,
услуги, зоны лейаута и модули с предложенными типами (`BlockOffers`). Открытое — §22.

## 22. Открыто и отложено

- **Перенос блока между контейнерами** — не перетаскивание, а «дублировать» плюс «убрать»: у
  `WxSortableList` нет судьи по `allow`.
- **Переводимость содержимого.** Скорее всего `blocks` и `draft` переводимы целиком (структура у
  каждого языка своя: вёрстка на языках расходится, «синхронизировать структуру» — источник вечных
  багов). Решить, когда вторая локаль понадобится на живой сущности.
- **Типы блоков из кода** — вторым источником реестра, контракт не меняется.
- **Правка простого текста прямо в превью** (`contenteditable` на узле с `data-field`) — тянет
  каретку, undo и вставку из Word.
- **Шаблоны блоков** — готовые связки из нескольких блоков.
- **Сравнение двух версий** типа построчно; сейчас — только откат.
- **Ссылка на черновик наружу** с длинным сроком и без права правки (§12).
- **Импорт вёрстки** — готовый HTML агенту и предложенное разбиение на поля: сценарий, ресурсы MCP
  для него есть.
- **Визуальный конструктор полей** — без JSON (добавить, переставить, настроить поле); сейчас
  «Поля» — JSON-редактор схемы с живой формой рядом.

## 23. Видимость блока

Блоку нужен выключатель: блок в содержимом есть, в панели виден и правится, а на сайте не
рисуется. Это **не** черновик страницы (тот про всю страницу и про публикацию целиком), **не**
удаление (после него значений не остаётся) и **не** `is_enabled` у типа блока (тот прячет тип от
редакторов в каталоге, но всё уже расставленное продолжает рисоваться).

### 23.1 Поле в структуре узла

Узел — `{ key, type, values }`, а видимость — четвёртый ключ рядом с ними:

```json
{ "key": "01H…", "type": "hero", "hidden": true, "values": { … } }
```

**Почему в структуре, а не в схеме полей.** Видимость есть у любого типа, в том числе у того,
чья схема давно другая или чей тип вообще снят с публикации. Поле схемы пришлось бы заводить
каждому типу заново, и первый же тип, где его забыли, оказался бы блоком, который нельзя
выключить.

**Почему `hidden`, а не `visible`.** Флага нет — блок виден: всё старое содержимое правильно без
миграции, а ключ появляется только там, где его осознанно выставили.

**Кто ещё должен знать про этот ключ.** `BlockTools::normalise()` — путь записи агента — узлы не
сливает, а собирает заново, чтобы в содержимое нельзя было протащить чужие ключи. Значит каждый
структурный ключ там называется поимённо, иначе флаг молча пропадает. Следующий структурный ключ
добавлять и туда.

### 23.2 Пропуск на публичной половине

Один `if` в `Renderer::list()` — там, где уже стоит проверка формы узла. Этого хватает на всё,
потому что рендер один (§2): `@blocks` на живой странице, вложенные списки, предпросмотр (скрытый
блок в нём **не показывается** — иначе непонятно, что выключено) и набор стилей: пропуск стоит до
`one()`, тип скрытого блока не попадает в `used[]`.

**Вложенность получается сама.** До детей выключенного контейнера рекурсия не доходит, и их
собственные `hidden` остаются нетронутыми: включили контейнер — внутри всё как было.

### 23.3 Как выглядит в панели

В дереве блоков (§14) у скрытой строки приглушено название и стоит `eye-off`. Переключатель —
первым в ряду действий строки (`eye` / `eye-off`), без вопроса: действие обратимо и видно сразу.
Дублирование копирует флаг: копия скрытого блока скрыта, иначе дубль молча уезжает на сайт. Форма
скрытого блока работает как обычно.

### 23.4 Черновики, версии и ревизия

Флаг — часть дерева: едет через `saveDraft`, `publish`, откат версии и входит в
`Content::revision()`. Пока страница не опубликована, выключение живёт в черновике, а на сайте
блок рисуется — публикация одна на всю страницу.

### 23.5 Агент

`blocks_edit_content` (§18.1) знает операции `hide` и `show` по ключу
(`{ "ops": [{ "op": "hide", "key": "01H…" }] }`); `outline` показывает `hidden: true` — агенту иначе
неоткуда узнать, что блок на сайте не рисуется.

## 24. Компоненты

**Компонент** — тип блока, который вызывают тегом из любого шаблона: другого блока, вьюхи модуля,
лейаута сайта.

```blade
<x-webx-block type="recipe-card" :card="$card" fallback="webx-recipes::partials.card" />
```

Нужен для кусков вёрстки, которые повторяются **внутри** других шаблонов (карточка рецепта в
каталоге, категории, «похожих» и на жёсткой странице сайта) и которые правят из панели и
агентом, а не кодом. Инфраструктура та же, что у блоков: Blade, CSS и JS в базе, версии,
черновик, предпросмотр, проверки, экспорт, MCP — нового хранилища и второго рендера нет. Это не
второй механизм вложенности содержимого (§2): `wx-blocks` — то, что редактор кладёт мышью,
компонент — то, что зовёт шаблон.

Код ссылается на «§N of the components spec» — это подразделы 24.N ниже (§3.4 → 24.3.4,
§5.1 → 24.5).

### 24.2. Решения (не переоткрывать)

1. **Тег, а не директива.** `<x-webx-block>` — Blade-компонент с классом (`Tags\BlockTag`).
   Шаблоны блоков компилируются `Blade::compileString()`, а тот разбирает `<x-…>` так же, как
   файлы, — один тег работает в шаблоне из панели, во вьюхе модуля и в лейауте. Тег даёт слоты, а
   синтаксис знают и верстальщик, и агент.
2. **Тегом вызывается любой тип, `kind` решает только, где тип виден.** `block` стоит в выборе
   «добавить блок», схема — форма редактора; `component` в выборе нет, схема описывает входные
   данные. Обычный блок с зашитыми значениями на жёсткой странице — законный случай.
3. **Компоненты заводят и модули, и сайт.** Модуль объявляет точку с запасной вьюхой (24.4),
   сайт заводит свои в панели или через MCP.
4. **Родитель берёт опубликованную версию ребёнка, не закреплённую** — «поменял карточку,
   поменялась везде». Защита от поломки — проверка родителей при публикации ребёнка (24.3.6).
5. **Запасная вьюха — у места вызова, а не у типа.** `fallback` печатается, когда компонента нет
   или у него нет опубликованной версии: модуль работает из коробки, а «сбросить к стандартному»
   — удалить свой компонент. Без `fallback` отсутствующий компонент — пусто на сайте, строка в
   логе и плашка в предпросмотре.
6. **Модуль не кладёт компонент в базу сам.** Объявленная точка — запись в реестре кода, а не
   документ `BlockOffers`: пока сайт её не настроил, работает partial модуля, и одна вёрстка не
   живёт в двух местах. «Настроить» копирует исходник partial в черновик нового типа (24.4.2).
7. **Граф вызовов виден только в шаблонах из базы.** Вызов из файловой вьюхи графу не виден и
   проверками не покрыт; модуль компенсирует это объявлением точки с образцом, сайт — `fallback`.

### 24.3. `module-blocks`

#### 24.3.1. Вид и граф в базе

- **`blocks.kind`** — `block` | `component`, по умолчанию `block`. На типе, а не на версии: вид —
  это то, где тип показывается. `block` → `component` — отказ (422), пока тип стоит в чьём-то
  содержимом: его никто не смог бы добавить; `component` → `block` — всегда.
- **`block_versions.uses`** — слаги типов, которые шаблон версии вызывает тегом, отсортированные,
  без повторов; пишется при каждом сохранении версии. На версии, а не на типе: у черновика и
  опубликованной версии графы разные. `json` nullable без дефолта (MySQL до 8.0.13), `null`
  читается как `[]`.

#### 24.3.2. Тег

- **Зарезервированы `type` и `fallback`.** Остальное — значения под своими именами:
  `:cta_label="…"` становится `$cta_label`; имя через дефис читается `$block->value('cta-label')`.
  Значения проходят `Values::resolve()`, как сохранённые (`wx-data` — как есть).
- **Тип ищется как в содержимом:** опубликованный, в предпросмотре — черновой. Правка черновика
  компонента видна в предпросмотре любой страницы под токеном, живой сайт её не видит.
- **`fallback` — имя вьюхи;** в неё уходят те же значения и слоты (но не переменные вызывающей
  вьюхи, в отличие от `@include`). Нет и вьюхи — исключение.
- `is_enabled = false` у компонента значит то же, что у блока: продолжает рисоваться.
  «Сбросить к стандартному» — удалить.
- **Не `<x-dynamic-component>`:** у того статический кеш компилятора на процесс — у нас имя тега
  постоянное, тип — атрибут. `BlockTag` раскодирует строковые атрибуты один раз и переопределяет
  `resolveView()` — иначе `&amp;` и повторная компиляция разметки как Blade.

**24.3.3. Входные данные.** Схема компонента — те же узлы, что у блока: из неё строится форма
образца, её поля — переменные шаблона, переменная не из схемы отбивает публикацию (§15). Любой тип
поля годится, и ещё два узла:

```json
{ "type": "wx-data", "id": "card", "label": "Recipe card", "props": { "shape": "recipes.card" } }
{ "type": "wx-slot", "id": "aside", "label": "Aside" }
```

- **`wx-data`** — структура, которую не редактируют в панели, а передают из кода. `props.shape` —
  имя формы данных из реестра `BlockShapes` (24.3.7): описание полей для справки и агента и
  образец. Без `shape` — свободный JSON. Тип поля без `store()`/`resolve()`.
- **`wx-slot`** — объявленный слот: переменная есть всегда, пустой `HtmlString`, если не передан.
  `$slot` объявлять не надо — он есть у любого вызова, пустой, если тег самозакрывающийся.
- `allow`, `allowed_in`, `max_per_entity`, `group` у компонента не спрашиваются.

**24.3.4. Рендер.** `Renderer` держит стек контекстов (`BlockContext`), отсюда тег знает, откуда его
позвали:

- **сущность** — `$entity` вершины стека (вызов из вьюхи вне блоков — `null`);
- **глубина** — вершина + 1, тот же предел `webx-blocks.max_depth`;
- **цикл** — слаг уже в стеке → `problem()`, ничего не рисуется (страховка рантайма; нормальный
  путь ловит цикл при публикации);
- **ключ** — `{ключ родителя}/{slug}-{номер вызова}`; маркеры предпросмотра вокруг вызванного
  **не** печатаются: вызов — часть шаблона родителя и заменяется вместе с ним;
- **падение** — в своём `try`/`catch`: компонент, упавший на одной карточке, оставляет пустое место
  в сетке, а не пустую страницу;
- **стили и скрипт** — тип попадает в `used[]`, значит в набор; вьюха, которая зовёт компонент,
  должна стоять на лейауте с `@webxBlocks`;
- **слоты** — `HtmlString` рядом со значениями.

Вход — `Renderer::tag()`; `Renderer::check()` принимает подмены «слаг → черновой тип» для
проверки родителей, и упавший там вызов — провал, а не пустое место.

#### 24.3.5. Граф вызовов

- **Разбор** — `Rendering\Calls::of()`: теги `<x-webx-block` с литеральным `type`. `:type="$x"` —
  динамический вызов, в граф не попадает, линт предупреждает.
- **`used_by`** — типы, у которых **опубликованная** версия содержит слаг в `uses`; черновики
  родителей никого ещё не ломают. Считается в PHP (`Panel\Graph`).
- **Циклы** — при публикации: обход от публикуемого черновика по `uses` и дальше по опубликованным
  версиям; встретил себя — отказ «recipe-card → badge → recipe-card».

**24.3.6. Проверки и запреты.** Перед публикацией типа, у которого есть `used_by`, сверх §15:

1. **Родители на своих данных** — транзитивно: образец каждого родителя и его значения со всех
   страниц рендерятся с публикуемым черновиком вместо опубликованной версии ребёнка. Упало —
   отказ, который называет родителя и страницу, с номером строки в шаблоне ребёнка.
2. **Объявленная точка на своём образце**, если слаг объявлен модулем: вызовы из файловой вьюхи
   графу не видны, и это их единственная проверка.
3. **Цикл** (24.3.5).

Отказы несут `parent`, `declared`, `cycle`, фраза — `PublishFailed::describe()`. **Удалить тип,
который кто-то вызывает, нельзя** — 422 со списком родителей; объявленная точка родителем не
считается (у неё `fallback`). Переименовать такой тип тоже нельзя (§15). Вызовы из сайтовых вьюх
не видны никому — об этом справка под редактором и гайд: «ставьте `fallback` или не удаляйте то,
что зовёт код».

**24.3.7. Реестры модуля.** `BlockShapes::register('recipes.card', fields: […], sample: fn (): array
=> …)` — формы данных для `wx-data`; `BlockComponents::declare(…)` — объявленные точки (24.4). Оба —
синглтоны, регистрация из провайдера модуля (не из маршрутов — `route:cache`). `sample` — замыкание:
модулю нужен настоящий рецепт, и зовётся оно только тогда, когда образец нужен. Названия объявленных
точек — ключи перевода (`declare()` зовётся на boot, языка ещё нет), переводит
`BlockComponents::words()` при чтении.

**24.3.8. Линты шаблона (предупреждения).** Тег с `type`, которого нет; динамический `:type` («not
tracked»). Вызов обычного блока — не предупреждение (решение 2).

#### 24.3.9. Панель

- Создание типа — выбор «Блок» / «Компонент». Экран «Блоки» — две группы; у компонента вместо «на
  3 страницах» — «в 2 блоках» и имя модуля у объявленного. **Объявленные, но не настроенные
  точки** стоят там же карточкой «Стандартный вид» с кнопкой «Настроить» — иначе о возможности
  никто не узнает.
- Редактор компонента — тот же экран без `allow`, `allowed_in`, `max_per_entity`, группы и
  «Предлагается редакторам»; «Поля» — «Входные данные», `wx-data` в форме образца — JSON-редактор,
  `wx-slot` — поле HTML. Под шаблоном — готовый тег вызова и поля формы `wx-data`.
- «Где используется» — плюс родители-типы и «вьюхи модуля». `BlockPicker` и `BlockTypes::all()`
  компонентов не отдают. Автодополнение — `<x-webx-block type="` предлагает типы (компоненты
  первыми), потом атрибуты по схеме и слоты.

**24.3.10. API.** `GET /blocks` — у каждого `kind`, `uses`, `used_by` (`{ id, slug, title }`), рядом
`declared: [{ slug, module, title, description, fallback, customised }]`; `GET /blocks/{id}` — ещё
`declared` и `shape` (описание форм `wx-data`); `POST`/`PUT` принимают `kind`; `POST
/blocks/components/{slug}/customise` → 201; `GET /blocks/catalog` — только `kind = block`. Число
страниц, где компонент виден через родителей, не считается: дорого и почти ничего не говорит.

**24.3.11. MCP.** `blocks_list` — `kind`, `used_by`, `declared`; `blocks_get` — ещё `uses` и формы
`wx-data`; `blocks_create` с объявленным слагом без `template` — то же, что «Настроить»;
`blocks_publish` называет родителя и страницу; `blocks_render` рисует компонент на его входных
данных. Ресурс домашних правил — когда заводить компонент, что `type` — литерал, что правка задевает
всех родителей и сначала смотрят `used_by`.

**24.3.12. Экспорт и импорт.** `kind` едет в документе (нет ключа — `block`). Импорт публикует в
порядке графа — вызываемое первым, иначе проверка родителя упадёт на отсутствующем ребёнке; цикл в
наборе — отказ до записи.

### 24.4. Объявленные точки

#### 24.4.1. Объявление и вызов из модуля

`BlockComponents::declare(slug, module, fallback, title, description, schema)` — из `boot()`
провайдера модуля. `module-blocks` у модуля необязателен, поэтому объявление — за `class_exists`,
а вьюхи модуля зовут точку директивой `@webxPart('recipe-card', ['card' => $card], 'webx-recipes::partials.card')`:
с блоками — тег, без них — `@include` запасной вьюхи. `@webxPart` и `@webxPartAssets` живут в
`module-admin` (`Support\Parts`), а не в `module-blocks`: директива необязательного пакета на сайте
без него печаталась бы текстом. Шаблоны блоков и сайты пишут тег.

Страница модуля сначала рисует тело, потом голову: слот `head` у `<x-dynamic-component>` считается
раньше тела, поэтому вьюха собирает тело в буфер, а в голове печатает `@webxPartAssets`.

**24.4.2. «Настроить».** `POST /blocks/components/{slug}/customise` (и `blocks_create`) — один
`Panel\Customiser`: слаг занят — 409 с `id`; иначе тип `kind = component` с названием и схемой из
объявления и черновой версией 1, где `template` — исходник запасной вьюхи (опубликованной сайтом в
`vendor/`, если есть), `sample` — образец формы. **Не публикуется:** до публикации на сайте работает
partial. Стили стандартного вида не копируются — они продолжают действовать на те же классы.

### 24.5. Первый потребитель — карточка рецепта

`module-recipes` объявляет `recipe-card` (класс `Rendering\RecipeCard`: слаг, форма, fallback,
`sample()` — первый опубликованный рецепт или фикстура) и зовёт её из каталога и «похожих». Карточка
сохраняет `categories` списком id (контракт `wx-collection`, им пользуется фильтр блока) и получает
рядом `category_links` и `service_links` — `[{ id, title, url }]` видимых категорий и услуг в
порядке выбора; услуги — одним запросом на весь список, а не на карточку. Страница рецепта
жёсткой структуры на сайте зовёт тег сама — сайтовый вызов, графу не виден (решение 7).

### 24.6. Отвергнуто и открыто

Отвергнуты: Blade-компоненты в коде сайта (не правятся из панели и агентом); директива
`@block(…)` (без слотов, свой синтаксис); `<x-dynamic-component>` поверх шаблонов из базы (мимо
наборов и изоляции падений); компонент документом `BlockOffers` (вёрстка в двух местах);
закрепление версии ребёнка (решение 4); **переопределение любой вьюхи пакета из базы** — у вьюх
нет договора данных и образца, а переименование в пакете молча ломает переопределения, тогда как
объявленная точка — публичный API модуля.

**Открыто:** точки для услуг, отзывов и FAQ (по строке объявления и `@webxPart`); `parent` /
`declared` / `cycle` панель отдельно не рисует — только фразу под шаблоном; нет теста на
заполнение `uses` миграцией. Одинаковое **содержимое** на многих страницах — не компонент, а общий
блок ([`WEBX_UI_BLOCK_FRAGMENTS.md`](WEBX_UI_BLOCK_FRAGMENTS.md)).
