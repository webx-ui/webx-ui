# Права доступа панели — спецификация

Задача webx-ui#17: любой экран, маршрут API, инструмент MCP и команда панели проверяют право; админ
с нужными правами создаёт роль, отмечает права галочками и назначает её другим админам; токен
агента не шире своего владельца. Этот документ — результат первого этапа: аудит того, что есть
(§3, §14), единая модель (§4–§11), карта прав всех модулей (§5), готовые роли (§12), план миграции
(§13) и развилки (§16).

Статус: этапы 1–3 из 5. Этап 1 — аудит и спека, закрыты две явные дыры (§14.1, пункты 1 и 6).
Этап 2 — политика и проверки на сервере (§17): одна политика, правила §6.2, история доступа,
обязательный тест в каждом пакете. Этап 3 — экран «Роли», назначение, меню и экраны по правам,
готовые роли (§18). Дальше — токены и профиль, гайдлайны.

Соседние спеки: MCP, согласие, ключи и журнал вызовов —
[`WEBX_UI_MCP_ACCESS.md`](WEBX_UI_MCP_ACCESS.md) (§6 там — правило «скоуп плюс право»); экраны и
узлы `can` — [`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md); журнал изменений —
[`WEBX_UI_HISTORY.md`](WEBX_UI_HISTORY.md); панель на сайте —
[`WEBX_UI_SITE_BAR.md`](WEBX_UI_SITE_BAR.md); медиатека —
[`WEBX_UI_MODULE_MEDIA.md`](WEBX_UI_MODULE_MEDIA.md); заявки —
[`WEBX_UI_MODULE_INBOX.md`](WEBX_UI_MODULE_INBOX.md).

## 1. Границы

**Делаем:** права администраторов панели — тех, кто входит в `/cms`. Роли, назначение, проверка на
сервере (маршруты, MCP, команды, файлы), скрытие в интерфейсе, защита от повышения прав, свой
профиль, токены MCP, история изменений доступа.

**Не делаем:**

- **Ограничения по записям** («только свои статьи», «заявки только своей формы», «только эта
  папка медиатеки»). Политика оставляет для них место (§10), но не реализует.
- **Права по языкам** («правит только немецкую версию»).
- **Посетители и покупатели сайта.** Это будущий модуль `module-users` (регистрация, вход, соцсети,
  кабинет) со своей сущностью. Граница — §2.

## 2. Администратор и посетитель — разные сущности

| Что               | Администратор панели                                 | Пользователь сайта (будущий `module-users`) |
| ----------------- | ---------------------------------------------------- | ------------------------------------------- |
| Модель и таблица  | `WebxUi\Auth\Models\CmsUser`, `cms_users`            | своя модель, `users` (имя оставлено ему)    |
| Гард              | `cms` (сессия панели), `api` (Passport, для MCP)     | свой гард сайта (`web` или `site`)          |
| Роли и права      | `cms_roles`, `cms_role_user`, права `<module>.<act>` | свои, если понадобятся; с панелью не общие  |
| Доступ в панель   | да, по правам                                        | **никогда**                                 |
| Токены MCP, ключи | да                                                   | нет                                         |
| Id модуля         | `admins` (раздел «Администраторы»)                   | `users`                                     |

Правила границы:

1. `module-users` не реализует `WebxUi\Admin\Contracts\HasPermissions`. `cms.auth` пускает только
   `CmsUser` (`module-auth/src/Http/Middleware/Authenticate.php`), `EnsurePermission` отвечает 401
   любому другому классу — так и остаётся.
2. Один человек может быть и тем и другим, но это **две учётки** с разными паролями: связывать их
   по адресу почты нельзя, вход в одну не открывает другую.
3. Право панели не может ссылаться на посетителя («видеть заказы клиента» — право модуля заказов
   над его записями, а не роль посетителя).
4. Переименование `users.* → admins.*` уже сделано
   (`module-auth/database/migrations/2026_01_01_000005_rename_users_permissions_to_admins.php`).

## 3. Как устроено сейчас (аудит механизма)

### 3.1. Данные

- `cms_users`: `is_super`, `is_active`, `locale`, `theme`, `site_bar`, `avatar`. Колонок 2FA нет.
- `cms_roles`: `slug` (уникальный), `name`, `permissions` (JSON-список строк). `cms_role_user` —
  связка, у админа может быть несколько ролей.
- **Сидера ролей нет.** Роли появляются только руками в базе или из снимка: на большинстве сайтов
  есть суперадмин и ничего больше.

### 3.2. Проверка

- `CmsUser::hasPermission($p)`: суперадмин — всегда да; иначе да, если хоть одна роль содержит
  `$p` **точным совпадением** (`Role::grants`, `in_array(..., true)`). Права ролей складываются.
  Подстановок (`blog.*`) и следствий (`manage ⇒ view`) нет.
- `CmsUser::permissions()` — объединение прав ролей; у суперадмина `[]` (фронт смотрит `isSuper`).
- Маршрут: `->middleware('cms.can:a,b')` — любое из перечисленных (`EnsurePermission`), 403 с
  `required`. Группа `webx.panel` = `web, webx.panel-locale, cms.auth, webx.history`.
- Общие механизмы `module-admin` принимают право от модуля, который в них регистрируется:
  категории (`CategoryRoutes`, `CategoryKind{view, manage}`), ссылки (`LinkSource::permission()`),
  подборки (`CollectionSource::permission()`), связи (`RelationTarget`), история
  (`HistoryType::permissions`), заметки (`Notable::notesPermission()`), «кто сейчас правит» и
  черновики (`EditedRecords`), загрузки (`UploadPurposes::register(..., permission:)`), панель на
  сайте (`SiteBar::entity(..., new EntityLink(permission:))`), узлы экранов (`can`).
- `GET /auth/me` отдаёт `isSuper`, `roles`, `permissions`. Фронт: `context.can(p)` =
  `isSuper || permissions.includes(p)` (`packages/module-admin/src/admin.ts`).

### 3.3. Что видит интерфейс

- **Меню не фильтруется по правам.** Манифест несёт `permissions` каждого модуля
  (`ManifestBuilder::describe`), но фронт их не читает: каждый админ видит каждый раздел, а внутри
  получает 403. Маршрутизатор проверяет только вход.
- Кнопки записи скрываются `can('<module>.manage')` на страницах модулей — это сделано почти везде.
- `GET screens/{name}` отдаёт любой экран любому вошедшему (узлы с `can` вырезаются).

### 3.4. MCP

Порядок в `RegistryTool::attempt`: скоуп токена → согласие (`read_only`) → право панели →
обработчик. `tools/list` фильтруется теми же проверками. Право по умолчанию:
`<id>:read → <id>.view|<id>.manage`, `<id>:write → <id>.manage`; модуль может назвать своё
(`permission:`). Итог уже сегодня — **скоупы токена ∩ права того, кого токен называет**. Дыра в
том, кого он называет: ключ выпускается на любого админа (§7, §14.1).

### 3.5. Администраторы

- Маршруты `auth/admins*`, `auth/roles`, `auth/keys*` — за `admins.view|admins.manage` (чтение) и
  `admins.manage` (запись). Права `admins.audit` — журнал входов и вызовов MCP.
- `RoleController` — только список. **Экрана и API для ролей нет**: создать или править роль из
  панели нельзя.
- `PATCH auth/admins/{id}` пишет `is_super`, `is_active`, `roles`, `password`, `email` без проверки
  того, кто правит (§14.1).
- MCP `admins_grant_role` / `admins_revoke_role` — за `admins.manage`, без проверок «себе»,
  «больше, чем у тебя», «суперадмину».
- **Ничего из этого не пишется в историю**: `CmsUser` и `Role` без `RecordsHistory`, связка ролей —
  не модель. Есть только `cms_login_records` и `mcp_calls`.

### 3.6. Профиль

`PUT auth/me` принимает `name`, `avatar`, `locale`, `password` + `current_password` (текущий пароль
уже обязателен для смены). Лишние поля (`roles`, `is_super`, `email`) **молча игнорируются** с 200.
Смены почты нет вовсе (поле только для чтения), 2FA нет, списка сессий нет. Свои подключения агентов
(`auth/connections`) видны без прав; свои ключи — только с `admins.manage`.

## 4. Модель

1. **Право** — строка `<module>.<action>`. `<module>` — идентификатор модуля или его семьи
   (`blog.articles`, `events.categories`); `<action>` — `view`, `manage` или особое действие
   (`delete`, `upload`, `reset`, `run`, `regions`, `update`, `publish`, `export`, …). Всё строчными,
   через точку и дефис.
2. **Объявление.** Модуль перечисляет свои права в `Module::permissions()`. Право, которое не
   объявлено ни одним установленным модулем, нельзя положить в роль и нельзя проверять в коде
   (тест модуля, §15). Для матрицы ролей объявление получает подпись и подсказку — словами модуля,
   на языке панели (форма объявления — этап политики; черновик: `Permission::make('pages.manage')
->label(...)->hint(...)->implies('pages.view')`).
3. **Роль** — именованный набор прав. У админа **несколько ролей**, права **складываются**
   (объединение). Отрицательных прав нет.
4. **Суперадмин** (`is_super`) обходит все проверки. Ему не нужны роли, и роли его не ограничивают.
5. **Запрет по умолчанию.** Нет права — нет действия. Маршрут панели без `cms.can` и без проверки в
   контроллере — ошибка, которую ловит тест (§15); исключения перечислены явно (§5.5).
6. **`manage` включает `view`** того же модуля (развилка 1 в §16 — рекомендуемый вариант). Сегодня
   это обеспечивает каждый маршрут списком `view,manage`, но не ссылки, подборки и связи (§14.3).
7. **Одна политика.** Все «можно ли» про права и доступ отвечает один класс в `module-auth`
   (`AccessPolicy`, этап политики): маршруты, MCP, команды и панель на сайте зовут его, а не
   повторяют правила. Скрытие кнопок — удобство, не защита.
8. **Команды Artisan** работают от имени того, кто запустил терминал, то есть с полным доступом:
   у консоли нет администратора. Это и есть «проверка» для команд — доступ к серверу. Команды,
   которые действуют от имени админа (`webx:mcp:token --admin`), подчиняются той же политике в
   части «кому выдаётся» и пишут историю с источником `console`.

## 6. Управление доступом и защита от повышения прав

### 6.1. Права

`admins.view`, `admins.manage`, `roles.manage`, `roles.assign` — отдельные права, не входят в права
модулей и не выдаются «заодно». По умолчанию — только у суперадмина; **в готовых ролях их нет**
(§12). `admins.manage` не включает `roles.assign`: управлять учётками и раздавать права — разные
вещи (кадровик и владелец сайта).

### 6.2. Правила (сервер, одна политика, кроме суперадмина)

| #   | Правило                                                                                      | Где проверять                                                                                              | Сейчас                                                                              |
| --- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 1   | Нельзя менять **свои** роли и права                                                          | `PATCH admins/{self}` (`roles`), MCP `grant_role`/`revoke_role` на себя, `PUT auth/me` (лишние поля → 422) | нет                                                                                 |
| 2   | Нельзя выдать роль или включить в роль право, которого нет у тебя                            | назначение роли (форма, MCP), создание админа с ролями, правка роли, выпуск ключа на другого (§7)          | нет                                                                                 |
| 3   | Создать суперадмина, сделать им или снять статус — только суперадмин                         | `POST/PATCH admins` (`is_super`)                                                                           | **исправлено в этапе 1**                                                            |
| 4   | Править, блокировать, удалять суперадмина, менять его пароль, почту, 2FA — только суперадмин | `PATCH/DELETE admins/{super}`, ключ на суперадмина, будущие 2FA-сбросы                                     | **исправлено в этапе 1** (без 2FA — её нет)                                         |
| 5   | Нельзя редактировать роль, назначенную тебе                                                  | будущие `PUT/DELETE roles/{id}`                                                                            | ролей не правят вовсе                                                               |
| 6   | Нельзя снять статус или удалить **последнего активного** суперадмина                         | `PATCH admins` (`is_super`, `is_active`), `DELETE admins`                                                  | частично: не считает `is_active`, не ловит выключение чужого последнего суперадмина |
| 7   | Токен не шире прав владельца; чужими токенами — только с `admins.manage` и по правилам 1–6   | `POST/DELETE auth/keys`, `auth/connections?all`, `webx:mcp:token`                                          | частично (§7)                                                                       |
| 8   | Нарушение — 403 с понятной причиной и строка в истории                                       | политика возвращает причину; история — §9                                                                  | 403/422 без истории                                                                 |

Уточнения:

- «Право, которого нет у тебя» считается по **эффективным** правам (объединение ролей); роль можно
  назначить, только если **все** её права есть у назначающего. Снять роль можно без этого условия,
  кроме правил 1, 4 и 6.
- Защищать ли от `admins.manage` админа с правами шире, чем у правящего (не только суперадмина), —
  в решениях человека не сказано; по правилу 4 защищён только суперадмин. Развилка 6.
- `PATCH admins/{id}` сегодня ведёт себя как PUT: отсутствующий `is_super` снимает статус,
  отсутствующий `is_active` включает учётку. В этапе политики — правка только присланных полей.
- Причины отказа — ключи `webx-auth::errors.*` (`only-super`, `not-yourself`, `last-super` уже есть;
  добавятся `own-roles`, `beyond-yours`, `role-you-hold`).

### 6.3. Через MCP

`admins_grant_role` и `admins_revoke_role` идут через ту же политику, их право —
`roles.assign` (сейчас `admins.manage`, миграция — §13). Отказ — `ok: false` с той же причиной и
строка истории. Создание и правка ролей — `admins_create_role` / `admins_update_role` за
`roles.manage` и правилами 2 и 5 (этап 4, §19): правка роли откатывается обратным вызовом и видна
в истории. Удаления ролей, паролей, ключей, учёток у агента нет: ошибочный вызов здесь не отменишь.

## 7. Токены MCP: владелец ∩ скоупы

- **Эффективные права вызова** = права владельца токена (того, от чьего имени он действует) ∩
  скоупы токена ∩ «только чтение» согласия. Это уже так (`RegistryTool::attempt`), и проверяется в
  момент вызова: снятая у владельца роль сразу сужает его токены.
- **Кому выдаётся ключ** — вот где была дыра: ключ на суперадмина в руках того, у кого
  `admins.manage`, — это все права. Теперь:
  1. Свой ключ — любой админ, **без `admins.*`**, из профиля или экрана «Подключение агента»
     (сейчас только с `admins.manage`). Скоупы — только тех модулей, где у него есть права.
  2. Ключ на другого — с `admins.manage`, только если все права владельца есть у выпускающего
     (правило 2), и никогда на суперадмина, если выпускающий не суперадмин (правило 4; **исправлено
     в этапе 1**).
  3. Скоупы в форме — только те, что владелец может использовать: модуль без единого права
     владельца не предлагается. `mcp:use` («всё») остаётся — это «всё, что может владелец».
- Список ключей: свои — всем; чужие — `admins.manage`. Отзыв чужого — `admins.manage`, кроме ключей
  суперадмина (их отзывает суперадмин или сам владелец).
- Подключения OAuth: уже «свои — всем, чужие — `admins.manage`»; добавить запрет на чужие
  подключения суперадмина.
- **Смена пароля, выключение учётки, снятие роли** — смена пароля завершает подключения и сессии
  (так обещает `WEBX_UI_MCP_ACCESS.md` §11, но код этого не делает) — развилка 9.

## 8. Свой профиль

Два диалога остаются как есть: **«Your profile»** (меню пользователя внизу сайдбара) — для себя,
любому админу без `admins.*`; **форма администратора** — с `admins.manage` и по §6. Отдельного
экрана нет. Профиль дополняется секциями (вкладками):

| Секция         | Что                                                                                                                       | Сейчас                                                                        |
| -------------- | ------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Основное       | фото, имя                                                                                                                 | есть                                                                          |
| Интерфейс      | язык панели, тема, панель на сайте                                                                                        | есть отдельными маршрутами, свести в секцию                                   |
| Пароль         | новый пароль с вводом текущего                                                                                            | есть                                                                          |
| Почта          | новый адрес + текущий пароль → письмо на новый адрес → подтверждение ссылкой                                              | нет; развилка 8                                                               |
| 2FA            | включить (TOTP), перевыпустить коды восстановления; выключить с паролем; если 2FA на сайте обязательна — выключить нельзя | нет вовсе; развилка 7                                                         |
| Сессии         | свои сессии и устройства, «завершить другие»                                                                              | нет; развилка 7                                                               |
| Агенты и ключи | свои подключения и свои ключи: выпустить, отозвать, скоупы в пределах своих прав                                          | подключения — на экране «Подключить агента»; ключи — только с `admins.manage` |

Нельзя самому себе (только через управление админами, §6): роли и права, статус суперадмина,
блокировка, удаление своей учётки.

**Белый список на сервере.** `PUT auth/me` принимает только поля профиля; любое другое поле
(`roles`, `is_super`, `is_active`, `email` в обход подтверждения, `permissions`) — **422 с именем
поля**, а не молчаливое игнорирование, как сейчас (тест `ProfileTest::what_a_person_is_allowed_to_do_is_not_theirs_to_change`
поменяет ожидание). Каждое изменение профиля — строка истории (без значений пароля).

## 9. История изменений доступа

Новый тип истории `admins` (и `roles`) в `module-auth`, право чтения — `admins.audit` или
`admins.manage`:

- роль создана, изменена (какие права добавлены и убраны), удалена;
- роль назначена, снята (кем, кому, источник: панель, MCP, консоль);
- админ создан, изменён (поля без секретов; «пароль изменён» — фактом), заблокирован, удалён;
  статус суперадмина выдан или снят;
- изменение своего профиля, смена почты (запрошена, подтверждена), включение и выключение 2FA;
- ключ выпущен, отозван; подключение отозвано;
- **отказ политики** — кто, что пытался, какое правило (§6.2 п. 8).

Связка ролей — не модель, поэтому запись делает политика явно, а не трейт `RecordsHistory`.

## 10. Место для ограничений по записям

Не реализуем, но не закрываем дверь:

- Политика спрашивается как `allows($user, $permission, $record = null)`: третий аргумент сегодня
  всегда игнорируется. Модули, где ограничение очевидно (заявки — по форме, статьи — по автору,
  медиатека — по папке), передают запись уже сейчас там, где она под рукой.
- Право в роли хранится строкой; ограничение ляжет рядом, не меняя формат: `permissions` роли —
  список строк, будущие условия — отдельная колонка `constraints` (JSON `{permission: {...}}`).
  Роль без условий значит «все записи», как сегодня.
- Списки (API и MCP) строятся запросом модуля; будущий фильтр — `scope` на запросе от политики,
  поэтому в коде списков не должно появляться своих `if (! hasPermission)` по записям.

## 11. Интерфейс

- **Меню** скрывает раздел, если у админа нет ни одного права из `permissions()` модуля (фронт,
  по манифесту и `auth/me`). Модуль без своих прав (спутники каталога, `regions`, `history`)
  объявляет, каким правом он виден (развилка 3). Сервер по-прежнему отвечает 403 — меню только
  удобство.
- **Маршрутизатор** не пускает на страницу раздела, который скрыт в меню, — показывает «нет
  доступа» вместо пустого экрана с ошибками запросов.
- **Кнопки записи** — `can('<module>.manage')`, как сейчас; добавятся особые права (`roles.*`).
- **Экран «Роли»** — вид раздела «Администраторы»: список ролей (сколько людей), форма роли —
  матрица прав, сгруппированная по модулям в порядке меню, подписи из объявления (§4 п. 2). Права,
  которых нет у правящего, показаны выключенными (правило 2). Роль, назначенная правящему, — только
  для чтения (правило 5).
- **Форма администратора** — несколько ролей мультивыбором (уже есть), за `roles.assign`;
  «Суперадминистратор» — только суперадмину.

## 13. План миграции

Цель: **после обновления никто не теряет доступ** и никто не получает лишнего.

1. **Суперадмины** — без изменений.
2. **Роли с `admins.manage`** получают `roles.assign` (миграция в `module-auth`): сегодня они
   назначают роли через форму админа — завтра делают то же. `roles.manage` не получает никто: правки
   ролей в панели не было, терять нечего.
3. **Новое особое право на действие, которое раньше закрывало другое** (например, если `purge`
   уйдёт под `<module>.delete`, развилка 5): миграция добавляет новое право каждой роли, где было
   старое. Правило для всех будущих разделений, а не разовая правка.
4. **`manage` включает `view`** (развилка 1): расширение, а не сужение — никто ничего не теряет;
   роли с одним `manage` начинают видеть свои записи в выборе ссылок и подборок.
5. **Свои ключи без `admins.manage`** — расширение. Ключи, выпущенные раньше на суперадмина не
   суперадмином, остаются живыми — миграция их не отзывает, а помечает в журнале и в списке ключей
   (`created_by` не суперадмин, владелец суперадмин), чтобы владелец решил сам. Развилка 10.
6. **Меню по правам** — без миграции: тот, кто раньше видел раздел и получал 403, теперь его не видит.
7. **Сидер готовых ролей** запускается `webx:setup` и миграцией обновления, но только создаёт
   отсутствующие роли — роли сайта с такими же `slug` остаются как есть.
8. **Профиль: 422 на лишние поля** — изменение поведения API; описать в changeset, фронт панели
   лишнего не шлёт.

### 14.2. Блокировка и порча — высокое

- Выключить **чужого** последнего активного суперадмина можно; `lastSuper()` не смотрит на
  `is_active` (`AdminController`).
- PATCH как PUT: забытый `is_super` снимает статус, забытый `is_active` включает учётку.
- Изменения админов, ролей, ключей, подключений не пишутся в историю (§9).
- Смена пароля не завершает сессии, ключи и подключения.

### 14.3. Проверка не того права — среднее

- **Контент записи через MCP без права раздела**: `blocks_set_content`, `blocks_edit_content`
  пишут черновик страницы (или другой записи) с одним `blocks.manage`, `blocks_get_content` и
  `blocks_preview_url` читают его с `blocks.view`; панель на сайте требует ещё и `pages.manage`
  (`module-blocks/src/Mcp/BlockTools.php::authorise` против `SiteBarBlocks::find`).
- **Экспорт удалённых товаров с `catalog.view`** (`selection.trashed`, MCP `deleted`) —
  **исправлено в этапе 1**: нужен `catalog.delete`.
- **Прогоны обмена каталога видны всем с любым правом каталога**: чужие экспорты, их файлы и
  подписанные ссылки без сессии, источник импорта (адрес, возможно с ключом в строке запроса);
  колонки, отобранные по правам создателя, достаются читателю с меньшими (`ExchangeController::runs`,
  `run`, `file`; MCP `catalog_exchange_run`). Развилка 11.
- **MCP `catalog_export` — инструмент чтения, который пишет файл** любого размера; хватает
  `catalog:read`. Должен быть `mutating` или с отдельным скоупом.
- **`catalog_index_status`** (MCP) — под `catalog.view`, хотя экран индекса — `search-index.view`.
- **Строки прогона в истории** (`history/runs/{id}`, MCP `history_runs` с `run_id`) проверяют только
  тип самого прогона, а строки внутри могут быть других типов (`HistoryReader::rowsOf`).
- **Предпросмотр уведомления**: HTTP — `notifications.manage`, MCP `notifications_preview` —
  `notifications.view`.
- **Ссылки, подборки, связи** проверяют один `<module>.view` точным совпадением: роль только с
  `manage` правит записи, но не видит их в выборе ссылок, подборок и связей (§4 п. 6).
- Мелкие расхождения HTTP и MCP: `audit.run` не читает результаты через MCP; `tasks_stage_release`
  в MCP без `tasks.manage`; `tasks_comment` не принимает скоуп `tasks:review`; `catalog.delete` без
  `view` читает через HTTP, но не через MCP; спутники каталога удаляют и восстанавливают с
  `catalog.manage`, а товары — с `catalog.delete`.

### 14.4. Интерфейс — низкое (сервер защищён)

- Меню и маршрутизатор не смотрят на права (§3.3).
- Поле `wx-media` и выбор файла не проверяют `media.view`: редактор раздела без него видит поле и
  получает 403 из выбора. Развилка 2.
- `BackupNote` показывается только с `settings.view`, роль с одним `settings.manage` его не видит.
- `PUT auth/me` молча игнорирует запрещённые поля (решение человека — отклонять).

### 14.5. Файлы

- **Вложения заявок** (в том числе резюме откликов на вакансии) — диск `local` (приватный), ключ
  `inbox/{form}/{submission}/{uuid}`, в медиатеке не видны (медиатека показывает только строки
  `media_files` на своём диске), скачиваются только `GET submissions/{s}/files/{f}` за `inbox.view`
  как вложение с `no-store`. **Дыры нет.** Риск только конфигурацией: `WEBX_INBOX_DISK=public`
  выложит резюме под `/storage/inbox/...`; код публичный диск не отвергает — этап медиатеки добавит
  отказ с понятной ошибкой и тест.
- **Отклики на вакансии** — это заявки формы Inbox; у `module-vacancies` файлов нет.
- **Обмен каталога** — диск `webx-catalog.exchange.disk`, по умолчанию `local`; загрузки — через
  `uploads` с целью `catalog.exchange` (`catalog.manage`), только свои. Чтение файлов — см. §14.3.
- **Экспорт SEO-перелинковки и FAQ** — временный файл, отдаётся за `seo.view` и удаляется; остаётся
  пустой файл `tempnam()` без расширения (мусор, не утечка).
- **Выгрузка заявок CSV** — поток, на диск не ложится.
- **Фото товаров** — публичный диск каталога, не медиатека, публичны по замыслу.

### 14.6. Безопасность вне модели прав (найдено попутно, не исправлено)

- **Хранимый XSS через медиатеку**: `svg` в белом списке, санитайзера нет, `mime` записывается из
  заголовка клиента; `SourceController` отдаёт файл inline с этим типом на домене панели, без
  `nosniff` и CSP, и тот же файл открыт на сайте по `/storage/media/...`. Хватает `media.upload`.
  Развилка 12.
- **SSRF при импорте каталога по адресу**: `ExchangeFiles::download` и загрузка картинок галереи
  идут на любой http(s) адрес (внутренние сети, metadata), `inspect` возвращает первые строки
  ответа, ошибка называет причину транспорта. Хватает `catalog.manage`. В медиатеке есть
  защищённый `RemoteFetcher` — каталог его не использует. Развилка 12.

## 15. Обязательный тест модуля (черновик для гайдлайнов)

Каждый модуль с `permissions()` несёт тест на базе общего помощника `module-admin`
(`AssertsPermissions`, этап проверок):

1. каждый маршрут панели модуля без права отвечает 403 (без входа — 401), с правом — не 403;
   маршрут без `cms.can` и без проверки в контроллере валит тест, если он не в списке исключений
   модуля с причиной;
2. каждый инструмент MCP без права не виден в `tools/list` и отвечает «not found»;
3. каждое право, проверяемое в коде модуля (маршруты, `permission:`, `can` экранов, ссылки,
   подборки, связи, `SiteBar::entity`, `UploadPurposes`), объявлено установленным модулем;
4. каждое объявленное право хоть где-то проверяется.

Раздел в `AGENTS.md` пакета — «Права»: что объявляет, что каждое открывает, особые действия.

## 16. Решения на утро

1. **`manage` включает `view`?**
   - (а) как сейчас: каждая проверка перечисляет `view,manage` сама; ссылки, подборки, связи
     чинятся по одной;
   - (б) **рекомендую**: следствие в объявлении права (`implies`), `hasPermission` раскрывает его;
     маршруты могут остаться со списками, а все места с одним `view` начинают работать.
2. **Выбор файла из медиатеки для редактора раздела.**
   - (а) **рекомендую**: правило «поле `wx-media` требует `media.view`», готовые роли его содержат,
     поле без права показывает выбранное, но не открывает выбор;
   - (б) выбор открыт любому, у кого есть `manage` модуля с полем `wx-media` (только чтение
     библиотеки) — удобнее, но размывает `media.view`.
3. **Как виден в меню модуль без своих прав** (спутники каталога, `regions`, `history`).
   - (а) **рекомендую**: модуль объявляет «виден при» (`visibleWith(): list<string>`) — права другого
     модуля, которые его открывают; `permissions()` остаётся «что я объявляю»;
   - (б) спутники объявляют свои права (`catalog-brands.manage` …) — тоньше, но удваивает матрицу и
     требует миграции ролей с `catalog.manage`.
4. **Готовые роли: список в сидере или вклад модулей.**
   - (а) **рекомендую**: модуль сам говорит, в какие готовые роли входят его права
     (`defaultRoles(): array<slug, list<permission>>`), сидер собирает; новый модуль не надо
     вписывать в `module-auth`;
   - (б) один список в сидере `module-auth` — проще, но устаревает с каждым новым модулем.
5. **Удалить навсегда (`purge`, очистка корзины)** — сейчас за `<module>.manage`, в HTTP есть только
   у страниц.
   - (а) оставить за `manage`;
   - (б) **рекомендую**: `<module>.delete` там, где есть корзина (как `catalog.delete`), с миграцией
     §13 п. 3 — роли с `manage` получают `delete`, поведение не меняется, но владелец может отнять.
6. **Защищать ли от `admins.manage` админов с правами шире, чем у правящего** (не только
   суперадмина): выключить, удалить, сменить почту и пароль.
   - (а) **рекомендую**: да, правилом 2 — правящий должен иметь все права цели; иначе смена почты и
     пароля — захват чужой, более сильной учётки;
   - (б) нет, защищён только суперадмин (буквально по решениям).
7. **2FA и сессии — их нет вовсе.**
   - 2FA: (а) **рекомендую** TOTP на `pragmarx/google2fa` (одна зависимость в `module-auth`, коды
     восстановления — хеши в своей таблице); (б) `laravel/fortify` — тянет свои маршруты и
     представления, плохо ложится на SPA панели; (в) отложить 2FA отдельной задачей.
   - Сессии: список возможен только при `SESSION_DRIVER=database` (скелет так и ставит). (а)
     **рекомендую** показывать секцию только при нём, «завершить другие» — через
     `Auth::logoutOtherDevices` при любом драйвере; (б) своя таблица устройств независимо от
     драйвера.
8. **Смена почты, если на сайте не настроена почта.**
   - (а) **рекомендую**: без настроенной отправки секция говорит «смену почты делает
     суперадмин» и не даёт сменить; (б) менять без подтверждения, но с паролем.
9. **Что завершает смена пароля** (своего или админом).
   - (а) **рекомендую**: другие сессии и подключения OAuth; ключи — нет (их выпускают для программ
     намеренно), но список ключей показывает «выпущен до смены пароля»;
   - (б) всё, включая ключи, — как буквально обещает `WEBX_UI_MCP_ACCESS.md` §11.
10. **Ключи на суперадмина, выпущенные раньше не суперадмином.**
    - (а) **рекомендую**: не отзывать, пометить в списке и в журнале;
    - (б) отозвать миграцией — безопаснее, но может остановить чью-то выгрузку на проде.
11. **Кто видит чужие прогоны обмена каталога и их файлы.**
    - (а) **рекомендую**: список — всем с `catalog.view` (без `source` с секретами), файл и ссылка —
      только создателю и суперадмину; у экспорта поля, недоступные читателю, — повод отказать;
    - (б) только свои прогоны, чужие — суперадмину.
12. **XSS через SVG медиатеки и SSRF импорта каталога** — вне модели прав.
    - (а) **рекомендую**: в этой задаче — на этапе медиатеки и файлов (SVG: чистить при загрузке
      и отдавать исходник с `Content-Disposition: attachment`, `nosniff`, `CSP: sandbox`; каталог —
      через `RemoteFetcher` медиатеки);
    - (б) отдельной задачей сразу после этой.
13. **Имена прав блога** (`blog.articles.*` при id модуля `articles`) — оставить (переименование —
    миграция ролей ради красоты) или привести к `articles.*`. Рекомендую оставить.

## 17. Что сделано на этапе проверок (этап 2)

- **Политика** — `WebxUi\Admin\Access\AccessPolicy` в `module-admin` (каркас, от которого зависят все
  модули и MCP-сервер): `allows/decide($user, $permissions, $record = null)`, `decideCall()` —
  скоупы токена ∩ права владельца, `missing()` и `covers()` для правила 2, `constrain()` — место
  для ограничений по записям (§10), `declared()` — права установленных модулей. Аккаунт, умеющий
  назвать свои права, реализует `HoldsPermissions` (`CmsUser`); `hasPermission()`, `cms.can`,
  `Permissions` и `Scopes` в `webx-ui/mcp`, журнал — спрашивают политику.
- **`cms.auth` и `cms.can` — до привязки моделей маршрута** (приоритет middleware в
  `AuthServiceProvider`): без права — 403, а не 404, по которому видно, есть ли запись.
- **Правила §6.2** — `WebxUi\Auth\Access\AccessRules` в `module-auth`, одни для формы админа, MCP
  `admins_grant_role`/`admins_revoke_role` и ключей. Отказ — 403 с `message`, `rule`, `missing` и
  строка журнала с событием `refused`. Правило 5 и `roles.manage` проверяются методами
  `saveRole()`/`deleteRole()` — маршрутов ролей ещё нет (этап экрана «Роли»).
- **Хранение** уже было (`cms_roles.permissions`, `cms_role_user`); добавлены права `roles.manage`,
  `roles.assign` и миграция: роли с `admins.manage` получают `roles.assign` (§13 п. 2).
- **История**: типы `admins.admin` (поля аккаунта, роли до/после, факт смены пароля) и
  `admins.role` (код, имя, права), чтение — `admins.audit` или `admins.manage` (`roles.manage` —
  для ролей).
- **`PATCH auth/admins/{id}`** меняет только присланное (§14.2).
- **Объявление прав** — как и было, `Module::permissions()`; единство держит тест: право, которое
  проверяет маршрут или инструмент, обязано быть объявлено установленным модулем.
- **Команды** работают от имени консоли (§4 п. 8): `AccessRules` с актором `null` не отказывает.
- **Обязательный тест** — `WebxUi\Auth\Testing\AssertsPermissions` (в `module-auth`, а не в
  `module-admin`: ему нужен настоящий администратор и гард панели), `AccessCoverageTest` в каждом
  пакете с маршрутами или инструментами. Маршрут без `cms.can`, открытый по замыслу, назван в
  тесте с причиной — это список §5.5.

Развилки §16, по которым пришлось решить на этом этапе без ответа человека, — консервативно:

- **1 (`manage` включает `view`)** — вариант (а), без следствий: ничьи права не расширились молча.
  Ссылки, подборки и связи с одним `view` (§14.3) не тронуты.
- **5 (`purge`)** — вариант (а), остаётся за `manage`.
- **6 (защита сильнее правящего)** — вариант (а): править, удалять, выпускать ключ можно только
  тому, чьи права целиком есть у правящего (`beyond-yours`); снять роль — можно.

## 18. Что сделано на этапе экрана «Роли» (этап 3)

- **Маршруты ролей** (`module-auth`, `RoleController`): `GET roles` (у каждой — `users` и `held`:
  назначена ли читающему), `GET roles/permissions` (матрица), `GET roles/{id}` (с `holders`) — за
  `admins.view|admins.manage|roles.manage|roles.assign`; `POST/PUT/DELETE roles` — за
  `roles.manage` и правила 2 и 5 (`AccessRules::saveRole/deleteRole`). Право в роли — только
  объявленное установленным модулем (422), кроме уже лежащих в роли: модуль, снятый с сайта, не
  ломает сохранение. Код роли без значения делается из названия и становится уникальным. Удаление
  снимает роль с держателей и пишет строку в историю каждого.
- **Матрица** (`Access\PermissionMatrix`): строка на модуль в порядке меню, право — под первым
  объявившим его модулем (общее `blog.taxonomy.manage` рубрик и тегов — один раз), у каждого права
  подпись и `held`. Подписи — `webx-auth::permissions`: своя строка для права с неговорящим
  последним словом (`roles-assign`, `inbox-update`), иначе слово действия (`view`, `manage`, …),
  иначе само слово. Объявление подписи модулем (§4 п. 2) не делали — хватает словаря.
- **Экран «Роли»** — вид раздела «Администраторы» (`/admins/roles`): список (код, сколько прав и
  людей, «Ваша»), диалог роли с матрицей: «все в модуле» одной галочкой, право, которого нет у
  правящего, видно и не ставится (снять уже стоящее можно), роль, назначенная правящему, — только
  для чтения. Удаление спрашивает, называя держателей. Виды раздела показываются по правам; адрес
  вида, который закрыт, открывает первый доступный.
- **Форма администратора**: роли — мультивыбор, только с `roles.assign` (без него поле не
  показывается и не отправляется); «Суперадминистратор» — только суперадмину.
- **Манифест по правам** (развилка 3, вариант (а)): у каждого модуля `allowed` — есть ли у
  читающего хоть одно право модуля, а у модуля без своих прав — хоть одно из `visibleWith()`
  (новый контракт `WebxUi\Admin\Contracts\HasVisibility`: спутники каталога и
  `catalog-categories` — `catalog.view|catalog.manage`, `regions` — `blocks.regions`). Модуль без
  прав и без контракта открыт всем вошедшим (`connect`, `history`). Модули из манифеста **не
  выкидываются**: разделы читают `meta` друг друга (блоки — группы, настройки — правила контента).
  Кешируемая часть манифеста — только слова, по языку; `allowed` считается на каждый запрос, поэтому
  в ключ кеша набор прав не входит и одному админу не достаётся чужое меню.
- **Фронт**: меню пропускает `allowed === false`, главная ведёт на первый доступный раздел; страница
  закрытого раздела — «Нет доступа» вместо экрана с отказами (`AdminForbidden`, маршруты модулей
  несут `meta.module`). Кнопки записи — `can()`, как и раньше.
- **Готовые роли** (`Access\DefaultRoles`, §12): создаются только отсутствующие и только из
  объявленных прав, роль без единого права не создаётся; `admins.*`, `roles.*`, `tasks.*`,
  `debug.*` — никогда. Запускаются первым `webx:admin` (а значит `webx:setup`), миграцией
  `2026_10_18_000001_seed_default_roles` (только на сайте, где уже есть админы, — новый сайт ещё не
  знает своих модулей) и командой `webx:roles:defaults`. Названия — на языке приложения.
- **Плейграунд**: `/panel/` с переключением админа в меню в углу — Анна (суперадмин), Дмитрий
  (редактор: страницы, статьи, файлы), Ольга (люди и роли, без контента).

## 19. Что сделано на этапе токенов MCP (этап 4)

- **Скоупы ключа — в пределах прав владельца.** `KeyIssuer::usable($owner)`: `mcp:use` и каждый
  скоуп, у которого есть хоть один инструмент, разрешённый владельцу (`AccessPolicy::allows` на
  `BoundTool::permissions()`). `KeyIssuer::issue()` отклоняет остальные (422 на `scopes`) — один путь
  для панели и `webx:mcp:token`, даже суперадмин не выпустит роботу скоуп, которым тот не
  воспользуется. Форма спрашивает `GET auth/keys/scopes?admin=` при выборе владельца и снимает
  выбранные скоупы, которых у нового владельца нет.
- **Проверка на лету** уже была (`RegistryTool::attempt`, `tools/list`): скоуп ∩ права владельца
  в момент вызова. Тест: снятая роль сразу убирает инструмент из списка и из вызова — и у ключа
  с модульным скоупом, и у ключа `mcp:use`.
- **Свои ключи — без `admins.*`** (§7 п. 1): `/api/cms/auth/keys` вынесен из группы
  `admins.manage`, контроллер решает сам, как у подключений. Список — свои, все — с
  `admins.manage` (`meta.can_see_everybody`); выпуск на другого — `admins.manage` и правила
  (`AccessRules::issueKeyFor`: `forbidden`, `only-super`, `beyond-yours`); отзыв — свой всегда,
  чужой с `admins.manage`, ключ суперадмина — только суперадмин или сам владелец
  (`AccessRules::revokeKeyOf`). Отказы — 403 и строка истории, как и прочие.
- **MCP-инструменты ролей**: `admins_list_roles` — права и держатели (читают те же, кто читает роли
  в панели); `admins_list_permissions` — матрица с `held`; `admins_create_role` и
  `admins_update_role` (`Tool::mutating`, `dry_run`, `roles.manage`): валидация — та же, что у
  формы (`RoleRequest::rulesFor`), правила 2 и 5 — `AccessRules::saveRole`, и в пробном прогоне
  тоже. Правка — целым списком или `add`/`remove`; ответ называет `gained`/`lost`.
- **Не сделано здесь:** экран своих ключей для админа без `admins.*` — вид «Ключи» живёт в разделе
  «Администраторы», которого такой админ не видит; API готов, место в интерфейсе — этап профиля.
