# Справка по разделам панели — спецификация

Статус: предложена на приёмку. Кода по ней нет; всё, что названо ниже новым классом, компонентом или
адресом, появится на этапах §9. Ответы человека на вопросы спеки внесены в §1, открытых вопросов не
осталось (§10).

Цифры §7 сняты с этой ветки замером, а не оценкой: деревья — `ScreenRegistry` на lab-сайте со всеми
модулями, маршруты — `routes` из собранных npm-пакетов.

## 1. Назначение и границы

В панели трудно ориентироваться даже автору, а клиенту — тем более. Подсказки под полями есть, но
они короткие и разрознены: на вопрос «что это за раздел, как в нём работать и что делает каждое
поле» панель не отвечает нигде. Справка отвечает на него в одном месте и одинаково на всех экранах.

**Чего здесь нет:**

- **Редактирования в панели.** Администратор сайта справку не дописывает и не правит: нет ни
  таблицы, ни экрана, ни инструмента записи. Справка — файлы пакета, она обновляется вместе с ним.
- **Подсказок в самой форме.** `help` узла остаётся как есть, под полем; справка его не заменяет
  (§2.6).
- **Обучающих туров, подсветки полей, поиска по всей справке.** Справка открывается на экране,
  где нужна, и рассказывает о нём.
- **Гайдов для разработчиков.** `apps/docs/guide/` пишется для того, кто ставит и расширяет панель;
  справка — для менеджера магазина, который в ней работает. Они не заменяют друг друга.

## 2. Формат и место текстов

### 2.1. Где лежат

Один файл — один экран на одном языке. Рядом с `resources/screens/` пакета:

```
php/packages/module-catalog-stock/resources/
├── screens/stock-status-form.json
└── help/
    ├── en/
    │   ├── catalog-stock.index.md
    │   └── catalog.stock-status-form.md
    ├── ru/
    │   ├── catalog-stock.index.md
    │   └── catalog.stock-status-form.md
    └── uk/                                # только эти три языка (§2.5)
```

Папка на язык, а не суффикс в имени: так устроен `lang/<код>/`, и пропавший язык виден одним `ls`.
Файлы, а не группа `help` в `lang/*.php`, какую завёл `WxHelpButton` у `module-blocks`, по двум
причинам: словарь уезжает клиенту целиком вместе с манифестом, а справки там быть не должно (§3),
и Markdown в отдельном файле читается и переводится как текст, а не как строка PHP. `resources/`
едет в dist: `.gitattributes` пакетов исключают только `/tests` и сам себя.

**Регистрация** — одна строка в провайдере пакета, папка целиком:

```php
// StockServiceProvider::boot()
$this->app->make(HelpRegistry::class)->directory(__DIR__.'/../resources/help');
```

Имя файла и есть ключ, больше ничего связывать не нужно. Реестр запоминает только папки; файлы
читаются, когда справку спросили (§3).

### 2.2. Формат файла

Markdown с короткой шапкой. Разделы называются фиксированными английскими словами первого уровня —
они не переводятся и на экран не попадают, по ним файл разбирается:

```md
---
title: Статусы наличия
guide: catalog#dictionaries-labels-stock-brands
---

# about

Зачем раздел: два-три предложения.

# howto

## Как сделать что-то одно

1. Шаг.
2. Шаг.

# fields

## code

Что поле делает и на что влияет на сайте.
```

| Часть      | Обязательна                 | Что это                                                                                                                           |
| ---------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `title`    | да                          | Как экран называется в справке и в списке для агента (§5). Панель показывает заголовок из шапки экрана, агенту его брать неоткуда |
| `guide`    | нет                         | Файл в `apps/docs/guide/` без расширения, можно с якорем. Адрес собирает сервер, и только если на сайте задан `docs_url` (§3.2)   |
| `include`  | нет                         | Ключи экранов, чьи поля показать здесь же: у формы в диалоге нет своей шапки (§4.5)                                               |
| `# about`  | да                          | Зачем раздел, 2–3 предложения                                                                                                     |
| `# howto`  | нет для теста, см. §8       | Сценарии: `##` — вопрос, под ним шаги                                                                                             |
| `# fields` | да, если у экрана есть поля | `##` — **`id` узла**, под ним описание. Порядка нет: порядок и вкладки берутся из дерева                                          |

Внутри текста заголовков нет: `#` и `##` — разметка файла. Разрешено то, что понимает
`renderMarkdown` из `module-admin`: абзацы, списки, inline-код, ссылки, выделение. Таблиц и картинок
он не рисует, и тест их не пропускает (§6).

`title`, `guide` и `include` повторяются в каждом из трёх языков. `guide` и `include` обязаны совпадать с
английским файлом, `title` переводится.

### 2.3. Связь с экраном и полями

**Ключ экрана.** У описанного экрана ключ — его имя: `catalog.product-form`. У страницы без дерева
(список, шаблон) ключ — имя маршрута без `webx.`; у маршрута из одного слова добавляется `.index`:
`webx.catalog.deleted` → `catalog.deleted`, `webx.faq` → `faq.index`. Формат тот же, что у экранов
(`<модуль>.<экран>`), поэтому адрес API один. Маршрут называет ключ сам — `meta.help` (§4.1), а не
выводится из имени: `webx.catalog.products.edit` — это `catalog.product-form`, и `new` с `edit`
одной формы ведут к одному файлу.

**Ключ поля — `id` узла, а не `name`.** `id` уникален в экране и объявлен публичным контрактом
(`WEBX_UI_SCREENS.md` §11): переименование и так идёт в changeset как ломающее, и патчи адресуют по
нему же. `name` — ключ модели, с точками внутри, и у разных экранов может совпадать.

**Подписи, подсказки, вкладки в файл не пишутся.** Сервер обходит дерево и подставляет к описанию
всё остальное (§3.2). Отсюда три следствия, ради которых это устроено так:

- поле переехало на другую вкладку — справка не меняется;
- подпись переведена иначе — справка сама говорит теми же словами, что и форма;
- узел вырезан по праву `can`, спутник не установлен или поле убрала настройка сайта — поля нет в
  дереве, и в справке его тоже нет. Описание без поля на сайте просто не показывается.

**Поле, которое убирает настройка сайта.** Патч провайдера снимает поле, если настройка выключена
(`facets`, `prices`, `barcode-col`, `mpn`). Описание такого поля лежит в файле экрана как обычно:
на сайте с выключенной настройкой панель и `help_get` его не выводят, потому что идут по дереву
сайта, а тест и `--check` ошибкой не считают. Что описать **можно**, они сверяют со всеми шагами
экрана: эталон и дерево после каждой операции патчей (`ScreenRegistry::stages()`). Что описать
**нужно**, сверяется с деревом этого сайта. `id`, которого нет ни на одном шаге, — красный (§6.2).

Поля строки `wx-repeater` — дети узла, их `id` уникальны в экране так же, и описываются они так же.
Обход полей экрана на узле с `name` останавливается (`WEBX_UI_SCREENS.md` §3), поэтому справке
нужен свой обход, заходящий внутрь.

**Страница без дерева.** Подписи взять неоткуда, поэтому у шаблона `# fields` необязателен, а `##`
там — сама подпись словами, показывается как есть. Покрытие полей на такой странице не проверить;
когда шаблон переедет на описание (`admins.form`, форма правила SEO — `WEBX_UI_SCREENS.md` §9.2),
ключ станет именем экрана и тест начнёт его держать.

### 2.4. Поля спутников в чужих формах

Поле спутника описывает спутник — там же, где лежит патч. Файл называется ключом чужого экрана:

```
php/packages/module-catalog-stock/resources/help/ru/catalog.product-form.md
```

```md
# fields

## stock-status

Какой статус наличия показать покупателю у этого товара. …
```

Части одного ключа собираются в порядке загрузки провайдеров, как патчи. `title` и `# about` — только
у владельца экрана; файл спутника несёт `# fields` и, если есть что сказать, `# howto` — сценарии
дописываются после сценариев владельца. Вкладку, которую добавил спутник, он же и описывает полями.
Спутник снят — вместе с ним уходят и поле, и описание, и сценарий.

**Общие поля.** `module-seo` кладёт одну карточку `seo-card` в 12 форм чужих модулей; 12 одинаковых
файлов на каждом языке незачем. Поэтому в папке языка может лежать `_fields.md`: только `# fields`,
а описания подходят к этим `id` на любом экране. Правило — только для `id`, которые пакет сам
добавляет патчами. Файл экрана сильнее `_fields.md`.

**Проект.** Поле, добавленное патчем в `AppServiceProvider`, описывает проект, той же строкой
`directory(resource_path('help'))`: провайдер проекта грузится последним, а `id`, описанный дважды,
берётся из последней части. Это файл в репозитории проекта, правится разработчиком, с решением 5 не
спорит. Не описал — поле в справке показывается подписью и подсказкой, без текста; тесты монорепы
проект не держат, сказать об этом может `webx:help --check` (§6.4).

### 2.5. Языки и запасной язык

Тексты пишутся на трёх языках: `en`, `ru`, `uk`. `en` — язык по умолчанию и эталон состава: какие есть
файлы и какие `id` описаны. Сравнение `ru` и `uk` с ним — в тесте (§6). Остальные семь языков панели
из `TranslationsCoverageTest::LOCALES` показывают английский текст: файлов на них нет, и это не
ошибка.

Цепочка для каждой части отдельно: язык панели администратора → `en`. Запасной язык сайта
(`Locales::fallback()`) в ней не участвует: справка — слова панели, а не содержимое сайта. Ответ говорит, на каком языке пришёл текст (`locale`), и если это не язык панели, панель пишет об
этом одной строкой над текстом. Берётся файл целиком, а не поабзацно: страница на двух языках
вперемешку читается хуже, чем целиком на английском, — то же решение уже принято для групп прозы
(`TranslationsCoverageTest::PROSE`).

Слова самой боковой панели (кнопка, «Как сделать», ошибка загрузки) — не тексты справки: они живут в
словаре `webx-admin::help.*` и идут на всех десяти языках, как весь словарь панели.

### 2.6. Как не дублировать `help` поля

У узла уже есть `help` — 283 подсказки на 465 полей. Разделение такое:

| Где                | Что отвечает                          | Размер          | Пример (`code`)                                     |
| ------------------ | ------------------------------------- | --------------- | --------------------------------------------------- |
| `help` под полем   | Что ввести и в каком виде             | одна строка     | Латиница, цифры и дефисы: статус в адресе фильтра…  |
| Описание в справке | Зачем это, на что влияет, что сломает | 1–3 предложения | Менять без нужды не стоит: старые ссылки на фильтр… |

- Панель показывает подсказку в справке автоматически, между подписью и описанием. Автор её не
  копирует, а продолжает: описание начинается с того, чего подсказка не сказала.
- Тест не пускает описание, совпадающее с подсказкой или содержащее её целиком (§6.2).
- Описание обязательно у каждого поля, даже у самого простого: пометки «подсказки достаточно» нет
  (решение 10). Правило 3 §8 всегда даёт что сказать — что увидит покупатель.
- Существующие подсказки на этапах наполнения не переписываем, кроме случая, когда в подсказке —
  объяснение на абзац: тогда оно переезжает в справку, а под полем остаётся строка.

## 3. Доставка в панель

### 3.1. Адрес и ленивая загрузка

```
GET /api/cms/help/{key}
```

Тексты справки не едут ни в манифесте, ни в словаре, ни вместе с экраном: за сессию её откроют на
одном-двух экранах из ста тридцати, а подсказка менеджеру не должна стоить ничего тому, кто её не
открыл. Запрос уходит **по нажатию на «?»**. В манифесте — только список ключей, как имена экранов
(`WEBX_UI_SCREENS.md` §4): кнопка рисуется, если ключ из `meta.help` в этом списке есть, поэтому
незаполненный экран кнопку не показывает, а не отвечает ошибкой (решение 14). Список стоит ~130
коротких строк в ответе манифеста, зато кнопки нет и у проектного экрана без справки.

Клиент кладёт ответ в память на сессию с ключом «ключ + язык» — как `loadScreen` (`WEBX_UI_SCREENS.md`
§4); смена языка панели сбрасывает. Перезагрузка страницы — новый запрос, поэтому новая версия
пакета видна сразу.

### 3.2. Ответ

Сервер сам собирает текст и дерево, клиент только рисует:

```json
{
  "data": {
    "key": "catalog.product-form",
    "title": "Товар",
    "locale": "ru",
    "about": "Markdown",
    "howto": [{ "title": "Как поставить товару скидку", "body": "Markdown" }],
    "groups": [
      {
        "id": "general",
        "label": "Основное",
        "fields": [
          {
            "id": "stock-status",
            "label": "Наличие",
            "hint": "Подсказка под полем, как в форме",
            "required": false,
            "body": "Markdown"
          }
        ]
      }
    ],
    "guide": null
  }
}
```

- `groups` — вкладки экрана в порядке дерева. Экран без вкладок — одна группа с `label: null`.
- Дерево берётся через `ScreenRegistry::render()` с теми же `can` и переводчиком, что у
  `ScreenController`: то, чего администратор не видит в форме, он не видит и в справке, а подписи уже
  переведены. Условная видимость (`visible`) здесь не считается — значений у справки нет, поэтому
  показываются все поля, которые могут появиться.
- Адрес гайда — `config('webx-admin.docs_url')` плюс значение `guide`. По умолчанию `docs_url` — `null`:
  в ответе `guide: null`, ссылки нет (решение 9). Гайды английские и написаны для разработчиков,
  менеджеру по ссылке неуютно. Сайт включает ссылку настройкой, задав адрес, например
  `https://webx-ui.github.io/webx-ui`; тогда в `guide` приходит
  `https://webx-ui.github.io/webx-ui/guide/catalog#products-and-categories`.
- Неизвестный ключ — 404 тем же словом, что у экранов.

### 3.3. Права и кеш

**Права.** Маршрут открыт каждому вошедшему администратору, как `screens/{name}`: это слова панели,
а не данные, и узлы за правом вырезаются внутри. В `AccessCoverageTest` пакета `module-admin` —
строка с этой причиной.

**Кеш на сервере не нужен.** Ответ — чтение двух-трёх файлов и обход дерева, которое и так собирается
для экрана; запросов к базе нет (держит тест), и случается это по нажатию человека, а не на странице
сайта. Группы `CacheGroups` рассчитаны на данные моделей, здесь сбрасывать нечего: файл меняется
только с деплоем. Если замер на этапе Х2 скажет иное — кеш с версией пакетов в ключе, как у словаря в
`TranslationController`.

## 4. Интерфейс

### 4.1. Кнопка «?»

Одно место — `WxScreenHead` из `module-admin`: его рисует каждый экран панели, и списки через
`WxListScreen`, поэтому страницы разделов править не нужно.

- **Где.** В блоке `.wx-screen-head__name`, сразу за заголовком и слотом `title-after`. Не среди
  действий справа: те на узкой шапке сворачиваются в `···`, а справка нужна как раз там.
- **Как выглядит.** `WxAction`, иконка `question`, тон `neutral`, размер `sm` — как у
  `WxHelpButton`. В `title` и `aria-label` — `webx-admin::help.open`.
- **Откуда ключ.** Новый проп `help?: string | false`. Не задан — шапка уровня 2 берёт
  `route.meta.help`. `false` — кнопки нет. Роут читается через `inject(routeLocationKey, null)`:
  шапка живёт и в тестах без роутера.
- **Панель внутри экрана.** Шапка `level="3"` (форма в `WxListDetail`, таких форм 9) роут не читает: у
  неё свой экран, поэтому панель передаёт `help="faq.form"` сама. На странице тогда две кнопки:
  у списка — про раздел, у записи — про её поля. Это честно: это два экрана.
- **Маршрут.** `meta.help` пишется в `routes` модуля. Общие конструкторы `dictionarySection` и
  `categoryRoutes` ставят его сами из своих `screen` и `id`.

`WxHelpButton` остаётся для объяснения одной вещи на месте (схема блока): это диалог с абзацем, а не
справка экрана. Менять его незачем.

### 4.2. Боковая панель

`WxHelpPanel` в `module-admin`, а не в ядре: ядро не ходит в API, а панель знает про него и про
словарь. Внутри — `WxDrawer` справа, готовый со своими шапкой, крестиком, изменением размера и памятью.
Один экземпляр на панель — в `AdminShell`; кнопки зовут его через `useHelp()`.

```vue
<wx-drawer
  v-model:open="open"
  side="right"
  :size="420"
  :min-size="320"
  :modal="blocking"
  :overlay="false"
  :close-on-overlay="false"
  resizable
  persist="wx-help"
  closable
/>
```

- **`modal: false`, `overlay: false`, `closeOnOverlay: false`** — это и есть «форма остаётся видна,
  можно читать и заполнять»: страница не затемнена, фокус и прокрутка не заперты, клик в форме
  панель не закрывает. Немодальный `WxDrawer` в панели используется впервые: возврат фокуса Reka и `z-index`
  рядом с другими слоями проверяются в браузере на этапе Х3. Не сработает — не новый компонент, а
  правка `WxDrawer` в ядре на том же этапе, с changeset на `@webx-ui/core` (решение 15).
- **Форма не уходит под панель.** Оболочка, пока справка открыта и места хватает, отдаёт ширину
  панели отступом `.wx-admin__screen`. Экран сужается, а не закрывается, контейнерные запросы
  пересчитываются сами, `WxActionBar` сдвигается вместе с содержимым. Хватает — это когда у экрана
  остаётся не меньше 720 px (порог сворачивания шапки), замер `useElementWidth` в оболочке. Не хватает —
  панель лежит поверх правого края, ширину можно потянуть. Как сужение на лету переживают экраны с
  `fill` (файловый менеджер, доска), проверяется в браузере на Х3; ломается — у таких экранов панель
  лежит поверх (решение 16).
- **Переход на другой экран.** Панель открыта — остаётся открытой и показывает справку нового экрана;
  ключа у него нет — закрывается. Несохранённая форма справку не волнует, она ничего не меняет.
- **Над модальным слоем.** Модальный диалог Reka ставит `body` `pointer-events: none`, и немодальная
  панель поверх него не получает кликов (`docs/pitfalls/vue-and-tests.md`, «Reka и слои»). Поэтому
  `blocking` — истина, если кнопка нажата внутри модального слоя (`closest('[role="dialog"]')`) или на
  телефоне: панель тогда сама модальная и открывается на следующем витке цикла — клик изнутри другой
  панели иначе закрыл бы её тут же (там же).

### 4.3. Что внутри

Сверху вниз:

1. **Заголовок** `Справка: <заголовок экрана>`, крестик. Текст не на языке панели — строка «Текст на
   английском».
2. **Зачем раздел** — абзац `about`, без подзаголовка.
3. **Как сделать** — `WxAccordion`, в пункте вопрос, раскрыт шаги. Закрыто всё: вопросы видны сразу.
4. **Поля** — группы по вкладкам формы. Подпись поля, подсказка мелким серым, описание. Звёздочка
   обязательного — как в форме.
5. **Руководство для разработчиков** — ссылка на гайд в конце, новая вкладка, `rel="noopener"`. Только
   если сайт её включил: по умолчанию ссылки нет (§3.2).

**Навигация.** Когда групп две и больше, над полями стоит полоса вкладок `WxTabs` в режиме `items` со
словами вкладок формы: те же слова, тот же порядок, и переключение показывает только свою группу.
Когда полей больше двенадцати (`catalog.product-form` — 22, `settings.index` — 44), над ними стоит
поле поиска: сужает по подписи и тексту, на всех вкладках сразу. Вкладка формы со справкой не
связана: у `WxTabs` наружу этого не выходит, а открывать в справке то, что открыто в форме, —
приятная мелочь, а не условие; на этапах не делаем.

**Состояния.** Загрузка — `WxSkeleton` в месте текста, ошибка — `WxAlert` с повтором. Справка пуста
быть не может: держит тест.

Markdown рисует `renderMarkdown` — тот, что у `WxHelpButton`, безопасный для `v-html`; стили прозы
`.wx-help` выносятся из `HelpButton.vue` в общий файл, чтобы их не было двух.

### 4.4. Доступность, 360 px, тёмная тема

**Клавиатура и фокус.** `role="dialog"` и подпись — у `WxDrawer` (Reka). При открытии фокус уходит на
заголовок панели (`tabindex="-1"`), а не на первую ссылку; Esc закрывает, и фокус возвращается на
«?». Немодальная панель фокус не запирает: Tab уводит обратно в форму, и это нужно — читать и
заполнять. Esc при открытом списке формы закрывает сначала список: слои Reka идут стопкой.

**Кнопка.** `aria-haspopup="dialog"`, `aria-expanded`, `aria-controls` на панель. Повторное нажатие
закрывает.

**Загрузка.** `aria-busy` на теле панели; пришедший текст читается по фокусу на заголовке, живая
область не нужна.

**360 px.** `WxDrawer` при `max-width: 640px` занимает весь экран сам (`fullScreen`). Это медиа-запрос
ядра, и здесь он законен: панель телепортирована в `body` и контейнера у неё нет. На телефоне форма
под справкой не видна, и это решение человека из задачи; закрытие крестиком и Esc возвращает на
то же место формы. Полоса вкладок сворачивается в один переключатель сама. Жест и переполнение
проверяются на устройстве: `scrollWidth` ≤ `clientWidth` на 360.

**Тёмная тема.** Только токены: поверхность — `--wx-bg-surface`, текст — `--wx-text-default`,
подсказка — приглушённый тон как у `WxFormItem`, код — `--wx-bg-subtle`. Несуществующий `var(--wx-…)`
молчит, поэтому перед гейтом — сверка с `tokens.css` (`CLAUDE.md` §5). Край панели без затемнения за
ней держит только граница: в тёмной теме проверяется глазами.

### 4.5. Экраны без своей шапки

| Случай                                            | Сколько | Что делаем                                                                                                                             |
| ------------------------------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Форма в панели списка (`WxListDetail`)            | 9       | Своя шапка `level="3"` — своя кнопка (§4.1)                                                                                            |
| Форма в диалоге (`PointDialog`, `LocalityDialog`) | 2       | Шапки нет, а «?» в заголовок `WxDialog` без нового слота не поставить. Поля показываются в справке списка через `include` (решение 11) |
| Вторая форма на странице (`ExchangeProfilePage`)  | 1       | `catalog.exchange-profile` делает `include` на `catalog.exchange-import`                                                               |
| Карточка на чужой странице (`ContentRulesCard`)   | 1       | Страница `connect.index` делает `include` на `settings.content`                                                                        |

`include` добавляет группы подключённого экрана после своих, с его заголовком как подписью. Сам
подключённый экран остаётся в покрытии: файл и описания у него есть, а кнопки нет.

## 5. MCP: доступ агента к справке

Агенту, работающему с сайтом через MCP, смысл поля нужен не меньше, чем менеджеру: `settings_list`
говорит подпись и тип, но не «что сломается». Сам формат выбирался под это: один Markdown служит
двум читателям.

Отдельный модуль `help` — `WebxUi\Admin\Help\Mcp\HelpModule`, по образцу `HistoryModule`: страницы у
него нет, регистрируется только там, где стоит `webx-ui/mcp`, инструменты зовутся `help_*`, скоуп —
`help:read`.

| Что                    | Вид           | Отвечает                                                                    |
| ---------------------- | ------------- | --------------------------------------------------------------------------- |
| `help_list`            | инструмент    | Все ключи справки на этом сайте: ключ, `title`, вид, есть ли поля, модуль   |
| `help_get`             | инструмент    | Один экран: `key`, `locale?` — JSON ответа §3.2, у поля ещё `name` и `type` |
| `help://screens`       | ресурс        | То же, что `help_list`, — для клиента, который читает ресурсы до работы     |
| `help://screens/{key}` | ресурс-шаблон | Один экран как `text/markdown`, одним документом                            |

- **`name` и `type` — только агенту.** Инструменты записи принимают `name` (`stock.status`), а не
  `id`; панели это незачем.
- **Язык** — `locale`, по умолчанию язык панели администратора, цепочка та же (§2.5). Агент читает
  на любом, пишет по `settings://content-rules`.
- **Права.** По правилу `WEBX_UI_MCP_ACCESS.md` §6 у инструмента есть право панели. Своего права у
  справки нет, поэтому `permission:` — любое из прав, объявленных модулями, как делает `HistoryModule`
  (решение 13). Администратор без единого права инструмента не увидит; отдельный признак «без права» в
  `webx-ui/mcp` — только если появится второй такой случай. `can` узлов режется как в панели; на stdio
  вызывающего нет, видно всё.
- **Только чтение.** Записи нет, `dry_run` не нужен, «только чтение» агента инструментам не мешает.
- **Подсказка агенту.** В инструкции `WebxServer` — строка «не уверен в смысле поля — `help_get`», если
  инструмент зарегистрирован.
- **Экраны без дерева** отдаются тем же инструментом: `groups` со словами из файла.

## 6. Тест-покрытие и список исключений

По образцу `AccessCoverageTest` (трейт в пакете, тест в каждом модуле) и `LatinSlugCoverageTest`
(список с причиной в коде теста): четыре проверки, у каждой свой случай.

### 6.1. Экран и поле: трейт `AssertsHelp`

`WebxUi\Admin\Testing\AssertsHelp`, тест `HelpCoverageTest` в каждом пакете, у которого есть экран или
патч. Такой тест поднимает провайдеры своего `TestCase`, то есть ядро плюс сам спутник, — поэтому
поле спутника без описания роняет тест спутника, а не ядра. Это и держит правило «поле спутника
описывает спутник» без учёта владельцев.

```php
final class HelpCoverageTest extends TestCase
{
    use AssertsHelp;

    #[Test]
    public function every_screen_and_field_is_explained(): void
    {
        $this->assertScreensHaveHelp();
    }
}
```

### 6.2. Что проверяет `assertScreensHaveHelp`

| Падает, если                                                           | Почему                                                     |
| ---------------------------------------------------------------------- | ---------------------------------------------------------- |
| Экрана нет в `en` (нет `title` или `# about`)                          | Решение 6                                                  |
| Поле, включая строку `wx-repeater`, без описания в `en`                | Решения 6, 10, 12                                          |
| Описан `id`, которого нет ни на одном шаге экрана (§2.3)               | Поле переименовали, справка отстала                        |
| Один `id` описан двумя пакетами                                        | Спутник описывает своё, а не чужое                         |
| `ru` или `uk` без файла или с другим составом `id`, `guide`, `include` | Решение 8: пишем на трёх языках                            |
| Описание равно подсказке или содержит её целиком                       | §2.6                                                       |
| В тексте таблица, картинка, HTML, заголовок                            | Их не нарисует `renderMarkdown` или сломается разбор файла |
| Файла из `guide` нет в `apps/docs/guide/` (только в монорепе)          | Мёртвая ссылка                                             |

Языки трейт берёт из своего списка `en`, `ru`, `uk`, а не из `TranslationsCoverageTest::LOCALES`:
отсутствие файлов на остальных семи языках ошибкой не является.

### 6.3. Маршрут и ключ: `scripts/help-coverage.test.mjs`

Сервер маршрутов панели не знает: они в npm-пакетах. Поэтому вторая половина — тест vitest, он уже
ходит в `scripts/**/*.test.mjs` и идёт после `pnpm build`. Берёт фабрики из `extra.webx.panel.register`
каждого `composer.json`, собирает `routes` из `dist` и падает, если у маршрута нет `meta.help` и он не
в списке исключений либо если для ключа нет `php/packages/*/resources/help/en/<ключ>.md`.

Плюс сторож в `module-admin` — `HelpPackagesCoverageTest`, чтением исходников, как
`SiteBarCoverageTest`: пакет с `$screens->register|extend` обязан иметь `HelpCoverageTest` и
`directory(...)` в провайдере. Без него новый пакет молча вне покрытия.

### 6.4. На полном наборе модулей: `webx:help --check`

Тест пакета не видит поля, которые появляются только при соседе (`notifications.channel` на lab — 17
полей против 6 в описании: каналы добавляют замыканиями). Команда `php artisan webx:help --check`
обходит экраны на реальном сайте и пишет, что не описано. На lab её гоняет этап Х11; проекту она
показывает его собственные поля. Сайт она не роняет.

### 6.5. Исключения

Только списком с причиной, в коде теста. Постоянные:

| Маршрут                               | Причина                                                     |
| ------------------------------------- | ----------------------------------------------------------- |
| `webx.home`, безымянный `/catalog`    | Перенаправление, экрана нет                                 |
| `webx.not-found`                      | Страница ошибки                                             |
| `webx.login`                          | Вход: администратора ещё нет, панели тоже                   |
| `webx.site-bar`                       | Панель на сайте: узкая рамка, у неё своя шапка (`SITE_BAR`) |
| страницы плейграунда (`history-demo`) | Не пакет                                                    |

**Временный список `PENDING`** — как в `AgentDocsCoverageTest`: ключ и причина «наполнение, волна А».
Этап Х5 заносит в него все ключи без файла, каждая волна вычёркивает свои тем же коммитом, что и тексты.
Ключ в списке, у которого файл уже есть, — тоже красный: забытые пункты не копятся. Новый экран в
список не попадает: только справка в том же коммите. После Х10 список пуст и удаляется.

## 8. Правила написания и пример

Читатель — менеджер магазина: он не знает, что такое slug, фасет и индекс, и не обязан. Он открыл
справку, потому что не понял, что будет, если нажать.

1. **Говорим словами экрана.** Поле называем так, как оно подписано в форме, раздел — как в меню.
2. **От последствия, а не от устройства.** Не «флаг `is_purchasable`», а «товар нельзя будет купить».
3. **Что увидит покупатель.** Описание поля отвечает, что изменится на сайте. Если на сайте ничего —
   так и пишем: «покупатель этого не видит».
4. **Предупреждаем о том, что больно.** Сломаются ссылки, пропадёт из поиска, изменится у всех товаров.
5. **Описание — 1–3 предложения**, не повторяет подсказку (§2.6). Раздел `about` — 2–3 предложения.
6. **Сценарий — про задачу, а не про поле.** Заголовок — вопрос «как сделать…», шаги — кнопки и поля
   словами экрана, 3–6 шагов. Минимум один сценарий у каждого экрана, где есть что делать; у формы из
   двух полей его может не быть.
7. **Без внутренних слов:** модуль, спутник, сущность, запись, slug, фасет, кеш, очередь, API, JSON. Без
   названий пакетов и классов. Есть слово панели — берём его: «адрес», «фильтр», «раздел».
8. **Обезличенно.** Примеры — «интернет-магазин запчастей», `@example.com`, `+800 1234 5678`; никаких
   названий клиентов и магазинов. Справка едет в публичном пакете.
9. **Что умеет сайт, то и пишем.** Перед текстом — проверить поведение по спеке модуля и на lab: спутник
   может быть не установлен, поэтому ссылаться на чужой раздел можно, только если он обязателен.
10. **Правишь экран — правишь справку.** Тем же коммитом; это пойдёт в `CLAUDE.md` (§9, этап Х5).

Эталон — `en`, русский и украинский пишутся вместе с ним, на том же этапе. Перевод не дословный: фраза
должна звучать как написанная на этом языке.

**Полный пример:** `php/packages/module-catalog-stock/resources/help/ru/catalog.stock-status-form.md`.

```md
---
title: Статус наличия
guide: catalog#dictionaries-labels-stock-brands
---

# about

Статус наличия говорит покупателю, можно ли получить товар сейчас: «В наличии», «Нет в наличии»,
«Под заказ». Здесь вы задаёте сам статус — как он называется, каким тоном показан и можно ли купить
товар в этом статусе. Сам товар получает статус в своей карточке.

# howto

## Как сделать статус, при котором товар нельзя купить

1. В списке статусов нажмите «Новый статус».
2. Заполните «Название»: например, «Снят с производства».
3. Выключите «Можно купить».
4. Сохраните статус и поставьте его нужным товарам в их карточках.

На сайте вместо кнопки покупки у этих товаров появится название статуса.

## Как поменять статус, который стоит у товаров сам

1. Откройте статус, который должен стоять сам.
2. Включите «По умолчанию» и сохраните. У прежнего статуса этот признак снимется.

Товары, которым статус выбирали вручную, останутся со своим статусом. Новый получат те, кому статус не
выбирали, и все новые товары.

## Как убрать статус из фильтра, не убирая его с сайта

1. Откройте статус и выключите «В фильтре».
2. Сохраните.

У товаров статус виден по-прежнему, но покупатель не сможет выбрать его в фильтре каталога.

# fields

## title

Это слово покупатель видит у товара и в фильтре каталога. Если покупка в этом статусе выключена, оно же
стоит на месте кнопки покупки, поэтому лучше писать коротко и понятно: «Нет в наличии», а не «Статус 3».

## code

Менять код у работающего статуса без нужды не стоит: ссылки на фильтр, которые уже разошлись по
рекламе и закладкам, перестанут выбирать этот статус. Покупатель код видит только в адресе страницы.

## color

Тон подсказывает смысл с первого взгляда: обычно «Успех» у «В наличии» и «Опасность» у «Нет в наличии».
От тона ничего, кроме вида, не зависит. Свой цвет здесь задать нельзя, чтобы «в наличии» выглядело
одинаково на всём сайте.

## is-purchasable

Самый важный переключатель статуса: он решает, появится ли у товара кнопка покупки. Выключайте его
только у статусов, в которых товара действительно нет. Изменение сразу касается всех товаров в этом
статусе.

## is-default

Удобно, когда почти весь каталог в одном статусе: не нужно ставить его каждому товару. Такой статус
всегда один. Его нельзя удалить: сначала сделайте статусом по умолчанию другой.

## is-visible

Выключайте у статуса, по которому покупатели не ищут: например, у служебного «Архив». Порядок статусов
в фильтре — тот, что в списке статусов.
```

>
