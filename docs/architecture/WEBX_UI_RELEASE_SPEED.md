## 1. Канал `next`

Цель — показать правку на хомлабе, не выпуская версию: без version PR, без гейта CI, без тегов.

### Где живёт

Отдельный джоб `next` в **`.github/workflows/release.yml`**, триггер `workflow_dispatch` с
любой ветки. Файл именно этот: Trusted Publishing на npmjs.com привязан к имени файла
воркфлоу (`webx-ui` / `webx-ui` / `release.yml`), а не к ветке — второй файл потребовал бы
второго доверенного издателя на каждом из пятнадцати пакетов. Существующий джоб `release`
получает `if: github.event_name == 'push'`, новый — `if: github.event_name == 'workflow_dispatch'`.

```
gh workflow run release.yml --ref feat/что-то
```

### Что делает

```
checkout ветки → pnpm install → pnpm build
changeset version --snapshot next        # не коммитится, не пушится
changeset publish --tag next --no-git-tag
php-split: каждый php/packages/* и php/site → ветка `next` в webx-ui/<пакет>
```

- **npm.** Dist-tag `next`; `latest` не трогается, тегов в git нет. Нужен
  `"snapshot": { "useCalculatedVersion": true }` в `.changeset/config.json`: без него снапшот
  называется `0.0.0-next-<время>`, и `^0.33.0` у соседей такую версию не примет. С ним —
  `0.33.3-next-20260924123456`.
- **`workspace:^` в снапшоте.** pnpm подставляет версию в момент публикации, то есть
  `^0.33.3-next-…` для пакетов, которые сдвинулись в этом снапшоте, и `^<выпущенная>` для
  остальных — ровно то, что уже лежит в реестре. Ловушка ручной первой публикации (§5 CLAUDE.md,
  «замораживает диапазоны») здесь не срабатывает: снапшот всегда собирается из того же дерева,
  которое публикует. Проверить на первом прогоне: `npm view @webx-ui/module-pages@next dependencies`.
- **Снапшот двигает только пакеты с changeset'ом и их зависимых.** Без changeset'а на ветке
  публиковать нечего — правило то же, что и сейчас.
- **Новый пакет через `next` не выйдет.** Trusted Publishing не создаёт имя (§5), и снапшот
  упадёт тем же 404. Первая версия — по-прежнему руками.
- **Composer.** `scripts/sync-php-version.mjs` на снапшоте **не** запускается: `^0.37.1-next-…`
  Composer не разбирает. Констрейнты между пакетами остаются `^0.37.0`, а сайт просит каждый
  пакет инлайн-алиасом `"dev-next as 0.37.99"` — алиас корня действует и на транзитивные
  требования. В `php-split.yml` — вход `branch` (по умолчанию `main`), который уходит в `branch`
  у `monorepo-split-github-action`; тег на `next` не ставится. Packagist подхватывает ветку тем же
  вебхуком (`dev-next`), с задержкой около минуты.
- **Гейта нет — сознательно.** Сборка обязана пройти, иначе нечего публиковать; остальное —
  опциональный вход `verify: true` (typecheck + test) для тех случаев, когда хочется.

### Сторона сайта

`scripts/packages.mjs` в `webx-cms.local` получает третий режим рядом с `local` и `registry`:

```
node scripts/packages.mjs next
```

- npm: для каждого пакета `npm view @webx-ui/<пакет> dist-tags` → точная версия `next`, если она
  новее `latest`, иначе `latest`. Точная, а не тег: хомлаб должен собирать то, что закоммичено.
  Сравнение с `latest` нужно потому, что `next` не сбрасывается релизом и через неделю указывает
  на старое.
- composer: каждый `webx-ui/*` (включая транзитивные `module-admin`, `routing`, `nested-set`,
  `localization`, `mcp`) — `dev-next as <версия из php/package.json на main>.99`.
- `check` считает `next` допустимым для коммита состоянием (в отличие от `local`), но пишет его
  отдельно, чтобы хомлаб не остался на снапшоте навсегда. Возврат — `registry` после релиза.

### Сколько это занимает

```
dispatch → install+build ~1.5 → publish ~1 → split ~1 (параллельно с npm)   ≈ 3 мин
npm отдаёт версию                                                           ≈ 5 мин
packages.mjs next + сборка + пуш                                            ≈ 5 мин
```

**Около 13 минут против сорока**, из них человек занят только последние пять. Задержка npm
от нас не зависит: пакетный манифест кешируется CDN реестра.

## 2. Сокращение полного цикла

### 2.1. CI параллельно

`ci.yml` делится на джобы, каждый со своей установкой (кеш pnpm делает её трёхсекундной):

| Джоб        | Шаги                                                                          | Оценка   |
| ----------- | ----------------------------------------------------------------------------- | -------- |
| `lint`      | install, проверка сгенерированных токенов\*, `pnpm lint`, `pnpm format:check` | ~1 мин   |
| `typecheck` | install, build, `pnpm typecheck`                                              | ~2.3 мин |
| `test` ×3   | install, build, `vitest run --shard=N/3`                                      | ~2.3 мин |
| `docs`      | install, build, `pnpm docs:build`                                             | ~1.8 мин |

\* проверка токенов смотрит на `packages/tokens/src/generated` после генерации — ей нужен
`generate`, а не весь `build`.

Сборку не передаём артефактом: каждый джоб собирает сам. Упаковка и скачивание `dist` съели бы
выигрыш, а минуты у публичного репозитория бесплатные. Шарды тестов — ради 149 секунд: без них
тест остаётся самым длинным джобом (~3.7 мин).

**Обязательный чек не трогаем.** Ruleset требует контекст `Lint, typecheck, test, build`; его
носит финальный джоб-агрегатор:

```yaml
verify:
  name: Lint, typecheck, test, build
  needs: [lint, typecheck, test, docs]
  if: always()
  runs-on: ubuntu-latest
  steps:
    - run: '[ "${{ contains(needs.*.result, ''failure'') || contains(needs.*.result, ''cancelled'') }}" = false ]'
```

`if: always()` обязателен: без него упавший джоб делает агрегатор `skipped`, а пропущенный
обязательный чек GitHub считает пройденным.

**Итого CI PR: ~2.5 мин вместо 6.5.**

### 2.2. Version PR без ручного approve

Сейчас `changesets/action` пушит ветку `GITHUB_TOKEN`'ом, и CI на ней встаёт в
`action_required`. Токен от GitHub App организации (та же, что у `php-split`:
`vars.PHP_SPLIT_APP_CLIENT_ID` + `secrets.PHP_SPLIT_APP_PRIVATE_KEY`) через
`actions/create-github-app-token`, суженный до `webx-ui` с `contents: write` и
`pull-requests: write`, — и прогон стартует сам.

Право **Pull requests: write** у App выдано и принято в установке организации; автор version
PR — `app/webx-ui-split`. Проверено на первом же релизе после этого (v0.40.0, #280, 24.09.2026):
прогоны встали в `queued` сами, без approve.

### 2.3. Version PR — лёгкий CI

Version PR меняет только версии, `CHANGELOG.md` и констрейнты php. Всё остальное в нём — это
`main`, который уже прошёл CI, и ветка всегда свежая (action пересобирает её с `main`). Поэтому
на `github.head_ref == 'changeset-release/main'` тяжёлые джобы пропускаются, а агрегатор
проверяет то, что version PR действительно может сломать: `pnpm install --frozen-lockfile` и
`pnpm build` (диапазоны `workspace:^`). **~1.5 мин вместо 6.5.**

Это честно только пока `main` зелёный по построению — то есть пока в силе 2.4.

### 2.4. «Ветка отстала» — merge queue

Правило `strict_required_status_checks_policy` держит `main` зелёным: каждый PR проверен поверх
текущего `main`. Цена — «влить `main`, ждать CI заново» руками. Merge queue даёт то же
обещание без человека: PR встаёт в очередь, GitHub сам собирает `main` + PR, гоняет CI и мержит.

- В ruleset `22758520`: правило `merge_queue` (метод `squash`, группа 1–5,
  `check_response_timeout` 15 мин, `ALLGREEN`) вместо `strict` — включено. В очередь ставит
  мутация `enqueuePullRequest`, а не `gh pr merge` (CLAUDE.md §5).
- В `ci.yml`: триггер `merge_group`.
- PHP CI и smoke — не обязательные чеки, в очереди их можно не гонять.

Минус: CI на PR идёт дважды (на PR и в очереди). Плюс: второй прогон никто не ждёт, а два PR,
вставшие в очередь вместе, проверяются одним прогоном.

Альтернатива — просто снять `strict`. Тогда `main` может покраснеть от двух несовместимых PR,
и 2.3 становится неверным: version PR снова должен гонять полный CI. Не рекомендую.

### 2.5. Release без двойной сборки

`release.yml` собирает пакеты шагом `Build packages`, а `publish: pnpm release` — это
`pnpm build && changeset publish`, то есть вторая сборка. И первая нужна только публикации,
а открывает version PR тот же джоб. Шаг `Build packages` убрать: открытие PR — ~30 с вместо
1.5 мин, публикация — на минуту короче. Тегу php сборка не нужна.

### 2.6. Фильтр по путям — не делать

Смотрели: почти каждый PR трогает `packages/`, так что `docs:build` пропускался бы редко. А
PR «только php» JS-половину всё равно задевает — `icons.test.ts` читает
`php/packages/*/{src,config}`, фикстуры плейграунда — `resources/screens` и `lang`. Экономия
редкая, а правило «что от чего зависит» пришлось бы держать руками. Единственное, что можно
сделать дёшево: PHP CI и smoke не гонять на PR без изменений в `php/` — они не на критическом
пути, но освобождают раннеры.

### Полный цикл после 2.1–2.5

```
CI PR (параллельно)                  ~2.5
merge queue (без человека)           ~2.5
Release открывает version PR         ~0.5
лёгкий CI version PR, без approve    ~1.5
мерж → publish                       ~2.5
npm отдаёт версию                    ~5
сайты                                ~5
                                     ≈ 20 мин, из них человек ждёт ~8
```

Против сорока, из которых человек ждал почти всё. Дальше резать можно только auto-merge на
version PR и автоматический бамп манифестов хомлаба — это отдельный разговор (см. ниже).

### Что сделано

- **Test и docs собирают без деклараций:** `WEBX_SKIP_DTS=1` выключает `vite-plugin-dts` в
  `vite.config.ts` каждого пакета. Version PR и релиз собирают полностью.
- **Typecheck — два шарда** на полном прогоне, один — на частичном. Каждый собирает всё

- **Lint and format:** `--cache --cache-strategy content` у ESLint и Prettier, кеш в
  `actions/cache`. Типовых правил ESLint нет, так что неизменившийся файл не может поменять вердикт.
- **PHP CI:** validate, pint и phpstan — только на 8.4 (нижняя поддерживаемая версия — её и

- **PHP smoke** на PR — только когда тронуты `php/**`, сам сценарий или его воркфлоу; push в
  `main` гоняет его всегда.

### Не сделано и почему

- **Параллельный PHPUnit (paratest).** 4:57 → 1:22 локально на 4 процессах — самый большой
  резерв. Но 38 тестов падают: процессы делят один скелет Testbench — `config`, `vite.config`,
  логи, скомпилированные шаблоны, сгенерированные файлы `webx:panel`. Нужна отдельная задача:
  `ParallelTesting::token()` в путях этих тестов, потом paratest в CI.
- **Шарды PHPUnit.** Матрица дала бы имена `(8.4, 1)`, а ruleset требует `(8.4)` и `(8.5)`;
  сначала ruleset, потом шарды — или сразу paratest.
- **Кеш `dist` между прогонами.** Ключ по исходникам всех пакетов промахивается на любой правке
  в `packages/`, а пакетный кеш — это свой turbo. Не стоит выигрыша после `WEBX_SKIP_DTS`.

## Открытые вопросы

1. **Auto-merge version PR.** С 2.2 и 2.3 его можно включать тем же воркфлоу, и тогда релиз
   уходит сам через ~2 минуты после мержа PR с changeset'ом. Но version PR — это единственная
   кнопка «выпускаем», и с каналом `next` она как раз и нужна: итерации идут в `next`, выпуск —
   осознанно. Предлагаю не включать.
2. **Хомлаб сам.** Ночной прогон не привозит релиз (§5): манифесты закоммичены. Можно, чтобы
   `release.yml` после публикации слал `repository_dispatch` в Gitea-репозиторий, а тот делал
   `packages.mjs registry` + коммит. Это ещё минус пять человеческих минут, но это вторая
   сторона и второй секрет. Позже.
3. **Снапшот с `main`.** Снапшот с `main` вместо feature-ветки допустим и полезен
   («показать, что уже смержено, не выпуская»). Ограничений нет, только привычка.
