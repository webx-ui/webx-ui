# WebX UI — скорость выпуска

Сколько идёт релиз от открытия PR ветки дня до версии на Packagist — замеры по меткам GitHub.
Сам порядок релиза — `WEBX_UI_PHP_RELEASE.md`, ловушки — `../pitfalls/release-and-ci.md`. Прежняя
версия этой спеки (план ускорения #278, замер CI по джобам 02.10.2026) — в git до #484.

## Как мерить

Метки берутся у GitHub, не на глаз:

- PR — `gh pr view <N> --json createdAt,mergedAt`; постановка в очередь — событие
  `AddedToMergeQueueEvent` в `timelineItems` (graphql);
- CI PR — `completedAt` чеков из `gh pr checks <N> --json name,completedAt,bucket`: агрегатор
  `Lint, typecheck, test, build` и последний из чеков (обычно `PHP lint, analyse, test (8.4)`);
- очередь — прогоны `gh run list --event merge_group` с `headSha` записи очереди;
- `release.yml` — `gh run view <id> --json jobs`: «Version or publish» (тег `php-v*` и npm) и
  `Publish PHP packages / Split *` (зеркала с тегом `v*`);
- Packagist — опрос `repo.packagist.org/p2/webx-ui/<пакет>.json` раз в 15 с после конца сплита;
  поле `time` версии — дата коммита, а не момент появления, им не мерить.

## Что видно

- План #278 обещал ≈20 минут, выходит 43–49. Дорога не JS-половина — агрегатор зеленеет за 2–4
  минуты, — а **PHP CI**: на PR ветки он гонит затронутое (4–6 мин), а на version PR и в его
  очереди — весь набор, потому что релиз меняет `composer.json` всех пакетов (шаг `Test` 7:17 на
  PR, ~10 мин в очереди). Это 20 из 43 минут вечернего релиза.
- Очередь гоняет тот же полный PHP CI второй раз поверх того же дерева: у version PR база не
  менялась, а прогон снова идёт ~10 минут. После зелёной очереди GitHub ещё
  ~2 минуты не мержит (17:04:05 → 17:06:09).
- Мерж version PR запускает на `main` сразу CI, PHP CI, Docs, smoke, push-сплит и Release;
  «Version or publish» вечером ждал раннера 3.5 минуты.
- Packagist быстрый: вебхук срабатывает за секунды после сплита.

Куда резать: PHP CI на `changeset-release/main` — как и JS, лёгкий путь (версии в `composer.json`
поменял скрипт, код тот же, что уже прошёл очередь); и очередь без повторного PHP CI для version
PR. Оба хода снимают ~15 минут.

## Лёгкий PHP CI релизного PR (webx-ui#37)

Сделано так: `php-ci.yml` спрашивает `scripts/release-pr.mjs`, и релизный PR — а в очереди группа
из одного релизного PR — идёт лёгким путём того же джоба: `composer validate` манифестов и
`php/site`, проверка, что `sync-php-version.mjs` ничего не меняет. Без pint, phpstan и phpunit:
код тот же, что прошёл очередь PR ветки дня. Обязательные чеки `PHP lint, analyse, test (8.4/8.5)`
отчитываются зелёным (8.5 на лёгком пути шагов не делает).

Признак релизного PR — ветка `changeset-release/main` **и** App (`webx-ui-split[bot]`) как автор PR и
актор прогона; в очереди — каждый сквош группы между `base_sha` и головой называет такой PR.
Дифф-защита: в изменении только `composer.json`, `package.json`, `CHANGELOG.md`, `.changeset/**`,
lock-файлы — иначе полный прогон. Всё недоказанное (нет диффа, не читается API, группа не
сходится) — тоже полный прогон. Ловушка — `../pitfalls/release-and-ci.md`.

Ожидание: «version PR → все чеки зелёные» ≈ агрегатор (~3:30) вместо 10–11 минут, «очередь
version PR → мерж» ≈ 4–5 вместо 8–12; итог ≈ 28–30 минут вместо 43.

**Замер — на ближайшем вечернем релизе**, по разделу «Как мерить»: добавить столбец в таблицу
выше. Сверх обычного — проверить в логах прогонов PHP CI version PR и его `merge_group`, что шаг
«Choose the path» напечатал `PHP CI path: light` (на PR ветки дня — `full` или `none`), и
длительность джобов `PHP lint, analyse, test (8.4)` (`gh run view <id> --json jobs`).

## Гейт этапа и гейт релиза (webx-ui#79)

Этап делается минуты, а полный гейт идёт ~20 минут (PHP ~5400 тестов, JS ~3200), и приёмщик
гонял его повторно. С 27.10.2026 гейтов два, и оба — одной командой `pnpm gate:affected`
(`scripts/gate-affected.mjs`):

- **Этап — `pnpm gate:affected <BASE>`**, `BASE` — `git rev-parse HEAD` до первой правки, он же
  в отчёте. Выбор делает `scripts/affected.mjs <BASE>` — тот же, по которому решает CI; скрипт
  гейта правил графа не дублирует, а повторяет шаги воркфлоу для его ответа:
  - всегда: `check-names` (дерево и сообщения `BASE..HEAD`), eslint и prettier по изменённым
    файлам (CI гоняет всё дерево с кешем по содержимому — вердикт тот же); при `node=all` —
    eslint по всему дереву и проверка сгенерированных токенов;
  - JS при `node≠none`: `pnpm build`, typecheck проектов `@webx-ui/*` из `node_filters`,
    `pnpm test <node_tests>` (весь `pnpm test` при `all`); `pnpm docs:build` при `docs=true`;
  - PHP при `php≠none` (из `php/`): `composer validate` манифестов, pint, phpstan
    (`-d memory_limit=-1`), `phpunit <php_tests>` напрямую, без таймаута composer;
  - `manticore=true` — как джоба CI «PHP on Manticore»: настоящий сервер (общий Manticore devbox,
    таблицы под своим префиксом) и `--fail-on-skipped`.
    Незатронутая половина печатается строкой «skipped: not affected». Шаги идут по очереди
    (параллельно упираются в память), первый красный останавливает прогон, в конце — сводка: шаг,
    время, итог. Отличия от CI: один PHP (CI ещё 8.5) и без шардов.
- **Релиз дня — `pnpm gate:affected --full`**: всё, как CLAUDE.md §5, один раз перед PR. Приёмщик
  этапа полный гейт не перезапускает — сверяет хеш, вывод `affected.mjs <BASE>` и итог отчёта.

## Прогоны без повторов (webx-ui#33)

Сделано так:

- **CI и PHP CI не слушают `push: main`.** В `main` попадает дерево группы очереди, которое оба
  воркфлоу уже проверили; повторный прогон (~2 × 10 минут на мерж) ничего не доказывал, а раннер
  отнимал — Release ждал его 3,5 минуты. От прогона CI на `main` ничего не зависит
  (`workflow_run` нигде нет; бейдж README показывает последний прогон ветки по умолчанию — им
  теперь будет ночной). Остались `pull_request`, `merge_group`, `schedule` (03:00 UTC) и
  `workflow_dispatch`.
- **JS CI релизного PR и его очереди — лёгкий путь на `scripts/release-pr.mjs`.** Тот же признак,
  что у PHP CI: джоба «What the change reaches» отдаёт `light`, и при `true` вместо lint,
  typecheck, тестов, доков и Manticore идёт одна джоба «Version PR installs and builds»
  (`install --frozen-lockfile`, `build`, prettier по изменённым файлам). Раньше признаком был
  `github.head_ref`, а в `merge_group` он пустой — очередь релизного PR гоняла полный гейт.
  Обязательные чеки (агрегатор `Lint, typecheck, test, build` и `No client names`) отчитываются
  как всегда.
- **Smoke — ночью в 04:00 UTC** (на час позже CI, чтобы не делить раннеры) и вручную; PR,
  трогающие `php/**`, гоняют его как раньше.
- **Smoke не идёт у version PR.** На 0.83.0 релизный PR #503 шёл от открытия до зелёных чеков
  6:36, и последним был smoke (`pull_request` по `paths`: релиз меняет все `composer.json`), хотя
  тот же код прошёл его в PR ветки дня. Теперь джоба «Is it the version PR» в `php-smoke.yml`
  спрашивает `scripts/release-pr.mjs` (тот же признак и env), и при `light=true` джоба smoke
  пропускается целиком: в ruleset'е обязательны только агрегатор JS CI и два PHP CI, так что
  пустой зелёный прогон не нужен. В очереди мержа smoke не гонялся и раньше — `merge_group` в его
  `on:` нет (у #503 в очереди только CI и PHP CI, прогон 39579050008).

Схема прогонов на один релиз: PR ветки дня — полный (затронутое) CI и PHP CI, его очередь — так
же; version PR и его очередь — лёгкие CI (~2 мин) и PHP CI (~20 с), smoke пропущен; мерж — только Release, сплит
и Docs. Ожидание: JS CI в очереди version PR держится около минуты (21.10 — 1:02 против 3:56 в
очереди PR дня), без `push: main` Release не ждёт раннера.

**Проверить на ближайшем релизе:** `gh run list --workflow ci.yml` и `--workflow php-ci.yml` — ни
одного прогона с `event=push`; JS CI version PR и его `merge_group` ≈ 2 минуты, в логе «Is it the
version PR» — `light=true`; у PR ветки дня — `light=false` и полный набор джобов; ожидание раннера
у «Version or publish» (разница `createdAt` прогона и `startedAt` джоба); PHP smoke version PR —
`light=true` и джоба smoke skipped, у PR ветки дня — smoke как раньше.

### Замер 21.10 вечер (0.84.0, #504/#505)

Первый релиз, где работают и #37, и #33. Пути сошлись с ожиданием:

- **`push: main` нет:** последние прогоны `ci.yml` и `php-ci.yml` с `event=push` — 09:43 (мерж
  #503, до #33). На мержах #504 и #505 на `main` шли только Release, PHP split и Docs.
- **PR ветки дня #504 и его очередь — полные:** CI, PHP CI и smoke — `light=false`
  (`reason=changes more than versions: …`), `PHP CI path: full`; джоб `PHP lint, analyse, test
(8.4)` 11:40 на PR и 11:08 в очереди, smoke «Install into a real Laravel app» 5:17.
- **Version PR #505 — лёгкий:** CI `light=true` (`reason=the version PR, versions only`), одна
  джоба «Version PR installs and builds» 2:48; PHP CI `PHP CI path: light`, 0:21; smoke —
  `light=true`, джоба skipped. Его очередь: CI `light=true` (`reason=a group of the version PR
alone, versions only`), «Version PR installs and builds» 2:51; PHP CI light, 0:20.
- Release не ждал раннера (0:03); «Version or publish» 3:05 — npm публиковал четыре пакета
  (`module-blocks` minor, `module-pages`, `module-blog`, `module-services` патчем).

Итог **42:07 против 33:23** утром, хотя сторона version PR — лучший замер:

- **Сторона version PR** (открыт → мерж) — **8:04** против 8:37; «все чеки зелёные» — **3:37**
  вместо 6:36 (цель — меньше 6:36 — достигнута): последним теперь отчитывается агрегатор JS, а не
  smoke.
- **Сторона PR ветки дня** (открыт → мерж) — 23:58 против 19:24: в ветке большой `php/**` (схемы
  блоков в `module-blocks`, `module-admin`, `themes`), полный PHP CI 8.4 шёл ~11 минут дважды.
  Это свойство ветки и защита, её не режем.
- **Packagist** отдал версию через 3:36–5:10 после сплита против секунд раньше — +4 минуты к итогу
  не от нас.

Без двух последних эффектов (PR дня как 20.10 вечером, Packagist за секунды) релиз шёл бы ≈26
минут.

**Что теперь узкое место.** Полный PHP CI PR ветки дня и его очереди — ~23 из 42 минут; это
защита. Из того, что режется: лёгкий JS CI version PR держит «Version PR installs and builds» —
`install --frozen-lockfile` и полная сборка ~2:50, дважды (PR и очередь), ≈5:40 на релиз, а не
«~1 минута», как ждали: сборка всех пакетов и есть почти весь лёгкий путь. Следующий ход —
собирать в нём только пакеты, чьи версии поменял релиз, или кешировать `dist` по дереву исходников.
