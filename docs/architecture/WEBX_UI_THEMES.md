# Темы сайта — спецификация

Статус: первая часть выпущена (TH1–TH6: движок, `theme-default`, модули в теме, иконки, ассеты,
слова, шрифты, письма, пакетная тема); впереди — репетиция с агентом (§18.6), темы магазинов и
вторая часть — каталог тем и сайты по подписке (§21). Пакеты — `webx-ui/themes` и
`webx-ui/theme-default` (§3), правки в `module-admin` (§14), `module-blocks` (§8, §9) и в модулях с
публичными страницами (§10). Соседние спеки: новый сайт —
[`WEBX_UI_NEW_SITE.md`](WEBX_UI_NEW_SITE.md), блоки — [`WEBX_UI_MODULE_BLOCKS.md`](WEBX_UI_MODULE_BLOCKS.md),
зоны — [`WEBX_UI_LAYOUT_REGIONS.md`](WEBX_UI_LAYOUT_REGIONS.md), виджеты —
[`WEBX_UI_WIDGETS.md`](WEBX_UI_WIDGETS.md). Гайды: `apps/docs/guide/themes.md` («Site themes»),
`apps/docs/guide/styles.md`, `apps/docs/guide/languages.md`.

Без темы вид сайта — файлы самого сайта: `layout.blade.php`, `app.css`, шапка и подвал, плюс типы
блоков в базе. На деле это кончается одним стилевым файлом на тысячи строк, где стили блоков,
оболочки и страниц модулей перемешаны и держатся на буквальных цветах; и второй сайт «как первый,
только другого цвета» — копия первого, которая с первого дня живёт своей жизнью.

Ответ — **тема**: набор файлов, устроенный по одним правилам (§4, §6), который сайт не копирует, а
надстраивает. Слоями:

```
theme/                      ← локальная тема сайта: только его отличия
  → webx-ui/theme-default   ← тема по умолчанию: оболочка, токены, универсальные блоки
    → модули                ← вид своих страниц и свои блоки (§10)
```

Новый сайт получает `theme/` на `theme-default` сразу при `webx:setup` и открывается уже
оформленным. Дальше вид сайта — это правка `theme/` под его стиль: токены, оболочка, свои блоки.
Исправления `theme-default` и модулей приходят `composer update`, как исправления модулей.
Вид сайта целиком — файлы темы в git: из панели его не правят (§2, решение 12).

Всё публичное: движок, тема по умолчанию, гайд и заготовка для агентов. Каталог готовых тем и
сайты по подписке строятся поверх того же механизма (§21): удачная локальная тема выносится
в пакет одной командой.

## 1. Границы

**Внутри (первая часть):**

- движок `webx-ui/themes`: цепочка слоёв, словарь токенов, проверки, sync, команды (§3, §7, §8);
- `webx-ui/theme-default`: оболочка, токены, универсальные блоки (§12); интерактивное — пакет виджетов (§11);
- устройство темы и манифест (§4, §5); где лежит какой стиль (§6);
- модули как нижний слой: вид своих страниц, свои блоки, точки расширения (§10);
- иконки и ассеты (§13); демо, языки, шрифты (§15);
- новый сайт с локальной темой, цикл разработки, вынос и отвязка (§14);
- документация для агентов и заготовка новой темы (§16);
- шов «состояние сайта» в панели (§20) — он нужен второй части, но живёт в публичном
  `module-admin` и ни от чего здесь не зависит.

**Вторая часть (§21):** каталог тем и галерея, пакеты контента по нишам, сайты по подписке и парк
сайтов, приватные пакеты — если понадобятся.

**Снаружи:**

- **Темы магазинов.** Механизм §10 для каталога описан, но вид витрины в `theme-default` и
  проверка на настоящем магазине — после того как оттестированы модули магазина.
- **Многосайтовость.** Тема здесь — одна цепочка на установку. Спека
  [`WEBX_UI_MULTISITE.md`](WEBX_UI_MULTISITE.md) (§7 там) проектирует тему как каталог вьюх на сайт
  внутри одной установки; когда до неё дойдёт, цепочка из этой спеки станет источником того
  каталога, а не вторым механизмом.
- **Смена темы на живом сайте** — отложено (§22).

## 2. Принятые решения (не переоткрывать)

1. **Тема — слой, а не копия.** Сайт надстраивает тему и перекрывает только своё (§7.1). Копия «на
   старте» отвергнута: исправление в теме не доедет ни до одного сайта, который её уже скопировал.
   Копия остаётся осознанным шагом — `webx:theme:eject` (§14.3).
2. **Каждый новый сайт — со своей локальной темой.** `webx:setup` кладёт `theme/` на
   `theme-default`, потому что тема по умолчанию сразу переписывается под стиль сайта, и этой
   правке нужно место, которое не затрёт обновление. Сайт без темы — флаг `--no-theme`.
3. **Движок и тема по умолчанию — разные пакеты.** Движок знает механизм и словарь, тема по
   умолчанию — обычный его потребитель, ровно как будущие каталожные темы. Выходят одной общей
   версией composer-пакетов, лишней работы с релизом нет.
4. **Модуль отвечает за вид своих страниц сам.** Тема по умолчанию не знает ни услуг, ни команды,
   ни каталога: модуль несёт вьюхи, базовый CSS на токенах и свои блоки (§10). Тема перекрывает,
   если хочет. Иначе каждый новый модуль — правка темы по умолчанию, а модуль, которого в ней
   забыли, выглядит голой разметкой.
5. **Блок модуля ставится один раз и дальше принадлежит сайту** (`BlockOffers`, §10.3):
   модуль предлагает простой блок — список записей и пара полей, — сайт его берёт и правит под себя.
6. **CSS знает только токены сайта.** Как компоненты ядра знают только `--wx-*`. Цвет или шрифт,
   написанный буквально, не перекрашивается пресетом — и тихо перестаёт работать на половине
   страницы (§8). Это касается и CSS модулей.
7. **Словарь токенов — в движке и общий для всех.** `--site-color-accent` значит одно и то же в
   любой теме и в любом модуле: модуль может написать базовый вид, не зная, какая тема стоит.
8. **У каждого стиля одно место** (§6). Второго общего файла на тысячи строк не будет, потому что
   ему некуда встать.
9. **Интерактивное — в пакете виджетов, а не в теме и не в модуле.** Слайдер, лайтбокс, видео,
   карта, согласие на cookie, меню, диалог, вкладки — один пакет `webx-ui/widgets` (§11): логика
   готова, вид — каркас на токенах, который тема перекрашивает. Модуль, которому нужен слайдер, не
   тащит свой. Движок тем остаётся без JavaScript.
10. **Типы блоков из пакетов — у пакетов, содержимое — у сайта.** Типы темы обновляются из пакета
    (§9); страницы, меню, зоны, тексты сеются один раз и дальше принадлежат сайту (§15).
11. **Шрифты — свои файлы, не внешний CDN.** Сторонний запрос шрифта на каждой странице — передача
    IP посетителя третьей стороне, и для сайтов в ЕС это вопрос согласия (§15.3).
12. **Вид сайта — в git, панель его не правит.** Сайт собирают под его тему, и все её параметры —
    токены, пресет, шрифты — лежат в `theme/` под git. Ни правки токенов, ни выбора пресета в
    панели нет: клиент с таким переключателем ломает вёрстку и контраст, а значение из базы стоит
    выше `theme/` и молча перекрывает то, что агент правит в `tokens.json`, — git и
    `webx:theme:check` этого не видят. Пресет выбирает автор темы ключом `preset` манифеста (§5);
    логотип и название сайта — слова, а не вид, и остаются в настройках.

## 3. Пакеты и роли

| Роль                  | Где                     | Что несёт                                                                                                            |
| --------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Движок**            | `webx-ui/themes`        | цепочка, словарь токенов, слияние, проверки, sync, команды, заготовка, `ThemeContract`, гайд для агентов             |
| **Тема по умолчанию** | `webx-ui/theme-default` | оболочка, значения токенов и пресеты, типографика, универсальные блоки, вид виджетов, иконки, шрифты, письма, ошибки |
| **Локальная тема**    | `theme/` в сайте        | отличия сайта: токены, оболочка, свои блоки, перекрытия                                                              |
| **Модуль**            | `webx-ui/module-*`      | вьюхи своих страниц, базовый CSS на токенах, предложенные блоки, точки расширения (§10)                              |

**`webx-ui/themes`** — библиотека без префикса `module-`: тема рисуется без панели и панелью не
правится (§2, решение 12). Namespace `WebxUi\Themes`, таблиц и JavaScript нет:

- `ThemeManifest`, `ThemeLocator`, `ThemeChain` — манифест, поиск темы по имени или каталогу,
  цепочка (§5, §7.1);
- `ThemeServiceProvider` — пути вьюх, `@webxTheme`, `theme_asset()`, `theme_token()`,
  `theme_active()`, `<x-theme::icon>`, страницы ошибок и слова `theme::` по цепочке;
- `Vocabulary`, `Tokens` — словарь и слияние значений (§7);
- `Checks\*` — проверки `webx:theme:check` (§8, §17);
- команды `webx:theme:sync`, `check`, `show`, `make`, `eject`, `extract` (§17);
- `Testing\ThemeContract`, `Testing\ModuleThemeContract` (§18); `AGENTS.md`, `RULES.md` и
  `stubs/` заготовки (§16).

**`webx-ui/theme-default`** — composer-пакет `"type": "webx-theme"`, устроенный по §4, без
PHP-классов и провайдера: движок находит его через `InstalledVersions`, как любую тему. Задача — не
быть красивым, а быть **хорошей отправной точкой**: аккуратная нейтральная типографика, сетка,
оболочка, которую не стыдно показать в первый день, и ясный код, который удобно переписать.

## 4. Устройство темы

Одинаковое у `theme-default`, локальной темы и любой будущей. Каталогов, которых нет, просто нет.

```
theme/
├── composer.json          ← манифест (§5); у локальной темы — theme.json с тем же содержимым
├── tokens.json            ← значения токенов и пресеты (§7)
│
├── views/                 ← Blade
│   ├── components/        ← layout, header, footer, общие куски оболочки
│   ├── vendor/<ns>/       ← перекрытия вьюх модулей: vendor/webx-pages/show.blade.php …
│   ├── parts/             ← вьюхи на точки расширения модулей (§10.4)
│   ├── mail/              ← письма (§7.5)
│   └── errors/            ← 404, 500, suspended
│
├── blocks/*.json          ← типы блоков: схема, шаблон, СВОЙ CSS, свой скрипт (§9)
├── regions/*.json         ← стартовые шапка и подвал деревьями блоков (§15.1)
│
├── src/
│   ├── css/               ← оболочка, сетка, типографика, перекрытия вида модулей (§6)
│   └── js/                ← то, что живёт вне блоков и не является виджетом (§11)
├── icons/*.svg            ← иконки (§13.1)
├── assets/
│   ├── fonts/             ← файлы шрифтов (§15.3)
│   └── img/               ← фоны, декор, заглушки
├── dist/                  ← у пакета: собранные theme.css, theme.js и sources.json
│
├── lang/<locale>/theme.php ← слова вёрстки (§15.2)
├── demo/<module>/*.json   ← демо-содержимое, если тема несёт своё (§15.1)
├── preview/               ← обложка и скриншоты
└── tests/ThemeTest.php    ← use ThemeContract (§18)
```

`src/` и сборка (Vite) живут там, где лежит тема. У пакета `dist/` **закоммичен** и входит в
выпущенную версию — сайту Node для пакетной темы не нужен; сплит зеркалит дерево git, и сборка в
нём была бы вторым конвейером, которому доверять сложнее, чем тесту. Сборка пишет
`dist/sources.json` — хеш каждого файла `src/`, — и `ThemeContract` падает, если `src/` правили без
сборки. У локальной темы `src/` собирает сам сайт, тем же `npm run build`, что уже есть в скелете.

## 5. Манифест

```json
{
  "name": "webx-ui/theme-default",
  "type": "webx-theme",
  "extra": {
    "webx": {
      "theme": {
        "title": "Default",
        "uses": [],
        "requires": ["module-pages", "module-blocks", "module-menu", "module-inbox"],
        "locales": ["en", "ru", "uk", "de", "pl", "fr", "es", "it", "pt", "tr"],
        "fonts": [
          {
            "family": "Inter",
            "weight": "100 900",
            "style": "normal",
            "files": {
              "latin": "fonts/inter-latin.woff2",
              "latin-ext": "fonts/inter-latin-ext.woff2",
              "cyrillic": "fonts/inter-cyrillic.woff2"
            }
          }
        ]
      }
    }
  }
}
```

| Ключ       | Смысл                                                                                                                                                                                                                                  |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`    | как тема называется                                                                                                                                                                                                                    |
| `uses`     | на чём стоит; у локальной темы нового сайта — `["webx-ui/theme-default"]`                                                                                                                                                              |
| `requires` | модули, без которых тема не рисуется; складываются по цепочке; `webx:doctor` ругается на нехватку                                                                                                                                      |
| `locales`  | на каких языках есть слова вёрстки и демо; проверка держит их полными (§15.2)                                                                                                                                                          |
| `preset`   | в каком пресете рисуется сайт (§7.3); решает верхний слой, который его назвал; неизвестное имя — ошибка                                                                                                                                |
| `settings` | какие вкладки настроек сайта тема печатает: `{"contacts": ["phones", "emails"]}`; вкладку решает ближайший к сайту слой, который её назвал — свой список наследника заменяет родительский, без объявления наследуется; `{}` — ни одной |
| `fonts`    | грани шрифта: семейство, вес, стиль и файл на каждую письменность — ключ `files` (§15.3)                                                                                                                                               |

Остальное — по соглашению из §4: есть `views/` — это вьюхи, есть `blocks/` — это блоки. Ключ,
который повторяет имя каталога, — второе место для ошибки, а не гибкость. Пакет в `uses`, у которого
тип не `webx-theme`, — ошибка, а не тихий пропуск; неизвестные ключи манифест не читает.

Локальная тема держит то же самое в `theme/theme.json` (ключ `theme` на верхнем уровне): у неё нет
своего `composer.json`, и заводить его ради манифеста незачем.

## 6. Где лежит какой стиль

| Что                                                    | Где                                                     |
| ------------------------------------------------------ | ------------------------------------------------------- |
| Цвет, шрифт, радиус, отступ, тень — значения           | `tokens.json`, и больше нигде буквально                 |
| Вид **одного блока**                                   | в самом блоке, под `.b-<slug>`                          |
| Оболочка: шапка, подвал, сетка, контейнер              | `src/css` темы                                          |
| Типографика текста (`h1`–`h6`, списки, цитаты в прозе) | `src/css` темы по умолчанию; локальная перекрывает      |
| Базовый вид страниц модуля (статья, услуга, товар)     | CSS модуля на его классах (§10.2)                       |
| Свой вид страниц модуля на этом сайте                  | `src/css` темы, на тех же классах; или перекрытая вьюха |
| Вид виджета (стрелки слайдера, баннер cookie)          | `src/css` темы на классах `webx-<виджет>-*` (§11)       |
| Поведение блока                                        | скрипт блока — по контракту входа (§10 спеки блоков)    |
| Слайдер, лайтбокс, меню, диалог, согласие              | пакет виджетов (§11); тема только оформляет             |

Правило проверки: если стиль описывает один тип блока, ему место в блоке, и `webx:theme:check`
предупреждает о селекторе `.b-<slug>` в `src/css`. Всё, что в таблице, подчиняется проверке на
токены (§8).

CSS `theme-default` пишет каждый селектор внутри `:where()` — нулевая специфичность: локальная
тема, модуль или блок перекрывают правило тем, что написали его, без `!important` и без копии
селектора. Колонка `<main>` стоит на `margin-inline: auto`, а не на `padding`, поэтому классу модуля
у прямого ребёнка `<main>` — только `margin-block`: `margin: 0` уводит его к краю окна. Проза темы
(`.site-main`, `.site-prose`): всё, что ставит фон (`code`, `pre`, `th`, `mark`), ставит и цвет
текста; приглушённый цвет `blockquote`, `figcaption`, `small` — только вне блоков, внутри — если
блок сам пометил содержимое `site-prose`.

## 7. Токены сайта

### 7.1 Цепочка слоёв

```
сайт        resources/views
локальная   theme/
по умолч.   vendor/webx-ui/theme-default
модули      vendor/webx-ui/module-*
```

| Что    | Как складывается                                                                               |
| ------ | ---------------------------------------------------------------------------------------------- |
| Вьюхи  | ищутся сверху вниз, первая найденная побеждает                                                 |
| CSS    | подключается снизу вверх: модули → тема по умолчанию → локальная; верхний перекрывает каскадом |
| JS     | виджеты по требованию (§11), потом снизу вверх `dist/theme.js` слоёв                           |
| Токены | значения сливаются снизу вверх: тема по умолчанию → локальная → пресет                         |
| Блоки  | тип верхнего слоя перекрывает тип нижнего с тем же slug (§9)                                   |
| Иконки | спрайты сливаются по имени, верхний слой побеждает                                             |
| Слова  | `theme::` ищется сверху вниз по ключу                                                          |
| Демо   | первый слой сверху, у которого есть файл в `demo/<module>/`, побеждает (§15.1)                 |

Цепочка любой длины: «тема на основе темы» — та же цепочка на слой длиннее; общая база одна и под
всеми («ромб»), первая из `uses` выше соседей. Цикл в `uses` или ненайденная тема — `ThemeException`
при загрузке, и в консоли тоже: сайт с испорченным `webx-themes.theme` (`WEBX_THEME`) не запустит и
`artisan` — это лучше, чем сайт, молча потерявший слой. `webx-themes.theme` — путь к локальной теме
(`'theme'`) или имя пакета; пусто — тем нет, провайдер не трогает пути.

**Порядок вьюх.** Общий путь — `View::addLocation()` для каждого слоя **после** `resources/views`,
в порядке цепочки. Пространства имён модулей тоньше: Laravel кладёт `resources/views/vendor/<ns>`
первым при `loadViewsFrom()` модуля; `prependNamespace()` слоя поставил бы его **перед** сайтом.
Поэтому провайдер перестраивает подсказки пространства целиком —
`[сайт, локальная, по умолчанию, ...пути модуля]` через `View::replaceNamespace()`, и делает это в
`$app->booted()`, а не в `boot()`: порядок провайдеров зависит от Composer, а `booted` видит все
пространства при любом. Тест — на все уровни, иначе перепутанный порядок молча отдаёт вьюху модуля
вместо темы.

Конфиг модулей (`webx-pages.layout`, `webx-catalog.layout`, `webx-blocks.layout`) **не меняется**:
он называет компонент `'layout'`, а какой файл за ним — решает порядок поиска. `<x-dynamic-component>`
и `FileViewFinder` кешируют разрешённые имена на процесс; с одной цепочкой на установку это
безвредно — пути ставятся при загрузке и больше не меняются.

Что верх цепочки обязан дать, чтобы сайт открылся: `components/layout.blade.php` с `@webxTheme`,
`@webxSeo`, `@webxBlocks` и зонами `header`/`footer`. У `theme-default` он есть; локальная тема его
наследует, пока не перекроет. `@webxSeo` и `@webxBlocks` лэйаут печатает, только если слота `head`
нет: вьюхи модулей кладут обе директивы в слот, а ни одна не идемпотентна.

**Страницы ошибок и слова — тоже по цепочке.** Laravel ищет `errors::<код>` в пространстве из
`config('view.paths')`, куда слои не попадают, поэтому движок встаёт в обработчик
(`ErrorPages`, `renderable` на `HttpExceptionInterface`): HTML-запросу отдаётся `errors.<код>`,
найденный обычным порядком вьюх; нет вьюхи, JSON или вьюха упала — дальше Laravel, статус тот же.
Laravel даёт пространству `theme::` один каталог, поэтому загрузчик переводов обёрнут (`ThemeLines`):
`lang/` слоёв снизу вверх, сверху — `lang/vendor/theme/` сайта.

### 7.2 Словарь

Словарь — в движке, один на всех: темы, модули, блоки (`Vocabulary::base()`, сорок токенов):

| Группа   | Токены                                                                                                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Цвет     | `color-bg`, `color-surface`, `color-surface-muted`, `color-text`, `color-text-muted`, `color-border`, `color-accent`, `color-accent-contrast`, `color-accent-2`, `color-highlight`, `color-danger`, `color-success` |
| Шрифт    | `font-body`, `font-heading`, `font-size-base`, `line-height-base`, `font-size-1` … `font-size-6`                                                                                                                    |
| Шкала    | `space-1` … `space-8`, `radius-sm`, `radius-md`, `radius-lg`, `radius-full`                                                                                                                                         |
| Глубина  | `shadow-sm`, `shadow-md`                                                                                                                                                                                            |
| Сетка    | `container-width`, `gutter`                                                                                                                                                                                         |
| Движение | `duration`, `easing`                                                                                                                                                                                                |

На странице это `--site-<имя>`. Цвета — **роли, а не оттенки**: у корпоративного сайта бренд — три-пять
цветов, и словарь из одного акцента кончается тем, что тема заводит `--site-olive`, а блоки перестают
переноситься. Поэтому `accent`, `accent-2`, `highlight`, `surface-muted` — и у каждой темы своё
значение.

Типы значений — `color`, `length`, `font`, `shadow`, `number`, `time`, `easing`. Проверка — список
разрешённых форм на тип плюс общий второй замок: нет `<`, `>`, `;`, фигурных скобок, `\`, `@`, `!`,
`/*`, `url(`, управляющих символов, скобки сбалансированы, не длиннее 200 символов. Ссылка на
другой токен сайта — `var(--site-…)` — годится любому типу; на `--wx-*` — нет.

Тема **может** расширить словарь своими токенами — ключом `vocabulary` в `tokens.json` (`имя → тип`).
Блоки этой темы их видят; модули и блоки `theme-default` — нет. Имя движка объявить заново нельзя
даже тем же типом; два слоя могут объявить одно имя, если сходятся в типе. Расширение словаря в
движке — обычное изменение пакета с changeset'ом; удаление токена — ломающее.

`theme-default` **обязана** дать значение каждому токену словаря (тест, §18); любая тема выше — нет:
недостающее берётся снизу.

Почему не `--wx-*`: это токены панели, на публичный сайт они не грузятся, и у них другая жизнь —
шкала панели меняется по нуждам панели, а сайты от этого перекрашиваться не должны.

**Три префикса, и каждый — своё.** Бренд в имени не нужен, а префикс, который говорит, чьё
значение, — нужен. Агент, который заводит четвёртый или путает эти три, ломает проверку §8 — она
различает их по префиксу:

| Префикс    | Что это                                                       | Кто задаёт значение                  | Правило                                                                                |
| ---------- | ------------------------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------- |
| `--site-*` | токен сайта из словаря (§7.2)                                 | `tokens.json` слоёв и пресет         | только имена словаря цепочки, без запасного значения; новое имя — в `vocabulary` темы  |
| `--webx-*` | своя переменная пакета: виджета, модуля (`--webx-slider-gap`) | сам пакет, на `--site-*`             | объявить в своём CSS; тема перекрывает её, чтобы настроить один виджет, а не весь сайт |
| `--wx-*`   | токен панели и компонентов ядра (`@webx-ui/tokens`)           | `@webx-ui/tokens`; ребрендинг панели | **никогда на публичном сайте** — там его нет, `var(--wx-…)` молча пустой               |

Своя переменная блока (`--team-columns`, ставится инлайном из поля) — не токен и без префикса
пакета: она живёт под `.b-<slug>`, и умолчание ей можно — иначе сломались бы блоки `team`,
`tariffs`, `reviews`, `gallery`. Цвет в таком умолчании — всё равно находка как цвет. Размер на
проводе префикс не решает: CSS уходит сжатым, и повтор префикса стоит десятки байт на файл.

### 7.3 Слияние и вывод

```
значения theme-default → значения локальной → пресет, который назвал манифест
```

```json
{
  "defaults": { "color-accent": "#0e6b5c", "font-heading": "Inter", "radius-md": "10px" },
  "presets": {
    "warm": { "title": "trans::theme::presets.warm", "tokens": { "color-accent": "#b4532a" } },
    "night": {
      "title": "trans::theme::presets.night",
      "tokens": { "color-bg": "#111418", "color-text": "#e8eaed" }
    }
  }
}
```

Ключи `tokens.json` — только `defaults`, `presets`, `schemes` (§7.6), `vocabulary` (опечатка
`default` — ошибка, а не пустая тема), имена в нижнем регистре, значения — строки. Имя вне словаря или значение не своего
типа — `ThemeException` при первом обращении: `tokens.json` — код. Пресет сливается по цепочке так
же, как значения: локальная тема дополняет `night` базовой, не повторяя его.

`@webxTheme` в `<head>` печатает `<style data-webx-theme>` с `:root { --site-… }` — результат
слияния, инлайном, чтобы смена пресета не требовала пересборки ни одного файла, — затем
`@font-face` (§15.3), виджеты, заявленные на странице (§11), `modules.css` (§10.2) и стили слоёв
снизу вверх: пакетный слой — `<link>` на опубликованные `dist/theme.css` (и `theme.js`, если он
собран), локальный — `src/css/theme.css` и `src/js/theme.js` через Vite сайта. Значения проходят
проверку типа при чтении `tokens.json` и ещё раз на выводе: значение не должно уметь закрыть
`</style>`. **На странице директива ничего не бросает:** неопубликованный пакет, несобранная
локальная тема, вход, которого нет в манифесте Vite, пропускаются, а при `app.debug` вместо них
HTML-комментарий с командой. Без темы директива печатает пустую строку.

### 7.4 Пресет и панель

**Панель вид сайта не правит** (§2, решение 12): вкладки «Внешний вид», выбора пресета и правки
токенов в базе нет.

Пресет выбирает автор темы: ключ `"preset"` в манифесте слоя (§5), обычно локальной темы —
`"preset": "night"` в `theme/theme.json`. Решает верхний слой, который его назвал. Имя, которого
нет ни в одном `tokens.json` цепочки, — ошибка: страница бросает `ThemeException`, а
`webx:theme:check` говорит об этом находкой со списком имеющихся пресетов. Переменной окружения
для пресета нет: `.env` — не git, и вид сайта не должен зависеть от того, что лежит на сервере.

Что цепочка даёт и откуда каждое значение — `webx:theme:show` (§17): агент читает его, прежде чем
править вид, и ресурсы MCP для этого не нужны — MCP-подключение к панели вид сайта не меняет.

### 7.5 Письма

Почтовые клиенты не понимают CSS-переменных, а многие — и `<style>` в `<head>`. Поэтому в письмах
токены — **значения**, подставленные на сервере: `theme_token('color-accent')` возвращает итог
слияния §7.3 (значение, которое ссылается на другой токен, — со значением того на месте ссылки;
ссылка в никуда или по кругу — `null`), и вьюхи `views/mail/` пишут его в `style="…"`. Шрифт —
семейство из токена и общий запасной: свои файлы шрифта почта не грузит. Размеры — в пикселях:
корневой размер почтового клиента неизвестен.

Рамка писем — `views/mail/layout` `theme-default` (название сайта, лист, строка «Sent from :site»).
Письмо модуля просит её по имени без пространства — `@component('mail.layout', ['title' => …])`, —
поэтому локальная тема и `resources/views/mail/` сайта её перекрывают. Модуль, который не требует
движка тем, берёт значения через свой помощник (`module-inbox`: `Mail\Look` — под темой
`theme_token()`, без темы — значения `theme-default` и своя рамка той же формы). Следующий модуль
с письмом берёт рамку и `Look` — тогда `Look` переезжает в `module-admin`, а не копируется.
`webx:theme:check` предупреждает о `var(` и буквальном цвете в письме: письмо тогда не
перекрашивается вместе с сайтом. Тёмной схемы (§7.6) у письма нет: `theme_token()` всегда отдаёт
светлое значение.

### 7.6 Тёмная схема

Второй набор значений тех же токенов, который посетитель видит, когда его система в тёмной схеме
или когда сайт поставил `data-theme="dark"` на `<html>`. Лежит в `tokens.json` слоя рядом с
`defaults`:

```json
{
  "defaults": { "color-bg": "#f7f7f4", "color-text": "#121413", "color-accent": "#2e49f5" },
  "schemes": {
    "dark": { "color-bg": "#0d0f0e", "color-text": "#ecede8", "color-accent": "#8394ff" }
  }
}
```

- **Формат.** Под `schemes` — только `dark` (светлая схема — это `defaults`); другое имя — ошибка
  `tokens.json` с понятным текстом, как неизвестный ключ. Имена — из словаря цепочки, значение —
  своего типа (`TokenType`), как у светлого.
- **Слияние** — по цепочке, как `defaults`: верхний слой переопределяет отдельные тёмные токены,
  не повторяя остальные. Токен без тёмного значения в тёмной схеме остаётся светлым и в тёмный блок
  не печатается. Пресет перекрашивает только светлую схему; тёмный набор у пресета не заводится.
- **Вывод.** Без тёмного набора `@webxTheme` печатает ровно то, что раньше. С ним:

  ```css
  :root {
    --site-…: светлые;
    color-scheme: light dark;
  }
  @media (prefers-color-scheme: dark) {
    :root:not([data-theme='light']) {
      --site-…: тёмные;
    }
  }
  :root[data-theme='dark'] {
    --site-…: тёмные;
    color-scheme: dark;
  }
  :root[data-theme='light'] {
    color-scheme: light;
  }
  ```

  Это единственный `@media` по схеме на странице: CSS темы `prefers-color-scheme` не пишет
  (`webx:theme:check`, §8), иначе он не слышит `data-theme`.

- **Переключатель — дело сайта.** Движок даёт контракт: `data-theme="dark|light"` на `<html>`
  перебивает системную схему, без атрибута решает `prefers-color-scheme`. Кнопку и запоминание
  выбора сайт пишет в своей теме; ранний скрипт, который ставит атрибут до отрисовки, — в `<head>`
  её `components/layout` (пример — `guide/themes.md`). Виджета переключателя нет.
- **Проверки.** Контраст правила 29 считается и в тёмной схеме — `dark scheme` и
  `preset <имя>, dark scheme`, незаданные тёмные значения падают на светлые: тест темы
  (`ThemeContract`) падает, `webx:theme:check` говорит замечанием. Слой, который перекрасил токен в
  `defaults`, а тёмное значение того же токена осталось от нижнего слоя, — замечание
  `webx:theme:check`: тёмное значение подбиралось к другой палитре. `webx:theme:show` показывает у
  токена тёмное значение и слой, откуда оно (или «as light»).
- **`light-dark()` в значении токена** формально проходит `TokenType`, но это обход: контраст по
  нему не считается, а `color-scheme` и `data-theme` движок тогда не ставит. Тёмные значения — в
  `schemes.dark`.
- **Тени** — тоже токены (`shadow-sm`, `shadow-md`): тёмная тень под тёмную схему задаётся там же.
  Подложки виджетов, смешанные из `color-text` (затемнение диалога и меню, кнопка видео), в тёмной
  схеме светлеют вместе с текстом — так же, как в пресете `night`.

## 8. CSS знает только токены

Одно правило — один класс движка, `Checks\CssCheck::check($css, $vocabulary)`. Находки:

- буквальный цвет в значении свойства: `#…`, цветовые функции (`rgb()`, `hsl()`, `oklch()`,
  `color()` …), именованный цвет. Исключения — `transparent`, `currentColor` и общие ключевые слова
  CSS; именованный цвет не ищется в свойствах-именах (`animation`, `grid-*`, `font*`, `content` …);
- буквальное семейство шрифта в `font-family`/`font` (общие семейства CSS — `sans-serif`,
  `ui-monospace`, `system-ui` … — можно);
- `var(--site-…)`, которого нет в словаре цепочки — та же ловушка, что `--wx-space-20` в ядре:
  несуществующая переменная молчит;
- запасное значение `var(--site-x, #fff)` — тоже буквальный цвет: не перекрашивается, та же дыра,
  только тише;
- `@media` по ширине (§16.1, правило 12);
- `@media` по `prefers-color-scheme`: тёмную схему печатает движок из `schemes.dark` (§7.6).

Не читаются комментарии, строки, `url()`, объявления внутри `@font-face` и `@property`, и собранное
(`dist/`: там чужие стили Swiper, PhotoSwipe, Leaflet). Своя переменная (`--webx-slider-gap: …`)
читается как любое значение: `#fff` в ней — цвет.

| Где                                   | Как строго                                          |
| ------------------------------------- | --------------------------------------------------- |
| Блок, сохранённый в панели            | предупреждение                                      |
| Блок слоя при импорте (§9.2)          | запрет: тип не ставится                             |
| `src/css` темы, CSS модуля и виджетов | запрет в `webx:theme:check` и в тесте пакета (§18)  |
| `tokens.json`                         | единственное место, где буквальное значение законно |

Предупреждения в панели (`Lints`: `literal-colors`, `literal-fonts`, `unknown-tokens`,
`token-fallbacks`; в редакторе — перенос правила в `css-tokens.ts`; MCP слышит то же) — **только на
сайте с темой**: у сайта без темы нет токенов, и типы на буквальных цветах там норма. Словарь
блоки получают от цепочки (`Panel\SiteTokens`); `webx-ui/themes` у `module-blocks` — `suggest` и
`require-dev`, не `require`. Виджеты строже: ни одного запасного значения вообще.

## 9. Блоки

### 9.1 Универсальные блоки `theme-default`

Примитивы, из которых собирается почти любая корпоративная страница, — без привязки к модулям,
кроме формы, которая есть на каждом сайте:

| Блок         | Что                                                                                                                  |
| ------------ | -------------------------------------------------------------------------------------------------------------------- |
| `hero`       | заголовок, строка, одна-две кнопки; тон (страница, тинт, акцент, картинка), выравнивание, ширина колонка/во всё окно |
| `text`       | проза с типографикой темы, колонка для чтения или вся; тело простыми строками — абзацами                             |
| `media-text` | картинка и текст рядом, сторона на выбор                                                                             |
| `cards`      | сетка карточек (не больше 2–4 в ряд, решает контейнер): фото или иконка, вся карточка — одна ссылка                  |
| `cta`        | полоса призыва с одной-двумя кнопками                                                                                |
| `contact`    | контакты из «Контактов» настроек и форма `module-inbox` по slug                                                      |

Каждый — со своим CSS на токенах, на `@container`, без медиа-запросов и `!important`; всё, что
читает посетитель, — поля с `localized`, постоянные подписи — `theme::`. Тег формы `contact`
рендерится через `Blade::render()` под `class_exists`, а не тегом в шаблоне: тип компилируется
целиком, и тег отсутствующего модуля не дал бы опубликовать тип на сайте без `module-inbox`. Блоки
модулей (услуги, команда, отзывы, FAQ, каталог) — не здесь, а в модулях (§10.3).

### 9.2 Блоки слоёв на сайте

Слои несут типы в `blocks/*.json` — формат `webx:blocks:export` (§17 спеки блоков). Итоговый набор
(`Blocks\LayerBlocks::of($chain)`): типы нижнего слоя, поверх — типы верхнего с тем же slug
(перекрытие целиком). Перекрывать схему можно только совместимо (`Blocks\SchemaCompatibility`) —
каждое поле нижней схемы есть в верхней под тем же ключом и того же типа, новые можно; узлы
раскладки полей не называют, поле можно переложить в колонку; `localized` не сравнивается.
Смена типа — находка `webx:theme:check` и отказ импорта: содержимое, заполненное под нижний блок,
в верхнем не подойдёт.

**Поле, которого в перекрытии нет, наследуется** (`SchemaCompatibility::inherit`, при чтении
слоёв в `LayerBlocks`): узел нижнего типа переходит целиком — подпись, `default`, дети — после
поля, за которым стоит внизу (внутри той же строки раскладки), иначе в конец своего списка; его
значение из нижнего `sample` — в `sample`. Описанное в файле поле — файла, нижнее его не правит;
под полем, у которого перекрытие сменило тип, ничего не переносится. Так итоговый набор видят все:
импорт, `webx:theme:show`, слепок `TypeHash`. Файл темы не меняется, `theme:check` пишет note
(`LayerBlocks::inherited()`): поле унаследовано, шаблон темы его не использует — вывести, если
нужно. Причина: пакет добавляет поле в свой блок минорным релизом, и при строгом «поле потеряно»
каждый сайт, чья тема перекрывает блок, падал бы на `theme:check`, импорте и тестах темы — а данные
редактора при наследовании не теряются, ради чего правило и было. Тип блока в базе сайта обновление
по-прежнему не трогает: унаследованное поле приходит туда только явным импортом, как и всё остальное.

**На сайт их ставит только явная команда** — `webx:blocks:import --theme` (правило и формат вывода —
`WEBX_UI_BLOCK_SCHEMAS.md` §1, §4). `webx:theme:sync`, а с ним `webx:boot` и `post-update-cmd`,
типов не пишет: тип на работающем сайте — зона клиента, деплой его не трогает. `webx:setup` зовёт
импорт один раз, для нового сайта (§14.1).

Импорт читает итоговый набор (`module-blocks`: `Themes\LayerSource`) и отдаёт его общему
`Panel\Importer`. Что может испортить только слой — файл не документ, стили против §8, несовместимое
перекрытие — строка `failed`, без записи. Дальше как у любого импорта: нового типа нет — создаёт
(с `--publish` публикует) и пишет `blocks.theme_source` (слой) и `blocks.theme_hash` (`TypeHash`:
не байты файла — экспорт пишет `version` и `exported_at`) — их показывает отладочная панель, логика на
них не держится. Тип есть и совпадает — `unchanged`; отличается — `differs`, остаётся как есть и
печатает расхождение, кто бы его ни менял (клиент, модуль, старая версия темы). Перезапись — только
`--replace=<slug>`, новой версией.

Типы, которые слои перестали нести, **не удаляются**: на них могут стоять страницы. Удалённый на
сайте тип не возвращается.

**Демо `module-blocks` уступает теме.** Демо не сеет slug, который несут слои. Сайт, получивший
демо раньше, чем тема понесла slug, увидит у импорта `differs`; взять тип темы —
`webx:blocks:import --theme --replace=hero` (копия демо остаётся в истории версий).

Локальная тема — тоже слой. Обычный путь блока: делается на dev в панели, выгружается в
`theme/blocks/` (`webx:blocks:export --path=theme/blocks`) и коммитится — вид сайта целиком лежит в
git, а не только в базе; на стейджинг и прод его переносит `webx:blocks:import --theme`, руками,
один раз.

Права. Конструктор блоков закрыт отдельным правом `blocks.manage` (по умолчанию у
супер-администратора, §16 спеки блоков), `webx-blocks.editing = false` выключает правку типов
целиком. Владелец сайта по умолчанию получает содержимое и не получает конструктор.

`webx:theme:sync` идемпотентна — её зовут `webx:setup`, `post-update-cmd` сайта, `webx:boot` и тот,
кто обновляет много сайтов разом; поэтому она публикует только файлы.

## 10. Модули в теме

Тема по умолчанию не знает модулей, кроме обязательных (§9.1). Каждый модуль с публичными
страницами сам несёт всё, чтобы выглядеть прилично на любой теме, и оставляет теме четыре двери —
от дешёвой к дорогой.

### 10.1 Разметка и классы

Вьюхи модуля печатают семантическую разметку с классами по БЭМ (`webx-catalog-card`,
`webx-catalog-card__price`, `webx-catalog-filter__group--…`). Классы — **публичный контракт
модуля**: переименование ломает темы, поэтому идёт как ломающее изменение, с записью в README.
Список классов и что они значат — подраздел `### Classes` в «Change it without forking» `AGENTS.md`
модуля (§16).

**Префикс:** модуль, у которого классов не было, получает `webx-<module>-*` (блог, услуги);
модуль, у которого классы уже были выпущены, дополняет свои, не меняя префикса — события, рецепты,
вакансии, пресса и меню остаются на `wx-*`, SEO — на `webx-breadcrumbs`/`webx-faq`/`webx-links`.
Переименование ради единообразия — ломающее изменение, которого никто не просил; `wx-*` на
публичном сайте с панелью не пересекается. `module-pages` классов не несёт: страница — это блоки и
проза темы.

### 10.2 Базовый вид

Модуль несёт `resources/theme/<module>.css` — свой базовый вид на токенах словаря (§7.2), под
своими классами, на `@container`. Это нижний слой цепочки (§7.1): он подключается, только если
модуль установлен, и проходит ту же проверку на токены (§8). Задача — не красота, а «прилично в
любой теме»: сетка карточек, отступы, состояния, читаемые цены и фильтры.

Без этого слоя каждый модуль либо голый на любой новой теме, либо требует правки
`theme-default` — а модулей больше двадцати, и их добавляется больше, чем тем.

`webx:theme:sync` склеивает `resources/theme/*.css` всех установленных модулей в **один** файл
`public/themes/modules/<хеш>/modules.css` (`ModuleStyles`), и `@webxTheme` ставит его до всех
слоёв темы — тема перекрашивает модуль тем же классом позже в каскаде. Один файл, а не по
странице: стили модулей малы, а форма и крошки стоят почти везде. Правка `resources/theme/*.css`
видна только после sync.

**Свой инлайн — только без темы.** Модуль, который печатал свой вид `<style>` или атрибутом
`style=""`, под темой не печатает ничего — инлайн позже в каскаде бил бы тему; спрашивает
`function_exists('theme_active') && theme_active()` (движок модулю не обязателен). Сайт без темы
видит то, что видел. Число колонок и подобное — модификатором класса, а не `style`.

Контракт модуля держит тест на трейте `Testing\ModuleThemeContract`: CSS проходит §8 со словарём
движка (модуль не знает темы над собой), без `@media` и `!important`, переменные — только
`--site-*` и свои `--webx-*`, объявленные тут же; каждый класс CSS перечислен в `AGENTS.md`, каждый
перечисленный есть во вьюхах; каждая точка `@webxPart` названа в `AGENTS.md`.

### 10.3 Блоки модуля

Модуль предлагает простые типы блоков — список своих записей плюс поля вокруг: заголовок, подпись,
кнопка, сколько показать. `BlockOffers` — файл `webx:blocks:export` в `resources/blocks` модуля,
сайт ставит его **один раз**, и дальше тип по этому slug не трогается: его переделывают под сайт.

Если в цепочке есть тип с тем же slug, ставится **он**, а не предложение модуля
(`BlockOffers::install()` → `CARRIED`, `webx:blocks:offered` говорит, что его поставит
`webx:blocks:import --theme`). Так
тема может нести свой вид блока «услуги» и быть уверенной, что на новом сайте стоит именно он. Если
тип уже стоит на сайте, ничего не меняется — правило «один раз» сильнее.

CSS предложенных блоков — тоже на токенах (§8): блок модуля, поставленный на сайт с любой темой,
сразу в её цветах.

### 10.4 Точки расширения

Места внутри вьюх модуля, куда спутник или тема добавляют своё, не перекрывая вьюху целиком, —
`@webxPart('<точка>', $data, '<вьюха по умолчанию>')` (`blog.card`, `services.card`, `events.card`,
`vacancies.card`, `recipe-card`, `catalog.card.badges` …). Точки и данные, которые в них приходят, —
тоже публичный контракт модуля. Тема отвечает вьюхой `views/parts/<точка через />.blade.php` — без
провайдера и без кода. Порядок: карточка, перекрытая в панели (`module-blocks`), → `parts.<точка>`
сайта → слоёв темы → партиал модуля; «Customise» в панели начинает с вьюхи темы. Точку, не
объявленную в `BlockComponents` (карточки блога, услуг, событий, вакансий), перекрывают только тема
и сайт.

### 10.5 Четыре двери, от дешёвой к дорогой

| Хочу                                       | Делаю                                                                            |
| ------------------------------------------ | -------------------------------------------------------------------------------- |
| другие цвета, шрифты, отступы              | токены — модуль подхватит сам                                                    |
| другой вид карточки, фильтра, страницы     | CSS в `src/css` темы на классах модуля                                           |
| добавить кусок (бейдж, кнопку, блок рядом) | вьюха на точку расширения (§10.4)                                                |
| другую разметку целиком                    | перекрыть вьюху в `views/vendor/<ns>/` — и следить за ней при обновлениях модуля |

Последняя дверь самая дорогая: перекрытая вьюха не получает исправлений модуля. `webx:theme:show`
перечисляет перекрытые вьюхи; сверка свежести перекрытия — открыта (§22).

### 10.6 Пример: каталог

| Что на витрине                 | Откуда                                                                                                |
| ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| листинг, сортировка, пагинация | вьюхи `webx-catalog::grid`, `sort`, `pagination` + `catalog.css` модуля                               |
| фильтры                        | `webx-catalog::filter` + группы по виду (`--range`, `--swatch`…); на телефоне — виджет `dialog` (§11) |
| страница товара                | `webx-catalog::product`; галерея — слайдер `gallery`, увеличение — лайтбокс (§11)                     |
| слайдеры товаров на страницах  | предложенные блоки «товары категории», «новинки» — слайдер `cards`                                    |
| бейджи, наличие                | точки `catalog.card.badges`, `catalog.card.meta` — у спутников                                        |

Тема магазина меняет витрину в основном второй дверью — CSS на классах, — и третьей для своих
вставок. Перекрытие вьюх каталога — исключение. Каталог и его спутники получают базовый вид вместе с
темами магазинов.

## 11. Виджеты

Всё интерактивное, что повторяется из сайта в сайт, — отдельный пакет `webx-ui/widgets`, спека
[`WEBX_UI_WIDGETS.md`](WEBX_UI_WIDGETS.md): лёгкие поведения (меню, диалог, вкладки, аккордеон),
слайдер на Swiper, лайтбокс, видео, карта, согласие на cookie с блокировкой стороннего до согласия.

Для темы из этого важно три вещи:

- пакет — **нижний слой цепочки**, как модуль: его вьюхи компонентов перекрываются в
  `views/vendor/webx-widgets/`, CSS идёт первым в каскаде, блоки — предложениями;
- вид виджета меняется теми же дверями, что вид модуля (§10.5): токены, в том числе локальные
  `--webx-<виджет>-*`; CSS на классах `webx-<виджет>-*`; перекрытие вьюхи компонента;
- скрипт и CSS виджета грузятся **только на странице, где он стоит**: компонент заявляет себя, а
  `@webxTheme` печатает заявленное.

Иконки виджетов (`webx-widgets::icons.*`) — свои, а не из спрайта темы: виджеты не зависят от
движка, и стрелки слайдера на сайте без темы должны рисоваться (под темой — §22).

`theme-default` зависит от `widgets`: шапка — виджет `<x-webx-header>` с мобильным меню внутри, ссылка «Настройки
cookie» в подвале, вид баннера согласия.

## 12. Что ещё в `theme-default`

- **Оболочка:** шапка на виджете `<x-webx-header>` — логотип из настроек, `menu('header')`,
  телефоны (`<x-webx-phones>` с «Заказать звонок» в окне); мобильное меню она собирает сама из тех
  же слотов; подвал — `menu('footer')`, контакты, часы, соцсети, переключатель языка и «Настройки
  cookie» из виджетов, данные — из вкладки «Контакты» настроек; обе — фолбэки зон `header`/`footer`
  (`components.header`/`components.footer` ищутся по цепочке). Классы оболочки — `site-*`.
- **Типографика прозы** — для `text`, страниц и статей.
- **Вьюхи модулей, которые есть почти везде:** страница (`webx-pages`), форма (`webx-inbox`); вид
  остальных — у самих модулей (§10.2).
- **FAQ и перелинковка `module-seo` — в конце `<main>` лэйаута**, после содержимого и перед
  подвалом: «что ещё спросить» и «куда читать дальше» к прочитанному, на любой странице, потому что
  правило SEO вешается на адрес. Компоненты — по имени за `view()->exists()`: без `module-seo` тема
  компилируется; выключенные функции печатают пусто.
- **Письма** (§7.5), **страницы ошибок** (404 в рамке сайта: язык префикса, `noindex`, без
  `@webxSeo`, переключатель ведёт на главные языков), 27 иконок (§13.1), Inter своими файлами
  (§15.3).
- **Пресеты `warm` и `night`** — готовые варианты палитры, которые автор сайта называет в
  манифесте (§7.4).
- **Демо** главной, вложенных страниц и витрины на трёх языках (§15, §18.3).

## 13. Иконки и ассеты

### 13.1 Иконки

`icons/<имя>.svg` каждого слоя `webx:theme:sync` собирает прямо из исходников в один спрайт
`public/themes/icons/<хеш>/icons.svg` (`ThemeIcons`): `<symbol>` с `id` по имени файла, верхний
слой побеждает по имени. Отдельной сборки иконок у слоя нет — один путь для пакета и локальной
темы; новая иконка видна после sync. Скрипты, `<style>`, `<foreignObject>` и обработчики спрайт
выбрасывает; атрибуты окраски корня сохраняет (штрих остаётся штрихом).

```blade
<x-theme::icon name="phone" />
<x-theme::icon name="arrow-right" class="b-hero__arrow" />
```

Компонент печатает `<svg class="theme-icon">` в `1em`, `currentColor`, с `<use>` на спрайт и
`aria-hidden`, или `role="img"` с `label`. Работает в оболочке, вьюхах модулей и шаблонах блоков и
зарегистрирован без темы — шаблон с иконкой компилируется на любом сайте. Цвет — `currentColor`,
поэтому иконка перекрашивается вместе с текстом. Размер — в CSS (`:where(.theme-icon)` в базе
темы, другой — классом), а не атрибутами. Неизвестное имя или неопубликованный спрайт — пустой
`<svg>` (подсказка в debug) и находка в `webx:theme:check`, а не исключение на живой странице.

### 13.2 Ассеты

`webx:theme:sync` кладёт `dist/` и `assets/` пакетных слоёв в `public/themes/<vendor>/<имя>/<хеш>/`,
а `assets/` локальной темы — в `public/themes/local-<каталог>/<хеш>/assets/`; её CSS и JS собирает
в `public/build` Vite сайта. Каталог назван хешем содержимого, а не версией: слинкованный с
монорепой сайт держит одну версию, пока файлы меняются. На какой смотрят страницы — файл `current`
рядом; копия пишется во временный каталог и переименовывается (страница не увидит половину темы);
остаются текущая и одна предыдущая. Веб-сервер отдаёт `/themes/` и `/build/` с вечным кешем —
`Cache-Control: public, max-age=31536000, immutable` в `docker/nginx.conf` и `public/.htaccess`
скелета.

```blade
<img src="{{ theme_asset('img/wave.svg') }}" alt="">
```

`theme_asset()` ищет файл по цепочке сверху вниз: отвечает самый верхний слой, у которого есть
`assets/<путь>`, адресом его опубликованной копии. Пути нет ни в одном слое, или верхний слой
получил файл после последнего sync — пустая строка (в debug — строка в логе), **а не копия нижнего
слоя**: это была бы другая картинка, и ошибка выглядела бы как «тема не перекрылась». `assets/`
локальной темы публикует sync, а не Vite: `Vite::asset()` знает только импортированные входом
файлы, и у `theme_asset()` было бы два пути поиска. `public/themes/` — в `.gitignore` и
`.dockerignore` скелета: это производное от `vendor/` и `theme/`, как `public/build`.

## 14. Новый сайт

### 14.1 `webx:setup`

Что делать с видом, setup решает до установки (`Setup\ThemeChoice`):

- новый сайт — `theme/` на `webx-ui/theme-default`; `--theme=<vendor/name>` — на другой теме (путь
  второй части, §21); не имя пакета — отказ до `composer require`;
- `--no-theme` — тема не ставится, в `resources/views/components/` пишутся лейаут, шапка и
  подвал, плюс `resources/css/app.css` и `resources/js/app.js` — заготовки `module-admin/stubs/site/`;
- `WEBX_THEME` уже не пуст — тема остаётся как есть: setup — ещё и способ добавить модуль на живой
  сайт;
- у сайта свой `components/layout` и `--theme` не передан — темы нет: смена вида — не то, о чём он
  просил. С `--theme` поверх своего лейаута тема ставится с предупреждением, что `resources/views`
  выше всех слоёв.

Порядок для нового сайта:

1. `webx-ui/theme-default` уходит в тот же `composer require`, что модули;
2. `webx:theme:make theme --uses=webx-ui/theme-default --local` — каталог `theme/` (§17);
3. `WEBX_THEME=theme` в `.env` — **только после** того, как каталог есть: имя на несуществующий
   каталог роняет загрузку любого `artisan` (§7.1);
4. `webx:theme:sync` — ассеты; потом `webx:panel --sync` (лейаут он ищет через
   `view()->exists('components.layout')`, а не по файлу сайта);
5. после `migrate` — `webx:theme:sync` и `webx:blocks:import --theme --publish` (типы блоков,
   §9.2) **до** `webx:blocks:offered`: тип цепочки ставится первым, предложение модуля видит slug
   занятым. Повторный setup существующих типов не трогает;
6. демо — из цепочки (§15), если не `--no-demo`.

Setup с темой дописывает `@php artisan webx:theme:sync --ansi` в `post-update-cmd` сайта (у скелета
этой строки нет: у сайта с `--no-theme` нет команды). `webx:boot` в контейнере тоже зовёт sync:
`public/themes` нет ни в репозитории, ни в свежем контейнере. Sync в setup и boot не фатален — сайт
откроется с меньшим стилем. Типов блоков ни sync, ни boot не пишут (§9.2).

Скелет `php/site` своего лейаута не несёт (оставлен только `regions/region.blade.php` для сайта без
`module-blocks`); входы Vite — `theme/src/…` и `resources/…` через `existsSync`, один конфиг для
сайта с темой и без. В Docker стадия ассетов берёт `theme/` из стадии `vendor`, где стоит
`mkdir -p theme`, — иначе сайт с `--no-theme` не собрался бы.

### 14.2 Цикл разработки

Сайт подключён к монорепе (`scripts/link-panel.sh` / `packages.mjs local`), и
`vendor/webx-ui/theme-default` — симлинк на чекаут. Локальная тема — `npm run dev` сайта:
Vite пересобирает `theme/src` на лету. Правка `theme-default` из монорепы — сборка в её каталоге и
`webx:theme:sync`; то же — после новой иконки, картинки или CSS модуля. Симлинк вместо копии
(`--link`) не построен (§22).

### 14.3 Вынос и отвязка

**`webx:theme:extract <vendor/имя>`** — локальная тема становится пакетом. Каталог `theme/`
переезжает в каталог пакета, `theme.json` становится `extra.webx.theme` как есть, `uses`
сохраняется, сайт переключается на пакет через `path`-репозиторий. Так удачный дизайн становится
темой, которую можно поставить второму сайту, — дорога в каталог (§21). Типы блоков не трогаются:
импорт видит тот же тип (`unchanged`), а `theme_source` у него остаётся прежним — это только
отметка для отладки.

**`webx:theme:eject`** — наоборот: пакетная тема (не `theme-default`) вливается в `theme/`, и
дальше обновления этой темы не приходят. Осознанный шаг для сайта, у которого отличий стало больше,
чем общего. Вливается слой прямо под локальной темой (глубже — отказ: тема между ними стояла бы на
исчезнувшей); побеждает то, что у сайта уже есть, как побеждало в цепочке: файлы — где у темы
своего нет, слова, токены и пресеты — по ключу, `src/` пакета импортируется первым. Сайт на пакете
без локальной темы получает его в `theme/` целиком.

Обе команды сравнивают вид цепочки до и после (`ThemeLook`: токены и пресет, файл-победитель
каждой вьюхи, ассеты и иконки, типы блоков, грани шрифтов, слова вёрстки; CSS — нет) и называют
каждое расхождение. Composer и npm они **не запускают, а печатают** команды: те долгие, ходят в
сеть, и упавший шаг виднее, когда его запускает человек.

## 15. Демо, языки, шрифты

### 15.1 Демо

Модуль сеет демо (`ProvidesDemo`, §9 спеки нового сайта) из первого слоя сверху, у которого есть
нужный файл в `demo/<module>/` (`ThemeDemo`), иначе — из своего `resources/demo/`; **по файлу, а не
по каталогу**: тема, которая приносит только витрину, не обязана копировать демо модуля. Формат и
журнал (`DemoLedger`) те же, `webx:demo --remove` убирает и это демо. Зоны `header` и `footer`
(`regions/*.json`) сеются так же: это содержимое, и после установки принадлежат сайту. Так тема
приносит страницы (`demo/pages/`, остальные `*.json` — страницы под главной), формы
(`demo/inbox/`), FAQ и ссылки страниц (`demo/seo/pages.json`).

Демо темы не занимает префиксов модулей, которые сайт может поставить (страница «What we do», а не
`/services`).

### 15.2 Языки

Любое строковое значение в фикстурах может быть картой языков:

```json
{ "title": { "en": "Harbor Logistics", "de": "Harbor Logistik", "pl": "Harbor Logistyka" } }
```

Через `WebxUi\Admin\Demo\DemoWords` идут страницы, меню, настройки, формы, зоны и демо модулей:

- поле с `localized` получает карту, урезанную до языков сайта (`--locales` в `webx:setup`);
- поле без `localized` — строку на основном языке сайта, а если её нет — на `en`; карта в таком поле
  остаётся картой, сайт читает её по форме (`Locales::isMap`), поэтому текстовые поля демо-типов
  помечены `localized`;
- основной язык, которого в карте нет, получает `en` (иначе первое значение) — запись не остаётся
  безымянной;
- язык сайта, которого нет в демо, — `webx:setup` предупреждает рядом с напечатанной строкой
  `webx:demo`, но не отказывает. Языки демо каждого модуля и темы записаны в `Setup\Catalogue`
  (`Catalogue::demoGaps`): до `composer require` фикстур на диске нет; тест сверяет каталог с
  фикстурами.

Витрина и демо модулей по умолчанию, блога, услуг, событий, вакансий, прессы и рецептов — на
en/ru/pl; FAQ, отзывы, команда, тарифы и баннеры — en/ru. Нарочно английские записи демо
показывают, что у непереведённой записи нет адреса на другом языке.

Слова вёрстки — «Skip to content», подписи блоков — в `lang/<locale>/theme.php` слоёв, ключ —
`theme::theme.<ключ>` (`theme::<ключ>` молча печатает сам ключ), ищутся по цепочке по ключу.
Основной словарь — у `theme-default` на десяти языках панели; локальная тема добавляет и перекрывает
только своё. Ни одного слова в шаблонах оболочки и блоков — это держит тест `theme-default`.
`webx:theme:check` (`LineCheck`) сверяет ключи каждого языка из `locales` слоя с его `en`; язык, не
объявленный в `locales`, не сверяется — локальная тема может перекрыть одно слово, не обещая язык
целиком. Слова модулей на их страницах — в словарях модулей.

Картинки в демо — без текста: картинку не переведёшь. Логотипы — исключение: это имя, его не
переводят.

### 15.3 Шрифты и письменности

Грань шрифта в манифесте — `family`, `weight` (у переменного шрифта диапазон, `"100 900"`), `style`
и `files` — карта «письменность → файл под `assets/` слоя»; письменности — ключи карты (по маске
файлов не понять, какой файл какую письменность покрывает). Письменности и их `unicode-range` —
нарезка Google Fonts и Fontsource (`latin`, `latin-ext`, `cyrillic`, `cyrillic-ext`, `greek`,
`greek-ext`, `vietnamese`): скачанный оттуда файл встаёт как есть. Семейство верхнего слоя
заменяет то же семейство снизу целиком.

`@webxTheme` печатает `<style data-webx-fonts>` — `@font-face` на файл с `unicode-range` и
`font-display: swap`, `latin` последней (на общих точках диапазонов побеждает файл, который
страница грузит всё равно), без `preload` — кириллица не грузится на английской странице.
Переключатель языков рисует названия других языков шрифтом читателя (`is-other`) — иначе «Русский»
скачивал бы кириллицу на каждой английской странице.

`webx:theme:check` и `webx:doctor` (`Doctor\FontsCheck`, если стоит `module-admin`; предупреждение)
сверяют письменности с языками сайта (`ThemeFonts::LANGUAGES`: `ru`/`uk` — `cyrillic`, `pl`/`tr` —
`latin-ext`; языка вне таблицы проверка не судит) и с `locales` слоя. Без этого сайт на польском
рисует `ą` и `ł` запасным шрифтом, и видно это только глазами.

## 16. Для агентов

Задача: агент, которому сказали «сделай вид сайта как на этом макете», знает, что править, где, и
чем проверить — не читая исходники движка.

- **`AGENTS.md` движка** (`webx-ui/themes`) — как устроена тема: цепочка, §4, §6, словарь, четыре
  двери модулей (§10.5), команды с флагами, `ThemeContract`, таблица «хочешь → делай»; первой
  строкой ведёт на `RULES.md`.
- **`AGENTS.md` `theme-default`** — что в ней есть: блоки и их поля, классы оболочки, все токены,
  пресеты, иконки; как перекрыть каждое.
- **`AGENTS.md` каждого модуля с публичными страницами** — классы (`### Classes`), точки
  расширения с данными, предложенные блоки, базовый CSS.
- **Корневой `AGENTS.md` сайта** — раздел «The site's look» называет цепочку этого сайта сверху
  вниз, двери его локальной темы, `webx:theme:show`/`check`, `RULES.md` и гайд; его собирает
  `webx:panel --sync`.
- **Гайды** `apps/docs/guide/themes.md` и `apps/docs/guide/styles.md` для людей.
- **`webx:theme:show`** (§17) — слои, итоговые токены и откуда каждый, пресет, перекрытые вьюхи,
  блоки, иконки и шрифты с их источником. Агент, который правит `theme/`, работает в репозитории,
  а не через панель (§2, решение 12), — ему команда, а не ресурс MCP.
- **Заготовка** — `webx:theme:make` (§17): тест зелёный сразу, агент начинает с работающей темы.
- **Обратная связь** — `webx:theme:check` и `ThemeContract` говорят не «не так», а что и где:
  «b-hero: literal colour #ff4343 at line 12, use a --site-* token».

Покрытие проверяет тест (`AgentsCoverageTest` движка, `WEBX_UI_AGENT_DOCS.md` §4): каждая команда
`webx:theme:*` и ключ манифеста — в `AGENTS.md` движка, каждый токен словаря — в `AGENTS.md`
`theme-default`, правила 1–41 — по порядку в `RULES.md`.

### 16.1 Правила построения темы

Свод живёт файлом `php/packages/themes/RULES.md` (по-английски, те же номера): каждое правило
начинается с **Do** или **Do not**. Каждое правило, которое можно проверить машиной, проверяет
`webx:theme:check` — в скобках, каким пунктом; остальное — дело глаз и ревью. Пометка «check» в
`RULES.md` — только у правил, которые проверка действительно держит (1, 5, 9, 13, 14 и 22 —
пока нет, §22).

**Где работать**

1. Вид сайта правится **только в `theme/`** (или в пакете темы). Не в `vendor/`, не в
   `resources/views` сайта, не в `public/`. Перекрытие в `resources/views` — для разработчика, а не
   путь темы. (check: файлы вида вне цепочки)
2. Сначала прочитать цепочку: `webx:theme:show` — что уже есть снизу,
   какие блоки, вьюхи и токены. Не писать то, что уже даёт `theme-default` или модуль.
3. Изменение — **самой дешёвой дверью**, которая решает задачу (§10.5): токен → CSS на классах →
   точка расширения → перекрытие вьюхи. Перекрыть вьюху, когда хватало CSS, — ошибка, а не стиль.

**Токены**

4. Любой цвет, шрифт, радиус, отступ, тень, длительность — **только `var(--site-…)`**. Буквальное
   значение законно в одном месте — `tokens.json`. (check §8)
5. Нужен цвет, которого нет, — сначала роль из словаря (`accent-2`, `highlight`,
   `surface-muted`), и только если ни одна не подходит — свой токен в `vocabulary` темы с
   **ролевым** именем (`color-badge`, не `color-pink`). (check: имя-оттенок в `vocabulary`)
6. Без запасных значений в `var()`: `var(--site-x, #fff)` не перекрашивается. (check §8)
   Префиксов три (§7.2): `--site-*` — токен сайта, `--webx-*` — своя переменная пакета, `--wx-*`
   — панель и на сайте не бывает. Четвёртого не заводить.
7. Значения бренда — в `defaults` локальной темы; варианты — пресетами, а не копией темы; тёмная
   схема — в `schemes.dark` (§7.6), не `light-dark()` в значении.
8. Пресет сайта — ключом `preset` в манифесте, а не переменной окружения и не настройкой в
   базе: вид сайта целиком в git (§2, решение 12). (check: пресет, которого нет в цепочке)

**Стили — у каждого одно место (§6)**

9. Вид одного блока — **в блоке**, под `.b-<slug>`. Селектор `.b-<slug>` в `src/css` — ошибка
   места. (check §6)
10. В `src/css` — оболочка, сетка, типографика, вид страниц модулей и виджетов на их классах.
    Больше ничего.
11. Страницы модулей стилизуются по классам модуля из его `AGENTS.md`. Не по тегам и
    не по вложенности (`.webx-catalog-listing > div > a`): разметка внутри может поменяться, классы
    — контракт.
12. Ширину решает контейнер: `@container`, не `@media`. (check: `@media` с шириной в блоках и
    `src/css`) Тёмную схему печатает движок: `@media (prefers-color-scheme)` в CSS темы не пишется.
    (check §8)
13. Голых селекторов элементов (`h2`, `a`, `img`) — только в типографике прозы, под её классом.
    (check: голый селектор вне типографики)
14. Без `!important`, кроме служебных (`[hidden]`); проблема каскада решается порядком слоёв, а не
    силой. (check)

**Блоки**

15. Новый блок — только если ни один из `theme-default` (§9.1) и модулей (§10.3) не решает задачу
    полями. Другой вид существующего блока — **перекрытие того же slug**, а не новый блок с
    похожим именем.
16. Перекрытая схема — **совместима**: те же поля с теми же типами, новые — добавлять можно,
    менять тип нельзя. Поле нижнего типа, которого нет в файле, наследуется с `default` (note
    проверки); в шаблоне его выводит сам автор, своя подпись или `default` — описать поле в файле.
    (check §9.2)
17. Корень блока — `data-wx-block="<slug>"`, все селекторы — под `.b-<slug>`. (lint блоков)
18. Тексты блока, которые видит посетитель, — поля схемы с `localized`, а не строки в шаблоне;
    постоянные подписи — `__('theme::…')`.
19. Слайдер, лайтбокс, видео, карта, вкладки, аккордеон, диалог — **виджетом** (§11), не своим
    скриптом и не своей библиотекой. Всё стороннее (YouTube, карты, счётчики) — только через виджет
    или с `data-webx-consent`: до согласия на странице нет ни одного запроса к третьей стороне.
    Свой скрипт — только для того, чего в виджетах нет, и по контракту входа.
20. Блок сделан в панели — выгружен в `theme/blocks/` (`webx:blocks:export --path=theme/blocks`) и
    закоммичен. Блок, который есть только в базе, потеряется при следующем развёртывании с нуля.

**Вьюхи**

21. `components/layout` держит `@webxTheme`, `@webxSeo`, `@webxBlocks` и зоны `header`/`footer`;
    на сайте с `module-snippets` — и три места кодов `head`, `body_start`, `body_end`
    (`<x-webx-snippets place="…" />`, SNIPPETS §4.1). (check: обязательные директивы; места кодов
    проверяет часть `ThemeCheckPart` модуля)
22. Перекрывая вьюху модуля, копировать **текущую** версию из `vendor/` и менять минимум; классы и
    `@webxPart` оставлять на месте — на них стоят спутники модуля. (check: свежесть перекрытия)
23. Ссылки — через `route()`/адреса сущностей, никаких зашитых путей; меню — `menu('…')`, контакты
    и название — `settings()`; ни одного текста сайта в шаблоне.
24. Иконки — `<x-theme::icon>` из спрайта, не инлайновый SVG в шаблоне; картинки темы —
    `theme_asset()`. (check: неизвестная иконка, отсутствующий ассет)
25. Письма — значения через `theme_token()` в `style="…"`, без `var()`. (check §7.5)

**Языки и шрифты**

26. Каждое слово вёрстки — во всех `locales` темы; добавил ключ в `en` — добавил во все. (check:
    паритет ключей)
27. Шрифт — своими файлами в `assets/fonts/`, с письменностями всех языков сайта; без Google Fonts
    и других CDN. (check §15.3)
28. Картинки демо — без текста.

**Доступность и вёрстка**

29. Контраст текста и фона в каждом пресете и в тёмной схеме — не ниже WCAG AA (4.5:1 для текста,
    3:1 для крупного и для элементов управления). (check: контраст пар `text`/`bg`,
    `accent-contrast`/`accent`, `text-muted`/`surface` по итоговым значениям каждого пресета и его
    тёмной схемы, §7.6)
30. У интерактивного — видимый фокус (`:focus-visible`), кликабельная область не меньше 44×44 на
    телефоне.
31. Без горизонтальной прокрутки страницы на ширине 360px.

**Проверка перед тем, как сказать «готово»**

32. `webx:theme:check` — без ошибок; тест темы (`ThemeContract`) — зелёный.
33. Скриншоты в браузере: главная, одна вложенная страница и страница каждого установленного модуля
    — на десктопе и на 375px, в каждом пресете. Jsdom вёрстку не проверяет.
34. Замер, а не взгляд, где это возможно: `scrollWidth` против `clientWidth` для горизонтальной
    прокрутки, `getComputedStyle` — что токен действительно дошёл.
35. Отчёт человеку — что изменено, какой дверью (§10.5) и почему, какие вьюхи перекрыты. Решение,
    хороша ли тема, — за человеком.

**Скорость** (номера после «Проверки»: номер правила — часть вывода проверки, перенумерация сломала
бы ссылки)

36. Фото — WebP или AVIF, той ширины, какой их рисует вёрстка: картинка медиатеки — превью и файл в
    `srcset`/`sizes`, как галерея `webx-ui/widgets`; старая медиатека — `webx:media:webp`. Не JPEG
    в 3000px в карточку шириной 400px.
37. У каждого `<img>` — `width` и `height` (файла или того размера, каким его рисует вёрстка):
    страница держит место до прихода файла, текст под картинкой не прыгает (CLS). (check: `<img>`
    без обоих — `Checks\ImageCheck`; значение может быть Blade и стоять под условием)
38. `loading="lazy"` — картинкам ниже первого экрана; `fetchpriority="high"` — одной, самой
    крупной картинке первого экрана (hero, LCP). Первый экран ленивым не делать.
39. Шрифты — `.woff2`, файл на письменность (правило 27 даёт каждому `unicode-range`), начертаний —
    сколько нужно макету (переменный шрифт — один файл на все веса); `font-display: swap` печатает
    `@webxTheme`. Без `<link rel="preload">` (§15.3: preload качает файл на каждой странице, на
    любом языке). (check: шрифт не `.woff2` — заметка, не отказ)
40. Страница грузит только то, что показывает: скрипт и стиль виджета приходят с его компонентом
    (`Widgets::need()`, WIDGETS §4), карта, видео и прочее тяжёлое стартуют у края экрана. Не класть
    библиотеку в собственный бандл темы ради одной страницы.
41. После правки вида — замер главной и самой тяжёлой страницы сайта (панель производительности
    браузера или Lighthouse, ширина телефона): самая крупная картинка (LCP), сдвиги (CLS), байты. Не
    судить о скорости на быстрой машине на глаз.

## 17. Команды

- **`webx:theme:make <имя> [--uses=<пакет>] [--local] [--path=<каталог>]`** — заготовка по §4.
  С `--local` — `theme.json` с `title` и `uses`, `tokens.json` вида `{"defaults": {}}`, пустые
  `src/css/theme.css` и `src/js/theme.js`, тест на `ThemeContract` плюс «сайт стоит на этой теме»;
  сьют `Theme` дописывается в `phpunit.xml` сайта. Без `--local` — пакетная тема в
  `packages/<имя>`, по умолчанию над `webx-ui/theme-default` (у новой темы нет токенов, и тест без
  нижней был бы красным): `composer.json` (`type: webx-theme`, лицензия `proprietary` — открыть тему
  решает владелец), собранный пустой `dist/`, `package.json`, `vite.config.js` (`theme.js` — только
  если файл есть), `phpunit.xml.dist`, тест на контракте, CI (`dist/` пересобирается без изменений,
  контракт). Каждое имя из `uses` проверяется до записи; непустой каталог — отказ. Сайт к пакету
  команда не подключает: печатает, как. Тест зелёный сразу.
- **`webx:theme:sync [--force] [--dry-run]`** — по порядку: `dist/` и `assets/` слоёв (§13.2), CSS
  модулей (§10.2), спрайт иконок (§13.1), потом шаги пакетов с тегом `webx-themes.sync`
  (`Contracts\SyncStep` — для файлов; своих шагов у пакетов WebX UI сейчас нет). Только файлы:
  `--force` копирует их заново, типов блоков команда не пишет — их ставит
  `webx:blocks:import --theme` (§9.2). Отказ — код 1 после всего остального.
- **`webx:theme:check [<путь>] [--locales=…]`** — без установки, тема сайта или тема по пути
  (`Checks\ChainCheck`): манифест и цепочка; `tokens.json` каждого слоя по словарю (и `schemes`) и
  пресет; замечаниями — контраст правила 29 во всех палитрах и тёмное значение, оставшееся от нижнего
  слоя под перекрашенным светлым (§7.6); CSS
  слоёв, нижних слоёв (виджеты) и установленных модулей по §8; типы блоков слоёв — документ, §8,
  совместимость перекрытия (§9.2); иконки — файл (имя строчными через дефис, `viewBox`, окраска
  только `currentColor`/`none`…, без скрипта и обработчиков) и шаблоны слоёв (имя, которого нет в
  цепочке, инлайновый `<svg>`); `theme_asset('…')` с буквальным путём, которого нет, или выходящим
  из `assets/`; слова по `locales` (§15.2); шрифты — грани и покрытие письменностей языков сайта
  (§15.3); письма слоёв и модулей — `var(`, буквальный цвет в `style`, `<style>`, старых атрибутах
  и запасном значении `theme_token()` (§7.5). Строка на находку (`файл:строка что — почему`), итог
  и код 1; чисто — итог по каждому пункту и 0.
- **`webx:theme:show [--json]`** — что цепочка даёт и откуда: слои сверху вниз, нижние
  пакеты (виджеты), выбранный пресет и все пресеты цепочки, каждый токен с типом, значением
  (ссылка на другой токен — с раскрытым), слоем или пресетом, который его задал, и тёмным значением со
  слоем (§7.6); каждая вьюха слоёв
  — кто её отдаёт (сайт, слой, модуль для `vendor/<ns>/…`) и кого она прячет; типы блоков с
  перекрытыми слоями, иконки, шрифты, CSS модулей. Читает только файлы. `--json` — для скрипта
  и агента; без темы — `null`.
- **`webx:theme:extract <vendor/имя> [--path=packages/<имя>]`** и
  **`webx:theme:eject [<vendor/имя>] [--path=theme]`** — §14.3.

## 18. Тесты

**`WebxUi\Themes\Testing\ThemeContract`** — трейт для PHPUnit-теста темы, пакетной или локальной:

```php
final class ThemeTest extends TestCase
{
    use ThemeContract;

    protected function themePath(): string { return dirname(__DIR__); }
}
```

Проверяет: цепочка строится с темой наверху; у каждого токена словаря цепочки есть значение;
`ChainCheck` без находок по самой теме (модули и виджеты читает `webx:theme:check` сайта);
контраст WCAG AA шести пар (правило 29) в значениях по умолчанию, в каждом пресете и в тёмной
схеме каждого из них (§7.6; только hex — другая запись остаётся глазам); верхний `components/layout` держит обязательные директивы и зоны
(правило 21); вьюхи темы компилируются (неизвестный компонент модуля пропускается — модуля может не
быть там, где идёт тест); у пакетной темы `dist/` собран из текущего `src/`. Сами проверки —
`Testing\ThemeProbe`, списками «что не так»: тесты движка держат к тому же контракту то, что
написали `make`, `extract` и `eject`.

В монорепе:

- `themes`: цепочка на фикстурах — порядок вьюх на всех уровнях (фейковый модуль **после**
  провайдера тем), ромб, цикл, ненайденная тема, пакет не того типа; слияние токенов и проверка
  типа значения; пресет из манифеста и ошибка на неизвестный; `@webxTheme` без темы не печатает
  ничего; слова, иконки, ассеты, шрифты, письма; страницы ошибок; `make`, `extract`, `eject`;
  `webx:theme:show` — источник каждого токена, вьюхи, блока и иконки.
- `theme-default`: `ThemeContract` — это и есть проверка механики на настоящей теме; плюс шесть
  блоков, ни одного слова в шаблонах, `locales` совпадают с `lang/`.
- `module-blocks`: новые пункты `Lints`; импорт слоёв — все ветки §9.2 (`ImportThemeTest`), sync и
  boot типов не пишут; настоящие блоки `theme-default` через импорт; предложение модуля уступает
  типу цепочки (§10.3).
- Модули с публичными страницами: `ThemeContractTest` на `ModuleThemeContract` (§10.2).
- `module-admin`: `webx:setup` с темой целиком на подменённых процессах — порядок шагов, `.env`,
  `--theme`, `--no-theme`, свой лейаут, повторный прогон; демо из цепочки; предупреждение о языке
  демо; состояние сайта (§20).
- Браузер (не jsdom) — на стартовом сайте, §18.4.

### 18.1 Как проверяем: стартовый сайт и слои проверок

Юнит-тесты пакетов проверяют механизм, но не то, ради чего он сделан: что **новый сайт** открывается
оформленным, вид меняется правкой `theme/`, а агент справляется по правилам. Для этого нужен сайт,
который ровно такой, каким будет каждый новый, — и ни одно из имеющихся мест на эту роль не годится:
плейграунд — панель на фикстурах без Laravel и Blade; доки — VitePress на Vue; демо-сайт панели —
демо модулей со своей историей и своим видом.

**Слои, снизу вверх:**

| Слой                  | Где                                                   | Когда                          | Что ловит                                                    |
| --------------------- | ----------------------------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| Юнит-тесты пакетов    | CI монорепы                                           | каждый PR                      | механизм: цепочка, токены, sync, разметка компонентов (§18)  |
| `ThemeContract`       | CI монорепы на `theme-default`, у сайта — на `theme/` | каждый PR                      | правила темы, которые проверяет машина (§16.1)               |
| Стартовый сайт        | одноразовый сайт рядом с монорепой, подключён к ней   | в работе над темой и виджетами | путь нового сайта целиком; глазами и замерами                |
| Витрина               | раздел демо `theme-default` на стартовом сайте        | там же                         | каждый виджет и блок во всех вариантах, в контексте страницы |
| Проверки в браузере   | Playwright по витрине, **локально**                   | перед PR в темы и виджеты      | замеры из спек: прокрутка, меню, шапка, согласие, контраст   |
| Настоящие устройства  | стартовый сайт на хостинге хомлаба                    | после этапа                    | жесты, iOS, высота экрана, медленная сеть                    |
| Репетиция с агентом   | стартовый сайт и макет                                | после выпуска                  | хватает ли правил и обратной связи для агента                |
| Первый настоящий сайт | —                                                     | дальше                         | хватает ли словаря, блоков, виджетов и дверей §10.5          |

### 18.2 Стартовый сайт

Эталон «нового сайта», **отдельный** от демо-сайта панели: тот — демо модулей, этот — то, что
получает каждый, кто сегодня запускает `webx:setup`. Смешивать их — не знать, что именно
проверяешь.

- **Одноразовый.** `scripts/starter-site.sh` сносит каталог (`STARTER_PATH`, рядом с чекаутом) и
  базу (`webx_starter_test`) и собирает заново: `composer create-project` скелета → подключение к
  монорепе тем же переключателем, что у других сайтов (`packages.mjs local`) → `webx:setup`, затем явно блоки темы, предложения и `webx:demo`
  с типовым набором модулей корпоративного сайта и тремя языками (`en,ru,pl`: один с кириллицей,
  один с расширенной латиницей) → сборка → `webx:doctor`, `webx:theme:check`, тест темы, ответы
  главной, языков, `/cms` и витрины. `--with=blog,services,events,vacancies,press,recipes` — модули
  сверх корпоративного набора, чьи страницы одевает тема; `--down` — только снос. Адрес, база,
  администратор и его пароль — переменными, их можно держать в `.env.starter` в корне монорепы (не
  в git). Сломалось после пересборки — сломалось у каждого будущего сайта; это главный тест, и
  запускать его стоит при каждой правке `webx:setup`, `theme-default` или скелета.
- **Ничего руками.** Всё, что на нём есть, — результат команд. Если что-то пришлось поправить руками,
  это находка: её место в `webx:setup`, теме или скелете, а не на сайте.
- **Свой `theme/` не правится** — он остаётся пустой заготовкой, чтобы сайт показывал чистый
  `theme-default`. Для опытов с локальной темой — ветка в git сайта, которую пересборка сносит.
- **Снос не трогает монорепу.** До `rm -rf` скрипт снимает все ссылки в каталоге сайта
  (`vendor/webx-ui/*`, `node_modules/@webx-ui/*`, `public/storage`); осталась ссылка — отказ;
  каталог под git (клон копии на хостинге, §18.5) — отказ: пересборка снесла бы его вместе с `.git`.
- Стартовый сайт включает FAQ и перелинковку `module-seo` (`WEBX_SEO_FAQ`, `WEBX_SEO_LINKS`) — новый
  сайт по-прежнему без них, стартовый показывает всё, что одевает тема.
- Ловушки сборки сайта рядом с монорепой (симлинки в `vendor`, кеш стилей блоков после
  пересборки, `resources/theme` до sync) — в `docs/pitfalls/packages-and-demo-sites.md`.

### 18.3 Витрина

Раздел демо `theme-default` — «Kitchen sink»: по странице на блок и на виджет, со всеми вариантами и
крайними случаями — шапка в каждом режиме, длинное и короткое меню, слайдер всех вариантов в узкой
колонке и на всю ширину, видео и карта до и после согласия, телефоны с одним и пятью номерами, часы в
выходной и в праздник, таблица шире экрана в прозе, длинные слова на немецком и польском. Разделы —
Blocks, Modules (форма, длинные крошки, меню, FAQ и ссылки), Icons, Assets, Fonts, Mail; страницы
модулей на стартовом сайте — сами себе витрина.

- Сеется вместе с остальным демо `theme-default` и убирается `webx:demo --remove`: на настоящем сайте
  её нет.
- Это аналог страниц компонентов в доках, только на Blade, в настоящей теме, в контексте страницы.
- Каждый этап тем и виджетов добавляет свои страницы; этап без страницы витрины не закрыт (кроме
  этапа-команды, у которого вида нет).

### 18.4 Проверки в браузере

Playwright по витрине стартового сайта, **локально** (`pnpm test:starter`), а не в CI: гейт и так
упирается в память и время. Запускается перед PR, который трогает `themes`, `theme-default`,
`widgets`, модули с базовым видом или скелет. Проверяет то, что в спеках записано замером, а не
взглядом:

- нет горизонтальной прокрутки на 360px ни на одной странице (`scrollWidth` против `clientWidth`);
- левые кромки всех детей `.site-main` совпадают; под темой нет инлайн-`<style>` модулей;
- пресет перекрашивает блоки, оболочку, иконки и страницу модуля (`getComputedStyle` до и после);
- контраст пар `text`/`bg`, `accent-contrast`/`accent`, `text-muted`/`surface` и текста блоков и
  модулей в каждом пресете; цели ≥ 44px;
- на `/ru`, `/pl` и их 404 — ни одного английского слова словарей темы и виджетов в оболочке;
  кириллица не грузится на английской странице;
- виджетные замеры — §16 спеки виджетов (меню, шапка, якоря, согласие, слайдер).

Результат — отчёт со скриншотами каждой страницы на 375 и 1280 в каждом пресете: его и показывают
человеку, а не «тесты зелёные».

### 18.5 Настоящие устройства

Копия стартового сайта на хостинге хомлаба (создание сайта и деплой по пушу в его репозиторий).
Там не монорепа, а пакеты из реестра: канал `next` во время этапа
(`docs/architecture/WEBX_UI_PHP_RELEASE.md`), выпущенные версии — после релиза. Модули и демо на ней —
результат команд, а не правок руками. Её репозиторий склонирован рядом с монорепой — там правится
`theme/` под дизайн, пуш из клона деплоит. С телефонов проверяются жесты (свайп меню и слайдера,
щипок в лайтбоксе), высота экрана и панель браузера iOS, медленная сеть.

### 18.6 Репетиция с агентом

После выпуска, до первого настоящего сайта: агент получает стартовый сайт, обезличенный макет и
только то, что получит любой агент, — `AGENTS.md` и команды. Смотрим, где он упёрся, какой дверью
(§10.5) пошёл не туда, где правила §16.1 промолчали, где `webx:theme:check` сказал не то или не
сказал ничего. Каждая находка — правка `AGENTS.md`, новый пункт проверки или заготовки, а не
подсказка агенту в чате. Репетиция повторяется после правок, пока агент не доходит до результата
без подсказок.

## 20. Состояние сайта

Шов в `module-admin`, рядом с `BrandingSource`, для второй части (сайты по подписке), но без
привязки к ней — пригодится и для режима обслуживания.

```php
interface SiteStateSource
{
    public function state(): SiteState;
}

final class SiteState
{
    // ok | notice | panel_locked | site_locked
    public function __construct(
        public readonly string $level,
        public readonly ?string $message = null,       // готовая строка для панели, на её языке
        public readonly ?CarbonImmutable $next = null, // когда наступит следующий уровень
        public readonly ?string $action = null,        // ссылка «что сделать», если есть
    ) {}
}
```

По умолчанию — источник, который всегда отвечает `ok`; реализацию привязывает тот, кто её написал.

| Уровень        | Панель                                                                                                                            | Публичный сайт                                                         | MCP |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | --- |
| `notice`       | полоса над экраном с `message`, датой `next` и `action`; закрыть нельзя                                                           | —                                                                      | —   |
| `panel_locked` | вход работает; вместо экранов — экран с `message` и `action`; API отвечает 423 на всё, кроме входа, `GET /api/cms/me` и состояния | работает                                                               | 423 |
| `site_locked`  | как `panel_locked`                                                                                                                | 503 со страницей `errors.suspended` из цепочки и `Retry-After` в сутки | 423 |

- Ничего не удаляется ни на одном уровне: блокировка — middleware, а не действие над данными.
  Снятие — следующий ответ `ok`.
- `503`, а не `403`/`410`: поисковик понимает «временно» и не выкидывает страницы сразу.
- **Отказ источника никогда не блокирует.** `SiteStateResolver` кеширует ответ на его `ttl`;
  исключение → последний известный ответ, пока не истёк его срок; иначе `ok` и `Log::warning`.
  Блокирующий уровень выводится только из ответа, никогда из ошибки — тест на это обязателен.
- Проверка: middleware `/api/cms` и манифест панели (`state` рядом с `branding`), полоса и экран в
  `AdminShell`; middleware группы `web` при `site_locked` с пропуском `/cms`, `/_preview`, `/oauth`,
  `/themes/` и маршрутов здоровья; общий вход инструментов MCP.

## 21. Вторая часть: каталог тем и сайты по подписке

Проектируется после того, как первая часть обкатана на новых сайтах. Что уже решено и на чём стоит:

- **Тема каталога — пакет**, обычно вынесенный из локальной темы удачного сайта
  (`webx:theme:extract`, §14.3), ставится `webx:setup --theme=<пакет>` с локальной `theme/` поверх.
  Где живут такие пакеты — публично или в приватном реестре — решается тогда; механизм от этого не
  зависит.
- **Галерея** — сайты на темах каталога с рыбным содержимым.
- **Пакеты контента по нишам** (`"type": "webx-content"`: `demo/`, `regions/`, `assets/img/` и
  `for` — на какой теме рисуется): галерея получается как «тема × ниша», а писать и переводить
  приходится сумму, а не произведение. В цепочке демо (§7.1) — выше темы.
- **Сайты по подписке** — каждый отдельной установкой на нашем сервере, полная изоляция, без
  многосайтовости. Владелец правит содержимое, вид сайта — нет (§2, решение 12), конструктор блоков
  у него закрыт. Обновление парка — `composer update` + `webx:theme:sync` на каждом сайте.
- **Оплата** — отдельный сервис; сайт узнаёт состояние через шов §20: предупреждение → блок панели →
  блок сайта, без удаления.
- **Парк сайтов** (создать, обновить, приостановить) — инфраструктура хостинга, отдельная спека.

## 22. Отложено и открытые вопросы

- **Темы магазинов** — после того как оттестированы модули магазина: базовый вид каталога и его
  спутников (§10.6) и проверка на настоящем магазине.
- **Конструктор для владельца сайта.** По умолчанию закрыт (§9.2). Открыть кому-то — выдать
  `blocks.manage`; нужно ли это вообще — открыто.
- **Смена темы на живом сайте.** Внутри одной базы (`theme-default` снизу) она дешевле: универсальные
  блоки общие, сопоставлять нужно только собственные блоки темы. Не раньше, чем будет вторая тема.
- **Поле «иконка» у блока** — выбор из спрайта цепочки прямо в форме блока. Пока иконка карточки —
  SVG из медиатеки (`pictures: icon`).
- **Иконки виджетов из спрайта под темой.** Стрелки слайдера, крестик диалога, гамбургер меню —
  `webx-widgets::icons.*`, свои, чтобы виджет рисовался и без темы. Под темой
  (`theme_active()`) брать иконку из спрайта, если в цепочке есть то же имя, — тогда тема
  перерисует их файлом в `icons/`.
- **Правила, которые машина пока не держит.** В §16.1 у правил 1 (вид вне цепочки), 5 (имя-оттенок
  в `vocabulary`), 9 (`.b-<slug>` в `src/css`), 13 (голый селектор вне прозы), 14 (`!important`) и
  22 (свежесть перекрытой вьюхи модуля) стоит «check», но `webx:theme:check` их не читает; в
  `RULES.md` у них пометки нет. Свежесть перекрытия требует версии вьюхи у модуля — решить,
  чем её мерить. Остальные — строчные проверки `src/css` и `vocabulary`.
- **`webx:theme:sync --link`** (§14.2) — симлинк вместо копии для правки пакетной темы из монорепы
  — не построен; пока `sync` после сборки.
- **Демо SEO требует блог** (`requires()` — `articles`): без `--with=blog` вопросы и ссылки витрины
  не сеются.
- **Существующие сайты** — переходят на тему, только если хотят: `webx:theme:make theme --local`
  и перенос своего вида в неё по §6. Ничего не меняется для сайта, у которого `webx-themes.theme`
  пуст: провайдер не трогает пути, `@webxTheme` не печатает ничего.

Решения, принятые при постройке и не записанные выше:

- **Строгость по источнику.** `tokens.json`, `"preset"` манифеста — код: ошибка бросается. Страница
  при этом ничего не бросает из-за неопубликованного или несобранного (§7.3), иконка и ассет без
  файла — пустые (§13). `Tokens` — синглтон: значения между запросами одного процесса не меняются.
- **`theme-default` без своего JavaScript** — интерактивное у виджетов; `src/js/theme.js` у неё не
  заведён. «Skip to content» — слово темы (`shell.skip`), а не виджета шапки: ссылку печатает
  лэйаут первой в `<body>`, даже когда зону `header` заменили в панели.
- **Хлебные крошки** — строкой `flex-wrap` без маркеров, разделитель — `::before`; узкая таблица
  модуля возвращает себе `display: table` (проза делает таблицы блоком с прокруткой).
- **Блоки `theme-default`:** своя переменная блока — только кольцо фокуса кнопки (`--hero-ring`
  …); поверх картинки — тень цвета текста и слова цветом фона, в `night` обе пары разворачиваются
  вместе; у `cards` колонки — наибольшее число, решает контейнер; повторитель карточек — `cards`, а
  не `items` (тест витрины ищет вложенные блоки по `values.items`); часы `contact` без своей подписи
  — таблица часов называет себя сама.
- **Демо `columns` остаётся типом `module-blocks`**: тема его не несёт, а `allow: ["text"]` берёт тот
  `text`, что стоит.
- **Отчёт `webx:theme:show`** схлопывает `vendor/composer/../webx-ui/<имя>` строкой, не разрешая
  ссылку path-репозитория, — иначе в отчёте был бы путь чекаута монорепы.
- **`extract`** удаляет тест сайта и пустую заглушку `src/js/theme.js`; `dist/` собирает человек.
  `composer remove` пакета печатает ошибку хука `pre-package-uninstall` скелета — удаление идёт
  дальше.

из §22. Playwright «background video» под нагрузкой нестабилен.
