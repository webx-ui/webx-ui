# Темы сайта — спецификация

Статус: спроектировано 07.10.2026, третья редакция 08.10.2026 — тема по умолчанию публичная, каждый
новый сайт получает свою локальную тему поверх неё, модули — нижний слой темы (§10); каталог тем
и сайты по подписке — вторая часть (§21). В работе с 09.10.2026 (ветка `hot/2026-10-09`): TH1.1 —
движок `webx-ui/themes` с манифестом, цепочкой и порядком вьюх; TH1.2 — словарь, слияние токенов,
`@webxTheme`, `theme_token()` и `webx:theme:sync` для ассетов; TH1.3 — пакет `webx-ui/theme-default`:
значения всех токенов, пресеты, лейаут с шапкой и подвалом, CSS оболочки и прозы; TH1.4 — `webx:theme:make --local`, `webx:setup` создаёт `theme/` (`--theme=`,
`--no-theme`), скелет без лейаута и инлайн-стилей; как легло в код — §23. Пакеты — новые `webx-ui/themes` и
`webx-ui/theme-default` (§3), правки в `module-admin` (§14), `module-blocks` (§8, §9),
`module-settings` (§7.4) и в модулях с публичными страницами (§10). Соседние спеки: новый сайт —
[`WEBX_UI_NEW_SITE.md`](WEBX_UI_NEW_SITE.md), блоки — [`WEBX_UI_MODULE_BLOCKS.md`](WEBX_UI_MODULE_BLOCKS.md),
зоны — [`WEBX_UI_LAYOUT_REGIONS.md`](WEBX_UI_LAYOUT_REGIONS.md), языки — гайд
`apps/docs/guide/languages.md`, где живут стили сайта сегодня — гайд `apps/docs/guide/styles.md`.

Сегодня вид сайта — это файлы самого сайта: `layout.blade.php`, `app.css`, шапка и подвал, плюс
типы блоков в базе. Новый сайт открывается восемьюдесятью строками `<style>` в лейауте, и весь
настоящий вид пишется с нуля — на каждом сайте заново, без общих правил. На деле это кончается
одним стилевым файлом на тысячи строк, где стили блоков, оболочки и страниц модулей перемешаны и
держатся на буквальных цветах; и второй сайт «как первый, только другого цвета» — копия первого,
которая с первого дня живёт своей жизнью.

Ответ — **тема**: набор файлов, устроенный по одним правилам (§4, §6), который сайт не копирует, а
надстраивает. Слоями:

```
theme/                      ← локальная тема сайта: только его отличия
  → webx-ui/theme-default   ← тема по умолчанию: оболочка, токены, универсальные блоки
    → модули                ← вид своих страниц и свои блоки (§10)
```

Новый сайт получает `theme/` на `theme-default` сразу при `webx:setup` и открывается уже
оформленным. Дальше вид сайта — это правка `theme/` под его стиль: токены, оболочка, свои блоки.
Исправления `theme-default` и модулей приходят `composer update`, как сегодня исправления модулей.
Владелец сайта меняет цвета и шрифты, которые тема открыла, **из панели**.

Всё публичное: движок, тема по умолчанию, гайд и заготовка для агентов. Каталог готовых тем и
сайты по подписке строятся поверх того же механизма потом (§21): удачная локальная тема выносится
в пакет одной командой.

## 1. Границы

**Внутри (первая часть):**

- движок `webx-ui/themes`: цепочка слоёв, словарь токенов, проверки, sync, команды (§3, §7, §8);
- `webx-ui/theme-default`: оболочка, токены, универсальные блоки (§12); интерактивное — пакет виджетов (§11);
- устройство темы и манифест (§4, §5); где лежит какой стиль (§6);
- модули как нижний слой: вид своих страниц, свои блоки, точки расширения (§10);
- иконки и ассеты (§13); демо, языки, шрифты (§15);
- новый сайт с локальной темой, цикл разработки, вынос и отвязка (§14);
- документация для агентов и заготовка новой темы (§16);
- шов «состояние сайта» в панели (§20) — он нужен второй части, но живёт в публичном
  `module-admin` и ни от чего здесь не зависит.

**Вторая часть (§21):** каталог тем и галерея, пакеты контента по нишам, сайты по подписке и парк
сайтов, приватные пакеты — если понадобятся.

**Снаружи:**

- **Темы магазинов.** Механизм §10 для каталога описан, но вид витрины в `theme-default` и
  проверка на настоящем магазине — после того как оттестированы модули магазина.
- **Многосайтовость.** Тема здесь — одна цепочка на установку. Спека
  [`WEBX_UI_MULTISITE.md`](WEBX_UI_MULTISITE.md) (§7 там) проектирует тему как каталог вьюх на сайт
  внутри одной установки; когда до неё дойдёт, цепочка из этой спеки станет источником того
  каталога, а не вторым механизмом.
- **Смена темы на живом сайте** — отложено (§22).

## 2. Принятые решения (не переоткрывать)

1. **Тема — слой, а не копия.** Сайт надстраивает тему и перекрывает только своё (§7.1). Копия «на
   старте» отвергнута: исправление в теме не доедет ни до одного сайта, который её уже скопировал.
   Копия остаётся осознанным шагом — `webx:theme:eject` (§14.3).
2. **Каждый новый сайт — со своей локальной темой.** `webx:setup` кладёт `theme/` на
   `theme-default`, потому что тема по умолчанию сразу переписывается под стиль сайта, и этой
   правке нужно место, которое не затрёт обновление. Сайт без темы — флаг `--no-theme`.
3. **Движок и тема по умолчанию — разные пакеты.** Движок знает механизм и словарь, тема по
   умолчанию — обычный его потребитель, ровно как будущие каталожные темы. Выходят одной общей
   версией composer-пакетов, лишней работы с релизом нет.
4. **Модуль отвечает за вид своих страниц сам.** Тема по умолчанию не знает ни услуг, ни команды,
   ни каталога: модуль несёт вьюхи, базовый CSS на токенах и свои блоки (§10). Тема перекрывает,
   если хочет. Иначе каждый новый модуль — правка темы по умолчанию, а модуль, которого в ней
   забыли, выглядит голой разметкой.
5. **Блок модуля ставится один раз и дальше принадлежит сайту.** Это уже так (`BlockOffers`, §10.3):
   модуль предлагает простой блок — список записей и пара полей, — сайт его берёт и правит под себя.
6. **CSS знает только токены сайта.** Как компоненты ядра знают только `--wx-*`. Цвет или шрифт,
   написанный буквально, не перекрашивается ни пресетом, ни правкой в панели — и они тихо
   перестают работать на половине страницы (§8). Это касается и CSS модулей.
7. **Словарь токенов — в движке и общий для всех.** `--site-color-accent` значит одно и то же в
   любой теме и в любом модуле: модуль может написать базовый вид, не зная, какая тема стоит.
8. **У каждого стиля одно место** (§6). Второго общего файла на тысячи строк не будет, потому что
   ему некуда встать.
9. **Интерактивное — в пакете виджетов, а не в теме и не в модуле.** Слайдер, лайтбокс, видео,
   карта, согласие на cookie, меню, диалог, вкладки — один пакет `webx-ui/widgets` (§11): логика
   готова, вид — каркас на токенах, который тема перекрашивает. Модуль, которому нужен слайдер, не
   тащит свой. Движок тем остаётся без JavaScript.
10. **Типы блоков из пакетов — у пакетов, содержимое — у сайта.** Типы темы обновляются из пакета
    (§9); страницы, меню, зоны, тексты сеются один раз и дальше принадлежат сайту (§15).
11. **Шрифты — свои файлы, не внешний CDN.** Сторонний запрос шрифта на каждой странице — передача
    IP посетителя третьей стороне, и для сайтов в ЕС это вопрос согласия (§15.3).

## 3. Пакеты и роли

| Роль                  | Где                     | Что несёт                                                                                                            |
| --------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Движок**            | `webx-ui/themes`        | цепочка, словарь токенов, слияние, проверки, sync, команды, заготовка, `ThemeContract`, гайд для агентов             |
| **Тема по умолчанию** | `webx-ui/theme-default` | оболочка, значения токенов и пресеты, типографика, универсальные блоки, вид виджетов, иконки, шрифты, письма, ошибки |
| **Локальная тема**    | `theme/` в сайте        | отличия сайта: токены, оболочка, свои блоки, перекрытия                                                              |
| **Модуль**            | `webx-ui/module-*`      | вьюхи своих страниц, базовый CSS на токенах, предложенные блоки, точки расширения (§10)                              |

**`webx-ui/themes`** — библиотека без префикса `module-`: тема рисуется и без панели, а правка
токенов — вкладка в `module-settings` (§7.4). Namespace `WebxUi\Themes`, таблиц нет:

- `ThemeManifest`, `ThemeChain` — манифест и цепочка (§5, §7.1);
- `ThemeServiceProvider` — пути вьюх, `@webxTheme`, `theme_asset()`, `theme_token()`,
  `<x-theme::icon>`;
- `Vocabulary`, `Tokens` — словарь и слияние значений (§7);
- команды `webx:theme:sync`, `check`, `make`, `eject`, `extract` (§17);
- `Testing\ThemeContract` (§18); `AGENTS.md` и `stubs/` заготовки (§16).

**`webx-ui/theme-default`** — composer-пакет `"type": "webx-theme"`, устроенный по §4. Задача — не
быть красивым, а быть **хорошей отправной точкой**: аккуратная нейтральная типографика, сетка,
оболочка, которую не стыдно показать в первый день, и ясный код, который удобно переписать.

## 4. Устройство темы

Одинаковое у `theme-default`, локальной темы и любой будущей. Каталогов, которых нет, просто нет.

```
theme/
├── composer.json          ← манифест (§5); у локальной темы — theme.json с тем же содержимым
├── tokens.json            ← значения токенов и пресеты (§7)
│
├── views/                 ← Blade
│   ├── components/        ← layout, header, footer, общие куски оболочки
│   ├── vendor/<ns>/       ← перекрытия вьюх модулей: vendor/webx-pages/show.blade.php …
│   ├── mail/              ← письма (§7.5)
│   └── errors/            ← 404, 500, suspended
│
├── blocks/*.json          ← типы блоков: схема, шаблон, СВОЙ CSS, свой скрипт (§9)
├── regions/*.json         ← стартовые шапка и подвал деревьями блоков (§15.1)
│
├── src/
│   ├── css/               ← оболочка, сетка, типографика, перекрытия вида модулей (§6)
│   └── js/                ← то, что живёт вне блоков и не является виджетом (§11)
├── icons/*.svg            ← иконки (§13.1)
├── assets/
│   ├── fonts/             ← файлы шрифтов (§15.3)
│   └── img/               ← фоны, декор, заглушки
├── dist/                  ← собранное: theme.css, theme.js, icons.svg, manifest.json с хешами
│
├── lang/<locale>/theme.php ← слова вёрстки (§15.2)
├── demo/<module>/*.json   ← демо-содержимое, если тема несёт своё (§15.1)
├── preview/               ← обложка и скриншоты
└── tests/ThemeTest.php    ← use ThemeContract (§18)
```

`src/` и сборка (Vite) живут там, где лежит тема. У пакета `dist/` входит в выпущенную версию — его
собирает CI перед тегом, сайту Node для пакетной темы не нужен. У локальной темы `src/` собирает
сам сайт, тем же `npm run build`, что уже есть в скелете.

## 5. Манифест

```json
{
  "name": "webx-ui/theme-default",
  "type": "webx-theme",
  "extra": {
    "webx": {
      "theme": {
        "title": "Default",
        "uses": [],
        "requires": ["module-pages", "module-blocks", "module-menu", "module-inbox"],
        "locales": ["en", "ru", "uk", "de", "pl", "fr", "es", "it", "pt", "tr"],
        "editable": ["color-accent", "color-accent-contrast", "font-heading"],
        "fonts": [
          {
            "family": "Inter",
            "files": "assets/fonts/inter-*.woff2",
            "scripts": ["latin", "latin-ext", "cyrillic"]
          }
        ]
      }
    }
  }
}
```

| Ключ       | Смысл                                                                                                    |
| ---------- | -------------------------------------------------------------------------------------------------------- |
| `title`    | как тема называется                                                                                      |
| `uses`     | на чём стоит; у локальной темы нового сайта — `["webx-ui/theme-default"]`                                |
| `requires` | модули, без которых тема не рисуется; складываются по цепочке; `webx:doctor` ругается на нехватку        |
| `locales`  | на каких языках есть слова вёрстки и демо; тест держит их полными (§18)                                  |
| `editable` | какие токены владелец меняет в панели; остальные — только пресетом; решает верхний слой, который объявил |
| `fonts`    | файлы и письменности, которые они покрывают (§15.3)                                                      |

Остальное — по соглашению из §4: есть `views/` — это вьюхи, есть `blocks/` — это блоки. Ключ,
который повторяет имя каталога, — второе место для ошибки, а не гибкость.

Локальная тема держит то же самое в `theme/theme.json` (ключ `theme` на верхнем уровне): у неё нет
своего `composer.json`, и заводить его ради манифеста незачем.

## 6. Где лежит какой стиль

| Что                                                    | Где                                                     |
| ------------------------------------------------------ | ------------------------------------------------------- |
| Цвет, шрифт, радиус, отступ, тень — значения           | `tokens.json`, и больше нигде буквально                 |
| Вид **одного блока**                                   | в самом блоке, под `.b-<slug>`                          |
| Оболочка: шапка, подвал, сетка, контейнер              | `src/css` темы                                          |
| Типографика текста (`h1`–`h6`, списки, цитаты в прозе) | `src/css` темы по умолчанию; локальная перекрывает      |
| Базовый вид страниц модуля (статья, услуга, товар)     | CSS модуля на его классах `webx-<module>-*` (§10.2)     |
| Свой вид страниц модуля на этом сайте                  | `src/css` темы, на тех же классах; или перекрытая вьюха |
| Вид виджета (стрелки слайдера, баннер cookie)          | `src/css` темы на классах `webx-<виджет>-*` (§11)       |
| Поведение блока                                        | скрипт блока — по контракту входа (§10 спеки блоков)    |
| Слайдер, лайтбокс, меню, диалог, согласие              | пакет виджетов (§11); тема только оформляет             |

Правило проверки: если стиль описывает один тип блока, ему место в блоке, и `webx:theme:check`
предупреждает о селекторе `.b-<slug>` в `src/css`. Всё, что в таблице, подчиняется проверке на
токены (§8).

## 7. Токены сайта

### 7.1 Цепочка слоёв

```
сайт        resources/views и правки в панели
локальная   theme/
по умолч.   vendor/webx-ui/theme-default
модули      vendor/webx-ui/module-*
```

| Что    | Как складывается                                                                               |
| ------ | ---------------------------------------------------------------------------------------------- |
| Вьюхи  | ищутся сверху вниз, первая найденная побеждает                                                 |
| CSS    | подключается снизу вверх: модули → тема по умолчанию → локальная; верхний перекрывает каскадом |
| JS     | виджеты по требованию (§11), потом снизу вверх `dist/theme.js` слоёв                           |
| Токены | значения сливаются снизу вверх: тема по умолчанию → локальная → пресет → правки владельца      |
| Блоки  | тип верхнего слоя перекрывает тип нижнего с тем же slug (§9)                                   |
| Иконки | спрайты сливаются по имени, верхний слой побеждает                                             |
| Слова  | `theme::` ищется сверху вниз по ключу                                                          |
| Демо   | первый слой сверху, у которого есть `demo/<module>/`, побеждает целиком (§15.1)                |

Цепочка любой длины: «тема на основе темы» — та же цепочка на слой длиннее. Цикл в `uses` — ошибка
при загрузке. `webx-themes.theme` — путь к локальной теме (`'theme'`) или имя пакета.

**Порядок вьюх.** Общий путь — `View::addLocation()` для каждого слоя **после** `resources/views`,
в порядке цепочки. Пространства имён модулей тоньше: Laravel кладёт `resources/views/vendor/<ns>`
первым при `loadViewsFrom()` модуля; `prependNamespace()` слоя поставил бы его **перед** сайтом.
Поэтому провайдер, загружаясь после модулей, перестраивает подсказки пространства целиком —
`[сайт, локальная, по умолчанию, ...пути модуля]` через `View::replaceNamespace()`. Тест — на все
уровни, иначе перепутанный порядок молча отдаёт вьюху модуля вместо темы.

Конфиг модулей (`webx-pages.layout`, `webx-catalog.layout`, `webx-blocks.layout`) **не меняется**:
он называет компонент `'layout'`, а какой файл за ним — решает порядок поиска. `<x-dynamic-component>`
и `FileViewFinder` кешируют разрешённые имена на процесс; с одной цепочкой на установку это
безвредно — пути ставятся при загрузке и больше не меняются.

Что верх цепочки обязан дать, чтобы сайт открылся: `components/layout.blade.php` с `@webxTheme`,
`@webxSeo`, `@webxBlocks` и зонами `header`/`footer`. У `theme-default` он есть; локальная тема его
наследует, пока не перекроет.

### 7.2 Словарь

Словарь — в движке, один на всех: темы, модули, блоки. Первая редакция:

| Группа   | Токены                                                                                                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Цвет     | `color-bg`, `color-surface`, `color-surface-muted`, `color-text`, `color-text-muted`, `color-border`, `color-accent`, `color-accent-contrast`, `color-accent-2`, `color-highlight`, `color-danger`, `color-success` |
| Шрифт    | `font-body`, `font-heading`, `font-size-base`, `line-height-base`, `font-size-1` … `font-size-6`                                                                                                                    |
| Шкала    | `space-1` … `space-8`, `radius-sm`, `radius-md`, `radius-lg`, `radius-full`                                                                                                                                         |
| Глубина  | `shadow-sm`, `shadow-md`                                                                                                                                                                                            |
| Сетка    | `container-width`, `gutter`                                                                                                                                                                                         |
| Движение | `duration`, `easing`                                                                                                                                                                                                |

На странице это `--site-<имя>`. Цвета — **роли, а не оттенки**: у корпоративного сайта бренд — три-пять
цветов, и словарь из одного акцента кончается тем, что тема заводит `--site-olive`, а блоки перестают
переноситься. Поэтому `accent`, `accent-2`, `highlight`, `surface-muted` — и у каждой темы своё
значение.

Тема **может** расширить словарь своими токенами — ключом `vocabulary` в `tokens.json` (`имя → тип`:
`color`, `length`, `font`, `shadow`, `number`, `time`). Блоки этой темы их видят; модули и блоки
`theme-default` — нет. Расширение словаря в движке — обычное изменение пакета с changeset'ом;
удаление токена — ломающее.

`theme-default` **обязана** дать значение каждому токену словаря (тест, §18); любая тема выше — нет:
недостающее берётся снизу.

Почему не `--wx-*`: это токены панели, на публичный сайт они не грузятся, и у них другая жизнь —
шкала панели меняется по нуждам панели, а сайты от этого перекрашиваться не должны.

### 7.3 Слияние и вывод

```
значения theme-default → значения локальной → выбранный пресет → правки владельца (только editable)
```

```json
{
  "defaults": { "color-accent": "#0e6b5c", "font-heading": "Inter", "radius-md": "10px" },
  "presets": {
    "warm": { "title": "trans::theme::presets.warm", "tokens": { "color-accent": "#b4532a" } },
    "night": {
      "title": "trans::theme::presets.night",
      "tokens": { "color-bg": "#111418", "color-text": "#e8eaed" }
    }
  }
}
```

`@webxTheme` в `<head>` печатает `<link>` на CSS слоёв (§13.2), `@font-face` (§15.3), виджеты,
заявленные на странице (§11), и один `<style>` с `:root { --site-… }` — результат слияния, инлайном, чтобы смена пресета не
требовала пересборки ни одного файла. Значения из базы проходят проверку типа токена на записи и
на выводе: строка из панели не должна уметь закрыть `</style>`.

### 7.4 В панели

Вкладка **«Внешний вид»** в `settings.index` — патчем экрана от `webx-ui/themes`, если тема стоит и
`module-settings` установлен:

- выбор пресета — карточками с образцом цвета;
- поля только для токенов из `editable`: цвет — `WxColorPicker`, шрифт — список из `fonts` цепочки;
- «Вернуть как в пресете» на каждом поле;
- логотип и название — уже в общих настройках (`PanelBranding`), здесь ссылкой.

Хранится ключом `appearance` в настройках (`{ preset, tokens }`). Без `module-settings` тема
рисуется на значениях слоёв и пресете из конфига `webx-themes.preset`. MCP: `settings_get` /
`settings_set` уже покрывают ключ; ресурс `theme://tokens` отдаёт агенту словарь, итоговые
значения, пресеты и что открыто для правки.

### 7.5 Письма

Почтовые клиенты не понимают CSS-переменных, а многие — и `<style>` в `<head>`. Поэтому в письмах
токены — **значения**, подставленные на сервере: `theme_token('color-accent')` возвращает итог
слияния §7.3, и вьюхи `views/mail/` пишут его в `style="…"`. Шрифт — семейство из токена и общий
запасной: свои файлы шрифта почта не грузит. `webx:theme:check` предупреждает о буквальном цвете в
письме, который не пришёл из `theme_token()`: письмо тогда не перекрашивается вместе с сайтом.

## 8. CSS знает только токены

Сегодня при сохранении типа блока `Lints::check()` предупреждает о селекторах без префикса
`.b-{slug}`, голых элементах и `@media` (§15 спеки блоков). Добавляется:

- буквальный цвет в значении свойства: `#…`, `rgb()`/`rgba()`/`hsl()`/`oklch()`, именованный цвет.
  Исключения — `transparent`, `currentColor`, `inherit`, `initial`, `unset`;
- буквальное семейство шрифта в `font-family`/`font` (кроме общих `sans-serif`, `serif`,
  `monospace`, `system-ui`);
- `var(--site-…)`, которого нет в словаре цепочки — та же ловушка, что `--wx-space-20` в ядре:
  несуществующая переменная молчит;
- запасное значение `var(--site-x, #fff)` — тоже буквальный цвет: не перекрашивается, та же дыра,
  только тише.

| Где                                   | Как строго                                          |
| ------------------------------------- | --------------------------------------------------- |
| Блок, сохранённый в панели            | предупреждение                                      |
| Блок, пришедший из слоя при sync (§9) | запрет: тип не ставится                             |
| `src/css` темы, CSS модуля            | запрет в `webx:theme:check` и в тесте пакета (§18)  |
| `tokens.json`                         | единственное место, где буквальное значение законно |

## 9. Блоки

### 9.1 Универсальные блоки `theme-default`

Примитивы, из которых собирается почти любая корпоративная страница, — без привязки к модулям,
кроме формы, которая есть на каждом сайте:

| Блок         | Что                                                           |
| ------------ | ------------------------------------------------------------- |
| `hero`       | заголовок, подзаголовок, одна-две кнопки, фон или картинка    |
| `text`       | проза с типографикой темы                                     |
| `media-text` | картинка и текст рядом, сторона на выбор                      |
| `cards`      | сетка карточек: иконка или картинка, заголовок, текст, ссылка |
| `cta`        | полоса призыва с кнопкой                                      |
| `contact`    | контакты из общих настроек и форма `module-inbox` по выбору   |

Каждый — со своим CSS на токенах, на `@container`, без медиа-запросов. Блоки модулей (услуги,
команда, отзывы, FAQ, каталог) — не здесь, а в модулях (§10.3).

### 9.2 Sync

Слои несут типы в `blocks/*.json` — формат `webx:blocks:export` (§17 спеки блоков). Итоговый набор:
типы нижнего слоя, поверх — типы верхнего с тем же slug (перекрытие целиком). Перекрывать схему
можно только совместимо — те же поля с теми же типами плюс новые; `webx:theme:check` сверяет, иначе
содержимое, заполненное под нижний блок, в верхнем потеряется.

`webx:theme:sync` для итогового набора:

1. Проверяет каждый тип (§8 и обычные проверки публикации).
2. Считает хеш содержимого файла.
3. Типа нет — создаёт, публикует, пишет `blocks.theme_source` (слой) и `blocks.theme_hash`.
4. Тип есть и `theme_hash` равен хешу опубликованной версии — на сайте его не трогали — создаёт
   новую версию из файла и публикует. Совпадает с файлом — ничего.
5. Тип правили в панели после последнего sync — **пропускает** и пишет строкой: «hero: changed on
   this site since the theme last set it, kept». `--force` перезаписывает.
6. У типа `theme_source` пуст — это тип сайта (или предложенный модулем, §10.3) с тем же slug.
   Отказ с объяснением: молча присвоить чужой тип — значит при следующем обновлении затереть чужую
   работу.

Типы, которые слои перестали нести, **не удаляются**: на них могут стоять страницы.

Локальная тема — тоже слой, и её блоки едут тем же sync. Обычный путь нового сайта: блок делается
в панели, выгружается в `theme/blocks/` (`webx:blocks:export --path=theme/blocks`) и коммитится —
тогда вид сайта целиком лежит в git, а не только в базе.

Права. Конструктор блоков закрыт отдельным правом `blocks.manage` (по умолчанию у
супер-администратора, §16 спеки блоков), `webx-blocks.editing = false` выключает правку типов
целиком. Владелец сайта по умолчанию получает содержимое и не получает конструктор.

`webx:theme:sync` идемпотентна — её зовут `webx:setup`, `post-update-cmd` скелета и тот, кто
обновляет много сайтов разом.

## 10. Модули в теме

Тема по умолчанию не знает модулей, кроме обязательных (§9.1). Каждый модуль с публичными
страницами сам несёт всё, чтобы выглядеть прилично на любой теме, и оставляет теме четыре двери —
от дешёвой к дорогой.

### 10.1 Разметка и классы

Вьюхи модуля печатают семантическую разметку с классами **`webx-<module>-<элемент>`** по БЭМ — так
уже сделан каталог (`webx-catalog-card`, `webx-catalog-card__price`, `webx-catalog-filter__group--…`).
Классы — **публичный контракт модуля**: переименование ломает темы, поэтому идёт как ломающее
изменение, с записью в README. Список классов и что они значат — в `AGENTS.md` модуля (§16).

Модули, у которых сегодня разметка без классов, получают их в этапе TH3.

### 10.2 Базовый вид

Модуль несёт `resources/theme/<module>.css` — свой базовый вид на токенах словаря (§7.2), под
своими классами, на `@container`. Это нижний слой цепочки (§7.1): он подключается, только если
модуль установлен, и проходит ту же проверку на токены (§8). Задача — не красота, а «прилично в
любой теме»: сетка карточек, отступы, состояния, читаемые цены и фильтры.

Без этого слоя каждый модуль либо голый на любой новой теме, либо требует правки
`theme-default` — а модулей больше двадцати, и их добавляется больше, чем тем.

### 10.3 Блоки модуля

Модуль предлагает простые типы блоков — список своих записей плюс поля вокруг: заголовок, подпись,
кнопка, сколько показать. Механизм уже есть: `BlockOffers` — файл `webx:blocks:export` в
`resources/blocks` модуля, сайт ставит его **один раз**, и дальше тип по этому slug не трогается:
его переделывают под сайт (так сейчас у `module-faq`, `module-press`, `module-recipes`,
`module-services`).

С темами добавляется одно: если в цепочке есть тип с тем же slug, ставится **он**, а не
предложение модуля. Так тема может нести свой вид блока «услуги» и быть уверенной, что на новом
сайте стоит именно он. Если тип уже стоит на сайте, ничего не меняется — правило «один раз»
сильнее.

CSS предложенных блоков — тоже на токенах (§8): блок модуля, поставленный на сайт с любой темой,
сразу в её цветах.

### 10.4 Точки расширения

Места внутри вьюх модуля, куда спутник или тема добавляют своё, не перекрывая вьюху целиком, —
`@webxPart('<точка>', $data, '<вьюха по умолчанию>')` (как `catalog.card.badges`,
`catalog.card.meta`). Точки и данные, которые в них приходят, — тоже публичный контракт модуля.
Тема регистрирует свою вьюху на точку в `views/parts/<точка>.blade.php` — без провайдера и без
кода.

### 10.5 Четыре двери, от дешёвой к дорогой

| Хочу                                       | Делаю                                                                            |
| ------------------------------------------ | -------------------------------------------------------------------------------- |
| другие цвета, шрифты, отступы              | токены — модуль подхватит сам                                                    |
| другой вид карточки, фильтра, страницы     | CSS в `src/css` темы на классах `webx-<module>-*`                                |
| добавить кусок (бейдж, кнопку, блок рядом) | вьюха на точку расширения (§10.4)                                                |
| другую разметку целиком                    | перекрыть вьюху в `views/vendor/<ns>/` — и следить за ней при обновлениях модуля |

Последняя дверь самая дорогая: перекрытая вьюха не получает исправлений модуля. `webx:theme:check`
перечисляет перекрытые вьюхи и предупреждает, если вьюха модуля изменилась после того, как тема её
перекрыла (сверка по хешу, записанному при перекрытии в `theme.json`).

### 10.6 Пример: каталог

| Что на витрине                 | Откуда                                                                                                |
| ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| листинг, сортировка, пагинация | вьюхи `webx-catalog::grid`, `sort`, `pagination` + `catalog.css` модуля                               |
| фильтры                        | `webx-catalog::filter` + группы по виду (`--range`, `--swatch`…); на телефоне — виджет `dialog` (§11) |
| страница товара                | `webx-catalog::product`; галерея — слайдер `gallery`, увеличение — лайтбокс (§11)                     |
| слайдеры товаров на страницах  | предложенные блоки «товары категории», «новинки» — слайдер `cards`                                    |
| бейджи, наличие                | точки `catalog.card.badges`, `catalog.card.meta` — у спутников                                        |

Тема магазина (вторым этапом) меняет витрину в основном второй дверью — CSS на классах, — и
третьей для своих вставок. Перекрытие вьюх каталога — исключение.

## 11. Виджеты

Всё интерактивное, что повторяется из сайта в сайт, — отдельный пакет `webx-ui/widgets`, спека
[`WEBX_UI_WIDGETS.md`](WEBX_UI_WIDGETS.md): лёгкие поведения (меню, диалог, вкладки, аккордеон),
слайдер на Swiper, лайтбокс, видео, карта, согласие на cookie с блокировкой стороннего до согласия.

Для темы из этого важно три вещи:

- пакет — **нижний слой цепочки**, как модуль: его вьюхи компонентов перекрываются в
  `views/vendor/webx-widgets/`, CSS идёт первым в каскаде, иконки — в общий спрайт, блоки —
  предложениями;
- вид виджета меняется теми же дверями, что вид модуля (§10.5): токены, в том числе локальные
  `--webx-<виджет>-*`; CSS на классах `webx-<виджет>-*`; перекрытие вьюхи компонента;
- скрипт и CSS виджета грузятся **только на странице, где он стоит**: компонент заявляет себя, а
  `@webxTheme` печатает заявленное.

`theme-default` зависит от `widgets`: шапка — виджет `<x-webx-header>` с мобильным меню внутри, ссылка «Настройки
cookie» в подвале, вид баннера согласия.

## 12. Что ещё в `theme-default`

- **Оболочка:** шапка на виджете `<x-webx-header>` — логотип из настроек, `menu('header')`,
  телефоны (`<x-webx-phones>` с «Заказать звонок» в окне); мобильное меню она собирает сама из тех
  же слотов; подвал — контакты, часы, соцсети, переключатель языка и «Настройки cookie» из виджетов,
  данные — из вкладки «Контакты» настроек; подвал с `menu('footer')` и контактами; обе — фолбэки зон `header`/`footer`.
- **Типографика прозы** — для `text`, страниц и статей.
- **Вьюхи модулей, которые есть почти везде:** страница (`webx-pages`), форма (`webx-inbox`); вид
  остальных — у самих модулей (§10.2).
- **Письма** (§7.5), **страницы ошибок**, иконки (20–30 штук: стрелки, телефон, почта, место,
  соцсети, галочка), один шрифт с латиницей, расширенной латиницей и кириллицей.
- **Два-три пресета** — чтобы вкладка «Внешний вид» с первого дня что-то делала.
- **Демо** главной и одной вложенной страницы на десяти языках (§15).

## 13. Иконки и ассеты

### 13.1 Иконки

`icons/*.svg` каждого слоя собираются в `dist/icons.svg` — спрайт из `<symbol>` с `id` по имени
файла. Sync сливает спрайты цепочки (верхний слой побеждает по имени).

```blade
<x-theme::icon name="phone" />
<x-theme::icon name="arrow-right" class="b-hero__arrow" />
```

Компонент печатает `<svg><use href="…/icons.svg#phone"/></svg>` с `aria-hidden`, если не передан
`label`. Работает в оболочке, вьюхах модулей и шаблонах блоков. Цвет — `currentColor`, поэтому
иконка перекрашивается вместе с текстом. Неизвестное имя — пустой `<svg>` и предупреждение в
`webx:theme:check`, а не исключение на живой странице.

### 13.2 Ассеты

`webx:theme:sync` кладёт `dist/` и `assets/` пакетных слоёв в `public/themes/<имя>/<версия>/`; их
отдаёт веб-сервер как статику с вечным кешем (`/themes/` → `immutable` в конфиге сервера скелета).
Новая версия — новый путь, сбрасывать кеш не нужно; sync оставляет одну предыдущую версию для
страниц, отданных за секунду до обновления. Локальная тема собирается в `public/build` тем же Vite
сайта, что и сегодня.

```blade
<img src="{{ theme_asset('img/wave.svg') }}" alt="">
```

`theme_asset()` ищет файл по цепочке сверху вниз. `public/themes/` — в `.gitignore` скелета: это
производное от `vendor/`, как `public/build`.

## 14. Новый сайт

### 14.1 `webx:setup`

После выбора модулей и до демо:

1. ставит `webx-ui/theme-default` тем же дочерним процессом, что ставит модули;
2. `webx:theme:make theme --uses=webx-ui/theme-default --local` — каталог `theme/` с
   `theme.json`, пустым `tokens.json`, пустыми `src/css/theme.css` и `src/js/theme.js`, тестом;
   вход Vite скелета (`vite.config.js`) указывает на них;
3. пишет `webx-themes.theme = 'theme'`;
4. `webx:theme:sync` — блоки `theme-default` и модулей (§9, §10.3), ассеты (§13);
5. демо — из цепочки (§15), если не `--no-demo`.

`--no-theme` — как сегодня: свой лейаут, свои стили. `--theme=<пакет>` — вместо `theme-default`
стоит другая тема (это путь второй части, §21), локальная `theme/` создаётся поверх неё так же.

Восемьдесят строк `<style>` в лейауте скелета уходят: лейаут теперь у темы.

### 14.2 Цикл разработки

Сайт подключён к монорепе так же, как сегодня (`scripts/link-panel.sh` / `packages.mjs local`), и
`vendor/webx-ui/theme-default` — симлинк на чекаут. Локальная тема — `npm run dev` сайта:
Vite пересобирает `theme/src` на лету. Правка `theme-default` из монорепы — `vite build --watch` в
её каталоге и `webx:theme:sync --link`: вместо копии ставится симлинк `public/themes/default/dev` →
её `dist/` и `assets/`, и `theme_asset()` в `APP_ENV=local` отдаёт файлы без версии.

### 14.3 Вынос и отвязка

**`webx:theme:extract <vendor/имя>`** — обратное: локальная тема становится пакетом. Каталог
`theme/` переезжает в новый каталог пакета с `composer.json` из `theme.json`, `uses` сохраняется,
сайт переключается на пакет через `path`-репозиторий. Так удачный дизайн становится темой, которую
можно поставить второму сайту, — дорога в каталог (§21).

**`webx:theme:eject`** — наоборот: пакетная тема (не `theme-default`) копируется в `theme/`, и
дальше обновления этой темы не приходят. Осознанный шаг для сайта, у которого отличий стало больше,
чем общего.

## 15. Демо, языки, шрифты

### 15.1 Демо

Модуль сеет демо (`ProvidesDemo`, §9 спеки нового сайта) из первого слоя сверху, у которого есть
`demo/<module>/`, иначе — из своего `resources/demo/`. Формат и журнал (`DemoLedger`) те же,
`webx:demo --remove` убирает и это демо. `DemoPlan` спрашивает у `ThemeChain` путь фикстур раньше
собственного. Зоны `header` и `footer` (`regions/*.json`) сеются так же: это содержимое, и после
установки принадлежат сайту.

### 15.2 Языки

Любое строковое значение в фикстурах может быть картой языков:

```json
{ "title": { "en": "Harbor Logistics", "de": "Harbor Logistik", "pl": "Harbor Logistyka" } }
```

- поле с `localized` получает карту, урезанную до языков сайта (`--locales` в `webx:setup`);
- поле без `localized` — строку на основном языке сайта, а если её нет — на `en`;
- язык сайта, которого нет в демо, — `webx:setup` предупреждает до установки.

Слова вёрстки — «Read more», «Send», «All services» — в `lang/<locale>/theme.php` слоёв,
пространство `theme::`, ищутся по цепочке по ключу. Основной словарь — у `theme-default` на десяти
языках панели; локальная тема добавляет и перекрывает только своё. Слова модулей на их страницах —
в словарях модулей, как сейчас. Тест паритета ключей — тот же, что в каждом пакете.

Картинки в демо — без текста: картинку не переведёшь.

### 15.3 Шрифты и письменности

Манифест объявляет письменности, которые покрывают файлы шрифта. `webx:theme:check` и `webx:doctor`
сверяют их с языками сайта: `ru`/`uk` — `cyrillic`, `pl`/`tr` — `latin-ext`. Без этого сайт на
польском рисует `ą` и `ł` запасным шрифтом, и видно это только глазами. `@webxTheme` печатает
`@font-face` с `unicode-range` по письменностям — кириллица не грузится на английской странице.

## 16. Для агентов

Задача: агент, которому сказали «сделай вид сайта как на этом макете», знает, что править, где, и
чем проверить — не читая исходники движка.

- **`AGENTS.md` движка** (`webx-ui/themes`) — как устроена тема: цепочка, §4, §6, словарь, четыре
  двери модулей (§10.5), команды, «чего не делать» (буквальные цвета, стили блока вне блока,
  перекрытие вьюхи, когда хватает CSS).
- **`AGENTS.md` `theme-default`** — что в ней есть: блоки и их поля, классы оболочки, пресеты,
  иконки; как перекрыть каждое.
- **`AGENTS.md` каждого модуля с публичными страницами** — раздел «Look»: классы `webx-<module>-*`,
  точки расширения с данными, предложенные блоки, базовый CSS.
- **Корневой `AGENTS.md` сайта** — раздел «The site's look» (сейчас ведёт на гайд по стилям)
  указывает на `theme/` и перечисляет цепочку этого сайта; его собирает `webx:panel --sync`, как
  остальное.
- **Гайд** `apps/docs/guide/themes.md` для людей, и `apps/docs/guide/styles.md` переписывается под
  тему.
- **MCP:** ресурс `theme://tokens` (§7.4) и `theme://chain` — слои, перекрытые вьюхи, блоки и их
  источник.
- **Заготовка** — `webx:theme:make` (§17): тест зелёный сразу, агент начинает с работающей темы.
- **Обратная связь** — `webx:theme:check` и `ThemeContract` говорят не «не так», а что и где:
  «b-hero: literal colour #ff4343 at line 12, use a --site-* token».

Покрытие проверяет тест `AGENTS.md`-плана (`WEBX_UI_AGENT_DOCS.md` §4): каждая команда, ключ
манифеста и токен словаря упомянуты.

### 16.1 Правила построения темы

Свод, который переходит в `AGENTS.md` движка дословно (по-английски), разделами «Do» и «Do not».
Каждое правило, которое можно проверить машиной, проверяет `webx:theme:check` — в скобках, каким
пунктом; остальное — дело глаз и ревью.

**Где работать**

1. Вид сайта правится **только в `theme/`** (или в пакете темы). Не в `vendor/`, не в
   `resources/views` сайта, не в `public/`. Перекрытие в `resources/views` — для разработчика, а не
   путь темы. (check: файлы вида вне цепочки)
2. Сначала прочитать цепочку: `webx:theme:check` или ресурс `theme://chain` — что уже есть снизу,
   какие блоки, вьюхи и токены. Не писать то, что уже даёт `theme-default` или модуль.
3. Изменение — **самой дешёвой дверью**, которая решает задачу (§10.5): токен → CSS на классах →
   точка расширения → перекрытие вьюхи. Перекрыть вьюху, когда хватало CSS, — ошибка, а не стиль.

**Токены**

4. Любой цвет, шрифт, радиус, отступ, тень, длительность — **только `var(--site-…)`**. Буквальное
   значение законно в одном месте — `tokens.json`. (check §8)
5. Нужен цвет, которого нет, — сначала роль из словаря (`accent-2`, `highlight`,
   `surface-muted`), и только если ни одна не подходит — свой токен в `vocabulary` темы с
   **ролевым** именем (`color-badge`, не `color-pink`). (check: имя-оттенок в `vocabulary`)
6. Без запасных значений в `var()`: `var(--site-x, #fff)` не перекрашивается. (check §8)
7. Значения бренда — в `defaults` локальной темы; варианты — пресетами, а не копией темы.
8. В `editable` — только то, что владелец может поменять без риска сломать вёрстку: акценты и
   шрифт заголовков, но не отступы и не размеры.

**Стили — у каждого одно место (§6)**

9. Вид одного блока — **в блоке**, под `.b-<slug>`. Селектор `.b-<slug>` в `src/css` — ошибка
   места. (check §6)
10. В `src/css` — оболочка, сетка, типографика, вид страниц модулей и виджетов на их классах.
    Больше ничего.
11. Страницы модулей стилизуются по классам `webx-<module>-*` из `AGENTS.md` модуля. Не по тегам и
    не по вложенности (`.webx-catalog-listing > div > a`): разметка внутри может поменяться, классы
    — контракт.
12. Ширину решает контейнер: `@container`, не `@media`. (check: `@media` с шириной в блоках и
    `src/css`)
13. Голых селекторов элементов (`h2`, `a`, `img`) — только в типографике прозы, под её классом.
    (check: голый селектор вне типографики)
14. Без `!important`, кроме служебных (`[hidden]`); проблема каскада решается порядком слоёв, а не
    силой. (check)

**Блоки**

15. Новый блок — только если ни один из `theme-default` (§9.1) и модулей (§10.3) не решает задачу
    полями. Другой вид существующего блока — **перекрытие того же slug**, а не новый блок с
    похожим именем.
16. Перекрытая схема — **совместима**: те же поля с теми же типами, новые — добавлять можно,
    удалять и менять тип нельзя. (check §9.2)
17. Корень блока — `data-wx-block="<slug>"`, все селекторы — под `.b-<slug>`. (lint блоков)
18. Тексты блока, которые видит посетитель, — поля схемы с `localized`, а не строки в шаблоне;
    постоянные подписи — `__('theme::…')`.
19. Слайдер, лайтбокс, видео, карта, вкладки, аккордеон, диалог — **виджетом** (§11), не своим
    скриптом и не своей библиотекой. Всё стороннее (YouTube, карты, счётчики) — только через виджет
    или с `data-webx-consent`: до согласия на странице нет ни одного запроса к третьей стороне.
    Свой скрипт — только для того, чего в виджетах нет, и по контракту входа.
20. Блок сделан в панели — выгружен в `theme/blocks/` (`webx:blocks:export --path=theme/blocks`) и
    закоммичен. Блок, который есть только в базе, потеряется при следующем развёртывании с нуля.

**Вьюхи**

21. `components/layout` держит `@webxTheme`, `@webxSeo`, `@webxBlocks` и зоны `header`/`footer`.
    (check: обязательные директивы)
22. Перекрывая вьюху модуля, копировать **текущую** версию из `vendor/` и менять минимум; классы и
    `@webxPart` оставлять на месте — на них стоят спутники модуля. (check: свежесть перекрытия)
23. Ссылки — через `route()`/адреса сущностей, никаких зашитых путей; меню — `menu('…')`, контакты
    и название — `settings()`; ни одного текста сайта в шаблоне.
24. Иконки — `<x-theme::icon>` из спрайта, не инлайновый SVG в шаблоне; картинки темы —
    `theme_asset()`. (check: неизвестная иконка, отсутствующий ассет)
25. Письма — значения через `theme_token()` в `style="…"`, без `var()`. (check §7.5)

**Языки и шрифты**

26. Каждое слово вёрстки — во всех `locales` темы; добавил ключ в `en` — добавил во все. (check:
    паритет ключей)
27. Шрифт — своими файлами в `assets/fonts/`, с письменностями всех языков сайта; без Google Fonts
    и других CDN. (check §15.3)
28. Картинки демо — без текста.

**Доступность и вёрстка**

29. Контраст текста и фона в каждом пресете — не ниже WCAG AA (4.5:1 для текста, 3:1 для крупного
    и для элементов управления). (check: контраст пар `text`/`bg`, `accent-contrast`/`accent`,
    `text-muted`/`surface` по итоговым значениям каждого пресета)
30. У интерактивного — видимый фокус (`:focus-visible`), кликабельная область не меньше 44×44 на
    телефоне.
31. Без горизонтальной прокрутки страницы на ширине 360px.

**Проверка перед тем, как сказать «готово»**

32. `webx:theme:check` — без ошибок; тест темы (`ThemeContract`) — зелёный.
33. Скриншоты в браузере: главная, одна вложенная страница и страница каждого установленного модуля
    — на десктопе и на 375px, в каждом пресете. Jsdom вёрстку не проверяет.
34. Замер, а не взгляд, где это возможно: `scrollWidth` против `clientWidth` для горизонтальной
    прокрутки, `getComputedStyle` — что токен действительно дошёл.
35. Отчёт человеку — что изменено, какой дверью (§10.5) и почему, какие вьюхи перекрыты. Решение,
    хороша ли тема, — за человеком.

## 17. Команды

- **`webx:theme:make <имя> [--uses=<пакет>] [--local] [--path=<каталог>]`** — заготовка по §4:
  манифест с `uses`, пустой `tokens.json`, `src/`, тест с `ThemeContract`, для пакета — ещё
  `composer.json`, `package.json`, `vite.config.js` и CI сборки `dist/`. Тест зелёный сразу.
- **`webx:theme:sync [--force] [--dry-run] [--link]`** — блоки (§9), ассеты и спрайт (§13).
- **`webx:theme:check [<путь>]`** — без установки: манифест, цепочка, обязательные вьюхи, значения
  токенов, CSS блоков, `src/` и модулей (§8), совместимость перекрытых схем (§9.2), стили блоков вне
  блока (§6), перекрытые вьюхи модулей и их свежесть (§10.5), иконки и ассеты по шаблонам (§13),
  письма (§7.5), полнота языков, шрифты.
- **`webx:theme:extract <vendor/имя>`**, **`webx:theme:eject`** — §14.3.

## 18. Тесты

**`WebxUi\Themes\Testing\ThemeContract`** — трейт для PHPUnit-теста темы, пакетной или локальной:

```php
final class ThemeTest extends TestCase
{
    use ThemeContract;

    protected function themePath(): string { return dirname(__DIR__); }
}
```

Проверяет: манифест валиден, цепочка строится; у `theme-default` каждый токен словаря имеет
значение, пресеты ссылаются только на объявленные токены; каждый тип блока проходит проверки
публикации и §8, перекрытые схемы совместимы; `src/css` проходит §8; иконки и ассеты из шаблонов
существуют; у каждого языка из `locales` ключи `theme.php` совпадают с `en`; демо полно по языкам;
шрифты покрывают письменности; оболочка рисуется на демо без ошибок.

В монорепе:

- `themes`: цепочка на фикстурах — порядок вьюх на всех уровнях, перекрытие блока по slug, слияние
  токенов, слова и иконки по цепочке, цикл в `uses`; проверка типа значения; `@webxTheme` без темы
  не печатает ничего; `theme_asset()`, `theme_token()`; `make`, `extract`, `eject`.
- `theme-default`: `ThemeContract` — это и есть проверка механики на настоящей теме.
- `module-blocks`: новые пункты `Lints`; sync — все ветки §9.2; предложение модуля уступает типу
  цепочки (§10.3).
- Модули с публичными страницами: CSS модуля проходит §8; классы из `AGENTS.md` есть во вьюхах.
- `module-admin`: `webx:setup` создаёт `theme/` и с `--no-theme` не создаёт; демо из цепочки;
  состояние сайта (§20).
- `module-settings`: вкладка только с темой; `editable` ограничивает поля.
- Браузер (не jsdom): новый сайт из скелета открывается оформленным; пресет перекрашивает блоки,
  оболочку, иконки и страницу модуля — замер `getComputedStyle` до и после; слайдер и диалог на
  телефонной ширине — на стартовом сайте, §18.4.

### 18.1 Как проверяем: стартовый сайт и слои проверок

Юнит-тесты пакетов проверяют механизм, но не то, ради чего он сделан: что **новый сайт** открывается
оформленным, вид меняется правкой `theme/`, а агент справляется по правилам. Для этого нужен сайт,
который ровно такой, каким будет каждый новый, — и ни одно из имеющихся мест на эту роль не годится:
плейграунд — панель на фикстурах без Laravel и Blade; доки — VitePress на Vue; `webx-cms.local` — демо
модулей со своей историей и своим видом.

**Слои, снизу вверх:**

| Слой                  | Где                                                   | Когда                          | Что ловит                                                    |
| --------------------- | ----------------------------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| Юнит-тесты пакетов    | CI монорепы                                           | каждый PR                      | механизм: цепочка, токены, sync, разметка компонентов (§18)  |
| `ThemeContract`       | CI монорепы на `theme-default`, у сайта — на `theme/` | каждый PR                      | правила темы, которые проверяет машина (§16.1)               |
| Стартовый сайт        | `webx-starter.local`, подключён к монорепе            | в работе над темой и виджетами | путь нового сайта целиком; глазами и замерами                |
| Витрина               | раздел демо `theme-default` на стартовом сайте        | там же                         | каждый виджет и блок во всех вариантах, в контексте страницы |
| Проверки в браузере   | Playwright по витрине, **локально**                   | перед PR в темы и виджеты      | замеры из спек: прокрутка, меню, шапка, согласие, контраст   |
| Настоящие устройства  | стартовый сайт на хостинге хомлаба                    | после этапа                    | жесты, iOS, высота экрана, медленная сеть                    |
| Репетиция с агентом   | стартовый сайт и макет                                | после TH6                      | хватает ли правил и обратной связи для агента                |
| Первый настоящий сайт | —                                                     | дальше                         | хватает ли словаря, блоков, виджетов и дверей §10.5          |

### 18.2 Стартовый сайт

`webx-starter.local` — эталон «нового сайта», **отдельный** от `webx-cms.local`: тот — демо модулей,
этот — то, что получает каждый, кто сегодня запускает `webx:setup`. Смешивать их — не знать, что
именно проверяешь.

- **Одноразовый.** `scripts/starter-site.sh` сносит каталог и базу и собирает заново:
  `composer create-project` скелета → подключение к монорепе тем же переключателем, что у других
  сайтов (`packages.mjs local`) → `webx:setup --demo` с типовым набором модулей корпоративного сайта и
  тремя языками (один с кириллицей, один с расширенной латиницей). Сломалось после пересборки —
  сломалось у каждого будущего сайта; это главный тест, и запускать его стоит при каждой правке
  `webx:setup`, `theme-default` или скелета.
- **Ничего руками.** Всё, что на нём есть, — результат команд. Если что-то пришлось поправить руками,
  это находка: её место в `webx:setup`, теме или скелете, а не на сайте.
- **Свой `theme/` не правится** — он остаётся пустой заготовкой, чтобы сайт показывал чистый
  `theme-default`. Для опытов с локальной темой — ветка в git сайта, которую пересборка сносит.
- Ловушки, которые всплывут при сборке сайта рядом с монорепой (симлинки в `vendor`, OSPanel, Git
  Bash), — в `docs/pitfalls/packages-and-demo-sites.md`.

### 18.3 Витрина

Раздел демо `theme-default` — «Kitchen sink»: по странице на блок и на виджет, со всеми вариантами и
крайними случаями — шапка в каждом режиме, длинное и короткое меню, слайдер всех вариантов в узкой
колонке и на всю ширину, видео и карта до и после согласия, телефоны с одним и пятью номерами, часы в
выходной и в праздник, таблица шире экрана в прозе, длинные слова на немецком и польском.

- Сеется вместе с остальным демо `theme-default` и убирается `webx:demo --remove`: на настоящем сайте
  её нет.
- Это аналог страниц компонентов в доках, только на Blade, в настоящей теме, в контексте страницы.
- Каждый этап тем и виджетов добавляет свои страницы; этап без страницы витрины не закрыт.

### 18.4 Проверки в браузере

Playwright по витрине стартового сайта, **локально** (`pnpm test:starter`), а не в CI: гейт и так
упирается в память и время. Запускается перед PR, который трогает `themes`, `theme-default`,
`widgets` или скелет. Проверяет то, что в спеках записано замером, а не взглядом:

- нет горизонтальной прокрутки на 360px ни на одной странице (`scrollWidth` против `clientWidth`);
- пресет перекрашивает блоки, оболочку, иконки и страницу модуля (`getComputedStyle` до и после);
- контраст пар `text`/`bg`, `accent-contrast`/`accent`, `text-muted`/`surface` в каждом пресете;
- виджетные замеры — §16 спеки виджетов (меню, шапка, якоря, согласие, слайдер).

Результат — отчёт со скриншотами каждой страницы на 375 и 1280 в каждом пресете: его и показывают
человеку, а не «тесты зелёные».

### 18.5 Настоящие устройства

Копия стартового сайта на хостинге хомлаба (`webx-hosting`: создание сайта, деплой по пушу в его
репозиторий). Там не монорепа, а пакеты из реестра: канал `next` во время этапа
(`docs/architecture/WEBX_UI_RELEASE_SPEED.md`), выпущенные версии — после релиза. Сайт пересобирается
так же целиком, а не латается. С телефонов проверяются жесты (свайп меню и слайдера, щипок в
лайтбоксе), высота экрана и панель браузера iOS, медленная сеть.

### 18.6 Репетиция с агентом

После TH6, до первого настоящего сайта: агент получает стартовый сайт, обезличенный макет и только
то, что получит любой агент, — `AGENTS.md` и команды. Смотрим, где он упёрся, какой дверью (§10.5)
пошёл не туда, где правила §16.1 промолчали, где `webx:theme:check` сказал не то или не сказал ничего.
Каждая находка — правка `AGENTS.md`, новый пункт проверки или заготовки, а не подсказка агенту в
чате. Репетиция повторяется после правок, пока агент не доходит до результата без подсказок.

## 20. Состояние сайта

Шов в `module-admin`, рядом с `BrandingSource`, для второй части (сайты по подписке), но без
привязки к ней — пригодится и для режима обслуживания.

```php
interface SiteStateSource
{
    public function state(): SiteState;
}

final class SiteState
{
    // ok | notice | panel_locked | site_locked
    public function __construct(
        public readonly string $level,
        public readonly ?string $message = null,       // готовая строка для панели, на её языке
        public readonly ?CarbonImmutable $next = null, // когда наступит следующий уровень
        public readonly ?string $action = null,        // ссылка «что сделать», если есть
    ) {}
}
```

По умолчанию — источник, который всегда отвечает `ok`; реализацию привязывает тот, кто её написал.

| Уровень        | Панель                                                                                                                            | Публичный сайт                                                         | MCP |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | --- |
| `notice`       | полоса над экраном с `message`, датой `next` и `action`; закрыть нельзя                                                           | —                                                                      | —   |
| `panel_locked` | вход работает; вместо экранов — экран с `message` и `action`; API отвечает 423 на всё, кроме входа, `GET /api/cms/me` и состояния | работает                                                               | 423 |
| `site_locked`  | как `panel_locked`                                                                                                                | 503 со страницей `errors.suspended` из цепочки и `Retry-After` в сутки | 423 |

- Ничего не удаляется ни на одном уровне: блокировка — middleware, а не действие над данными.
  Снятие — следующий ответ `ok`.
- `503`, а не `403`/`410`: поисковик понимает «временно» и не выкидывает страницы сразу.
- **Отказ источника никогда не блокирует.** `SiteStateResolver` кеширует ответ на его `ttl`;
  исключение → последний известный ответ, пока не истёк его срок; иначе `ok` и `Log::warning`.
  Блокирующий уровень выводится только из ответа, никогда из ошибки — тест на это обязателен.
- Проверка: middleware `/api/cms` и манифест панели (`state` рядом с `branding`), полоса и экран в
  `AdminShell`; middleware группы `web` при `site_locked` с пропуском `/cms`, `/_preview`, `/oauth`,
  `/themes/` и маршрутов здоровья; общий вход инструментов MCP.

## 21. Вторая часть: каталог тем и сайты по подписке

Обсуждено 07.10.2026, проектируется после того, как первая часть обкатана на новых сайтах. Что уже
решено и на чём стоит:

- **Тема каталога — пакет**, обычно вынесенный из локальной темы удачного сайта
  (`webx:theme:extract`, §14.3), ставится `webx:setup --theme=<пакет>` с локальной `theme/` поверх.
  Где живут такие пакеты — публично или в приватном реестре — решается тогда; механизм от этого не
  зависит.
- **Галерея** — сайты на темах каталога с рыбным содержимым.
- **Пакеты контента по нишам** (`"type": "webx-content"`: `demo/`, `regions/`, `assets/img/` и
  `for` — на какой теме рисуется): галерея получается как «тема × ниша», а писать и переводить
  приходится сумму, а не произведение. В цепочке демо (§7.1) — выше темы.
- **Сайты по подписке** — каждый отдельной установкой на нашем сервере, полная изоляция, без
  многосайтовости. Владелец правит содержимое и «Внешний вид», конструктор блоков у него закрыт.
  Обновление парка — `composer update` + `webx:theme:sync` на каждом сайте.
- **Оплата** — отдельный сервис; сайт узнаёт состояние через шов §20: предупреждение → блок панели →
  блок сайта, без удаления.
- **Парк сайтов** (создать, обновить, приостановить) — инфраструктура хостинга, отдельная спека.

## 22. Отложено и открытые вопросы

- **Темы магазинов** — после того как оттестированы модули магазина: базовый вид каталога и его
  спутников (§10.6) и проверка на настоящем магазине.
- **Конструктор для владельца сайта.** По умолчанию закрыт (§9.2). Открыть кому-то — выдать
  `blocks.manage`; нужно ли это вообще — открыто.
- **Смена темы на живом сайте.** Внутри одной базы (`theme-default` снизу) она дешевле: универсальные
  блоки общие, сопоставлять нужно только собственные блоки темы. Не раньше, чем будет вторая тема.
- **Поле «иконка» у блока** — выбор из спрайта цепочки прямо в форме блока. После TH4.
- **Тёмный режим у посетителя** — второй набор значений под `prefers-color-scheme`; не в первой
  редакции, пресет `night` — просто другая палитра.
- **Существующие сайты** — переходят на тему, только если хотят: `webx:theme:make theme --local`
  и перенос своего вида в неё по §6. Ничего не меняется для сайта, у которого `webx-themes.theme`
  пуст: провайдер не трогает пути, `@webxTheme` не печатает ничего.

## 23. Как легло в код

### TH1.1 — манифест, цепочка, порядок вьюх

Пакет `php/packages/themes` (`WebxUi\Themes`), без таблиц и без JavaScript.

- **`ThemeManifest`** — `fromPackage($path)` читает `extra.webx.theme` из composer.json и требует
  `"type": "webx-theme"` (пакет другого типа в `uses` — ошибка, а не тихий пропуск);
  `fromLocal($path, $name)` читает ключ `theme` из `theme.json`. Ключи §5 проверяются на тип,
  остальное — по соглашению: `views()` и `namespaceViews($ns)` отдают каталог, только если он есть.
- **`ThemeLocator`** — ссылка из конфига или `uses` → манифест. Сначала имя пакета (зарегистрированное
  вручную через `register($name, $path)` или известное Composer через `InstalledVersions`), потом
  каталог относительно корня проекта с `theme.json`. Имя локальной темы — та строка, которой её
  назвали (`theme`). `register()` — шов для тестов, монорепы и темы, которую разрабатывают рядом
  с сайтом без установки.
- **`ThemeChain`** — слои сверху вниз; `resolve()` — обход в глубину с обратным пост-порядком:
  каждая тема выше всего, на чём стоит, первая из `uses` выше соседей, общая база одна и под всеми
  («ромб» в тесте). Цикл — `ThemeException` с путём `a -> b -> a`; ненайденная тема — тоже, с
  именем того, кто её просил. Синглтон в контейнере, пустой при пустом конфиге.
- **`ThemeServiceProvider`** — конфиг `webx-themes.theme` (`WEBX_THEME`, по умолчанию пусто).
  Вьюхи раскладываются в `$app->booted()`, а не в `boot()`: «загрузиться после модулей» зависит от
  порядка, в котором Composer поставил пакеты, а `booted` видит все пространства имён при любом.
  Тест держит фейковый модуль **после** провайдера тем — с `boot()` вместо `booted()` он падает.
  Пространство перестраивается, только если у какого-то слоя есть `views/vendor/<ns>`; пути сайта
  узнаются по той же строке, что строит `loadViewsFrom()` (`<view.paths>/vendor/<ns>`).
- **Тесты** — на фикстурах каждый уровень порядка для простых вьюх и для `<ns>::`, `<x-layout>` из
  цепочки, итоговые подсказки пространства, пустой конфиг, цикл, ромб, ненайденная тема и пакет не
  того типа. Порядок проверяется по файлу, который нашёл `FileViewFinder`, — тот же поиск, что у
  `view()`, но без `view-string`, на который ругается Larastan.

Отступления от спеки: нет. Ошибка загрузки бросается и в консоли — сайт с испорченным
`webx-themes.theme` не запустит и `artisan`; чинится правкой `.env`, и это лучше, чем сайт,
молча потерявший слой.

### TH1.2 — словарь, слияние, `@webxTheme`

- **`TokenType`** — enum семи типов: шесть из §7.2 и `easing` (у токена `easing` словаря иначе не
  было типа: кривая — не `time` и не `number`). Проверка — список разрешённых форм на тип (hex,
  `oklch()`, `clamp()`, стек шрифтов в кавычках…) плюс общий второй замок для всех: нет `<`, `>`,
  `;`, фигурных скобок, `\`, `@`, `!`, `/*`, `url(`, управляющих символов, скобки сбалансированы,
  не длиннее 200 символов. Ссылка на другой токен сайта — `var(--site-…)` — годится любому типу;
  на `--wx-*` — нет.
- **`Vocabulary`** — `base()` (сорок токенов §7.2) и `forChain()`: база плюс `vocabulary` слоёв
  снизу вверх. Имя движка объявить заново нельзя даже тем же типом; два слоя могут объявить одно
  имя, если сходятся в типе.
- **`ThemeManifest::tokens()`** читает `tokens.json` в `TokenFile` и проверяет форму: ключи только
  `defaults`, `presets`, `vocabulary` (опечатка `default` — ошибка, а не пустая тема), имена в
  нижнем регистре, значения — строки. Тот же `read()`, что у манифеста, с другим исключением.
- **`Tokens`** (scoped в контейнере) — слияние §7.3. Пресет сливается по цепочке так же, как
  значения: локальная тема дополняет `night` базовой, не повторяя его; заголовок — верхнего слоя.
  `editable` — список верхнего слоя, который его объявил, без имён вне словаря. Строгость разная по
  источнику: `tokens.json` — код, поэтому имя вне словаря или значение не своего типа —
  `ThemeException` при первом обращении; выбор владельца — данные, поэтому неизвестный пресет и
  неподходящее значение молча отбрасываются. `css()` проверяет каждое значение ещё раз на выводе.
- **Шов для TH5** — `Contracts\Appearance` (`preset()`, `tokens()`), по умолчанию
  `ConfigAppearance` из `webx-themes.preset` (`WEBX_THEME_PRESET`) без правок; зарегистрирован
  `singletonIf`, чтобы вкладка «Внешний вид» встала своим при любом порядке провайдеров.
- **`@webxTheme`** → `ThemeHead::render()`: `<style data-webx-theme>` с `:root`, затем стили слоёв
  снизу вверх. Пакетный слой — `<link>` на `dist/theme.css` из `public/themes/`; локальный —
  `src/css/theme.css` и `src/js/theme.js` через Vite сайта (имена — зеркало `dist/` пакета).
  На странице ничего не бросает: не опубликованный пакет и не собранная локальная тема
  пропускаются, а при `app.debug` вместо них HTML-комментарий с командой. Vite спрашивается только
  о входах, которые есть в его манифесте: о пропавшем он бросает, а сайт до первого
  `npm run build` должен открываться. Без темы директива зарегистрирована и печатает пустую строку.
- **`theme_token($name, $default = null)`** — `src/helpers.php` через `autoload.files`.

Отступления от спеки:

- **`webx:theme:sync` появился уже в TH1, но только для ассетов** (§13.2): без него у пакетного
  слоя нет CSS на странице, и TH1.5 не открыл бы сайт оформленным. Блоки sync получит в TH2,
  `--link` — когда понадобится.
- **Каталог в `public/themes/<имя>/` назван хешем содержимого, а не версией** (12 знаков sha1 по
  путям и содержимому `dist/` и `assets/`); на какой смотрят страницы — файл `current` рядом. Сайт,
  слинкованный с монорепой path-репозиторием, держит одну версию, пока файлы меняются, а путь под
  `/themes/` кешируется навсегда. Копируется во временный каталог и переименовывается — страница не
  увидит половину темы; остаются текущая и одна предыдущая копия.
- `@font-face` (§15.3) и виджеты (§11) `@webxTheme` пока не печатает — их этапы TH4 и W1.

### TH1.3 — `theme-default`: токены, лейаут, оболочка

Пакет `php/packages/theme-default`, `"type": "webx-theme"`, без PHP-классов и без провайдера:
движок находит его через `InstalledVersions`, как любую тему.

- **`tokens.json`** — значение каждому из сорока токенов словаря и пресеты `warm` и `night`. Шрифты
  — системный стек (`font-heading` — `var(--site-font-body)`): свои файлы шрифта и `@font-face` —
  TH4. Заголовки пресетов — пока строки, а не `trans::theme::…`: слов вёрстки ещё нет.
- **Манифест** — `requires: [module-pages, module-blocks, module-seo]`, `editable` — три токена из
  §5. `locales` и `fonts` не объявлены: слов вёрстки и файлов шрифта ещё нет, а пустое обещание
  тест паритета (TH4) принял бы за правду.
- **`views/components/layout`** — `@webxTheme`, затем голова страницы, `@stack('head')`, зоны
  `header`/`footer` с фолбэками `components.header`/`components.footer` (ищутся по цепочке, так что
  локальная тема заменяет фолбэк, просто положив файл), `<main id="content">` и ссылка «к
  содержимому». **`@webxSeo` и `@webxBlocks` печатаются, только если слота `head` нет:** вьюхи
  модулей уже кладут обе директивы в слот, а ни одна не идемпотентна — второй вызов дал бы второй
  `<title>` и второй бандл. Своя страница сайта, написавшая `<x-layout>` без головы, получает их от
  лейаута. Шапка и подвал — логика шапки скелета (`menu('header')`, потом страницы под главной) и
  `menu('footer')` с копирайтом; название — `config('app.name')`: ключа названия в настройках нет.
  Виджет `<x-webx-header>` с мобильным меню — W1.
- **CSS** — `src/css/theme.css` импортирует `base.css` (документ, медиа, фокус), `shell.css`
  (классы оболочки `site-*`: `site-container`, `site-header__*`, `site-main`, `site-footer__*`,
  `site-bleed`, `site-skip`) и `prose.css` (типографика в `.site-main` и под `.site-prose`). Каждый
  селектор — внутри `:where()`, нулевая специфичность: локальная тема, модуль или блок перекрывают
  правило тем, что написали его, без `!important` и без копии селектора. Колонка `<main>` — ширина
  `min(100% - 2·gutter, container - 2·gutter)` и `margin-inline: auto`, а не `padding`: прямой
  ребёнок `<main>` бывает и списком, и цитатой, и отступ прозы с нулевой специфичностью иначе
  заменяет поле колонки (так и было в первой сборке: список прилипал к краю). Проза поэтому пишет
  только `margin-block`. Таблица шире колонки прокручивается внутри себя.
- **Сборка** — `vite.config.js` без зависимостей, кроме самого Vite (тот, что в монорепе или в
  сайте): вход `src/css/theme.css` → `dist/theme.css`, JS нет. `src/js/theme.js` не заведён: в
  теме нечего исполнять, интерактивное — виджеты. `package.json` пакета приватный и вне
  pnpm-воркспейса — только скрипты `build`/`watch`.
- **`dist/` закоммичен** (строка `!php/packages/theme-default/dist/` в `.gitignore`), а не
  собирается в сплите: сплит зеркалит дерево git, и сборка в нём — второй конвейер, которому
  доверять сложнее, чем тесту. Сборка пишет `dist/sources.json` — sha256 каждого файла `src/` с
  нормализованными концами строк, — а тест пересчитывает и падает, если `src/` правили без сборки.
- **Тест** `ThemeDefaultTest` — каждый токен словаря имеет значение своего типа; пресеты называют
  только токены словаря; контраст AA (4.5:1) пар `text`/`bg`, `text`/`surface`,
  `text-muted`/`bg`, `text-muted`/`surface`, `accent-contrast`/`accent`, `accent`/`bg` в значениях
  по умолчанию и в каждом пресете; `dist/` собран из текущего `src/`; в CSS нет буквального цвета,
  `var(--site-…)` вне словаря, запасного значения в `var()` и `@media` по ширине (кусок §8, который
  стоит держать уже сейчас); лейаут рисует токены, голову и обе зоны, слот `head` заменяет свою пару
  директив; лейаут найден через цепочку.

Отступления от спеки:

- **Шапка и подвал в тесте не рисуются, только компилируются.** `menu()` и модель страниц
  автозагружаются везде, где стоят их модули, в монорепе тоже, и без загруженных модулей с их
  таблицами (и макросом `nestedSet`) шапка падает на запросе. Тест лейаута подставляет шапку и
  подвал сайта (что заодно проверяет поиск фолбэка по цепочке), а настоящие проверяются в браузере на
  стартовом сайте (TH1.5). Вёрстка оболочки и прозы снята в браузере на статической странице с
  `dist/theme.css`: колонка, шапка и подвал на одной кромке, нет прокрутки на 360px, ссылки меню
  44px, `night` перекрашивает.
- «Skip to content», «Main», «Footer» — через `__()` по-английски, без словаря: слова вёрстки
  `theme::` — TH4.
- Иконок, блоков, писем, страниц ошибок и демо ещё нет — их этапы TH2 и TH4. `AGENTS.md` темы
  появился уже здесь, а не в TH6: тест покрытия гайдов (`AgentDocsCoverageTest`) требует его у
  каждого пакета с первого дня; в TH6 он дополняется блоками, пресетами и иконками.

### TH1.4 — `webx:theme:make --local`, `webx:setup` с темой, скелет без лейаута

- **`webx:theme:make <имя> --local [--uses=…] [--path=…]`** (`WebxUi\Themes\Console\MakeCommand`,
  заготовки в `php/packages/themes/stubs/local/`) — `theme.json` с `title` (имя сайта из
  `app.name`, иначе имя темы) и `uses`, `tokens.json` вида `{"defaults": {}}`, `src/css/theme.css`
  и `src/js/theme.js` (имена — `ThemeHead::LOCAL_ENTRIES`, с комментарием о трёх дверях §10.5 и
  `:where()`), `tests/ThemeTest.php`. Каждое имя из `uses` проверяется через `ThemeLocator` до
  записи: опечатка — сообщение о флаге, а не исключение на первой странице. Непустой каталог —
  отказ без записи. Без `--local` — отказ: пакетная заготовка (`composer.json`, `package.json`,
  `vite.config.js`, CI) — TH6.
- **Тест локальной темы — тест сайта, а не `ThemeContract`** (его ещё нет, TH6): `Tests\Theme\ThemeTest`
  на `Tests\TestCase` скелета проверяет, что сайт стоит на этой теме (верхний слой цепочки —
  локальный, путь — каталог теста), что токены сливаются без исключения и что у цепочки есть
  `components.layout`. Команда дописывает в `phpunit.xml` сайта сьют `Theme` с `<каталог>/tests`
  — только если тег `</testsuites>` один и каталог ещё не упомянут, иначе говорит, что добавить.
  Так `php artisan test` сайта гоняет тест темы без правки автозагрузки.
- **`webx:setup`** решает про тему в `gather()`, до установки (`Setup\ThemeChoice`):
  - новый сайт — `theme/` на `webx-ui/theme-default`; `--theme=<vendor/name>` — на другой теме
    (наш пакет — с общей версией `^x.y.z`, чужой — без ограничения); не имя пакета — отказ до
    `composer require`;
  - `--no-theme` — тема не ставится, в `resources/views/components/` пишутся лейаут, шапка и
    подвал, которые раньше лежали в скелете (с теми же восемьюдесятью строками `<style>`), плюс
    `resources/css/app.css` и `resources/js/app.js` — заготовки в `module-admin/stubs/site/`;
  - **`WEBX_THEME` уже не пуст** — тема остаётся как есть, повторный прогон только синхронизирует
    файлы; так `webx:setup` остаётся способом добавить модуль на живой сайт;
  - **у сайта свой `components/layout` и `--theme` не передан** — темы нет: это сайт, который
    жил до тем, и смена вида — не то, о чём он просил. С `--theme` поверх своего лейаута тема
    ставится, а setup предупреждает, что `resources/views` выше всех слоёв и лейаут надо удалить.

  Шаг `installTheme()` стоит после `installModules()` (пакет темы уходит в тот же `composer
require`) и **до** `wireThePanel()`: `webx:panel --sync` указывает модулям на `<x-layout>`, только
  когда находит лейаут, а у сайта с темой он в теме. Порядок внутри — `webx:theme:make`, потом
  запись `WEBX_THEME=theme` в `.env` и в окружение детей, потом `webx:theme:sync`: **`WEBX_THEME`
  на каталог, которого нет, роняет загрузку любого `artisan`** (решение TH1.1), так что имя пишется
  только после того, как каталог есть. Sync не фатален — сайт откроется с меньшим стилем.

- **`webx:panel --sync`** ищет лейаут через `view()->exists('components.layout')`, а не по файлу в
  `resources/views`: в дочернем процессе с `WEBX_THEME` цепочка уже в путях вьюх.
- **Скелет `php/site`** — `components/layout`, `header`, `footer`, `resources/css/app.css` и
  `resources/js/app.js` уехали в заготовки `--no-theme`; `regions/region.blade.php` остался (нужен
  сайту без `module-blocks`, а значит без темы). Вход Vite — `theme/src/css/theme.css`,
  `theme/src/js/theme.js`, `resources/css/app.css`, `resources/js/app.js` через
  `.filter(existsSync)`: один конфиг для сайта с темой и без, и `webx:panel --sync` по-прежнему
  дописывает `admin.ts` в тот же массив. `.env.example` — `WEBX_THEME=` и закомментированный
  `WEBX_THEME_PRESET`. `public/themes` — в `.gitignore` и `.dockerignore`.
- **Docker:** стадия ассетов берёт `theme/` из стадии `vendor` (`COPY --from=vendor /app/theme`), где
  после установки стоит `mkdir -p theme`: `COPY theme` из контекста на сайте с `--no-theme` остановил
  бы сборку. **`webx:boot`** получил шаг `webx:theme:sync` (не фатальный), если стоит
  `webx-ui/themes` и `webx-themes.theme` не пуст: `public/themes` не в репозитории и не в свежем
  контейнере.
- **`AGENTS.md` сайта** (`Agents\RootFile`) говорит про `theme/` вместо `resources/css/app.css`;
  README скелета — раздел «The look»; гайды `styles.md` и `new-site.md` переписаны под тему.
- **Тесты** — `themes`: `MakeCommandTest` (раскладка, цепочка из созданной темы, тест сайта — PHP,
  сьют в `phpunit.xml` один раз, отказы: непустой каталог, ненайденная тема, без `--local`).
  `module-admin`: `SetupThemeTest` — решение `ThemeChoice` на всех ветках и **весь `webx:setup`**
  на sqlite с подменёнными процессами: порядок `composer require` → `webx:theme:make` →
  `webx:theme:sync` → `webx:panel --sync`, `.env`, `--theme`, `--no-theme` с файлами лейаута, свой
  лейаут сайта, повторный прогон. `BootTest` — шаг sync; `PanelSyncTest` — лейаут из пути темы.
  `scripts/php-smoke.sh` проверяет, что скелет без лейаута, что после setup есть `theme/` на
  `theme-default`, `WEBX_THEME=theme` и `public/themes/webx-ui/theme-default/current`, а главная
  несёт `<style data-webx-theme>` и `<link>` на `theme.css` темы.

Отступления от спеки:
