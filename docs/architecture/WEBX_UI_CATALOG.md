# Каталог товаров — семейство модулей, архитектура

Статус: архитектура согласована 28.09.2026 (решения 1–22), адреса уточнены 29.09.2026 (решения
23–26, §8.5); ядро выпущено 29.09.2026 в v0.50.0, спутники не начаты. Спека ядра — [`WEBX_UI_MODULE_CATALOG.md`](WEBX_UI_MODULE_CATALOG.md). Этот документ — про семейство целиком: границы,
контракты ядра и раскладку по пакетам. Спека каждого модуля (схема, экраны, API, MCP, тесты)
пишется отдельным файлом `WEBX_UI_MODULE_CATALOG_<ИМЯ>.md`, когда до него доходит очередь.

Каталог — не один модуль, а ядро и спутники. Сайту-витрине без корзины хватает ядра и двух
спутников; магазину одежды — ещё таблиц размеров и группировки; магазину запчастей на 100 тысяч
позиций — свойств, поиска и обмена с учётной системой. Всё это одна установка, собранная из
разного набора пакетов, и ни один пакет не знает, какие ещё стоят рядом.

Образец, с которого снят опыт, — `C:/Work/OSPanel/home/shop.test` (85 тысяч товаров,
дальше больше 100 тысяч). Что там берём и что там слиплось — §9.

## 1. Границы

**Внутри семейства:** товары, категории, цена, свойства, метки, наличие, бренды, связи между
товарами (похожие, сопутствующие, замена), таблицы размеров, группировка, конфигурируемый
товар, поисковый движок, импорт и экспорт.

**Снаружи:** корзина, заказы, покупатели, оплата, доставка — это следующее семейство
(«commerce»), и каталог готовит ему ровно один шов: `Purchasability` (§4.4). Типы цен и валюты
(§7). Многосайтовость (решение 8). Всё, что просил конкретный клиент: производители, модели
оборудования, серийные номера, схемы (решения 7 и 9).

## 2. Принятые решения (не переоткрывать)

Приняты в обсуждении 28.09.2026.

1. **Ядро и спутники, не мономодуль.** Спутник знает только ядро; ядро не знает ни одного
   спутника. Спутник со спутником разговаривают только через реестры ядра. Исключение — настоящая
   зависимость, объявленная в `require` (группировке и конфигурируемому товару без свойств не из
   чего строить оси).
2. **Спутник хранит своё в своей таблице** с `product_id` и никогда не добавляет колонок в
   `catalog_products`. Удалили модуль — ушла его таблица, товар цел.
3. **Группировка и конфигурируемый товар — два модуля.** Группа связывает самостоятельные
   товары: каждый со своей страницей, своим местом в каталоге и в фасетах; на странице товара
   видны переключатели по осям группы (цвет, размер). Конфигурируемый — наоборот: в каталоге один
   родитель, дети без него не видны. Общее у них одно — оси берутся из свойств.
4. **Цена — в ядре и выключается конфигом.** Базовая и старая. Каталог без цены бывает, и тогда
   её нет ни в форме, ни в фасетах, ни в индексе, ни в обмене. Фасет цены — ползунок. Валюта одна,
   валюта сайта.
5. **Наличие ставится руками.** Статус — справочник с флагом «можно купить». Количество —
   опциональное поле, включается конфигом, и тогда статус может считаться по остатку. Фасет
   наличия тоже включается конфигом.
6. **Масштаб — сотни тысяч товаров.** Отсюда: поисковый движок — часть архитектуры, а не
   опциональный спутник (§5); индексация очередью и пачками (§5.3); свойства типизированные (§6.2);
   всё, что обходит каталог, обходит его пачками, а не по товару.
7. **В базе только бренд.** Производитель у reference-shop — просьба клиента, и она живёт в его
   проекте своим фасетом через `Facets`. Это и проверка шва: если чужой признак ложится в фильтр,
   индекс и обмен без правки ядра — контракты верные.
8. **Многосайтовости в каталоге v1 нет** — ни колонок, ни связей с сайтом. Её проектируют целиком
   (`WEBX_UI_MULTISITE.md`), а не закладывают заранее кусками.
9. **Оборудование, модели, серийные номера, схемы — проект reference-shop**, а не база. Вторая проверка
   шва, та же, что в решении 7.
10. **Импорт и экспорт — контракт ядра с первого дня** (§4.5). Интеграции будут всегда, и десять
    модулей с десятью импортами — ровно то, чего не должно случиться.

Имена — по правилу `module-*` для разделов панели и без приставки для библиотек. Семейная
приставка `module-catalog-` держит их рядом в `Setup\Catalogue`. Идентификатор модуля в панели —
то, что там показано: `catalog`, `properties`, `brands`.

Похожие, сопутствующие и замена — один модуль, а не три: это одна таблица (или `webx_relations`
с видом связи — решить в спеке модуля) и один интерфейс «выбрать товары», различается только
смысл. Замена вдобавок участвует в `Purchasability`: снятый с производства товар отвечает
«нельзя, есть замена».

Адаптеры обмена (CSV, YML, CommerceML/1С, Google Merchant) — отдельные пакеты поверх §4.5;
сколько их и какие первые — §7.

## 4. Контракты ядра

Имена и сигнатуры — набросок для спеки ядра, не окончательные.

### 4.1. `Facets` — что можно отфильтровать

Реестр фасетов. Фасет регистрирует модуль, которому принадлежит признак: цену — ядро (если она
включена), бренд — бренды, наличие — наличие (если включено конфигом), каждое свойство с флагом
«в фильтре» — свойства, производителя — проект reference-shop.

```php
interface Facet
{
    public function key(): string;          // 'price', 'brand', 'p.color'
    public function kind(): FacetKind;      // Terms | Range | Toggle
    public function label(): string;
    public function field(): IndexField;    // как признак лежит в индексе
    public function labels(array $values): array; // id значения → подпись, пачкой
    public function applySql(Builder $query, FacetValue $value): void; // для SQL-движка
}
```

Фасет не считает сам. Счётчики, диапазоны и то, что при выбранном бренде фасет брендов
показывает и остальные бренды (фасет без собственного фильтра), — поведение движка, одно на
всех. У reference-shop этот код был написан трижды и отдельно для каждого типа — §9.

Какие фасеты видны в какой категории и в каком порядке — настройка категории в ядре (у reference-shop
так же, и это удачно).

### 4.2. `ProductDocument` — из чего собран документ индекса

Каждый модуль дописывает свои поля в поисковый документ товара — **пачкой**, а не по одному:

```php
interface DocumentContributor
{
    /** @return list<IndexField> */
    public function fields(): array;

    /** @param Collection<int, Product> $products  @return array<int, array<string, mixed>> */
    public function contribute(Collection $products): array;
}
```

Движок собирает схему индекса из `fields()` всех вкладчиков и сравнивает её с живой (как
`manticore:update-tables` у reference-shop). Ядро кладёт категории **вместе с предками** — у reference-shop
это закомментировано, и счётчики по дереву пересчитывались в PHP квадратичным циклом.

### 4.3. `CatalogEngine` — кто отвечает на запрос каталога

```php
interface CatalogEngine
{
    public function search(CatalogQuery $query): CatalogResult; // ids страницы, total, facets
    public function index(Collection $products): void;
    public function remove(array $ids): void;
}
```

Две реализации: `SqlEngine` в ядре (честно работает на небольших каталогах) и `ManticoreEngine`
в `catalog-manticore`. Выбор — конфигом. Витрина получает id страницы и поднимает из базы только
их, сохраняя порядок движка.

### 4.4. `Purchasability` — можно ли купить и почему нет

Цепочка правил, каждое может отказать с причиной:

- наличие — «нет в наличии, заказать нельзя» (флаг статуса);
- связи — «снят с производства, есть замена»;
- конфигурируемый товар — «не выбран вариант»;
- ядро — «цена не указана», если цена включена.

Корзины сейчас нет; этот вопрос — единственное, что она будет задавать каталогу. Пока его
задают карточка товара («Купить» или «Узнать цену» через `module-inbox») и MCP.

### 4.5. `ExchangeColumns` — обмен

Каждый модуль объявляет свои колонки обмена: ключ, подпись, как прочитать пачку товаров и как
записать значение. Ядро держит конвейер:

- ключ сопоставления строки с товаром — артикул, настраивается;
- чтение потоком, запись пачками в очереди, каждая пачка — одна транзакция;
- журнал запуска с ошибками по строкам (строка, колонка, причина), а не «импорт упал»;
- профили — сохранённое сопоставление колонок файла с колонками обмена;
- по окончании пачки — пометка товаров для индексации одним запросом (§5.3), а не по товару.

Формат (CSV, XML, YML, CommerceML) — адаптер поверх колонок, отдельным пакетом. Колонки
отключённого признака (цена, остаток) не объявляются вовсе.

### 4.6. `RelatedProviders` — подбор связанных

Сначала ручные связи, не хватило — алгоритм: «та же категория и бренд», «близкая цена»,
«покупали вместе» (когда появятся заказы). Алгоритм регистрирует любой модуль; `module-catalog-links`
только спрашивает реестр.

### 4.7. Остальное — уже существующие швы

| Нужно                                            | Чем                                                               |
| ------------------------------------------------ | ----------------------------------------------------------------- |
| Адрес товара, категории, бренда                  | `routing`: строки реестра, а не маршрут на категорию при загрузке |
| Вкладка или поле спутника в форме товара         | патч экрана `catalog.product-form`                                |
| Витрины на страницах («акции», «новинки бренда») | `CollectionSource` + `wx-collection` + `BlockOffers`              |
| Выборки в шаблоне                                | `RecordQuery`: `products()->brand('x')->label('sale')`            |
| Бейдж, наличие, бренд в карточке                 | точки `@webxPart` в компоненте `product-card`                     |
| Ссылка на товар из меню                          | `LinkSource`                                                      |
| SEO товара и категории                           | `HasSeo` из `module-seo`                                          |

## 5. Масштаб

### 5.1. Что считает движок, а что база

База — источник правды и место записи. Список, фильтр, счётчики, диапазоны, сортировка на
витрине — движок. Админский список товаров — база с индексами и пагинацией; поиск по нему — §8.

### 5.2. Сохранение не зависит от индекса

Упавший Manticore не роняет ни сохранение товара, ни импорт: товар помечается и ждёт. Витрина
при недоступном движке отвечает понятно (и может упасть на `SqlEngine`, если каталог это
выдерживает), `webx:doctor` показывает очередь и доступность. У reference-shop не так: ни одного
`try` вокруг Manticore, сохранение товара падает вместе с поиском.

### 5.3. Индексация

- Любой модуль, изменивший своё, помечает товары: `Catalog::touch($ids)` — одна вставка в
  очередь индексации, без обращения к движку.
- Воркер забирает пачку, собирает документы у всех вкладчиков одним проходом на пачку и отдаёт
  движку. Повтор той же пачки безвреден.
- Полная перестройка — `webx:catalog:index --rebuild` пачками, со схемой из §4.2.
- Изменение справочника (свойство переименовали, метку удалили) помечает затронутые товары
  запросом, а не циклом.

### 5.4. База

Индексы на всём, по чему ищут и соединяют, — с первой миграции (у reference-shop нет индекса даже на
артикуле). Порядок записей без `max(position) + 1` на каждом создании. Кеш — настоящий (store
Laravel), а не память одного запроса.

## 6. Ядро и свойства — главное про данные

### 6.1. Товар

`catalog_products`: артикул (уникальный), переводимые название и слаг, публикация, цена и старая
цена (nullable, `decimal`), основная категория колонкой (от неё адрес) плюс связь с
дополнительными категориями, описание. Каким будет содержимое товара — §8.

### 6.2. Свойства

Типизированный EAV, как у reference-shop: свойство (тип: справочник, число, текст; флаги «несколько
значений», «в фильтре», «в карточке», «на странице»), справочник значений, значения товара —
одна строка на значение, с отдельными колонками под id значения, число и текст. Наборы свойств
привязаны к категориям. В индекс справочные значения идут одним многозначным полем глобально
уникальных id, числа — JSON-атрибутом по id свойства, чтобы новое числовое свойство не меняло
схему индекса.

Чего у reference-shop не повторяем: тип свойства там смешан с псевдотипами фильтров (бренд, цена,
наличие). У нас свойство — это свойство, а фильтр — фасет.

## 7. Отложено

- Типы цен (розница, опт) и несколько валют.
- Производитель и прочие «вторые бренды» в базе (решение 7).
- Многосайтовость (решение 8).
- Корзина, заказы и всё семейство «commerce».
- «Покупали вместе» — до появления заказов.

## 8. Решения второго круга (28.09.2026)

11. **Посадочные страницы фильтров будут** — SEO их потребует всегда. Делаем «как удобнее», форма —
    §8.1 (предложение, не утверждено).
12. **Содержимое товара — только rich-text** (`wx-rich-text`). Никаких блоков у товара.
13. **Картинки товара — своя галерея, не библиотека `module-media`.** Загрузка прямо на сервер
    (и по адресу при импорте), но у каждой картинки правятся `alt` и `title` — так же, как в
    галерее на основе файлового менеджера. Полмиллиона файлов в дереве библиотеки не нужны ни
    дереву, ни редактору.
14. **Поиск в админке — тем же движком, что на сайте.** Стоит Manticore — админский список ищет и
    фильтрует им; на каталоге в сотню товаров Manticore не нужен, и там работает `SqlEngine`.
    Значит, в индексе лежат и неопубликованные товары, а витрина отсекает их фильтром.
15. **Обмен: CSV и XLS.** Для 1С — отдельное API, интеграцию пишет интегратор 1С, а не мы.
    YML и прочие фиды — позже, тем же контрактом.
16. **Связи товаров — универсальные и расширяемые:** виды связи регистрируются (похожие,
    сопутствующие, замена — наши; «запчасти», «комплект» — проекта), у вида есть направленность
    и подбор алгоритмом.

17. **Фильтры — только ЧПУ, без GET-параметров.** В индексе — категория, фильтр первого уровня
    (применён один признак) и посадочные. Любая комбинация закрыта. Формат и правила — §8.1
    (предложение, не утверждено).

### 8.1. Адрес фильтра — предложение

Беда reference-shop — в разборе: `color-black` нельзя однозначно разрезать на признак и значение, если
слаги произвольные, и разбор по префиксу и порядку ломается на первом совпадении. Лечится не
слагом-заплаткой у каждого свойства, а форматом, где граница — символ, которого в слаге быть не
может. Слаги у нас — `[a-z0-9-]`, значит граница — `_`:

```
/noutbuki/                              категория
/noutbuki/brand_apple/                  первый уровень — в индексе
/noutbuki/brand_apple_dell/             два значения одного признака — закрыт
/noutbuki/brand_apple/color_black/      комбинация — закрыта
/noutbuki/brand_apple/price_100-500/    диапазон — закрыт всегда
```

- **Сегмент с `_` — фильтр, без `_` — категория.** Разбор: `explode('_', $segment)` → код фасета и
  значения. Двусмысленности нет ни между признаками, ни с подкатегориями — `_` запрещён в слагах
  категорий, кодах фасетов и слагах значений, и проверяет это реестр при регистрации и форма при
  сохранении.
- **У каждого фасета обязательный код** (`brand`, `color`, `price`), уникальный в реестре; у
  значения — слаг, уникальный внутри фасета. Код свойства предлагается из названия и правится;
  менять его после публикации — это 301 со старых адресов.
- **Одно написание.** Сегменты — в порядке фасетов, значения — по слагу; любое другое — 301 на
  каноническое. Хвост категории разбирает `routing`: точный адрес категории бьёт префиксный, хвост
  принимает тип «категория».
- **Что открыто:** категория; ровно один фасет с ровно одним значением, если фасет помечен
  «индексируемый» (по умолчанию да у справочных, нет у диапазонов и переключателей — «в наличии»
  своей страницы не заслуживает) и выдача не пуста; посадочные.
- **Что закрыто:** всё остальное — `noindex, follow`, ссылки на такие адреса в фильтре с
  `rel="nofollow"`, в карте сайта их нет. Пустой первый уровень — тоже `noindex`.
- **Первый уровень получает SEO шаблоном** («{категория} {значение}») через `module-seo`;
  посадочная на тот же набор забирает адрес: `/noutbuki/brand_apple/` → 301 на `/noutbuki/apple/`.
- **Карта сайта:** категории, непустые первые уровни, посадочные.
- **Сериализатор — за интерфейсом**, фасеты формата не знают. Ссылки фильтра строит он же и
  пропускает через переписчиков (§8.5): так посадочная получает ссылку на себя сразу, без 301.

### 8.2. Решения третьего круга (28.09.2026)

18. **§8.1 принят.** Разделитель `_`. Открыт ровно один признак с ровно одним значением;
    несколько значений и комбинации открываются только посадочной, то есть по запросу сеошника.
19. **Посадочные — спутник `module-catalog-landings` в волне A**, одно из первых требований SEO.
20. **Категория — тоже фасет, и значения свойств бывают деревом.** Форма — §8.3 (предложение).

### 8.3. Древовидные фасеты — предложение

Категория и дерево значений свойства — одна задача: признак, у которого значение имеет предков,
и выбор предка означает «любой из потомков». Поэтому это **один вид фасета, `FacetKind::Tree`**,
одна техника в индексе, один компонент фильтра и одно правило адреса.

**Индекс.** В документ кладётся значение **вместе со всеми предками** — уже решено для категорий
(§4.2). Выбран «Металл» — совпадают товары со «Сталью» и «Нержавеющей»; счётчик «Металла» движок
считает сам, без свёртки дерева в PHP (у reference-shop — квадратичный цикл).

**Значения свойств деревом.** Справочник значений свойства — `nested-set` со scope на свойство.
Флаг у свойства «древовидное»; флаг «только листья» — можно ли товару поставить значение
середины дерева (для «подходит ко всем поколениям BMW 3» — можно). Слаг значения уникален во всём
дереве свойства, поэтому адрес — просто `material_nerzhaveyushchaya`. Обмен принимает путь
(«Металл / Сталь / Нержавеющая») и по флагу профиля создаёт недостающие узлы. Большие деревья
(марки и модели — тысячи узлов) в панели — ленивым деревом с поиском (`useTreeNodes`).

**Категория фасетом.** Поведение зависит от того, где стоит фильтр:

| Где                                       | Что показывает                        | Выбор одного                                                      | Выбор нескольких |
| ----------------------------------------- | ------------------------------------- | ----------------------------------------------------------------- | ---------------- |
| страница категории                        | детей текущей категории со счётчиками | **переход** на подкатегорию, а не фильтр — иначе дубль её адреса  | фильтр, закрыт   |
| бренд, поиск, корень каталога, посадочная | дерево категорий                      | фильтр `category_…`, первый уровень — открыт («Apple — ноутбуки») | фильтр, закрыт   |

Слаг категории уникален на весь сайт (решение 23), поэтому в фильтре он и есть значение:
`/brands/apple/category_igrovye-noutbuki/`. Отдельного «слага для фильтра» нет — он был нужен,
пока слаги категорий повторялись у соседей по дереву. Путь через точку отвергнут (28.09.2026):
точка в адресе похожа на расширение файла для правил веб-сервера и не нравится SEO.

**Правило одного написания для деревьев:** выбранный предок поглощает выбранных потомков
(`material_metall_stal` → 301 на `material_metall`).

**Контекст фасета.** Раз поведение категории зависит от страницы, фасет получает контекст запроса
(категория, бренд, поиск, посадочная) — это часть `CatalogQuery`, а не знание фасета о модулях.
Бренд на странице бренда так же прячет собственный фасет.

### 8.4. Решения четвёртого круга (28.09.2026)

21. **§8.3 принят целиком:** древовидный фасет один на категории и свойства, выбранный предок
    поглощает потомков, на странице категории выбор одной подкатегории — переход, у категории
    слаг для фильтра, уникальный среди всех категорий. _Поправлено 29.09.2026: слаги категорий
    плоские и уникальны на весь сайт, отдельный слаг для фильтра не нужен (решение 23)._
22. **Совместимость («марка → модель → поколение») — древовидным свойством и ничем сверх.** Что
    нужно конкретному проекту дальше, делается спутником проекта по его требованию.

### 8.5. Решения пятого круга — адреса (29.09.2026)

23. **Категории — от корня сайта, слаги плоские на любом уровне.** `/igrovye-noutbuki/`, а не
    `/noutbuki/igrovye/`: слаг подбирает админ, уникальность на весь сайт (на своём языке)
    проверяет `routing`. Перенос категории по дереву не меняет ни одного адреса; хлебные крошки
    строятся по дереву. Цена — админ не сделает страницу со слагом, занятым категорией.
24. **Товар — плоский `/{slug}-{id}` от корня сайта.** Суффикс — `id`, а не артикул: артикула
    бывает нет, при импорте он меняется, в нём встречаются слэши. Слаг поэтому не уникален, а
    сменившийся слаг отвечает 301 на новое написание. В реестр `routing` товар пишется, как любая
    сущность — оттуда карта сайта и алиасы.
25. **Корень каталога `/catalog/`** (приставка — конфигом) — страница с верхними категориями и
    фильтром по всему каталогу, **выключена по умолчанию**: у большинства магазинов верхняя
    категория — просто список, и отдельная страница не нужна. Выключена — адреса нет.
26. **Псевдоним фильтра без редиректа.** Посадочная забирает адрес набора
    (`/noutbuki/brand_apple/` → `/noutbuki-apple/`), и фильтр, выбирая Apple, ставит ссылку сразу
    на псевдоним. Для этого ядро строит все ссылки фильтра одним построителем с реестром
    переписчиков; переписчик работает пачкой (посадочные грузят псевдонимы текущей категории одним
    запросом). Пришедший снаружи адрес фильтра — 301 на псевдоним. Выбор поверх посадочной: основой
    становится наибольшая посадочная, покрывающая выбранное, остальное — сегментами
    (`/noutbuki-apple/color_black/`), закрыто, как любая комбинация.

Открытых вопросов архитектуры семейства нет. Решения по ядру (поля, состояния товара,
популярность, журнал) — в его спеке.

## 11. Анатомия спутника

Спутник — пара пакетов (composer + npm), как любой модуль панели. Ядро даёт ему восемь точек
подключения; спутник берёт только нужные:

| Точка           | Что спутник делает                                           | Контракт ядра                                |
| --------------- | ------------------------------------------------------------ | -------------------------------------------- |
| данные          | своя таблица с `product_id`, свои справочники                | — (решение 2)                                |
| раздел панели   | справочник (бренды, статусы, метки) в группе «Каталог»       | манифест                                     |
| форма товара    | вкладка или поле; читает и пишет **своё** в общей транзакции | `ProductParts` + патч `catalog.product-form` |
| список в панели | колонка, фильтр — фасет тот же, что на сайте                 | `ProductColumns`, `Facets`                   |
| индекс          | поля документа, пачкой                                       | `DocumentContributor`                        |
| витрина         | фасет в фильтре, кусок карточки, выборка в шаблоне           | `Facets`, `@webxPart`, `RecordQuery`         |
| обмен           | свои колонки CSV/XLS                                         | `ExchangeColumns`                            |
| покупка         | правило «можно ли купить»                                    | `Purchasability`                             |

Плюс общие для всех модулей: MCP-инструменты, демо, регистрации (`Setup\Catalogue`, `extra.webx`).

`ProductParts` — новое по сравнению с §4: форма товара одна, а пишут в неё несколько модулей.
Ядро открывает транзакцию, сохраняет товар, отдаёт каждой части её кусок ввода (`rules()`,
`write()`), потом один `Catalog::touch()`. Упала любая часть — откатилось всё. Так же читает:
`read()` каждой части собирает значения формы.

Выключенный признак (цена без цены, остаток без остатка) не регистрирует ни одной точки.
