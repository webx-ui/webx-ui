# Каталог товаров — семейство модулей, архитектура

Волна A выпущена (v0.50.0–v0.56.0, §10); спека — справочник того, что есть. Ядро —
[`WEBX_UI_MODULE_CATALOG.md`](WEBX_UI_MODULE_CATALOG.md). Этот документ — про семейство целиком:
границы, решения, контракты ядра, раскладку по пакетам и анатомию спутника; спеки модулей —
в таблице §10.

Каталог — не один модуль, а ядро и спутники. Сайту-витрине без корзины хватает ядра и двух
спутников; магазину одежды — ещё таблиц размеров и группировки; магазину запчастей на 100 тысяч
позиций — свойств, поиска и обмена с учётной системой. Всё это одна установка, собранная из
разного набора пакетов, и ни один пакет не знает, какие ещё стоят рядом. Образец, с которого
снят опыт, — эталонный магазин на 85 тысяч товаров (§9).

## 1. Границы

**Внутри семейства:** товары, категории, цена, свойства, метки, наличие, бренды, связи между
товарами (похожие, сопутствующие, замена), таблицы размеров, группировка, конфигурируемый
товар, поисковый движок, импорт и экспорт.

**Снаружи:** корзина, заказы, покупатели, оплата, доставка — следующее семейство («commerce»),
и каталог готовит ему ровно один шов: `Purchasability` (§4.4). Типы цен и валюты (§7).
Многосайтовость (решение 8). Всё, что просил конкретный клиент: производители, модели
оборудования, серийные номера, схемы (решения 7 и 9).

## 2. Принятые решения (не переоткрывать)

1. **Ядро и спутники, не мономодуль.** Спутник знает только ядро; ядро не знает ни одного
   спутника. Спутник со спутником разговаривают только через реестры ядра. Исключение — настоящая
   зависимость, объявленная в `require` (группировке и конфигурируемому товару без свойств не из
   чего строить оси).
2. **Спутник хранит своё в своей таблице** с `product_id` и никогда не добавляет колонок в
   `catalog_products`. Удалили модуль — ушла его таблица, товар цел.
3. **Группировка и конфигурируемый товар — два модуля.** Группа связывает самостоятельные
   товары: каждый со своей страницей, местом в каталоге и в фасетах; на странице товара —
   переключатели по осям группы (цвет, размер). Конфигурируемый — наоборот: в каталоге один
   родитель, дети без него не видны. Общее одно — оси берутся из свойств.
4. **Цена — в ядре и выключается конфигом.** Базовая и старая. Выключена — её нет ни в форме, ни
   в фасетах, ни в индексе, ни в обмене. Фасет цены — диапазон. Валюта одна, валюта сайта.
5. **Наличие ставится руками.** Статус — справочник с флагом «можно купить». Количество —
   опциональное, включается конфигом, и тогда статус может считаться по остатку (пока
   отложено, §7). Фасет наличия тоже включается конфигом.
6. **Масштаб — сотни тысяч товаров.** Поисковый движок — часть архитектуры, а не опциональный
   спутник (§5); индексация очередью и пачками (§5.3); свойства типизированные (§6.2); всё, что
   обходит каталог, обходит его пачками, а не по товару.
7. **В базе только бренд.** Производитель — просьба клиента и живёт в его проекте своим фасетом
   через `Facets`. Это и проверка шва: чужой признак ложится в фильтр, индекс и обмен без правки
   ядра (проверено — §10).
8. **Многосайтовости в каталоге v1 нет** — ни колонок, ни связей с сайтом. Её проектируют целиком
   (`WEBX_UI_MULTISITE.md`), а не закладывают кусками.
9. **Оборудование, модели, серийные номера, схемы — проект клиента**, а не база. Вторая проверка
   шва, та же, что в решении 7.
10. **Импорт и экспорт — контракт ядра с первого дня** (§4.5): десять модулей с десятью
    импортами — ровно то, чего не должно случиться.
11. **Посадочные страницы фильтров есть** — SEO их требует всегда; спутник
    `module-catalog-landings`.
12. **Содержимое товара — только rich-text** (`wx-rich-text`). Никаких блоков у товара.
13. **Картинки товара — своя галерея, не библиотека `module-media`.** Загрузка прямо на сервер
    (и по адресу при импорте), у каждой картинки правятся `alt` и `title`. Полмиллиона файлов в
    дереве библиотеки не нужны ни дереву, ни редактору.
14. **Поиск в админке — тем же движком, что на сайте.** Стоит Manticore — список панели ищет и
    фильтрует им; на маленьком каталоге — `SqlEngine`. Значит, в индексе лежат и
    неопубликованные (и удалённые) товары, а витрина отсекает их фильтром.
15. **Обмен — CSV и XLSX в ядре.** Для 1С — отдельное API, интеграцию пишет интегратор 1С, а не
    мы. YML и прочие фиды — пакетами через реестр форматов ядра.
16. **Связи товаров — универсальные и расширяемые:** виды связи регистрируются (похожие,
    сопутствующие, замена — наши; «запчасти», «комплект» — проекта), у вида есть направленность
    и подбор алгоритмом.
17. **Фильтры — только ЧПУ, без GET-параметров.** Открыты категория, первый уровень фильтра и
    посадочные; любая комбинация закрыта (§8.1).
18. **Разделитель фильтра в адресе — `_`.** Открыт ровно один признак с ровно одним значением;
    несколько значений и комбинации открываются только посадочной, то есть по запросу сеошника.
19. **Посадочные — в волне A**, одно из первых требований SEO.
20. **Категория — тоже фасет, и значения свойств бывают деревом** (§8.3).
21. **Древовидный фасет один на категории и свойства:** выбранный предок поглощает потомков; на
    странице категории выбор одной подкатегории — переход, а не фильтр; значение категории в
    фильтре — её слаг (решение 23), отдельного слага для фильтра нет.
22. **Совместимость («марка → модель → поколение») — древовидным свойством и ничем сверх.** Что
    нужно проекту дальше — спутник проекта.
23. **Категории — от корня сайта, слаги плоские на любом уровне** (§8.2).
24. **Товар — плоский `/{slug}-{id}` от корня сайта** (§8.2).
25. **Корень каталога `/catalog/` выключен по умолчанию** (§8.2).
26. **Псевдоним фильтра без редиректа** — ссылки фильтра строит один построитель с
    переписчиками (§8.2).

Решения по ядру (поля, состояния товара, популярность, журнал) — в его спеке, §2.

Имена — по правилу `module-*` для разделов панели. Семейная приставка держит их рядом в
`Setup\Catalogue`. Идентификатор модуля в панели — то, что там показано: `catalog`,
`properties`, `brands`.

Похожие, сопутствующие и замена — один модуль: одна таблица (или `webx_relations` с видом
связи — решит спека модуля) и один интерфейс «выбрать товары», различается только смысл. Замена
вдобавок участвует в `Purchasability`: снятый с производства товар отвечает «нельзя, есть
замена».

## 4. Контракты ядра

Здесь — смысл; сигнатуры и подробности — §7 и §8 спеки ядра.

### 4.1. `Facets` — что можно отфильтровать

Фасет регистрирует модуль, которому принадлежит признак: цену и категорию — ядро, бренд —
бренды, наличие — наличие, свойство с флагом «в фильтре» — свойства (из базы, источником),
производителя — проект. Фасет описывает признак (`key`, `code($locale)`, `kind` —
`Terms | Range | Toggle | Tree`, `field(): IndexField`, подписи и слаги значений пачкой,
`applySql` для `SqlEngine`), но **не считает сам**: счётчики, диапазоны и то, что фасет при
выбранном значении показывает и остальные (без собственного фильтра), — поведение движка, одно
на всех. Какие фасеты видны в категории и в каком порядке — настройка категории в ядре.

### 4.2. `DocumentContributor` — из чего собран документ индекса

Каждый модуль дописывает свои поля в поисковый документ — **пачкой**:
`fields(): list<IndexField>` и `contribute(Collection $products, array $locales)`. Движок
собирает схему индекса из `fields()` всех вкладчиков и сравнивает её с живой. Ядро кладёт
категории **вместе с предками**, чтобы счётчики по дереву считал движок.

### 4.3. `CatalogEngine` — кто отвечает на запрос каталога

`search(CatalogQuery): CatalogResult` (id страницы, total, фасеты), `needsIndex()`,
`prepare($fields, $rebuild)`, `index($documents)`, `remove($ids)`. Реализации: `SqlEngine` в ядре
(честен на небольших каталогах) и `module-catalog-manticore`; выбор — конфигом. Витрина получает
id страницы и поднимает из базы только их, в порядке движка.

### 4.4. `Purchasability` — можно ли купить и почему нет

Цепочка правил `PurchaseRule::refuse(Collection)` пачкой, первый отказ — ответ с причиной:
наличие — «нет в наличии» (флаг статуса); связи — «снят с производства, есть замена»;
конфигурируемый — «не выбран вариант»; ядро — «снят с продажи» и «цена по запросу». Корзины
нет; пока вопрос задают карточка товара («Купить» или «Узнать цену» через `module-inbox`) и
MCP.

### 4.5. `ExchangeColumns` — обмен

Каждый модуль объявляет свои колонки обмена; конвейер, форматы (реестр `ExchangeFormats`),
профили, журнал прогона с ошибками по строкам и одна пометка индекса на пачку — в ядре
([`WEBX_UI_MODULE_CATALOG_EXCHANGE.md`](WEBX_UI_MODULE_CATALOG_EXCHANGE.md)). Колонки выключенного
признака (цена, остаток) не объявляются вовсе.

### 4.6. `RelatedProviders` — подбор связанных (волна B, не построено)

Сначала ручные связи, не хватило — алгоритм: «та же категория и бренд», «близкая цена»,
«покупали вместе» (когда появятся заказы). Алгоритм регистрирует любой модуль;
`module-catalog-links` только спрашивает реестр.

### 4.7. Уже существующие швы

| Нужно                                            | Чем                                                               |
| ------------------------------------------------ | ----------------------------------------------------------------- |
| Адрес товара, категории, бренда                  | `routing`: строки реестра, а не маршрут на категорию при загрузке |
| Вкладка или поле спутника в форме товара         | патч экрана `catalog.product-form`                                |
| Витрины на страницах («акции», «новинки бренда») | `CollectionSource` + `wx-collection` + `BlockOffers`              |
| Выборки в шаблоне                                | `RecordQuery`: `products()->brand('x')->label('sale')`            |
| Бейдж, наличие, бренд в карточке                 | точки `@webxPart` и реестр `StorefrontParts`                      |
| Ссылка на товар из меню                          | `LinkSource`                                                      |
| SEO товара и категории                           | `HasSeo` из `module-seo`                                          |

## 5. Масштаб

### 5.1. Что считает движок, а что база

База — источник правды и место записи. Список, фильтр, счётчики, диапазоны, сортировка на
витрине и в списке панели — движок (решение 14).

### 5.2. Сохранение не зависит от индекса

Упавший движок не роняет ни сохранение товара, ни импорт: товар помечается и ждёт в очереди.
Витрина при недоступном движке падает на базу, если каталог это выдерживает, иначе отвечает
503; `webx:doctor` показывает очередь и доступность.

### 5.3. Индексация

Любой модуль, изменивший своё, помечает товары (`Catalog::touch($ids)`, для справочников —
`touchQuery()` одним запросом), без обращения к движку. Воркер забирает пачку, собирает
документы у всех вкладчиков одним проходом и отдаёт движку; повтор пачки безвреден. Полная
перестройка — `webx:catalog:index --rebuild`. Подробно — §8.3 ядра.

### 5.4. База

Индексы на всём, по чему ищут и соединяют, — с первой миграции. Порядок записей без
`max(position) + 1` на каждом создании. Кеш — настоящий (store Laravel), а не память запроса.

## 6. Данные

### 6.1. Товар

Схема — §3 ядра. Артикул уникальный и необязательный, переводимые название и слаг, цена и
старая цена (`decimal`, nullable), основная категория колонкой (от неё адрес и крошки) плюс
дополнительные связью, описание rich-text.

### 6.2. Свойства

Типизированный EAV: свойство (справочник, число, текст, да/нет; флаги «несколько значений»,
«в фильтре», «в карточке», «на странице»), справочник значений, значения товара — строка на
значение с отдельными колонками под id значения, число и текст. Наборы свойств привязаны к
категориям. В индекс справочные значения идут одним многозначным полем глобально уникальных
id, числа — JSON-атрибутом по id свойства, чтобы новое числовое свойство не меняло схему
индекса. Свойство — это свойство, а фильтр — фасет: псевдотипов «бренд», «цена», «наличие» у
свойства нет. Подробно — [`WEBX_UI_CATALOG_PROPERTIES.md`](WEBX_UI_CATALOG_PROPERTIES.md).

## 7. Отложено

- Типы цен (розница, опт) и несколько валют.
- Количество на складе и статус по остатку (решение 5).
- Производитель и прочие «вторые бренды» в базе (решение 7).
- Многосайтовость (решение 8).
- Корзина, заказы и всё семейство «commerce».
- «Покупали вместе» — до появления заказов.

## 8. Адреса и фильтр

### 8.1. Адрес фильтра

`color-black` нельзя однозначно разрезать на признак и значение, если слаги произвольные, и
разбор по префиксу ломается на первом совпадении. Поэтому граница — символ, которого в слаге
быть не может. Слаги — `[a-z0-9-]`, граница — `_`:

```
/noutbuki/                              категория
/noutbuki/brand_apple/                  первый уровень — в индексе
/noutbuki/brand_apple_dell/             два значения одного признака — закрыт
/noutbuki/brand_apple/color_black/      комбинация — закрыта
/noutbuki/brand_apple/price_100-500/    диапазон — закрыт всегда
```

- **Сегмент с `_` — фильтр, без `_` — категория.** `_` запрещён в слагах категорий, кодах
  фасетов и слагах значений — проверяют реестр при регистрации и форма при сохранении.
- **У каждого фасета код** (`brand`, `color`, `price`, на языке страницы), уникальный в реестре;
  у значения — слаг, уникальный внутри фасета. Смена кода или слага — 301 со старых адресов
  (`catalog_filter_aliases`).
- **Одно написание.** Сегменты — в порядке фасетов, значения — по слагу; любое другое — 301 на
  каноническое.
- **Открыто:** категория; ровно один фасет с ровно одним значением, если фасет индексируемый
  (по умолчанию справочные — да, диапазоны и переключатели — нет) и выдача не пуста; посадочные.
- **Закрыто всё остальное:** `noindex, follow`, ссылки фильтра на такие адреса — с
  `rel="nofollow"`, в карте сайта их нет. Пустой первый уровень — тоже `noindex`.
- **Первый уровень получает SEO шаблоном** («{категория} {значение}») через `module-seo`.
- **Карта сайта:** категории, непустые первые уровни, посадочные.
- **Сериализатор — за интерфейсом** (`FilterUrls`, §7.7 ядра), фасеты формата не знают.

### 8.2. Адреса сущностей

- **Категория — `/{slug}` от корня сайта, слаг плоский на любом уровне** (решение 23):
  `/igrovye-noutbuki/`, а не `/noutbuki/igrovye/`. Уникальность на весь сайт (на своём языке)
  проверяет `routing`. Перенос по дереву не меняет ни одного адреса; крошки строятся по дереву.
  Цена — админ не сделает страницу со слагом, занятым категорией.
- **Товар — `/{slug}-{id}`** (решение 24). Суффикс — `id`, а не артикул: артикула бывает нет,
  при импорте он меняется, в нём встречаются слэши. Слаг поэтому не уникален, сменившийся слаг
  отвечает 301. Товар — строка реестра `routing`, как любая сущность: оттуда карта сайта и
  алиасы.
- **Корень `/catalog/`** (приставка — конфигом) — верхние категории и фильтр по всему каталогу,
  **выключен по умолчанию** (решение 25): у большинства магазинов верхняя категория — просто
  список. Выключен — адреса нет.
- **Псевдоним фильтра без редиректа** (решение 26). Посадочная забирает адрес набора
  (`/noutbuki/brand_apple/` → `/noutbuki-apple/`), и фильтр ставит ссылку сразу на псевдоним:
  все ссылки фильтра строит один построитель с реестром переписчиков, переписчик работает
  пачкой (псевдонимы текущей категории одним запросом). Пришедший снаружи адрес набора — 301 на
  псевдоним. Выбор поверх посадочной: основа — наибольшая посадочная, покрывающая выбранное,
  остальное — сегментами (`/noutbuki-apple/color_black/`), закрыто, как любая комбинация.

### 8.3. Древовидные фасеты

Категория и дерево значений свойства — одна задача: значение имеет предков, и выбор предка
значит «любой из потомков». Поэтому это **один вид фасета, `FacetKind::Tree`**: одна техника в
индексе, один компонент фильтра, одно правило адреса.

**Индекс.** В документ кладётся значение **вместе со всеми предками**. Выбран «Металл» —
совпадают «Сталь» и «Нержавеющая»; счётчик «Металла» движок считает сам, без свёртки дерева в
PHP.

**Значения свойств деревом.** Справочник значений — `nested-set` со scope на свойство. Флаг
свойства «древовидное»; флаг «только листья» — можно ли товару поставить значение середины
дерева («подходит ко всем поколениям BMW 3» — можно). Слаг значения уникален во всём дереве
свойства: адрес — просто `material_nerzhaveyushchaya`. Обмен принимает путь («Металл / Сталь /
Нержавеющая») и по флагу профиля создаёт недостающие узлы. Большие деревья в панели — ленивым
деревом с поиском.

**Категория фасетом** ведёт себя по-разному в зависимости от страницы:

| Где                                       | Что показывает                        | Выбор одного                                                      | Выбор нескольких |
| ----------------------------------------- | ------------------------------------- | ----------------------------------------------------------------- | ---------------- |
| страница категории                        | детей текущей категории со счётчиками | **переход** на подкатегорию, а не фильтр — иначе дубль её адреса  | фильтр, закрыт   |
| бренд, поиск, корень каталога, посадочная | дерево категорий                      | фильтр `category_…`, первый уровень — открыт («Apple — ноутбуки») | фильтр, закрыт   |

Значение — слаг категории (`/brands/apple/category_igrovye-noutbuki/`). Путь через точку
отвергнут: точка похожа на расширение файла для правил веб-сервера и не нравится SEO.

**Одно написание для деревьев:** выбранный предок поглощает выбранных потомков
(`material_metall_stal` → 301 на `material_metall`).

**Контекст фасета.** Поведение зависит от страницы, поэтому фасет получает контекст запроса
(категория, бренд, поиск, посадочная) — часть `CatalogQuery`, а не знание фасета о модулях.
Бренд на странице бренда так же прячет собственный фасет.

## 9. Опыт эталонного магазина

**Взяли:** типизированный EAV свойств с наборами по категориям; наличие справочником с флагом
«можно купить»; группировку и конфигурируемый товар отдельными сущностями; «движок отдаёт id и
счётчики, база поднимает одну страницу»; фасеты со снятием собственного фильтра; настройку
фильтров по категориям.

**Не повторили** — и это объясняет решения выше:

| У эталонного магазина                                                             | У нас                                                     |
| --------------------------------------------------------------------------------- | --------------------------------------------------------- |
| тип свойства смешан с псевдотипами фильтров (бренд, цена, наличие)                | реестр `Facets` (§4.1), свойство — не фильтр (§6.2)       |
| модель товара знает поисковик, оборудование, API-ресурсы                          | ядро не знает спутников, индекс собирают вкладчики (§4.2) |
| фасеты написаны трижды, отдельно для каждого типа                                 | одна реализация фасетов в движке                          |
| категории в индексе без предков, счётчики дерева — квадратичным циклом в PHP      | предки в документе (§4.2, §8.3)                           |
| индексация синхронная, без очереди, по одному товару                              | очередь, пачки, идемпотентность (§5.3)                    |
| упал поисковик — падают витрина и сохранение                                      | §5.2                                                      |
| маршрут на каждую категорию при загрузке, фильтр в адресе разбирается по префиксу | `routing` и однозначный формат (§8.1)                     |
| сохранение: удалить и вставить каждую связь, без транзакции                       | каждый модуль пишет своё в общей транзакции формы (§11)   |
| нет индексов на `slug`, `sku`, `brand_id`                                         | §5.4                                                      |
| админский API принимает произвольные имена колонок в фильтре и сортировке         | белый список                                              |
| импорта каталога нет вовсе                                                        | §4.5                                                      |

### Проверка швов: справочник проекта

Решения 7 и 9 проверены в конце волны A: производитель — справочник проекта, а не пакета —
подключается к каталогу без правки ядра. Проверено на демо-сайте и на копии реальной выгрузки
магазина (~93 тыс. товаров, все с производителем): фильтр витрины, счётчики, порядок сегментов
в адресе, страница с выбранным значением. Проектный код, у пакетов ничего не просили:

| Точка           | Чем подключён производитель                                                                                                   |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| данные          | миграция проекта: `$table->category()` + своя таблица связей с `product_id`                                                   |
| раздел панели   | `dictionarySection()` из `@webx-ui/module-catalog` в `admin.ts` сайта, `CategoryRoutes` и `ModuleRegistry` в провайдере сайта |
| форма товара    | `ProductPart` + патч `catalog.product-form` с `wx-select` и `CategorySources`                                                 |
| список в панели | `ProductColumn`; фильтр — тот же фасет                                                                                        |
| индекс          | `DocumentContributor`                                                                                                         |
| витрина         | фасет `Terms`, `OrderedFacet`, подпись — через `__()` сайта                                                                   |
| обмен           | `ExchangeColumn` (слаг, имя или `#id`; `create_missing` создаёт)                                                              |

Справочник проекта ходит под `catalog/<слаг>` API панели — так его адрес строит
`dictionarySection()`. Не хватило одного, и не шва: `ProductController::counted()` затирал свой
ответ переменной с тем же именем, и из `facets` списка пропадали все фасеты со значениями,
кроме последнего (починено, тест — `RegistriesTest`).

## 11. Анатомия спутника

Спутник — пара пакетов (composer + npm), как любой модуль панели. Ядро даёт ему восемь точек
подключения; спутник берёт только нужные:

| Точка           | Что спутник делает                                           | Контракт ядра                                |
| --------------- | ------------------------------------------------------------ | -------------------------------------------- |
| данные          | своя таблица с `product_id`, свои справочники                | — (решение 2)                                |
| раздел панели   | справочник (бренды, статусы, метки) в группе «Каталог»       | манифест, `dictionarySection()`              |
| форма товара    | вкладка или поле; читает и пишет **своё** в общей транзакции | `ProductParts` + патч `catalog.product-form` |
| список в панели | колонка, фильтр — фасет тот же, что на сайте                 | `ProductColumns`, `Facets`                   |
| индекс          | поля документа, пачкой                                       | `DocumentContributor`                        |
| витрина         | фасет в фильтре, кусок карточки, выборка в шаблоне           | `Facets`, `StorefrontParts`, `RecordQuery`   |
| обмен           | свои колонки CSV/XLSX                                        | `ExchangeColumns`                            |
| покупка         | правило «можно ли купить»                                    | `Purchasability`                             |

Плюс общие для всех модулей: MCP-инструменты, массовые действия (`BulkActions`), демо,
регистрации (`Setup\Catalogue`, `extra.webx`).

Форма товара одна, а пишут в неё несколько модулей: ядро открывает транзакцию, проверяет
`rules()` всех частей, сохраняет товар, отдаёт каждой `ProductPart` её кусок ввода (`write()`),
потом один `Catalog::touch()`. Упала любая часть — откатилось всё. Читает так же: `read()`
каждой части собирает значения формы.

Выключенный признак (цена без цены, остаток без остатка) не регистрирует ни одной точки.
