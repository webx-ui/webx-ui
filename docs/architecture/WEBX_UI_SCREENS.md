# WebX UI — экраны как описание: спецификация

Статус: **третья редакция, согласована**, код идёт (§13). Первый потребитель —
`module-settings`, второй — форма администратора в `module-auth`. Механизм общий и живёт в
каркасе (`module-admin` + `@webx-ui/schema`), модули только описывают свои экраны.

## 1. Задача

Экран панели, написанный шаблоном, снаружи не изменить: слот даёт вставить что-то в
предусмотренное место, но убрать карточку, переставить вкладки или заменить тип поля шаблон не
позволяет. А проекты именно это и делают: у одного в настройках вкладка «Контакты» и карта, у
другого нет карты вовсе, у третьего в форме администратора поле «Должность».

Решение: экран не пишется, а **описывается** — деревом узлов в JSON, у каждого узла стабильный
`id`. Модуль везёт дерево по умолчанию, проект (или другой модуль) накладывает на него
**патч** — список операций «добавить, убрать, заменить, переставить». Рендерер рисует результат
компонентами ядра, беря их из **реестра типов**. Один формат, одни операции и один рендерер для
всех экранов панели.

Что **не** решается здесь: визуальный конструктор экранов, хранение описаний в базе, язык
выражений. Формат выбран так, чтобы всё это можно было добавить потом, не меняя его.

## 2. Термины

| Термин | Что это                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------- |
| Узел   | Единица описания: `{ id, type, props, children, … }`. Вкладка, карточка, поле — всё узлы.         |
| Тип    | Имя в реестре, по которому рендерер находит Vue-компонент: `wx-card`, `wx-input`, `wx-media`.     |
| Экран  | Именованное дерево узлов: `settings.index`, `admins.form`. Имя — `<модуль>.<экран>`.              |
| Патч   | Упорядоченный список операций над деревом экрана.                                                 |
| Реестр | Соответствие «тип → компонент» на фронте и «тип поля → правила и приведение значения» на сервере. |
| Модель | Объект со значениями, которые экран показывает и меняет: настройки, запись администратора.        |

## 3. Узел

```json
{
  "id": "robots",
  "type": "wx-textarea",
  "name": "seo.robots-txt",
  "label": "trans::webx-settings::screen.robots",
  "help": "trans::webx-settings::screen.robots-help",
  "localized": false,
  "props": { "rows": 8, "placeholder": "trans::webx-settings::screen.robots-placeholder" },
  "children": [],
  "slot": null,
  "visible": true,
  "can": null
}
```

| Ключ        | Обязателен | Смысл                                                                                                                                          |
| ----------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`        | да         | Уникален **в пределах экрана**. Это адрес для патчей и публичный контракт модуля: переименование — ломающее изменение.                         |
| `type`      | да         | Имя типа из реестра.                                                                                                                           |
| `name`      | для полей  | Ключ в модели. **Буквальная строка**, точки внутри — часть ключа (`seo.robots-txt`), а не путь. Вложенность даёт `wx-repeater`.                |
| `label`     | нет        | Подпись.                                                                                                                                       |
| `help`      | нет        | Подсказка под полем.                                                                                                                           |
| `localized` | нет        | Поле мультиязычное: значение — запись `{ "ru": …, "uk": … }`, рендерер включает переключатель языка.                                           |
| `props`     | нет        | Пропсы компонента как есть. Рендерер их не интерпретирует.                                                                                     |
| `children`  | нет        | Вложенные узлы. Для `wx-repeater` — поля одного элемента; узел с `name` владеет тем, что под ним, и на нём обход полей экрана останавливается. |
| `slot`      | нет        | В какой именованный слот родителя попасть: `"sidebar"` у карточки, `"extra"` у шапки. Без него — в слот по умолчанию.                          |
| `visible`   | нет        | `true`/`false` или условие (§7). Скрытый узел не рисуется, значение его полей не трогается.                                                    |
| `can`       | нет        | Право вида `settings.manage`. Без права узел не рисуется, а его поля не принимаются на запись.                                                 |

Ключей вне этого списка у узла нет: всё своё — в `props`. Это делает формат проверяемым
JSON-схемой (§10).

**Переводимые строки.** Любая строка в узле, начинающаяся с `trans::`, — ключ словаря:
`trans::<namespace>::<key>`, то есть `trans::webx-settings::screen.robots`. Маркер один и тот же в
`label`, `help` и в любом значении `props`. Переводит сервер, когда отдаёт экран (§4), в языке
администратора; клиентские патчи из `admin.ts` переводит клиент из словаря панели тем же
маркером. Строка без маркера едет как есть — так проект пишет «Телефон» прямо в патче, если ему
не нужны языки.

## 4. Экран: где живёт и как доставляется

**Эталонное дерево живёт в composer-пакете модуля** — там же, где правила записи, права и MCP,
которым оно нужно не меньше, чем отрисовке. Файл
`php/packages/module-settings/resources/screens/index.json`, регистрация в провайдере:

```php
// SettingsServiceProvider::boot()
Screens::register('settings.index', __DIR__.'/../resources/screens/index.json');
```

**Манифест деревья не везёт.** Экран приезжает, когда открывается страница, которой он нужен:

```
GET /api/cms/screens/settings.index
```

Ответ — готовое дерево: эталон, серверные патчи в порядке §5, узлы без права уже вырезаны,
строки `trans::` уже переведены в языке администратора. Клиент кладёт его в память на сессию
(ключ — имя экрана и язык) и второй раз не ходит; перезагрузка страницы — новый запрос, поэтому
патч, добавленный на деплое, виден сразу. Запрос уходит параллельно с запросом значений —
страница настроек и так ждёт свой `GET /settings`, так что ожидания это не добавляет. Экран
диалога (`admins.form`) модуль может запросить заранее, входя в свой раздел, чтобы первое
открытие диалога не ждало.

В манифесте от экранов остаётся только список имён — чтобы клиент знал, что вообще есть, и мог
предзагрузить.

Почему не всё в манифесте: манифест собирается на каждый запрос и перечитывается при смене
языка; с ростом числа модулей в нём оказались бы все деревья всех экранов, из которых
администратор за сессию откроет два. Почему не во фронтовом пакете: дерево нужно серверу для
записи, прав и MCP, и второй экземпляр в npm-пакете пришлось бы держать синхронным с первым.
Один файл, отданный по запросу, снимает обе проблемы.

При регистрации дерево проверяется: уникальность `id`, соответствие JSON-схеме, существование
`target` у каждого патча. Ошибка — исключение, не предупреждение: сломанное описание — баг, а не
режим работы.

## 5. Патч

Патч — массив операций. Порядок применения на клиенте:

1. дерево модуля;
2. серверные патчи — сначала других пакетов, потом проекта (порядок загрузки провайдеров,
   провайдер проекта последний); всё это происходит на сервере, и клиент получает результат
   одним запросом (§4);
3. клиентские патчи из `admin.ts` — уже на клиенте, поверх полученного.

Формат один на обеих сторонах.

```json
[
  { "op": "remove", "target": "project-logo" },

  { "op": "set", "target": "robots", "props": { "rows": 16 }, "label": "robots.txt" },

  {
    "op": "add",
    "target": "tabs",
    "position": "after:general",
    "node": {
      "id": "contacts",
      "type": "wx-tab",
      "label": "trans::app::settings.contacts",
      "children": [
        {
          "id": "contacts-card",
          "type": "wx-card",
          "children": [
            { "id": "phone", "type": "wx-input", "name": "contacts.phone", "label": "Телефон" },
            {
              "id": "email",
              "type": "wx-input",
              "name": "contacts.email",
              "label": "Почта",
              "props": { "type": "email" }
            },
            { "id": "map", "type": "map", "name": "contacts.map", "label": "На карте" },
            {
              "id": "offices",
              "type": "wx-repeater",
              "name": "contacts.offices",
              "label": "Офисы",
              "children": [
                {
                  "id": "office-city",
                  "type": "wx-input",
                  "name": "city",
                  "label": "Город",
                  "localized": true
                },
                {
                  "id": "office-address",
                  "type": "wx-textarea",
                  "name": "address",
                  "label": "Адрес",
                  "localized": true
                }
              ]
            }
          ]
        }
      ]
    }
  },

  { "op": "move", "target": "seo", "position": "first" },

  {
    "op": "replace",
    "target": "default-og",
    "node": { "id": "default-og", "type": "og-preview", "name": "seo.default-og" }
  }
]
```

| Операция  | Поля                         | Что делает                                                                                                            |
| --------- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `add`     | `target`, `node`, `position` | Вставляет `node` в `children` узла `target`. `position`: `first`, `last` (по умолчанию), `before:<id>`, `after:<id>`. |
| `remove`  | `target`                     | Убирает узел с потомками.                                                                                             |
| `replace` | `target`, `node`             | Заменяет узел целиком. `id` нового может отличаться.                                                                  |
| `move`    | `target`, `position`, `to?`  | Переставляет узел среди соседей или в другого родителя `to`.                                                          |
| `set`     | `target` + любые ключи узла  | Меняет ключи поверхностно; `props` сливаются по ключам, остальное заменяется.                                         |

Адрес — голый `id`: он уникален в экране, и этого достаточно. Патч, чей `target` не найден, —
ошибка: исключение на сервере при регистрации, ошибка в консоли и пропуск операции на клиенте.
Так патч проекта, переживший переименование в модуле, не молчит.

Регистрация на сервере:

```php
// проект, AppServiceProvider::boot()
Screens::extend('settings.index', resource_path('screens/settings.json'));
Screens::extend('admins.form', [
    ['op' => 'add', 'target' => 'fields', 'node' => ['id' => 'position', 'type' => 'wx-input', 'name' => 'position', 'label' => 'Должность']],
]);
```

На клиенте — теми же операциями, для того, что серверу знать незачем (компоненты проекта,
чисто интерфейсные пропсы):

```ts
createAdmin({
  basePath: '/cms',
  modules: [media(), admins(), settings()],
  screens: {
    'settings.index': [{ op: 'set', target: 'robots', props: { rows: 24 } }],
  },
})
```

Клиентский патч не может открыть ключ на запись: поле, добавленное только на клиенте, сервер
отбросит при сохранении (§8). Это не ограничение, а граница: что пишется — решает сервер.

## 6. Реестр типов

### 6.1. На фронте: тип → компонент

Реестр живёт в `@webx-ui/schema` и по умолчанию заполнен компонентами ядра. Правило имени:
**полное имя компонента, `wx-input`, `wx-card`** — по имени видно, что это наш UI-kit. Типы
проекта называются как угодно (`map`, `og-preview`) и регистрируются той же строкой:

```ts
createAdmin({
  types: {
    map: { component: WxMapField, kind: 'field' },
    'og-preview': { component: OgPreview, kind: 'field' },
  },
})
```

Запись реестра:

```ts
interface TypeEntry {
  component: Component
  /** Как рендерер обращается с узлом. */
  kind: 'layout' | 'field' | 'display'
  /** Куда класть детей без `slot` (по умолчанию — слот default). */
  childrenSlot?: string
}
```

- `layout` — контейнер: получает `children` в слоты, модель не трогает.
- `field` — получает `modelValue` по `name`, отдаёт `update:modelValue`, показывает ошибку 422 по
  своему `name`. Обёрнут в `wx-form-item` с `label` и `help`. При `localized` — в контекст языков.
- `display` — рисует, ничего не редактирует.

Кнопок среди типов нет: они остаются в шаблонах страниц (§8).

Первая версия:

| kind    | типы                                                                                                                                                                    |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| layout  | `wx-tabs`, `wx-tab`, `wx-card`, `wx-row`, `wx-col`, `wx-divider`                                                                                                        |
| field   | `wx-input`, `wx-textarea`, `wx-input-number`, `wx-select`, `wx-switch`, `wx-checkbox`, `wx-radio-group`, `wx-date-picker`, `wx-color-picker`, `wx-media`, `wx-repeater` |
| display | `wx-text`, `wx-alert`                                                                                                                                                   |

Второй волной: `wx-rich-text`, `wx-tree-select`, `wx-transfer`, `wx-slider`, `wx-rate`,
`wx-upload` — всё, что есть в ядре и годится в CRUD.

`wx-media` — это `WxMediaField` из `module-media`; модуль медиа регистрирует его сам при
подключении. Без него тип неизвестен, и экран показывает на его месте заглушку «тип не
зарегистрирован: wx-media» — громко, а не пустое место.

`wx-repeater` — единственный тип с вложенной моделью: значение — массив объектов, `children` —
поля одного элемента, `name` внутри — ключи элемента. Сортировка, добавление, удаление — его
собственные; это `WxSortableList` с формой внутри (ядро: `WxRepeater`, схема: `WxScreenRepeater`,
который и раздаёт детей по строкам). Условие видимости внутри строки читается по этой же строке.

Вложенный тип объявляет себя `nested: true` в реестре: рендерер передаёт такому компоненту сам
узел и контекст, и дальше тот сам решает, к чему привязаны дети. Свой тип с вложенной моделью
пишется так же — `WxScreenNodes` экспортируется для этого.

### 6.3. `wx-list` — панель списка

`module-admin` приносит свой тип поверх ядра: `wx-list`, каркас, в котором рисуется список
любого раздела. Заведён 17.09.2026 этапом 5 визуальной переделки (`WEBX_UI_VISUAL.md` §10, §18,
§19, §20) — до него каждый раздел отвечал на вопрос «где заголовок» сам, и ответов было пять.

Форма одна: имя раздела слева на своей строке, единственное главное действие справа, виды
списка вкладками под ними, карточка с одними строками. Поиск остаётся внутри таблицы — он сужает
строки, а не экран. Своего заголовка у карточки нет: вид называет вкладка, раздел — строка над
ней. Заголовок внутри карточки законен только у группы полей формы, где их два и больше.

```json
{
  "id": "list",
  "type": "wx-list",
  "label": "trans::webx-pages::module.title",
  "props": {
    "views": [
      { "value": "", "label": "trans::webx-pages::page.filter-all" },
      { "value": "draft", "label": "trans::webx-pages::page.filter-draft" }
    ]
  },
  "children": [{ "id": "rows", "type": "wx-pages-table" }]
}
```

`label` едет в заголовок, `props` принимают `views`, `card`, `padding`, `fill` и `collapseBelow`,
дети попадают внутрь карточки. Вкладки — `WxTabs` в режиме `items`: полоса строится списком, а
панель под ней одна, поэтому переключение вида не размонтирует таблицу и не теряет её поиск,
страницу и прокрутку. Ниже `collapseBelow` (по умолчанию 560) полоса сворачивается в один
переключатель, подписанный открытым видом, — не в три точки: три точки означают действия, а это
выбор того, что на экране.

Сами строки остаются типом модуля (`wx-pages-table`, `wx-media`): только модуль знает, что он
перечисляет и у кого спрашивает.

Действия строки — отдельный кирпич того же этапа: `WxRowMenu` из `module-admin`, меню `···` во
всех списках, даже когда пункт один. Разрушающее в нём последнее, за разделителем и красным;
недоступное по правам не показывается вовсе. Рисуется он `WxActions collapse="always"` — ряд
иконок не строится вообще, поэтому ширина ячейки перестаёт что-либо решать.

### 6.2. На сервере: тип поля → значение

Серверу важен не компонент, а **что за значение** приходит и как его отдавать сайту:

```php
interface FieldType
{
    /** Правила валидации для значения этого типа; `$node` — узел целиком. */
    public function rules(array $node): array;

    /** Что хранить: пришедшее значение, приведённое. */
    public function store(mixed $value, array $node): mixed;

    /**
     * Что отдать сайту: `settings('seo.default-og')` возвращает это. `$locale` — запрошенный
     * язык; нужен только типу, который сам хранит переводимые значения (`wx-repeater`).
     */
    public function resolve(mixed $stored, array $node, ?string $locale = null): mixed;
}
```

Встроенные: `wx-input` (string), `wx-textarea` (string), `wx-input-number` (numeric),
`wx-switch`/`wx-checkbox` (bool), `wx-select`/`wx-radio-group` (значение из `props.options`),
`wx-date-picker` (date), `wx-color-picker` (hex), `wx-media` (ключ библиотеки; `resolve` → адрес),
`wx-repeater` (массив, рекурсивно по детям). `localized` — не тип, а модификатор: правила
применяются к каждому языку, `resolve` отдаёт текущий язык с фолбэком на язык по умолчанию.

Неизвестный серверу тип (`map` проекта) хранится как есть, без правил, `resolve` возвращает
сохранённое. Проект добавляет свой тип, если хочет валидацию:

```php
FieldTypes::register('map', new MapFieldType());
```

## 7. Условная видимость

Речь о «показать блок, когда в другом поле выбрано то-то». Пример: переключатель «Разрешить
индексацию» и под ним поле «Адрес sitemap», которое нужно только при включённом переключателе:

```json
{ "id": "indexing", "type": "wx-switch", "name": "seo.indexing", "label": "Разрешить индексацию" },
{ "id": "sitemap-url", "type": "wx-input", "name": "seo.sitemap-url", "label": "Адрес sitemap",
  "visible": { "when": "seo.indexing", "is": true } }
```

Формы: `{ "when": name, "is": value }`, `{ "when": name, "in": [ … ] }`, `{ "when": name, "not": value }`,
`{ "all": [ … ] }`, `{ "any": [ … ] }`. Считается на клиенте по текущей модели, работает и на
карточке, и на вкладке. Сервер условия не трогает: значение скрытого поля не валидируется и не
сохраняется, если его не прислали.

Это дешёвая вещь, и в CRUD она нужна постоянно; предлагаю оставить в первой версии. Всё, что
сложнее «поле зависит от поля», — свой компонент.

## 8. Экран и страница модуля

Экран не ходит в API и не знает, как сохраняться. Это делает **страница** модуля, которая его
открывает, и кнопки — её:

```vue
<wx-card>
  <template #extra>
    <wx-button type="primary" @click="save">{{ t('save') }}</wx-button>
  </template>

  <wx-screen name="settings.index" v-model="values" :errors="errors" />
</wx-card>
```

`WxScreen` запрашивает экран (§4), накладывает клиентские патчи, рендерит по реестру. Страница модуля настроек грузит значения из своего API, отдаёт `values`, на
«Сохранить» шлёт их обратно и раскладывает 422 в `errors`. Форма администратора делает то же
со своей записью. Так экран остаётся чистой функцией от дерева и модели, а всё специфичное —
где и было.

Сохранение на сервере — тоже по описанию: контроллер берёт то же дерево, что отдал бы
клиенту (эталон плюс серверные патчи), собирает из полей правила (`FieldType::rules`),
валидирует, приводит (`store`) и пишет. Поле, которого в дереве нет, не принимается: серверный
патч не только рисует, но и открывает ключ на запись. Узел с `can`, на которое у администратора
нет права, на запись закрыт так же, как не показан.

## 9. Два первых потребителя

### 9.1. `module-settings`

- Таблица `cms_settings`: `key` (уникальный), `value` (json), timestamps. Без `site_id`:
  мультисайт не в этой версии.
- Экран `settings.index` — дерево из §4. Вкладка по умолчанию одна: «Общее» (название проекта).
  Набор нарочно маленький: остальное у каждого проекта своё, и его добавляет патч.
- **Вкладка SEO приезжает патчем от `module-seo`** (с 14.09.2026; раньше её накладывал сайт).
  Это первый случай, когда патч кладёт не проект, а другой модуль, и механизм это выдержал без
  правок: `ScreenRegistry::extend` принимает патч к ещё не зарегистрированному экрану, порядок
  загрузки провайдеров значения не имеет, а провайдер приложения всё равно грузится последним и
  остаётся с последним словом. Идентификаторы её узлов — публичный контракт, они перечислены в
  `WEBX_UI_MODULE_SEO.md` §9 и в гайде.
- API: `GET /api/cms/settings` — значения; `PUT /api/cms/settings` — сохранение по описанию.
- Права: `settings.view`, `settings.manage`.
- На сайте: `settings('general.project-name')` — значение после `resolve`, кэш целиком, сброс при
  сохранении, событие `SettingsSaved`.
- MCP: `settings_list` (ключи с подписями и типами — из дерева), `settings_get`, `settings_set`
  (mutating, `dry_run`, только ключи из дерева).

### 9.2. `admins.form`

Форма администратора переезжает в дерево `admins.form`: сайдбар с `wx-media` (фото), поля
`name`, `email`, `password`, `roles`, `is_active`, `is_super`. Кнопки диалога остаются у диалога.

У `cms_users` появляется колонка `extra` (json): `AdminRequest` принимает в неё всё, что есть в
дереве, но не является колонкой. Так поле «Должность» из патча проекта получает место, не
требуя миграции в проекте.

Проверка механизма: из `webx-cms.local` без правок в пакетах
(а) в настройки добавляется вкладка «Контакты» и убирается логотип,
(б) в форму администратора добавляется поле «Должность».
Если (б) не проходит, общий слой не общий.

## 10. JSON-схема и проверка

`@webx-ui/schema` публикует `screen.schema.json` и `patch.schema.json`, доки отдают их по
постоянному адресу. Назначение:

- редактор подсказывает и подсвечивает ошибки прямо в JSON-файле проекта
  (`"$schema": "https://webx-ui.github.io/webx-ui/schema/screen.json"`);
- обе половины валидируют описания при регистрации теми же схемами;
- тесты пакетов проверяют, что деревья по умолчанию схеме соответствуют.

Ключи узла закрыты (`additionalProperties: false`), поэтому опечатка в `childrens` — ошибка, а не
молча пустая вкладка.

## 11. Совместимость

- `id` узлов экрана по умолчанию — публичный API модуля. Переименование или удаление — в
  changeset как ломающее изменение, с указанием старого и нового `id`.
- Добавление узлов в дерево по умолчанию — не ломающее: патчи адресуют по `id`, а не по позиции.
- Патч, не нашедший `target`, падает громко (§5). Это и есть обнаружение несовместимости.

## 12. Что дальше на том же формате

- **Списки.** `columns` таблиц уже массив с `key`; фильтры и действия строки описываются так
  же, и экран `admins.index` получит патчи теми же операциями.
- **Редактор компонентов в панели** (CLAUDE.md §6): поля блока — те же узлы, и хранить их
  можно в базе как есть.
- **`@webx-ui/adapter-laravel`**: экран + модель + API модуля — это и есть адаптер.

## 13. Решено и открыто

Решено:

- адрес патча — голый `id`, уникальный в экране;
- эталонное дерево — в composer-пакете, один файл; экран отдаётся отдельным запросом, когда
  открывается страница, и кэшируется на сессию; манифест деревьев не везёт;
- условная видимость — в первой версии, объектной формой; улучшать по мере надобности;
- переводимые строки — маркер `trans::<namespace>::<key>`, везде в узле;
- `extra` (json) у администраторов — принято;
- имена типов — полные, с `wx-`;
- кнопки — в шаблонах страниц, типа `action` нет.

Открыто: ничего. Порядок кода — снизу вверх, от того, что можно увидеть без сервера:

1. `WxCodeEditor` в ядре — патчи на странице документации пишутся в нём, а не в textarea
   (сделано: [CodeEditor](https://webx-ui.github.io/webx-ui/components/code-editor.html)).
2. Рендерер в `@webx-ui/schema` и страница документации с двумя редакторами — эталонное дерево и
   патч — и живым превью. Это площадка, на которой механизм проверяется до всякого PHP
   (сделано: [Screens](https://webx-ui.github.io/webx-ui/guide/screens.html), `wx-repeater` — тоже).
3. Общий слой в `module-admin`: эндпоинт экранов, реестр патчей (сделано: `Screens`, `FieldTypes`,
   `ScreenValues`, `GET /api/cms/screens/{name}`; на клиенте `createAdmin({ screens, types })` и
   `WxScreen`).
4. `module-settings` (сделано; вкладка SEO — патч, см. §9.1 — с 14.09.2026 его кладёт
   `module-seo`, а не сайт), затем `admins.form` и обе проверки на демо (§9.2). Форму
   администраторов на экраны пока не переводим — решение от 14.09.2026, вернуться позже.
5. `module-seo` (сделано): второй модуль, который регистрирует свой тип поля — `wx-seo`, — и
   первый, который патчит чужой экран. Форма правила при этом осталась шаблоном, как
   `admins.form`: механизм обкатывается на том, что уже переведено.

## 14. Документация, которая выходит вместе с кодом

Механизм бесполезен, если о нём знает только сессия, которая его писала. Поэтому в тот же PR, что
и код, входит:

- **Гайд `apps/docs/guide/screens.md`** — для того, кто подключает панель к проекту: как выглядит
  узел, как написать патч, где его зарегистрировать (PHP и `admin.ts`), как добавить свой тип на
  обеих половинах, как включить условную видимость. Примеры — из этой спецификации, проверенные.
- **Таблица реестра типов** в том же гайде: тип, kind, компонент, какое значение хранит, какие
  `props` имеют смысл. Таблица **генерируется из реестра** скриптом, и тест падает, если она
  устарела: список типов не должен жить в двух местах.
- **Раздел в гайде каждого модуля** (`guide/settings.md`, `guide/admins.md`): имена его экранов и
  `id` узлов по умолчанию — это публичный контракт, по которому проект пишет патчи, и его надо
  видеть без чтения JSON.
- **JSON-схемы** по постоянным адресам на сайте документации (§10).
- **`CLAUDE.md`**: ссылка на эту спецификацию в §1 и, по мере появления, ловушки в §4 — как со
  всем остальным.
- **README** пакетов `module-admin`, `@webx-ui/schema` и `module-settings` — по абзацу, куда идти
  дальше.
