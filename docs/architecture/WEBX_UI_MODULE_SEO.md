# `webx-ui/module-seo` — спецификация и план реализации

Раздел панели для SEO, не привязанного к сущности, и рендер `<head>` на публичной части. Пара к
нему — `@webx-ui/module-seo`. Реестр пакетов — [`WEBX_UI_COMPOSER_PACKAGES.md`](WEBX_UI_COMPOSER_PACKAGES.md),
экраны — [`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md).

Статус: выпущено — правила, редиректы и `<head>`, SEO сущностей, сопровождение сущностей (§17),
перелинковка и FAQ страниц (§18), Open Graph (§20), соседи списка (§21). Итог — §13, отложенное —
§16.

## 1. Границы

Модуль владеет **SEO, у которого нет сущности**: параметрами для произвольных URL, редиректами и
глобальными дефолтами. Он же **собирает ответ для шаблона** — резолвер и печать `<head>` живут
здесь.

SEO сущности хранит сама сущность: трейт `HasSeo` и таблица `seo_meta` лежат здесь, а модуль
сущности подключает их у себя. Для резолвера сущность — ещё один источник (§5), без правок
резолвера.

### Почему один пакет, а не два

В реестре SEO записан двумя пакетами — библиотека `webx-ui/seo` и раздел `webx-ui/module-seo`.
**Решено делать одним.** Наше правило именования (CLAUDE.md §1): `module-*` — то, из чего состоит
панель, голое имя — библиотека, которая живёт **без** панели. `nested-set` — чистый алгоритм,
`localization` публичная часть использует сама по себе, а SEO-рендеру без SEO-раздела рисовать
нечего: ни правил, ни дефолтов, ни Organization — всё это авторится в панели. По собственному
критерию библиотекой он не является.

Шов при этом намечен внутри и его надо держать: рендер и резолвер — в `WebxUi\Seo\Rendering\`,
раздел — в `WebxUi\Seo\Panel\`, источники регистрируются через контракт, а не зашиваются. Если
когда-нибудь контентным модулям понадобится трейт без раздела, разрез по готовому шву —
механический, и на 0.x он дёшев.

## 2. Принятые решения (не переоткрывать)

1. **Один пакет на обеих половинах**: composer `webx-ui/module-seo` (namespace `WebxUi\Seo\`),
   npm `@webx-ui/module-seo`.
2. **Префикс таблиц — `seo_*`, не `cms_*`.** `cms_users` и `cms_settings` — каркас; модуль
   называет таблицы по себе, как `module-media` называет `media_directories` и `media_files`.
3. **Приоритет мержится по полям, а не по источникам.** Правило для URL, в котором заполнен только
   `title`, не стирает `description`, пришедший ниже по цепочке. Иначе первое же правило обнуляет
   половину разметки, и это выглядит как поломка движка.
4. **Текстовые контентные поля переводимые**: `title`, `h1`, `description`, `keywords`,
   `og_title`, `og_description` — по колонке на поле. Не переводимые: `og_image`, `pattern`,
   `match_type`, `priority`, `canonical`, `robots`, `json_ld`, `is_active`. Механизм —
   существующий `HasTranslations` из `webx-ui/localization`, без новых зависимостей и без своего
   варианта хранения (§3).
5. **`robots` и `robots.txt` — разные вещи.** `SeoData::$robots` — мета-директивы страницы
   (`noindex`, `nofollow`, …), печатаются в `<meta name="robots">`. `seo.robots-txt` — глобальная
   настройка, отдаётся маршрутом `/robots.txt`. Слова похожие, сущности разные; сказать это в
   гайде прямо.
6. **Микроразметка делится на три уровня.** Про сайт (`Organization`, `WebSite`) — полями в
   настройках, JSON-LD собирается из них сам. Про сущность (`Article`, `Product`,
   `BreadcrumbList`) — кодом модуля, контрактами §17: заполнять руками вредно, разметка разъедется
   с содержимым. Штучные исключения — поле «свой JSON-LD» у правила URL. Конструктора schema.org в
   панели **не делаем**: типов сотни, польза мала.
7. **Карточка `wx-seo` — в `@webx-ui/module-seo`**, не в ядре: ядро не знает предметных областей.
   Она же регистрируется типом в реестре экранов, чтобы её можно было вставить патчем в форму
   сущности.
8. **Вкладка SEO в настройках приезжает из модуля** (§9), а не патчем сайта.
9. **Форма правила — шаблон, а не экран.** Как `admins.form`: на экраны пока не переводится.
10. **Лога 404 нет** (§16); аудит — отдельный модуль (§19).
11. **Релиз общий** — своего порядка у модуля нет.

## 3. Схема

### `seo_urls`

| Колонка                                                                | Тип                         | Примечание                                       |
| ---------------------------------------------------------------------- | --------------------------- | ------------------------------------------------ |
| `id`                                                                   | `bigIncrements`             |                                                  |
| `match_type`                                                           | `string(8)`                 | `exact` \| `mask` \| `regex`                     |
| `pattern`                                                              | `string(2048)`, без индекса | адрес, маска (`/catalog/*`) или регулярка        |
| `priority`                                                             | `integer` default `0`       | внутри группы совпадения, по убыванию            |
| `title`, `h1`, `description`, `keywords`, `og_title`, `og_description` | `json` null                 | переводимые, ставятся `Translatable::columns()`  |
| `og_image`                                                             | `json` null                 | значение `wx-media` — объект, **не** переводимое |
| `canonical`                                                            | `string(2048)` null         |                                                  |
| `robots`                                                               | `string(255)` null          | мета-директивы через запятую                     |
| `json_ld`                                                              | `json` null                 | свой блок разметки для этого адреса              |
| `is_active`                                                            | `boolean` default `true`    |                                                  |
| `created_at`, `updated_at`                                             | `timestamps`                |                                                  |

Модель `SeoUrl` использует **наш** `HasTranslations` из `webx-ui/localization` — `spatie/laravel-translatable`
не подключается ни здесь, ни где-либо ещё. Совпадает только форма данных в колонке
(`{"en": "…", "ru": "…"}`), и это сделано нарочно: карту, записанную по такой конвенции, прочитает
что угодно, а уход от неё — вопрос чтения колонки, а не миграции.

Каст вместо трейта не подходит: он закрывает разрешение значения и запись, но не даёт скоупов
запроса (`whereTranslation`, `orderByTranslation` строят путь `title->ru`), а `__toString` вернул
бы язык неявно — тогда как у нас он передаётся явно везде, от `X-Webx-Locale` до
`FieldType::resolve()`. Если каст понадобится, это правка в `webx-ui/localization` для всех
модулей сразу, а не развилка внутри SEO.

**Почему по колонке на поле, а не одна `data` со всем внутри.** `HasTranslations` работает по
атрибуту: он читает `$this->attributes[$key]` и ждёт там карту языков. Общая колонка означала бы
`{"title": {"en": …}}` — уровнем глубже, чем трейт понимает, то есть второй механизм переводов
рядом с первым. Плюс поиск и сортировка в таблице правил: `whereTranslationLike('title', …)`
собирает путь `title->ru` сам, а с общей колонкой это писалось бы руками мимо скоупов. Словарь
SEO-тегов закрыт — это стандарт, а не пользовательские поля, поэтому новая колонка здесь событие
редкое и честное. Произвольное содержимое без схемы живёт в `json_ld`.

**`og_image` не переводимое**: картинок на разных языках у нас нет. Если понадобятся, это будет
**не просто флаг**: колонка уже хранит объект (`{"path": …}`), и `getTranslations()` примет его ключи за коды
языков. Значит, миграция должна переписать строки (`{…}` → `{"<язык по умолчанию>": {…}}`), а не
только добавить поле в `translatable()`. То же касается любого другого объектного значения, которое
позже решат переводить.

Уникальности по `pattern` нет намеренно: два правила на один адрес разводятся `priority`, и это
дешевле, чем объяснять редактору конфликт уникального индекса.

**Индекса по `pattern` тоже нет**: колонку такой ширины переносимо не
проиндексировать — MySQL кончается на 191 символе utf8mb4, а `Blueprint` длину префикса не умеет.
И индексировать нечего: публичная часть сверяется со скомпилированным списком из кеша, а панель
ищет через `like '%…%'`, которому индекс не помог бы всё равно.

| -------------------------- | ----------------------------- | ------------------------------------------ |

## 4. Подбор по адресу

Один класс `UrlMatcher` обслуживает и правила, и редиректы — иначе они разъедутся в поведении, и
«почему маска работает в правилах и не работает в редиректах» станет вопросом поддержки.

- **Что сравниваем:** путь с query-строкой, как пришло, без схемы и хоста
  (`/catalog/shoes?page=2`). Query нужен: страницы фильтров и пагинации — половина смысла правил
  для URL. Хвостовой слэш нормализуется (кроме корня).
- **Порядок:** сначала все `exact`, потом `mask`, потом `regex`; внутри группы — `priority` по
  убыванию, при равенстве `id` по возрастанию. Побеждает первое совпадение.
- **Маска:** `*` — любой отрезок без `/`, `**` — с `/`. Компилируется в регулярку один раз.
- **Регулярка:** хранится как есть, проверяется при сохранении (`preg_match` на пустой строке в
  try/catch); битая регулярка — ошибка валидации, а не 500 на публичной части.
- **Кеш:** активные правила и редиректы лежат в кеше скомпилированным списком, сброс — на
  `saved`/`deleted` модели. Публичная часть не должна делать запрос на каждый хит.

## 5. Источники и резолвер

```
interface SeoSource
{
    public function priority(): int;
    public function forUrl(string $url, ?object $subject = null, ?string $locale = null): ?SeoData;
}
```

Язык — в сигнатуре, а не из глобального состояния: он передаётся явно везде, от `X-Webx-Locale`
до `FieldType::resolve()`.

- `SeoSources` — реестр-синглтон, источники регистрируются из провайдеров. Резолвер сам ничего не
  знает ни про таблицы, ни про настройки.
- `UrlRuleSource` — приоритет `100`, читает `seo_urls`.
- `DefaultsSource` — приоритет `10`, читает `settings('seo.*')`: OG по умолчанию, шаблон title,
  Organization/WebSite в JSON-LD.
- `EntitySource` — приоритет `50`, читает `seo_meta` через `HasSeo` у переданного subject.
- `FallbackSource` — приоритет `30`: собственные имя, лид и картинка сущности без карточки
  (`HasSeoFallback::seoFallback()`, ответ собирает `SeoData::fallback()`), или то, что передал
  шаблон страницы-маршрута: `@webxSeo(fallback: ['title' => …])`. Ниже карточки, выше дефолтов —
  фото рецепта побеждает `seo.default-og`. Шаблоны модулей `<title>` сами не печатают — иначе
  мимо шаблона заголовка, `og:title` и картинки.

`SeoData` — value-object: `title`, `h1`, `description`, `keywords`, `canonical`, `robots`,
`og` (массив), `jsonLd` (список блоков). Ключевой метод — `mergeOver(SeoData $lower): SeoData`:
пустое поле уступает нижнему источнику, `jsonLd` складывается.

`Seo::for(string $url, ?object $subject = null, ?string $locale = null): SeoData` — обходит
источники по убыванию приоритета, мержит, подставляет шаблон (`{title} — {site}`), обрезает по
лимитам из конфига. Шаблон не трогает заголовок, в котором название сайта уже есть (сравнение по
буквам и цифрам, без регистра): «О нас | Акме» не превращается в «О нас | Акме — Акме». Главная
без написанного заголовка называется именем сайта, а не «Главная — Акме». Self-canonical и
`og:url` строятся от корня сайта без фронт-контроллера (`/index.php/about` → `…/about`). Язык — запрошенный; значения разворачиваются `forLocale()`, как это делает
`FieldType::resolve` у настроек.

## 6. Рендер

- Blade-компонент `<x-webx-seo::head :for="$page" />` и директива `@webxSeo` / `@webxSeo($page)`.
- Печатает `<title>`, `meta description`, `meta keywords`, `meta robots`, `link rel=canonical`,
  `og:*`, блоки `application/ld+json`.
- Конфиг `webx-seo.php`: шаблоны по умолчанию, мягкие лимиты длин (для счётчиков в панели и
  подрезки), какие блоки печатать, приоритеты источников.
- Экранирование — обязательный тест: заголовок с кавычками и `<` не должен ломать разметку, а
  JSON-LD печатается через `json_encode` с `JSON_UNESCAPED_UNICODE | JSON_HEX_TAG`.

## 7. Редиректы

Middleware `webx.redirects` — **глобальная, не в группе `web`**. Адрес, ради которого пишут
редирект, — это адрес, под который у сайта уже нет маршрута, а запрос к такому адресу ни в какую
группу не попадает: роутер бросает `NotFoundHttpException` раньше. В группе редиректы срабатывали
бы только на страницах, которые и так работают. Testbench этого не видит (маршрут в тесте есть) —
ловит `scripts/php-smoke.sh`.

Раз middleware глобальная, она видит и адреса панели, поэтому пропускает всё под
`webx-admin.path` и `webx-admin.api_path`: маска `/**`, написанная редактором, иначе закрыла бы
ему и экран, на котором он её написал, и тот, где её можно было бы убрать. Алиас `webx.redirects`
остаётся — на случай, если приложение захочет расставить её само.

Ищет совпадение, отдаёт `301`/`302`, увеличивает `hits` и пишет `last_hit_at` (`increment()` без
загрузки модели).

Защита от петли: если цель совпадает с источником после нормализации — правило игнорируется, и это
видно в панели меткой. Цепочки (A→B→C) сами не схлопываются — это исправление аудита
`seo.collapse-chain` (§19).

## 8. `robots.txt`

Маршрут `/robots.txt` отдаёт значение настройки `seo.robots-txt` с `Content-Type: text/plain`.
Если значение пустое — `404`, чтобы не перебивать файл, который может лежать в `public/`. Ловушка
для гайда: физический файл веб-сервер отдаёт раньше Laravel, и это нормальное поведение, а не баг
модуля.

## 9. Патч настроек

Из провайдера модуля: `Screens::extend(Settings::SCREEN, __DIR__.'/../resources/screens/settings.json')`.
Порядок загрузки безопасен — `ScreenRegistry::extend` допускает патч к ещё не зарегистрированному
экрану, а провайдер проекта грузится последним и остаётся с последним словом.

Узлы патча (их `id` — публичный контракт, по которому проект пишет свои патчи):

| `id`             | тип           | `name`               | назначение                      |
| ---------------- | ------------- | -------------------- | ------------------------------- |
| `seo`            | `wx-tab`      | —                    | вкладка                         |
| `seo-card`       | `wx-card`     | —                    |                                 |
| `default-og`     | `wx-media`    | `seo.default-og`     | в слот `sidebar`, `aspect 16/9` |
| `title-template` | `wx-input`    | `seo.title-template` | `{title} — {site}`              |
| `robots-txt`     | `wx-textarea` | `seo.robots-txt`     | содержимое файла                |
| `org-name`       | `wx-input`    | `seo.org-name`       | Organization, переводимое       |
| `org-logo`       | `wx-media`    | `seo.org-logo`       | Organization                    |
| `org-socials`    | `wx-repeater` | `seo.org-socials`    | `sameAs`: список адресов        |

Ловушка, уже стоившая времени (CLAUDE.md §4): **точка в ключе — часть ключа, а не путь**.
`seo.default-og` — одно имя; валидатор Laravel и `assertJsonPath` читают его как вложенность.

## 10. API панели

Префикс `config('webx-admin.api_path').'/seo'`, middleware `['web', 'webx.panel-locale', 'cms.auth']`,
права `cms.can:seo.view,seo.manage` на чтение и `cms.can:seo.manage` на запись.

| Метод и адрес                   | Что делает                                                                |
| ------------------------------- | ------------------------------------------------------------------------- |
| `GET /urls`                     | список правил, поиск по `pattern`, фильтр по `match_type`                 |
| `POST /urls`                    | создать                                                                   |
| `GET`/`PUT`/`DELETE /urls/{id}` | одно правило                                                              |
| `GET /redirects` и т.д.         | то же для редиректов                                                      |
| `POST /test-url`                | `{ url }` → какое правило совпало, итоговый `SeoData`, цепочка источников |

`test-url` — главный инструмент поддержки: «почему на этой странице не тот title» задают чаще
всего, и отвечать на это должен один вызов, а не чтение кода.

Списки отдаются `->paginate()` как есть — таблица ядра принимает формат Laravel.

## 11. Модуль в панели

`SeoModule extends AbstractModule`: `id()` — `seo`, `group()` — `system`, `permissions()` —
`seo.view`, `seo.manage`, `order()` — рядом с настройками (у `module-settings` 800; взять 700,
чтобы SEO стоял выше), `icon()` — уточнить имя в наборе ядра.

MCP-инструменты (`ProvidesMcpTools`): `urls_list`, `urls_get`, `urls_set`, `urls_delete` (mutating,
`dry_run`), `test_url`, `redirects_list`, `redirects_set`, `redirects_delete`, `import_redirects`
(список «старый → новый»). `test_url` спрашивает источники с сущностью, которую реестр адресов
нашёл по этому адресу, — как публичная страница.
Скоупы `seo:read` / `seo:write`.

## 12. npm-половина

```
packages/module-seo/src/
├── module.ts         seo(): AdminModule — маршруты /seo и /seo/redirects, types: { 'wx-seo': … }
├── SeoUrlsPage.vue   таблица правил + диалог правила
├── SeoRedirectsPage.vue  таблица редиректов, быстрый ввод, импорт списком
├── SeoCard.vue       WxSeo — карточка полей
├── api.ts  types.ts  messages.ts  i18n.ts  index.ts
```

`WxSeo` — карточка: title, h1, description, keywords, robots (набор чекбоксов, не свободная
строка), canonical, OG (через `wx-media` + превью), счётчики длины с мягкими лимитами, превью
сниппета как в выдаче, поле «свой JSON-LD» на `WxCodeEditor` с проверкой синтаксиса. Языковые
чипы — тем же механизмом, что у названия проекта в настройках (флаг `localized` у узла).

Регистрация типа — как у медиа (`types: { 'wx-seo': { component: SeoCard, kind: 'field' } }` в
`module.ts`, `FieldTypes::register('wx-seo', …)` на php). Значение типа — объект полей SEO;
описать его форму в гайде.

Английские дефолты фраз — в `messages.ts`, словарь с сервера их перекрывает. Второго словаря
внутри npm-пакета быть не должно.

## 13. Выпуск

- **Правила по адресу, редиректы, `robots.txt`, `<head>`**, вкладка SEO в настройках патчем от
  модуля; карточка `wx-seo`.
- **SEO сущностей** вместе с `module-pages`: `seo_meta`, `HasSeo`, `EntitySource` (приоритет 50),
  тип поля `wx-seo` на сервере, карточка патчем в форму. Карточку форма сущности пишет сразу, а не
  в черновик; пустая карточка удаляет строку, а не хранит строку из `null`; имена и лимиты полей —
  в классе `Fields`, а не в трейте (константу трейта снаружи не прочитать); список переводимых
  полей называет модель, не трейт.
- **Сопровождение сущностей** (§17): карта сайта, canonical на себя, hreflang, крошки, schema.org.
- **Перелинковка и FAQ страниц** (§18) — тремя заходами: php перелинковки, её панель, FAQ целиком.
- **Open Graph из данных страницы** (§20), **соседи страницы списка** (§21).

Что важно помнить: физический `public/robots.txt` отдаётся раньше Laravel — на сайте с модулем
его быть не должно; в npm-половине тест паритета `messages.ts` и `lang/en/*.php`.

## 17. Сопровождение сущностей

SEO у модулей полное с первого дня, а не «карточка сейчас, остальное потом». Живёт в `module-seo`
и `routing`; страницы, блог и все модули после них получают это готовым.

### 17.1. Принятые решения (не переоткрывать)

1. **Контракты, а не плагины.** У каждой вещи ниже ровно один вопрос к сущности, и он пишется
   интерфейсом на модели. Модуль реализует то, что ему нужно, и ничего не регистрирует.
2. **В карту сайта попадает ровно то, чему `<head>` не печатает `noindex` и чей canonical
   указывает на себя, — и отвечает на это тот же резолвер `Seo::for()`.** Своих правил отбора у
   карты нет. Иначе тег блога с правилом SEO (решение 10 спеки блога) был бы в индексе, но не в
   карте, или наоборот, и расхождения никто не увидит.
3. **«Видно ли на сайте» — один ответ для обработчика и для карты:** контракт `Visible` в
   `routing` (§17.2). Карте нужен ответ запросом, а не на одной модели, и обработчики отвечают 404
   по нему же (`WEBX_UI_ROUTING.md` §8.6).
4. **Источник адресов карты — реестр `routing`**, канонические строки. Сущность без строки в
   реестре в карту не попадает по определению: у неё нет адреса.
5. **Собственный canonical по умолчанию — у любой страницы**, а не только у сущности: ставится в
   `Seo::for()`, его видят `<head>`, карта и `test-url`; `og:url` берёт его же. Из query
   сохраняется только `page` (решение 12 блога: пагинация в query), остальное отбрасывается.
   Заполненное поле карточки или правила выигрывает. Настройки — `webx-seo.canonical.self` и
   `webx-seo.canonical.query`.
6. **Хлебные крошки — одна цепочка для разметки и для вёрстки.** Сущность отдаёт список, из него
   печатаются и `BreadcrumbList`, и видимые крошки (Blade-компонент). Две цепочки разъедутся
   первой же сменой главной рубрики.
7. **schema.org сущности модуль пишет кодом** (§2.6). Конструктора типов в панели нет. Поле «свой
   JSON-LD» у правила — для штучных исключений.
8. **hreflang — из реестра.** Альтернативы языков у сущности — её канонические строки в других
   языках, в которых она видна **и открыта для индекса** (ни `noindex`, ни чужого canonical);
   меньше двух языков — ни одной строки. Для адресов без сущности (лента блога, свои маршруты
   модулей) — тот же путь под приставкой каждого активного языка, и только при стратегии `prefix`:
   при `header` адрес один на все языки. Общий ответ «почему закрыто» — `Seo::closedBecause()`.

### 17.2. Контракты

```php
namespace WebxUi\Routing\Contracts;

/** Whether the public site shows this entity. The handler and the sitemap ask the same thing. */
interface Visible
{
    public function isVisible(?string $locale = null): bool;

    /** The same answer as a query, for lists and the sitemap. */
    public function scopeVisible(Builder $query, ?string $locale = null): Builder;

    /** For <lastmod>: when what a reader sees last changed. */
    public function visibleUpdatedAt(): ?CarbonInterface;
}
```

```php
namespace WebxUi\Seo\Contracts;

/** The trail above an entity, the entity itself last, the site's home not included. */
interface HasBreadcrumbs
{
    /** @return list<Crumb> */
    public function breadcrumbs(string $locale): array;
}

final readonly class Crumb
{
    public function __construct(public string $title, public ?string $url) {}
}

/** Schema.org blocks this entity says about itself. */
interface HasStructuredData
{
    /** @return list<array<string, mixed>> */
    public function structuredData(string $locale): array;
}
```

Главную сайта в крошки первым пунктом добавляет сам `module-seo`: её название — настройка
`seo.home-crumb` (переводимая, по умолчанию слово из словаря), адрес — корень в языке. Сущность
про главную не знает. Шаг крошек без адреса печатается текстом и остаётся в `BreadcrumbList` без
`item`; невидимый предок и скрытая главная рубрика выпадают из цепочки; у главной цепочки нет.

JSON-LD, который зависит не от сущности, а от конкретной выдачи (`ItemList` на странице рубрики),
кладёт обработчик: `Seo::push(array $block)`. Блок живёт в атрибутах запроса и складывается с
остальными, как `jsonLd` в `mergeOver()`.

### 17.3. Карта сайта

- **`/sitemap.xml` — индекс**, по файлу на тип реестра: `/sitemap-{type}.xml`; больше 45 000
  адресов — `/sitemap-{type}-{n}.xml` (лимит протокола 50 000, запас на языки). Именованные
  маршруты модулей без сущности (лента блога, индекс услуг) — `SitemapRoutes::register('blog.feed')`
  из провайдера, файлом `sitemap-routes.xml`; отбор тот же — через резолвер.
- **Строка карты:** `<loc>` канонического адреса, `<lastmod>` из `visibleUpdatedAt()`, на
  многоязычном сайте — `xhtml:link rel="alternate" hreflang` на каждый язык и `x-default`.
  `changefreq` и `priority` не печатаем: поисковики их игнорируют, а редактор будет их крутить.
- **Отбор** (решение 2). Тип участвует, если его модель реализует `Visible`. Строки берутся
  пачками по 500 с `scopeVisible()`, `seo_meta` подгружается к пачке одним запросом, и каждая
  строка проходит `Seo::for()` против скомпилированного кеша правил (§4).
- **Тип, который не страница.** Сайт может подменить обработчик модуля своим (`bind`), который на
  каждый адрес отвечает 301 (события ведут на внешнюю запись). Такой обработчик реализует маркер
  `WebxUi\Routing\Contracts\NotAPage`; тип выпадает из карты целиком, `status()` и `verdict()`
  говорят `not-a-page`. Списка типов в конфиге нет намеренно — он разошёлся бы с привязкой.
- **Кеш.** Файлы строятся по первому запросу и кладутся в кеш приложения. Ключ несёт поколение,
  которое поднимает один wildcard-слушатель `eloquent.*` на реестр, `seo_meta`, `seo_urls` и любую
  модель `Visible`, плюс `SettingsSaved` с `seo.*`: новому модулю с `Visible` делать ничего не
  нужно. В ключе ещё формат, флаг стиля и набор типов `NotAPage` (подмена приезжает деплоем).
  Страховка — TTL в сутки: будущая дата статьи наступает без события. `webx:seo:sitemap`
  прогревает всё сразу (адреса от `APP_URL`; запрос — от своего хоста).
- **`robots.txt`** дописывает строку `Sitemap: <абсолютный адрес>`, если в настройке её нет;
  подсказка под полем говорит, что она добавится сама.
- **Вид файла** — элемент на строку, атрибуты `xhtml:link` колонкой; каждый файл ссылается на
  `/sitemap.xsl` (корневой путь: браузер применяет стиль только со своего origin) — тот же текст с
  подсветкой и кликабельными адресами, не таблица: таблица прячет разметку, которую и проверяют.
  Отключается `webx-seo.sitemap.stylesheet`.
- **Выключатель** — `webx-seo.sitemap.enabled` (по умолчанию включено). Сайт со своей картой
  выключает его и остаётся со своей.

### 17.4. `<head>` сущности

`<x-webx-seo::head :for="$entity" />` (и `@webxSeo($entity)`) дополнительно печатает
`<link rel="alternate" hreflang>` по решению 8, `BreadcrumbList` из `breadcrumbs()`, блоки
`structuredData()` и всё, что положено через `Seo::push()`. Twitter и Open Graph — §20.

Видимые крошки — `<x-webx-seo::breadcrumbs :for="$entity" />`: `<nav aria-label>` со списком,
последний пункт без ссылки, с `aria-current="page"`. Вьюху сайт публикует и переделывает, но
цепочку берёт отсюда же (решение 6). Всё печатаемое идёт через конфиг `webx-seo.print`, и каждую
вещь можно выключить.

### 17.5. Первые потребители

| Модель    | `Visible`                          | `HasBreadcrumbs`                              | `HasStructuredData`                            | `lastmod`                    |
| --------- | ---------------------------------- | --------------------------------------------- | ---------------------------------------------- | ---------------------------- |
| `Page`    | опубликована, не в корзине         | предки из `nested-set` (кроме главной)        | —                                              | дата публикации              |
| `Article` | `published_at <= now()`            | лента (если есть приставка) → главная рубрика | `BlogPosting`: заголовок, даты, автор, обложка | позднее из даты и публикации |
| `Rubric`  | `is_visible`                       | лента → рубрика                               | — (`ItemList` кладёт обработчик через `push`)  | `updated_at`                 |
| `Tag`     | всегда (`noindex` решает резолвер) | лента → тег                                   | —                                              | `updated_at`                 |

Тег — проверка решения 2: тег с флагом `noindex` и без правила в карту не попадает, тег с правилом
попадает, хотя флаг стоит. И ни строчки про теги в коде карты.

### 17.6. Панель и MCP

- Над списком правил — полоса «Карта сайта»: адрес, число адресов по типам, когда собрана,
  «Пересобрать» и сколько адресов **не** вошло (`noindex`, чужой canonical): это первый вопрос,
  когда страницы нет в выдаче.
- `test-url` (§10) отвечает `sitemap: {included, reason}` (`disabled`, `unknown`, `alias`,
  `hidden`, `noindex`, `canonical`).
- MCP: `seo_sitemap_status`. Отдельного инструмента пересборки нет: карта пересобирается сама.

### 17.7. Тесты

Карта: черновика и запланированной статьи нет (статья появляется по TTL), `noindex` карточки и
маски убирает адреса, чужого canonical нет; тег по решению 2; многоязычие и `x-default`, при
`header` альтернатив нет; разбиение на файлы — порогом из конфига; поколение кеша; canonical с
`?page=2` и без `utm_`; крошки из одной цепочки; `Sitemap:` в `robots.txt` один раз; обработчики
отвечают 404 по `Visible` на тех же случаях; экранирование JSON-LD; `scripts/php-smoke.sh` — карта
после `route:cache` и `config:cache`.

## 18. Перелинковка и FAQ страниц

Спроектировано вместе с посадочными каталога
([`WEBX_UI_CATALOG_LANDINGS.md`](WEBX_UI_CATALOG_LANDINGS.md)). Обе вещи — инструменты сеошника на
любом адресе сайта: категория, посадочная, статья, страница. Поэтому они здесь, а не в модулях
сущностей. Автоматическая перелинковка внутри каталога (подборки, «товар в подборках») — у
посадочных, §7 их спеки; здесь — то, что сеошник задаёт руками.

### 18.1. Принятые решения (не переоткрывать)

1. **Две независимые функции, обе выключены по умолчанию**: `webx-seo.links.enabled`
   (`WEBX_SEO_LINKS`) и `webx-seo.faq.enabled` (`WEBX_SEO_FAQ`). Включает разработчик под проект —
   это решение по ТЗ, а не кнопка администратора.
2. **Выключенная функция исчезает целиком:** нет вкладки в панели, маршрутов API (404), MCP-
   инструментов; компонент ничего не печатает. Таблицы есть всегда — миграции общие, выключение
   данных не стирает.
3. **Перелинковка — отдельный инструмент со списком доноров**, а не часть правил адресов: её
   присылают по ТЗ целиком на сотни доноров и заменяют целиком, и список правил утонул бы в
   строках «только ссылки».
4. **Блок перелинковки принадлежит донору:** список «акцептор + анкор» в порядке и необязательный
   заголовок. Пустой заголовок — настройка `seo.links-heading`.
5. **Заголовок на группу доноров** («Похожая техника…» на весь раздел) — массовым действием на
   отобранных донорах, а не правилами по маске: механизм подбора один, у отдельной страницы может
   быть свой заголовок.
6. **FAQ страницы — вкладка точного правила адреса**, рядом с мета-тегами: сеошник пишет их одной
   задачей. Правило с одним FAQ мета-теги не перетирает — пустое поле уступает нижнему источнику
   (решение 3 §2).
7. **FAQ — только у точных правил.** Одинаковая разметка `FAQPage` на десятках страниц — то, о чём
   Google просит не делать.
8. **`module-faq` не нужен и не мешает.** Он ставится по ТЗ; если стоит, `FAQPage` на странице одна
   — вопросы обоих источников без повторов.
9. **Адрес привязывается к сущности.** Донор, акцептор и точное правило при сохранении проходят
   резолвер `routing`; найдена сущность — запоминается она, и переименование посадочной или
   категории ничего не теряет. Не найдена — остаётся путь.

### 18.2. Адрес и сущность

Общий для обеих функций и правил объект `UrlTarget`: `locale`, `path`, `entity_type`, `entity_id`.
При сохранении — `Resolver::lookup()`: каноническая строка реестра даёт сущность; алиас даёт
сущность своей канонической строки (адрес из ТЗ мог устареть); путь, который стоит источником
редиректа `seo_redirects`, заменяется целью, и отчёт об этом говорит. Хост отрезается, чужой хост
— ошибка: перелинковка внутренняя.

Текущий путь привязанного адреса — канонический путь сущности на его языке, а не сохранённый.
Сущность удалили — адрес остаётся последним известным путём и считается битым (§18.4).

**Точные правила `seo_urls`** получают `entity_type`/`entity_id` (null у масок, регулярок и
точных адресов с query). Скомпилированный список `SeoRules` подставляет для привязанных правил
текущий путь сущности; кеш правил сбрасывается тем же слушателем, что поднимает поколение карты
(сохранение строки реестра), — правило на `/noutbuki-apple/` после смены слага продолжает
совпадать. В таблице правил видно текущий адрес, старый — подсказкой.

### 18.3. Флаги

- `SeoModule::manifest()` отдаёт `meta: { links, faq }` — npm-половина прячет вкладки по ним, как
  `module-blocks` читает свой `meta`.
- Маршруты API функции регистрируются только при включённом флаге.
- `SeoTools::all()` отдаёт инструменты функции только при флаге — первый модуль, который фильтрует
  MCP-инструменты конфигом.
- Компоненты `<x-webx-seo::links />` и `<x-webx-seo::faq />` при выключенном флаге — пустая строка,
  и шаблон сайта можно не трогать.

### 18.4. Перелинковка

Схема:

| `seo_link_blocks`          | Тип                         | Примечание                                    |
| -------------------------- | --------------------------- | --------------------------------------------- |
| `id`                       | `bigIncrements`             |                                               |
| `locale`, `path`           | `string(8)`, `string(2048)` | донор: язык из приставки адреса, путь без неё |
| `entity_type`, `entity_id` | null                        | §18.2                                         |
| `heading`                  | `string(255)` null          | на языке донора, поэтому не переводимый       |
| `is_active`                | `boolean` default `true`    |                                               |
| timestamps                 |                             |                                               |

| `seo_link_items`                   | Тип                  | Примечание      |
| ---------------------------------- | -------------------- | --------------- |
| `block_id`                         | `foreignId`, cascade |                 |
| `path`, `entity_type`, `entity_id` |                      | акцептор, §18.2 |
| `anchor`                           | `string(255)`        |                 |
| `position`                         | `integer`            |                 |

Донор — адрес на одном языке (у `/ru/catalog/…` и `/uk/catalog/…` разные блоки), поэтому анкор и
заголовок — строки, а не переводы. Донор уникален по (`locale`, сущность) или (`locale`, `path`).

**Битый акцептор:** привязанная сущность удалена или не видна (`Visible`), или путь без сущности
не отвечает ни реестром, ни именованным маршрутом из `SitemapRoutes`. Битые ссылки на сайте не
печатаются, в панели подсвечены.

**Рендер:** `<x-webx-seo::links />` — блок текущего адреса (из `Resolution` запроса, иначе по
пути). Один запрос на блок, кеш с поколением, как у правил. Партиал `webx-seo::links` —
`<nav aria-labelledby>` с заголовком и списком; сайт переопределяет вьюху. Нет блока — ничего.

**Импорт CSV/XLSX** — формат ТЗ как есть: колонки «донор», «акцептор», «анкор» и необязательная
«заголовок» (значение берётся из первой строки донора, где оно есть). Строки группируются по
донору, порядок — порядок файла. Режим: «заменить блоки доноров из файла» (по умолчанию) или
«дописать». Сначала всегда предпросмотр (`dry_run`): доноров и ссылок, что создастся и заменится,
ошибки по строкам — акцептор не найден, ссылка на себя, дубль в блоке, чужой хост, замена по
редиректу. Чтение — `openspout`, как у обмена каталога (зависимость модуля). Выгрузка — тем же
плоским файлом.

**Панель:** вид «Перелинковка» в разделе SEO рядом с правилами, редиректами и алиасами. Список
доноров: адрес, заголовок, ссылок, битых; поиск по адресу донора и по анкору; фильтр «с битыми».
Донор — диалог: заголовок и список «акцептор + анкор» с перетаскиванием (`WxSortableList`),
акцептор — поле адреса с подсказкой из реестра. Массовое действие «Заголовок» — выбранным
галочками или всем донорам с адресом, начинающимся на введённое (`/catalog/s-kh-tekhnika/`);
предпросмотр числа доноров перед применением.

**MCP:** `seo_links_list`, `seo_links_get` (по адресу), `seo_links_set` (блок донора целиком),
`seo_links_delete`, `seo_links_import` (строки JSON, режим, `dry_run`), `seo_links_heading`
(массово по префиксу, `dry_run`).

### 18.5. FAQ страниц

| `seo_faq_items`      | Тип                  | Примечание                                       |
| -------------------- | -------------------- | ------------------------------------------------ |
| `id`                 | `bigIncrements`      |                                                  |
| `seo_url_id`         | `foreignId`, cascade | только `exact`                                   |
| `question`, `answer` | `json`               | переводимые, как поля правила; ответ — rich-text |
| `position`           | `integer`            |                                                  |

- **Форма правила:** у точного правила при включённом флаге — вкладка «FAQ» рядом с карточкой
  мета-тегов в `SeoUrlDialog` (не в `SeoCard`: карточка общая с сущностями). Список «вопрос +
  ответ» (`wx-rich-text`) с перетаскиванием. Смена типа правила с точного при непустом FAQ — 422.
- **Список правил:** колонка «FAQ» (число вопросов) и фильтр «с FAQ».
- **Разметка — из правила, а не из компонента.** `UrlRuleSource` кладёт `FAQPage` в `jsonLd`
  данных правила, поэтому разметка не зависит от того, где и успел ли шаблон поставить
  компонент. Текст ответа — без тегов, как у `module-faq`.
- **Одна `FAQPage` на страницу:** `Seo::blocks()` сливает `FAQPage` из данных правила и блок,
  положенный `module-faq` через `put('faq')`, в одну — вопросы подряд, повтор по тексту вопроса
  выбрасывается.
- **Рендер:** `<x-webx-seo::faq />` — вопросы правила текущего адреса, партиал `webx-seo::faq` на
  `<details>`/`<summary>` (без скрипта), сайт переопределяет. Нет вопросов — ничего.
- **Импорт CSV/XLSX:** «адрес», «вопрос», «ответ» (HTML или текст) — находит активное точное
  правило адреса или создаёт его с пустыми мета-полями; режим «заменить FAQ адреса» или
  «дописать»; предпросмотр, как у перелинковки. Выгрузка — тем же форматом.
- **MCP:** `seo_faq_get` и `seo_faq_set` (по адресу, вопросы целиком), `seo_faq_import`
  (`dry_run`); `seo_urls_get` отдаёт число вопросов.

### 18.6. Тесты

- Флаги: выключено — нет маршрутов (404), инструментов MCP, `meta` ложь, компонент пуст; данные
  после выключения и включения на месте.
- Привязка: правило и донор на категории переживают смену слага; адрес-алиас из ТЗ привязывается к
  сущности; путь за редиректом заменяется целью; чужой хост — ошибка.
- Перелинковка: импорт группирует по донору и держит порядок; «заменить» и «дописать»; ссылка на
  себя и дубль — ошибки строк, остальные строки проходят; битый акцептор не печатается; заголовок
  по умолчанию; массовый заголовок по префиксу.
- FAQ: только у точного правила; `FAQPage` в `<head>` без компонента в шаблоне; одна `FAQPage` при
  стоящем `module-faq` и повторе вопроса; правило с одним FAQ не стирает title сущности; импорт
  создаёт правило с пустыми мета-полями.
- Экранирование: анкор и вопрос с кавычками и `<` — в разметке и в JSON-LD.

### 18.7. Выпуск

Выпущено тремя заходами: php перелинковки (флаги, `UrlTarget`, привязка правил, схема, импорт,
API, MCP), её панель, FAQ целиком на обеих половинах. Чего из текста выше не видно:

- **Флаги** — `WebxUi\Seo\Features::links()/faq()`, читаются в момент вопроса. POST на маршрут
  выключенной функции отвечает **405**, а не 404: его ловит GET-only fallback `routing`. Вкладки
  npm-половины читают `meta` манифеста на каждом рендере — манифест приезжает позже панели.
- **`UrlTarget.path`** — адрес без языковой приставки, со слэшем в начале и с query. Текущий путь
  привязанной цели даёт `UrlTargets::href()`; приставку пишет `SiteUrl::prefix()` из `routing`,
  своей копии правила нет. У `seo_link_items` есть `locale`: акцептор с приставкой другого языка
  — тоже адрес сайта. У `seo_urls` языка нет — он берётся из приставки `pattern`.
- **Привязка точного правила** — в `saving` модели `SeoUrl`, поэтому её получают все двери
  записи. Хвост за строкой реестра (`/catalog/x/red`) — не сущность. Замена по редиректу
  переписывает `pattern`, ответ несёт `redirected_from` один раз.
- **Уникальность донора** держит код, а не индекс: `path` шириной 2048 переносимо не
  индексируется. Список доноров, поиск и массовый заголовок считаются в PHP: адрес привязанного
  донора — текущий адрес сущности, его нет ни в одной колонке (на десятках тысяч доноров
  понадобится колонка). Префикс массового заголовка — по сегментам: `/catalog/tech/` не берёт
  `/catalog/tech-2`.
- **«Акцептор не найден» — ошибка только импорта.** Панель и `seo_links_set` такую ссылку
  сохраняют и показывают битой: иначе сломавшаяся после записи ссылка не дала бы сменить
  заголовок блока.
- **Кеш блоков** — своё поколение, как у карты; кеш правил сбрасывается тем же слушателем на
  строке реестра.
- **Заголовок блока ссылок по умолчанию** — настройка `seo.links-heading` (поле появляется только
  при включённом флаге), затем слово модуля. У FAQ настройки заголовка нет: заголовок ссылок
  меняют по ТЗ, а «Частые вопросы» — нет.
- **Импорт** узнаёт шапку по-английски и по-русски; без шапки — порядок колонок по умолчанию.
  Разделитель CSV угадывается по первой строке; номер строки в ошибках — строка файла. Чтение и
  запись — общий `Spreadsheets\Sheet`. «Заменить» в FAQ стирает FAQ правила во всех языках.
- **FAQ едет с правилом:** отдельных маршрутов нет, `faq` — поле `POST/PUT /seo/urls`; не прислал
  `faq` — вопросы не тронуты, прислал `[]` — стёрты. Сменить тип с точного нельзя, пока у правила
  остаются вопросы, — **и при выключенной функции**: вопросы в таблице есть, маска их размножила
  бы. В диалоге вкладка FAQ у неточного правила с вопросами остаётся заблокированной, с одной
  кнопкой «удалить».
- **Ответ FAQ — HTML.** Текст без тегов (импорт, агент) становится `<p>` с экранированием: иначе
  `a<b` открывал бы тег на странице. Слияние `FAQPage` — `PageFaq::fold()` в конце
  `Seo::blocks()`: все `FAQPage` страницы, откуда бы ни пришли, сворачиваются в первую; повтор —
  по тексту вопроса без регистра и лишних пробелов.
- **Плейграунд** — `apps/playground/server/panel/seo-links.ts` и `seo-faq.ts`; XLSX там
  отбивается, проверяется на настоящем сайте.

## 19. Аудит сайта — в `module-audit`

Аудит — отдельный модуль: большинству его проверок SEO-модуль не нужен, а по правилу имён это свой
раздел панели. Спецификация — [`WEBX_UI_MODULE_AUDIT.md`](WEBX_UI_MODULE_AUDIT.md).

`module-seo` приносит в него, если тот установлен (§7 той спеки): проверки по таблицам (дубли
title, правила на мёртвые адреса, цепочки и битые цели редиректов), middleware нормализации адреса
`NormaliseAddress` (зеркало, https, слэши, индексные файлы, конечный слэш, регистр — одним 301,
каждая часть — настройка, по умолчанию выключена) и исправления кнопкой, включая схлопывание
цепочек редиректов (`seo.collapse-chain`).

## 20. Open Graph из данных страницы

Карточка для соцсетей не заполняется руками — каждая строка выводится из того, что у страницы уже
есть. Поля `og_title`, `og_description`, `og_image` в карточке `wx-seo` видны
(`webx-seo.og.panel_fields`, `WEBX_SEO_OG_FIELDS`, выключает `false`): выведенное остаётся
основой, а поля нужны там, где картинка для соцсетей не та, что у страницы. Записанные значения
побеждают выведенные.

- **Что печатается** (`Rendering\SocialTags`, вызывается из `Seo::head()` и из `AddressReport`
  — ключ `social` в `test-url` / `seo_test_url`): `og:title`, `og:description`, `og:url`
  (= canonical), `og:type`, `og:site_name`, `og:locale`, `og:locale:alternate`, `og:image` с
  `:type`, `:width`, `:height`, `:alt`; `article:published_time`, `:modified_time`, `:section`,
  `:tag`; `twitter:card`, `:site`, `:title`, `:description`, `:image`, `:image:alt`. Пустое не
  печатается; группы — `print.og`, `print.article`, `print.twitter`.
- **Тип страницы** — контракт `Contracts\HasOpenGraph`: `openGraphType()` спрашивается при
  каждом резолве (дёшево, sitemap резолвит всё), `openGraphProperties($locale)` — только при
  печати `<head>` (рубрика и теги — запросы). `article` — статья блога и рецепт (у OG нет типа
  рецепта, а дата и раздел в карточке нужны); всё остальное — `website`: событие, услуга, издание,
  вакансия, каталог — у OG для них нет живого типа, а неверный хуже общего. `product` для товара
  каталога не делали — открыто.
- **Картинка.** `SeoData::$images` — картинки всех источников сверху вниз; первая, которую сеть
  покажет, становится `og:image`. SVG и ICO не показывает никто — проваливаемся к следующему
  источнику (обычно `seo.default-og`). Описывает картинку `Contracts\SharesImages`: без
  `module-media` — по расширению (тип), с ним (`LibraryImages`, привязывается, только если
  провайдер медиатеки загружен) — по записи библиотеки: mime, размеры, а ландшафтное фото от
  1200×630 отдаётся вариантом ровно этого размера (`og.image`; портрет и широкий логотип — как
  есть, иначе обрезка съест суть). Вариант пишется в формате оригинала, то есть после конвейера
  загрузки — WebP. `og:image:secure_url` не печатаем: адрес и так https. Alt — тот, что дали
  картинке при выборе (`SeoData::fallback(..., $imageAlt)`), иначе заголовок страницы; alt едет
  вместе со своей картинкой, а не мержится по полям.
- **Язык** — `og:locale` из языка страницы: `pt-BR` → `pt_BR`, голый код — по таблице
  (`en` → `en_US`, `uk` → `uk_UA`), иначе `xx_XX`; `og.locales` переопределяет.
  `og:locale:alternate` — те же языки, что `hreflang` (`Alternates`).
- **Twitter** — зеркало OG (X читает `og:*` при отсутствии `twitter:*`, но не все читатели);
  `twitter:site` — профиль x.com / twitter.com из `seo.org-socials`; `twitter:card` —
  `summary_large_image`, если есть `og:image`, иначе `summary`.

Открыто: `og:type=product` с ценой для каталога; JPEG-вариант для сетей, которые не берут WebP
(сейчас вариант наследует формат оригинала).

## 21. Соседи страницы списка

`Seo::paginate(Paginator)` — тот, кто сделал пагинатор
(обработчик, контроллер, листинг модуля), до печати `<head>` сообщает, что ответ — страница
списка; `head` печатает `<link rel="prev">` и `<link rel="next">` после canonical. Хранится
на запросе, как `push()`. Первая страница — адрес списка без `?page=1`, как у self canonical и
`<x-webx-pagination>`. Выключатель — `print.pagination` (по умолчанию включён). Первый
пользователь — `module-blog` (`Feed`: лента, рубрика, тег, автор).
