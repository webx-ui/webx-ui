# WebX UI — модуль задач для агентов (`module-tasks`)

Спецификация. Статус: выпущено (§11). Пакеты: `webx-ui/module-tasks` (composer, namespace
`WebxUi\Tasks`) и `@webx-ui/module-tasks` (npm). Идентификатор модуля в панели — `tasks`,
таблицы — `tasks_*`. Гайд — `apps/docs/guide/tasks.md`.

## 1. Зачем

Очередь работы между человеком и агентами (Claude Code и др.). Человек — сам или с ассистентом
через MCP — ставит задачу: спецификация, критерии приёмки, этапы. Агенты-исполнители берут этапы
по одному, каждый этап — отдельная сессия агента с чистым контекстом, и отчитываются в задаче.
Проверка этапа — автоматическая (агентом-диспетчером) или человеком, если этап так помечен.
Вся история — в задаче: кто, что, когда, с каким результатом.

Это **таблица задач со статусами и этапами**, а не трекер общего назначения: без канбана, без
спринтов, без оценок времени, без вложений файлов (ссылки — да). Простота важнее охвата.

Ничего специфичного для конкретных сайтов, людей и проектов в пакете нет: проекты, пути и
правила заводятся данными на сайте.

## 2. Понятия

- **Проект** — где идёт работа: репозиторий, рабочая папка агента, ветка по умолчанию, правила
  проекта для агентов (свободный текст).
- **Задача** — цель, спецификация (markdown), критерии приёмки (markdown), ветка задачи,
  приоритет, статус. Принадлежит проекту.
- **Этап** — законченный, проверяемый сам по себе кусок задачи: задание (markdown), критерии
  этапа, способ проверки (`auto` | `human`), статус, исполнитель, отчёт, ссылка на результат
  (ветка, коммит, PR). Этапы задачи идут **по порядку**: следующий становится доступен, когда
  принят предыдущий.
- **Журнал** — лента событий задачи: смена статусов, отчёты, замечания, вопросы и ответы,
  правки, комментарии. Пишется автоматически и вручную; ничего из него не удаляется.
- **Кто действует** — `Actor`: `admin` (человек), `agent` (имя сессии), `system`. Правила про
  людей спрашивают только `isPerson()`.

## 3. Статусы

### Этап

```
pending ──► ready ──► in_progress ──► review ──► done
              ▲           │   ▲          │
              │           ▼   │          │
              │        blocked┘          │
              └──── rework ◄─────────────┘
любой, кроме done ──► cancelled
```

| Статус        | Значит                                                                       | Кто переводит                                                                           |
| ------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `pending`     | ждёт предыдущих этапов                                                       | система (при создании)                                                                  |
| `ready`       | можно брать                                                                  | система: при `tasks_ready` для первого этапа, при приёмке предыдущего — для следующего  |
| `in_progress` | взят исполнителем                                                            | `tasks_claim_next` (атомарно)                                                           |
| `review`      | исполнитель отчитался                                                        | `tasks_stage_report`                                                                    |
| `rework`      | вернули с замечаниями                                                        | `tasks_stage_rework`                                                                    |
| `blocked`     | исполнитель не может продолжить без решения человека (вопрос, доступ, выбор) | `tasks_stage_block` (с вопросом); обратно в `ready` — `tasks_stage_unblock` (с ответом) |
| `done`        | принят                                                                       | `tasks_stage_accept`                                                                    |
| `cancelled`   | отменён вместе с задачей или вручную                                         | `tasks_cancel` / панель                                                                 |

- `rework` берётся так же, как `ready`, и **раньше** любых `ready` (сначала доделать начатое).
- **Освобождение** возвращает этап туда, откуда его взяли: `rework`, если попытка не первая, —
  чтобы не потерять место в очереди. Ответ на вопрос — в `ready`.
- Переход `ready → pending` есть только у перестановки: этап, перед которым поставили другой,
  снова ждёт.
- Таблица переходов — enum `StageStatus` (`canBecome()`).

### Задача

`draft` → `ready` → `in_progress` → `review` → `done`, плюс `cancelled`. Кроме `draft` и
`cancelled` статус задачи **выводится из этапов** (`TaskStatus::of()`) и руками не ставится:
есть этап `in_progress`/`rework`/`blocked` → `in_progress` (`blocked` — работа начата и ждёт
человека); все этапы `done` → `done`; иначе есть этап `review` → `review`; иначе `ready`.
Отменённые этапы в выводе не участвуют: задача из принятых и отменённых — `done`.

### Правка

В `draft` задачу и этапы можно править как угодно — список этапов заменяется целиком. После
`ready` у задачи меняется только приоритет (это порядок выдачи, а не содержание работы); в списке
этапов должны быть все этапы: начатые и отменённые стоят на своих местах и не меняются, неначатые
(`pending`/`ready`) переставляются и правятся, новые — только в конец. Удаления нет — ненужный
этап отменяют (`cancelStage`; последний оставшийся — нельзя: это отмена задачи). Правка пишется
в журнал видом `edit` с перечнем полей и этапов.

### Кто что может

- Этап `human` принимает и возвращает только человек; на вопрос отвечает только человек.
- Агент не проверяет этап, который сам делал (`assignee`), и отчитывается и спрашивает только по
  этапу, который держит.

## 4. Данные

```
tasks_projects  id, slug, title, workdir, repo_url, default_branch, rules (text),
                archived_at, timestamps
tasks_tasks     id, project_id, number (сквозной в проекте: #12), title, status, priority
                (low|normal|high), spec (text), acceptance (text), branch, created_by
                (admin_id, nullable), closed_at, timestamps
tasks_stages    id, task_id, position, title, brief (text), acceptance (text),
                review_mode (auto|human), status, assignee (строка — имя сессии агента),
                attempt (int, растёт на каждый rework), claimed_at, reported_at,
                accepted_at, status_changed_at, stale_notified_at, report (text),
                result_ref (text: ветка/коммит/URL), timestamps
tasks_journal   id, task_id, stage_id (nullable), actor_type (admin|agent|system),
                actor_name, kind (status|report|rework|question|answer|edit|comment),
                body (text), meta (json: from/to статусы и т.п.), created_at
```

- Таблицы — одной миграцией.
- `status_changed_at` — время последней смены статуса для очереди диспетчера и `stage.stale`
  (`claimed_at` после освобождения пуст). `stale_notified_at` — одно уведомление на «заход»,
  очищается при новой выдаче.
- `question` и `answer` — половины блокировки: их отдают следующей попытке, искать среди
  комментариев нельзя.
- Markdown хранится как есть; в панели рендерится. Удаление задач — только мягкое. Строка журнала
  не меняется и не удаляется — модель бросает исключение.
- Таблицы — `content` для `webx:snapshot`: очередь переезжает вместе с сайтом.

## 5. MCP

Инструменты по правилам WebX: `<module>_<tool>`, `dry_run` у меняющих, ответ — JSON. Каждый
меняющий вызов пишет запись в журнал с именем того, кто вызвал.

| Инструмент                                    | Что делает                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tasks_projects_list` / `_create` / `_update` | проекты                                                                                                                                                                                                                                                                                                                                                                                   |
| `tasks_list`                                  | задачи: фильтры `project`, `status`, `waiting_for_person` (этапы на проверке человеком и с вопросом); сначала приоритет, потом свежие                                                                                                                                                                                                                                                     |
| `tasks_get`                                   | задача целиком: спецификация, этапы с отчётами, журнал                                                                                                                                                                                                                                                                                                                                    |
| `tasks_queue`                                 | компактная сводка для диспетчера: этапы в `ready`, `rework`, `in_progress`, `blocked`, `review` (с `review_mode`), с проектом, задачей, исполнителем, попыткой и временем последней смены статуса, сверху самые давние. Дёшево вызывается раз в минуту                                                                                                                                    |
| `tasks_create`                                | задача **вместе с этапами** одним вызовом (массив `stages`), статус `draft`                                                                                                                                                                                                                                                                                                               |
| `tasks_update`                                | правка задачи и этапов по правилам §3                                                                                                                                                                                                                                                                                                                                                     |
| `tasks_ready`                                 | `draft` → `ready`, первый этап — `ready`                                                                                                                                                                                                                                                                                                                                                  |
| `tasks_claim_next`                            | **атомарно** берёт следующий этап (`rework` раньше `ready`, затем приоритет и возраст задачи), фильтр `project`; аргумент `agent` — имя сессии. Возвращает **пакет контекста**: задача (спецификация, критерии, ветка), проект (`workdir`, `rules`), этап (задание, критерии, номер попытки, замечания последнего rework), отчёты принятых этапов. Нечего брать — пустой ответ, не ошибка |
| `tasks_stage_report`                          | исполнитель: `report`, `result_ref` → `review`                                                                                                                                                                                                                                                                                                                                            |
| `tasks_stage_accept`                          | проверяющий: → `done`, следующий этап — `ready`; последний — задача `done`                                                                                                                                                                                                                                                                                                                |
| `tasks_stage_rework`                          | проверяющий: замечания (обязательно) → `rework`, `attempt + 1`                                                                                                                                                                                                                                                                                                                            |
| `tasks_stage_release`                         | вернуть взятый этап в `ready`/`rework` (исполнитель упал или завис)                                                                                                                                                                                                                                                                                                                       |
| `tasks_stage_block`                           | исполнитель: вопрос человеку (обязательно) → `blocked`; этап не выдаётся, пока не разблокируют                                                                                                                                                                                                                                                                                            |
| `tasks_stage_unblock`                         | человек: ответ (обязательно) → `ready`; ответ попадает в пакет контекста следующей попытки                                                                                                                                                                                                                                                                                                |
| `tasks_comment`                               | комментарий в журнал задачи или этапа                                                                                                                                                                                                                                                                                                                                                     |
| `tasks_cancel`                                | отменить задачу (незавершённые этапы — `cancelled`)                                                                                                                                                                                                                                                                                                                                       |

- **Устройство.** Операции — `Workflow\Tasks`, панель и MCP их только вызывают. Каждая —
  транзакция с блокировкой задачи и этапа, запись в журнал и пересчёт статуса задачи. Открытие
  следующего этапа (`pending → ready`) пишется от имени `system`, всё остальное — от того, кто
  действовал. Ошибки правил — `TaskRefused` с ключом причины (`reason`) и текстом из словаря;
  плохие значения — `ValidationException`. Инструменты (`Mcp\TasksTools`) тонкие: найти задачу,
  проект или этап, решить, кто действует, перевести `TaskRefused` в `ToolFailure`.
- **Имена.** Задача называется id или ссылкой `<проект>#<номер>` (`shop#12`), этап — id из
  `tasks_get`, `tasks_queue`, `tasks_claim_next`. Неизвестный аргумент и неизвестное поле этапа
  отклоняются (`Arguments::strict`).
- **`dry_run`** — настоящая запись в откатываемой транзакции (`Rehearsal`), включая
  `tasks_claim_next`.
- **Выдача** — `Dispatcher`, единственная точка выдачи работы: кандидаты читаются без блокировки
  в порядке «`rework` → приоритет → возраст задачи», каждый берётся условным
  `UPDATE … WHERE status = <прочитанный>`, победителя определяет число изменённых строк;
  проигравший идёт к следующему кандидату. Черновики, отменённые и удалённые задачи и архивные
  проекты не выдаются.
- **Пакет контекста** — `ContextPackage`: проект с `rules`, задача (ветка — своя или ветка по
  умолчанию проекта), этап с номером «n из m», попыткой, замечаниями последнего `rework` и парами
  «вопрос — ответ», отчёты принятых этапов.
- Отдельной отмены этапа в MCP нет; в панели — есть.

### Права

| Скоуп          | Даёт                                                                                                  | Право панели                             |
| -------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `tasks:read`   | `_list`, `_get`, `_queue`, `_projects_list`                                                           | любое из `tasks.view/manage/work/review` |
| `tasks:write`  | создание и правка задач, проектов, `tasks_ready`, `tasks_cancel`, `tasks_comment`                     | `tasks.manage`                           |
| `tasks:work`   | `tasks_claim_next`, `tasks_stage_report`, `tasks_stage_release`, `tasks_stage_block`, `tasks_comment` | `tasks.work`                             |
| `tasks:review` | `tasks_stage_accept`, `tasks_stage_rework`                                                            | `tasks.review`                           |

`tasks_comment` достаётся и `write`, и `work`: скоуп инструмента в `webx-ui/mcp` — список «любой
из» (`scope: [...]` у `Tool::mutating`). `tasks_stage_unblock` — `tasks:write` и `tasks.manage`,
плюс проверка на человека.

**Кто действует.** Аргумент `agent` — значит агент с этим именем сессии. Без него — человек, и
только если соединение человеческое: сессия панели или OAuth-токен с `mcp:use`. **Человек — это
`mcp:use` и не машинный ключ** (`Keys::isKey()`, `WEBX_UI_MCP_ACCESS.md` §12): ключ
`webx:mcp:token` тоже несёт `mcp:use`, но человеком не считается никогда, с какими бы скоупами
ни был выпущен; без `agent` он отклоняется. stdio-сервер (`mcp:start`) без `agent` тоже
отклоняется: за ним нет человека. Поэтому исполнителю — `read + work`, принять собственную работу
он не может; диспетчеру — ещё `review`, но **этапы `review_mode=human` принимает только
человек**: `accept` на таком этапе от агента отклоняется с понятной ошибкой.

### Ресурсы MCP

- `tasks://rules` — правила процесса для агентов (`resources/mcp/rules.md`, общий для всех
  сайтов): как брать этап, что делать до отчёта (гейт проекта), формат отчёта (ниже), что
  запрещено (принимать свою работу, править чужие этапы, менять спецификацию задачи), что делать
  при блокере (`tasks_stage_block` с конкретным вопросом, а не тихий выход и не ожидание ответа в
  сессии).
- `tasks://projects/{slug}` — проект с его `rules`; шаблон адреса (`RegistryResourceTemplate` в
  `webx-ui/mcp`: адрес с `{переменной}` уходит в `resources/templates/list`, переменная — в
  аргументы обработчика).

Формат отчёта (рекомендуемый, рендерится в панели как markdown):

```
## Сделано
## Как проверить
## Результат        ветка / коммит / PR
## Не сделано и почему
## Риски и что задето за пределами этапа
```

## 6. Панель

Без канбана. Экраны на компонентах ядра; из панели действует всегда человек (`Actor::admin`).
API — `routes/api.php` под `webx.panel`, те же операции, что у MCP. Смотреть может любой из
четырёх прав; планировать, отвечать на вопрос и отменять — `tasks.manage`; принять и вернуть —
`tasks.review`; освободить — `tasks.manage` или `tasks.work`; комментарий — любой, кто работает.
Отказ правил — **422** с `message` и `reason` (не 409: его панель читает как конфликт правок и
подменяет текст), плохие значения — 422 с `errors`. Ответ любой операции — задача целиком: один
ход меняет и соседний этап, и статус задачи.

### 6.1. Задачи

Таблица, не доска: проект, #, название, статус, текущий этап (n/m и его статус), приоритет,
обновлено. Виды вместо фильтра статуса: все, «ждёт меня» (`Task::waitingForPerson()` — этап на
проверке человеком или с вопросом; тот же скоуп, что `waiting_for_person` в MCP), в работе,
черновики, закрытые; фильтр проекта и поиск по названию. Список — пагинатор Laravel как есть плюс
`counts` по видам.

**Бейдж «ждёт меня» в меню** — `TasksModule::manifest()` отдаёт `meta.badge` только тому, кто
может действовать (`tasks.review` или `tasks.manage`). В `module-admin` это общее: `NavEntry.badge`
из `meta.badge` любого модуля (положительное целое, иначе ничего), `AdminNav` рисует его в слоте
`trailing` пункта; экран задачи после хода зовёт `refreshManifest()`. На свёрнутом меню бейджа нет.

### 6.2. Задача

Спецификация и критерии (markdown через `renderMarkdown` и `WxProse`), этапы аккордеоном (открыт
тот, что ждёт кого-то): номер, название, статус, исполнитель, попытка; у этапа — задание,
критерии и отчёт, вопрос заблокированного этапа — плашкой над заданием. Действия по статусу и
правам: «В работу» (`draft` → `ready`), «Принять», «Вернуть» (с обязательным текстом),
«Ответить» (на `blocked`, с обязательным текстом), «Освободить», «Отменить этап», «Отменить
задачу». Журнал — лентой внизу; тело отчёта в журнале не повторяется — его читают на этапе.

### 6.3. Форма задачи

Описанный экран `tasks.form`, правила §3 — патчем страницы: после `ready` поля задачи, кроме
приоритета, заблокированы; начатые и отменённые этапы — списком над редактором, в повторителе
только неначатые; при сохранении список собирается заново — начатые на своих местах, остальные в
порядке редактора, новые в конце. Поле, добавленное патчем проекта, нарисуется, но не сохранится:
у задачи нет `extra`.

**Проекты** — `/tasks/projects`, список с диалогом формы; архив — переключателем.

Даты — `WxDate`. Словари — `screen` (подписи формы, переводит сервер) и `panel` (слова экранов,
английский по умолчанию в `messages.ts`), десять языков.

## 6a. Уведомления (Telegram)

Человек не сидит в панели — о том, что от него что-то нужно, он узнаёт из мессенджера. Модуль
шлёт уведомления сам, по событиям задач; каналы — за контрактом `Notifications\Notifier`
(`configured()`, `send(Notice)`), из коробки — `TelegramNotifier` через `bindIf`: привязка сайта
побеждает в любом порядке провайдеров.

**События** (каждое включается в настройках отдельно):

| Событие              | Когда                                                                   | По умолчанию |
| -------------------- | ----------------------------------------------------------------------- | ------------ |
| `stage.review_human` | этап с `review_mode=human` перешёл в `review`                           | вкл          |
| `task.done`          | принят последний этап                                                   | вкл          |
| `stage.blocked`      | исполнитель задал вопрос (`tasks_stage_block`) — в сообщении сам вопрос | вкл          |
| `stage.rework`       | этап вернули на доработку                                               | выкл         |
| `stage.review_auto`  | этап `auto` ждёт проверяющего агента                                    | выкл         |
| `stage.stale`        | этап в `in_progress` дольше N часов (планировщик)                       | вкл, N = 6   |

**Как устроено.** Операции и выдача бросают `Events\StageMoved` и `Events\TaskStatusChanged`
внутри транзакции хода; слушатель `NotifyPeople` решает, о чём сказать, и ставит `SendNotice` с
`afterCommit` — откатанный ход (отказ, `dry_run`) ничего не отправляет. Текст собирается в момент
события (`Notices`) на языке сайта (`app.locale`), ссылка — от `app.url`, а не от запроса:
одинаковая из панели, очереди и планировщика. `stage.stale` — команда `webx:tasks:stale` в
планировщике каждые 15 минут.

**Сообщение** — коротко и со ссылкой, простым текстом без разметки (отчёт агента полон символов,
на которых Markdown Telegram отказывает):

```
⏳ #12 · <проект> — <название задачи>
Этап 2/4 «<этап>» ждёт вашей проверки (попытка 1)
<первые ~300 символов раздела «Сделано» отчёта>
Результат: <result_ref>
<ссылка на задачу в панели>
```

**Доставка.** Переход статуса не ждёт Telegram и не откатывается из-за него. `SendNotice` сам
считает попытки: три, паузы 30 и 120 секунд, ошибка не выбрасывается — на `sync`-очереди она
стала бы ошибкой запроса, который сделал ход; на `sync` попытка одна. Последняя неудача — в лог и
в журнал (`comment` от `system`, `meta.notice`). Ошибка называет чат и слова Telegram, но не
токен. Если из двух чатов один принял, а другой нет, повтор уйдёт в оба.

**Настройки** — экран `tasks.settings`: токен бота, один или несколько `chat_id`, переключатели
событий, `N` для `stage.stale`, кнопка «Отправить тестовое» (шлёт сразу, отказ — 422 со словами
Telegram). Ключи `tasks.notify.*` и `tasks.telegram.chats` — в `module-settings` (поэтому
`module-tasks` его требует), по умолчанию — `config/webx-tasks.php`. Токен — под
`tasks.telegram-token` зашифрованным (`Crypt`), ни одним экраном не описан, поэтому
`settings_get` и `settings_list` его не видят; API отдаёт только `token_set`. Пустое поле токена
его сохраняет, «Забыть токен» — удаляет. Подсказка в форме: как получить токен у `@BotFather` и
узнать `chat_id`.

## 7. Минимальный сайт под задачи

Сайту нужна только панель: публичной части нет. Модули — `admins` (вход, администраторы, OAuth
для MCP), `settings`, `tasks`; ничего больше.

```bash
composer create-project webx-ui/site tasks --no-scripts
cd tasks && cp .env.example .env && php artisan key:generate
WEBX_ADMIN_PASSWORD=… php artisan webx:setup --no-interaction \
  --name="Tasks" --domain=… --modules=admins,settings,tasks --locales=ru \
  --db-connection=mariadb … --admin=… --no-demo
php artisan webx:doctor --strict
```

**Сайт без публичной части — общее для любого сайта**, не только задач:

- У модулей в `Setup\Catalogue` есть признак `public: false` (`admins`, `settings`, `tasks`);
  `Catalogue::hasPublicPart()` — есть ли среди выбранных хоть один модуль, который что-то
  показывает посетителю (чужой модуль — показывает). Нет — `webx:setup` пишет
  `WEBX_PUBLIC=false`, не ставит тему (одевать нечего; `--theme` ставит) и вписывает в
  `routes/web.php` редирект `/` → панель (`// webx:panel-home`, не замыкание — `route:cache` его
  берёт).
- `webx-admin.public` (`WEBX_PUBLIC`, по умолчанию `true`). Выключенный — глобальный middleware
  `Gate\KeepOutOfSearch`: `/robots.txt` отвечает `Disallow: /` раньше любого маршрута (иначе его
  отдал бы `module-seo`), каждый ответ — `X-Robots-Tag: noindex, nofollow`, 404 включительно.
  **Флаг, а не вывод из отсутствия `pages`:** сайт без страниц, но с блогом или каталогом
  публичный, и закрывать его от поисковиков молча нельзя.
- `scripts/php-smoke.sh` собирает такой сайт из скелета и проверяет `WEBX_PUBLIC=false`,
  отсутствие `theme/`, `/` → `/cms`, закрытый `robots.txt`, `noindex` у панели. `webx:doctor
--strict` — на развёртывании, с собранной панелью.

**Подключение агентов:**

- ассистент в чате — коннектор на `https://<сайт>/api/cms/mcp`, вход админом, согласие OAuth;
- агент в терминале — машинный ключ со скоупами (`tasks:read,work` для исполнителя, `+review`
  для диспетчера) через `webx:mcp:token --name=… --scopes=…` и заголовок
  `Authorization: Bearer …` в конфигурации MCP агента.

## 8. Как этим работают агенты (для `tasks://rules` и гайда)

1. Человек с ассистентом пишет задачу: `tasks_create` (draft) → правки → `tasks_ready`.
2. Диспетчер (долгоживущая сессия агента) периодически смотрит `tasks_queue`; для каждого этапа
   `ready`/`rework` открывает **новую** сессию исполнителя в `workdir` проекта.
3. Исполнитель: `tasks_claim_next(agent=<имя сессии>)` → работа в ветке задачи → гейт проекта →
   `tasks_stage_report`. Нужен ответ человека — `tasks_stage_block` с вопросом; человек отвечает
   в панели (`tasks_stage_unblock`), этап снова `ready` и уходит новой сессии вместе с ответом.
4. Диспетчер читает отчёт: этап `auto` — сверяет с критериями и `accept`/`rework`; этап `human`
   — человеку уходит уведомление (§6a), этап ждёт его решения.
5. Последний этап принят — задача `done`.

## 9. Регистрации

Стандартные для composer-пакета и раздела панели (CLAUDE.md §4): раздел в `Setup\Catalogue`
(`default: false`, требует `admins`), `extra.webx.npm`/`panel`, плейграунд с фикстурами
`apps/playground/server/panel/tasks.ts`.

## 10. Что держат тесты

- переходы статусов этапа и вывод статуса задачи — по таблицам §3, включая запрещённые;
- `tasks_claim_next` под конкуренцией: два параллельных вызова — один этап, один пустой ответ
  (в тестах — два чтения кандидата до записи);
- приоритет выдачи: `rework` раньше `ready`, затем приоритет, затем возраст;
- агент не принимает этап `human` и не принимает без скоупа `review`; машинный ключ без `agent`
  не проходит за человека;
- `tasks_create` с этапами одним вызовом, `dry_run` ничего не пишет;
- журнал: каждая смена статуса оставляет запись с автором; правка журнала невозможна;
- уведомления: событие → задание в очереди с нужным текстом; выключенное событие не шлётся;
  ошибка доставки не откатывает переход и пишется в журнал; токен бота не виден через MCP;
- сайт из §7: `/` ведёт в панель, `robots.txt` закрыт, публичных страниц нет.

## 11. Выпуск

Выпущено одним выпуском, пятью этапами:

- **T1** — пакет, таблицы, машина статусов, неизменяемый журнал, операции и выдача, пакет
  контекста.
- **T2** — MCP: инструменты, скоупы, «этап `human` принимает только человек», ресурсы; в
  `webx-ui/mcp` — скоуп-список у инструмента и шаблоны ресурсов.
- **T3** — панель: API, npm-половина, бейдж «ждёт меня» (общий `meta.badge` в `module-admin`),
  словари, плейграунд.
- **T4** — уведомления: `Notifier`, Telegram, настройки, очередь с повтором, `stage.stale`.
- **T5** — сайт без публичной части (`public: false`, `WEBX_PUBLIC`, `KeepOutOfSearch`), гайд,
  реестр пакетов.

Попутно закрыта дыра: ключ `webx:mcp:token` без `--scopes` проходил за человека (§5 «Кто
действует»).
