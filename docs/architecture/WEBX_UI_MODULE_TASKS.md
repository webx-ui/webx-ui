# WebX UI — модуль задач для агентов (`module-tasks`)

Спецификация. Статус: черновик к реализации. Пакеты: `webx-ui/module-tasks` (composer) и
`@webx-ui/module-tasks` (npm). Идентификатор модуля в панели — `tasks`, таблицы — `tasks_*`.

## 1. Зачем

Очередь работы между человеком и агентами (Claude Code и др.). Человек — сам или с ассистентом
через MCP — ставит задачу: спецификация, критерии приёмки, этапы. Агенты-исполнители берут этапы
по одному, каждый этап — отдельная сессия агента с чистым контекстом, и отчитываются в задаче.
Проверка этапа — автоматическая (агентом-диспетчером) или человеком, если этап так помечен.
Вся история — в задаче: кто, что, когда, с каким результатом.

Это **таблица задач со статусами и этапами**, а не трекер общего назначения: без канбана, без
спринтов, без оценок времени, без вложений файлов (ссылки — да). Простота важнее охвата.

Ничего специфичного для конкретных сайтов, людей и проектов в пакете нет: проекты, пути и
правила заводятся данными на сайте.

## 2. Понятия

- **Проект** — где идёт работа: репозиторий, рабочая папка агента, ветка по умолчанию, правила
  проекта для агентов (свободный текст).
- **Задача** — цель, спецификация (markdown), критерии приёмки (markdown), ветка задачи,
  приоритет, статус. Принадлежит проекту.
- **Этап** — законченный, проверяемый сам по себе кусок задачи: задание (markdown), критерии
  этапа, способ проверки (`auto` | `human`), статус, исполнитель, отчёт, ссылка на результат
  (ветка, коммит, PR). Этапы задачи идут **по порядку**: следующий становится доступен, когда
  принят предыдущий.
- **Журнал** — лента событий задачи: смена статусов, отчёты, замечания, комментарии. Пишется
  автоматически и вручную; ничего из него не удаляется.

## 3. Статусы

### Этап

```
pending ──► ready ──► in_progress ──► review ──► done
              ▲           │   ▲          │
              │           ▼   │          │
              │        blocked┘          │
              └──── rework ◄─────────────┘
любой, кроме done ──► cancelled
```

| Статус        | Значит                                                                       | Кто переводит                                                                           |
| ------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `pending`     | ждёт предыдущих этапов                                                       | система (при создании)                                                                  |
| `ready`       | можно брать                                                                  | система: при `tasks_ready` для первого этапа, при приёмке предыдущего — для следующего  |
| `in_progress` | взят исполнителем                                                            | `tasks_claim_next` (атомарно)                                                           |
| `review`      | исполнитель отчитался                                                        | `tasks_stage_report`                                                                    |
| `rework`      | вернули с замечаниями                                                        | `tasks_stage_rework`                                                                    |
| `blocked`     | исполнитель не может продолжить без решения человека (вопрос, доступ, выбор) | `tasks_stage_block` (с вопросом); обратно в `ready` — `tasks_stage_unblock` (с ответом) |
| `done`        | принят                                                                       | `tasks_stage_accept`                                                                    |
| `cancelled`   | отменён вместе с задачей или вручную                                         | `tasks_cancel` / панель                                                                 |

`rework` берётся так же, как `ready`, и **раньше** любых `ready` (сначала доделать начатое).

### Задача

`draft` → `ready` → `in_progress` → `review` → `done`, плюс `cancelled`. Кроме `draft` и
`cancelled` статус задачи **выводится из этапов** и руками не ставится:
есть этап `in_progress`/`rework` → `in_progress`; все этапы `done` → `done`; иначе есть этап
`review` → `review`; иначе `ready`.

В `draft` задачу и этапы можно править как угодно; после `ready` менять можно только этапы в
`pending`/`ready` (задание, критерии, порядок) и добавлять новые в конец.

## 4. Данные

```
tasks_projects  id, slug, title, workdir, repo_url, default_branch, rules (text),
                archived_at, timestamps
tasks_tasks     id, project_id, number (сквозной в проекте: #12), title, status, priority
                (low|normal|high), spec (text), acceptance (text), branch, created_by
                (admin_id, nullable), closed_at, timestamps
tasks_stages    id, task_id, position, title, brief (text), acceptance (text),
                review_mode (auto|human), status, assignee (строка — имя сессии агента),
                attempt (int, растёт на каждый rework), claimed_at, reported_at,
                accepted_at, report (text), result_ref (text: ветка/коммит/URL), timestamps
tasks_journal   id, task_id, stage_id (nullable), actor_type (admin|agent|system),
                actor_name, kind (status|report|rework|comment), body (text),
                meta (json: from/to статусы и т.п.), created_at
```

Markdown хранится как есть; в панели рендерится. Удаление задач — только мягкое; журнал не
редактируется.

## 5. MCP

Инструменты по правилам WebX: `<module>_<tool>`, `dry_run` у меняющих, ответ — JSON. Каждый
меняющий вызов пишет запись в журнал с именем того, кто вызвал (админ или имя агента из
аргумента `agent`).

| Инструмент                                    | Что делает                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tasks_projects_list` / `_create` / `_update` | проекты                                                                                                                                                                                                                                                                                                                                                                                   |
| `tasks_list`                                  | задачи: фильтры `project`, `status`, `review_mode=human` с этапами на проверке                                                                                                                                                                                                                                                                                                            |
| `tasks_get`                                   | задача целиком: спецификация, этапы с отчётами, журнал                                                                                                                                                                                                                                                                                                                                    |
| `tasks_queue`                                 | компактная сводка для диспетчера: этапы в `ready`, `rework`, `in_progress`, `review` (с `review_mode`), с проектом, задачей, исполнителем, попыткой и временем последней смены статуса. Дёшево вызывается раз в минуту                                                                                                                                                                    |
| `tasks_create`                                | задача **вместе с этапами** одним вызовом (массив `stages`), статус `draft`                                                                                                                                                                                                                                                                                                               |
| `tasks_update`                                | правка задачи и этапов по правилам §3                                                                                                                                                                                                                                                                                                                                                     |
| `tasks_ready`                                 | `draft` → `ready`, первый этап — `ready`                                                                                                                                                                                                                                                                                                                                                  |
| `tasks_claim_next`                            | **атомарно** берёт следующий этап (`rework` раньше `ready`, затем приоритет и возраст задачи), фильтр `project`; аргумент `agent` — имя сессии. Возвращает **пакет контекста**: задача (спецификация, критерии, ветка), проект (`workdir`, `rules`), этап (задание, критерии, номер попытки, замечания последнего rework), отчёты принятых этапов. Нечего брать — пустой ответ, не ошибка |
| `tasks_stage_report`                          | исполнитель: `report`, `result_ref` → `review`                                                                                                                                                                                                                                                                                                                                            |
| `tasks_stage_accept`                          | проверяющий: → `done`, следующий этап — `ready`; последний — задача `done`                                                                                                                                                                                                                                                                                                                |
| `tasks_stage_rework`                          | проверяющий: замечания (обязательно) → `rework`, `attempt + 1`                                                                                                                                                                                                                                                                                                                            |
| `tasks_stage_release`                         | вернуть взятый этап в `ready`/`rework` (исполнитель упал или завис)                                                                                                                                                                                                                                                                                                                       |
| `tasks_stage_block`                           | исполнитель: вопрос человеку (обязательно) → `blocked`; этап не выдаётся, пока не разблокируют                                                                                                                                                                                                                                                                                            |
| `tasks_stage_unblock`                         | человек: ответ (обязательно) → `ready`; ответ попадает в пакет контекста следующей попытки                                                                                                                                                                                                                                                                                                |
| `tasks_comment`                               | комментарий в журнал задачи или этапа                                                                                                                                                                                                                                                                                                                                                     |
| `tasks_cancel`                                | отменить задачу (незавершённые этапы — `cancelled`)                                                                                                                                                                                                                                                                                                                                       |

`tasks_claim_next` — единственная точка выдачи работы; гонка двух исполнителей за один этап
должна быть невозможна (условный `UPDATE … WHERE status IN (ready, rework)` и проверка числа
затронутых строк, либо блокировка строки).

### Права

Скоупы токена (по модели прав WebX; если отдельные скоупы на действия не поддерживаются —
то же через роли администраторов):

| Скоуп          | Даёт                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------- |
| `tasks:read`   | `_list`, `_get`, `_queue`, `_projects_list`                                                           |
| `tasks:write`  | создание и правка задач, проектов, `tasks_ready`, `tasks_cancel`, `tasks_comment`                     |
| `tasks:work`   | `tasks_claim_next`, `tasks_stage_report`, `tasks_stage_release`, `tasks_stage_block`, `tasks_comment` |
| `tasks:review` | `tasks_stage_accept`, `tasks_stage_rework`                                                            |

`tasks_stage_unblock` — только администратор (человек): ответ на вопрос исполнителя не даёт
другой агент.

Исполнителю — `read + work`: принять собственную работу он не может. Диспетчеру — ещё
`review`, но **этапы `review_mode=human` принимает только человек**: `accept` на таком этапе от
агентского токена отклоняется с понятной ошибкой.

### Ресурсы MCP

- `tasks://rules` — правила процесса для агентов: как брать этап, что делать до отчёта (гейт
  проекта), формат отчёта (ниже), что запрещено (принимать свою работу, править чужие этапы,
  менять спецификацию задачи), что делать при блокере (`tasks_stage_block` с конкретным
  вопросом, а не тихий выход и не ожидание ответа в сессии).
- `tasks://projects/{slug}` — проект с его `rules`.

Формат отчёта (рекомендуемый, рендерится в панели как markdown):

```
## Сделано
## Как проверить
## Результат        ветка / коммит / PR
## Не сделано и почему
## Риски и что задето за пределами этапа
```

## 6. Панель

Без канбана. Три экрана, на компонентах ядра, экраны — описанием (`@webx-ui/schema`):

1. **Задачи** — таблица: проект, #, название, статус, текущий этап (n/m и его статус),
   приоритет, обновлено. Фильтры: проект, статус, «ждёт меня» (этапы `review` с
   `review_mode=human`). Счётчик «ждёт меня» — бейджем в меню.
2. **Задача** — спецификация и критерии (markdown), список этапов: номер, название, статус,
   исполнитель, попытка; у этапа раскрывается задание, критерии и отчёт. Действия по статусу:
   «В работу» (`draft` → `ready`), «Принять», «Вернуть» (с обязательным текстом), «Ответить»
   (на `blocked`, с обязательным текстом), «Освободить», «Отменить задачу». Журнал — лентой
   внизу. Фильтр «ждёт меня» в списке включает и `blocked`.
3. **Форма задачи** — поля задачи и повторитель этапов (название, задание, критерии,
   проверка auto/human) с перетаскиванием порядка; правка ограничена правилами §3.
   Плюс справочник **Проекты**: простой список с формой.

Даты — `WxDate`, слова — в словаре модуля (минимум `en`, `ru`, `uk`).

## 6a. Уведомления (Telegram)

Человек не сидит в панели — о том, что от него что-то нужно, он узнаёт из мессенджера. Модуль
шлёт уведомления сам, по событиям задач; каналы — за контрактом (`Notifier`), из коробки —
Telegram-бот, другие каналы сайт подключает своей привязкой в контейнере.

**События** (каждое включается в настройках отдельно):

| Событие              | Когда                                                                   | По умолчанию |
| -------------------- | ----------------------------------------------------------------------- | ------------ |
| `stage.review_human` | этап с `review_mode=human` перешёл в `review`                           | вкл          |
| `task.done`          | принят последний этап                                                   | вкл          |
| `stage.blocked`      | исполнитель задал вопрос (`tasks_stage_block`) — в сообщении сам вопрос | вкл          |
| `stage.rework`       | этап вернули на доработку                                               | выкл         |
| `stage.review_auto`  | этап `auto` ждёт проверяющего агента                                    | выкл         |
| `stage.stale`        | этап в `in_progress` дольше N часов (планировщик)                       | вкл, N = 6   |

**Сообщение** — коротко и со ссылкой, без простыней:

```
⏳ #12 · <проект> — <название задачи>
Этап 2/4 «<этап>» ждёт вашей проверки (попытка 1)
<первые ~300 символов раздела «Сделано» отчёта>
Результат: <result_ref>
<ссылка на задачу в панели>
```

**Настройки** — экран модуля в разделе настроек: токен бота, один или несколько `chat_id`
(личка или группа), переключатели событий, `N` для `stage.stale`, кнопка «Отправить тестовое».
Токен хранится зашифрованным, в ответах MCP и API не возвращается никогда (только «задан / не
задан»). Подсказка в форме: как получить токен у `@BotFather` и узнать `chat_id`.

**Доставка** — заданием в очереди после коммита перехода: переход статуса не ждёт Telegram и
не откатывается из-за него. Ошибка доставки — в лог и в журнал задачи (`kind=comment`,
`actor_type=system`), с повтором (3 попытки с паузой).

**Позже (не в первой версии):** кнопки в сообщении «Принять» / «Вернуть» — через вебхук бота на
сайт; ответ на сообщение с кнопки «Вернуть» становится замечанием `rework`. Для этого бот должен
знать, какой пользователь Telegram — какой администратор (привязка в профиле администратора).

## 7. Минимальный сайт под задачи

Сайту нужна только панель: публичной части нет.

**Модули:** `admins` (вход, администраторы, OAuth для MCP), `settings`, `tasks`. Больше ничего:
**без** `pages`, `blocks`, `media`, `seo`, `menu`, `inbox`, `audit`, `blog` и прочих разделов.
Если что-то из этого обязательно для каркаса — отметить в реализации, какое и почему.

**Установка из скелета:**

```bash
composer create-project webx-ui/site tasks --no-scripts
cd tasks && cp .env.example .env && php artisan key:generate
WEBX_ADMIN_PASSWORD=… php artisan webx:setup --no-interaction \
  --name="Tasks" --domain=… --modules=admins,settings,tasks --locales=ru \
  --db-connection=mariadb … --admin=… --no-demo
php artisan webx:doctor --strict
```

**Сайт без публичной части:** `/` — редирект на панель; `robots.txt` — `Disallow: /`;
`X-Robots-Tag: noindex` на всём. Это должно получаться штатно: `webx:setup` без модуля `pages`
не должен оставлять сломанную главную (сейчас «главная свежего сайта без `--demo` — 404»; здесь
ожидается редирект в панель). Если для этого нужна правка скелета или `module-admin` — она часть
этой работы, общая для всех сайтов без страниц.

**Подключение агентов:**

- ассистент в чате — коннектор на `https://<сайт>/api/cms/mcp`, вход админом, согласие OAuth;
- агент в терминале — машинный токен со скоупами (`tasks:read,work` для исполнителя,
  `+review` для диспетчера), например через `webx:mcp:token --name=… --scopes=…`, и заголовок
  `Authorization: Bearer …` в конфигурации MCP агента.

## 8. Как этим работают агенты (для `tasks://rules` и гайда)

1. Человек с ассистентом пишет задачу: `tasks_create` (draft) → правки → `tasks_ready`.
2. Диспетчер (долгоживущая сессия агента) периодически вызывает `tasks_list`; для каждой задачи
   с этапом `ready`/`rework` открывает **новую** сессию исполнителя в `workdir` проекта.
3. Исполнитель: `tasks_claim_next(agent=<имя сессии>)` → работа в ветке задачи → гейт проекта →
   `tasks_stage_report`. Нужен ответ человека — `tasks_stage_block` с вопросом; человек отвечает
   в панели (`tasks_stage_unblock`), этап снова `ready` и уходит новой сессии вместе с ответом.
4. Диспетчер читает отчёт: этап `auto` — сверяет с критериями и `accept`/`rework`; этап `human`
   — человеку уходит уведомление (§6a), этап ждёт его решения.
5. Последний этап принят — задача `done`.

## 9. Выпуск

Новый пакет — по чек-листам монорепы: composer-половина прописывается в `php/` (require,
autoload-dev, phpunit, phpstan), раздел панели — в `Setup\Catalogue`, `extra.webx.npm` и
`extra.webx.panel`, плейграунд и демо-сайт; changeset; первую версию npm-пакета публикует
человек. Реестр пакетов и оглавление спек — дополнить.

## 10. Тесты, обязательные к выпуску

- переходы статусов этапа и вывод статуса задачи — по таблицам §3, включая запрещённые;
- `tasks_claim_next` под конкуренцией: два параллельных вызова — один этап, один пустой ответ;
- приоритет выдачи: `rework` раньше `ready`, затем приоритет, затем возраст;
- агентский токен не принимает этап `human` и не принимает без скоупа `review`;
- `tasks_create` с этапами одним вызовом, `dry_run` ничего не пишет;
- журнал: каждая смена статуса оставляет запись с автором; правка журнала невозможна;
- уведомления: событие → задание в очереди с нужным текстом; выключенное событие не шлётся;
  ошибка доставки не откатывает переход и пишется в журнал; токен бота не виден через MCP;
- сайт из §7: `webx:doctor --strict` зелёный, `/` ведёт в панель, публичных страниц нет.

## 13. Как легло в код

### T1 (15.10.2026)

- **Пакет** `php/packages/module-tasks`, namespace `WebxUi\Tasks`; прописан в `php/` (require,
  autoload-dev, phpunit, phpstan). Раздел `tasks` в реестре панели без npm-половины: в
  `Setup\Catalogue`, `extra.webx.npm`/`panel` и плейграунд он попадёт с экранами (T3) — до этого
  `webx:setup` его не предлагает. Зеркало `webx-ui/module-tasks` на GitHub уже есть; на Packagist
  пакет отправляет человек (шаг 3 `WEBX_UI_PHP_RELEASE.md`) после первого пуша в `main`.
- **Таблицы §4** — одной миграцией. Сверх §4 у этапа `status_changed_at`: очереди диспетчера
  (`tasks_queue`) и `stage.stale` нужно время последней смены статуса, а `claimed_at` после
  освобождения пуст. Таблицы — `content` для `webx:snapshot`: очередь переезжает вместе с сайтом.
- **Статусы** — enum'ы `StageStatus` (`canBecome()` — таблица §3) и `TaskStatus::of()`. Два
  уточнения §3: `blocked` считается работой (`in_progress`), а не `ready` — работа начата и ждёт
  человека; отменённые этапы в выводе не участвуют, задача из принятых и отменённых — `done`.
  Переход `ready → pending` есть только у перестановки: этап, перед которым поставили другой,
  снова ждёт.
- **Операции** — `Workflow\Tasks`, панель и MCP их только вызывают. Каждая — транзакция с
  блокировкой задачи и этапа, запись в журнал и пересчёт статуса задачи. Открытие следующего
  этапа (`pending → ready`) пишется от имени `system`, всё остальное — от того, кто действовал.
  Ошибки правил — `TaskRefused` с ключом причины (`reason`) и текстом из словаря; плохие значения —
  `ValidationException`.
- **Кто** — `Actor`: `admin` (человек), `agent` (имя сессии), `system`. Правила про людей
  спрашивают только `isPerson()`: этап `human` принимает и возвращает только человек, на вопрос
  отвечает только человек; агент не проверяет этап, который сам делал (`assignee`), и отчитывается
  и спрашивает только по этапу, который держит. Как токен превращается в `Actor`, решает T2.
- **Правка по §3.** В черновике список этапов заменяется целиком. После `ready` у задачи меняется
  только приоритет (это порядок выдачи, а не содержание работы); в списке этапов должны быть все
  этапы, начатые и отменённые стоят на своих местах и не меняются, неначатые переставляются и
  правятся, новые — только в конец; удаления нет — ненужный этап отменяют
  (`cancelStage`, последний оставшийся — нельзя: это отмена задачи). Правка пишется в журнал
  видом `edit` с перечнем полей и этапов.
- **Журнал** — сверх четырёх видов §4 ещё `question`, `answer` (половины блокировки: их отдают
  следующей попытке, искать среди комментариев нельзя) и `edit`. Строка журнала не меняется и не
  удаляется — модель бросает исключение.
- **Выдача** — `Dispatcher`: кандидаты читаются без блокировки в порядке «`rework` → приоритет →
  возраст задачи», каждый берётся условным `UPDATE … WHERE status = <прочитанный>`, победителя
  определяет число изменённых строк; проигравший идёт к следующему кандидату. Черновики,
  отменённые и удалённые задачи и архивные проекты не выдаются. Гонка в тестах — два чтения
  кандидата до записи, как у двух параллельных вызовов.
- **Освобождение** возвращает этап туда, откуда его взяли: `rework`, если попытка не первая, —
  чтобы не потерять место в очереди. Ответ на вопрос — в `ready`, как в §3.
- **Пакет контекста** — `ContextPackage`: проект с `rules`, задача (ветка — своя или ветка по
  умолчанию проекта), этап с номером «n из m», попыткой, замечаниями последнего `rework` и парами
  «вопрос — ответ», отчёты принятых этапов.

### T2 (15.10.2026)

- **Инструменты §5** — `Mcp\TasksTools`, все 18, тонкие: найти задачу, проект или этап, решить,
  кто действует, и перевести отказ `TaskRefused` в `ToolFailure`. Задача называется id или ссылкой
  `<проект>#<номер>` (`shop#12`), этап — id из `tasks_get`, `tasks_queue`, `tasks_claim_next`.
  Неизвестный аргумент и неизвестное поле этапа отклоняются (`Arguments::strict`). `dry_run` —
  настоящая запись в откатываемой транзакции (`Rehearsal`), включая `tasks_claim_next`.
- **Кто действует.** Аргумент `agent` — значит агент с этим именем сессии. Без него — человек, и
  только если соединение человеческое: сессия панели или токен с `mcp:use` (OAuth). Машинный
  ключ с названными скоупами без `agent` отклоняется и человеком не считается никогда — поэтому
  этап `human` и ответ на вопрос агенту недоступны, каким бы ключом он ни пришёл. **Дыра,
  закрытая 15.10.2026:** ключ, выпущенный `webx:mcp:token` без `--scopes`, несёт `mcp:use`, как
  OAuth, и проходил за человека. Теперь человек — это `mcp:use` **и** не ключ (`Keys::isKey()`,
  `WEBX_UI_MCP_ACCESS.md` §12). stdio-сервер
  (`mcp:start`) без `agent` тоже отклоняется: за ним нет человека.
- **Скоупы и права.** `read` — `tasks.view|manage|work|review`; `write` — `tasks.manage`; `work` —
  `tasks.work`; `review` — `tasks.review`. `tasks_stage_unblock` — `tasks:write` и
  `tasks.manage`, плюс проверка на человека. `tasks_comment` достаётся и `write`, и `work` — для
  этого в `webx-ui/mcp` скоуп инструмента стал списком «любой из» (`scope: [...]` у
  `Tool::mutating`, `BoundTool::scopes()`); у существующих модулей ничего не поменялось.
- **Ресурсы.** `tasks://rules` — markdown из `resources/mcp/rules.md`, общий для всех сайтов.
  `tasks://projects/{slug}` — шаблон адреса: в `webx-ui/mcp` появился `RegistryResourceTemplate`
  (адрес с `{переменной}` уходит в `resources/templates/list`, переменная — в аргументы
  обработчика).
- **`tasks_queue`** показывает и `blocked`, которого нет в §5: без него диспетчер не отличит пустую
  очередь от очереди, где всё ждёт человека. Сортировка — по времени последней смены статуса,
  сверху самые давние. **`tasks_list`** — сначала приоритет, потом свежие; `waiting_for_person`
  — этапы на проверке человеком и с вопросом (фильтр «ждёт меня» панели).
- **Отдельной отмены этапа в MCP нет** — её нет в §5; операция `cancelStage` есть, кнопка придёт
  с панелью.

### T3 (15.10.2026)

- **API панели** — `routes/api.php` под `webx.panel`, те же операции T1. Смотреть может любой из
  четырёх прав; планировать, отвечать на вопрос и отменять — `tasks.manage`; принять и вернуть —
  `tasks.review`; освободить — `tasks.manage` или `tasks.work`; комментарий — любой, кто
  работает. Из панели действует всегда человек (`Actor::admin`). Отказ правил — 422 с
  `message` и `reason` (не 409: его панель читает как конфликт правок и подменяет текст), плохие
  значения — 422 с `errors`. Список — пагинатор Laravel как есть плюс `counts`
  по видам; ответ любой операции — задача целиком, потому что один ход меняет и соседний этап, и
  статус задачи.
- **Виды списка** вместо фильтра статуса: все, «ждёт меня» (`Task::waitingForPerson()` — этап
  на проверке человеком или с вопросом), в работе, черновики, закрытые; фильтр проекта и поиск по
  названию. «Ждёт меня» и `tasks_list(waiting_for_person)` в MCP — один и тот же скоуп запроса.
- **Бейдж в меню** — `TasksModule::manifest()` отдаёт `meta.badge` только тому, кто может
  действовать (`tasks.review` или `tasks.manage`). В `module-admin` это общее: `NavEntry.badge`
  из `meta.badge` любого модуля (положительное целое, иначе ничего), `AdminNav` рисует его в
  слоте `trailing` пункта; экран задачи после хода зовёт `refreshManifest()`, и число меняется
  без перезагрузки. На свёрнутом меню бейджа нет — там нет и подписи.
- **Форма — описание `tasks.form`**, правила §3 — патчем страницы: после `ready` поля задачи,
  кроме приоритета, заблокированы; начатые и отменённые этапы — списком над редактором, в
  повторителе только неначатые; при сохранении список собирается заново — начатые на своих
  местах, остальные в порядке редактора, новые в конце. Поле, добавленное патчем проекта,
  нарисуется, но не сохранится: у задачи нет `extra`.
- **Экран задачи** — спецификация и критерии (markdown через `renderMarkdown` и `WxProse`),
  этапы аккордеоном (открыт тот, что ждёт кого-то), кнопки по статусу и правам, вопрос
  заблокированного этапа — плашкой над заданием, журнал лентой. Тело отчёта в журнале не
  повторяется — его читают на этапе.
- **Проекты** — `/tasks/projects`, список с диалогом формы; архив — переключателем.
- **npm-половина** `@webx-ui/module-tasks` (`tasks()`), `extra.webx.npm`/`panel`, раздел в
  `Setup\Catalogue` (`default: false`, требует `admins`), плейграунд с фикстурами
  `apps/playground/server/panel/tasks.ts`. В `scripts/packages.mjs` сайта `webx-cms.local` — после
  первой публикации npm-пакета: в режиме `registry` неопубликованный пакет ломает установку.
- **Словари** — `screen` (подписи формы, переводит сервер) и `panel` (слова экранов, английский
  по умолчанию в `messages.ts`), десять языков.

### T4 (15.10.2026)

- **Контракт и канал.** `Notifications\Notifier` (`configured()`, `send(Notice)`), из коробки
  `TelegramNotifier` через `bindIf` — привязка сайта побеждает в любом порядке провайдеров. Bot API
  `sendMessage`, простой текст без разметки: отчёт агента полон символов, на которых Markdown
  Telegram отказывает. Ошибка называет чат и слова Telegram, но не токен.
- **События.** Операции T1 и выдача этапа бросают `Events\StageMoved` и `Events\TaskStatusChanged`
  внутри транзакции хода; слушатель `NotifyPeople` решает, о чём сказать, и ставит `SendNotice` с
  `afterCommit` — откатанный ход (отказ, `dry_run`) ничего не отправляет. Текст собирается в
  момент события (`Notices`) на языке сайта (`app.locale`), ссылка — от `app.url`, а не от
  запроса: одинаковая из панели, очереди и планировщика.
- **Доставка.** `SendNotice` сам считает попытки: три, паузы 30 и 120 секунд, ошибка не
  выбрасывается — на `sync`-очереди выброшенная ошибка стала бы ошибкой запроса, который сделал
  ход. На `sync` попытка одна: пауза держала бы запрос. Последняя неудача — в лог и в журнал
  (`comment` от `system`, `meta.notice`). Если из двух чатов один принял, а другой нет, повтор
  уйдёт в оба.
- **`stage.stale`** — команда `webx:tasks:stale` в планировщике каждые 15 минут; один раз на
  «заход»: колонка `stale_notified_at` (в той же миграции — пакет ещё не выпущен) очищается при
  новой выдаче этапа.
- **Настройки** — экран `tasks.settings` (свой, как у аудита), ключи `tasks.notify.*` и
  `tasks.telegram.chats` в `module-settings`; по умолчанию — `config/webx-tasks.php`. Токен —
  под `tasks.telegram-token` зашифрованным (`Crypt`), ни одним экраном не описан, поэтому
  `settings_get` и `settings_list` его не видят; API отдаёт только `token_set`. Пустое поле
  токена его сохраняет, «Забыть токен» — удаляет. Кнопка «Отправить тестовое» шлёт сразу и
  отвечает 422 со словами Telegram (не 409: его панель читает как конфликт правок и подменяет текст). `module-tasks` теперь требует `module-settings`.

### T5 (15.10.2026)

- **Сайт без публичной части** — общее для любого сайта, не только задач. У модулей в
  `Setup\Catalogue` появился признак `public: false` (`admins`, `settings`, `tasks`);
  `Catalogue::hasPublicPart()` — есть ли среди выбранных хоть один модуль, который что-то
  показывает посетителю (чужой модуль — показывает). Нет — `webx:setup` пишет `WEBX_PUBLIC=false`,
  не ставит тему (одевать нечего; `--theme` ставит) и вместо заглушки `demo` вписывает в
  `routes/web.php` редирект `/` → панель (`// webx:panel-home`, не замыкание — `route:cache` его
  берёт). Догадка спеки «главная свежего сайта без `pages` — 404» не подтвердилась: её отвечала
  заглушка, которую `webx:setup` вписывает сам.
- **`webx-admin.public`** (`WEBX_PUBLIC`, по умолчанию `true`). Выключенный — глобальный
  middleware `Gate\KeepOutOfSearch`: `/robots.txt` отвечает `Disallow: /` раньше любого маршрута
  (иначе его отдал бы `module-seo` по своей настройке), каждый ответ — `X-Robots-Tag: noindex,
nofollow`, 404 включительно. Флаг, а не вывод из отсутствия `pages`: сайт без страниц, но с
  блогом или каталогом публичный, и закрывать его от поисковиков молча нельзя.
- **Smoke** — `scripts/php-smoke.sh`, сайт из скелета с `--modules=admins,settings,tasks`:
  `WEBX_PUBLIC=false`, нет `theme/`, `/` → `/cms`, `robots.txt` закрыт, у панели `noindex`.
  `webx:doctor --strict` на таком сайте — на развёртывании (с собранной панелью), в smoke его
  держит отказ «нет сборки» из-за `--no-build`.
