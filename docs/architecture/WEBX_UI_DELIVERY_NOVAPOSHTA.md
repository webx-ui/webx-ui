# `webx-ui/delivery-novaposhta` — спутник службы доставки «Нова пошта» — спецификация

Статус: принята (webx-ui#102), реализуется задачей webx-ui#103 по плану §17; этап 1 — правка базы
(§5, §6.4, §10.4) — сделан. Решения человека 02.11.2026 (1–9), ответы на открытые вопросы первой
редакции (10–18) и решение 19 — §2, не пересматриваются.

> **Решение 19 — ключ клиента, только чтение** (02.11.2026, важнее любой формулировки ниже).
> Ключ `NOVAPOSHTA_KEY` в env lab-сайта — ключ реального клиента. С ним:
>
> - **только методы чтения**: справочники (`getCities`, `getWarehouses`, `getStreet`, типы
>   точек), чтение кабинета для выпадашек отправителя (контрагенты, контактные лица); трекинг —
>   только по номерам, которые прямо даст человек;
> - **никогда, ни на каком этапе, ни скриптом, ни через панель или MCP на lab** — методы записи:
>   `Counterparty.save`, `ContactPerson.save`, `Address.save`, `InternetDocument.save` /
>   `update` / `delete` и любые другие, меняющие что-то в кабинете клиента. Накладная, получатель
>   и отмена проверяются только на записанных обезличенных и фейковых ответах (`Http::fake()`);
> - на lab способы службы с этим ключом для оформления не включаются, заказы, ведущие к накладной
>   на этом ключе, не создаются, кнопка «Создать накладную» с этим ключом не нажимается — ни руками,
>   ни скриптом;
> - **бережно к лимитам клиента**: полный проход улиц (~12 тыс. запросов, §6.4) на этом ключе не
>   запускается — улицы проверяются на выборке ≤ 20 пунктов; полные справочники пунктов и точек —
>   не чаще одного раза за задачу;
> - ключ — только из env: никогда в репозиторий, фикстуры, лог, отчёт, MCP, скриншот;
> - данные кабинета (имена, телефоны, адреса отправителей и получателей, номера накладных) — данные
>   клиента: в фикстуры только обезличенными (`FixturesAreScrubbedTest`), в отчёты и логи —
>   никогда.
>
> Сомнение, не нарушит ли действие это правило, — вопрос человеку, действие не выполняется.

Первый настоящий спутник службы доставки по шаблону §13 спеки
[`WEBX_UI_MODULE_DELIVERY.md`](WEBX_UI_MODULE_DELIVERY.md) (дальше — «спека доставки»). Служба —
крупнейшая национальная служба доставки Украины: сеть отделений, почтоматов и курьерской доставки,
публичный JSON API справочников, накладных и трекинга. Пакет — `webx-ui/delivery-novaposhta`
(composer, namespace `WebxUi\Delivery\NovaPoshta`, словарь `webx-delivery-novaposhta`), ключ
службы — `novaposhta`, страна — `UA`. npm-пары нет (§14).

Всё, что база уже умеет (реестры, таблицы, запись справочников страницами, снятие с порогом,
журнал, расписание, цена в цепочке, снимок, отправления, опрос трекинга, вкладка заказа, MCP), —
в спеке доставки и в коде `php/packages/module-delivery`. Здесь — только то, что делает спутник,
и две правки базы, без которых его не собрать (§5, §10.4).

## 1. Чем владеет спутник

**Внутри:**

- служба `novaposhta` (`Carrier`): ключ API, настройки отправителя и накладной, проверка
  подключения, подписи (§4);
- тонкий клиент API службы (§3): один адрес, разбор ответа, ошибки словами, паузы и бюджет
  запросов, ключ не попадает в логи;
- справочники (`SyncsDirectories`, §6): населённые пункты, точки (отделения и почтоматы), улицы —
  записи в форме базы, курсоры, расписание;
- три типа способов (§7): `novaposhta.branch`, `novaposhta.locker`, `novaposhta.courier` —
  `LabelledMethodType`, цена всегда «по тарифам перевозчика», накладная (`CreatesWaybills`, §8),
  трекинг (`TracksShipments`, §9);
- варианты полей настроек из кабинета службы (§5) — реализация нового необязательного контракта
  базы;
- словарь `webx-delivery-novaposhta` на 10 языках (§11), `AGENTS.md`, тесты на записанных
  обезличенных ответах (§13).

**Не внутри (база, спека доставки):** таблицы и запись страниц, сопоставление пунктов
(`Matcher`), снятие исчезнувших и порог, журнал запусков, очередь задач, экраны панели, MCP,
вкладка «Доставка» заказа, веха «получен». Спутник не пишет в базу и своих таблиц не заводит.

**Не в v1** (решения 3–5, 12, 14, 16, §15): расчёт цены через API, наложенный платёж и контроль
оплаты, автоматическая накладная, вебхуки трекинга, печатная форма накладной, отправка с адреса,
распознавание возврата.

## 3. API службы и свой клиент

### 3.1. Как сверялось

Официальная документация — портал разработчиков службы `developers.novaposhta.ua` (раньше —
`devcenter.novaposhta.ua`). Портал закрыт от автоматического чтения проверкой браузера, обходить
её мы не стали: методы сверены по выдержкам **официальных страниц** портала через поиск; адреса
страниц — в таблице §3.3. Всё, чего в выдержках нет, помечено **«не подтверждено — проверить на
ключе»**. Это снимает **этап 3** (§17, решение 10) сразу после клиента: клиент этапа 2 вызывает
методы чтения §3.3 на lab-сайте с ключом клиента (только чтение, решение 19), ответы записываются в обезличенные фикстуры (§13.1),
пометки в §3.3 снимаются или правятся по фактам. Факт, противоречащий решению человека, — вопрос
человеку, а не тихая правка. Сторонние обёртки и память как источник не использованы.

**Этап 3 (02.11.2026) сверил на ключе** все методы чтения, кроме трекинга (номеров накладных
человек не давал): 35 вызовов на ключе клиента и один с ключом из нулей, только `Methods::READ`,
по журналу клиента. Пометки методов чтения сняты или заменены фактами; методы записи помечены «по
документации, на ключе не проверяется» (решение 19). Решениям человека факты не противоречат:
пустой `FindByString` отдаёт все улицы (решение 7); одноимённых пунктов много — координаты из
точек нужны (решение 11, этап 5); обязательность габаритов почтомата без накладной на ключе не
выяснить (решение 17, этап 7 — по документации).

### 3.2. Транспорт

- **Один адрес**: `POST https://api.novaposhta.ua/v2.0/json/`, тело —
  `{"apiKey", "modelName", "calledMethod", "methodProperties"}`. Портал рекомендует `POST`
  (подтверждено, страница `getWarehouses`).
- **HTTP 200 даже на логическую ошибку** (подтверждено: `getStatusDocuments`, `getCounterparties`,
  `InternetDocument.delete`): успех — по полю `success` и пустому `errors` тела, не по коду.
  Тело ответа — на ключе (этап 3): всегда `success`, `data`, `errors`, `warnings`, `info`,
  `messageCodes`, `errorCodes`, `warningCodes`, `infoCodes`. `info` — объект `{totalCount}` у
  списков, пустой список `[]` у ошибки и у `getWarehouseTypes`, список строк у отказа по лимиту.
  `errorCodes` — строки цифр (`20000201204`, `20000401501`).
- **Числа — строками** (на ключе, этап 3): `"Page": 1` служба отвергает — `success: false`,
  «Page is invalid format»; `"Page": "1"` принимает. Клиент сам отправляет числа
  `methodProperties` строками.
- **Редирект 303 на готовый файл** — `getWarehouses` для некоторых городов отвечает 303 на
  закешированный файл, и список таких городов меняется (подтверждено): клиент идёт по редиректу
  и разбирает тот же формат. На шести запросах `getWarehouses` этапа 3 (вся сеть и два пункта)
  303 не встретился — разбор 303 держится на документации и тесте на `Http::fake()`.
- **Язык**: справочники по умолчанию — на украинском, `DescriptionRu` — русский (подтверждено для
  точек; для пунктов на ключе — `DescriptionRu`, `AreaDescriptionRu`, `SettlementTypeDescriptionRu`
  есть). Других языков служба не отдаёт.
- **Ключ API**: генерируется в бизнес-кабинете службы («Налаштування» → «Безпека») —
  подтверждено. Методы кабинета (контрагенты, накладные, трекинг с полными данными с 24.05.2024)
  требуют ключ; справочники `Address` — ключ передаём всегда; нужен ли он им, этап 3 не проверял
  (ключ из нулей проверен только на `getCounterparties`) — не важно, ключ у спутника есть всегда.
  Неизвестный ключ (на ключе, этап 3): `success: false`, «API key expired», код `20000201204`.
- **Лимиты частоты** в документации не опубликованы; лицензионное соглашение API оставляет службе
  право ограничивать число и частоту запросов по своему усмотрению (подтверждено). Поэтому
  спутник сам держит бюджет (§6.6): пауза между запросами синхронизации, потолок запросов в
  минуту, один поток. Ответ на превышение лимита — на ключе (этап 3): HTTP 200, `success: false`,
  `errors` «To many requests» (так у службы), `errorCodes` `20000401501`, `info` «Try again after
  0.5 seconds». Получен на втором `getWarehouses` в ту же секунду; 13 запросов `getStreet` по
  ~2 в секунду прошли. Пауза ~1 с бюджета §6.6 его не задевает; клиент отдаёт его как
  `NoAnswer`, база повторяет страницу.

черновые файлы по документации и фейковые ответы `Http::fake()` с пометкой в тесте; поля, которые
по ним «не подтверждено», остаются помеченными.

### 3.4. Свой клиент, а не сторонняя библиотека

`WebxUi\Delivery\NovaPoshta\Api\Client` поверх `Illuminate\Http\Client` (`Http::`):

- **методов — десяток, адрес один**: обёртка над всем API службы тянет сотни ненужных методов,
  свои DTO и свой HTTP-клиент; нашему коду нужен один `call(model, method, properties)`;
- **поведение, которого обёртки не дают**: редирект 303 на файл, «листать до пустого `data`»,
  пауза и бюджет запросов синхронизации (§6.6), таймаут базы для накладной, ошибки в
  `CarrierUnavailable` / `WaybillRefused` с `SyncFailure` базы;
- **тесты на `Http::fake()`** с записанными ответами (§13) — без моков чужих классов;
- **ключ под контролем**: тело запроса с `apiKey` не попадает ни в лог, ни в исключение — клиент
  пишет в лог модель, метод и номер страницы, а не тело;
- **зависимости**: публичный пакет монорепы не тянет чужой код с неизвестным темпом поддержки и
  лицензией.

Ответ клиента — `ApiResponse` (`data`, `warnings`, `errors`, `errorCodes`, `totalCount`).
Сопоставление ошибок: нет ответа, таймаут, 5xx, отказ по лимиту — `SyncFailure::NoAnswer`;
ошибка ключа (на ключе: «API key expired», код `20000201204`) — `KeyRejected`; ответ не того формата —
`BadResponse`. Логическая ошибка накладной — `WaybillRefused` с текстом службы (§8.7).

## 5. Решение 6 — варианты полей настроек из API службы (правка `module-delivery`)

Новый **необязательный** контракт базы: служба отдаёт варианты для полей своих настроек по своему
API. Любая следующая служба получает те же зависимые выпадашки; служба без контракта — обычные
поля ручного ввода, как сейчас.

### 5.1. Контракт

```php
namespace WebxUi\Delivery\Contracts;

use WebxUi\Delivery\Settings\SettingOption;
use WebxUi\Delivery\Sync\CarrierUnavailable;

/**
 * Optional on top of Carrier: the options of some settings fields come from the carrier's own
 * account — senders, their contact persons, their addresses — so the panel draws a select instead
 * of a text field. A carrier without it keeps plain fields typed by hand.
 */
interface ProvidesSettingOptions
{
    /**
     * The options of one field for the values chosen so far.
     *
     * @param  string  $field  a name from settings() whose 'options' is 'carrier'
     * @param  array<string, mixed>  $values  the form's current values: what this field depends on
     * @param  array<string, mixed>  $credentials  the stored keys; never shown, never logged
     * @param  string|null  $query  what the admin typed, for a field with 'search' => true
     * @return list<SettingOption>  at most 50; for a search field — the best matches
     *
     * @throws CarrierUnavailable the carrier did not answer or refused the key
     */
    public function settingOptions(string $field, array $values, array $credentials, ?string $query = null): array;
}
```

```php
namespace WebxUi\Delivery\Settings;

final readonly class SettingOption
{
    public function __construct(
        public string $value,          // the carrier's id: a Ref
        public string $label,          // as the admin sees it: "Sender A, Town A"
        public ?string $hint = null,   // a second line: a phone, a tax id
    ) {}
}
```

Форма поля в `Carrier::settings()` получает три необязательных ключа (`Field` не меняется для
остальных служб):

```php
['name' => 'contact', 'type' => 'select', 'options' => 'carrier', 'depends' => ['sender'], 'search' => false],
['name' => 'sender_point', 'type' => 'select', 'options' => 'carrier', 'depends' => ['sender_city'], 'search' => true],
```

- `options: 'carrier'` — варианты спрашиваются у службы; без него `select` берёт свои `options`, как
  сейчас;
- `depends` — поля, от которых зависят варианты: пока они пусты, поле выключено с подсказкой
  «Сначала выберите: Отправитель»; смена родителя очищает детей по цепочке;
- `search` — варианты не грузятся списком, а ищутся по введённому (сотни городов и точек).

Ключ «поле видно только при значении другого» (`when`) первой редакции не нужен: он служил виду
отправки, а отправка в v1 только из отделения (решение 14). Понадобится отправке с адреса — тогда
и в базу.

### 5.2. Как рисует панель

Экран службы (`CarrierDialog.vue` npm-пакета `@webx-ui/module-delivery`, §14.2 спеки доставки):

1. поле с `options: 'carrier'` рисуется `wx-select` (с `filterable`/серверным поиском при
   `search`); варианты — `GET api/cms/delivery/carriers/{key}/options/{field}?values[…]&q=`
   (`delivery.manage`), без ключа в запросе — база берёт сохранённые `credentials`;
2. **ключ не задан** — поля с вариантами выключены с подсказкой «Сначала задайте ключ API и
   проверьте подключение»;
3. порядок — сверху вниз по `depends`: отправитель → контакт; город → точка отправки;
4. подпись выбранного значения хранится рядом со значением: `settings._labels.<поле>` — экран и
   журнал показывают «Sender A» без запроса к API, а при недоступной службе есть что показать;
5. кнопка «Обновить списки» — повторный запрос мимо кеша.

### 5.3. Кеш

`Cache` (не `CacheGroups`: варианты не зависят от правок сайта) на 10 минут ключом
`delivery.options:<служба>:<поле>:<хеш значений depends и q>:<отпечаток ключа>`, где отпечаток —
`hash('xxh128', ключ)`: смена ключа — другие варианты. «Обновить списки» и сохранение настроек —
мимо кеша. Таймаут запроса — 5 с (панель, не оформление).

### 5.4. Ошибки и исчезнувшее значение

- **API не ответил** (`CarrierUnavailable`) — поле показывает сохранённую подпись из `_labels`,
  выключено, под ним «Не удалось получить список из кабинета службы: <слова SyncFailure>» и
  «Повторить». Сохранение других полей работает; сменить поле с вариантами без ответа службы
  нельзя — проверить нечем.
- **Сохранённое значение исчезло** из вариантов (контакт удалили в кабинете) — поле показывает
  «<подпись> — нет в кабинете службы», предупреждение на экране служб (как замечания
  синхронизации) и в `delivery_carriers_list`; значение не стирается само.
- **Сохранение** — база заново спрашивает варианты каждого изменённого поля с вариантами (мимо
  кеша) и принимает только значение из списка: 422 «Выберите из списка». Для поля с `search` —
  `settingOptions(…, query: null)` с `values` и проверкой, что значение среди точных совпадений
  по `value` (спутник отвечает на `query` = значение — §5.5).
- **Накладная** с исчезнувшим отправителем — отказ службы приходит словами службы (§8.7); заранее
  база не проверяет — лишний запрос на каждую накладную.

### 5.5. MCP и защита

- `delivery_carriers_options` (`delivery:read`, право `delivery.manage`): служба, поле, значения
  родителей, `q` → варианты (`value`, `label`, `hint`); ключи не показываются.
- `delivery_carriers_update` принимает значения таких полей, проверяет их по вариантам, как
  панель (§5.4); `dry_run` — проверка без записи; ответ при недоступной службе — `ToolFailure`
  словами.
- Служба без `ProvidesSettingOptions` — ни эндпоинта, ни инструмента для её полей: ответ «Carrier X
  has no options from its account».
- Варианты содержат данные кабинета (имена контактов, телефоны) — только `delivery.manage`, не
  `delivery.view`.

На ключе (этап 3): у пунктов, где все `Delivery1…7` = `"0"`, улиц нет (3 из 3 в выборке); хотя бы один `"1"` — у ~91 % пунктов (456 из 500, 210 из 232). начинающиеся с префикса из словаря спутника. Объём — на ключе (этап 3) `totalCount` 11 232 пункта:
23 запроса на проход (22 полных страницы и последняя на 232 записи). Порядок — по алфавиту.

**Одноимённые одной области — два пункта, не один** (решение человека 02.11.2026, этап 4). На ключе
есть пары одного типа в одной области, которые служба различает только уточнением: «Щасливе
(Бориспільський р-н)» и «Щасливе (Згурівський р-н)»; «Білин (Волинська обл.)» и «Білин
(Володимир-Волинський р-н)». Координат в `getCities` нет, и шаг 3 базы привязал бы вторую запись к
пункту, который ведущая служба только что создала из первой, — два села стали бы одним, и в него
потом легли бы точки обоих. Правка базы (§4.3 спеки доставки): пункт, к которому уже привязана
другая запись этой же службы, — не кандидат для следующей. Нова пошта ведёт UA, поэтому вторая
запись создаёт свой пункт; у ведомой службы она ушла бы в очередь привязок. Полный проход на lab (этап 4, только чтение) был первым и шёл уже по новому правилу: 23 запроса, 11 232 пункта, все созданы, очередь 0, ни один пункт не держит две записи; у 1 395 пунктов есть район. Групп одноимённых одного типа в одной области — около 1 000 (около 2 300 пунктов); по старому правилу около 1 300 из них слились бы. Около 100 групп, где у двух и больше пунктов нет района, в подсказках выглядят одинаково — их различат координаты из точек (этап 5).

### 6.4. Улицы — `getStreet` по всем пунктам (решение 7)

Улицы у службы — по пункту (`CityRef`); общего списка нет. Значит, проход улиц — обход всех
пунктов службы.

**Список пунктов.** Спутник берёт его у базы, а не у API: id пунктов службы, неснятые, по
возрастанию — `delivery_carrier_localities` (`carrier = novaposhta`, `removed_at IS NULL`,
`features` содержит `courier`) keyset-выборкой `external_id > ? ORDER BY external_id LIMIT 200`.
Это чтение, не запись (спутник по-прежнему не пишет в базу); в базу — маленький публичный метод
`CarrierLocalities::externalIds($carrier, ?$after, $limit, $feature)` в той же правке, что §5
(этап 1 §17), чтобы спутник не читал чужую модель напрямую. Пункты без курьера (`features` без
`courier`) не обходятся — курьеру там улицы не нужны.

**Курсор** — `"<id пункта>:<страниц>"`: последний начатый пункт и сколько его страниц `getStreet`
уже взято; `0` — пункт пройден, следующий `pull()` начинает со следующего по id. `"…:3"` — идти
дальше со страницы 4 того же пункта. Один `pull()` идёт по пунктам и страницам, пока не набрал
`pageSize` (2 000) улиц, не сделал `max_requests_per_pull` запросов (20) или не прошло
`pull_seconds` (20 с; новый запрос после этого не начинается, первый идёт всегда), и возвращает
курсор следующего шага. Так повтор страницы базой (3 попытки, паузы 60/300/900 с) повторяет ≤ 20
запросов, а отрезок `job_seconds` очереди не рвёт `pull()` посередине. Пунктов не осталось —
`next = null`, конец прохода. Курсор другого вида — «Ответ не того формата», запросов нет.

**Выборка** (решение 19). `sync.streets_sample` = N — проход идёт только по первым N пунктам с
курьером (по id) и кончается после них. При `read_only = true` (ключ чужого кабинета) выборка по
умолчанию — 20, а расписание улиц — `manual` (`sync.streets_cron`): на dev-копии с ключом клиента
полный проход сам не запускается и руками не выходит за 20 пунктов. Снять — явным
`NOVAPOSHTA_STREETS_SAMPLE=0` и `NOVAPOSHTA_STREETS_CRON`.

**Запрос:** `getStreet` с `CityRef`, `FindByString = ""`, `Page`, `Limit = 500`; конец пункта —
меньше `Limit` записей. **Пустой `FindByString` отдаёт все улицы пункта — подтверждено на ключе
(этап 3):** село — 11 улиц при `totalCount` 11; большой город — `totalCount` 2 829, страницы 1 и 2
по 500, шестая — 329; у пункта без улиц — `success: true`, пустой `data`, `totalCount` 0. Решение 7
стоит как есть.

**`StreetRecord`:** `externalId` — `Ref`; `localityExternalId` — `CityRef` пункта; `name` —
`Description` (на ключе — уже без типового слова: «Гоголя», «Центральна»); `kind` — по
`StreetsTypeRef`, на ключе это английское слово: `Street` → `street`, `Prospectus` → `avenue`,
`Lane` → `lane`, `Square` → `square` (и `Avenue` → `avenue` на всякий случай), другое (`Line`,
`Boulevard`, `Lifting`, `Highway`, `Passage`, `Village`, `Road`, `Deadlock`, `Microdistrict`, …) →
`other` (`Directories\Streets::KINDS`). `StreetsType` — слово службы (`вул.`, `пров.`, `просп.`,
`площа`, `бульвар`, `узвіз`, …). **Как сделано (этап 6):** у `StreetRecord` и `delivery_streets` нет
`meta`, а показ `other` в базе — голое имя, поэтому у `other` слово службы идёт в имя после него в
скобках: «Шевченка (бульвар)», «1-а (лінія)». После имени — чтобы улицу находил префикс её имени;
без слова бульвар и узвіз одного имени в списке не различить. У видов базы слово не пишется —
его ставит словарь базы (`street_kinds`). `names` не отдаются: русского названия служба не даёт,
имя — основное, база кладёт его в язык сайта по умолчанию. Запись без `Ref` или имени
пропускается (иначе база отвергла бы всю страницу).

**Оценка прохода** (оценка по `totalCount` пунктов; полный проход на ключе клиента **не
запускается** — улицы проверяются на выборке ≤ 20 пунктов, решение 19):

| Величина                      | Оценка                                                                    |
| ----------------------------- | ------------------------------------------------------------------------- |
| пунктов с курьером            | ~10 200 (91 % из 11 232 по записанным страницам)                          |
| запросов `getStreet`          | ≈ пунктов + доп. страницы больших городов: ~10 300–10 500                 |
| бюджет                        | 60 запросов в минуту (пауза ~1 с между запросами, §6.6)                   |
| время полного прохода         | ~3 часа (10 500 / 60 = 175 мин)                                           |
| строк `delivery_streets`      | ~150 000–250 000 (выборка: село 4–11, малый город 45–91, большой — 2 829) |
| страниц базы (по 2 000 строк) | ~75–125, ≤ 4 запроса к базе на страницу (§17 спеки доставки)              |

Проход недельный, ночью: в окно с 00:30 до ~04:00 он укладывается и с бюджетом 60/мин. Упавший
после трёх попыток проход — `failed`; следующий начнётся сначала (база не продолжает курсор
упавшего запуска). Правка базы «продолжить курсор упавшего запуска» — по факту падений на живом
ключе (решение 18, §15). Снятие исчезнувших улиц — после полного прохода с
порогом базы (§7.5 спеки доставки).

### 6.5. Ведущая служба страны (решение 8)

- При установке спутник **предлагает** себя ведущей для `UA`: в панели «География» у страны —
  «Ведущая служба: Нова пошта» (запись `StoredLeadingCarriers::choose('UA', 'novaposhta')` при
  первой синхронизации, если ведущей нет — это и есть правило базы «первая синхронизировавшая
  служба», §4.4 спеки доставки). Конфиг `webx-geography.countries.UA.source` сильнее.
- Ведущая создаёт общие пункты для несопоставленного (`created_by = carrier:novaposhta`) и регионы
  (область) по `AreaDescription`.
- **Совместимость с ручной географией** (решение 42): ручные пункты и регионы — кандидаты
  сопоставления; служба к ним привязывается, не создаёт дублей и не переименовывает; правленные
  руками поля (`manual_fields`) синхронизация не трогает. Всё это делает `Matcher` базы — спутник
  только отдаёт записи.
- Пакет данных географии (webx-ui#100) отложен: когда появится, импорт ляжет поверх, служба
  будет привязываться к импортированным пунктам.

## 7. Типы способов

### 7.1. Три типа

| Тип                  | `asks()`  | `pointKinds()` | Ключ способа после установки | Название (en / uk)                                   |
| -------------------- | --------- | -------------- | ---------------------------- | ---------------------------------------------------- |
| `novaposhta.branch`  | `Point`   | `['branch']`   | `novaposhta-branch`          | «Nova Poshta branch» / «Відділення Нової пошти»      |
| `novaposhta.locker`  | `Point`   | `['locker']`   | `novaposhta-locker`          | «Nova Poshta parcel locker» / «Поштомат Нової пошти» |
| `novaposhta.courier` | `Address` | `[]`           | `novaposhta-courier`         | «Nova Poshta courier» / «Кур'єр Нової пошти»         |

Все три — `LabelledMethodType`: `title($locale)` и `description($locale)` («Pick up at a branch
of the carrier; you pay the carrier on receipt») — словарь, 10 языков (§11). Название службы
в словаре — латиницей «Nova Poshta» на языках с латиницей (решение 13), кириллицей на `uk`, `ru`.

Миграция спутника при установке создаёт три способа (`delivery_methods`) с `enabled = false`
(решение 2), `price = null`, `honours_paid_by_store = true`, `countries = ['UA']`; магазин включает
нужные. Повторный запуск миграции ничего не дублирует (по `key`).

### 7.2. `quote()` — всегда «по тарифам перевозчика» (решение 3)

`quote()` → `Quote::carrierRates(null)`: без `estimate`, без API. Строка цены — «по тарифам
перевозчика», в «к оплате» не входит, плательщик — получатель (§9.3 спеки доставки).

Если сайт задал способу фиксированную `price` — база берёт её (магазин берёт с покупателя сам и
платит службе — плательщик в накладной «отправитель»); спутник этого не меняет.

### 7.3. «Доставку оплачивает магазин»

Привилегию `shipping.paid_by_store` применяет база: `carrierRates()` → `free(was: null)`,
`payer = Store` — покупатель видит «Бесплатно» без зачёркнутой цены (оценки нет). Спутник читает
плательщика из снимка (`payer`): `sender` → `PayerType = Sender` в накладной, `recipient` →
`Recipient` (§8.3).

### 7.4. `available()` и `validate()`

- `available()` — `true`: точки и привязки уже отфильтровала база (§6.3 спеки доставки).
- `validate()` — базовый `AbstractMethodType`: точка активна, своего вида и пункта; у курьера —
  улица из `delivery_streets` этого пункта этой службы обязательна, дом обязателен (решение 31

  доставки), наложенного платежа нет.

### 7.5. Снимок

Снимок пишет база (§11.1 спеки доставки): `point.external_id` — `Ref` отделения или почтомата

## 10. Панель, MCP, ключ

### 10.1. Панель — что своё, что базы

Всё — экраны базы: службы (включить, ключ «задано / заменить», «Проверить подключение», настройки
§4.3 с выпадашками §5, справочники и их журнал), способы, вкладка «Доставка» заказа с диалогом
накладной. Своих экранов, Vue-компонентов и npm-пакета у спутника нет (§14).

### 10.2. MCP

База даёт всё (§15 спеки доставки): `delivery_carriers_list` / `_update` (+ `_options` из §5),
`delivery_sync_*`, `delivery_methods_*`, `delivery_points_search`, `delivery_shipments_*`,
`delivery://catalog` (типы спутника с возможностями: накладная, трекинг, без расчёта). Спутник
своих инструментов не добавляет: всё, что агенту нужно от службы, идёт через контракты.

### 10.3. Ключ API

- хранится только в `delivery_carriers.credentials` (`encrypted:array`, база); ни в настройках, ни
  в конфиге, ни в `.env` спутника;
- в панели — «задано / заменить», в MCP и журнале — никогда (база); в логах спутника — модель,
  метод, страница, без тела запроса (§3.4);
- в репозитории — ни одного настоящего ключа: тесты на `Http::fake()` с ключом `test-key`
  (§13);
- ключ для записи ответов (этап 3) — только переменная `NOVAPOSHTA_KEY` в env lab-сайта
  (решение 10): команда записи читает её сама; в репозиторий, лог, отчёт этапа, MCP и скриншот
  она не попадает, в фикстуры `apiKey` не пишется (`FixturesAreScrubbedTest`);
- это ключ реального клиента — **только чтение** (решение 19): команда записи ответов и всё, что
  работает на lab с этим ключом, не вызывает методов записи; клиент спутника пишет в журнал модель
  и метод каждого вызова — по журналу проверяемо, что записи не было.

### 10.4. Правки базы для накладной

Одним этапом с накладной (этап 7 §17), правка чужого пакета `module-delivery`:

- `WaybillRequest::$carrierLocality` — id пункта у службы (`delivery_carrier_localities.external_id`
  по службе и пункту снимка), его заполняет `Shipments::request()` одним запросом: накладной нужен
  `CityRecipient`, а снимок хранит только общий пункт;
- `WaybillRequest::$extra` и необязательный интерфейс типа
  `DescribesWaybill::waybillFields(): list<Field>` (+ `supportsCod(): bool`) — диалог рисует поля
  службы (§8.1) и прячет наложенный платёж;
- `WaybillRequest` — имя и фамилия получателя раздельно (`recipientFirstName`,
  `recipientLastName`) вместо одной строки `recipientName`: заказ уже хранит их раздельно
  (решение 40 спеки заказов, решение 15); `Shipments::request()` берёт `recipient` заказа или,
  если он `null`, покупателя; склейка для служб без раздельных полей — метод `recipientName()`;
- строки этих правок — в список §5.6 для спеки доставки.

## 12. Производительность

- **Страница справочника** (500 пунктов, 500 точек, 2 000 улиц) — бюджеты базы (§17 спеки
  доставки): ≤ 8, ≤ 8, ≤ 4 запроса к БД — спутник БД не трогает, кроме keyset-выборки пунктов
  улиц (1 запрос на ≤ 200 пунктов внутри `pull()`). Замер этапа 6 (`PerformanceTest`): страница
  2 000 улиц — 6 запросов на каждой странице: 4 базы (пункты страницы, какие улицы есть, `upsert`,
  журнал) + ключ службы + следующие пункты; страница пунктов без улиц — 3; последняя — 11 (снятие,
  счёт улиц пунктов, журнал).
- **HTTP на страницу**: пункты и точки — 1 запрос на `pull()`; улицы — ≤ `max_requests_per_pull`.
- **Оформление** API службы не зовёт никогда: цена — `carrierRates` без API, справочники — база
  (решение 38 спеки доставки).
- **Варианты настроек** — кеш 10 минут (§5.3), только панель.
- Кеша и `CacheGroups` своих нет; `bump()` групп после страниц делает база.

  - справочники урезаются до 20 записей; публичные данные службы (пункты, точки, улицы) остаются
    как есть — на них проверяется разбор; телефоны в них — тоже `+800 1234 5678`;
  - в ответах кабинета заменяется каждая строка `data`, кроме перечислений службы
    (`CounterpartyType`, `OwnershipFormDescription`, …): прочее — «Приклад»;
- `FixturesAreScrubbedTest` — по всем файлам: ни одного телефона не `+800`, ни одного e-mail вне
  `example.com`, ни одного `apiKey` и строки из 32 шестнадцатеричных цифр; в ответах кабинета — UUID
  только из фейкового диапазона, имена только заглушки.
