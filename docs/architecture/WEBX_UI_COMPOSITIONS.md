# Композиции — спецификация

Статус: принята 23.10.2026 со всеми рекомендациями §11; этап 2 (движок, `layout`) сделан, этапы 3–4 —
впереди (webx-ui#49). Пакеты — новая библиотека
`webx-ui/compositions` (§2.1, вопрос 1 в §11), правки в `webx-ui/themes`, `webx-ui/theme-default`,
`module-admin` (шаг `webx:boot`), `module-seo`, `module-snippets`, `webx-ui/widgets`, `module-blog`
(пилот) и в модулях, которые зовут layout (§6.5). Соседние спеки: темы —
[`WEBX_UI_THEMES.md`](WEBX_UI_THEMES.md), зоны — [`WEBX_UI_LAYOUT_REGIONS.md`](WEBX_UI_LAYOUT_REGIONS.md),
экраны панели — [`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md), производительность —
[`WEBX_UI_PERFORMANCE.md`](WEBX_UI_PERFORMANCE.md).

Сейчас составной вид пакета — один Blade-файл. `theme-default/views/components/layout.blade.php`
держит документ, `<head>`, швы `@webxTheme`/`@webxSeo`/`@webxBlocks`, зоны шапки и подвала и куски
четырёх пакетов: три места `module-snippets`, FAQ и перелинковку `module-seo`, полосу объявления и
кнопку связи `widgets`. Чтобы тема сайта поменяла в нём хоть что-то — один атрибут на `<html>`, —
ей приходится скопировать файл целиком (дверь 4 из THEMES §10.5). Копия перестаёт получать правки
релизов: на сайте студии ради `data-webx-smooth-scroll` на `<html>` скопирован весь layout, ради
пары атрибутов формы — вид формы inbox. Флаги «включить/выключить» на каждый кусок и Blade
`@extends` с секциями отвергнуты: флагов становится больше, чем кусков, а `@extends` возвращает ту
же копию, только мельче.

Ответ — **композиция**: составной вид описан деревом узлов с `id` в JSON. Пакет даёт базовое
дерево, модули добавляют свои куски, тема и сайт патчат дерево по `id`. Итог **компилируется** в
обычный Blade-вид — один на пару «композиция × хендл»; Blade остаётся для листьев. HTML на выходе
прежний, на запросе — ни слияния, ни `x-dynamic-component`, ни `view()->exists()`.

## 1. Термины и границы

| Термин         | Что это                                                                                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Композиция** | Именованный составной вид, собранный из дерева: `layout`, `layout.minimal`, `blog.article`. Имя — то, чем вид зовут (`<x-layout>`), или `<модуль>.<вид>` для вида модуля. |
| **Узел**       | Элемент дерева: `{ "id": …, <вид узла>: …, … }` (§2.3). Контейнер, вид, компонент, регион, слот, стек, директива, сырой HTML, группа.                                     |
| **Хендл**      | Тип страницы, для которого собирается вариант композиции: `default` и `<модуль>.<страница>` (`blog.article`, `services.show`). Хендлов под конкретную страницу нет (§4).  |
| **Слой**       | Источник файлов композиций: пакетная тема, модуль, локальная тема `theme/`, конфиг сайта (§5).                                                                            |
| **Патч**       | Файл слоя для пары «композиция × хендл»: операции `add`, `remove`, `move`, `replace`, `attrs`, `props` над деревом по `id` (§3).                                          |
| **База**       | Файл, который задаёт дерево целиком (корневой узел) или объявляет `extends` (§2.2). У композиции ровно одна база.                                                         |
| **Находка**    | Сообщение о патче, который нельзя применить как написан: ссылка на несуществующий `id`, дубль, цикл. Не исключение (§3.6).                                                |

**Чем это не является.**

- **Не регионы и не блоки панели.** Регион (`<x-webx-blocks::region>`, LAYOUT_REGIONS) — место, чьё
  содержимое раскладывает редактор в панели и которое живёт в базе. Композиция — структура, которую
  пишет разработчик или агент темы, и живёт она в git (THEMES §2, решение 12). В дереве регион — обычный
  лист `region` (§2.3): композиция решает, _где_ стоит шапка, редактор — _что_ в ней. Блоки из панели в
  композиции не превращаются, и композицию из панели не правят.
- **Не экраны панели.** Экраны (SCREENS) — дерево узлов для Vue-рендерера, которое собирается на
  каждый запрос экрана и отдаётся JSON-ом; композиция — дерево для Blade, которое собирается один раз
  и отдаётся файлом. Общие идеи взяты оттуда: стабильный `id` как публичный контракт пакета,
  `add`/`remove`/`move`/`replace` в том же смысле, маркер `trans::` для слов, проверка JSON-схемой.
  Разное — обдуманно: патч записан ключами по операциям (формат из постановки задачи), а не списком
  `op`; `set` экрана разделён на `attrs` и `props`; ссылка на несуществующий `id` — находка, а не
  исключение, потому что упавший layout роняет каждую страницу сайта, включая ту, где ошибку чинить
  (LAYOUT_REGIONS, решение 1).
- **Не замена Blade.** Лист — обычный Blade-вид или компонент; условия, циклы, данные модели — в
  листе. В дереве нет `@if` и выражений: узел либо есть в варианте композиции, либо нет.
- **Вне композиций:** письма, PDF, ответы API, страницы ошибок (`views/errors`) — они остаются видами.

**Решения человека, на которых стоит спека (не переоткрывать):** дерево с `id` в JSON; патчи по
`id`; хендлы `default` + тип страницы, без хендлов страницы; слои «пакетная тема → модули → локальная
тема → конфиг сайта»; слияние не в рантайме, а компиляцией в Blade; без `@extends` и без флагов на
каждый кусок; несколько именованных layout, выбор — модулем, роутом или конфигом, **не в панели**;
наследование деревьев (`extends`); файл вида в теме важнее композиции; Vue — лист или отдельный узел.

## 2. Формат

### 2.1 Пакет и файлы

Движок — библиотека **`webx-ui/compositions`** (namespace `WebxUi\Compositions`, без префикса
`module-`: живёт без панели и без темы, как `routing`). Без темы композиции модулей (`blog.article`)
работают так же; layout — композиция темы, и у сайта без темы (`--no-theme`) композиции `layout` нет.

**Пути.** Один каталог на слой, внутри — каталог на композицию, файл на хендл:

```
<слой>/compositions/<композиция>/<хендл>.json
```

| Слой           | Каталог                                        | Пример                                                  |
| -------------- | ---------------------------------------------- | ------------------------------------------------------- |
| пакетная тема  | `<пакет>/compositions/`                        | `theme-default/compositions/layout/default.json`        |
| модуль         | `<пакет>/resources/compositions/`              | `module-seo/resources/compositions/layout/default.json` |
| локальная тема | `theme/compositions/`                          | `theme/compositions/layout/blog.article.json`           |
| конфиг сайта   | `config/webx-compositions.php`, ключ `patches` | `'patches' => ['layout' => ['default' => [...]]]`       |

Почему не `<слой>/layout/<хендл>.json`, как в первом наброске: композиций будет больше одной
(`header`, `footer`, `blog.article`, `catalog.product-card`, `inbox.form`), и каталог на каждую в корне
темы смешал бы их с `views/`, `blocks/`, `regions/`, где у каждого каталога свой смысл (THEMES §4).
Один корень `compositions/` — одно место для проверки, `eject` и `show`; имя каталога — имя
композиции ровно как его пишут (`layout.minimal/`, `blog.article/`), без перевода точек в слэши.
У модуля — под `resources/`, рядом с `resources/theme/` и `resources/blocks/`.

### 2.2 База и патч

Файл — либо **база**, либо **патч**. База — у нижнего слоя, который композицию вводит (у `layout` —
`theme-default`, у `blog.article` — `module-blog`), и только для хендла `default`:

```json
{
  "$schema": "https://webx-ui.github.io/webx-ui/schema/composition.json",
  "root": { "id": "html", "tag": "html", "children": [] }
}
```

или наследование (§3.7):

```json
{ "extends": "layout", "remove": ["footer"] }
```

Патч — объект с ключами операций (§3); в нём нет `root` и `extends`. Ключи вне списка — ошибка схемы.
`"$comment"` разрешён везде: JSON без комментариев, а объяснить «почему» нужно.

### 2.3 Узлы

У узла **ровно один** ключ вида — он и говорит, что это за узел. Общие ключи — `id` (обязателен) и
`attrs` (где разрешён).

| Вид         | Ключи                                        | Во что компилируется                                                                                                                                  |
| ----------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tag`       | `tag`, `attrs?`, `children?`                 | `<tag attrs>…</tag>`; пустые элементы (`meta`, `link`, `hr`…) — без закрывающего и без детей. `tag: "html"` сам ставит `<!doctype html>` перед собой. |
| группа      | `children`                                   | только дети, без своей разметки. Корень вида модуля, логический контейнер без лишнего `<div>`.                                                        |
| `view`      | `view`, `with?`                              | `@include('<view>', <with>)` — вид ищется по цепочке, как любой (THEMES §7.1); переменные места вызова (`$slot`, `$head`) видны.                      |
| `component` | `component`, `props?`, `attrs?`, `children?` | `<x-<component> :prop="…" attrs>children</x-…>`; дети — в слот по умолчанию компонента. Статический тег, не `x-dynamic-component`.                    |
| `region`    | `region`, `fallback?`                        | `<x-webx-blocks::region name="…" fallback="…" />`; без `module-blocks` — `@include('<fallback>')` или ничего (решено при компиляции).                 |
| `slot`      | `slot`, `fallback?`                          | `default` → `{{ $slot }}`; именованный → `{{ $<slot> }}`, а пока он пуст — `fallback` (§2.4).                                                         |
| `stack`     | `stack`                                      | `@stack('<stack>')`.                                                                                                                                  |
| `directive` | `directive`, `args?`                         | `@<directive>` или `@<directive>(<args>)`. Только зарегистрированные директивы (`Blade::getCustomDirectives()`) — иначе находка.                      |
| `html`      | `html`                                       | строка как есть; синтаксис Blade в ней экранируется (`@` → `@@`, `{{` → `@{{`) — сырой HTML не исполняется.                                           |
| `vue`       | `vue`, `props?`, `attrs?`                    | точка монтирования `<div data-webx-vue="<entry>" data-props='…'>` и `@vite('<entry>')` в стек `scripts` (§2.6). Позже этапа 4.                        |

- **Значения `props` и `attrs` — литералы JSON.** Выражений нет: динамика — в листе (`view`,
  `component`). Строка с маркером `trans::<ns>::<ключ>` (как в SCREENS §3) компилируется в
  `{{ __('<ns>::<ключ>') }}` — слово переводится на запросе, в языке страницы.
- `props` компонента компилируются в `:name="<php-литерал>"`, `attrs` — в обычные атрибуты, которые
  компонент получает в `$attributes`.
- `with` у `view` — литералы, которые дописываются к переменным места вызова.
- Виды `view`/`component`/`region`, которых нет при компиляции, — находка; узел пропускается.

### 2.4 Слот и запасной вариант

Именованный слот печатается, если вызывающий его передал и он не пустой, иначе — `fallback`. Это то,
что сейчас делает layout с `head` (модуль уже печатает `@webxSeo`/`@webxBlocks` в слоте, повтор дал
бы второй `<title>`). `fallback` — массив узлов; строка в массиве — краткая запись директивы:
`["webxSeo", "webxBlocks"]` ≡ `[{ "id": "head.slot.seo", "directive": "webxSeo" }, …]`.

```blade
@if (isset($head) && trim((string) $head) !== '')
    {{ $head }}
@else
    @webxSeo
    @webxBlocks
@endif
```

### 2.5 `id`

- `id` уникален в пределах **итогового дерева** композиции (после всех слоёв). Это адрес для патчей
  и публичный контракт пакета: переименование — ломающее изменение, в changeset.
- Символы: `[a-z0-9-]` и точка как разделитель: `meta.viewport`, `seo.faq`, `account.menu`.
- **Пространства имён.** Узлы базы композиции — без префикса (`html`, `main`, `footer` у layout;
  `article`, `article.title` у `blog.article`). Узел, который **модуль** кладёт в чужую композицию, —
  с префиксом идентификатора модуля: `seo.faq`, `snippets.head`, `widgets.contact-button`. Тема и сайт
  пишут свои `id` свободно, но не с префиксом модуля — иначе находка (`webx:theme:check`): узел темы,
  названный `seo.*`, столкнётся со следующим узлом модуля.
- В первом наброске кнопка связи называлась `contact-button`; здесь — `widgets.contact-button` по
  правилу префикса.

### 2.6 JSON-схема

`webx-ui/compositions/resources/schema/composition.json`, публикуется с доками рядом со схемой
экранов (`https://webx-ui.github.io/webx-ui/schema/composition.json`). План:

- draft 2020-12; верхний уровень — `oneOf` из `base` (`root` | `extends` + операции) и `patch`
  (только операции), `additionalProperties: false`;
- `node` — `oneOf` по видам: у каждого `required` — `id` и ключ вида, `additionalProperties: false`;
  `children` — массив `node`; `id` — `pattern: ^[a-z0-9-]+(\.[a-z0-9-]+)*$`;
- `attrs` — объект: строка | `true` | `false` | `null` | `{ "remove": "…" }` (только у `class`);
- позиция в `add`/`move` — `oneOf` из `before` | `after` | `first: true` | `last: true` (ни одного —
  `last`);
- проверяет `webx:theme:check` и тест пакета на каждом файле; редактор подсказывает по `$schema`.

`vue` в схеме появляется вместе с реализацией, не раньше: формат, который никто не исполняет, —
обещание без проверки.

## 3. Операции

```json
{
  "attrs": { "html": { "data-webx-smooth-scroll": true }, "body": { "class": "is-article" } },
  "props": { "seo.faq": { "limit": 5 } },
  "add": [
    {
      "id": "reading-progress",
      "to": "body",
      "after": "header",
      "view": "components.reading-progress"
    }
  ],
  "move": [{ "id": "notice-bar", "after": "header" }],
  "replace": { "header": { "region": "header", "fallback": "components.header-compact" } },
  "remove": ["widgets.contact-button"]
}
```

### 3.1 `attrs`

`{ "<id>": { "<атрибут>": <значение> } }` — у узлов `tag`, `component`, `vue`.

| Значение                 | Что делает                                                           |
| ------------------------ | -------------------------------------------------------------------- |
| строка                   | ставит атрибут с этим значением (экранируется; `trans::` — перевод)  |
| `true`                   | атрибут без значения: `data-webx-smooth-scroll`                      |
| `false` / `null`         | снимает атрибут                                                      |
| `class`: строка          | **дописывает** классы через пробел, без повторов: `site is-article`  |
| `class`: `{"remove": …}` | снимает перечисленные классы; `class: false` снимает атрибут целиком |

**Зарезервированные атрибуты** — патч их не меняет (находка, операция пропускается):

- `lang` у `html` — его считает компилятор из языка страницы (`app()->getLocale()`);
- `id` у `main` — `content`: на него ведёт ссылка «Перейти к содержимому» (WCAG 2.4.1);
- `name` у `region` и `slot`/`stack` — это вид узла, а не атрибут; поменять — `replace`.

### 3.2 `props`

`{ "<id>": { "<проп>": <литерал> } }` — только у `component` и `vue`; сливается поверхностно по
ключам, `null` снимает проп (компонент берёт своё значение по умолчанию). Пропсы — да, патчем: иначе
«FAQ на пять вопросов» снова потребовал бы копии. Чего патч не может — передать выражение; это
решает лист.

### 3.3 `add`

Массив узлов; у каждого, кроме ключей узла, — `to` (контейнер: `tag`, группа, `component`) и
позиция: `before: <id>` | `after: <id>` | `first: true` | `last: true` (по умолчанию `last`).
`before`/`after` называют соседа **внутри `to`**.

- `to` нет в дереве — находка, узел не добавлен.
- Соседа из `before`/`after` нет в `to` — находка, узел встаёт `last` в `to`: кусок модуля не теряется
  из-за того, что тема переставила его соседа.
- `to` — не контейнер (`region`, `view`…) — находка, узел не добавлен.
- `id` уже есть — находка, узел не добавлен (заменить — `replace`).

### 3.4 `move`

`{ "id": …, "to"?: …, <позиция> }` — без `to` узел остаётся у своего родителя и переставляется среди
соседей. Узла нет — находка. Перенос узла в самого себя или в своего потомка (цикл) — находка,
операция пропускается.

### 3.5 `replace`

`{ "<id>": <узел без id> }` — другой вид, компонент, вид узла для того же места: `id` и позиция
остаются, дети нового узла — из замены. Если у старого узла были дети, добавленные **другими**
слоями (модулями), они пропадают — находка-замечание: «header replaced by theme/…; drops seo.x added
by module-seo». Заменить узел на узел с другим `id` — `remove` + `add`.

### 3.6 Порядок и ошибки

**Внутри файла** — фиксированный порядок, потому что порядок ключей JSON-объекта не контракт:

```
add → move → replace → attrs → props → remove
```

Внутри списка — по порядку записи. `remove` последним: файл может добавить узел «после X» и тут же
убрать X. `attrs` после `add` и `replace` — у узлов, которые этот же файл добавил или заменил.

**Между слоями** — §5.2.

**Защищённые узлы** базы layout: `html`, `head`, `body`, `main`, `content`, `head.slot`, `head.stack`,
`scripts.stack`, `theme.assets`. Их нельзя `remove` и `replace` (находка): без них ломается не вид,
а швы модулей — пропадает `<title>`, стили блоков, скрипты. `html`, `head`, `body` нельзя и
`move`; `content` двигается только внутри `main` (кабинет кладёт его в свою сетку, §3.7). Стек
`head` обязан остаться в `head`. Защиту объявляет база ключом узла `"protected": true` (в схеме —
только у базы), чтобы у других композиций был тот же механизм.

**Находки, а не исключения.** Ссылка на несуществующий `id`, дубль, цикл, защищённый узел,
неизвестный вид или директива — операция пропускается, находка пишется. `remove` узла, который
нижний слой уже убрал (тема сняла кнопку связи в `layout`, а `layout.minimal` через `extends`
снимает её ещё раз), — замечание, а не находка: узла нет, как файл и просил.

Находка:

- при компиляции — в лог (`warning`) и в вывод `webx:composition:compile`;
- `webx:theme:check` — строкой `файл:операция что — почему`, код 1;
- `ThemeContract` (тест темы) и тест модуля **падают** на находках своих файлов: в CI пакетные темы и
  модули чистые, а сайт на проде не падает из-за патча, пережившего переименование.

**Исключение** (`CompositionException`) — только когда дерево не построить вовсе: невалидный JSON,
ошибка схемы, две базы у композиции, `extends` на неизвестную композицию или цикл в `extends`.
Компиляция тогда не заменяет прежний скомпилированный набор (§6.2).

### 3.7 Наследование: `extends`

База `{"extends": "layout", …операции}` берёт **итоговое** дерево родителя для того же хендла —
со всеми модулями и патчами тем — и накладывает на него свои операции, затем слои своей композиции
(§5.2). Так вариант получает шапку, подвал, куски модулей и патчи темы основного layout, и правка
`theme/compositions/layout/default.json` видна во всех вариантах сразу.

`layout.minimal` в `theme-default` — для чекаута и мастеров:

```json
{
  "extends": "layout",
  "replace": { "header": { "view": "components.header-minimal" } },
  "remove": ["footer", "widgets.contact-button"]
}
```

`layout.account` (личный кабинет; кабинет — следующей задачей, здесь — формат):

```json
{
  "extends": "layout",
  "add": [
    {
      "id": "account",
      "to": "main",
      "first": true,
      "tag": "div",
      "attrs": { "class": "site-account" },
      "children": [
        {
          "id": "account.menu",
          "tag": "nav",
          "attrs": {
            "class": "site-account__menu",
            "aria-label": "trans::theme::theme.account.menu"
          }
        },
        { "id": "account.body", "tag": "div", "attrs": { "class": "site-account__body" } }
      ]
    }
  ],
  "move": [{ "id": "content", "to": "account.body" }]
}
```

`layout.blank` — **своя база**, а не `extends`: пустая оболочка для промо и встраиваемых страниц не
должна получать то, что модули добавляют в `layout` (FAQ, кнопку связи). Модуль, которому место на
любом документе (`module-snippets`: счётчики и менеджер тегов), кладёт файл и для `layout.blank`
(вопрос 8 в §11).

```json
{
  "root": {
    "id": "html",
    "tag": "html",
    "protected": true,
    "children": [
      {
        "id": "head",
        "tag": "head",
        "protected": true,
        "children": [
          { "id": "meta.charset", "html": "<meta charset=\"utf-8\">" },
          {
            "id": "meta.viewport",
            "html": "<meta name=\"viewport\" content=\"width=device-width, initial-scale=1\">"
          },
          { "id": "theme.assets", "directive": "webxTheme", "protected": true },
          {
            "id": "head.slot",
            "slot": "head",
            "fallback": ["webxSeo", "webxBlocks"],
            "protected": true
          },
          { "id": "head.stack", "stack": "head", "protected": true }
        ]
      },
      {
        "id": "body",
        "tag": "body",
        "attrs": { "class": "site site--blank" },
        "protected": true,
        "children": [
          {
            "id": "main",
            "tag": "main",
            "attrs": { "id": "content", "class": "site-main" },
            "protected": true,
            "children": [{ "id": "content", "slot": "default", "protected": true }]
          },
          { "id": "scripts.stack", "stack": "scripts", "protected": true }
        ]
      }

```

## 4. Хендлы

- **`default`** — всегда; файл `default.json` слоя применяется к каждому варианту.
- **Тип страницы** — `<модуль>.<страница>`: `pages.page`, `blog.article`, `blog.feed`, `blog.rubric`,
  `blog.tag`, `blog.author`, `services.show`, `catalog.product`, `catalog.category`, `catalog.checkout`.
  Не путать с `type` у `RouteType` (`article` — алиас морфа без модуля): у страницы без адреса
  (лента, поиск, чекаут) `RouteType` нет, а хендл нужен.
- **Хендлов под конкретную страницу (`page.42`) нет**: это вид одной записи, и он решается контентом
  (блоки, регионы), а не файлом темы на каждую запись.
- Один хендл на запрос. Иерархии (`blog.*` для всех страниц блога) нет — вопрос 15 в §11.

**Кто называет хендл.** Модуль — в виде своей страницы, атрибутом вызова layout:

```blade
<x-dynamic-component :component="config('webx-blog.layout') ?: 'webx-blog::standalone'" handle="blog.article">
```

Явный атрибут, а не глобальное состояние: вид знает, что он печатает, ещё до того, как вызовет
layout; `RouteType` и резолвер не меняются; вызов без `handle` — `default`; собственный layout сайта
и `webx-blog::standalone` атрибут просто не читают. Модуль объявляет свои хендлы в провайдере —
`Compositions::handles('blog', ['blog.article', 'blog.feed', …])`, — чтобы `webx:theme:check` поймал
опечатку в имени файла (`blog.artcle.json` — находка «unknown handle»), а `show` показал их списком.

**Порядок:** `default` → тип страницы, внутри **каждого слоя** (§5.2).

**Какой layout у страницы** решает не панель (выбора в панели нет: это лишние вопросы на сайтах,
где он не нужен), а:

1. конфиг модуля — как сейчас, `webx-<модуль>.layout` (`'layout'`, `'layout.minimal'`);
2. конфиг сайта — `webx-compositions.layouts`: `['catalog.checkout' => 'layout.minimal']`, хендл →
   композиция; для модуля, у которого своего ключа нет, и для сайта, которому так проще;
3. по умолчанию — `layout`.

Пункт 2 решается при компиляции (§6.3): диспетчер `layout` для хендла `catalog.checkout` сразу
печатает скомпилированный `layout.minimal × catalog.checkout`, лишнего на запросе нет.

## 5. Слои

### 5.1 Источники

```
конфиг сайта      config/webx-compositions.php → patches
локальная тема    theme/compositions/
пакетные темы     <пакет>/compositions/   (сверху вниз по цепочке, THEMES §7.1)
модули            <пакет>/resources/compositions/
база              нижний слой, который композицию ввёл
```

**Регистрация модуля** — в провайдере, как экраны (`Screens::register`) и виды (`loadViewsFrom`):

```php
// SeoServiceProvider::boot()
Compositions::load(__DIR__.'/../resources/compositions');
```

Явный вызов, а не поиск по `InstalledVersions`: модуль, чей провайдер не загружен (выключен,
testbench без него), ничего не добавляет, — и это ровно тот набор, который увидит веб-запрос.
**Модуль без каталога ничего не добавляет.** Темы находит движок тем по цепочке, им регистрация не
нужна.

### 5.2 Порядок применения

```
1. база (default.json нижнего слоя; у extends — итоговое дерево родителя для этого хендла)
2. модули         — каждый: default, затем <хендл>
3. пакетные темы над базой, снизу вверх — каждая: default, затем <хендл>
4. локальная тема — default, затем <хендл>
5. конфиг сайта   — default, затем <хендл>
```

Если база — пакетная тема (`theme-default` для `layout`), её собственный `<хендл>.json` идёт сразу
за базой, до модулей. Пакетная тема **над** `theme-default` (каталожная тема на её основе) идёт
после модулей — иначе она не могла бы тронуть их куски; при одной пакетной теме это ровно порядок
«пакетная тема → модули → локальная тема → конфиг» из постановки.

**Слой целиком, потом следующий** (а не «все `default`, потом все хендлы», как у Magento): верхний
слой всегда сильнее нижнего. Иначе `blog.article.json` модуля мог бы вернуть узел, который
локальная тема убрала в `default.json`, и тема проиграла бы модулю — против правила цепочки
(THEMES §7.1).

**Между модулями** — по идентификатору модуля по алфавиту: порядок установки Composer не стабилен, а
итог не должен зависеть от того, кто поставился первым. Позиции модулей заданы якорями (`after:
content`), поэтому порядок важен только когда два модуля ставят `first`/`last` в один контейнер.
Явный `"after": ["seo"]` в патче модуля — если понадобится (вопрос 4 в §11).

### 5.3 Что меняется у пакетов, которые сейчас пришиты в layout

| Кусок                           | Сейчас                                              | Будет                                                                                                                                                                                                                                                                                                  |
| ------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Три места `module-snippets`     | `view()->exists()` + `x-dynamic-component` в layout | `module-snippets/resources/compositions/layout/default.json`: `snippets.head` (в `head` после `meta.viewport`), `snippets.body-start` (`body`, `first`), `snippets.body-end` (`body`, `last`); то же для `layout.blank`. `PlacesCheck` смотрит итоговое дерево, а при своём файле layout — как сейчас. |

| Кнопка связи `widgets`          | `<x-webx-contact-button />` в layout                | `widgets/resources/compositions/layout/default.json`: `widgets.contact-button` (`body`, после `footer`)                                                                                                                                                                                                |
| Полоса объявления `widgets`     | `<x-webx-notice-bar>@stack('notice')</…>` в layout  | остаётся в базе `theme-default` узлом `notice-bar`: место над шапкой — решение оболочки, `widgets` для темы обязателен                                                                                                                                                                                 |

## 6. Компиляция

### 6.1 Что получается

На каждую композицию — по виду на каждый хендл, у которого есть хоть один файл в каком-нибудь слое
(родителя — тоже, для `extends`), плюс `default`. Набор пишется в свой каталог сборки и становится
текущим переименованием `manifest.php`: запрос посреди компиляции читает старый набор или новый,
но не половину:

```
storage/framework/compositions/
├── build-<id>/layout__default.blade.php
├── build-<id>/layout__blog_article.blade.php
├── build-<id>/layout_minimal__default.blade.php
├── build-<id>/place/…                         ← части для `place` (§6.4), по первому запросу
└── manifest.php                               ← виды по композиции и хендлу, источники и их mtime, находки
```

Виды — в пространстве `webx-composition::` (точки имён — в `_`: Blade читает точку как слэш).
Хранятся текущая сборка и одна прошлая: запрос, прочитавший старый манифест, дорисует по нему.

**Диспетчер** — обычный вид пакета, который ввёл композицию: у `layout` —
`theme-default/views/components/layout.blade.php` (и `layout/minimal`, `layout/blank`), одна строка:

```blade
@include(composition_view(layout, $attributes->get(handle)))
```

`composition_view()` берёт имя вида из манифеста: хендл без своего файла получает `default`,
хендл из `webx-compositions.layouts` — вариант другой композиции (решено при компиляции). Диспетчер
лежит в цепочке тем, поэтому `components/layout.blade.php` локальной темы или сайта стоит выше
него и печатает вместо композиции (§6.4) — без отдельного правила. `@include` передаёт виду
`$slot`, `$head`, `$attributes` места вызова — компонент остаётся анонимным, сигнатура layout
(слот `head` и слот по умолчанию) не меняется.

> Отличие от первого варианта спеки: сгенерированный диспетчер с `match` в `storage/` и
> `View::addLocation()` заменены видом пакета с `composition_view()`. Так виден один и тот же файл
> в цепочке тем, `webx:theme:check` и `PlacesCheck` находят диспетчер там же, где раньше layout,
> а лишнего каталога в поиске видов нет; цена на запросе — чтение манифеста, один раз за запрос.

**Статические теги вместо проверок на запросе.** Модули известны на этапе компиляции, поэтому:

- `<x-webx-seo::faq />` вместо `view()->exists('webx-seo::faq')` + `x-dynamic-component`;
- узла модуля, который не установлен, в дереве просто нет — проверять нечего;
- `region` без `module-blocks` компилируется в `@include` запасного вида;
- директива без своего пакета — находка, узла нет.

### 6.2 Когда пересобирается

- **`webx:composition:compile`** — собирает всё; шаг `webx:boot` **до** `view:cache` (Blade затем
  кеширует сгенерированные виды как любые). Ошибка дерева (§3.6) — шаг падает с кодом 1, прежний
  набор остаётся на месте, шаг не фатальный: сайт продолжает работать на прошлой сборке, а не
  ложится. Выкладка на cPanel без SSH и так идёт через `webx:boot` — отдельного шага не нужно.
- **По `mtime` источников на запросе** — как сам Blade (`view.check_cache_timestamps`): перед
  первым рендером диспетчера движок сверяет `manifest.php` с источниками и пересобирает изменившиеся
  композиции. Источники — каждый JSON слоёв, **каталоги** `compositions/<имя>/` слоёв (новый файл
  хендла меняет mtime каталога), `config/webx-compositions.php`, `vendor/composer/installed.php`
  (поставили или убрали модуль) и `theme.json`/`tokens.json` (тема и `theme-color`, §7). `filemtime`
  идёт по симлинку, поэтому live-сайты, где `vendor/webx-ui/*` — ссылки на монорепу, видят правку
  JSON модуля сразу, без `webx sync`. Это десяток-другой `stat` на запрос — та же цена, что Blade
  платит за свои виды; включено, пока включено у Blade (вопрос 11 в §11).
- Запись атомарная (временный файл + `rename`), под блокировкой: два одновременных запроса на dev не
  пишут один файл наполовину.
- `webx:composition:clear` — снести набор; `view:clear` его не трогает.

### 6.3 Конфиг сайта

`config/webx-compositions.php` (публикуется скелетом `webx-ui/site`):

```php
return [
    // Patches above the local theme: the same JSON shape, as PHP arrays.
    'patches' => [
        'layout' => ['default' => ['attrs' => ['html' => ['data-webx-smooth-scroll' => true]]]],
    ],
    // Which layout a page type stands in, when its module has no key of its own (§4).
    'layouts' => ['catalog.checkout' => 'layout.minimal'],
];
```

Зачем слой выше темы: сайт без темы, отличие окружения (`env()` в конфиге), конфиг модуля сайта.
Обычное место патчей сайта — `theme/compositions/`.

### 6.4 Свой файл вида — выход из схемы

`theme/views/components/layout.blade.php` (или `resources/views/components/layout.blade.php`)
работает, как сейчас: он раньше в поиске, чем сгенерированный диспетчер. Композиция `layout` для
такого сайта не используется, и `webx:theme:check` говорит **замечание** (не ошибку): «components/layout
overrides the composition layout; compositions/layout/*.json of theme are not applied». То же для
любого вида-композиции (`views/vendor/webx-blog/article.blade.php` против `blog.article`).

**Гибрид** — разметка своя, куски модулей приходят с релизами:

```blade
<main id="content" class="my-main">
    {{ $slot }}
    <x-webx-composition::place id="main" :handle="$attributes->get('handle')" only="added" />
</main>
<x-webx-composition::place id="body" only="added" />
```

`place` печатает детей контейнера `id` из итогового дерева (`composition="layout"` по умолчанию,
`handle` — `default`, если не передан): `only="all"` — всех, кроме узла `content` (слот печатает сам
вызов); `only="added"` — только добавленных выше базы (модули, патчи тем) — то, чего рукописный файл
не знает. Тоже скомпилировано: на каждый контейнер варианта — свой частичный вид, `place` выбирает
его так же развилкой. `webx:theme:check` для файла с `place` проверяет, что такой контейнер есть.

### 6.5 Миграция

Живых сайтов на композициях нет, обратная совместимость не обязательна, но путь должен быть:

- **`theme-default`** сводит `views/components/layout.blade.php` к диспетчеру (§6.1) и ставит `compositions/layout/`,
  `layout.minimal/`, `layout.blank/`, виды `components/skip-link`, `components/header-minimal`.
- **Модули с публичными страницами** дописывают `handle="…"` в вызов layout и объявляют хендлы;
  ключ `webx-<модуль>.layout` и `webx-<модуль>::standalone` не меняются.
- **`module-snippets`, `module-seo`, `widgets`** — файлы из §5.3.
- **Сайт без своего layout** получает композицию с `composer update` — ничего делать не нужно.
- **Сайт со своим `components/layout.blade.php`**: продолжает работать; переход — сравнить копию с
  базой (`webx:composition:show layout --blade` печатает итоговый Blade), выразить отличия патчем в
  `theme/compositions/layout/*.json`, удалить копию, сверить HTML страницы до и после. Для сайта
  студии — отдельная задача после релиза (вне этой).
- **RULES.md**, правило 21 («держи швы в `components/layout`») меняется: швы — защищённые узлы
  композиции; свой файл layout — осознанный выход, со `place` для кусков модулей.

## 7. `theme-color`

Сейчас его не печатает никто: ни `@webxTheme` (`ThemeHead`), ни `module-seo`, ни виды
`theme-default` (проверено поиском по пакетам). Узел базы `layout` (и `layout.blank`) в `head` после
`theme.assets`:

```json
{ "id": "meta.theme-color", "directive": "webxThemeColor" }
```

`@webxThemeColor` — директива движка тем, значение — токен **`color-bg`** цепочки (с раскрытыми
ссылками на другие токены, с пресетом):

```html
<meta name="theme-color" content="#f7f7f4" />
```

Если у токена есть значение в `schemes.dark` (THEMES §7.6) — два тега:

```html
<meta name="theme-color" media="(prefers-color-scheme: light)" content="#f7f7f4" />
<meta name="theme-color" media="(prefers-color-scheme: dark)" content="#0d0f0e" />
```

- Другой токен — `replace` с аргументом: `{"meta.theme-color": {"directive": "webxThemeColor", "args": "'color-surface'"}}`.
- Свой цвет — `replace` на `html`; отключить — `remove: ["meta.theme-color"]`.
- `data-theme="dark|light"` от переключателя сайта медиа-запрос не слышит: переключатель темы сайта
  сам переписывает `content` (пример — в `guide/themes.md` рядом с ранним скриптом).
- Без темы директивы нет — узла тоже (база `layout` и так у темы).

Значения известны при компиляции, но директива считает их на запросе из уже собранных токенов
(`ThemeLook`): пресет и токены меняются без пересборки композиций, а цена — та же, что у
`@webxTheme`.

## 8. Инструменты

**`webx:composition:show [<композиция>] [--handle=<хендл>] [--json] [--blade] [--origin]`**

- без аргументов — композиции, их хендлы, слои и файлы, находки;
- с композицией — итоговое дерево отступами; `--origin` у каждого узла — кто его ввёл и кто тронул:

  ```
  body                        theme-default   attrs.class +is-article ← theme/compositions/layout/blog.article.json
    snippets.body-start       module-snippets
    skip-link                 theme-default
    header                    theme-default
    reading-progress          theme/compositions/layout/blog.article.json (add)
    notice-bar                theme-default   moved ← theme/compositions/layout/default.json
    main                      theme-default
      content                 theme-default
      seo.faq                 module-seo
  removed: seo.links ← theme/compositions/layout/blog.article.json; widgets.contact-button ← theme/…/default.json
  ```

- `--blade` — сгенерированный Blade; `--json` — дерево с происхождением для скрипта и агента.

Имя `webx:composition:*`, а не `webx:layout:*`: движок общий (`blog.article`, потом карточки и
формы), а `layout` — первая из композиций.

**`webx:composition:compile [--force]`** и **`webx:composition:clear`** — §6.2.

**`webx:theme:check`** — часть `CompositionCheck` (через `ThemeCheckPart`, как `PlacesCheck` у
snippets): схема каждого файла; находки §3.6 на каждом хендле и каждом варианте; файл хендла,
которого никто не объявил; композиция, которой нет; `id` темы с префиксом модуля; свой файл вида
против композиции — замечание (§6.4); `place` на контейнер, которого нет.

**`webx:doctor`** — скомпилированный набор старее источников, а проверка `mtime` выключена (прод
без `webx:boot`); прошлая компиляция упала; находки в итоговых деревьях сайта; модуль зовёт layout
без `handle` (замечание).

**`webx:theme:show`** перечисляет композиции слоёв рядом с видами; `webx:theme:eject` и `extract`
переносят `compositions/` как остальные каталоги темы.

**MCP.** Ресурса не предлагаю: композиции — файлы темы в git, агент, который их правит, работает в
репозитории и читает `webx:composition:show --json` (тот же довод, что THEMES §7.4 и §16);
MCP-подключение к панели вид сайта не меняет. Правило «каждая функция покрыта MCP» — про функции
панели, а здесь функции панели нет. Если понадобится объяснять из панели «почему на странице нет
FAQ» — ресурс только для чтения `site://compositions/<имя>` (вопрос 12 в §11).

## 9. Производительность

**Ожидание:** не медленнее, скорее чуть быстрее. Убираются четыре `view()->exists()` и четыре
`x-dynamic-component` (разбор имени, поиск класса или вида) на каждый запрос; добавляется один
`@include` диспетчера и проверка `mtime` (§6.2).

**Методика** (замер до и после, в отчёте этапа 2 и этапа 4):

1. Стартовый сайт (`scripts/starter-site.sh`) на релизе до и на ветке после; `APP_DEBUG=false`,
   `config:cache`, `route:cache`, `view:cache`, OPcache включён, тёплый кеш (20 запросов прогрева).
2. Страницы: главная (`pages.page`) и статья блога (`blog.article`) — та, где композиций больше всего.
3. 200 последовательных запросов на страницу (`curl -w '%{time_starttransfer}'` в цикле, без
   параллельности — меряем рендер, а не очередь), медиана и p95; два прогона, берётся лучший по
   медиане.
4. Отдельно — то же с проверкой `mtime` выключенной и включённой; и время `webx:composition:compile`
   на стартере.

**Критерий:** медиана «после» ≤ медиана «до» × 1,02 (шум прогона), p95 ≤ × 1,05; HTML без патчей —
тот же (§10, этап 2). `PerformanceTest` модулей, где он есть, не поднимает бюджет.

**Замер этапа 2** (23.10.2026, стартер `--with=blog,services` на этой ветке, общий dev-сервер,
`php -S` с OPcache, `APP_DEBUG=false`, `config:cache`, `route:cache`, `view:cache`). «До» — layout
релиза 0.85.0 файлом сайта `resources/views/components/layout.blade.php`: тот же путь рендера, что
был (`view()->exists()` + `x-dynamic-component`), остальной код общий. Состояния чередовались
шестью кругами по 60 запросов на страницу с прогревом после каждого переключения — шум общего хоста
ложится на все поровну; 360 образцов на ячейку, `time_starttransfer`, мс:

| Страница                | До: медиана / p95 | После, mtime вкл. | После, mtime выкл. |
| ----------------------- | ----------------- | ----------------- | ------------------ |
| главная (`pages.page`)  | 39,75 / 51,55     | 40,52 / 52,96     | 40,86 / 58,93      |
| статья (`blog.article`) | 50,23 / 102,65    | 49,76 / 128,28    | 49,07 / 64,70      |

Разница — в шуме прогона: «mtime выкл.» делает строго меньше работы, чем «вкл.», а на главной
вышла медленнее. Отдельно, внутри одного процесса, рендер `<x-layout>` 600 раз за круг, четыре круга
по очереди: медиана «до» 12,06–12,11 мс, «после» 12,05–12,14 мс (без первого, холодного круга).
`webx:composition:compile` на стартере — 0,17 с с загрузкой artisan; первый запрос после
`webx:composition:clear` компилирует сам. HTML главной и статьи «до» и «после» совпадает с точностью
до пробелов между тегами (снятые комментарии Blade, §11 п. 6) и нового `theme-color`.

## 10. План внедрения

**Этап 2 — движок и `layout`.** Пакет `webx-ui/compositions` (четыре места регистрации в `php/`, реестр
пакетов); формат, схема, операции, слои, `extends`, компиляция, диспетчер, проверка `mtime`, `place`;
`theme-default`: `layout`, `layout.minimal`, `layout.blank`, `skip-link`, `header-minimal`;
`@webxThemeColor` в `themes`; файлы `module-seo`, `module-snippets`, `widgets`; `handle` в вызовах
layout модулей; шаг `webx:boot`. Тесты: **золотой HTML** — рендер страниц стартера на текущем layout
сохраняется до правки и сравнивается побайтно с композицией без патчей; патчи `default` и хендла;
порядок слоёв; находки; `extends`; свой файл вида побеждает. Замер §9.

**Этап 3 — инструменты и доки.** `webx:composition:show/compile/clear`, `CompositionCheck`, доктор;

## 11. Риски и открытые вопросы

Человек решает при приёмке; у каждого — варианты и рекомендация.

1. **Где движок.** (а) Новая библиотека `webx-ui/compositions`; (б) внутри `webx-ui/themes`.
   **Рекомендую (а):** композиции модулей (`blog.article`) работают и на сайте без темы, а `themes` —
   про цепочку и токены. Цена — новый пакет (четыре места в `php/`, реестр, зеркало для Packagist,
   первая версия — как у любого composer-пакета общей версией).
2. **Пути.** (а) `<слой>/compositions/<имя>/<хендл>.json`; (б) `<слой>/layout/<хендл>.json` из
   наброска и каталог на каждую композицию в корне. **Рекомендую (а)** — §2.1.
3. **Порядок слоёв и хендлов.** (а) Слой целиком (`default` → хендл), потом следующий, пакетные темы
   над базой — после модулей; (б) все `default`, потом все хендлы (как Magento). **Рекомендую (а)** —
   §5.2: верхний слой всегда сильнее.
4. **Порядок между модулями.** (а) По алфавиту, позиции якорями; (б) явный `"after": [...]` в патче
   модуля сразу. **Рекомендую (а)**, (б) — когда встретится настоящий конфликт двух `first`.
5. **`move` в регион.** Пример наброска двигал полосу _в_ `header`, а `header` — регион. (а) Находка,
   до композиции `header`; (б) разрешить «в регион» как «первым в его разметку» — это значит лезть
   внутрь вида шапки. **Рекомендую (а).**
6. **Побайтно прежний HTML.** Комментарии Blade в нынешнем layout оставляют в HTML пустые строки с
   отступами, и `theme-color` — новый тег. (а) Этап 2 первым коммитом снимает комментарии-пробелы из
   нынешнего файла (HTML меняется только пробелами между тегами), снимает с него золотой HTML,
   композиция без патчей совпадает с ним побайтно; `theme-color` — отдельным коммитом с осознанным
   обновлением золотого файла; (б) сравнивать с нормализацией пробелов. **Рекомендую (а):** критерий
   остаётся побайтным и проверяемым.
7. **Токен `theme-color`.** (а) `color-bg`; (б) `color-surface` (если шапка на поверхности).
   **Рекомендую (а)** с аргументом директивы для темы, у которой шапка другого цвета.
8. **`layout.blank`.** (а) Своя база, модули добавляют в неё явно; (б) `extends: layout` и снятие
   всего лишнего. **Рекомендую (а):** при (б) каждый новый кусок модуля в `layout` появится на промо,
   пока его кто-то не уберёт.
9. **`place`.** (а) Два режима — `all` (по умолчанию) и `added`; (б) только `added`. **Рекомендую
   (а)**, гибрид в гайде — с `added`.
10. **Как называть хендл.** (а) Атрибут `handle` в вызове layout из вида модуля; (б) хендл из
    `RouteType` на резолвере (нет у страниц без адреса); (в) глобальное «текущий хендл» на запрос.
    **Рекомендую (а).**
11. **Проверка `mtime` на проде.** (а) Как у Blade — пока `view.check_cache_timestamps`; (б) только при
    `APP_DEBUG` и на live-сайтах, на проде — только `webx:boot`. **Рекомендую (а):** выкладка, забывшая
    `webx:boot`, всё равно увидит новый JSON, а цена — десяток `stat`.
12. **MCP.** (а) Без ресурса, `show --json`; (б) ресурс только для чтения с итоговым деревом.
    **Рекомендую (а)** — §8.
13. **Находка против исключения.** (а) На сайте — находка и пропуск, в тестах пакетов и тем — падение;
    (б) исключение, как у экранов. **Рекомендую (а)** — §3.6.
14. **Выражения в `attrs`.** (а) Только литералы и `trans::`; (б) `:attr` с PHP-выражением. **Рекомендую
    (а):** выражение в JSON — код без проверок и подсветки; динамике место в листе.
15. **Иерархия хендлов** (`blog` для всех `blog.*`). (а) Не делать; (б) `blog.json` между `default` и
    `blog.article`. **Рекомендую (а)** сейчас: пять файлов хендлов блога проще, чем ещё одно правило
    порядка; вернуться, если темы начнут копировать одинаковые патчи.
16. **Риск: `id` как контракт.** Переименование узла пакета молча делает патчи сайтов находками.
    Смягчение — `id` в `AGENTS.md` пакета (`### Compositions`), находки в `theme:check` и доктора,
    переименование — ломающее изменение в changeset.
17. **Риск: файл вида и композиция вместе.** Сайт, у которого есть и копия layout, и
    `compositions/layout/*.json`, видит только копию. Смягчение — замечание `theme:check` (§6.4).
