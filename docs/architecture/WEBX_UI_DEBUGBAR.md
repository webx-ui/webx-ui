# Отладочная панель на сайте — спецификация

Полоса снизу публичной страницы для администратора с правом `debug.view`, и только не на проде:
какие SQL-запросы сделала страница, сколько это стоило, где повторы (N+1), какие регионы и блоки
нарисованы и из какой темы, что прочитано из кеша, что нашёл резолвер — и откуда в коде всё это
пришло. Тот же отчёт агенту — инструментом MCP `debug_page`.

Статус: серверная половина в `php/packages/module-debug` (задача webx-ui#19, этап 2): сборщики, отчёт, доступ, API, MCP `debug_page`; на странице пока только строка-сводка, вкладки — DB3. Развилки — §16.

Соседние спеки: панель на сайте (показ, загрузчик, Shadow DOM, `no-store`) —
[`WEBX_UI_SITE_BAR.md`](WEBX_UI_SITE_BAR.md); сборщик запросов и бюджеты —
[`WEBX_UI_PERFORMANCE.md`](WEBX_UI_PERFORMANCE.md) §5 и
[`WEBX_UI_PERFORMANCE_AUDIT.md`](WEBX_UI_PERFORMANCE_AUDIT.md) §7; версионный кеш —
[`WEBX_UI_CACHE.md`](WEBX_UI_CACHE.md); резолвер — [`WEBX_UI_ROUTING.md`](WEBX_UI_ROUTING.md);
регионы и блоки — [`WEBX_UI_MODULE_BLOCKS.md`](WEBX_UI_MODULE_BLOCKS.md),
[`WEBX_UI_LAYOUT_REGIONS.md`](WEBX_UI_LAYOUT_REGIONS.md); цепочка тем —
[`WEBX_UI_THEMES.md`](WEBX_UI_THEMES.md); MCP — [`WEBX_UI_MCP_ACCESS.md`](WEBX_UI_MCP_ACCESS.md).

## 1. Границы

Полоса — **инструмент разработчика сайта, а не мониторинг.** Она отвечает на вопрос «что сделала
эта страница, когда её открыл я» и ведёт к месту в коде. Не делает:

- историю и агрегаты по многим запросам, графики, алерты — это APM, не наша задача;
- профилирование PHP по функциям (xdebug, xhprof) — только наши точки замера (§6);
- запросы панели, API, JSON, файлы, редиректы — только HTML-страницы сайта (§3);
- прод — никогда, ни под каким флагом (§3);
- правку чего-либо: полоса только читает. Ссылки ведут в панель или на панель сайта.

## 2. Принятые решения (не переоткрывать без новой причины)

1. **Свой лёгкий сборщик, не готовый debugbar.** Сравнение — §4. Внешний пакет не ставится ни в
   продовые, ни в dev-зависимости сайта.
2. **Отдельный composer-пакет `webx-ui/module-debug`** (namespace `WebxUi\Debug`, идентификатор
   модуля `debug`): своё право `debug.view`, свой инструмент `debug_page` (имя MCP —
   `<модуль>_<инструмент>`), свой конфиг. Без npm-пары: экрана в панели нет, полоса — ES-модуль
   без зависимостей в самом composer-пакете, как загрузчик панели сайта. Почему не внутри
   `module-admin` — §16, развилка 1.
3. **Решает сервер.** Показывать или нет, собирать или нет, знает только сервер. Посетителю ответ
   отдаётся байт в байт таким, каким он был без пакета, и без единого лишнего запроса к базе —
   это проверяется тестами (§14), а не обещанием.
4. **На странице — только сводка и id отчёта.** Детали — отдельным запросом к API панели под тем же
   администратором; отчёт живёт минуты (§9).
5. **Полоса снизу, поверх страницы**, в Shadow DOM, не сдвигает вёрстку и не перекрывает ящик панели
   сайта (§11).
6. **Точки замера в наших пакетах — события, которые стреляют, только когда их слушают.** Ни
   `module-blocks`, ни `routing`, ни `cache` не знают о `module-debug`; без слушателя цена — одна
   проверка `hasListeners` (§6.1).

## 3. Когда полоса есть

### 3.1. Условия показа

Полоса вставляется в ответ, если **все** условия верны (от дешёвых к дорогим, как в панели сайта):

1. **Не прод:** `app()->environment('production')` — ложь. Проверяется в `register()` провайдера:
   на проде пакет не регистрирует **ни одного** слушателя, маршрута и инструмента MCP — как если
   бы его не было. Конфиг этого не переопределяет.
2. **Включено:** `webx-debug.enabled` (`WEBX_DEBUGBAR`, по умолчанию `true`; на проде значение не
   читается вовсе).
3. Ответ — страница сайта: те же правила, что `SiteBar\Insertion::wanted()` и `isPage()` —
   `GET`, группа `web`, путь не панель, не API и не `_preview/*`, `Sec-Fetch-Dest` не `iframe`,
   статус 200, не поток, не файл, не JSON, `Content-Type: text/html`, в теле есть `</body>`. Правила
   выносятся из `Insertion` в общий `WebxUi\Admin\SiteBar\PageResponse` (публичный API
   `Insertion` не меняется), чтобы два пакета не разошлись в том, что такое «страница».
4. **Администратор:** `auth(<webx-auth.guard>)->user()` есть, активен (`is_active`) — та же
   проверка, что у панели сайта (гард по имени из конфига, только если объявлен).
5. **Право `debug.view`** (`hasPermission`). Суперадмин имеет его всегда (`CmsUser::hasPermission`).
   При установке **ни одна роль его не получает** — как `snippets.manage`: отчёт показывает
   значения запросов, а в них персональные данные посетителей.
6. **Личный выключатель не выключен** — `localStorage` полосы (§11.4). Он прячет полосу в браузере,
   но сервер про него не знает: сводка и отчёт всё равно собираются. Серверный выключатель —
   `WEBX_DEBUGBAR=false`.

Нарушено любое — тело ответа и заголовки не трогаются, отчёт не сохраняется.

### 3.2. Когда начинается сбор

«Сбор включается только когда полоса будет показана» упирается в порядок: кто администратор,
известно только после `StartSession` и чтения пользователя, а запросы до этого (глобальные
middleware SEO и закрытия сайта, сессия, сам пользователь) — тоже часть страницы. Решение — две
ступени:

- **Метка в cookie.** При входе в панель (событие `Login` гарда `cms`) и при открытии оболочки
  панели, если метки нет, администратору с `debug.view` ставится cookie `wx_debug`
  (зашифрованная стандартным `EncryptCookies`, `HttpOnly`, `SameSite=Lax`, срок — как у сессии;
  содержит id администратора). Выход — cookie снимается. Без права — не ставится, при потере права
  снимается на ближайшем ответе панели.
- **Первый глобальный middleware `WebxUi\Debug\Http\StartCollecting`** (ставится `prepend`, раньше
  `CloseSite` и SEO): условия 1–2, метод `GET` и **наличие** cookie `wx_debug` — проверка строки
  без расшифровки и без базы. Есть — включаются сборщики (§5), отсчёт идёт от `LARAVEL_START`.
- **Проверка на выходе** (слушатель `RequestHandled`, после ответа): условия 3–5 по-настоящему.
  Не прошли (метку подделали, сеанс истёк, право сняли) — собранное выбрасывается, ответ не
  трогается. Подделанная метка стоит самому подделавшему немного памяти на его же запрос и ничего не
  раскрывает.
- **Нет метки, но администратор с правом** (вошёл до установки пакета, cookie почищены) — запасной
  путь: route-middleware `webx.debug` в группе `web` после `StartSession` проверяет администратора и
  включает сбор с этого места; полоса показывает «Early phase not recorded» и ставит метку на этом
  ответе (заголовок `Set-Cookie` только у администратора, ответ и так `no-store`).

Посетитель без cookie `wx_debug` стоит одной проверки окружения в `register()` и одной проверки
наличия cookie в middleware — ни слушателей запросов, ни событий, ни запросов к базе.

## 4. Основа: свой сборщик или debugbar

| Критерий                  | `barryvdh/laravel-debugbar` (на `php-debugbar`)                                                                      | Clockwork                                                   | Свой сборщик                                                                              |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Вес и зависимости         | два пакета + `symfony/*`; своя вёрстка, иконочный шрифт, свой JS-фронт; ставится как `require-dev`                   | пакет + веб-интерфейс или расширение браузера               | ~1,5–2 тыс. строк PHP и ES-модуль без зависимостей, как `site-bar.js`                     |
| Как решает, показывать ли | `APP_DEBUG` и свой `enabled`; про наших администраторов и права не знает — нужен свой гейт поверх                    | то же, плюс свой маршрут для данных                         | наш гард, `debug.view`, `production` — с первой строки                                    |
| Сбор без показа           | регистрирует коллекторы на загрузке приложения, для всех запросов, если включён                                      | собирает каждый запрос в хранилище                          | только при метке и только до проверки на выходе (§3.2)                                    |
| Изоляция стилей           | вставляет CSS и JS прямо в страницу; тема сайта и полоса влияют друг на друга, отдельные `z-index`                   | вне страницы (расширение) — не вариант для «снизу страницы» | Shadow DOM и токены на `:host` — уже проверено панелью сайта                              |
| Хранение и выдача         | файлы `storage/debugbar` и свой открытый маршрут `_debugbar/open`; известная история утечек при `APP_DEBUG` на проде | файлы и маршрут `/__clockwork`                              | короткий TTL в кеше, выдача под `cms.auth` + `cms.can:debug.view` и только владельцу (§9) |
| Наши данные               | регионы, блоки, слой темы, группы версионного кеша, `Resolution` — всё своими коллекторами поверх чужого API         | то же                                                       | те же события, без прослойки                                                              |
| MCP                       | отчёт в своём формате, ради `debug_page` пришлось бы переводить                                                      | то же                                                       | один формат для полосы и агента (§12)                                                     |

Вывод — свой сборщик. Готовые пакеты экономят только сбор SQL и Http-клиента, а это несколько
подписок на события Laravel; всё остальное (гейт, хранение, блоки, кеш, MCP, изоляция) всё равно
пришлось бы писать, но поверх чужого жизненного цикла и с чужим фронтом на странице. Вне ядра
остаётся вариант «разработчик сайта ставит debugbar сам в `require-dev`» — гайд упомянет, что
наша полоса ему не мешает.

## 5. Сборщики

Один объект запроса `WebxUi\Debug\Collector` (привязан к запросу, сбрасывается на
`RequestHandled`/`RequestReceived` под Octane/`JobProcessing`, правило 7 `WEBX_UI_PERFORMANCE.md`
§2) и сборщики-подписчики. Каждый подписывается **только** в момент включения сбора и
отписывается на выходе.

| Сборщик    | Источник                                                                                                                 | Что пишет                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| `queries`  | `DB::listen` (`QueryExecuted`) на всех соединениях; транзакции — `TransactionBeginning`/`Committed`/`RolledBack`         | SQL, значения, время, соединение, место вызова (§7), отметка времени от начала, форма для повторов       |
| `timeline` | события Laravel и наши (§6)                                                                                              | отрезки: начало, конец, родитель, число запросов внутри                                                  |
| `blocks`   | события рендера `module-blocks` (§6.1)                                                                                   | дерево регион → блок → вложенные: ключ, тип, версия, слой темы типа, время, запросы, ошибка/запасной вид |
| `views`    | `creating:*` вида (`View::creator('*')`)                                                                                 | Blade-виды: имя, файл, владелец по цепочке тем (§8), число отрисовок                                     |
| `cache`    | `CacheHit`, `CacheMissed`, `KeyWritten`, `KeyForgotten` хранилища + `GroupRead` из `CacheGroups` (§6.1)                  | обращения по ключам и группам, источник (мемо, хранилище, промах), версии всех групп на конец запроса    |
| `request`  | `Resolution::of($request)`, маршрут, ответ                                                                               | §10.5                                                                                                    |
| `http`     | `RequestSending`, `ResponseReceived`, `ConnectionFailed` Http-клиента                                                    | метод, адрес (секреты в query — маска), статус, время                                                    |
| `queue`    | `JobQueued`                                                                                                              | класс задания, очередь, соединение, задержка                                                             |
| `mail`     | `MessageSending`                                                                                                         | кому (маска локальной части), тема, mailer                                                               |
| `events`   | наши события пакетов `WebxUi\*` (`HistoryRecorded`, `StoredContentRewritten`, …) — по списку из конфига, не wildcard `*` | имя, число                                                                                               |
| `log`      | `MessageLogged`                                                                                                          | уровень, сообщение, контекст (маска), исключение — класс, сообщение, файл:строка                         |
| `memory`   | `memory_get_peak_usage(true)` на выходе                                                                                  | пик                                                                                                      |

**Пределы** (конфиг `webx-debug.limits`): запросов — 1000 (дальше только счёт и время), длина
значения — 500 символов, длина SQL — 10 000, обращений к кешу — 2000, записей лога — 200. Отчёт
сверх предела помечается `truncated`.

**Накладные расходы.** Сбор не бесплатен: `debug_backtrace` на каждый запрос, событие на каждый
блок, `View::creator` на каждый вид. Цель — не больше 10–15 % ко времени ответа на странице из
100 запросов и 200 блоков; полоса показывает собственную цену отдельной строкой («collector:
N ms»), а время отрезков в отчёте — как намерено, без вычета. Счёт запросов от сбора не меняется:
сборщики к базе не ходят (запись отчёта — после отправки ответа, §9).

## 6. Шкала времени

Отрезки (вложенные, у каждого — начало и длительность от `LARAVEL_START`):

| Отрезок         | Откуда                                                                                 |
| --------------- | -------------------------------------------------------------------------------------- |
| `boot`          | `LARAVEL_START` → `StartCollecting`                                                    |
| `middleware`    | `StartCollecting` → `RouteMatched`                                                     |
| `resolve`       | `routing`: `Resolver::resolve()` до `hand()` — событие `Resolving`/`Resolved` (§6.1)   |
| `handler`       | `hand()` → возврат `RouteHandler::handle()` (тип обработчика в подписи)                |
| `render`        | первый `creating:*` вида страницы → конец рендера                                      |
| `region:<name>` | `Regions::render()`                                                                    |
| `block:<key>`   | `Renderer::evaluate()` — точка, через которую проходит каждый блок (`one()` и `tag()`) |
| `widgets`       | `Widgets::finish()` на `RequestHandled`                                                |
| `terminate`     | `RequestHandled` → сборка отчёта                                                       |

Запросы показываются точками на шкале; клик по отрезку фильтрует вкладку SQL этим окном.

### 6.1. События-точки в наших пакетах

Новые события в пакетах, которые не знают о `module-debug`, с одним правилом: **создаётся и
отправляется, только если есть слушатель** —
`if ($this->events->hasListeners(BlockRendering::class)) { … }`. Без пакета или без сбора
слушателей нет, цена — проверка массива.

| Пакет           | Событие                                                                   | Где                                                                                            |
| --------------- | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `routing`       | `Resolving(path)`, `Resolved(Resolution)`                                 | `Resolver::resolve()` в начале, `hand()` перед `RouteHandler::handle()`                        |
| `module-blocks` | `RegionRendering(name)`, `RegionRendered(name, source)`                   | `Regions::render()`; `source` — дерево, запасной вид или пусто                                 |
| `module-blocks` | `BlockRendering(BlockContext)`, `BlockRendered(BlockContext, ?Throwable)` | вокруг `Renderer::evaluate()`                                                                  |
| `cache`         | `GroupRead(name, depends, source: memo\|store\|miss)`                     | `CacheGroups::remember()`/`get()`: мемо-попадания хранилище не видит, без события их не счесть |

Существующее `BlockDrawn` (рисование одного блока для панели и MCP) не трогается.

## 7. Место вызова

Для каждого запроса — **первый кадр стека вне фреймворка и вне самого сборщика**:
`debug_backtrace(DEBUG_BACKTRACE_IGNORE_ARGS, 40)`, пропускаются `vendor/laravel/*`,
`vendor/illuminate/*`, остальной `vendor/*`, кроме `vendor/webx-ui/*` (это и есть «пакет/модуль»),
и `WebxUi\Debug\*`. Показывается:

- `webx-ui/module-blog · src/Feed.php:84` — для пакета (путь от корня пакета; в монорепе симлинк
  `vendor/webx-ui/*` раскрывается в `php/packages/*`);
- `app/Http/Controllers/Foo.php:12` — для кода сайта;
- **скомпилированный Blade** (`storage/framework/views/*.php`) переводится в исходный вид по
  строке `/**PATH … ENDPATH**/` в конце файла: `theme-default · views/layouts/app.blade.php`;
- **скомпилированный шаблон блока** (`TemplateCompiler::path()`) — в тип блока: `block hero
(type v12)`, со ссылкой на тип в панели.

Плюс подпись ближайшего блока или региона со стека сборщика `blocks` — так повтор внутри
карточки списка сразу виден как «в блоке `cards`».

## 8. Блоки и шаблоны

- **Дерево отрисовки:** регион → блок → вложенные (`wx-blocks`, элементы повторителей), для
  каждого — ключ, тип, версия типа, время (своё и с детьми), запросы (свои и с детьми), признак
  «из черновика» (предпросмотр) и ошибка, если блок упал и нарисовался запасной вид.
- **Откуда тип блока:** колонка источника темы у `blocks` (`webx:theme:sync`, THEMES §9.2) —
  слой темы или «сайт» (тип заведён в панели).
- **Откуда вид Blade:** владелец файла по той же логике, что `ThemeReport::views()` в
  `webx:theme:show` — первый в цепочке (сайт → слои → модули) и кого он перекрыл. Отчёт хранит
  только итог, повторный разбор не делается: цепочка берётся из `ThemeChain`, файл — из
  `creating:*`.
- **Ссылки:** «Open in panel» у блока страницы и у региона — тем же реестром `SiteBar`
  (`EntityLink::edit` записи + ключ блока; регион — его экран), с правом **на запись**, как у
  панели сайта; без права ссылки нет. Тип блока — экран типа в конструкторе (`blocks.view`).

## 9. Хранение отчётов

- **Где:** хранилище кеша `webx-debug.store` (по умолчанию — хранилище сайта), ключ
  `webx:debug:<id>`, TTL `webx-debug.ttl` — 10 минут. Отдельной таблицы и миграции нет; чистка —
  TTL хранилища (на `database` просроченное подметает `webx:cache:prune`, кеш §8).
- **id** — 26 символов случайного ULID; в отчёте — id администратора, который его собрал.
- **Когда пишется:** в `terminate` (после отправки ответа), сжатый `gzdeflate` JSON. Запись
  отчёта не попадает в него самого и не задерживает страницу.
- **Сколько:** у администратора не больше `webx-debug.keep` (20) последних — список id в записи
  `webx:debug:index:<admin>`; старые удаляются при записи нового.
- **Выдача:** `GET {api_path}/debug/reports/{id}` в группе API панели (`cms.auth`,
  `cms.can:debug.view`), только если `user_id` отчёта — текущий администратор; чужой или
  истёкший — 404 (не 403: id не подтверждается). `no-store`. Список «мои последние» —
  `GET …/debug/reports` (id, адрес, время, сводка) — для вкладки истории в полосе (§10).
- **На странице** (`data-wx-debug` на теге загрузчика) — только id, адрес API и сводка:
  число запросов, время SQL, время ответа, пик памяти, число повторяющихся форм, медленных
  запросов, ошибок лога.

## 10. Маскирование

Маска — `••••` вместо значения, длина не раскрывается.

- **Значения запросов:** по имени колонки, которой значение присваивается или с которой
  сравнивается (`"password" = ?`, `set "remember_token" = ?`, вставка с перечнем колонок) —
  колонки из `webx-debug.mask.columns` (по умолчанию `password`, `remember_token`, `token`,
  `secret`, `api_key`, `access_token`, `refresh_token`, `*_secret`, `*_token`); таблицы целиком из
  `webx-debug.mask.tables` — значения запросов к `sessions`, `cache`, `cache_locks`, `oauth_*`,
  `personal_access_tokens`, `jobs` (в них сериализованные полезные нагрузки) маскируются все.
  Неразобранная форма запроса — значения показываются; список дополняется сайтом.
- **Заголовки** запроса и ответа: `Authorization`, `Cookie`, `Set-Cookie`, `X-CSRF-TOKEN`,
  `X-XSRF-TOKEN`, `Proxy-Authorization` + `webx-debug.mask.headers`. У cookie показываются имена,
  не значения.
- **Сессия:** только ключи, значения — для `locale`, флагов согласия и `url.intended`; `_token`,
  `login_*`, `password_hash_*` — маска.
- **Http-клиент:** query-параметры и заголовки по тем же спискам; тело не хранится.
- **Лог и исключения:** контекст по ключам из того же списка.

## 11. Полоса: разметка и поведение

### 11.1. Вставка

Слушатель `RequestHandled` пакета, после проверки §3.1, перед последним `</body>` ставит одну
строку — рядом с тегом панели сайта, если он есть, и независимо от него:

```html
<script
  type="module"
  src="/cms/_debug/bar.{hash}.js"
  data-wx-debug='{"id":"01J…","api":"/api/cms/debug/reports","locale":"ru","theme":"dark","words":{…},"summary":{…}}'
></script>
```

Ответ получает `Cache-Control: private, no-store`, `Vary: Cookie`, без `Content-Length` — как с
панелью сайта (одно и то же можно ставить дважды). Загрузчик — `module-debug/resources/js/debug-bar.js`,
отдаётся PHP с хешем содержимого и токенами на `:host`, как `SiteBar\Loader` (общий код вписывания
токенов — вынести из `Loader` в `module-admin`, публичный API не меняется).

### 11.2. Вид

- **Свёрнута:** строка-сводка во всю ширину снизу, высота 28 px:
  `SQL 42 · 18.3 ms · ×3 repeated · 1 slow │ 142 ms │ 12.4 MB │ ⚠ 1 │ ▴`. Цифры повторов, медленных
  и ошибок — тинтами `--wx-*-warning`/`danger`, если не ноль.
- **Раскрыта:** панель снизу высотой 40 % окна (тянется за верхнюю кромку мышью и пальцем, от 120
  px до 90 % окна), вкладки (§12) и строка поиска.
- **Скрыта:** личный выключатель — кружок 28 px в левом нижнем углу; клик возвращает строку.
- Поверх страницы, `position: fixed`, ничего не сдвигает: отступ снизу у `body` сломал бы
  фиксированные подвалы и `100vh`-разметку. Последние 28 px страницы прикрывает строка — её можно
  скрыть.
- Слой — `--wx-z-index-overlay` − 2: ниже ящика и язычка панели сайта и рамок блоков.
- Shadow DOM одного корня `<div data-wx-debug-root>` с `:host{all:initial}`, токены панели на
  `:host`, тема — `data-theme` администратора (светлая и тёмная). Полоса не читает и не пишет
  cookie и DOM сайта вне своего корня.
- Узкое окно (< 640 px): строка-сводка сокращается до `SQL 42 · 142 ms · ⚠`, раскрытая панель — во
  всю высоту, вкладки прокручиваются вбок; таблицы — карточками.

### 11.3. Рядом с панелью сайта

Ящик панели сайта — справа, 380 px, во всю высоту. Загрузчик панели сайта при открытии и
закрытии ящика шлёт `window` событие `wx-bar:layout` с `{ right: 380 | 0 }` (одна строка в
`site-bar.js`; если ящик во всю ширину — `right: 0` и полоса уходит под него). Полоса занимает
`left: 0; right: <right>px`. Панель сайта может открыться раньше полосы (ящик раскрыт с прошлого
раза), поэтому та же правка ставит на корень `data-wx-bar-root` атрибут `data-open`, и полоса
читает его при старте. Сегодня ни события, ни атрибута в `site-bar.js` нет — это две строки DB3. Язычок панели сайта (28×48 у правой кромки на средней высоте) с полосой не
пересекается; при высоте раскрытой полосы больше половины окна язычок остаётся над ней по слою.

### 11.4. Память

`localStorage['wx-debug']` в `try`/`catch`: раскрыта/свёрнута/скрыта, высота, вкладка, сортировка
SQL. Пишется только у администратора.

## 12. Вкладки

Детали грузятся одним `fetch` при первом раскрытии (свёрнутой полосе хватает сводки).

1. **SQL.** Таблица: №, SQL с подставленными значениями (подсветка ключевых слов), время,
   соединение, место вызова (§7). Сверху — итог (число, общее время, доля от ответа). Повторы
   **сгруппированы по форме** (та же нормализация, что `QueryTally::shape()`: `in (?, ?, ?)` любой
   длины — одна форма; функцию вынести в общий класс, тестовый хелпер её переиспользует) и
   подсвечены, если форма повторилась ≥ `webx-debug.repeat` (3) раз — «likely N+1», с местом
   вызова. Медленные (≥ `webx-debug.slow_ms`, 50 мс) — выделены. Сортировка по порядку и по
   времени; фильтр по тексту и по месту вызова; «Copy» — SQL со значениями (маска остаётся маской);
   у `select` — «Copy EXPLAIN». Транзакции — отступом.
2. **Timeline.** Шкала §6: вложенные полосы, запросы точками, пик памяти, своя цена сборщика.
3. **Blocks.** Дерево §8: регионы и блоки, время и запросы, тип и слой темы, виды Blade с
   владельцем по цепочке, ссылки в панель.
4. **Cache.** Группы версионного кеша: версия на конец запроса, сколько раз прочитана, из мемо /
   хранилища / промах, какие записи (`remember`-имена) читались через неё; отдельно — обращения к
   хранилищу по ключам вне `webx:`. Промахи на тёплой странице подсвечены: это либо первый заход
   после сброса, либо ключ, который не кешируется.
5. **Request.** Маршрут (имя, URI, middleware), что нашёл резолвер (`Resolution`: тип, id, язык,
   хвост, алиас), обработчик, тема и её цепочка, вид страницы, статус, заголовки ответа и запроса
   (маска), язык и откуда взят, согласие на cookies (виджет согласия), ключи сессии (маска).
6. **Other.** Исходящие HTTP, задания в очередь, письма, наши события, записи лога и исключения,
   предупреждения (`deprecated` из лога).
7. **History** (добавлено агентом): последние отчёты этого администратора (§9) — открыть отчёт
   предыдущей страницы (например, POST формы с редиректом: у редиректа полосы нет, а отчёт у
   следующей страницы есть только свой). Сбор на не-HTML ответах при этом не включается — в
   историю попадают только страницы; расширить — развилка 6.

## 13. MCP `debug_page`

- Модуль `debug`, инструмент `page`: `Tool::read('page', …, scope: 'debug:read', permission:
'debug.view')`. На проде провайдер его не регистрирует — в списке инструментов его нет.
- Вход: `url` — путь своего сайта (хост, схема, `//` — отказ, как `site-bar/context`),
  `locale?`, `include?` — какие вкладки отдать (по умолчанию все, кроме `views` и `log`), `cold?` —
  перед запросом забыть мемо (кеш хранилища не трогается).
- **Как получает отчёт:** настоящим HTTP-запросом к своему сайту, как краулер аудита
  (`module-audit` `SiteClient`: настоящий `Host`, `resolve_to` для стенда), с заголовком
  `X-Webx-Debug: <токен>`. Токен — одноразовый, 60 секунд, подписан ключом приложения и несёт id
  администратора, от имени которого работает агент; `StartCollecting` принимает его вместо cookie,
  проверка на выходе — по токену, а не по сессии. Ответ сайта — как у гостя (агент не входит в
  панель), отчёт сохраняется и читается инструментом из хранилища.
  Почему не запрос внутри процесса (`app()->handle()`): синглтоны, мемо кеша, `Renderer::flush()` и
  уже загруженное приложение дают другие цифры, чем видит человек, а смысл инструмента — те же
  цифры. Развилка 4.
- Выход — тот же JSON, что API отчёта (`version` формата, `summary`, `queries`, `repeated`,
  `timeline`, `blocks`, `cache`, `request`, `other`), плюс `id`, чтобы человек открыл его в полосе
  (`/?wx-debug=<id>` открывает полосу с этим отчётом, если он его).
- В `AGENTS.md` пакета и `module-admin` — «Check your work»: при оптимизации смотреть
  `debug_page` до и после.

## 14. Тесты и проверка

PHP (Testbench), в `module-debug/tests`:

- **гость получает ответ байт в байт** таким же, как без пакета (тело и заголовки), и **тем же
  числом запросов** (`assertQueriesWithin` с бюджетом из прогона без пакета); слушателей
  `QueryExecuted` и событий §6.1 после его запроса нет;
- **прод** (`APP_ENV=production`), администратор с правом и cookie: ни тега, ни заголовков, ни
  маршрутов `debug/*` (404), ни инструмента в списке MCP;
- без права, неактивный, `WEBX_DEBUGBAR=false`, JSON, редирект, 404, `_preview/*`, iframe, файл,
  без `</body>` — полосы нет; подделанная cookie `wx_debug` гостем — ответ байт в байт;
- администратор с правом: один тег перед `</body>`, `no-store`, сводка совпадает с отчётом;
  запросы до `StartSession` в отчёте есть;
- отчёт: чужой id — 404, истёкший — 404, свой — 200; маска значений, заголовков и сессии;
  пределы и `truncated`;
- место вызова: пакет, код сайта, скомпилированный Blade, шаблон блока;
- повторы: N+1 из фикстуры (список с обложкой без `with`) — форма с числом и местом;
- события §6.1 без слушателя не создаются (счётчик конструктора);
- MCP: отчёт по адресу, чужой хост — отказ, одноразовый токен второй раз — без сбора.

Браузер (Playwright, на сайте на пакетах монорепы, не jsdom — ловушка №1): строка-сводка,
раскрытие, перетаскивание высоты, вкладки, ширина 375 px, светлая и тёмная, рядом с открытым
ящиком панели сайта (полоса не под ним и не поверх), стили темы не протекают в полосу и обратно,
тема с фиксированным подвалом.

## 15. Пакет и регистрация

`php/packages/module-debug` (`webx-ui/module-debug`), зависит от `module-admin`, `module-auth`,
`mcp`, `cache`, `routing`; `module-blocks` и `themes` — `suggest` (без них нет вкладки блоков и
цепочки). Регистрация — по `CLAUDE.md` §5: четыре места в `php/` и реестр
`WEBX_UI_COMPOSER_PACKAGES.md`; из «четырёх молчащих мест раздела панели» — только
`Setup\Catalogue` (модуль с правом, без пунктов меню и экранов); `extra.webx.npm` и
`extra.webx.panel` не нужны — npm-пары нет. В скелет `php/site` — как обычный пакет; на проде
установленный пакет ничего не делает (§3.1).

Конфиг `webx-debug.php`: `enabled`, `store`, `ttl`, `keep`, `slow_ms`, `repeat`, `limits`,
`mask.{columns,tables,headers}`, `events`.

Гайд — `apps/docs/guide/debug-bar.md`; `AGENTS.md` пакета по `WEBX_UI_AGENT_DOCS.md`.

## 16. Решения на утро

Развилки, где выбран самый осторожный вариант; альтернативы — человеку.

1. **Пакет.** Выбрано: отдельный `webx-ui/module-debug` без npm-пары. Причины: сайт может не
   ставить его вовсе, право и MCP-модуль `debug` — свои (`debug_page` и так требует модуля с id
   `debug`), продовая сборка с ним ничего не регистрирует. Альтернатива: внутри `module-admin`
   рядом с панелью сайта (как SB1 решил для панели сайта) — меньше регистрации, но код сборщиков
   едет на каждый сайт и модуль `debug` пришлось бы объявить из каркаса.
2. **Интерфейс деталей.** Выбрано: всё в ES-модуле без зависимостей в Shadow DOM (как
   `site-bar.js`, ~1,5 тыс. строк). Альтернатива: строка-сводка в загрузчике, детали — экран
   панели в iframe на компонентах ядра (`WxTable`, вкладки, фильтры) — меньше ручного UI, но нужна
   npm-пара `@webx-ui/module-debug` (первую версию публикует человек), бандл панели грузится на
   каждое раскрытие, и полоса перестаёт работать, когда сломана сборка панели — а отладка нужна
   именно тогда.
3. **Начало сбора.** Выбрано: метка `wx_debug` в cookie + проверка на выходе (§3.2).
   Альтернатива проще: включать сбор только в route-middleware после `StartSession` — без cookie,
   но без запросов глобальных middleware, сессии и пользователя в отчёте.
4. **MCP — через HTTP.** Выбрано: настоящий запрос к своему сайту с одноразовым токеном (те же
   цифры, что у человека). Альтернатива: `app()->handle()` внутри процесса — работает там, где сайт
   не достаёт сам себя по сети, но цифры другие. Если на стендах окажется, что сайт себя не
   видит, — `resolve_to` аудита, иначе запасной путь внутри процесса с пометкой `in_process`.
5. **Право.** Выбрано: `debug.view` не получает ни одна роль, по умолчанию — только суперадмин.
   Альтернатива: выдавать роли «разработчик», если она появится в наборе ролей по умолчанию.
6. **Не-HTML ответы.** Выбрано: не собирать. Альтернатива: собирать и POST/JSON сайта (формы,
   виджеты) в историю (§12, вкладка History) — полезно для форм, но значения POST — самые
   чувствительные данные посетителей; если да — маска полей формы целиком.
7. **`Server-Timing`.** Не выбрано: заголовок с отрезками шкалы для DevTools браузера —
   администратору безвреден (ответ и так `no-store`), но это ещё один след в ответе. Добавить
   одной строкой в DB1, если человек хочет.
8. **Хранилище отчётов.** Выбрано: кеш сайта с TTL. Альтернатива: файлы в
   `storage/framework/webx-debug` — не нагружают `database`-кеш записью сотен килобайт, но не
   видны с соседнего сервера за балансировщиком.
9. **Отступ под строку.** Выбрано: полоса поверх страницы, низ прикрыт 28 px. Альтернатива:
   `padding-bottom` у `body` на высоту строки — видно всю страницу, но это правка DOM сайта и
   поломка фиксированных подвалов.
