# `webx-ui/module-notifications` — каналы уведомлений: Telegram, e-mail, шаблоны — спецификация

Статус: спроектировано, решения человека внесены (§2, решения 11–15; §17 закрыт). Пакеты —
`php/packages/module-notifications` (namespace `WebxUi\Notifications`) и
`packages/module-notifications` (`@webx-ui/module-notifications`). Идентификатор модуля —
`notifications`, в панели раздел «Уведомления» (Notifications), таблицы — `notifications_*`.
Эталон устройства пакета — `module-faq` ([`WEBX_UI_MODULE_FAQ.md`](WEBX_UI_MODULE_FAQ.md)), форма
спеки — [`WEBX_UI_MODULE_SNIPPETS.md`](WEBX_UI_MODULE_SNIPPETS.md). Соседние спеки: заявки —
[`WEBX_UI_MODULE_INBOX.md`](WEBX_UI_MODULE_INBOX.md) (§9 письма, §2.19 обработчики), задачи —
[`WEBX_UI_MODULE_TASKS.md`](WEBX_UI_MODULE_TASKS.md) (§6a Telegram), журнал —
[`WEBX_UI_HISTORY.md`](WEBX_UI_HISTORY.md), экраны — [`WEBX_UI_SCREENS.md`](WEBX_UI_SCREENS.md),
MCP — [`WEBX_UI_MCP_ACCESS.md`](WEBX_UI_MCP_ACCESS.md).

Один механизм уведомлений для всех модулей. Администратор один раз заводит **канал** — куда и
как слать (Telegram-бот и чаты, почта и адреса) и каким текстом; модули-потребители объявляют
свои **события** и хранят только список каналов. Первый потребитель — Inbox: «новая заявка ушла
во все выбранные каналы». Всё, что умеет панель, умеет и MCP.

## 1. Границы

В модуле:

- реестр **провайдеров** (`telegram`, `email` из коробки; свой — без форка, §4);
- реестр **событий**, которые объявляют потребители (§5);
- **канал** — креденшелы (зашифрованы), получатели, шаблон, необязательное событие, вкл/выкл,
  копия (§3);
- шаблоны `{{var}}` без исполнения кода, с экранированием под провайдера (§7);
- **отправка** через очередь с повторами, без воркера — после ответа (§8);
- **журнал отправок** и его чистка командой (§9);
- раздел панели: каналы, форма канала, «Найти чаты», «Отправить тест», журнал (§10);
- MCP: инструменты и ресурсы (§12); диагностика в `webx:doctor` (§13);
- событие `inbox.submission` и поле «Уведомлять через» в форме Inbox (§15).

Не в модуле:

- **входящие** — кнопки и ответы в Telegram, вебхук бота: модуль только отправляет. «Найти
  чаты» читает `getUpdates` разово (§6.3) и вебхук не ставит;
- **рассылки и маркетинг** — канал шлёт одно сообщение на одно событие;
- **другие провайдеры** (Slack, VK, вебхук, SMS) — контракт готов (§4), реализаций нет;
- **перевод `module-tasks`** на каналы — только описание, как перевести потом (§16.3);
- **автоответ формы как отдельная функция** — это просто канал, настроенный на адресата события
  (решение 12), своей кнопки «автоответ» модуль не заводит.

## 2. Принятые решения (не переоткрывать)

Из постановки задачи:

1. **Шаблон живёт только в канале.** У события нет «шаблона по умолчанию», который правят;
   у события есть **пример шаблона** (`sample`), которым заполняется новый канал с этим событием.
2. **Канал без события — универсальный:** любой потребитель может его выбрать; неизвестная
   переменная подставляется пустой с пометкой в журнале. Канал с событием предлагается только
   потребителю этого события, редактор подсказывает и проверяет его переменные.
3. **Креденшелы шифруются и не возвращаются никогда:** ни в панели (там «••••, заменить»), ни в
   MCP (только запись), ни в журнале изменений (маска).
4. **Отправка — через очередь, три попытки с паузой;** без воркера — после ответа; `webx:doctor`
   предупреждает.
5. **Отдельное право модуля, по умолчанию — только у суперадмина.**
6. **Шаблон не исполняет кода:** не Blade из базы; движок — Mustache без лямбд,
   вложенных шаблонов и смены разделителей (§7, решение 16).

Принятые этой спекой (обоснование — в разделах):

7. **Провайдер выбирается при создании канала и потом не меняется** — у Telegram и e-mail
   разные креденшелы, получатели и разметка; смена — это новый канал (копия не поможет, §3.4).
8. **Одна строка журнала — один получатель одного канала;** повтор шлёт только тем, кому не
   ушло (у `module-tasks` повтор уходит во все чаты — здесь так не делаем).
9. **Привязка у потребителя — список id каналов** в его собственных данных (у Inbox — в
   `options` формы); своей таблицы привязок модуль не заводит.
10. **Модуль не обязателен потребителю:** Inbox работает и без `module-notifications` — тогда
    поля «Уведомлять через» нет, а письма уходят по-старому (§15).

Решения человека при приёмке спеки (16.10.2026) — главнее всего выше:

11. **Живых сайтов нет, совместимость не нужна.** Встроенное письмо Inbox (получатели формы,
    очередь, `inbox_notify`) остаётся **навсегда** как базовый механизм простых сайтов и работает
    параллельно с каналами (вариант A, §15.4) — без команды и кнопки «перевести в канал» и без
    планов удаления. Зависимость Inbox → notifications мягкая; Inbox всегда бросает
    документированное Laravel-событие о заявке.
12. **Адресат из события.** Событие объявляет **адресатов** — переменные, значение которых —
    адрес (e-mail посетителя из поля заявки, позже e-mail покупателя заказа). Получатели канала —
    фиксированные и/или адресаты события (§5, §6). Автоответ посетителю — канал, настроенный на
    адресата события. Заложено в модель, API отправки, панель и MCP.
13. **Шаблон переводимый.** Тема и тело — localized-поля (`HasTranslations`, карта языков). Язык
    отправки приходит от события (язык, на котором оформлена заявка или заказ), запасной —
    основной язык сайта, затем любой заполненный. Каналу достаточно одного языка.
14. **Права — два:** `notifications.view` и `notifications.manage`. Журнал — 90 дней. Копия
    переносит креденшелы зашифрованными. Повтор заявки в окне дубля в каналы не шлётся. Тело
    e-mail — текст в рамке письма. Готовые `{{fields}}` и `{{field.<name>}}` остаются для быстрой
    настройки (циклы — решение 16). Супергруппа —
    ошибка с новым id в журнале. Несекретное — `options`, секретное — `credentials`. Вне
    `production` шлём, с баннером в разделе.
15. **Правка `module-admin`** — `RecordsHistory::historyMasked()` — принята.

Решение человека 16.10.2026 (этап 2) — главнее решения 6 в прежней редакции:

16. **Шаблонизатор — Mustache** (`mustache/mustache`, сервер). Не свой синтаксис и не Blade
    (Blade из базы — выполнение кода на сервере). Поддерживаются `{{var}}` с экранированием под
    провайдера, секции-списки `{{#items}}…{{/items}}` (событие объявляет списки и поля их
    элементов), секции «есть/нет» `{{#var}}` / `{{^var}}`. Вложенные шаблоны и смена
    разделителей — отказ. Тройные `{{{var}}}` и `{{&var}}` приравнены к обычным. Шаблон
    проверяется при сохранении: синтаксис и, если выбрано событие, переменные и списки (§7).

Словари пакета — пространство `webx-notifications::` (как `webx-snippets::`), конфиг —
`config/webx-notifications.php`; где ниже написано `notifications::`, читать так.

## 3. Канал

### 3.1 Схема

```
notifications_channels
  id            bigint pk
  name          string(160)               -- для администратора
  provider      string(32) index          -- ключ провайдера (§4); не FK: провайдеры в коде
  event         string(64) null index     -- ключ события (§5); null — универсальный канал
  credentials   text null                 -- cast encrypted:array (§11); $hidden; только секретное
  options       json null                 -- несекретные настройки провайдера (отправитель, хост SMTP)
  recipients    json                      -- получатели в форме провайдера (§6) и адресаты события
  subject       json null                 -- тема по языкам {en: …}; только у провайдеров с темой
  template      json                      -- шаблон по языкам {en: …} (§7, решение 13)
  enabled       boolean default false     -- выключенный канал не шлёт ничего, кроме теста
  copied_from   bigint null               -- id канала-источника копии (§3.4), без FK
  deleted_at    timestamp null            -- корзина, как у FAQ
  timestamps
```

### 3.2 Модель

`WebxUi\Notifications\Models\Channel` — `RecordsHistory`, `SoftDeletes`
(`php/packages/module-admin/src/History/RecordsHistory.php`).

- `credentials` — cast `encrypted:array` и `$hidden`. `RecordsHistory::followsInHistory()`
  (`RecordsHistory.php:150-172`) пропускает и `$hidden`, и любой cast на `encrypted` — значит,
  без доработки журнал о смене токена **молчит**. Постановка просит маску: в `module-admin`
  добавляется точка расширения `historyMasked(): list<string>` рядом с `historyKeepsFull()`
  (`RecordsHistory.php:86`) — для таких полей журнал пишет `••••` → `••••` с пометкой
  «изменено», если зашифрованное значение поменялось, и ничего, если нет. `Channel` возвращает
  `['credentials']` (§14).
- `enabled` по умолчанию `false`: новый и скопированный канал ничего не шлёт, пока его не
  включили. Тест (§8.5) шлёт и через выключенный канал — им проверяют перед включением.
- Удалённый (в корзине) канал не шлёт; id в данных потребителя остаётся и молча пропускается
  при отправке, а в журнал пишется строка `skipped` с причиной `channel_deleted` (§9) — чтобы
  «почему не пришло» имело ответ. Восстановление из корзины возвращает канал во все привязки.

### 3.3 Правила значений

`WebxUi\Notifications\Channels\ChannelValues` — одни правила для панели и MCP (как
`Panel\FormInput` в Inbox, INBOX §14):

- `name` — обязательно, ≤160.
- `provider` — зарегистрированный ключ (§4); при правке — только тот же (решение 7).
- `event` — зарегистрированный ключ (§5) или пусто. Событие, которое пропало (потребитель
  удалён), у существующего канала сохраняется, канал работает как универсальный, панель и
  доктор подсвечивают «событие не объявлено».
- `credentials` — по правилам провайдера; при правке пустое секретное поле **сохраняет**
  прежнее значение, `forget: ["token"]` — стирает (как `forget_token` у задач,
  `module-tasks/src/Http/Controllers/SettingsController.php:40-63`).
- `recipients` — по правилам провайдера (§6), не пустой список для включённого канала.
- `subject` — обязательно для e-mail, одна строка, ≤255 после подстановки примера.
- `template` — обязательно, ≤16 000 символов. С событием — каждая `{{var}}` должна быть
  переменной события (иначе отказ под `template` с названием переменной и списком допустимых);
  без события — любая. Разметка проверяется провайдером (§6.1: допустимые теги Telegram).
- **Включённый канал** должен быть полным: креденшелы заданы (у e-mail в режиме «почта сайта» —
  не нужны), получатели есть. Иначе отказ под полем — «нельзя включить, пока нет токена».

### 3.4 Копия канала

«Создать копию» — новый канал с теми же `provider`, `event`, `recipients`, `subject`,
`template`, именем «<имя> (copy)», `enabled: false`, `copied_from = <id>`.

Креденшелы — **переносятся зашифрованными на сервере** (рекомендация, §17 вопрос 1): копия
делается одним запросом `POST channels/{id}/copy`, значение не покидает сервер, ни панель, ни
агент его не видят. Форма копии показывает «Токен скопирован из „<имя>“ — замените, если нужен
другой бот». Альтернатива — копия без креденшелов, с вводом заново; она безопаснее против
ошибки «тест ушёл не тем ботом», но превращает копию в полуфабрикат, который нельзя включить.

## 4. Провайдер

### 4.1 Контракт

```php
namespace WebxUi\Notifications\Contracts;

interface Provider
{
    public function key(): string;                 // 'telegram'
    public function label(): string;               // ключ словаря: 'notifications::providers.telegram'
    public function icon(): string;                // иконка ядра

    /** Поля креденшелов: имя → описание (тип, секретное ли, правила, подсказка). */
    public function credentials(): array;          // list<CredentialField>
    /** Правила списка получателей и его форма для экрана и MCP. */
    public function recipients(): RecipientShape;
    /** Есть ли у сообщения тема (e-mail — да, Telegram — нет). */
    public function hasSubject(): bool;

    /** Проверить шаблон: допустимая разметка и т. п. Ошибки — под `template`. */
    public function checkTemplate(string $template): array;     // list<string>
    /** Экранировать значение переменной под формат провайдера (§7.3). */
    public function escape(string $value): string;

    /** Отправить одному получателю. Неудача — DeliveryFailed (§8.3). */
    public function send(Message $message, Credentials $credentials, Recipient $to): void;
    /** Проверить креденшелы без отправки: getMe у Telegram, соединение SMTP у e-mail. */
    public function check(Credentials $credentials): CheckResult;
}
```

- `Message` — уже отрендеренные `subject?`, `body`, плюс `plain` (тот же текст без разметки,
  для e-mail и для обрезки Telegram, §6.1). `Credentials` — расшифрованный массив, живёт только
  внутри задания отправки и `check()`; `__debugInfo`/`__serialize` маскируют значения, чтобы
  дамп и лог задания не унесли токен. `Recipient` — `{key, label}` (`key` — `chat_id` или адрес).
- `DeliveryFailed` несёт `message` (без секретов), `permanent: bool` (неверный токен, чат не
  найден — повторять бессмысленно) и `retryAfter: ?int` (429 Telegram).
- Дополнительные возможности — отдельными интерфейсами, чтобы контракт не рос:
  `Contracts\FindsRecipients` (`find(Credentials): list<FoundRecipient>`) — у Telegram это
  «Найти чаты» (§6.3); панель и MCP показывают кнопку/инструмент только провайдерам, которые его
  реализуют.

### 4.2 Реестр

`WebxUi\Notifications\Providers` — singleton, `register(Provider)`, `get(key)`, `all()`. Свои
провайдеры пакет `telegram` и `email` регистрирует в провайдере пакета; сторонний пакет или сайт —
так же, через `callAfterResolving(Providers::class, …)` (как `DoctorChecks` у сниппетов,
`module-snippets/src/SnippetsServiceProvider.php:44-46`). Канал с провайдером, которого больше
нет, не шлёт: строка журнала `skipped` / `provider_missing`, доктор — `warn`.

Поля креденшелов и получателей провайдер описывает узлами экрана (§10.3), а не своим Vue:
провайдер без npm-половины работает в панели сразу. Особые кнопки («Найти чаты») — типы узлов
npm-пакета модуля.

## 5. Событие

```php
NotificationEvents::register(new EventDefinition(
    key: 'inbox.submission',
    label: 'webx-inbox::notifications.event',           // «Новая заявка с формы»
    module: 'inbox',                                    // чей; для панели и прав
    variables: [
        new Variable('form', 'webx-inbox::notifications.vars.form', example: 'Contact us'),
        // …
    ],
    sample: ['subject' => '…', 'template' => '…'],      // чем заполнить новый канал (§2, решение 1)
    url: fn (array $vars) => $vars['submission_url'] ?? null, // ссылка «открыть» в журнале
));
```

- Ключ — `<модуль>.<что>`, `[a-z0-9_.]+`, ≤64.
- **Адресаты** (решение 12) — переменные с `address: 'email'` (или `'telegram'` — `chat_id`):
  `new Variable('reply_to', '…', example: 'visitor@site.test', address: 'email')`. Канал с
  этим событием может назвать адресата получателем — `{variable: "reply_to"}`; провайдер
  принимает только адресатов своего вида. Пустое или негодное значение в момент отправки —
  строка журнала `skipped` / `no_address`.
- **Язык** отправки — аргумент `locale` у `send()` (§8.1); событие без языка — основной язык
  сайта.
- `variables` — имя, описание (ключ словаря), пример значения. Пример идёт в тест (§8.5) и в
  подсказку редактора. Имя — `[a-z0-9_]+`, допускается одна точка для семейства
  (`field.<name>`, объявляется как `field.*` с описанием «значение поля по машинному имени»).
- Объявление — в провайдере пакета-потребителя, под `class_exists(NotificationEvents::class)`:
  потребитель не требует модуль (решение 10).
- **Списки** (решение 16) — переменная с полями элемента:
  `new Variable('items', '…', fields: ['name' => '…', 'qty' => '…', 'price' => '…'], example: [['name' => 'Tea', 'qty' => '2', 'price' => '3.00']])`.
  Имя списка — без точки, адресатом список не бывает; пример — список строк с этими полями.
  Шаблон перебирает его секцией `{{#items}}…{{/items}}` (§7.2).
- Событие без канала — норма: потребитель зовёт `send()` с пустым списком, ничего не происходит.

## 6. Провайдеры из коробки

### 6.1 Telegram

**Креденшелы:** `token` (секретное). Проверка — `getMe` (`check()`, кнопка «Проверить» в
форме): ответ называет бота `@username`. Имя бота видно в форме и после сохранения — поле
`bot` ответа API, вычисляется `check()` и кешируется на час; сам токен не возвращается.

**Получатели:** список `chat_id` — число (`123456789`, группы и супергруппы — отрицательные,
`-100…`) или `@username` публичного канала. Каждый с необязательной подписью (`{id, label}`),
подпись — из «Найти чаты» или руками.

**Отправка:** `POST {api}/bot{token}/sendMessage` с `chat_id`, `text`, `parse_mode: HTML`,
`link_preview_options.is_disabled: true`. Клиент — `Illuminate\Http\Client\Factory`, как у задач
(`module-tasks/src/Notifications/TelegramNotifier.php:33-67`); базовый адрес —
`config('webx-notifications.telegram.api')`, по умолчанию `https://api.telegram.org` (для тестов
и прокси), таймаут 10 с. Токен в тексте ошибки — `***` (как у задач).

**Разметка — HTML Telegram.** Шаблон пишет администратор, его теги — как есть; допустимы только
теги Telegram: `b strong i em u ins s strike del a[href] code pre blockquote tg-spoiler span.tg-spoiler`.
Другой тег или незакрытый — отказ под `template` при сохранении (`checkTemplate`), а не 400 от
Telegram в момент заявки. Значения переменных экранируются (`&`, `<`, `>`, `"` → сущности, §7.3).
У задач разметки нет вовсе (простой текст, `Notices::cut()` вычищает Markdown) — здесь HTML
нужен постановке, а экранирование значений снимает ту же проблему.

**Длина:** 4096 символов текста после разбора разметки. Отрисованное сообщение длиннее —
отправляется `plain` (без тегов), обрезанное до 4095 + «…»; в журнал — пометка `truncated`.
Резать HTML по символу нельзя: обрезанный тег — 400 от Telegram.

**Ошибки и лимиты:**

| Ответ Telegram                                    | Что делаем                                                                 |
| ------------------------------------------------- | -------------------------------------------------------------------------- |
| 401 Unauthorized                                  | `permanent` — «токен не принят Telegram»; повторов нет                     |
| 400 chat not found / 403 bot was blocked / kicked | `permanent` по этому получателю — «бот не в чате или его заблокировали»    |
| 400 group chat was upgraded to a supergroup       | `permanent`; в ошибке — `migrate_to_chat_id` из ответа: «новый id чата: …» |
| 400 can't parse entities                          | `permanent`; не должно случаться после `checkTemplate` — признак бага      |
| 429 Too Many Requests                             | повтор через `parameters.retry_after` (не через общую паузу)               |
| 5xx, таймаут, нет соединения                      | временная — повтор по §8.3                                                 |

Лимиты Telegram (≈1 сообщение в секунду в чат, 20 в минуту в группу, 30 в секунду всего) на
потоке заявок не достигаются; задания одного канала не распараллеливаются (§8.2), а 429
обработан. Автоматической замены `chat_id` при переходе в супергруппу нет (§17, вопрос 7).

### 6.2 E-mail

**Режимы креденшелов:** `mode` — `site` (по умолчанию: почта сайта, `config('mail.default')`,
креденшелов нет) или `smtp` (`host`, `port`, `encryption` — `tls`/`ssl`/нет, `username`,
`password` — секретное). SMTP канала — мейлер, собранный на лету `MailManager::build([...])`
(Laravel 13, `illuminate/*: ^13.0` в `module-admin/composer.json`), без правки `config/mail.php`.
`check()` — для `smtp` открыть и закрыть соединение транспорта; для `site` — `ok`, если
мейлер сайта не `log`/`array` (иначе предупреждение «почта сайта никуда не уходит»).

**Отправитель:** `from_address`, `from_name` — необязательные открытые поля канала в колонке
`options` (§3.1; в `credentials` они спрятались бы за маской без нужды — §17, вопрос 9). Там же
несекретные поля SMTP: `mode`, `host`, `port`, `encryption`, `username`. Пусто — `mail.from` сайта.

**Получатели** — та же форма, что у Inbox сегодня (`inbox_forms.options.recipients`,
`module-inbox/src/Models/Form.php:114`): `{admin_id}` — администратор панели (адрес берётся из
учётной записи и меняется вместе с ней; неактивный и удалённый пропускаются с причиной, как
`Mail\Recipients` Inbox, `module-inbox/src/Mail/Recipients.php`) и `{email}` — произвольный адрес.
Плюс `{variable}` — адресат события (решение 12). Одно письмо на получателя (адреса не видят
друг друга).

**Тема и тело:** тема — шаблон одной строкой (значения без экранирования, переводы строк
вырезаются). Тело — **текстовый шаблон**: письмо уходит `multipart` — `text/plain` как есть и
`text/html`, где текст экранирован, переводы строк — `<br>`, адреса `http(s)://` — ссылки, в
рамке пакета (`notifications::mail.frame`, публикуемая вьюха). HTML в шаблоне e-mail не
разрешается (§17, вопрос 4). `Reply-To` — переменная события, если событие её объявило
(`reply_to` у `inbox.submission`, §15.1).

### 6.3 «Найти чаты»

`Telegram\ChatFinder` (`FindsRecipients`): `GET {api}/bot{token}/getUpdates` с
`allowed_updates: ["message","channel_post","my_chat_member"]`, **без `offset`** — без него
Telegram не подтверждает обновления, и они остаются тому, кто их ещё читает. Из ответа —
уникальные чаты: `id`, `type` (`private`/`group`/`supergroup`/`channel`), подпись
(`title` или `first_name last_name`, `@username`). Панель показывает список с флажками,
выбранные добавляются в получателей.

- **Токен** — сохранённый токен канала (`channel`) или введённый в форме ещё до сохранения
  (`token`); во втором случае он идёт только в этот запрос и нигде не пишется.
- **У бота стоит вебхук** — `getUpdates` отвечает 409 «can't use getUpdates method while webhook
  is active». Вебхук **не снимаем** (бот может работать где-то ещё): ответ — «У этого бота
  настроен вебхук, Telegram не отдаёт обновления. Впишите chat_id руками или используйте
  отдельного бота». Тот же 409 бывает, когда бот кто-то читает long-polling'ом — слова те же.
- **Пусто** — Telegram хранит обновления 24 часа. Подсказка: «Напишите боту что-нибудь в личку
  или добавьте его в группу и напишите там, затем нажмите „Найти чаты“ ещё раз». В группе с
  режимом приватности бот видит своё добавление (`my_chat_member`) — этого хватает.
- Отправка не нужна: поиск ничего не пишет и не шлёт; в журнал отправок не попадает.

## 7. Шаблоны

Решение 16: шаблон рендерит `mustache/mustache` (`Templates\Template`). Сам Mustache кода не
исполняет. Лямбды выключены (`lambdas: false`), `strict_callables` включён. Значения — только
строки и списки строк, так что вызвать из шаблона нечего.

### 7.1 Синтаксис

| Запись                                   | Что делает                                                          |
| ---------------------------------------- | ------------------------------------------------------------------- |
| `{{name}}`, `{{ name }}`                 | значение через экранирование провайдера (§7.3)                      |
| `{{field.phone}}`                        | поле по машинному имени; точка — вложенность Mustache (см. ниже)    |
| `{{#items}}…{{/items}}`                  | список: тело — на каждую строку, внутри доступны поля строки (§7.2) |
| `{{#note}}…{{/note}}`                    | показать, если значение не пустое (`''` и `'0'` — пусто)            |
| `{{^note}}…{{/note}}`                    | показать, если значения нет или список пуст                         |
| `{{! комментарий }}`                     | не выводится                                                        |
| `{{{name}}}`, `{{&name}}`                | **приравнены к `{{name}}`** — неэкранированного вывода нет          |
| `{{>partial}}`, `{{<parent}}`            | отказ: вложенных шаблонов нет                                       |
| `{{=<% %>=}}`                            | отказ: разделители не меняются                                      |
| `{{%PRAGMA}}`, `{{$block}}`, `{{*name}}` | отказ: прагмы, блоки и динамические имена выключены                 |

- Имя — `[a-z0-9_]+(\.[a-z0-9_]+)?`. Другое имя (`{{ Имя }}`, `{{.}}`) — отказ на сохранении.
- **Точка.** Потребитель отдаёт значения плоско (`'field.phone' => '…'`). Перед рендером они
  вкладываются (`field → phone`), как Mustache читает точку. Поэтому `{{field.phone}}` работает
  как раньше, а `{{#field.phone}}…{{/field.phone}}` — как секция по одному полю.
- Тройные скобки и `&` не дают отказа. Шаблон пересобирается из токенов Mustache, и такие теги
  становятся обычными `{{name}}`. Отказ здесь только мешал бы вставке готовых шаблонов, а
  значение всё равно экранируется.
- Шаблон хранится в базе и **никогда не попадает в Blade**. Mustache сам компилирует его в
  PHP-класс из токенов, прошедших проверку; текст шаблона попадает туда только строковыми
  литералами, имена — ключами поиска в значениях.

### 7.2 Списки

Событие объявляет список и поля его элемента (§5): например, позиции заказа с `name`, `qty`,
`price`. Шаблон перебирает список:

```
Заказ {{number}}
{{#items}}
- {{name}} × {{qty}}: {{price}}
{{/items}}
{{^items}}
Позиций нет
{{/items}}
```

- Строка с одной секцией (`{{#items}}`, `{{/items}}`) не оставляет пустой строки — это
  поведение Mustache для «самостоятельных» тегов.
- Внутри секции имя ищется сначала в полях строки, потом в переменных события (как в
  Mustache): `{{number}}` внутри `{{#items}}` — номер заказа.
- `{{items}}` без секции на канале с событием — отказ: «это список, перебирайте его».
- Значения: `send()` принимает список строк (`list<array<string, scalar>>`). Поля приводятся к
  строкам, вложенные массивы в полях — пусто, элемент, который не строка-карта, отбрасывается.
  В журнал (`variables`) список пишется как есть: повтор рисует то же сообщение.
- Готовые переменные потребителя остаются для быстрой настройки (решение 14): `{{fields}}` у
  Inbox — строки «Подпись: значение», `{{field.<name>}}` — одно поле.

### 7.3 Экранирование

Значения экранирует **провайдер** (`Provider::escape`) — он и есть `escape` движка Mustache,
вместо его встроенного `htmlspecialchars`. Поэтому двойного экранирования нет, а текст шаблона
не экранируется:

| Провайдер    | Шаблон                                | Значения                                                                   |
| ------------ | ------------------------------------- | -------------------------------------------------------------------------- |
| Telegram     | HTML Telegram, теги проверены (§6.1)  | `htmlspecialchars(…, ENT_QUOTES)`                                          |
| E-mail, тема | текст                                 | как есть, `\r\n` → пробел                                                  |
| E-mail, тело | текст → HTML при сборке письма (§6.2) | в `text/plain` как есть; в `text/html` экранируется вместе со всем текстом |

Внутри секции действует то же экранирование. Значение, которое само содержит `{{…}}`
(посетитель ввёл в поле), второй раз не раскрывается: Mustache рендерит шаблон один раз, а
значения в шаблон не превращаются.

### 7.4 Проверка при сохранении и неизвестные переменные

`ChannelValues` проверяет тему и тело в каждом языке по порядку:

1. **Синтаксис Mustache.** Незакрытая секция — «Секция {{#items}} не закрыта…». Лишний
   `{{/x}}`, незакрытый тег `{{x`, запрещённое из §7.1 — отказ под полем со словами, что
   исправить (`errors.template-*`).
2. **Имена.**
   - Канал с событием: имя должно быть у события там, где стоит. Внутри секции списка это поле
     списка или переменная события, снаружи — переменная события. Иначе отказ, в словах
     перечислены переменные и поля списков.
   - Если событие позже перестало объявлять переменную, при отправке она пустая, в журнале —
     `unknown_variables: ["…"]`.
   - Универсальный канал: при отправке пустая, в журнале — `unknown_variables`. На сохранении
     отказа нет, но в ответе `warnings`, если имени нет ни у одного зарегистрированного события
     (опечатка).
3. **Разметка провайдера** (`checkTemplate`). Telegram проверяет теги с учётом секций: тег,
   открытый внутри `{{#items}}…{{/items}}`, должен закрыться в ней. Иначе сообщение ломается,
   как только в списке не одна строка или он пуст.

Шаблон, который не проходит шаг 1, не рендерится и при отправке: строка журнала — `failed`. Но
сохранить такой шаблон нельзя, так что это защита на всякий случай.

### 7.5 Редактор

`wx-textarea` (моноширинным) с панелью переменных события под ним: кнопка-чип на переменную
вставляет `{{name}}` в курсор, подсказка — описание и пример. Без события — переменные всех
событий, сгруппированно. Предпросмотр — отрисованное сообщение на примерах (`POST preview`,
§10.5) в рамке «как в Telegram» / «как письмо». `wx-code-editor` не нужен: подсветки HTML для
шаблона из десятка строк мало, чипы важнее.

## 8. Отправка

### 8.1 API для потребителей

```php
use WebxUi\Notifications\Notifications;

app(Notifications::class)->send(
    event: 'inbox.submission',
    channels: $form->notificationChannels(),   // list<int>
    variables: $vars,                          // array<string, scalar|null|list<array<string, scalar>>>
    subject: $submission,                      // ?Model — о чём; ссылка из журнала и «что ушло по заявке»
    locale: $submission->locale,               // ?string — язык шаблона (решение 13)
);                                             // → Dispatch: сколько каналов, сколько строк журнала
```

- Каналы фильтруются: удалённый, выключенный, чужого события (канал с событием `X` при отправке
  `Y`) — строка журнала `skipped` с причиной; универсальный проходит.
- Переменные — строки и списки строк (§7.2); `null` → пусто. Потребитель собирает их **в момент события**: шаблон
  рендерится в задании, но значения уже сняты — правка заявки после отправки письма не меняет.
- На каждого получателя — строка журнала `queued` (§9); затем задание на канал (§8.2).
- `send()` не бросает исключений наружу: потребитель (приём заявки) не должен падать из-за
  уведомлений. Ошибка постановки в очередь — строки `failed` с текстом, лог Laravel.
- `subject` — morph (`subject_type`, `subject_id`) в журнале; тип — алиас морф-карты
  потребителя, `Notifications::deliveriesFor($model)` отдаёт строки по нему (§15.3).

### 8.2 Задание

`Jobs\Deliver` (`ShouldQueue`) — одно задание на канал и отправку, несёт id строк журнала, не
креденшелы (их читает из модели в момент выполнения — смена токена до отправки подхватится).
`$tries = 3`, паузы — `backoff = [30, 120]` с., как у `SendNotice` задач
(`module-tasks/src/Notifications/SendNotice.php:29`); 429 Telegram — `release(retry_after)`.
Соединение и очередь — `config('webx-notifications.queue.connection'|'name')`, по умолчанию
сайта. `afterCommit` — отправка, начатая в откатанной транзакции, не уходит.

Внутри — получатели по очереди: удачный — `sent`, `permanent` — `failed` без повтора, временная
ошибка — остаётся `queued`, `attempts++`, задание повторяется **только для неотправленных**
(решение 8). Последняя попытка — `failed` с текстом ошибки. Исключение задание наружу не
бросает (на `sync` это была бы ошибка запроса посетителя), `failed_jobs` не копится.

### 8.3 Без воркера

Что есть сейчас: скелет `php/site` — `QUEUE_CONNECTION=database` (`php/site/.env.example:42`,
`php/site/config/queue.php:16`), воркер и планировщик — в том же контейнере
(`php/site/docker/supervisord.conf`: `queue:work --tries=3 --max-time=3600`, `schedule:work`;
NEW_SITE §16.1 п. 5–6). Платформенные сайты собраны из скелета — воркер у них есть; dev-копии
(`site up`, шаблоны `webx`/`laravel`) тоже запускают очередь. `afterResponse()` и `dispatchSync`
в пакетах сейчас нигде нет; ветвление «на `sync` — сразу» есть у аудита
(`module-audit/src/Runs/Nightly.php:32-38`, `Http/Controllers/RunController.php:210-215`).

Режим — `config('webx-notifications.queue.mode')`:

- `auto` (по умолчанию): драйвер соединения не `sync` → очередь (§8.2); `sync` →
  `dispatch(...)->afterResponse()` — задание выполняется после отправки ответа посетителю
  (на php-fpm — после `fastcgi_finish_request`), с тремя попытками **внутри одного выполнения**
  и короткими паузами 2 и 5 с (долгий `sleep` держал бы воркер php-fpm).
- `queue` — всегда очередь; `after_response` — всегда после ответа (сайт, где очередь есть, но
  воркер не держат).

Воркер, который стоит (очередь `database`, задания копятся), модуль сам не видит — это видит
доктор (§13) по строкам `queued` старше 15 минут и общий `QueueBacklog`
(`module-admin/src/Doctor/QueueBacklog.php`).

### 8.4 Повтор из журнала

`Notifications::retry(Delivery)` — строку `failed` (и `queued` старше 15 минут — «застряло»)
отправить ещё раз тем же текстом, что сняли значения (§9: `variables` хранятся в строке).
Новая строка не заводится — `attempts` растёт, `status` → `queued`. Панель — кнопка в журнале,
MCP — `notifications_retry`.

### 8.5 «Отправить тест»

Из формы канала (и `notifications_test`): рендер шаблона на **примерах переменных события**
(для универсального — пустые с пометкой), отправка **сразу, синхронно, мимо очереди**, всем
получателям канала или одному выбранному; результат по получателям — в ответе (ошибка — словами
провайдера, токен — `***`). Работает и для выключенного канала, и на несохранённых значениях
формы (креденшелы — введённые или сохранённые). В журнал — строки с `is_test: true`.
Ограничение частоты — 10 тестов в минуту на администратора (`RateLimiter`), чтобы кнопка не
стала спам-пушкой.

## 9. Журнал отправок

```
notifications_deliveries
  id                bigint pk
  channel_id        bigint null index       -- nullOnDelete при удалении насовсем
  channel_name      string(160)             -- снимок: канал могли переименовать или удалить
  provider          string(32)
  event             string(64) index
  subject_type      string(64) null         -- morph (§8.1)
  subject_id        bigint null
  locale            string(12) null         -- язык шаблона (решение 13); null — основной язык сайта
  recipient         string(255)             -- chat_id / адрес; у admin_id — адрес на момент отправки
  recipient_label   string(255) null        -- подпись чата / имя администратора
  status            string(16) index        -- queued | sent | failed | skipped
  reason            string(32) null         -- у skipped: channel_disabled, channel_deleted, wrong_event,
                                            --   provider_missing, admin_inactive, …
  error             text null               -- слова провайдера, без секретов
  attempts          tinyint default 0
  is_test           boolean default false
  truncated         boolean default false
  unknown_variables json null
  variables         json                    -- снятые значения (§8.1); для повтора и «что ушло»
  created_at, sent_at timestamp
  index (subject_type, subject_id)
```

- **Тело сообщения не хранится** — только `variables`: текст восстанавливается шаблоном, а
  повтор (§8.4) рендерит заново (если шаблон поменяли — по новому; так и надо: чинят шаблон и
  повторяют).
- В `variables` — персональные данные посетителей (поля заявки). Поэтому чистка (§9.1) и права
  (§11): журнал видит только `notifications.view`.

### 9.1 Чистка

`webx:notifications:prune {--days=} {--dry-run}` — удаляет строки старше `--days`
(`config('webx-notifications.log.days')`, по умолчанию 90; 0 — не удалять), пачками по 1000.
По образцу `webx:history:prune` (`module-admin/src/Console/PruneHistoryCommand.php`):
планировщик — `->dailyAt('03:50')->onOneServer()->withoutOverlapping()` через
`callAfterResolving(Schedule::class, …)` в провайдере пакета, как
`AdminServiceProvider.php:494-509`. Заявку Inbox удалили (`webx:inbox:prune`) — её строки
журнала остаются до своей чистки (в них снимок, а не ссылка), `subject` повисает — панель
пишет «заявка удалена».

## 10. Панель

### 10.1 Раздел

Раздел «Уведомления» (Notifications), иконка — `bell`, группа `system` («Система», рядом с
настройками и кодами). `WebxUi\Notifications\Panel\NotificationsModule extends AbstractModule
implements ProvidesDemo, ProvidesMcpTools`, `permissions()` — `['notifications.view',
'notifications.manage']` (§11). Вкладки: «Каналы» и «Журнал».

### 10.2 Список каналов

Строка: иконка провайдера, название, событие (бейдж; «любое» — для универсального;
«не объявлено» — предупреждение), получатели кратко («2 чата», «3 адреса»), состояние последней
отправки (`sent`/`failed` с датой — `WxDate`), переключатель `enabled` (пишется сразу; включение
неполного канала — тост с отказом §3.3). Действия: «Изменить», «Создать копию», «Удалить»
(корзина), корзина с восстановлением и удалением насовсем. «Новый канал» — сначала выбор
провайдера и (необязательно) события, затем форма с `sample` события.

### 10.3 Форма канала (экран `notifications.channel`)

Экран JSON (SCREENS), общая часть + части провайдеров патчем при `boot()`, каждая —
`visible: { when: "provider", is: "<key>" }` (условия — SCREENS §7, `docs/architecture/WEBX_UI_SCREENS.md:410-413`):

- `name` — `wx-input`; `provider` — только чтение после создания;
- `event` — `wx-select` из `NotificationEvents::all()`, пусто — «Любое событие»;
- креденшелы провайдера — `wx-input` `type: "password"`, `autocomplete: "off"`; при заданном
  значении — плейсхолдер `••••••••`, подпись «задан, введите новый, чтобы заменить» и кнопка
  «Забыть» (как форма задач: `packages/module-tasks/src/TasksSettingsPage.vue:56-63,115,132`,
  экран `module-tasks/resources/screens/settings.json:10-19`). Отдельного типа поля «секрет» в
  проекте нет — и не заводим;
- e-mail: `mode` — `wx-segmented` «Почта сайта / Свой SMTP», поля SMTP `visible` по `mode`;
  `from_address`, `from_name`;
- получатели: Telegram — узел `wx-notifications-chats` (npm-пакет модуля): список `chat_id` с
  подписями + кнопка «Найти чаты» (диалог с найденными, §6.3); e-mail — узел
  `wx-notifications-emails`: администраторы и адреса, как `FormNotifications.vue` Inbox
  (`packages/module-inbox/src/FormNotifications.vue`), с подсветкой проблем;
- `subject` (e-mail), `template` — редактор §7.5;
- `enabled` — `wx-switch`;
- «Проверить подключение» (`check()`), «Предпросмотр», «Отправить тест» (§8.5, выбор получателя);
- журнал изменений — `wx-history` (креденшелы — маской, §3.2).

### 10.4 Журнал отправок

Таблица (`WxTable`, `->paginate()` как есть): дата, событие, канал, получатель, статус (бейдж),
попытки, ошибка (раскрывается), ссылка на предмет («Заявка #123» — URL из
`EventDefinition::url`), тест — пометкой. Фильтры: канал, событие, статус, период, «без тестов».
Действие строки `failed` — «Отправить ещё раз» (`notifications.manage`). Вне `production` —
`WxAlert` «окружение `<env>`»; уведомления при этом **шлются** (§17, вопрос 10).

## 11. Права и секреты

- `notifications.view` — раздел, список каналов, журнал (с персональными данными заявок).
- `notifications.manage` — создание, правка, копия, тест, поиск чатов, повтор.
- Ни одна роль не получает их при установке; `CmsUser::hasPermission()` пропускает
  суперадмина (`module-auth/src/Models/CmsUser.php:95-102`) — после установки раздел видит
  только суперадмин.
- Выбор каналов у потребителя (§15.2) права модуля не требует: цель выбора
  (`RelationTarget`, §15.2) отдаёт только id, название, провайдер и `enabled` — без получателей и
  креденшелов, как `FormTarget` Inbox (`module-inbox/src/Relations/FormTarget.php`, permission
  `null`). Право на правку формы Inbox — своё (`inbox.manage`).

Где ещё секреты могут утечь и что с этим:

| Место                   | Как закрыто                                                                                                                                   |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| База                    | `encrypted:array` — ключ `APP_KEY`; смена ключа без `APP_PREVIOUS_KEYS` → креденшелы нечитаемы (§13)                                          |
| Журнал изменений        | `$hidden` + `encrypted` пропускаются; маска — `historyMasked()` (§3.2, §14)                                                                   |
| Журнал вызовов MCP      | аргументы `token`, `password`, `credentials` → `[redacted]` по имени (`mcp/src/Calls/Recorder.php:34-36`; `credentials` уже под `credential`) |
| Сериализованное задание | креденшелов нет — задание несёт id (§8.2)                                                                                                     |
| Ошибки провайдера       | токен в адресе Telegram → `***`; SMTP — пароль не попадает в текст `TransportException`, проверяется тестом                                   |
| Ответы API и MCP        | только `credentials_set` (§10.5, §12)                                                                                                         |

Своего трейта «секретные поля» в проекте нет: единственный прецедент — токен задач,
`Crypt`/`StringEncrypter` под отдельным ключом настроек
(`module-tasks/src/Notifications/NotificationSettings.php`), ключи MCP у `module-auth`
показываются один раз и не хранятся вовсе (`module-auth/src/Keys/IssuedKey.php`). Здесь
стандартный cast `encrypted:array` проще и ложится на правило журнала.

## 15. Inbox

### 15.1 Событие `inbox.submission`

Объявляет `InboxServiceProvider` под `class_exists(NotificationEvents::class)`. Переменные
(значения — снимок в момент приёма; примеры обезличенные):

| Переменная       | Что                                                                           | Пример                                        |
| ---------------- | ----------------------------------------------------------------------------- | --------------------------------------------- |
| `form`           | название формы, простым текстом (`Shortcodes::plain`, как в письме)           | `Contact us`                                  |
| `form_slug`      | слаг формы                                                                    | `contact`                                     |
| `submission_id`  | номер заявки                                                                  | `128`                                         |
| `submission_url` | заявка в панели, от `app.url` (не от запроса — одинаково из очереди)          | `https://site.test/cms/inbox/submissions/128` |
| `created_at`     | дата и время приёма, формат языка сайта (`useDates`/`Dates` панели)           | `16.10.2026 14:05`                            |
| `fields`         | все непустые поля строками «Подпись: значение» (§7.2)                         | `Name: Alex\nPhone: +0 000 000-00-00`         |
| `field.<name>`   | значение поля по машинному имени (`Submission::value()`)                      | `field.phone` → `+0 000 000-00-00`            |
| `files`          | имена вложений через запятую (файлы — только в панели, INBOX §8)              | `brief.pdf`                                   |
| `page`           | адрес страницы, с которой пришла заявка (`meta.page`)                         | `https://site.test/contacts`                  |
| `locale`         | язык заявки                                                                   | `en`                                          |
| `utm`            | метки строкой `source=…, medium=…`                                            | `source=newsletter`                           |
| `reply_to`       | значение поля `options.email_field`, если похоже на адрес (для Reply-To §6.2) | `visitor@site.test`                           |

`ip` и `user_agent` не переменные: в мессенджер персональные данные сверх формы не нужны.
`sample` события: Telegram — `<b>{{form}}</b>\n{{fields}}\n\n<a href="{{submission_url}}">Open in the panel</a>`;
e-mail — тема `New submission: {{form}}`, тело — то же текстом.

Ссылку на заявку сейчас письмо строит от `url()` запроса
(`module-inbox/src/Mail/SubmissionReceived.php:208-213`), задачи — от `app.url`
(`module-tasks/src/Notifications/Notices.php:119-133`); переменная — от `app.url`, как у задач.

### 15.2 Поле «Уведомлять через»

- Хранение — `inbox_forms.options.notify_channels: list<int>` (решение 9), чистится
  `FormOptions::clean()`: только целые, без повторов, только существующие каналы (удалённые
  насовсем — выпадают; в корзине — остаются, шлются `skipped`).
- Выбор — механизм webx-ui#12 в множественном виде. В webx-ui#12 сделан одиночный
  `wx-inbox-form` (`packages/module-inbox/src/FormField.vue` на `WxAutocomplete` +
  `createRelationsApi(admin, 'inbox-form')`, цель `module-inbox/src/Relations/FormTarget.php`);
  множественный выбор с поиском уже есть в `module-admin` — `WxRelationsField`
  (`packages/module-admin/src/relations/RelationsField.vue`, экспорт из
  `packages/module-admin/src/index.ts:217`; сервер — `RelationController`,
  `module-admin/routes/web.php:43`, `GET relations/{target}?q=&ids[]=`). Его и берём:
  `FormNotifications.vue` ставит `<WxRelationsField target="notify-inbox-submission" sortable=false>`
  — экраны Inbox — Vue-компоненты, не JSON (INBOX §2.13), поэтому компонент, а не узел экрана.
- Цель — `Relations\ChannelTarget extends RelationTarget` в `module-notifications`, **по одной на
  событие**: при регистрации события регистрируется цель `notify-<событие, точки → дефисы>`
  (ключ цели — `[a-z0-9-]+`, точка в маршрут не проходит). `query()` — каналы этого события и
  универсальные, без корзины; строка — название, подзаголовок — провайдер и «выключен».
- Поле видно, только если модуль уведомлений установлен (`meta` Inbox несёт `notifications:
bool`); рядом — ссылка «Настроить каналы» (если есть `notifications.manage`).
- MCP: `inbox_form_save` принимает `options.notify_channels` (те же правила), `inbox_form_get`
  отдаёт его с названиями каналов.

### 15.3 Когда шлётся

Слушатель `Notifications\SendToChannels` на `Events\SubmissionStored`
(`module-inbox/src/Events/SubmissionStored.php`, `ShouldDispatchAfterCommit`): не `repeated`,
источник `web`, у формы есть `notify_channels` → `Notifications::send('inbox.submission', …,
subject: $submission)`. Это расходится со старым письмом, которое зовёт контроллер приёма
(`module-inbox/src/Http/Controllers/SubmitController.php:110`) **и на повторе в окне дубля**;
каналы на повтор не шлют (§17, вопрос 3).

Карточка заявки — блок «Уведомления»: строки журнала по `subject` (`deliveriesFor`), рядом со
старым статусом письма (`Submission::notification()`). В лог заявки
(`inbox_submission_events`) каналы не пишут — журнал отправок и так привязан к заявке.

`inbox_notify` (`module-inbox/src/Mcp/InboxTools.php:196-239`) и кнопка «Отправить ещё раз» —
повторяют и письмо (как сейчас), и неудачные строки каналов этой заявки (`retry`); новый
аргумент `channels: bool = true`.

Аудит `inbox.no_recipients` (`module-inbox/src/Audit/NoRecipients.php`) считает форму
«уведомляющей», если у неё есть получатели письма **или** включённый канал.

### 15.4 Переход со старых уведомлений

**Что есть сейчас.** Только e-mail: получатели формы — `options.recipients`
(`[{admin_id} | {email}]`), `Mail\Notifier` → `SubmissionReceived` (`ShouldQueue`, шаблон
`webx-inbox::mail.submission` с таблицей значений, файлами, метаданными и кнопкой в панель,

`inbox_notify` и `POST submissions/{id}/notify` — повтор письма; аудит `NoRecipients`,
`NotificationTrouble`. Telegram в Inbox нет (INBOX, «не в модуле», строка 579).

Сосуществование + перевод по кнопке** (рекомендуется) | A, плюс у формы с получателями — «Перевести в канал»: создаётся e-mail-канал «<форма> — письма» с событием, получателями формы и шаблоном-`sample`, форма получает его в `notify_channels`, `options.recipients` очищается — **одной транзакцией**; то же — `webx:inbox:notifications-to-channels {--form=} {--dry-run}` и аргумент MCP | на живых сайтах ничего не меняется, пока человек не решит; перевод обратим (журнал формы); доктор/аудит подсказывают | два механизма до следующего мажора; код старого письма живёт дальше                                                                                                     |

**Решение — A** (решение 11): встроенное письмо остаётся навсегда и работает параллельно с
каналами; перевода по кнопке и команды нет. Ниже — прежняя рекомендация C, для истории. Порядок для живых сайтов: релиз с каналами (старое письмо работает как
было) → администраторы переводят формы, когда хотят → строка аудита `inbox.legacy_recipients`
(«форма шлёт письма по-старому, переведите в канал») как `content`-подсказка → удаление старого
механизма — отдельной задачей, когда на сайтах платформы не останется форм с `recipients`
(проверяется `webx:doctor --json` по сайтам). Колонки `notify_*` у заявок остаются для истории.

## 17. Открытые вопросы — закрыты

Решения — §2, 11–15: вопрос 2 — A; вопрос 6 — (b), переводимый шаблон, язык от события;
вопрос 8 — (b), адресат из события; остальные — по рекомендации. Ниже — варианты, как их
обсуждали.

1. **Креденшелы при копии канала.** (a) переносятся зашифрованными на сервере; (b) не
   переносятся, ввести заново. **Рекомендация — (a)** (§3.4): секрет не покидает сервер, копия
   выключена, форма говорит, откуда токен.
2. **Переход Inbox со старых писем.** A — сосуществование; B — автоматическая миграция; C —
   сосуществование + перевод по кнопке/команде. **Рекомендация — C** (§15.4).
3. **Слать ли в каналы на повтор заявки в окне дубля** (сейчас письмо уходит и на повтор).
   (a) нет — повтор это двойной клик; (b) да, как письмо. **Рекомендация — (a).**
4. **HTML в шаблоне e-mail.** (a) только текст, письмо собирается в рамке (§6.2); (b) HTML с
   белым списком тегов, как у Telegram; (c) Markdown. **Рекомендация — (a)** сейчас: проще,
   безопаснее, `{{fields}}` текстом читается; (b) — когда попросят.
5. **Списки в шаблоне.** (a) готовые переменные `{{fields}}` + `{{field.<name>}}`; (b) простой
   цикл `{{#each fields}}…{{/each}}`. **Рекомендация — (a)** (§7.2). Решено иначе — оба:
   готовые переменные остаются, а циклы — секции Mustache (решение 16).
6. **Язык шаблона.** (a) один шаблон на канал; (b) переводимый шаблон (`HasTranslations`) с
   выбором языка по заявке / администратору. **Рекомендация — (a):** канал — это «куда и как»,
   нужен другой язык — второй канал. Сейчас письмо Inbox пишет администратору на языке его
   панели — при переводе (C) это теряется, сказать в гайде.
7. **Группа стала супергруппой** (Telegram меняет `chat_id`). (a) ошибка в журнале с новым id —
   поменять руками; (b) автоматически заменить id в канале и повторить. **Рекомендация — (a)**
   сейчас: молчаливая правка получателей — сюрприз; кнопка «Заменить на новый id» в журнале —
   дешёвое продолжение.
8. **Уведомления посетителю** («мы получили вашу заявку» на адрес из формы). (a) не в модуле;
   (b) получатель-переменная `{{reply_to}}` в e-mail-канале. **Рекомендация — (a)** в этой
   задаче: это автоответ формы, а не уведомление администратора, и у него свои риски (спам через
   форму на чужие адреса).
9. **Где хранить открытые настройки провайдера** (отправитель e-mail, режим, хост SMTP). (a)
   колонка `options json` у канала, секретное — в `credentials`; (b) всё в `credentials`.

10. **Вне `production`.** (a) шлём как везде; (b) не шлём, кроме теста, как коды вне прода

## 18. Тесты

- Шаблон (Mustache): подстановка, пробелы в скобках, `field.<name>`, неизвестная — пусто +
  `unknown_variables`, значение с `{{x}}` не раскрывается. Список, поля элемента, пустой список,
  `{{#var}}` / `{{^var}}`. Экранирование Telegram и e-mail внутри секции, без двойного. Тройные
  скобки и `&` не выводят HTML как есть. Отказ на partial, смену разделителей, прагмы,
  незакрытую секцию и тег. Неизвестная переменная или список при выбранном событии — отказ,
  `{{items}}` без секции — отказ. Теги Telegram в секции. E-mail: тема без переводов строк.
  Список доходит через журнал и очередь до сообщения.
- Telegram: допустимые/недопустимые теги, обрезка > 4096 → `plain` + `truncated`, таблица
  ошибок §6.1 (`Http::fake`), 429 → `release(retry_after)`, токен не в тексте ошибки.
- «Найти чаты»: разбор `getUpdates` (личка, группа, канал), без `offset`, 409 → слова §6.3.
- E-mail: режим сайта и SMTP (`MailManager::build`), получатели-администраторы (неактивный —
  `skipped`), одно письмо на адрес, `Reply-To`, `multipart`.
- Отправка: очередь — три попытки и только неотправленным; `sync` + `auto` — после ответа;
  `afterCommit`; удалённый/выключенный/чужого события — `skipped`; `send()` не бросает.
- Тест канала: шлёт сразу, мимо очереди, выключенному тоже, лимит частоты, `is_test`.
- Секреты: ни один ответ API/MCP (включая `dry_run` и ошибки) не содержит значения токена и
  пароля — один тест прогоняет все маршруты и инструменты и ищет строку токена; журнал
  изменений — маска; журнал вызовов MCP — `[redacted]`.
- Копия: креденшелы перенесены, канал выключен, `copied_from`.
- Журнал и чистка: `--days`, `--dry-run`, 0 — не удаляет; повтор.
- Доктор: каждая строка §13.
- MCP: каждый инструмент, `dry_run` не пишет и не шлёт, `ToolFailure` §12.2.
- Права: без `notifications.view` — 403; суперадмин — да; цель выбора каналов — без права.
- Inbox: событие объявлено только с модулем; `notify_channels` чистится; заявка → строки
  журнала по каналам; повтор в окне — не шлёт; перевод формы в канал (команда, `--dry-run`,
  транзакция); без модуля — всё как раньше.
