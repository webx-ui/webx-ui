# Релиз и CI: ловушки

Читать, когда PR не мержится или висит в очереди, когда публикация в npm отвечает странно или
«упала», когда php-теги не дошли до Packagist и когда релиз не доезжает до демо-сайтов. Сам порядок
действий — в §5 `CLAUDE.md` и в `docs/architecture/WEBX_UI_PHP_RELEASE.md`; здесь только то, что
в этом порядке ломается и как это выглядит.

## Мерж и очередь

- Было: два зелёных PR давали красный `main` — PHP CI не шёл в очереди. Починено в #398: оба
  PHP-чека обязательны и идут в очереди.
- **`actions/setup-node@v5` падает «Unable to locate executable file: pnpm» в джобе без pnpm.**
  Пятая версия сама включает кеш по полю `packageManager` корневого `package.json` (у нас pnpm).
  Джобе, которой pnpm не нужен (смоук ставит сайт через npm), — `package-manager-cache: false`.
- **`gh pr merge` в очередь мержа не ставит — ни с `--squash`, ни без флага.** Он отвечает «The
  merge strategy for main is set by the merge queue» и пытается включить auto-merge, которого у
  репозитория нет: «Auto merge is not allowed for this repository». PR остаётся `OPEN` и `CLEAN`,
  то есть выглядит готовым к мержу, которого никто не делает. В очередь ставит только
  graphql-мутация `enqueuePullRequest` (см. §5 `CLAUDE.md`); проверять `gh pr view <N> --json state`.
- **`enqueuePullRequest` на свежем PR отказывает, пока не прошёл его собственный CI.** Ответ —
  «Required status check "Lint, typecheck, test, build" is expected», то есть звучит как сломанный
  ruleset, а не как «рано». Дождаться зелёного чека на PR (минуты три), потом ставить; с релизным PR
  то же.
- **Запись в очереди может встать в `QUEUED` с `headCommit: null` и не запустить ничего.** Прогона
  `merge_group` нет, позиция первая, и так она висит сколько угодно — выглядит как медленный CI, а
  CI не начинался. Смотреть `headCommit` у `mergeQueueEntry` через graphql; пустой дольше пяти
  минут — `dequeuePullRequest` и снова `enqueuePullRequest`, после этого сборка стартует сразу.
- **Упавший чек `Lint, typecheck, test, build` — это агрегатор.** Он собирает параллельные джобы
  `ci.yml`; причину смотреть в них, а не в нём. У агрегатора `if: always()` обязателен: без него
  упавший джоб делает его `skipped`, а пропущенный обязательный чек GitHub считает пройденным.
- **Лёгкий CI релизного PR честен, только пока `main` зелёный по построению.** У релизного PR и
  его очереди тяжёлые джобы JS CI пропускаются (`install --frozen-lockfile`, `build` и prettier
  по изменённым файлам — всё, что релизный PR может сломать), а это верно, лишь пока каждый PR
  проверен поверх текущего `main` очередью мержа. Снять очередь — значит вернуть релизному PR
  полный CI.
- **JS CI релизного PR в очереди гоняет lint, typecheck и тесты, как у PR ветки дня, — признак не
  сошёлся.** По времени это не видно: лёгкий путь — одна джоба «Version PR installs and builds»,
  и она сама идёт ~3 минуты (install и полная сборка), почти как полный гейт. Смотреть набор
  джобов, а не длительность. Решает тот же `scripts/release-pr.mjs`, что и в PHP CI: шаг «Is it the version PR»
  джобы «What the change reaches», его `reason=` и выход `light`. Условие на `github.head_ref` не годится: в
  `merge_group` он пустой, и очередь релизного PR гоняла полный гейт. Второй признак не
  заводить — лёгкий путь обеих половин должен включаться и выключаться вместе.
- **PHP CI релизного PR и его очереди — лёгкий путь, но только для PR от App и только с версиями.**
  `scripts/release-pr.mjs` пускает в него, если ветка `changeset-release/main` **и** PR открыл и
  прогон запустил App (`webx-ui-split[bot]`), а в очереди — если каждый сквош группы (`… (#N)`
  между `base_sha` и головой) — такой PR. Дифф при этом — только `composer.json`, `package.json`,
  `CHANGELOG.md`, `.changeset/**`, lock-файлы. Лёгкий путь — тот же джоб: `composer validate`
  манифестов и `php/site` плюс «Versions agree» (`sync-php-version.mjs` ничего не меняет), без
  pint, phpstan и phpunit; обязательные чеки отчитываются как обычно. Симптом «релизный PR снова
  гонит полный PHP CI 7–10 минут» — смотреть строку `reason=` шага «Is it the version PR»: обычно
  PR правили руками, кто-то допушил в ветку (актор не App), в группе очереди есть соседний PR или
  App сменил логин (тогда — `RELEASE_APP` в скрипте). Это не поломка: полный прогон — безопасный
  ответ на всё, что скрипт не доказал.
- **После мержа локальный `main` остаётся старым.** `gh` синхронизирует его через remote по
  умолчанию, то есть `origin`, куда доступа нет: в конце вывода «Could not read from remote
  repository» и «not possible to fast-forward», хотя PR на GitHub уже смержен. Выглядит страшно —
  рабочие файлы будто откатились. Лечится `git fetch claude && git merge --ff-only claude/main`.
- **Релизный PR без CI («no checks reported», `BLOCKED`) — значит, его запушил не App.** Релизный
  PR открывает GitHub App организации, и его CI стартует сам. Если прогон снова встал в
  `action_required` — у App нет права **Pull requests: write** (или его не приняли в установке
  организации); временно `gh api -X POST repos/webx-ui/webx-ui/actions/runs/<id>/approve`, id — из
  `gh run list --branch changeset-release/main`.
- **Красный Release на `main` посреди очереди — если релизный PR стоял в ней не первым.** Каждый
  мерж в `main` запускает Release, и тот пересобирает `changeset-release/main` force-push'ем, а
  ветку PR из очереди GitHub менять не даёт: «GH006: Protected branch update failed … Branches that
  are queued for merging cannot be updated». Похоже на сломанный релиз, но ничего не потеряно, если
  перед ним мержились PR без changeset'ов: собиралось бы то же самое, а следующий Release — на
  мерже самого релизного PR — публикует всё. PR с changeset'ом впереди в этот релиз не попадёт:
  его changeset останется в `main` и уедет следующим релизным PR. Поэтому релизный PR ставить в
  очередь последним, когда перед ним никого нет, и после того, как App пересобрал его на свежем
  `main`.
- **Горячая ветка, на которой продолжили работать после её релиза, снова несёт выпущенные
  changeset'ы.** PR ветки мержится сквошем, а `chore: version packages` удаляет changeset'ы уже в
  `main`; сама ветка этого не видит, и `git diff claude/main..hot` показывает старые
  `.changeset/*.md` как новые — следующий PR выпустил бы их второй раз. Обычный `git merge
claude/main` их тоже не уберёт: от общего предка они «добавлены» только веткой. Лечится мержем
  `main` в ветку (конфликты add/add — где версия `main` равна ветке на коммите прошлого PR, берётся
  ветка; версии — `node scripts/sync-php-version.mjs`; npm-диапазоны в `extra.webx.npm` — из `main`)
  и `git rm` changeset'ов, которые были в ветке на голове прошлого PR (`gh pr view <N> --json
headRefOid`). `sync_with_base_branch` здесь не поможет: он ходит в `origin` с хоста, а ключа к
  нему у хоста нет («fetching main from origin failed»).

## Публикация в npm

- **Первую версию нового npm-пакета публикует человек, а не CI.** Trusted Publishing по OIDC не
  умеет создавать имя, и npm отвечает на публикацию `404 Not Found` — выглядит как опечатка в
  имени, а не как «нет прав». Порядок: ручная публикация (с 2FA, из настоящего терминала), затем на
  npmjs.com у пакета Settings → Trusted Publishing → GitHub Actions (`webx-ui` / `webx-ui` /
  `release.yml`, environment пустой, в «Allowed actions» отмечен **Allow `npm publish`**), и только
  потом релизный PR. Без этой галочки доверенному издателю разрешён только `npm stage publish`:
  версия ждёт ручного одобрения, а `changeset publish` из CI не проходит; `npm dist-tag` не нужен —
  `next` ставится флагом `--tag` при публикации. Настройка доходит не мгновенно:
  первый перезапуск джобы может ещё раз ответить 404, второй проходит. По той же причине **новый
  пакет не выходит и через канал `next`**: снапшот тоже публикует CI.
- **Доверенный издатель привязан к имени файла воркфлоу, а не к ветке.** Поэтому и релиз, и канал
  `next` — джобы одного `release.yml` (`push` и `workflow_dispatch`); вынести публикацию во второй
  файл — значит заводить второго доверенного издателя на каждом пакете, иначе тот же 404.
- **Ручная публикация замораживает диапазоны на версиях «до релиза».** `workspace:^` подставляется
  в момент публикации, а первую версию человек выпускает, когда соседи в чекауте ещё старые. Пакет
  уезжает с диапазоном на каркас, в котором нужного экспорта ещё нет; npm ставит рядом вторую,
  старую копию каркаса, и сборка сайта падает на `[MISSING_EXPORT]`. В монорепе этого не видно —
  там всё резолвится в чекаут. **Публиковать вручную не из `main`, а из ветки
  `changeset-release/main`**, где бот уже проставил итоговые версии: дождаться, пока Release
  обновит релизный PR, снять ветку в отдельный worktree (обычный каталог, не симлинк —
  `pnpm install` там безопасен), положить `dist`, `pnpm pack` и проверить диапазоны в
  `package/package.json` тарбола **до** публикации, а не `npm view` после.
- Было: PHP smoke на релизном PR падал «setup left no package-lock.json» — версий из чекаута ещё
  нет на npm. Починено: сценарий узнаёт релиз в пути и пропускается со списком этих версий.
- **Версия на npm появляется минут через пять после того, как воркфлоу отчитался.** Тег в git
  ставится сразу, регистр отстаёт; проверять `npm view @webx-ui/<пакет> version`.
- **Без changeset'а на ветке канал `next` публиковать нечего.** Снапшот (`gh workflow run
release.yml --ref <ветка>`) берёт только пакеты с changeset'ами и их зависимых; гейта у канала
  нет, пока не передан `-f verify=true`.
- **Снапшот без `"snapshot": { "useCalculatedVersion": true }` в `.changeset/config.json`
  называется `0.0.0-next-<время>`**, и `^0.33.0` у соседей такую версию не примет. С ним —
  `0.33.3-next-<время>`. Проверка на снапшоте — `npm view @webx-ui/<пакет>@next dependencies`.
- **Composer не разбирает `^0.37.1-next-…`,** поэтому `sync-php-version.mjs` на снапшоте не
  запускается: констрейнты между пакетами остаются выпущенными, php-пакеты зеркалятся веткой `next`
  без тега, а сайт просит каждый `webx-ui/*` (с транзитивными) алиасом `"dev-next as <версия>.99"`.
  Packagist подхватывает `dev-next` вебхуком с задержкой около минуты.
- **Dist-tag `next` релиз не сбрасывает** — через неделю он указывает на старое. `packages.mjs next`
  берёт версию `next`, только если она новее `latest`; после настоящего релиза сайт возвращать в
  `registry`.

## Что гоняет CI

PR и очередь проверяют только то, до чего дотягивается правка: решает `scripts/affected.mjs`;
ночной прогон и ручной (`workflow_dispatch`) проверяют всё.

- **После мержа в `main` нет прогонов CI и PHP CI — так и задумано.** На `push` в `main` они не
  запускаются: в `main` попадает ровно дерево группы очереди, которое те же воркфлоу только что
  проверили, а повторный прогон отнимал раннер у Release. «Гниение» (новые версии зависимостей,
  раннеры) ловит ночной `schedule` в 03:00 UTC, smoke (`php-smoke.yml`) — ночной в 04:00 UTC и PR,
  трогающие `php/**`. Нужна проверка `main` сейчас — `gh workflow run ci.yml` / `php-ci.yml` /
  `php-smoke.yml`. На `push` в `main` по-прежнему работают Release, сплит и Docs.

- **У version PR джоба «Install into a real Laravel app» серая (skipped) — так и задумано.** Релиз
  переписывает все `composer.json`, и фильтр `paths` пускает smoke, но код уже прошёл его в PR
  ветки дня. Джоба «Is it the version PR» в `php-smoke.yml` спрашивает тот же
  `scripts/release-pr.mjs`, что CI и PHP CI, и при `light=true` smoke пропускается целиком — чек
  не обязательный, очередь его не ждёт. В очереди мержа smoke не идёт вообще (`merge_group` у
  него нет). Version PR, поправленный руками, получает `light=false` и smoke как обычно.

- **Джоба «No client names» красная — в дереве, коммите или PR имя клиентского проекта.** В
  публичное не пишем ни имён клиентов, ни их доменов, ни путей их сайтов: ни в файлах, ни в
  коммитах, ветках, PR и changeset'ах. Вместо имени — описание: «эталонный магазин», «клиентский
  сайт», демо-данные — вымышленные. Список имён — регулярное выражение в секрете репозитория
  `FORBIDDEN_NAMES` (в коде его нет: сам список и есть утечка); `scripts/check-names.mjs` читает
  его из `WEBX_FORBIDDEN_NAMES` и называет только место, не совпадение — лог CI публичный. Без
  секрета (форк) проверка проходит. Локально — хуки `pre-commit` (`--staged`) и `commit-msg`
  (`--message "$1"`), выражение из файла вне репозитория. Заголовок и тело PR CI проверяет при
  открытии и каждом пуше, а правку описания и имя ветки — нет: их проверять глазами.
- **Обязательный чек нельзя выключать `paths-ignore`.** Воркфлоу, который не стартовал, не
  отчитывается вовсе, и очередь ждёт чек `PHP lint, analyse, test (8.4)` вечно — выглядит как
  зависшая очередь. Пропуск решается внутри джобы: шаги с `if:` пропущены, джоба зелёная. И не
  джобой перед ней через `needs`: если та упадёт, обязательная окажется `skipped`, а GitHub
  считает пропущенный обязательный чек пройденным.
- **Имена обязательных чеков держит ruleset.** Матрица шардов PHPUnit дала бы джобам имена
  `(8.4, 1)`, а ruleset ждёт `(8.4)` и `(8.5)` — очередь встанет. Переименовать джобу — сначала в
  ruleset, потом в воркфлоу.
- **Правку воркфлоу не проверить «частичным» прогоном её же PR.** Изменение в `.github/` или в
  `scripts/affected.mjs` гонит всё — так и задумано. Чтобы увидеть, как новый воркфлоу ведёт себя
  на узкой правке, — черновой PR с этой правкой **в ветку** PR-а с воркфлоу (`--base <ветка>`):
  `pull_request` берёт воркфлоу из головы, а база — та ветка, так что дифф только пробный.
- **Пропущенная матричная джоба называется `Test ${{ matrix.shard }}/${{ strategy.job-total }}`**
  — буквально, потому что матрицу не из чего было развернуть. Это не сломанное имя, а `node=none`.
- **Сборка с `WEBX_SKIP_DTS=1` — без деклараций.** Так собирают тесты и доки в CI (две трети
  `pnpm build` — `vite-plugin-dts`); typecheck, релизный PR и релиз собирают полностью: проверке
  типов нужны декларации зависимостей, и такой `dist` ей не годится.
- **Параллельный PHPUnit (paratest) роняет десятки тестов**, которые по одному зелёные: процессы
  делят один скелет Testbench — `config`, `vite.config`, логи, скомпилированные шаблоны, файлы
  `webx:panel`. Перед paratest — `ParallelTesting::token()` в путях таких тестов.
- Было: правка одного `php/packages/*/AGENTS.md` не гоняла `AgentDocsCoverageTest`, и перерост
  150 строк ловил только `main`. Починено в `affected.mjs`; перед пушем всё равно
  `wc -l php/packages/*/AGENTS.md`.

## PHP-половина

- **Новый composer-пакет с релизом сам не приезжает.** `php-split` зеркалит только репозитории,
  которые уже есть, а вебхук Packagist обновляет только отправленные пакеты: сайт на опубликованных
  пакетах отвечает «webx-ui/<имя> could not be found in any version», хотя тег стоит и changeset
  выпущен. Руками, до мержа релизного PR: `gh repo create webx-ui/<имя> --public`, после мержа
  PR с пакетом — отправить зеркало на Packagist («Однажды настроено» в
  `docs/architecture/WEBX_UI_PHP_RELEASE.md`). Ждёт этого `webx-ui/cache`.
- **Тег php-пакетов ставится до публикации в npm и переживает её падение.** Шаг «Tag the PHP
  packages» стоит раньше changesets нарочно, поэтому упавшая npm-джоба оставляет `php-v<версия>`,
  а зеркалирование пропускает (`needs: release`). Перезапуск не помогает: тег уже есть, шаг выходит
  молча, `php_version` пустой, `php-split` снова пропущен. Лечится ручным запуском:
  `gh workflow run php-split.yml --ref main -f tag=v<версия>`.
- **«Упавшая» npm-джоба не значит неопубликованная.** Changesets публикует все пакеты, а потом
  пушит git-теги параллельно; часть пушей может получить от GitHub `cannot lock ref … reference
already exists` — гонка на самом GitHub, теги при этом созданы все. Джоба красная, `php-split`
  пропущен. Сначала `npm view` и `git ls-remote --tags claude`; если всё на месте — только ручной
  `php-split`, без перезапуска.
- **Composer минут десять не видит новую версию, хотя Packagist её уже отдаёт.** `curl` на
  `repo.packagist.org/p2/webx-ui/<пакет>.json` показывает новую версию, а `composer update` отвечает
  «found … but it does not match the constraint»: его запрос попадает на узел CDN со старой копией
  (`Cache-Control: max-age=900`), и `composer clear-cache` не помогает — дело не в локальном кеше.
  Удалить `~/.cache/composer/repo/https---repo.packagist.org/provider-webx-ui~*` и повторять раз в
  минуту.
- **npm так же минут десять не видит только что опубликованный патч.** Changesets пишет
  `packages published successfully`, `curl registry.npmjs.org/@webx-ui%2f<пакет>/<версия>` отдаёт
  тарбол, а `npm view` показывает старую `latest`, и `npm install <пакет>@<версия>` падает с
  `notarget`: общий документ пакета (packument) на CDN ещё старый, `--prefer-online` не помогает.
  `webx:doctor` на сайте при этом справедливо ругается, что npm-половина отстаёт. Проверять
  `curl …/<пакет> | grep latest` и повторить установку, когда там новая версия.
- **Переписанная история монорепы не доходит до зеркал `webx-ui/<пакет>`, и php-split её не
  исправит.** Экшен сплита не выводит историю зеркала из монорепы, а коммитит копию папки пакета
  со своим сообщением, поэтому старые коммиты зеркала переживают и `filter-repo` монорепы, и
  повторный сплит. Каждое зеркало сканировать и переписывать отдельно той же картой
  (`git clone --mirror`, `filter-repo`, force-push веток и тегов). Ruleset в зеркалах нет, но
  SSH-ключ монорепы туда не пускает (`Permission denied`) — пушить по HTTPS через
  `gh auth git-credential`. Packagist перечитывает force-push'нутые теги по вебхуку за несколько
  минут, после этого `composer update "webx-ui/*"` на сайтах в режиме registry.
- **Файл в `dist/` php-пакета не попадает в коммит, а `git status` молчит.** Корневой `.gitignore`
  прячет любой `dist` (наследство шаблона Node), в том числе `php/packages/*/…/dist`. Так легла
  фикстура пакетной темы в `themes` — открыта строкой `!php/packages/themes/tests/Fixtures/*/dist/`.
  Для настоящей темы (`theme-default`: `dist/` входит в выпущенную версию, §4 спеки тем) это значит,
  что `php-split.yml` зеркалит дерево без `dist/`: собранное надо либо открыть в `.gitignore` и
  коммитить, либо собирать в самом сплите перед тегом. Проверка — `git check-ignore -v <файл>`.

## После релиза: демо

- **Стиль из `@webx-ui/schema/style.css` проверять в CSS-бандле сайта, а не в JS.** Его отдаёт
  `style.css` `module-admin`; проверка правила на сайте — `grep` по `public/build/assets/*.css`:
  класс в JS-бандле есть всегда, правила может не быть.
- **Минорный релиз `module-blocks` на сайте — это и `module-pages`, и `module-blog` следом.**
  Changesets поднимает им диапазон новым патчем, но `npm install` на сайте патч не берёт: прежняя
  версия из lock-файла под старый диапазон подходит. Страницы остаются со своей вложенной копией
  `module-blocks`, `provideBlocksPreview` кладёт ключ одной копии, поле блоков ищет ключ другой — и
  у страницы молча пропадает превью: дерево есть, фрейма нет, ошибок нет. Проверка —
  `npm ls @webx-ui/module-blocks`: строка с версией ровно одна, остальное `deduped`. Лечится
  `npm install "@webx-ui/module-pages@^<новый патч>"` (и блога).
- **`packages.mjs registry` сразу после релиза пишет старые патчи.** Диапазоны он берёт у
  `npm view`, а тот первые минуты после релиза ещё отдаёт прежние версии части пакетов. Сайт
  собирается, но `npm ls @webx-ui/module-admin` показывает вторую, старую копию каркаса под
  пакетами со старым диапазоном, а `webx:doctor` — «npm halves: … needs ^0.8.9». Дождаться, пока
  `npm view` отдаёт новые версии всех пакетов релиза, и переключить ещё раз; проверка — одна
  строка с версией в `npm ls`, остальное `deduped`.
- **`packages.mjs registry --no-install` плюс свой `npm install` оставляет сайт на чекауте.**
  Диапазоны в `package.json` уже реестровые, а `node_modules/@webx-ui/*` — всё ещё симлинки: lock
  держит `file:`-записи, и `npm ls` отвечает `invalid: "workspace:^"`. Переключать тем же скриптом
  без `--no-install` — он чистит lock сам — и проверять `ls -la node_modules/@webx-ui`.
- **Ночной прогон хомлаба свежий релиз не привозит.** Он собирает по закоммиченным манифестам
  (`packages.mjs check` только проверяет, что они не смотрят в чекаут), а каретка на нулевой
  мажорной версии пинует минор — `^0.18.0` до 0.19.0 не доедет никогда. Релиз доходит до хомлаба
  ровно тем коммитом, который поднял диапазоны (`registry`, `composer update "webx-ui/*"`, коммит,
  пуш); ждать ночи бессмысленно. После канала `next` — вернуть сайт в `registry` после настоящего
  релиза.
